## 背景

Rigorは、チェックされていない型の主張を、チェックされた型の主張に置き換えるために存在します。しかし自身の`lib/`には、**1,121件のチェックされていない型の主張**が存在していました — このリポジトリ内のいかなるツールも読んだことのない、角括弧で囲まれた型スロットを持つ720件の`@param`および401件の`@return` YARDタグです。ツールの開発者自身が毎日触れるツリーこそが、最も巨大な未チェックの型の塊でした。まさに「紺屋の白袴」です。

誰もこれを意図して決定したわけではありません。YARDの角括弧はRubyのドキュメントコメントのデフォルトの形状であり、すべてのタグはコードを読んで自分が信じた型を書いた誰か — または何か — によって記述されたものです。それこそがRigorが排除するために作られたアーティファクトであり、その信念は記録されたその日ですら往々にして間違っていました。

2つの読み取り方があり、両方が重要です。34件の戻り値の不一致はドリフトの直接的な測定値です: **281件の戻り値アノテーションの12%が、初めてチェックされた時点で実装と矛盾していました**。他の46件は、中途半端にアノテーションされたツリーの*形状*です — 部分的に宣言されたクラスは未宣言のクラスよりも悪く、これが下記の[#823](https://github.com/rigortype/rigor/issues/823)です。

### モデルは何を書くか、ルールの有無による比較

タグは過去の遺物ではありません。次に書かれるものです。2026-09-08の調査、5つのモデル、**各1サンプル** — 測定ではなく調査（probe）です。フィクスチャは`rigor-type-oracle`スキルの評価フィクスチャとして保持されています。

**ラウンド1 — 模範が存在する場合**（すでに型なしYARDになっているファイル、5つのタスク）: 5/5が角括弧ゼロの型なし形式を模倣した；5/5が明示されたルールに従った；`@param format …`が何の型を述べているか問われた際、5/5が「明記されていない」と答え、代わりに散文の制約を抽出した；5/5がパラメータの改名`format` → `fmt`をタグに伝播させた；5/5が`call-seq`や型単語を捏造することなくRDocスタイルのファイルを模倣した。バッファ内に模範があれば、形式への準拠は容易です。

**ラウンド2 — 文書化されていないクラス、模範なし**。これがルールの配置を決定づけるケースです:

| モデル | `AGENTS.md`内のルール | ルールなし |
| --- | --- | --- |
| Claude Haiku | 型なしYARD | 型付きYARD — `currency [String]`、推測 |
| Claude Sonnet | 型なしYARD | rbs-inline `#:` — `(Regexp?) -> Array[[Numeric, String?, Time]]`、`at: Time`、推測 |
| Claude Opus | 型なしYARD；`@raise`は例外クラスを失った | 散文のみ、RDocマークアップ |
| DeepSeek V4 Pro | 型なしYARD | 型付きYARD — `currency [Object]`、推測 |
| Qwen3.7 Max | 型なしYARD；`@raise [ArgumentError]`と記述 | 型付きYARD — `pattern [Regexp, String, nil]`、推測 |

5モデル中4モデルが促されずに未チェックの型を書きました。契約内にルールがある場合、**5/5が角括弧付きの`@param` / `@return`をゼロ件としました**。両方の逸脱は`@raise`に関するものであり、そのペイロードは値型ではなく例外クラスです。Sonnetのセルが最も尖鋭的です: 製品のデフォルト（[ADR-93](../93-default-rbs-inline-ingestion/)）の下では、これらの`#:`行は生きた契約として取り込まれていたはずです — 推測された型がチェック対象の型へと昇格し、運任せでパスするか失敗するかになるのです。

ルールが届かない残滓: ファイルあたり1つか2つの散文の型単語（「a numeric value」、「an array of entries」）。ゲート不能であり、§ 結果では既知のコストとして扱われます。

## 決定

> **Rigor自身のツリーにおいて、型の記述は厳密に3つの状態のいずれか1つでのみ存在する: Rigorによって推論される（何も書き留められない）、Rigorによって宣言されチェックされる、または存在しない。「ドキュメントのために書かれた」という第4の状態は存在しない**。現実に対してチェックされずに生成された型は、Rigorが排除するために存在するまさにそのアーティファクトである。実装内に1,121件もそれを抱え込むことは、ドキュメントのスタイルではなく、製品のテーゼが自身のソースコードの中で否定されている状態である。

この基準はコメントを超えて一般化されます: *型に関する主張がアナライザーによって生成または検証されていない場合、読者が信頼するような場所にそれを書き記してはならない。* `.rb`のコメントに適用されれば型スロットを禁止します；`sig/`に適用されれば説明のない手書きシグネチャを禁止します；エージェントに適用されれば「周囲のコードを読むのではなく、Rigorに尋ねよ」を意味します。

### 役割: 型が存在できる場所

| 情報源 | 保持するもの | 正しさを担保するもの |
| --- | --- | --- |
| **実装** | 真実 | — |
| **推論** | 第1の型情報源。何も書き留められず、オンデマンドで計算される | 上方にしか動かない精度ゲート`rigor coverage --threshold 0.58 lib` |
| **`sig/`** | 契約: [ADR-2](../2-extension-api/)の公開API境界、および著述された意図 | `make check`、`spec/rigor/public_api_drift_spec.rb`、`make steep-check` |
| **インラインアノテーション**（`#:`, `# @rbs`） | チェックされるドキュメント: `void` / `bot`の意図、名前から推測できない戻り値、公称クラス以上のことを語る型、パラメータの契約 | 製品デフォルトがそれらを取り込み（[ADR-93](../93-default-rbs-inline-ingestion/)）、`make check`がそれらをチェックする；`sig/`が同じメンバーを宣言している場合、`sig/`が勝ち、`:info`がその旨を通知する（[ADR-32](../32-rbs-inline-comment-ingestion/) WD13） |
| **コメント** | 散文のみ — 決して型ではない | `spec/docs/type_shaped_comments_spec.rb` |

`sig/`には[ADR-5](../5-robustness-principle/)の非対称性から導かれる内部的な来歴ルールが存在します:

- **戻り値型は生成される** — `rigor sig-gen`は本体が証明する最も厳格なキャリアを出力し（ADR-5条項1）、ジェネレータはアナライザー自体が拒絶するような厳格化を決して出力しません。唯一の例外は`void`です: これは値が契約の一部ではないと著者が述べているものであり、いかなるシンセサイザーもこれを生成しません — 本体から構築される型は常に最後の式の型であるため、`void`はチェック側でのみ機能します。したがって宣言された`void`は、パラメータ型と同様に意図であり、マーカーを必要としません（[#836](https://github.com/rigortype/rigor/issues/836)）。
- **パラメータ型は著述された意図である** — 推論はそれらを導出せず、ADR-5条項2はそれらを意図的に寛容に保ちます。手書きされたパラメータ型は、そのメソッドが何のためのものかを著者が述べているのであり、これは実装には含まれていない情報です。
- **それ以外のすべての手書きは、記録された推論ギャップである**（単なる好みではない）。[ADR-14](../14-rbs-sig-generation/)に従い、ギャップこそがより価値のあるシグナルです: 手作業で手早く埋めるのではなく、エンジンを拡張することがその対応です。[#825](https://github.com/rigortype/rigor/issues/825)のゲートは、3番目のカテゴリーを仮定ではなく記録されたものにします。そのシード監査（[`docs/notes/20260908-sig-provenance-audit.md`](../../notes/20260908-sig-provenance-audit/)）によると、このカテゴリーは対象となる1,052件の宣言中671件に上ったため、ゲートは671個のマーカーを要求するのではなく、ジェネレータが積極的に矛盾する15件にマーカーを付け、残りをファイル単位で固定しました — そして本ADR自身の予測を覆しました: 15件のうち1件も推論の不完全さによるものはなく、12件は宣言が意図したものよりも推論が*精密*であったことによるものでした。

### コメントは散文を担持する

コメントは、後続のコード行とシグネチャが述べていないことを述べます:

- **理由（Why）** — ADR、issue、偽陽性の境界、試行されたが却下された代替案。
- **型システムが表現できない制約** — 順序、2つの引数間の不変条件、ガードの後にのみ成り立つ境界。
- **ここで`nil`が意味するもの** — 不在、「まだ計算されていない」、および「明示的に空」は3つの異なる事柄であり、型はそのうちのどれが表現可能であるかしか告げません。

コメントが名前、型、またはシグネチャを言い直すことは決してありません。ドキュメントコメントはYARDのタグ文法を使用しますが、型スロットは空のままにします — 文法上オプショナルであるため、これらは有効なタグであり続け、ゲートがチェック可能なパラメータ名のバインディングを維持します — そして名前トークンの後にエムダッシュ（—）を置くことで、パラメータリストを知らなくても名前と散文の境界が可視化されます:

```ruby
# Resolves the receiver's declared shape.
#
# @param node — the call whose receiver is resolved
# @param scope — the enclosing scope; its narrowing facts bind the receiver
# @return nil when the receiver's class carries no declaration at all —
#   distinct from a declaration that resolves to an empty shape
# @raise Rigor::Error — when the environment has no definition builder
def resolve_receiver(node, scope)
```

**なぜエムダッシュなのか（WD）**。 YARDのデフォルト文法では`[Type]`が名前と説明の間の区切り文字でもあり、PHPDocの`$name`シジルも同じ役割を果たします。スロットを空にすると、`@param format the output format`では境界が隠れてしまいます。名前のバインディング（R3ゲートとYARDの未知パラメータ警告の双方が依拠する特性）が維持されるかどうかを確認するため、YARD自身のパーサ（0.9.x）を通じて8つの候補形式がテストされました:

| 形式 | YARDの解釈 | 名前のバインディング |
| --- | --- | --- |
| `@param format desc` | text `desc` | 維持、可視の境界なし |
| `@param format — desc` | text `— desc` | 維持 — **採用** |
| `@param format -- desc` | text `-- desc` | 維持、しかしrbs-inlineの`-- prose`区切り文字であり、`# @rbs format: T -- desc`と1トークン差 |
| `@param format [] desc` | text `[] desc`（空の型スロットではない） | 維持、空の配列と読め、埋めることを誘発する |
| `@param [] format desc` | name `[]` | 破壊 |
| `` @param `format` desc `` | name `` `format` `` | 破壊 |
| `@param format: desc` | name `format:` | 破壊、かつrbs-inline自身の表記 |
| RDoc `format:: desc` | 定義リスト、タグなし | バインドすべき`@param`なし |

エムダッシュはすでにこのコーパスの散文区切り文字であり、型やキーワード引数と誤認されることがなく、いずれにせよYARDのHTMLレンダラーが名前と説明の間に挿入するものです — 唯一の代償はrubydoc.infoがそれを2回表示することです（`format — — desc`）。`@return`は名前を持たず、区切り文字も取りません。ゲートR5は、すべての`@param` / `@yieldparam` / `@option`の名前の後、およびすべての`@raise`クラスの後にダッシュを要求します。

`{Foo#bar}`の相互参照や`@see`は残ります — これらはナビゲーションであり、型の主張ではありません。`@!attribute [r]`はその角括弧を維持します: `[r]`はアクセスモードであり、型ではありません。

### インラインアノテーションはチェックされるドキュメントである

インラインの`#:` / `# @rbs`アノテーションは型の情報源です: 製品デフォルトがそれを取り込み（[ADR-93](../93-default-rbs-inline-ingestion/)）、`make check`がチェックし、`sig/`が同じメンバーを宣言している場合は両方のファイル名を挙げる`:info`とともに`sig/`が勝ちます（[ADR-32](../32-rbs-inline-comment-ingestion/) WD13）。したがって、本ADRが禁止する第4の状態に入ることは決してありません。アノテーションを書くべきかどうかを決定する基準は、コメントルールが適用するものと同じテストです: 名前や周囲のコードが語っていない何かを語っているか？

- 書く価値があるもの: `void` / `bot`の意図（仕様自身のスタイルガイダンスは`#: void`を強く推奨しており、いかなるシンセサイザーも生成できない唯一の戻り値です）；メソッド名が示唆しない戻り値；公称クラス以上のことを語る型 — `Symbol`ではなく`:asc | :desc`、`Hash`ではなくレコードの形状；パラメータの契約。
- ノイズ: 推論がすでに示している公称クラスをすべてのメソッドに列挙すること（`#: String`、`#: Array`）。これは名前を言い直すコメントの型レベルの双子であり、本ADRの初版が全面禁止に手を伸ばした理由です。禁止は間違った手段でした — 仕様が推奨する`#: void`までも削除してしまったからです — したがって基準は品質であり、コメントの品質が判断されるのと同じ方法で判断され、機械的なゲートは`make check`です。

本ADRが書かれた翌日の2つの事実により、禁止は不要になりました: 1つのメソッドのアノテーションがその兄弟の型を書き換えることがなくなり（[#823](https://github.com/rigortype/rigor/issues/823)）、`sig/`との重複がクラスを劣化させなくなりました（[#824](https://github.com/rigortype/rigor/issues/824)）。[ADR-0](../0-concept/)から変わらない真実: このツリーはアノテーションが*必須ではない*ことを実証しており、これは推論に関する主張であって、読者が恩恵を受けるドキュメントを差し控える理由ではありません。

`rigor-type-oracle`スキル（[ADR-108](../108-type-provenance-for-agents/)）はこれによって変更されません: エージェントは依然としてRigorまたは呼び出しサイトの証拠から型を取得し、人間がドキュメントとして書いたアノテーションはチェックが検証する意図であり、エージェントが書き換えるべき推測では決してありません。

### 型を読むことは生成されたビューである

型はバッファの中ではなく、1つのコマンドの先にあります:

| コマンド | 回答するもの |
| --- | --- |
| `rigor annotate FILE` | すべての行の推論された型。`#=> T`として末尾に追加（xmpfilter規約） |
| `rigor type-of FILE:LINE:COL` | 1つの位置における型 |
| `rigor sig-gen --print` | 実装が証明するRBS |

これらのいずれも嘘をつくことはできません。どれも保存されていないからです: 各コマンドは呼び出しごとに実装から再生成されます。それがトレードオフのすべてです — コメントは読むコストがゼロですが何年も古い可能性があります；生成されたビューはコマンドのコストがかかりますが、古くなり得ません。

## 不変条件が浮き彫りにしたエンジンの課題

ADR-14に従い、著者に手書きを促すギャップはエンジンに関する情報です。実験は2つの課題を生み出し、両方ともissueとして起票されました:

- **[#823](https://github.com/rigortype/rigor/issues/823) — 部分的なアノテーションが兄弟を劣化させる**。 1つのメソッドがアノテーションされているクラスにおいて、アノテーションのない兄弟は`master`上で`untyped`なシャドウになり（または#779のバリアントではメソッドが欠落する） — 上記の85件の診断のうち44件を占める`call.undefined-method` + `call.wrong-arity`のペア。兄弟が着地すべき状態は「存在するとして宣言され、推論によって型付けされる」です: アノテーションは指名したメソッドに対して契約を追加すべきであり、指名していないメソッドを降格させるべきではありません。
- **[#824](https://github.com/rigortype/rigor/issues/824) — 同じメソッドに対する`sig/`とインラインアノテーションの間の優先順位**。現在、衝突はクラス全体を`Dynamic[top]`に劣化させます。#779のバリアントは代わりにインライン宣言を黙って取り除きましたが、これは2つのダイアレクトが一致しない場合、沈黙こそ回避すべき失敗であるという[ADR-32](../32-rbs-inline-comment-ingestion/) WD12のルールに違反します。

両者とも下記の「自ツリー内でのチェック対象rbs-inline」という代替案の前提条件であり、それが即座に却下されるのではなく延期された理由です。

## 却下された代替案

| 候補 | 敗れ去った理由 |
| --- | --- |
| **RDoc規約**（`name::`リストを伴う`== Parameters:`） | 標準ライブラリネイティブであり十分に学習されているが、約3.2万行のMarkdown風味のコメントを変換することはマークアップの移行であってコメントパスではない；ゲートすべきパラメータ名バインディングがない；そして`:call-seq:`自体が散文の中の型スロットである。調査が示すように、モデルは*模範があれば*喜んでRDocを模倣するが、模範がなければ事前の知識から型付きYARDや`#:`に手を伸ばしてしまう（ラウンド2）。決定的な点: RDocには機械的に検出可能な失敗モードがない。角括弧こそが検出器である。 |
| **本ツリー内でのチェック対象rbs-inline**（`# @rbs`を維持し、取り込みゲートをオフにする） | 製品仕様と整合的であり、#779が求めたものの誠実なバージョン。現時点では成立しない: #823により部分的にアノテーションされたクラスは未アノテーションのものより悪化し、#824は既存の`sig/`に対する優先順位ルールを持たない。また、それを実証している唯一のツリーにおいてADR-0のテーゼを逆転させることになり、パラメータ側に対するRigor自身の回答は呼び出し元の観察（ADR-14 `--observe`）であってアノテーションではない。ユーザーのプロジェクトは別の問題であり、ADR-93が有効である。**2026-09-09差し替え**: #823と#824は翌日にクローズされ、上記の修正によってインラインアノテーションはドキュメント基準の下で認められる。 |
| **YARD→RBSシンセサイザープラグイン経由で型付きYARDをチェック対象にする** | モデルの事前分布と一致するため準拠コストは低い。しかし、チェックをたまたまパスした*推測された*型が契約を暗黙に狭めてしまう — Sonnetの`Regexp?`のケースは誰も選んでいない本物のパラメータ契約として出荷されていたはずである。また、まず#823を必要とし、34件の`Rigor::Type?`不一致の原因となった「非公式な型言語」問題を再移入してしまう。 |
| **Rubyコアスタイルの散文のみ**（タグを一切使わない） | 正準であり、最も学習された形式。しかしゲートすべき`@param`名バインディングがなく、コアスタイルの散文は文の中で型を記述する（「Returns a new Array」） — したがって§ 結果がすでに受け入れている暗黙の残滓は大幅に大きくなり、それを測定する手段もなくなる。 |
| **取り込みゲートを維持する**（`.rigor.dist.yml`の`require_magic_comment: true`、すなわち#779を出荷する） | 最悪の組み合わせ: 製品自身の構文による、製品自身のツリー内のアノテーションを、製品が読まないように設定する。チェックされているように見える。ゲートがオンの間、85件の診断のすべてが不可視であった。 |

## 結果

利点:

- 1つの検出器を持つ1つのルールが、すべてのセッションが読み込む契約内に一度だけ記載され、そのセッションが終了した後に強制されます。調査はこのルールが機能することを示しています: 5モデル中4モデルが促されずに未チェックの型を書きましたが、ルールが存在すれば5モデル中0モデルになりました。
- `lib/`内の1,121件の未チェックの主張が、スタイル変更されるのではなく消滅し、実装と積極的に矛盾していた34件が暗黙のうちに復活することはできなくなります。
- 44件のダックタイプタグが判断パスを経て散文となり、`[#call]`以上のことを述べるようになりました — rbs-inlineへの変換が捨て去っていたはずの情報です。
- 「これは何の型か？」に対する参照先が、食い違い得る3つの情報源ではなく、単一のアドレス（`rigor annotate` / `type-of` / `sig-gen --print`）になります。

欠点:

- **ゲートに見えない残滓**。ファイルあたり1つか2つの散文の型単語が生き残ります（「a numeric value」、「an array of entries」）。角括弧は形状ですが、文は形状ではありません。ルールはそれらをカバーするように明記されていますが、ゲートはそうではありません。
- **型を読むのにコマンドが必要になる**。見慣れないファイルをざっと読む人間にとって、これはよく維持された型付きコメントに対する実質的なリグレッションです — そして全体の賭けは、1,121件のタグと12%の矛盾率が示すように「よく維持された」などというものは存在しないということです。
- **不変条件は承認された当日に完全にゲートされていたわけではない**。 G2とG3の両方がその後に着地しました: #827での`--fail-on=warning`、#835での`sig/`の来歴。§ ゲートが各々の担保するものを名指ししています。
- **このツリーは、Rigorが導入プロジェクトに指示している内容と意図的に乖離している**。 ADR-93はインラインアノテーションを契約と定めていますが、ここでは禁止されていました。乖離は#823/#824によって境界づけられており、どちらの方向にも「修正」すべき矛盾と解釈されないよう記録されています。
- **YARDのレンダリングされたパラメータ型が失われる**（このツリーからYARDドキュメントを生成する人にとって）。今日そうしているコンシューマーはいません。

持ち越し: #823および#824（エンジンの課題）、およびG3のシード監査が浮き彫りにした3つの`sig-gen`の課題（ノート内の§「提案されたissue」）。#822は**changelogフラグメントを担持しません**（[ADR-105](../105-pr-landing-flow/)）: 差分はPrismのコメント行のみに触れており、すべてのファイルの非コメントバイトストリームは変更されておらず、ユーザーに影響するものはありません。

## 他のADRとの関係

- **[ADR-0](../0-concept/)** — 「アプリケーションのRubyコードはRigor専用のアノテーション構文を持たないままである」。本ADRは同じ基準をRigor自身のコード、およびADR-0が許可している隣接する構文に適用します: 推論優先の型付けを実証するツリーは、推論によって型付けされるべきです。
- **[ADR-5](../5-robustness-principle/)** — `sig/`の来歴ルールを提供します。戻り値は条項1によりアナライザーの仕事となるため生成されます；パラメータは条項2により著者の仕事となるため著述されます。
- **[ADR-14](../14-rbs-sig-generation/)** — 親ポリシー。§「著述ポリシーとその理由」はすでに`sig-gen`の優先を述べており、ギャップこそがより価値のあるシグナルであるとしています；本ADRは同じルールを`.rbs`から`.rb`のコメントへと拡張し、ゲートを追加します。その矛盾ルールは、34件の戻り値不一致がコメントではなく`sig/`にあった場合に裁定されていたルールです。
- **[ADR-32](../32-rbs-inline-comment-ingestion/) / [ADR-93](../93-default-rbs-inline-ingestion/) / [ADR-94](../94-rbs-inline-reader-and-the-rbs-3x-floor/)** — 製品のインライン取り込み契約であり、変更されません。ここでの除外はこのリポジトリにスコープされており、#824はADR-32 WD12の沈黙ルールがすでに予測していた優先順位の問題です。
- **[ADR-57](../57-self-call-return-adoption/)** — 85件の診断が読み取られた裁定プロトコル: 各発火を分類し、アーティファクトを根本で修正し、残差に決定させます。#823と#824がその残差です。
- **[ADR-97](../97-adr-index-budgets/)** — 異なるサーフェスにおける同じ基準: 強制されないドキュメントルールは観測可能な真実ではなく、ゲートは決定へのフォローアップではなく決定の一部です。4ヶ月で3回の手動スイープは、本ADRにおける`db8d01bf`です。
- **[ADR-73](../73-skill-driven-user-experience/) / [ADR-81](../81-skill-set-optimization/)および[ADR-108](../108-type-provenance-for-agents/)** — 出荷されたスキルのサーフェス。ADR-108は製品レベルでの一般化を担います: 同じ「周囲を読むのではなくツールに尋ねよ」ルールが、`rigor-type-oracle`スキルと、導入プロジェクトがそれとともに継承する契約として表現されます。
- **[ADR-105](../105-pr-landing-flow/)** — なぜ#822が`changelog.d/`フラグメントを持たないか（§ 結果）。
