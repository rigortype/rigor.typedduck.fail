ステータス: **Accepted、2026-11-01、K = 64**。[#2564](https://github.com/rigortype/rigor/pull/2564)で実装済み。以下のプロトタイプ測定は、`a53b68c4d`上で環境変数切り替えのプロトタイプと参照パッチを用いて取得した。この作業は[#2520](https://github.com/rigortype/rigor/issues/2520)をクローズし、[#2521](https://github.com/rigortype/rigor/issues/2521)および[#2522](https://github.com/rigortype/rigor/issues/2522)をオープンとして残す（WD4）。

根拠: [`inference-engine.md`](../../internal-spec/inference-engine/)の#2104の箇条書き。[#2516](https://github.com/rigortype/rigor/pull/2516)、[#2524](https://github.com/rigortype/rigor/issues/2524)、および[#2558](https://github.com/rigortype/rigor/pull/2558)で修正されたメモキーの不具合。

## コンテキスト

calleeミューテーションフロア（callee mutation floor）は、ローカルリテラルが渡されたcalleeがそれを書き換える可能性があるとき、そのリテラルのシェイプファクト（shape fact）をドロップする。それを判定するために、各パラメータのハンドオフグラフ（hand-off graph）をウォークする。ノードは、1つのオーナーコンテキスト下における1つのdefの1つのパラメータである。ウォークはパラメータあたり最大`MAX_NODES`（32）ノードを読み取り、打ち切り時点で未読のままのノードはミューテーションされたものとしてカウントされる（#2516）。その解釈は保守的だが、広い読み取り専用のファンアウト（#2520）で真陽性を失う: 40個の純粋なリーフに渡されたリテラルがフロアされてしまう。

明白な修正は、確定した答えのメモである。各ノードの答えを永続化するウォークであれば、後のウォークは予算を消費せずにそれをスキップできる。そのプロトタイプ（V1/V2）はmasterに対してアロケーションが−0.43%となり、64ノードの予算で#2520の診断を取り戻した。しかし、それは*新しい（fresh）*ノードに対して予算を課金するため、ウォークの答えが同じファイル内の以前のウォークが何を永続化したかに依存してしまう。例: `a(x)`が`x`を70個のリーフに渡し、`b(x)`が同じリーフのうち40個に渡すとする。`a`を先にウォークすると`a`の引数はフロアされる。`b`を先にウォークすると`a`には30個の新しいリーフしか残らず、予算内に収まるため、`a`の引数はフロアされない。すると同じ呼び出しが、あるファイルでは報告され、別のファイルでは報告されないことになる。

このサブシステムは1か月で3つのメモキーの不具合を抱えており、いずれも順序依存の偽陽性であった: シングルトン側、型付きレシーバーメモにおける呼び出し元の定数ナローイング、およびdefごとのセンサスメモにおける同じナローイングである。4つ目の、履歴に依存する不具合は誤った方向である。

測定された2つの事実が設計を形作る（`lib/`、`--no-cache --workers 0`）:

- **グラフは小さい**。27,980個の（root, parameter）ウォーク全体で、すべての到達範囲の和集合は22,340ノードである。最大の到達範囲は400ノードであり、64ノードを超えて到達する純粋なウォークはわずか130個である。
- **訪問自体はコストではない**。上限なしのウォークでも、上限32と比べて訪問数は16%しか増えない。コストは新たに到達したdefに対する`compute_forwarding_edges`であり、約2.0Mオブジェクト、実行全体の4.8%を占める。遠いdefに到達するすべてのファイルがこれを毎回支払うことになる。センサスメモとエッジメモがファイルの`DiscoveryIndex`をキーとしているためである。したがって、それらは実行ごとではなくファイルごとになっている（`ScopeIndexer.index`がファイルごとに新しいものを構築する）。

## 決定

**基準: calleeフロアにおけるメモ化された答えはそのキーの関数であり、予算はグラフが定義する量のみをカウントし、以前のウォークが何をしたかは決してカウントしない**。仕様はフロアをパラメータフローグラフの性質として記述し、実装はその性質の任意の計算となる。

パラメータ`r`に対する性質: **`r`がフロアされるのは、def自身がミューテーションしないノードを経由して`r`から自身のミューテーション（own-mutated）ノードに到達可能であるか、またはK個より多くの異なるノードが`r`から到達可能である場合、かつその場合に限る**。打ち切りがミューテーションとしてカウントされるため、これはmasterがすでに意味していることと一致する。変更点は、どの入力も訪問履歴に依存しないことである。

### WD1 — ウォーク

パラメータごとに、ウォークローカルの`seen`セットを用いた幅優先探索を行う:

- ノードが最初に発見されたときに、そのノードをカウントし、自身のミューテーションをチェックする。
- 最初のown-mutatedノードで*ミューテーションあり（mutated）*として停止する。
- K個より多くのノードが発見されたとき、*打ち切り（cut）*として停止する。その場合、フロンティアのエッジは一切計算されない。これがコスト削減の源泉である。
- 到達範囲を探索し尽くしたとき、*ミューテーションなし（not mutated）*と答える。

最小不動点が到達可能性であるため、収束ループ（settle loop）は不要である。フロアの答えは幅優先順やエッジ順に依存しない。変化しうるのはラベル（正確な答えか打ち切りか、そしてそれによる`BudgetTrace::CALLEE_CHAIN_CAP`のカウント）のみである。**K = 64**。

### WD2 — 永続化されるもの

グラフのファクトのみ:

- def自身のセンサス（`def_census`、ASTのみ、すでにファイル間で共有されている）;
- 転送エッジ（`resolved_census(:edges)`、すでにメモ化されている）;
- 新しい後続ストア`def → owner-or-context → name → [callee, name, owner, …]`。

後続ストアはdiscoveryをキーとする`RunScopedSlots`スロットであり、`hand_off_memo_bypassed?`（定数ナローイング、またはアクティブな依存関係レコーダー）の下ではバイパスされる。ウォークの結論は一切永続化されない。closureは現在（discovery, side, class, def, K）の関数であるため、defごとのclosureメモは維持される。永続キャッシュフォーマットの変更はない。

キーは完全である。ウォークが読み取るすべての入力は、defノード、センサス種別、discovery、環境（実行あたり1つ）、self型のsideとclass、定数ナローイング（バイパス対象）、またはレコーダー（バイパス対象）である。字句的ネスティングは、いずれの定数が型付けされるよりも前にクラス名から上書きされる。ルート化された`::K`アームはネスティングを読み取らない。

### WD3 — 順序依存性は機械的に捕捉する

- **メモ監査モード（Memo-audit mode）**。`BudgetTrace`のようなspecおよびCI専用のスイッチ。`resolved_census`、`hand_off_memo`、後続ストア、および`def_census`のすべてのヒット時に値を再計算し、格納された値と等しいことをアサートする。これにより、それを露呈する順序を見つけ出す必要なく、入力を取りこぼしたキーを発見できる。#2516および#2524の不具合はどちらもこれで失敗していたはずである。CIはこれをcallee specおよび`rigor check --no-cache --workers 0 lib`上で実行する。
  不一致はスレッドごとのリストにも保持され、ランナーが各ファイルの後にそのファイルのクラッシュ行へ排出するため、型付けパス上の`rescue StandardError`に飲み込まれた不一致であっても実行を失敗させる（#2785、ADR-129 WD5）。すべてのファイルの解析外で発生したものは実行の最後に失敗させる。
- **順列spec**。敵対的プログラム（#2516と#2524のプローブ、ファンアウト、上記のウィットネス）を、ファイル内のすべてのdef順序、異なるファイル名順序、および`workers: 0`と`workers: 2`の下で実行し、単一の診断セットとなることをアサートする。
- **`CalleeMutationChain`に対するプロパティテスト**。ランダムな小さなグラフ上で、答えが参照性質と等しく、ストアを共有する事前のウォークに対して不変であることを検証する。
- **`callee_chain_mutation_spec.rb`の上限例**を`K + 9`のチェーンに書き換える。

### WD4 — 継承されたdefとオーナーを切り替えるdefは引き続きフロアされる

これらは`FLOOR_ALL`を維持する。これらをウォークするには、現時点でモード非依存に利用できない2つのものが必要である:

- 定義クラスのネスティング。`discovered_def_nestings`は存在するが、アイデンティティをキーとしておりキャッシュスナップショットに存在しないため、これを使用すると`--incremental`と`--no-cache`が不一致になる（#2522）;
- 祖先を通じたインスタンス側のself呼び出し解決。

ノードキー（def, owner, name）は両方のアイデンティティを運ぶオーナーをすでに対応できるようになっているため、それらが着地すれば#2521はこのADRの上に構築される。

### WD5 — 仕様テキスト

#2104の箇条書きにある「幅優先で最大32ノードを読み取り、打ち切り時点で未読のままのノードはミューテーションされたものとしてカウントしなければならない（MUST）」は、K = 64のグラフの性質になる。また、`CALLEE_CHAIN_CAP`はラベルをカウントするため順序によって変化しうる一方、フロア自体は変化しないことも明記する。

## 却下された代替案

| 代替案 | 却下理由 |
|---|---|
| 新しいノード予算による確定済み答えメモ（プロトタイプV1/V2） | 答えがウォーク履歴に依存し（上記の`a`/`b`のウィットネス）、それを仕様として記述できないため。 |
| 上限なし | アロケーション+1.87%: 遠いdefに到達する各ファイルがそのエッジを再計算してしまう。 |
| discovery全体に対する事前SCC単位の先行パス | すべての実行ですべてのdefのエッジを計算するため、決してフロアしないプロジェクトでもコストを支払い、同じKで精度も向上しない。 |
| SCC単位の予算 | エッジコストを制限できず、再帰を過剰にフロアする。 |
| 到達セットまたは到達サイズ合計の永続化 | 順序非依存だが、ダイヤモンド形状で過剰に打ち切るかメモリを消費し、そもそも訪問自体はコストではない。 |
| 出次数または深さの上限 | まさに#2520のファンアウトを打ち切ってしまう。 |
| ファイル間で共有されるエッジメモ（プロジェクトシードをキーとする） | 真のコスト削減レバー（推定−1.4%）だが、教科書的なキー完全性のリスクがある: ファイルごとのテーブルが勝ち、エディタバッファが乖離する。WD3の監査モードでガードできるようになるまで先送り。 |

## 結果

- **正の影響:**フロアはファイル内順序、ファイル間、ワーカー分割、およびキャッシュモード全体を通じて構築上順序非依存となる。`lib/`での測定: masterに対してアロケーション−0.12%（K = 32なら−0.42%、K = 128なら+0.24%）。打ち切られるウォークは645から130に減少する。`lib/`、kramdown、およびhamlの診断は同一であり、#2520の両フィクスチャは診断を取り戻す。
- **負の影響:** `lib/`上の130個の純粋なウォークはK = 64でも引き続きフロアされる。`CALLEE_CHAIN_CAP`のカウントは順序間で安定しなくなる。コストは#2516以前の水準（`b48ed7393`）より約0.3ポイント高いままとなる。K = 48であればほぼ同水準になるが、フロアされるウォークが約276に増加する代償を伴う。
- **繰り越し事項:**監査モードが存在するようになった後の、ファイル横断エッジメモ（上記で却下）。#2522およびインスタンス側の祖先self呼び出しの後の#2521。読み取りのみを行う継承されたdefがリテラルを保持するかどうかについての別途の決定（現在はウォーク対象; `approval-queue.d/callee-floor-lexical-owner.md`を参照）。
