**ステータス:** Accepted — record-and-validateの実行キャッシュがランディングした。単純な解析前フィンガープリント（fingerprint）は却下された（`pundit_plugin_spec`のクロスプロセス退行テストによって不健全（unsound）であることが実証された）。健全（sound）なrecord-and-validateの設計が実装・検証済みであり、変更のないMastodonの`app/models`（248ファイル）は11.6秒→1.8秒（約6倍）に短縮し、診断（diagnostics）はバイト単位で同一、`make verify`はグリーン。

`rigor check`は、プロジェクトに何も変更がない場合でも、呼び出しのたびに**ファイル単位の推論全体**を再実行する。永続キャッシュ（`.rigor/cache`、ADR-6）は中間成果物のみ——RBS環境とプロデューサーごとのプラグインテーブル——をコンテンツアドレス指定の`Cache::Descriptor`をキーとして保持するが、解析の**結果**はキャッシュしない。そのため、全ファイルに対する`CheckRules.diagnose`——ADR-44のプロファイリングで計測したアロケーションバウンドな処理で、ウォームな実行では壁時計時間の~90%以上を占める——は、バイト単位で同一の結果を再現するためにフルコストを支払う。GitLabの設定済みサブセット（2,630ファイル、11プラグイン）では「何も変わっていない」と知るだけに~100～150秒かかる。

このADRは、変更のないプロジェクトの全結果をキャッシュから提供するファストパスを設計し、自明な実装が健全でない理由を記録する。

背景：[`docs/notes/20260604-gitlab-plugin-contribution-allocation.md`](../../notes/20260604-gitlab-plugin-contribution-allocation/)のプロファイルと[ADR-6](../6-cache-persistence-backend/)のキャッシュアーキテクチャ。

## コンテキスト——実行の診断が依存するもの

1. **解析された各ファイルの内容**。
2. **他の解析済みファイルの内容**——クロスファイルのユーザーメソッド戻り値推論（`infer_user_method_return`）：`B#foo`を呼び出すファイルAは`B#foo`の*推論された*戻り値の型を採用し、それは`B#foo`の**本体**に依存する。解析済みファイルの変更はどれも別のファイルの診断を変更しうる。
3. **プラグインが読み込むファイル**——そして*いつ*読み込むか。`prepare`中に読み込まれるものもある（rails-routesの`config/routes.rb`、actionpackのコントローラー）。**他のものはファイル単位の解析中にオンデマンドで読み込まれる**。`rigor-pundit`は`authorize`呼び出しを初めて見たときにポリシーファイルを読み込み、ポリシーがそのアクションを定義しているか確認する——つまりプリパス後、`analyze_files`の途中で読み込まれる。そして、プラグインが探して**見つけられなかった**ファイルもそうだ: `db/schema.rb`を探して何も得られなかったプラグインは、その不在に基づいて結果を形作る——符号が反対の依存関係である（WD1）。
4. **RBS環境**——`Gemfile.lock`のgemセット、`sig/`ファイル、`rbs`のバージョン、`target_ruby`。
5. **設定**——`severity_profile`、`disabled_rules`、`plugins`、`paths`、`exclude`、`pre_eval`、`--explain`など。
6. **エンジン**——`Rigor::VERSION` / キャッシュスキーマ。

## 決定

### 却下——解析前フィンガープリントをキーとする実行全体キャッシュ

最初の実装（プロトタイプ後に差し戻し）は、診断の計算を`Cache::Store#fetch_or_compute`でラップし、**プリパス後に**以下から構成した`Cache::Descriptor`をキーとした：解析済み全ファイルのダイジェスト、RBSディスクリプタ（gems + sig）、各プラグインの`io_boundary.cache_descriptor`、`Configuration#to_h`のダイジェスト、および`Rigor::VERSION`。

基本的な健全性チェックは通過した（変更なし→バイト同一の診断でヒット；エラーを修正→ミス→新鮮な結果）。しかし、**`spec/integration/plugins/pundit_plugin_spec.rb`のクロスプロセスのキャッシュ無効化退行テスト**に失敗した。このテストはまさにこのハザードに対する標準的なガードである：

> `archive`**なし**でポリシーを書く→`rigor check`が`authorize :archive`呼び出しをフラグする；`archive`**あり**でポリシーを書き直す→2回目の`rigor check`（新しいプロセス、同じキャッシュ）はフラグを**立てていけない**。

フィンガープリントはプリパス直後に構築されるが、Punditはポリシーファイルを`analyze_files`の**最中に**（`authorize`呼び出しごとに）読み込む。そのため、フィンガープリント構築時点ではポリシーの読み込みはまだ発生しておらず、解析対象ファイル（`demo.rb`）は変更されておらず、フィンガープリントは両方の実行で同一になる→2回目の実行は古いヒットになり、修正済みの呼び出しを再報告する。**解析前に計算されたフィンガープリントは、解析自体が発見する入力を捕捉できない**。これを出荷すると編集をまたいで偽陽性（false positive）が生まれる——正確性ツールとして最悪の障害モードである——ため却下する。

### 採用済み（ランディング）——依存関係のrecord-and-validate

健全なモデルは順序を逆転させる：**実行し、実際に読み込んだすべての入力を記録する；その依存集合（dependency set）とともに結果をキャッシュする；次回の実行では、記録された依存関係を再読み込みして検証する**。

- **キー：**実行前に安定して判明している——解析パス*セット* + 設定ダイジェスト（`Configuration#to_h`）+ gems（`RbsDescriptor`のgem/configエントリー）+ `Rigor::VERSION` + `--explain`。ファイルの追加/削除はパスセットを変更→新しいキー；ファイルの編集はキーを保持し検証によって捕捉される（つまりコンテンツの編集は同じスロットを再利用——キャッシュが肥大化しない）。
- **保存値：**`[diagnostics, dependency_descriptor]`。ディスクリプタの`files`は実行**後に**収集される——解析済みファイル + RBSの`sig`ファイル + 各プラグインの`io_boundary.cache_descriptor`（Punditポリシーのような解析時読み込みを含む完全な実行後の情報。そしてWD1以降は、プラグインが探して見つからなかったパスも含む）。`Diagnostic`はフラットな値オブジェクトなので、ペアは`Marshal`クリーンである。
- **ルックアップ：**`Cache::Store#fetch_or_validate`は安定したキーのエントリーを読み込み、`Descriptor#fresh?`を呼び出す。これは記録された全`FileEntry`を再ダイジェストし、すべてが一致する場合のみ**ヒット**（不一致なら→ミス→再実行→同じスロットを上書き）。最初の実行後にポリシーが依存集合に含まれるため、Punditポリシーを捕捉できる。

実装が強制するロバストネスの2つのルール：**キャッシュが実行を絶対に壊してはならない**——書き込み時のシリアライズ/ディスク障害は飲み込まれ（キャッシュをスキップ）、キャッシュパスエラーはいずれもキャッシュなしの直接解析にフォールバックする；そして実行後の依存関係収集は各プラグインの`@io_boundary`を遅延`||=`初期化子をトリガーせずに読み込む（プラグインインスタンスは実行後にフリーズされており、境界を構築しなかったプラグインはそれを通じてファイルを読み込んでいない）。ファストパスは順次実行・書き込み可能キャッシュ・非エディタ・非プリビルドの実行にのみ適用される；キャッシュヒット時は`nil`のstatsを返す（要約するはずだった解析は実行されなかった）。

検証済み：変更のないMastodonの`app/models`（248ファイル）は**11.6秒→1.8秒（約6倍）**に短縮；`fix-an-error → 0 errors`（古いものなし）；`pundit_plugin_spec`のクロスプロセス退行テストとプロデューサーごとのキャッシュテスト（rigor-routes、rigor-rbs-inline）はパス；`make verify`グリーン。

### WD1（ランディング、#577）——不在もまた依存関係である

着地した時点でのrecord-and-validateの集合は、**成功した**読み取りだけを記録していた: `IoBoundary#read_file`は読み取りがバイトを返したときに`FileEntry`を追加し、raiseしたときには何も追加しなかった。ファイルを探し、見つからず、その不在に基づいて結果を形作るプラグイン——`db/schema.rb`が欠けているときのrigor-activerecordの縮退モード（#569）——は、したがって、そのファイルが後に現れても無効化するためのエッジを何も残さなかった: ウォームな実行は、他の記録された入力が動くまで、縮退したインデックスと今や偽になった「スキーマが見つからない」という開示を提供し続けたのである（#576のレビューで発見。帰属のプローブは、この陳腐化のクラスが#576より前から存在することを示した）。逆向きの編集——実行が読んだファイルを削除する——はすでに捕まえられていた。記録された読み取りの行が、ファイルが消えた時点で古いものとして読まれるからだ。この依存関係の集合には、その負の半分が欠けていた: *この解析はXが不在であることに依存していた*、という半分が。

修正は、その負の半分を同じサーフェスで記録する。パスが存在しないために失敗する`read_file`（`Errno::ENOENT`、または親の構成要素が通常ファイルであるときの`Errno::ENOTDIR`）は、再raiseする前に**不在の行**——`FileEntry.absent(path:)`、値`"false"`を持つ`:exists`の比較器——を記録する。他は何も動かない: ランナーの実行後の依存関係ディスクリプタも各プロデューサーの依存関係ディスクリプタも、どちらも境界の`cache_descriptor.files`から構築されるので、この1つの記録点が実行全体のエントリーとプラグインのプロデューサーのエントリーの両方をカバーし、`Descriptor#fresh?`はすでに`:exists`の行を検証していた。不在の行は`File.exist?`1回で検証される——statのタプルもダイジェストも、変更のないツリーでドリフトしうるものは何もない——ので、ウォームな実行からヒットを奪うことは決してない。

3つの境界がこの記録を意図的なものに保つ。それが発火するのは「そこにない」という結果に対してだけだ: 存在するが読めないパス（`EISDIR`、権限の失敗）は、プラグインが報告する失敗であって存在の探索ではないので、従来どおり何も記録しない。信頼された読み取りのスコープの内側でだけ発火する。ポリシーの検査が読み取りに先行するからだ。そして1つの境界の内側では、あるパスの内容の行が不在の行によって置き換えられることは決してなく（1回の実行で1つのパスに2つの結果が出るということは、解析の足下でファイルが動いたということであり、内容と存在の両方を検証がカバーするのは内容の行のほうだ）、一方で探索の後の読み取りの成功は不在の行を置き換える。`SCHEMA_VERSION`は7 → 8: 8より前のエントリーは不在の行を運んでおらず、まさにこれが閉じる編集をまたいで新鮮だと検証してしまうので、マーカーの規律がそれを退役させる。

ゲート: `spec/integration/plugins/activerecord_plugin_spec.rb`のrigor-activerecordのウォーム実行のフィクスチャ——スキーマなしのコールドの実行、`db/schema.rb`の追加、そしてキャッシュをオンにしたままウォームな実行が再解析すること（`unknown-column`が発火し、開示が撤回される）。スキーマを削除する逆向きのケース（記録された読み取りによってすでに健全）と、変化なしの対照（何も変わっていないウォームな実行は依然として提供される）がその隣に並び、境界・ディスクリプタ・ストア・プロデューサーキャッシュの各半分はそれぞれ自身のユニットスペックで固定されている。

### WD1b（ランディング、#613）——プローブもまた読み取りである

WD1は`read_file`の時点で不在を記録したが、これは*読み取りを試みて失敗した*プラグインをカバーする。すべてのプラグインが読み取りを試みるわけではない: 一般的な形状は、まず`File.file?` / `File.directory?`プローブで読み取りをゲートする（`return nil unless File.file?(config/sidekiq.yml)`、`next [] unless File.directory?(app/models)`）が、`File`を通じたプローブは何も記録しない。したがって、WD1がまさに書かれた対象のプロジェクト——ファイルが欠けているプロジェクト——では読み取りが決して発生せず、不在の行も記録されず、ウォームな実行は出現前の結果を提供し続ける。記録点は正しかったが、サーフェスは1呼び出し分遅すぎた。

WD1bはプローブ自体を境界へ移動させる。`IoBoundary#file?(path)`および`#directory?(path)`は`File.file?` / `File.directory?`が返すものを正確に返し、その答えを`:exists`行として記録する: プローブが求めたものを見つけた場合は`FileEntry.present`、そこに何も存在しない場合は`FileEntry.absent`、そこに何かが存在するが求められたものではない場合は何も記録しない（WD1が`EISDIR`に対してピン留めした境界のプローブ形式）。境界管理下のプロジェクトパスに対するすべてのプラグインプローブはこれらに変換される。ただし1つの名前付き例外を除く: rigor-actionpackの`Analyzer`テンプレートプローブ（`locate_template`、`abstract_base_controller?`）は境界を保持せず、`render`ごとに多くの候補パスを試すため、それらの変換はカーディナリティの決定待ちである（#629）。存在の行は存在のみを検証する: 同じパスでディレクトリが通常ファイルに置き換えられた場合（またはその逆）、述語は異なる答えを返すようになるにもかかわらず、新鮮なままと判定される——これは境界であり、現実的なプロジェクト編集ではない。

2つの呼び出しは意図的な設計である。述語はすべてのパスに対して忠実に答え、決して例外を発生させない——信頼された読み取りスコープの外側でも同様であり、そこでは何も記録しない: プラグインコード内の素の`File.file?`を置き換えるものであり、例外を発生させたり、存在するスコープ外のパスに対して`false`を返したりする述語は、記録するものだけでなく変換されたプラグインが*行うこと*を変えてしまうことになり、これは偽陽性優先のルールの下では誤ったトレードオフである。そして、読み取りが続くプローブは直後に`:stat`コンテンツ行によって置き換えられるにもかかわらず、存在の行は記録される: 読み取りが続か*ない*プローブ——globされる探索ルート、その存在だけでモードを切り替える設定ファイル——こそが、まさにファイルシステムへの他のエッジをまったく持たないものである。

`SCHEMA_VERSION`のバンプはなし: WD1bは行の種類、comparator、および値の文法を追加しない——`:exists` / `"true"`はすでに構築可能であり、すでに1回の`File.exist?`で検証され、すでに`COMPARATOR_STRICTNESS`でランク付けされていた。バンプがもたらす唯一の利点は、WD1とWD1bの間に書き込まれた、プローブ行を持たないエントリーを退役させることである;それらはサイクル途中の開発者の`.rigor/cache`にしか存在しない。なぜなら`SCHEMA_VERSION` 8はリリースで出荷されておらず、リリースされたすべてのキャッシュは7以下であり、どちらにせよ次のアップグレードでミスするからである。

ゲート: 変換されたプラグインごとのWD1の3フィクスチャパターン——rigor-sidekiqの`config/sidekiq.yml`プローブとrigor-activestorageの探索ルートプローブ。それぞれ実ディスク上の実際のStoreに対して実際のRunnerを通じてコールド → 追加 → ウォームで駆動され、さらに変化なしの対照と、ヒット後に削除する逆向きのケースを含む。

### WD2（ランディング、#1507）——2つ目のライター: `--incremental`セッション

上記のスロットは、すべてのファイルを解析した実行によって書き込まれる。ウォームな`rigor check --incremental`は決してそうではないため、[ADR-87](../87-null-build-floor/) WD4のエンジンフリープローブはそれを辞退し、変更のないプロジェクトは何も変わっていないと知るためにインクリメンタルパスの固定コスト全体を支払っていた: Mastodon（約1,400ファイル）に対するCIでは、デフォルト実行の0.29秒に対して`--incremental` null実行は1.43秒 ── エンジンのロードに343ミリ秒、スナップショットの読み取りに273ミリ秒、その依存先インデックスの再構築に123ミリ秒、空のクロージャに対する環境の構築に160ミリ秒、ディスカバリーとダイジェストに約190ミリ秒である。

WD2はインクリメンタルセッションを2つ目のライターとする。スナップショットを永続化するすべての実行の後、`IncrementalSession#run_incremental`は実行の診断（CLIがベースラインフィルターの前に出力するリストであり、#1524によってフル実行の順序でのフル実行のリストとなった）をそれ自身のレコードアンドバリデートスロットに記録し、`rigor check --incremental`はエンジンをロードする前にそこからnull実行を提供する（`Analysis::IncrementalRunSlot`）。同じ実行に対してフルパスが出力する`--incremental warm`バナーも伴う。

**キー**。WD4が設定のみから再構築するもの（`RunCacheKey`: `rbs.virtual_rbs`を含まないライブラリリスト、`template-units`スロットなし、`--explain` false）に、解析ルートを加えたものであり、独自のプロデューサーIDである`analysis.incremental-run-diagnostics`の下に置かれる。ルートはファイルから暗黙的に定まるものではない: `extra`が存在しない場合の`--incremental lib extra`は`--incremental lib`が解析するものを解析し、前者のみが`extra`の欠落を報告する（素のキーにも同じギャップがある、#1559）。キーはそれらを絶対パスに正規化してソートした状態で保持するため（そこでは`lib`、`./lib`、および`lib/`は1つのルートである）、それらを並べ替えた実行でも依然として前のスロットのチェーンを見つけることができ（それらを同様にソートするスナップショットフィンガープリントが依然として復元するのと同様）、綴りを変えた実行は隣にスロットを追加するのではなくスロットを置き換える。エントリーはそれらを実行に与えられたとおりに保持し、同じ順序で同じように指定した実行にのみ提供される: 欠落したルートは書かれたとおりに報告され（`./extra`は`extra`ではない）、`b a`が`b`のファイルを先にリストするのに対し、`--incremental a b`は`a`のファイルを先にリストする。プロデューサーIDとルートエントリーの双方が、それ単体でも2つのスロットを互いに分離するため、どちらのプローブももう一方のエントリーを読み取ることはできない。

WD4のキーが省いているスロットのいずれも必要とされない。合成されたRBSバッファは、解析されたファイルのバイト列（検証された行）と、合成を行うプラグインのアイデンティティおよび設定（キーの`configuration`、ロックファイル、およびエンジンスロット）の関数である。テンプレートユニット（#392）は、そのテンプレートのバイト列と変換が読み取った他のすべてのもの、変換自体、および合成バージョンの関数である: テンプレートファイルと要求されたglobごとの1つのリスト行が行であり、変換のその他の読み取りはプラグインの境界を経由し、プラグインとエンジンはキー内にある。したがって、あらゆるRailsアプリケーション上でrigor-actionpackが行うように、プラグインがテンプレートglobを要求するプロジェクトも提供される;素のプローブは、素のキーがコンパイル済みユニットのダイジェストを運ぶため、それに対してミスする。

**ディスクリプタ**。絞り込まれた再チェックはそのクロージャのみを読み取った;その回答の残りは以前の実行によって計算されたものである。行は3つのソースから生じる:

1. 解析されたファイルごとに1つの`:stat`行。セッションがそのファイルに対して保持しているダイジェスト ── キャッシュから提供されたファイルについては、そのキャッシュされた行の計算元となったバイト列 ── からパックされ、バイト列は依然として一致するがタプルが移動した場合（`touch`、チェックアウト）には現在のstatに対して再パックされるため、後のプローブはそれを再ハッシュするのではなくstatする。再パックはファイルを新たにハッシュ化し、変更検知が読み取ったバイト列を記述する実行ごとのメモからは決してハッシュ化せず、そのハッシュの後にパックするタプルがその前に取得されたものである場合にのみ行われる。実行後の再ダイジェストは、実行が読み取りを行っている最中に変更されたバイト列を保証してしまうことになる。
2. すべての実行が再度読み取り、そこから回答を再導出するもの（`Runner#incremental_slot_rows`）、2種類。実行が読み取ったとおりに取得されるもの: すべてのプラグイン`IoBoundary`行であり、その中にはプロデューサーが計算したか提供されたかに関係なく#1558が境界へリプレイする各プロデューサーの`watch:` globが含まれる。実行終了時に取得されるもの: テンプレートファイルとglob（実行ごとに再解析）、および解析ルートごとと`pre_eval:`エントリーごとの存在行。素のスロットは存在行を記録しないが、インクリメンタルパスは実行ごとにパスエラー行を再生成するため、それを取り消す編集を越えてエラー行を提供したスロットは、ツリーのいかなる実行も出力しないものを出力してしまうことになる。これらはWD1bの境界条件を運ぶ。
3. スロットの値が前方へ引き継ぐ**チェーン**。そのベースライン部分は、再チェックが再導出**しない**入力に対してフル実行が記録するもの（`Runner#baseline_dependency_rows`）である: シグネチャツリー（`RbsDescriptor.file_entries` / `.glob_entries`）と、設定されたまたは自動検出された`sig`のシグネチャルートごとの存在行;発見されたが解析されていないファイル（#684）とディスカバリールートごとのリスト行;および解析対象セット外の`pre_eval:`ファイル。その読み取り部分は、解析された各ファイルに帰属するプラグインの読み取りである: `Runner#analyze_file`は依存関係を記録する際、各ファイルの解析を`Plugin::IoBoundary.attributing`でラップする。フル実行がチェーンを開始する;再チェックはベースライン部分を変更せずに引き継ぎ、再解析した各ファイルの読み取りを今回の実行のもので置き換え、削除されたファイルのものを破棄する。

ベースライン部分を再計算するのではなく引き継ぐことは意図的である。再チェックは空のクロージャ上で環境を再構築することもディスカバリーを拡張することもなく、スナップショットフィンガープリントは設定された`signature_paths:`のみをダイジェストし（#1554）、セッションは解析されたファイルのみを追跡するため（#1560）、それらの入力のいずれかへの変更は、フルパスがその変更前に計算された行を提供し続ける状態を残す。再計算した場合、次のスロットはその古い回答を保証してしまうことになる;引き継ぐことで、プローブは次のフル実行まで辞退する。

読み取りは、その解析がそれを生じさせたファイルに帰属し、境界が記録した読み取りのみが帰属する。プラグインがメモ化した値 ── ivar内、`producer_value`経由、またはADR-84戻り値メモによってファイル間を運ばれるもの ── は、後続のファイルに独自の読み取りなしで到達するため、読み取りをトリガーした最初のファイルのみがそれを保護する。独自のレコードアンドバリデートエントリーから回答されたプロデューサーは何も読み取らないが、#1558以降、自身のエントリーが記録した行を自身の境界へとリプレイし、`IoBoundary#replay`はライブの読み取りが行うのと同様にそれらの各々をシンクへ渡し、保持された行が勝った行も含まれる。ファイルが解析されている間に最初に尋ねられたプロデューサー（rigor-actionpackの`:controller_index`、rigor-rails-i18nの`:locale_index`）は、そのファイルに自身の入力を帰属させる;その帰属がないと、ファイルごとのループ中にリプレイされる行によって`Runner#incremental_slot_rows`が辞退し、そのようなプロジェクトに対してスロットが書き込まれることは決してなくなる。ミス時、リプレイされるディスクリプタは境界全体のものとなるため、ファイルにはプロデューサーが読み取った以上のものが帰属し、これはスロットをより早く辞退させる方向にのみ働く。

**実行が読み取ったツリーに対してのみ書き込まれる**。スロットの一部は実行が終了したときにツリーから読み取られる: 解析されたファイルの行（フル実行はファイルを解析した後にダイジェストする）、項目2が終了時に取得する行、およびフル実行のベースライン行である。実行が読み取りを行っている最中に着地した保存 ── エディタ、`bundle install`、`mkdir` ── は、解析が見ていないツリーをそれらが保証してしまうことになる: 環境が構築された後に保存されたシグネチャファイル、mtimeを維持したまま置き換えられた提供済みファイル、実行が欠落を報告した後に作成された解析ルート。再チェックの引き継がれたベースラインも別の形で同じリスクを持つ: 空でないクロージャを持つ再チェックはシグネチャツリーを再度読み取り、それが読み取った保存が実行終了前に元に戻された場合、引き継がれたすべての行が新鮮なまま残ってしまう。そのため、セッションは実行が何かを読み取る前にマークを取得し（`IncrementalRunSlot::WriteGuard`）、書き込み時に、引き継がれたか取得されたそれらの行のいずれもがその後に移動していない場合にのみ書き込みを行う: 内容行が指定するファイル、glob行がリストするディレクトリ、およびstatモードglobがマッチするファイルのいずれも移動していないこと。存在行はそのパスが存在するかどうかのみを尋ねるため、マークはそのような行が指定しうる各パス（解析ルート、`pre_eval:`エントリー、シグネチャルート）が存在するかどうかを記録し、その後にパスが現れたり消えたりした場合に行が移動したとみなされる。そのディレクトリの変更時刻は尋ねられない: パスの隣で作成および削除されたエディタのロックファイルはそれを動かし、それによって拒絶された再チェックは次のフル実行までチェーンを壊したまま残してしまう。実行内に現れて再び消えるパスがその境界条件である。マークが記録しなかったパスの存在行は、それ自身の変更時刻、またはその最も近い既存の祖先の変更時刻にフォールバックする。プラグインの読み取りとして取得された行はガードを必要としない。後の保存はその行を陳腐化させたまま残すためである。

キーにも同様の配慮が必要である: 実行終了時に計算され、その唯一のファイル入力はロックファイルである。したがってガードは、キーまたはスナップショットフィンガープリントが読み取る可能性のあるすべてのロックファイルも監視する: マーク時に存在していたものはその変更時刻がマーク前である状態で依然として存在しなければならず（これはロックファイルが書き換えられたり、削除されたり、書き換えられて元に戻されたりした場合──ダイジェストでは実行開始時のバイト列と区別できない──を拒絶する）、マーク時に存在しなかったものは依然として存在してはならない。呼び出し元は実行が開始する前にスナップショットフィンガープリントを計算するため、その間にロックファイルや設定されたシグネチャファイルが変更された場合、実行が復元するスナップショットが1つのツリーでキー付けされ、実行は別のツリーを読み取る状態になってしまう。したがってマークはフィンガープリントも再計算し、それが移動していた場合はマークを取得しない。

マークはその目的のために書き込まれたファイルの変更時刻であるため、ファイルシステム自身のクロックから読み取られる。変更時刻（ctime）は修正時刻（mtime）とは異なり、`cp -p`や`touch -d`によって戻すことはできず、マーク自身のファイルシステム上では粗いティックによって編集が隠されることはない: マークのティック内の変更はそのマークの後としてカウントされる。このルール単体では、実行の直前に着地した保存を拒絶してしまう。粗いファイルシステム（ext4、tmpfs）はそれに最初のスタンプ自身の変更時刻を与えるためである。したがってマークはティック境界で取得される: スタンプは、最初のスタンプよりも後の変更時刻を保持するものが現れるまで（同じデバイス上で）書き込まれ、その後の変更時刻がマークとなる。実行前の保存は最大でも最初のスタンプの変更時刻を保持するため許可され、マークの後の保存は少なくともマークを保持するため拒絶される。待機は有界であり（50ミリ秒）、その中でティックしないファイルシステムはマークを取得しない: スロットは書き込まれず、これは常に安全である。1つのクロックは1つのファイルシステムを必要とするため、マークはストアがプロジェクトのファイルシステム上にある場合にのみ取得される。別のファイルシステム上の行は、それを特定するものによって決定される。プロジェクト自身のシグネチャルート外のシグネチャファイルは、キーによってすでに特定されている: エンジン独自のもの（`data/`、バンドルされたプラグインの`sig/`、gemオーバーレイ）はエンジンスロットによって、gemの`sig/`および`rbs collection`ディレクトリはロックファイルによって。それらはエンジンやgemがインストールされている任意の場所、コンテナイメージのレイヤーやNixストアに存在するため、別のファイルシステム上ではガードはそれらを読み飛ばし、マークのファイルシステム上では他の行と同様にそれらをチェックする（`Runner::BaselineRows#pinned`）。別のファイルシステム上の他のすべての行は書き込みを拒絶する。チェックアウトの場合、エンジンスロットはエンジンのRubyソースのみをピン留めするため、チェックアウトがプロジェクトとは別のファイルシステム上にある場合、実行が読み取りを行っている最中に寄与者がバンドルされたシグネチャファイルを編集することはガードの対象外となる。ガードが見ることができないのは、実行中にクロックが逆行すること（NTP補正、ネットワークファイルシステムのサーバー）であり、これによりマーク前の保存の日付が付けられる可能性がある。ガードは尋ねられたときにもう1回スタンプを取得し、それがマークより前を読み取った場合（または書き込めない、あるいは別のデバイス上にある場合）は拒絶するため、実行終了前に元に戻されない限り逆行は検知される。その他の境界条件: 最初のスタンプが丸1秒に着地するファイルシステム（HFS+、FAT、ext3）は即座にマークを取得しない;ネイティブWindowsはマークを取得しない（そこでは変更時刻は作成時刻であるため）;ネットワークまたはFUSEファイルシステム（NFSの属性キャッシュ、virtiofs、sshfs）は保存前の変更時刻を報告することがあり、それを検知するものは何もない。実行が読み取ったとおりに記録された行はマークまで引き下げられた記録時刻を運ぶため、粗いクロック上では、読み取り後の同じサイズの保存は、動いていないstatタプルで信頼されるのではなく再ハッシュされる。したがって、ライターの実行中に保存されたプラグイン読み取りファイルはレーシーなままであり、そのリーダーが再解析され行が再記録されるまで、各プローブで再ハッシュされる;コストはそのようなファイルの数によって制限され、回答は正しいままとなる。

**なぜチェーンが維持されるのか**。それを開始したフル実行からの帰納法による: その実行のディスクリプタは素のスロットのものであり、各再チェックのディスクリプタは、再解析したファイルについては今回の実行の読み取りを、提供したファイルについては前のスロットの読み取りを運ぶ。これは、前のスロットが再チェックが復元したスナップショットを記述している場合にのみ成り立つ。スロットが欠落している場合（退避、削除、書き込まれなかった）、または別の実行がスロットを書き込まずにスナップショットを書き換えた場合（ワーカーの読み取りがそれらを記録するプロセスに決して到達しないプール実行;ストアを持たない`--incremental --no-cache`;失敗したスロット書き込み）、これは成り立たない。そのため、スロットはその実行が残したスナップショットファイルのアイデンティティ ── `(size, mtime_ns, ctime_ns, inode)`;保存は新しいファイルを適切な場所にリネームする ── を記録し、再チェックは、存在し復元したスナップショットファイルを指している前のスロットからのみチェーンを引き継ぐ。それ以外の場合は何も書き込まず、次のフル実行が新しいチェーンを開始するまで高速パスは無効のままとなる: プールまたは`--no-cache`の編集実行後、書き込みガードが捕捉した保存、新しいチェックアウト（新しいinode）上に復元されたキャッシュ、スナップショットフィンガープリントが見ないロックファイルの変更（#1532）、または2つの実行の競合の後。`Runner#incremental_slot_rows`は、ファイルごとのループ中に境界行が変更されどのファイルにも帰属しなかった場合（プラグインが開始したスレッドからの読み取り）にも辞退する。

「次のフル実行まで」は無期限を意味しうる: フル`--incremental`パスは、そのフィンガープリントが移動したとき（設定、ロックファイル、設定された`signature_paths:`、エンジン）またはスナップショットが消失したときにのみフル実行を開始し、プローブが提供を停止したからという理由で開始することは決してない。連鎖した入力が変更された後（後述）も同様である。安価なフォローアップとしては、前のスロットのチェーンがそのベースライン部分で検証を通らなくなったとき、またはチェーンを引き継げなくなったときに、セッション自体がベースラインを実行することが考えられるが、ここでは構築されていない。

**書き込まれず、提供もされないもの**。エディタバッファ（決して永続化されない）、プール実行、エフェクト収集（その`effects:`ブロックはキーの外にあり、そのエンベロープ行は#428の辞退である）、不透明なプラグイン（その次回のフルパス実行は、プローブが代行するウォーム実行ではなくコールド実行となる）、または実行後にセッションが解析された一部のファイルに対するダイジェストを保持していない実行に対しては、スロットは書き込まれない: #1536のソースRBSゲートはクロージャが決定された後に保存されたファイルのダイジェストを忘れ、そのリーダーが何から計算されたかをどの行も語れなくなるためである。スロットはそれ以外の点ではそのゲートのクロージャ決定に依存しないため、信頼されていないゲート下の実行は書き込まれる。CLIがプローブに尋ねるのは素の`--incremental`のみである: `--no-cache`、`--verify-incremental`、ワーカープール、`--coverage`、`--cache-stats`、`RIGOR_*_TRACE`プローブ、または`--explain`（セッションはまだ尊重せず（#1533）、したがってキー付けされたスロットを書き込まない）は対象外である。ヒットは通常のcheckのものではなく、インクリメンタルの末尾を出力する（`CheckCommand#write_incremental_result`）。

`Runner#run_result_cacheable?`は依然として記録実行およびサブセット実行を除外するが、その理由は本スロットには及ばない: 記録実行はグラフを記録するために解析しなければならず、サブセット実行の部分的な回答はフル実行のキーを共有してしまうためである。セッションは記録後に、マージされた完全な回答を独自のプロデューサーIDの下で書き込む。ヒットはスナップショットを読み書きしない: すでにスナップショットをそのまま残しているnull再チェック（ADR-87 WD3）を代行するため、次回の編集実行は復元するはずだったものを復元する。

**ヒットが保証するもの**。ヒットは、スロットを書き込んだ実行が出力したものを正確に出力し、記録されたすべての行が検証を通る間だけ出力する。行は、フルインクリメンタルパス自身の変更検知が見るすべての入力をカバーしている ── 解析されたファイル、設定、キー内のルートとロックファイル、シグネチャツリー、および境界が記録する各プラグイン読み取り（これがADR-88のファクトサーフェスの出所である） ── そのため、フルパスが変更に気付いて再解析する場所では、プローブが先に辞退する。これは、プラグインがその`IoBoundary`を通じて読み取りを行うというADR-45自体の前提、およびヒット時にプロデューサーの行をリプレイする#1558に依拠している;それ以前は、プロデューサーの入力が変更された際に、フルパスがプロデューサーを再計算してリビルドする一方で、プローブが変更前の回答を提供してしまう可能性があった。WD2が#1558の後に着地したのはそれが理由である。

ヒットはコールド実行と等しいことを保証するものではない。フルパスが変更を見逃す場所では、2つのことのいずれかが発生する。チェーンが引き継ぐ入力（#1554の自動検出された`sig/`、#1560の発見されたファイル、解析対象セット外の`pre_eval:`ファイル）について、プローブは次回のフル実行まで辞退する一方で、フルパスはその古い回答を提供する。別のファイルに帰属したプラグイン読み取り、またはメモを通じてファイルに到達したもの（#1553）について、プローブはフルパスが提供するのと同じ古い回答を提供する ── 同等性であり、それ以上ではない。

Mastodon上でローカルに測定（macOS、`tool/engine_warm_ab.rb`によってインストールされたgemとして配置されたエンジン）。スイープ設定（`data/oss-sweep/mastodon-rigor.yml`、1,404ファイル、テンプレートを要求するプラグインなし）では、`--incremental` null実行は0.94秒から0.18秒へと短縮され、デフォルトのnull実行の0.17秒と同水準になった。サーベイ設定（1,328ファイル; `app/views/**/*.erb`を要求するrigor-actionpack、および他の9つのRailsプラグイン）では、すべてのnull実行が提供され、2.49秒から0.28秒へと短縮された（デフォルトのnull実行は素のキーの`template-units`スロットがWD4のプローブの回答を妨げるため1.1秒かかる）。その設定の編集実行は、#1574のため、両方のエンジンでコールドである。スロットの書き込みコストは、スイープ設定では実行あたり17〜20ミリ秒、サーベイ設定では48〜62ミリ秒であり、ガードが11〜13ミリ秒を占め、残りが6,348のファイル行からなる0.5 MBのエントリーを構築して書き込む。CIの数値は`engine-warm.yml`のディスパッチで確認される。

ゲート: `spec/rigor/analysis/incremental_run_slot_spec.rb`（各入力クラス、ルートとその綴り、引き継がれた読み取り、フル実行まで辞退する入力、チェーンの切断、2つのスロットの分離、キャッシュヒットを通じたプロデューサーの入力、ノードルールから最初に尋ねられたプロデューサー、テンプレートユニット、および書き込みガード: 保存、ルートの作成または削除、ネストされたシグネチャファイルの削除、および実行が読み取りを行っている最中に書き換えられた設定済みロックファイル、および別のファイルシステム上の行）、`spec/rigor/cli/run_cache_probe_spec.rb`内のサブプロセス例（ヒット時に`rigor/inference`なし）、`spec/rigor/cli/check_command_spec.rb`（フォーマット、ベースライン、および`--fail-on`ごとの同一の出力）、および`tool/engine_warm_ab.rb`（`--incremental` nullプローブヒットをカウントし、エンジンをロードしなかった編集実行を失敗させる）。

### 付随機能（ランディング）——検証ゲートはキャッシュプルーフ

結果キャッシュは、プロジェクト自身のゲートが古い結果を読み込むことを絶対に許してはならない。フィンガープリントはエンジンコードを意図的に除外している（`Rigor::VERSION`のみ）ため、バージョンを変えずにエンジンを編集するとヒットによってマスクされる可能性がある。そのため`make check` / `check-plugins`は`rigor check --no-cache`を実行する——ゲートは常に解析を再実行する。`lib/`を編集した後に実際のプロジェクトで`rigor check`を実行する開発者も同様に`--clear-cache`（または`--no-cache`）すべきである。

## 影響

- **健全性がすべて**。単純な設計は解析時のプラグイン読み込みに対して無効化が不十分であり；record-and-validateの設計は、実行前の推測からではなく実行が実際に読んだものから依存集合を導出することでこれを解消する。pundit退行テストが実装の受け入れゲートである。
- **変更なし時のフロアはプリパスであり、ゼロではない**。健全なキャッシュでも、検証してサーブする前に`run_project_pre_passes`（発見済みシンボルインデックス + プラグイン`prepare`のために解析済み全ファイルをパース）を実行する。後続のスライスで同じファイルダイジェストセットをキーとしてプリパスの成果物をキャッシュし、ほぼ即座に近づけることができる；先送り。
- **ファイル単位の粒度はスコープ外**。AのDiagnosticsがBの*本体*（項目2）に依存するため、単一ファイルの編集を生き延びるファイル単位のキャッシュにはRigorが構築しないクロスファイル依存グラフが必要である；実行全体のエントリーが適切な最初の粒度である。

## 却下した代替案（まとめ）

- **解析前の実行全体フィンガープリント**——解析時のプラグイン読み込み（Pundit）に対して不健全；既存の退行テストによって実証済み。
- **解析セットのみからのフィンガープリント**——`paths:`外のプラグイン読み込みファイルも見逃す；上記に包含される。
- **手動選択した設定フィールドのフィンガープリント**——脆弱；`Configuration#to_h`全体をダイジェストする。
- **単一ファイル編集用のファイル単位キャッシュ**——クロスファイル依存グラフが必要；先送り。
