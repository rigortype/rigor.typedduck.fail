アーキタイプ: deliberative。ステークス: high（フローエンジンのコア。現在の挙動は仕様のMUSTに違反する。修正は、他のdiagnosticが消費する畳み込み定数を動かす）。

## コンテキスト

フローエンジンはすべてのブロック本体を評価する（`StatementEvaluator#evaluate_block_if_present`、`lib/rigor/inference/statement_evaluator.rb`のおよそL1583）が、**ブロックの出口スコープを破棄する**。クロージャ脱出モデル（`record_closure_escape_if_any`のおよそL1608）は、キャプチャしたローカルを`Dynamic[top]`へ広げるのは`:escaping`ブロックに対してのみだ。`:non_escaping`分類（each / times / upto / map …）は呼び出し後のスコープを**変更しないまま**にする。帰結はこうだ。

```ruby
result = 1
1.upto(6) { |i| result *= i }
result  # typed Constant[1] — runtime value is 720. UNSOUND.

e = 1
[1].each { e = 99 }
e       # typed Constant[1] — runtime value is 99. UNSOUND.
```

ブロックキャプチャの書き込み形（`=`、`+=`、`*=`、多重代入。IntegerもStringも同様）はすべて落とされる。`while`は隣接しているが別物だ: `eval_loop`（およそL811）は事前スコープと**一度**の本体パスをjoinする（`d = 1; while …; d *= 2; end` → `1 | 2`、`4, 8, …`を取りこぼす）。

仕様はすでにこれを決めている: [`control-flow-analysis.md`](../../type-specification/control-flow-analysis/)の §「Fact stability and mutation」──*「Rubyの挙動が観測対象を変異・置換・脱出させうるとき、Rigor MUSTファクト（fact）を無効化または弱める」*とあり、**キャプチャされたローカルのファクト**が第一級のカテゴリーとして名指しされている。さらに § call-timing──*「即時の非脱出呼び出し、回数不明」*が、まさにeach/uptoのケースである。実装はこのMUSTに違反している。本ADRはその追いつきであって、新しい方針ではない。`MutationWidening.widen_after_block`（レシーバーの変異、`arr << x`）とブロック内のivar書き込みはすでに処理されている──ギャップは具体的には非脱出ブロックでの**ローカルの再束縛**だ。

## 決定

> **ブロック本体（またはループ本体）が再束縛しうるキャプチャされた外側のローカルは、継続スコープにおいて呼び出し前の束縛を未変更のまま決して保持してはならない**。継続の束縛は、事前状態を、保守的に広げられた反復後状態とjoinしたものである──本体は0..N回走って累積しうるので有界不動点で計算される──そして任意の非収束は、そのローカル（だけ）を`Dynamic[top]`へデグレードさせる。これは確立済みの脱出ブロックのフロアである。

### WD1 — スライスA: 非脱出ブロックがキャプチャしたローカルのライトバック

`sub_eval(block, block_entry)`の後、ブロックの出口スコープをキャプチャする。ブロック本体が書き込む外側のローカルごとに（`captured_local_writes`のおよそL1652を拡張する──現在は`LocalVariableWriteNode`しか見ていない──`LocalVariableOperatorWriteNode`、`LocalVariableOrWriteNode`、`LocalVariableAndWriteNode`、`MultiWriteNode`配下の`LocalVariableTargetNode`へ）、継続の束縛を**有界不動点**（上限3、ADR-55の形）として計算する: 種＝呼び出し前の束縛。「現在の束縛でブロック本体を評価し、書き込まれたローカルの出口型をjoinし戻す」を反復し、許される最後の反復で値ピン留め構成要素をその名前的基底へ広げ、なお不安定ならそのローカルを`Dynamic[top]`にする。0反復のケースもカバーされる、なぜなら呼び出し前の束縛が一貫してjoin構成要素として残るからだ。書き込まれないローカルはその束縛を手つかずのまま保つ（仕様の「無関係なローカル束縛のファクトを保つ」）。`:escaping`/`:unknown`のパスは不変である（すでにDynamic）。

期待される観測値: `upto`ブロックの後の`result` → `1 | Integer`（または`Integer`）であり、決して`Constant[1]`ではない。`[1].each { e = 99 }`の後の`e` → `1 | 99`。

**2026-06-11に実装**。`StatementEvaluator#write_back_block_captures`が`eval_call`内で`record_closure_escape_if_any`の後に走り、`:non_escaping`分類でゲートされる。有界不動点は新しい共有の`Inference::BodyFixpoint`に置かれる（上限3、`evaluate_body`callableでパラメータ化されているのでスライスBがそのまま再利用する）。`captured_local_writes`は5つの書き込み形すべてを収集するようになった。`Type::Combinator.widen_value_pinned`（`ExpressionTyper`から昇格し、それは現在委譲する）は`Refined` / `IntegerRange` → 名前的基底への広げを得たので、有界intのアキュムレータが収束する。非収束の崩れは新しい`BudgetTrace::BLOCK_WRITEBACK_CAP`を計上する。ゲート: `make verify`がグリーン（新しいセルフチェック／プラグインチェックの発火なし）。コーパス（Mastodonの`app/models`、hamlの`lib`、kramdownの`lib`）＝**除去1、新しいdiagnosticゼロ**──その除去は本物の勝利だ（`form/account_batch.rb`の`each`内`error ||= e`に続く`raise error if error.present?`が、もはや誤った常に偽の定数へ畳み込まれない）。perfはニュートラル（libセルフチェックがおよそ17.8秒、ベースラインのおよそ17.5秒に対して）。*（WD2.13の第2の残余の解消により修正: 本体のその場変異を受けるキャプチャされたローカルは、呼び出し前の内容ではなく、すべてのパスにおいてその未知格納の広げ（unknown-store widening）で読み取られる。）*

### WD2 — スライスB: ループ本体の不動点

`eval_loop`（および同等の`until`パス）は、その単一パスのjoinを、本体が書き込むローカルに対する同じ有界不動点で置き換える: joinが安定するまで、joinされたスコープから本体評価を反復する（上限3、最終反復での値ピン留めの広げ、非収束時にローカルごとの`Dynamic[top]`）。`d = 1; while …; d *= 2; end` → `1 | Integer`（現在の不健全な`1 | 2`）。述語に対するループ持ち越しのナローイングは反復ごとにjoinされたスコープから再計算されるので、既存のbreak／出口エッジの挙動は保たれる。

**2026-06-11に実装**。`StatementEvaluator#eval_loop`は歴史的な単一パスのjoinをベースとして保ち（それはなお、再束縛されないローカルのレシーバー変異の広げ、本体が導入するnil注入、そしてループ値を担う）、本体が再束縛するローカルについては`BodyFixpoint.converge`の結果をオーバーレイする。`loop_body_local_writes`は本体が書き込むローカルを、既存（種＝述語後の束縛）と本体先（種＝0反復パス向けの`nil`）に分割する。`loop_body_exit_bindings`は述語のループ入りエッジ（`while`→真、`until`→偽）を反復ごとに再適用するので、ループ持ち越しのナローイングが健全に保たれる。本体がいかなるローカルも再束縛しないループは、単一パスのjoinとバイト単位で同一のまま留まる（高速パス）。非収束（`g = [g]`）はそのローカルを`Dynamic[top]`へフロアし、`BudgetTrace::BLOCK_WRITEBACK_CAP`ヒット（スライスAと共有）を計上する。**1つの盲点が表面化し、スライス内で修正された**: `nil`を種とする本体先ローカルは本体の再評価にオーバーレイしては**ならない**──本体が走るとき使用前にそのローカルを代入するので、`nil`をフィードし戻すと、エンジンが分岐へ通さない条件形の代入を越えて`nil`が漏れ（`while …; if x > (count = 3); (count + 1)…`）、`+`/nil-レシーバーを偽発火させる。`nil`は0反復の結果のためのjoin構成要素としてのみ保持される。ゲート: `make verify`がグリーン（新しいセルフチェック／プラグインチェックの発火なし──反復ごとの述語ナローイングがすでに解消する継承された`expression_typer.rb:461-462`のセルフチェック発火を含む）。プローブが`d = 1; while …; d *= 2; end` → `Integer`（不健全な`1 | 2`だった）、`until`の同等性、本体先 → `T?`、書き込みなしループのバイト同一、累積 → `Dynamic[top]`を確認する。コーパス（Mastodonの`app/models` 5/5、hamlの`lib` 13/13がバイト同一。kramdownの`lib`は**除去2**──`until stack.empty?`内の`converter/html.rb:455`の`item = stack.pop`が、もはや誤ってnilレシーバーへ畳み込まれない──と、同一箇所での5つのメッセージ言い換え（`undefined method 'value' for nil` → `possible nil receiver`、レシーバーが純粋な`nil`ではなく`T | nil`と型付けされるため）、本物の新発火ゼロ）。

### WD2.5 — スライスC: レシーバー内容の要素型join（2026-06-12に追加）

2026-06-12のDynamic落ち調査（[`docs/notes/20260612-dynamic-fall-pattern-survey.md`](../../notes/20260612-dynamic-fall-pattern-survey/)、バケットB1/B3/B4）は、スライスA/Bのライトバックがローカルの**再束縛**はカバーするがレシーバーの**内容**変異はカバーしないことを見つけた: `out = [0]; [1, 2, 3].each { |x| out << x }`は`Array[0]`と型付けされる（ランタイムは`[0, 1, 2, 3]`）──**不健全**であり、伝播する（`out.first.zero? → true`）。既存の`MutationWidening`パスは変数を広げるが、追加された要素型をコレクションの要素パラメータにjoinすることは決してない。空でない種は種の要素しか保たない。スライスC: 非脱出ブロック本体（またはループ本体）が、キャプチャされた外側のローカルに対して内容変異メソッド（`<<`、`push`、`unshift`、`[]=`、`concat`、`merge!`、Stringの`<<`、…）を呼び出すとき、継続の要素／キー／値／内容の型は、同じ`BodyFixpoint`の上限／広げ／フロアの規律のもとで計算された、**事前状態の内容型と変異で入る型のjoin**となる（内容のフロアは`Array[Dynamic[top]]` / 素のコレクション──すでに健全な空の種の挙動だ）。`each_with_object`の戻り値は同じjoinされたmemo型を採用する（B3）。上の決定基準はすでにこれをカバーしている──「再束縛」は「再束縛または内容変異」と読める。スライスCは内容側の半分の到来である。

**2026-06-12に実装**。3つの合成する継ぎ目があり、いずれもスライスA/Bの`MutationWidening`キャリア広げヘルパーを再利用する。

1. **ブロック** — `StatementEvaluator#content_writeback_block_captures`が`eval_call`内で`MutationWidening.widen_after_block`（これはすでにリテラルのアリティを忘れるが、種の要素だけを保っていた）の後に走る。それはブロック本体を歩いて、キャプチャされた外側のローカルに対する内容変異子の呼び出し（`MutationWidening::CONTENT_ADDERS`＝Arrayの`<< push append prepend unshift concat insert []= fill replace`、Hashの`[]= store`、Stringの`<< concat prepend insert replace`）に加えてインデックス書き込み形（`h[k] ||= v`）を探し、各変異子の引数をブロック入りスコープで型付けし、追加／格納された要素／キー／値の型を、`MutationWidening.join_array_content` / `join_hash_content`を介して継続コレクションパラメータへJOINする。事前状態は`post_scope`から読まれるので、再束縛（スライスA）も内容変異もされたローカルが合成される。空の種の`Dynamic[top]`フロアは、実エビデンスが存在すれば落とされる（`out = []; arr.each { |x| out << x*2 }` → `Array[Integer | Dynamic[top]]`ではなく`Array[Integer]`）。
   *（WD2.9によって置き換え: 種は今や`widen_after_block`が走る**前**のスコープから読まれるので、空のリテラルは要素を何も寄与せず、何も落とされない——宣言された`untyped`をフロアと取り違えようのない経路による同じ`Array[Integer]`である。）*

2. **ループ** — `eval_loop`は高速パスの単一パスjoinとスライスBの不動点結果の両方に`loop_content_writeback`をオーバーレイする。引数は不動点で広げられた`post_loop`に対して型付けされるので、追加されたループカウンタは入りの定数ではなく`Integer`と読まれる。

3. **`each_with_object`の戻り値（B3）** — `each_with_object_return`がmemoブロックパラメータの内容変異からjoinされたmemo型を計算し、それを呼び出しの戻り値として採用して、ディスパッチャーが他では生む`Dynamic[top]`を置き換える。

Stringのアキュムレータは`String`の名前的基底へ広がる（要素パラメータはない。定数値はもはや健全ではない）。ネストしたコレクションを介してHashを内容変異するインデックス書き込み（`h[k] ||= []; h[k] << v`）は値を`Dynamic[top]`へフロアするが、もはや`h`を空の`{}`のまま残さない（それは`h.empty?`を誤った`true`へ畳み込んでいた）。ゲート: `make verify`がグリーン（新しいセルフチェック／プラグインチェックの発火なし）。プローブテーブルが調査の4つの再現形すべてを確認する（`Array[0]` → `Array[0 | 1 | 2 | 3]`、`out.first.zero?`がもはや誤った`true`でない、空の種 → `Array[Integer]`、`each_with_object` → joinされたmemo、Hash構築 → `Hash[K, V]`）。コーパス（Mastodonの`app/models`はバイト同一。hamlの`lib`は**除去1**──`each`内`parser.rb:746`の`dynamic_attributes << …`に続く`dynamic_attributes == "{}"`が、もはや誤った常に偽へ畳み込まれない。kramdownの`lib`は同一箇所での1つのメッセージ言い換え（`undefined method 'strip!' for nil` → `possible nil receiver`、レシーバーが`T | nil`と型付けされるため）、本物の新発火ゼロ）。perfはニュートラル（libセルフチェックがおよそ19.9秒）。`loop_body_fixpoint`フィクスチャの`acc.push(m)`ケースは、不精密だが健全な`Array[Dynamic[top]] | []`から`Array[Integer]`へ締められた（スライスCの精度の勝利、フィクスチャと仕様を更新）。

**直線コードへ一般化（2026-09-01、issue #560）**。同じ被覆不足はブロックなしでも存在する: `u = [1, 2]; u.push(6)`は`Array[1 | 2]`を保っていたので、`u.last == 6`が定数へ畳み込まれ、誤ったalways-falseyを引いた。したがってこのjoinはもはやブロック経路の機構ではなく、その代数は`MutationWidening`から`Rigor::Inference::ContentJoin`へ移された——`CONTENT_ADDERS`・`array_added_elements`・`join_array_content`・`join_hash_content`——ので、`widen_after_call` / `IndexWriteWidening.widen`と上記のブロックの継ぎ目は、WD3が警告する2つ目のコピーではなく1つの実装を共有する。直線側の呼び出し元は変異子の引数をそれが評価されるスコープで型付けし、`arg_types:`として通す;インデックス書き込みのノード（`h[k] ||= v`とその兄弟）は`[]=`の引数の形`[key, stored_value]`を合成する。

ブロック経路が必要としない3つのゲートが直線側を縛り、3つ目が荷重を支えるものだ:

- **種の許容性**。キャリアの要素のユニオンを育てることは、手書きのシグネチャを壊しうる。そこではjoinの結果が`def`の戻り値の検査に届くからだ。hamlの`temple = [:multi]; temple << [:static, s]`は、追加されたタプルがそれ自身としてjoinされると`-> Array[:multi]`に対して8件の誤った`def.return-type-mismatch`を引き、PR #561は反対方向から同じ壁にぶつかった。したがって、種がまだ運んでいないクラスのメンバーは、代わりに`Dynamic[top]`を寄与する。漸進的なメンバーがあってもこれだけでは救われない——`Array[:multi | [:static, String] | Dynamic[top]]`は依然として拒否される。`Dynamic`でないメンバーはそれぞれ個別に判定されるからだ——ので、このゲートと下記のフロアは独立であり、どちらももう一方の代わりにはならない。
- **追加される値のシェイプの消去**。格納されたリテラルのコレクションはエイリアスされたままスロットを通じて変異される（`params[:f] ||= []; params[:f] << :status`）ので、そのリテラルのシェイプは値のピン留めとともに消去される——`[]`は`Array[Dynamic[top]]`としてjoinされる。リテラルの`[]`をjoinすれば、スロットが`[:status]`を保持しているハッシュに`Hash[Symbol, []]`をピン留めしてしまい、`params[:f].empty?`が誤った`true`へ畳み込まれる: この変更が取り除くために存在するのと同じクラスの古い畳み込みだ。
- **直線のjoinは、自分が供給するパラメータを決して閉じない**。この広げは一方通行の扉であり——`Nominal`を残し、`widen_for_mutator`はそれを辞退する——だからこの継ぎ目が見るのはちょうど**1つ**の格納であり、次のものは不可視である。育っていく母集団の1サンプルの上で閉じることは、不正確な型ではなく誤った型だ:

      a = []
      a.push(1)       # joins -> Array[Integer]
      a.push("s")     # DECLINED -- pre-state is a Nominal now
      a.last.upcase   # correct Ruby, prints "S"

  これは`undefined method 'upcase' for Integer`を引き、mailの`Message#to_yaml`はキャリアが1つ違うだけの同じ欠陥である。したがってすべての直線のjoinは、自身の証拠と並べて`Dynamic[top]`を寄与する。それはissue #560について何のコストにもならない: `Dynamic`を運ぶユニオンは定数畳み込みできないので、このjoinが取り除くために存在する古いalways-falseyは取り除かれたままになる。

**将来の読者にとって重要な訂正**。上記の規則の最初の試みは**キャリア**を責めていた: Arrayの要素のユニオンは位置についてのものなので格納の取りこぼしを生き延びるが、Hashの値のユニオンはキーについてのものなのでそうならない、と。`a.last.upcase`のプローブがそれを反証する——`a.last`は`hash[k]`がキーを選ぶのとまったく同じように位置を選ぶのであり、落とされた腕はどちらにせよ誤った答えだ。本当の線は**joinする経路がどれだけを見たか**であり、それはスライスCを、この規則と緊張関係に置くのではなく同じ規則の反対側に置く: `content_writeback_block_captures`と`loop_content_writeback`は**本体全体**を走査し、書き戻す前にその中のすべての変異子の呼び出しをjoinするので、その本体についての証拠は完全であり、精密なjoinは正当化されたままだ。`acc = []; xs.each { |x| acc.push(x) }`は`Array[Integer]`と読まれ続ける。

この分割には、記録しておく価値のある機械的な帰結が1つと、その隣に記録しておく価値のある誤った経路が1つある。直線側のフロアは`post_loop`を通じて**ループ**の再導出へ到達しうるが、その束縛はすでに本体内のjoinの出力を運んでいる——その上で再導出することは、導出された出力の上での導出だ。出荷された修正はその源にある: `loop_content_writeback`は、ループが再束縛しない各名前を本体前のスコープ（`post_pred`）からシードするので、フロアはその入力に決して入らない;ループが再束縛もする名前は`post_loop`を読み続け（スライスB/Cの合成）、そこでは生き残ったフロアが払うのは精度であって正しさでは決してない。`ContentJoin.drop_dynamic`はトップレベルのメンバーに対する素の`grep_v`のままだった（WD2.9がそれを丸ごと取り除くまで）。誤った経路のほう: 以前のあるheadは代わりに`drop_dynamic`の内側で`Union`のメンバーを平坦化しており、それはこの継ぎ目を片付けたが、他のあらゆる場所で**宣言**由来の漸進的な腕を落としてしまった——宣言された`Array[Integer | untyped]`のパラメータがブロックの変異の下で`Array[Integer]`へ閉じ、正しいコードで発火したのだ。`keeps_declared_gradual_arm`のフィクスチャがそのような腕の生存を固定する;フロア由来のDynamicと宣言由来のDynamicをきちんと区別することは#580の由来のマークであり、意図的にここでは作っていない。

### WD2.6 — 引数が証拠を運ばない変異子は1格納の漸進的な腕を取る（2026-09-02、issue #580）

WD2.5のjoinは変異子の引数を読む。そこから何も読めないとき、この広げは以前は種の要素をそのまま保っていた: `m = [1, 2]; m.concat(xs)`は`Array[1 | 2]`のままで、`m.last == 6`は、実行時の値が本当に6であるコードに対してfalseへ定数畳み込みされた。変異は走ったので、保たれた定数は、何によってかをアナライザーが言えるかどうかにかかわらず偽にされていた——#540 / #541 / #544 / #560と同じ古い証拠のファミリーに、別の扉から到達したものだ。生き残った要素はピン留めを保ち、漸進的な腕を得る。

そのような格納は**1つの読めない格納**として扱われ、通常の1格納のパイプラインを走る: 許容された証拠なし、加えてWD2.5の`Dynamic[top]`の腕。`m`は`Array[1 | 2 | Dynamic[top]]`と読まれる。代わりにそれを——最初の切り出しがそうしたように、種の名前的な基底へ——閉じることは、1つの格納しか見ていない継ぎ目はパラメータを閉じてはならないというWD2.5自身の規則に違反し、まさにその規則が守るものを払う: hamlの手書きの`-> Array[:multi]`の下での`Array[Symbol]`は#561の`def.return-type-mismatch`を呼び戻し、concat後の`m.last.upcase`は、引数が文字列を保持していれば正しいコードに対して`undefined method`を引く。畳み込みのアサーションだけではどちらも見えないので、両方とも今はフィクスチャとして固定されている。

判別条件は、抽出された証拠が空である一方で`arg_types`が**空でない**ことである: 抽出器が読めなかった実在の引数だ。**空の**`arg_types`は、引数の機構がその呼び出しに到達しなかったことを意味し、キャリアには手を触れない。WD2.5のブロックキャプチャの経路がそこで重要な生産者である——それが何も渡さないのは、スライスCのjoinが後から追加された型を再度加えるからであり、キャリアに触れれば意図的に保っている種のピン留めを剥がしてしまうからだ（`out = [0]; arr.each { out << x }`は`0 | …`のままでなければならない）——が、それだけではない: 引数なしの追加子（`m.concat`）と、引数のタイパー自身のrescueもそこに着地し、それらについてもキャリアに手を触れないのが正しい。

既知かつ受容している偽陰性: `m.concat([])`は実行時のno-opなので、その後の`m.last == 6`は本当に常にfalseであり、`Dynamic`の腕は**正しい**always-falseyを抑制する。no-opの呼び出しに対する偽陰性は、上記の2件の偽陽性よりも良いトレードだ。

これは#580に記録された2つの残余のうちの1つである。もう1つ、エイリアスへの盲目性（`b = a; a.push(6); b.last == 6`）は手つかずだ: それにはレシーバーのエイリアスの集合を、すべてのエイリアスへ書き通す必要がある。このissue自身の主題——広げられた`Nominal`を再joinして後続の格納が蓄積するようにすること——も未決のままである;その試みから得られた証拠、とりわけスコープ側の由来のマークがメソッドの戻りをまたいでシグネチャの保護を運べない理由は、issueに記録されている。

### WD2.7 — マージが構造体の畳み込み安全性を取り消していた（2026-09-02、issue #589）

「本体が一度も触れていなくても`while`ループが構造体のローカルのキャリアを消す」として報告され、このADRの領分におけるループの継ぎ目の広げの問題だと予想された。どちらでもなかった。

キャリアはマージを無傷で生き延びる——そこでも`s`は`S(raw: "r")`と読める。失われていたのは、メンバーの読み取りがそれを参照することを許す**付与**のほうだった: `Scope#join`がコンストラクタの呼び出しから`struct_fold_safe_locals`を省いていたので、空の既定値へフォールバックしていたのだ。メソッド本体のあらゆるマージが、それ以降のすべてについて構造体のメンバーの畳み込みを黙って取り消しており、`if`も`while`とまったく同じようにそれを行っていた——これは決してループ固有ではなかった。この付与は今やマージをまたいで積集合を取られる（両方の腕は通常は同一の集合を運ぶ。それはメソッドのルートに対する静的な走査だからだ;積集合を取るのが偽陽性に対して安全な方向である。この付与は畳み込みを許可するものだからだ）。

畳み込みの**安全性**については何も動いていない。静的な走査は、セッターがループやブロックの内側に座るローカル（`deferred_setter`）、本体が再束縛するもの、そしてエスケープするものを、すでに失格にしている;joinはその走査の答えと矛盾していたのではなく、それを捨てていたのだ。3つとも依然として辞退し、そして畳み込みは今や単一パスではなく、このADRのループの不動点をまたいでも成り立つ。

付与を復元したことで、その走査に実在するギャップが露わになり、同じ変更で修正された。走査の数え上げの同一性は**ローカル**についてのものであって、メンバーの読み取りの**結果**については何も言わない: `s.x << v`は`s.x`が返すコンテナを変異させるが、`s.x`自体は教科書どおりの純粋な読み取りなので、そのローカルは畳み込み安全なまま、メンバーの値だけが足下で変わっていた。メンバーの読み取りの結果がそれ自身レシーバーになるローカルは、今や独自の許可リストなしで丸ごと失格にされる——`s.x.to_s`は何の見返りもなく精度を失うが、許可リストこそがこのバグを生んだものであり、広すぎることのコストは`Dynamic[top]`だけである。それはまた、このブランチが存在する前から発火していた直線形式における既存の偽陽性も取り除く。取りこぼしたケースは「決して不健全にならない」という走査のヘッダーの主張は偽であり、そこで訂正されている。残る残余: #597。

**見返りは計測されており、それはmailのragelのクラスタでは**ない**。** issueはそれを対象として名指していた。そのファイルの2つの構造体は、どちらもこの修正が触れない理由で除外される: `address`はragelの`while`の**内側で**131個のメンバーのセッターを取るので`deferred_setter`が失格にする——そしてそのゲートは荷重を支えている（#525の兄弟が、それを取り除くと古い`nil`が提供されることを検証した）;`address_list`は素の読み取りとして2度返されるので、エスケープの規則が失格にする。約250のサイトのうち0個しか解放されない。**解放される**のは、マージが以前は取り消していたすべての構造体のローカルだ: 触れない`if`や`while`の後のメンバーの読み取り、そしてそれを生き延びるADR-48のスライス4のセッターの書き戻しである。mailに届くには別のレバー——ループ内のセッターの反復ごとの効果をモデル化すること——が要るのであって、これではない。

### WD2.8 — ループのjoinが反復ごとのサマリーで**ない**理由（2026-09-02、issue #597）

WD2.7の後も、ループの内側でセッターを取る構造体のローカルのメンバーの読み取りはすべて`Dynamic[top]`と答える。`StructFoldSafety`のオールオアナッシングな`deferred_setter`のゲートによってだ。#597はそのゲートを反復ごとのサマリーで置き換えることを提案した。**試み、計測し、取り下げた**;再導出されないようにその理由をここに記録する。

魅力的な観察は、`eval_loop`がすでに本体の出口のスコープをループ前のスコープとjoinしているので、セッターの効果が「ループが走った」と「走らなかった」のユニオンとして継続へ届くように見える——一見、このゲートが代役を務めているサマリーそのものに見える——というものだ。それを読めるようにする変更は2つ: `while` / `until`を遅延の境界として扱うのをやめること、そしてメンバーの読み取りが同一クラスの`StructInstance`のユニオンを透かして見られるようにすること。どちらも実装され、分かりやすい形の上ではissueの求めるとおりに動く（設定されたメンバーは`1 | 9`と読まれ、設定されていない兄弟は`2`のままになる）。

**そのjoinはサマリーではなく単一の展開である**。そしてその差は見た目の問題ではない。4つのプローブがそれぞれ、プログラムが決して保持しない値へ畳み込む——ここでは最悪の失敗クラスだ。誤った精密な型は、下流のすべてのルールへ黙って供給されるからである:

- **ループを跨いで運ばれるメンバーの状態**。`while`の中の`p.x = p.y; p.y = 5`は`1 | 2`と読まれる;実行時は5を保持している。`loop_body_local_writes`はスライスBの不動点をローカルの**書き込み**ノードでキーするので、セッターしかない本体は高速パスを取る——単一の展開だ。これはスライスB以前の`d *= 2`のバグ（「4にも8にも決して到達しない」）を、1つ下の層、メンバーにおいて再現したものである。
- **ループがまったくない、後続のセッター**。`p.x = 9 if cond; p.x = 5`は`1 | 9`と読まれる;実行時は**常に**5だ。`apply_setter_writeback`はユニオンの束縛に対してはno-opなので、ユニオンの読み取りは書き戻しが一度も更新しなかったキャリアを参照する。「if / caseのマージはただで畳み込まれる」という主張はこれを出荷することになる。
- **`break`の経路**。breakの辺のメンバーの状態は落とされる: 高速パスは`join_break_scopes`より前に戻り、収束した経路はbreakを再束縛された**ローカル**についてのみjoinする。
- **本体内の読み取り**。セッターより前の読み取りはループ前の束縛しか見ないので、反復2以降も反復1の値を畳み込む。

したがってユニオンの読み取りが健全であるのは、何もチェックしていない4つの副条件の下だけである: セッターの右辺がループを跨いで運ばれるメンバーの状態に依存しないこと、そのメンバーがループの**後**でのみ読まれること、ループがその述語を通じて出ること、そして後続のセッターがjoinの記録したものを上書きしないこと。本物の版には、不動点の**内側**でのメンバーのセッターの効果（畳み込み安全な構造体のローカルを収束する名前として扱い、上限ではメンバーのマップを広げる）、ユニオンの腕へ写像する書き戻し、構造体のキャリアを寄与するbreakのシンクのスコープ、そして収束したエントリーの状態を参照する本体内の読み取りが要る。それはスライスB自体と同じ規模のスライスであって、調整ではない。

これが作られなかったのは、動機が対象との接触を生き延びないからだ。#597はmailのragelのクラスタのために存在し、WD2.7はすでに、`address`がこのゲートより上流の規則によって三重に失格であることを計測している——決定的なのは、`fold_safe_locals`がちょうど1回の書き込みを要求するのに対し、それが27回**再束縛**されていることだ。反復ごとのセッターのサマリーは、状態機械が毎反復で再実体化するローカルを助けられない。このゲートはそのファイルにとっては見当違いであり、単一書き込みの要件のほうが本当の関門である。

取り下げから生き延びたのは訂正された推論である: `for`が境界であるのは上記の展開の理由によるのであって、そのコメントがかつて挙げていたブロックスコープの理由によるのではなく、そしてブロックのケースとループのケースは、共有された「単一の静的なパス」という手振りではなく、本当に別々の理由で辞退する。

### WD2.9 — 種自身の漸進的な腕が再導出を生き延びる（2026-09-02、issue #586）

WD2.5のB2の注記は、宣言された腕のバグの1つの綴りをそのまま残し、そう述べていた（「素の`Array[untyped]`の隣接……masterに既存」）。`Array[Integer | untyped]`と宣言されたパラメータが生き延びたのは、その`untyped`が`Union`のメンバーの**内側**に座っており、非再帰的なdropがそれに手を触れなかったからだ。`Array[untyped]`と宣言されたものは生き延びなかった: その種の要素が`Dynamic`**そのもの**であり、`join_array_content`は本体の格納が具体的なクラスを寄与した瞬間にトップレベルの`Dynamic`をすべて落としたので、

    #: (Array[untyped]) -> String
    def m(a)
      [1, 2].each { a.push(rand(9)) }
      a.first.upcase          # correct: the declaration licenses it
    end

は`a`を`Array[Integer]`へ閉じ、`undefined method 'upcase'`を引いた。`while`の形も`loop_content_writeback`を通じて同一に発火し、宣言された`Hash[untyped, untyped]`は両側で同じように閉じた。カテゴリーエラーは、B2がすでに直線の継ぎ目について名指していたものである: 宣言された漸進的な腕は、そのコレクションが**すでに**保持しているものについての言明であり、本体の格納は本体が**入れた**ものについての証拠であって、本体について完全な見方は世界について完全な見方ではない。

**決定: このjoinは種の腕を1つも、決して落とさない**。`drop_dynamic`は消えた;`join_array_content` / `join_hash_content`は種の腕を追加された証拠とユニオンするだけで、他には何もしない。このdropはちょうど1つの生産者のために存在していた——`widen_after_block`が、ブロックの継ぎ目が種を読むより前に空の`[]`を`Array[untyped]`と綴っており、その製造された`untyped`を、`out = []; xs.each { out << x*2 }`を`Array[Integer]`に保つために洗い落とす必要があったのだ。いったんキャリアの内側に入ってしまえばそれは宣言されたものと区別がつかない（B2が`post_loop`について行ったのと同じ観察）ので、修正はB2がすでにループの継ぎ目に適用したもの——フロアをその**源**で締め出すこと——である。`content_writeback_block_captures`は今や、`widen_after_block`が走る**前**の状態のスコープから種を読む——呼び出し**前**の`scope`ではなく広げ**前**の`post_scope`なので、スライスAの再束縛の書き戻しと、広げより先に適用された他のすべての呼び出し後の効果は依然としてその中にある。すると空のリテラルは要素を何も寄与せず、本体の証拠がそれを閉じる。以前とまったく同じだ;一方、宣言された`Array[untyped]`、同じものを返すシグネチャを持つ呼び出しからシードされたローカル、そしてエンジンが型付けできないリテラルの`[x]`のスロットは、その腕を寄与し、それを保つ。

種をより早く読むことから2つの帰結が生じる。1つは修復であり、1つは意図的なトレードだ:

- **これらの継ぎ目は、以前は基底に出会っていたところで`Difference`に出会うようになった**。`xs.any?`のナローイングの後、`xs`は`non-empty-array[String]`である;広げは、ブロックの継ぎ目が見るより前にそれを`Array[String]`へ変換していた。広げ前に読むと、リファインメントのキャリアがjoin自体へ届くので、`collection_element_types` / `hash_shape_key_values`と`arrayish?` / `hashish?`のゲートは`Difference`をその基底まで透かして読む。代わりにそれを辞退すれば、継続には追加された腕がすべて欠けた広げ後の基底**だけ**が渡ることになる——そしてそれこそ、B2が`pre_body`へ移して以来**ループ**の継ぎ目が行っていたことだ: `if xs.any?; while …; xs << 1; end`は`Array[String] | non-empty-array[String]`と読まれ、`1`が消えていた。今や両方の継ぎ目が`Array[1 | 2 | String]` / `Array[1 | String]`と読む。
- **「証拠なし」かもしれないがキャリアをまとった`Dynamic`も保たれる**。手書きのシグネチャが`Array[untyped]`を返す呼び出しからシードされたアキュムレータは、閉じた`Array[1 | 2]`と読まれていたところで今は`Array[1 | 2 | Dynamic[top]]`と読まれ、エンジンが型付けできない`[x]`のスロットはその腕を保つ。直線経路の`gradual_seed`のフィクスチャはすでに同じように読んでいる。（`Array.new`はこの集合に入って**いなかった**: 型引数のない素の`Array`として型付けされ、joinはそれを要素なしと読み、依然として閉じていた —— そしてそれはこの規則が除外するケースではなくWD2.12が修正するバグであることが判明した; `Hash.new(default)`の種は`Hash[Dynamic, V]`と型付けされ、今はそのキーの腕を保つ（単調であり、診断は何も動かない）; `Array(x)`は丸ごと`Dynamic`であり、joinには決して到達しない。）どれも稀な綴りにおける単調な不正確さであり——アキュムレータの慣用形は`[]`が支配的だ——そして代替案、すなわちどの`Dynamic`が「本当は」空なのかを推測することは、#580が所有する由来の問いである。偽陽性のコストは最悪ケースの静的な読みに優先する;このトレードは取る。

ゲート: `mutation_join_declared_sig`のフィクスチャが、素の宣言された腕をブロック・ループ・Hashの各形式で運び（発火してはならない）、依然として閉じ依然として発火する新鮮な種の兄弟（`call.undefined-method`の行の集合を厳密に——どこでも漸進的になった継ぎ目はそこでも黙ってしまうからだ）、そして`Difference`の種をブロックとループの形式で運ぶ;`block_path_stays_precise`と`loop_body_fixpoint`の`Array[Integer]`のスナップショットは不変であり、`block_captured_writeback`のフィクスチャが`[x]`のスロットを固定する。dropを復元する（あるいは種を再び`post_scope`から読む）と、発火してはならない例が赤になり、他は何も変わらない。

これが**触れなかった**もの: 直線の継ぎ目の`Difference`の分岐であり、そこでは`widen_for_mutator`が変異子の引数をjoinせずに`non-empty-array[T]`をその基底へ広げていた（`if xs.any?; xs << 1`は`Array[String]`と読まれていた）。それは#560のファミリーに4つ目の扉から到達したものであり、独立した変更として着地した（issue #936）: この腕は現在、リファインメントの基底の上に追加されたコンテンツをjoinし、レシーバーを空にし得る変異子に対してのみempty witnessを撤回するようになった。そのため追加操作は`non-empty-array[String | Integer]`と読まれ、`xs.clear`は引き続き`Array[String]`と読まれる。

### WD2.10 — 要素ごとの畳み込みが再束縛されたキャプチャをその収束した束縛で見る（2026-09-02、issue #587）

スライスAの不動点は**継続**に答える: ブロックが0回以上走った後にキャプチャされたローカルが何であるか、だ。それは呼び出し自体が型付けされた後に`StatementEvaluator#eval_call`で走るので、ブロックの**戻り**のパス——その呼び出しの型付けの内側からディスパッチされる`ExpressionTyper`——はその結果を決して見ない。単一yieldのメソッドにとってそれは無害だ: `m.synchronize do total += 1; total end`は唯一の反復で`1`である。要素ごとのTupleの畳み込みにとっては、それはすべての位置における誤って精密な答えになる: この畳み込みは同じエントリースコープから要素ごとに本体を型付けし直すので、`total = 0; [1, 2].map do total += 1; total end`は`[1, 1]`へ畳み込まれ（実行時は`[1, 2]`）、そして`r.first == 1`が`Constant[true]`へ畳み込まれた——正しいコードに対する生きたalways-truthyである（PR #584のレビュー、プローブ2）。

修正の方向は2つ開かれていた。継続の束縛を`eval_call`からの2回目の呼び出しの型付けへ戻す方法は、一般の`Array[U]`の経路も直すが、レシーバーと引数を広げられた束縛の下で型付けし直し、キャプチャを再束縛するすべてのブロックについて呼び出しの型付けを2倍にし（`sum = 0; xs.each { |x| sum += x }`が典型だ）、それ自体が文でない畳み込み（述語の内側の`… .map do … end.first == 1`）を取り逃がす。畳み込みを丸ごと辞退する方法は、このピン留めが一度も触れていない畳み込みを失う: `[1, 2].select do seen += 1; e > 1 end`は要素だけで判断するので`[2]`のままであり、再束縛されていないキャプチャを読む末尾はそのリテラルを保つ。

決定は狭いほうだ: 畳み込み自体が、いずれの位置を型付けするより前に、同じ「キャプチャされた再束縛の名前の集合」（今は`Inference::CapturedLocals`。スライスAとサブフェーズ3cのドロップと共有され、4者が乖離しえない）の上でWD3の不動点を走らせ、再束縛された各ローカルをすべての位置のエントリースコープでその収束した型に束縛する。答えは、そのローカルが**いずれかの**反復で取りうるもの——`[Integer, Integer]`——であり、構造的に累積していく再束縛（`x = [x]`）は不動点がすでに定義しているフロアを取る。コストは欠陥のあった形に限定される: 畳み込みのファミリーの下のTupleレシーバーで、その本体がキャプチャを再束縛するもの、多くても上限＋1回ぶんの追加の本体の評価で、パラメータは要素のユニオンに束縛され、アリティには依存しない。#584のブロック本体のスレッディングの抑制の下（スレッディングされた本体の中にネストした畳み込み）では不動点は走らず、それらの名前はエスケープするブロックのフロアを取る。

2つの残余は、ここで修正するのではなく記録する。一般の`Array[U]`の経路（名前的なレシーバーに対する`xs.map do total += 1; total end`）は依然として`U`を最初の反復にピン留めする——`Array[1]`であり、`r.last == 2`に同じalways-falseyの危険がある——ブロックの戻りのパスは単一yieldのメソッドとイテレータを区別できず、単一yieldの答えは厳密だからだ;その修正にはyield回数のシグナルか上記の`eval_call`の並べ替えが要り、それ自身のissueに属する。そして`[1, 2].map { total += 1 }`は、エントリーで`total: Integer`であっても依然として`[1, 1]`へ畳み込まれる。`ExpressionTyper#type_of_assignment_write`がすべての複合代入をその右辺として型付けする——`total += 1`を`1`として——からであり、これは畳み込みではなく式タイパーの欠陥であって、その修正はすべての`||=` / `&&=` / `op=`の式に及ぶ。

### WD2.11 — 再導出されたキャリアはそれが表すメンバーのみを置き換える（2026-09-02、issue #631）

WD2.9は要素の腕を解決した。しかし変数全体の腕は依然として落とされており、それを落とすことで以下が発火していた:

    def f(flag, u)
      out = flag ? u : [2]     # Dynamic[top] | [2]
      [1].each { out << 2 }    # -> Array[2]; Dynamicの腕が消える
      out.first.upcase         # undefined method `upcase' for 2
    end

同じ種を`out.first == 3`を通じて読んだ`g`は、双子のalways-falseyを引いた。どちらも`u`が文字列の配列である限り正しいプログラムであり、どちらもスライスCまで遡るmaster上でバイト単位で同一だった。

メカニズムは、誰も書き留めていなかった継ぎ目の契約の1行である: `join_array_content`は新しく**単一の**`Nominal[Array]`を構築し、呼び出し側はそれを束縛全体に上書きする。それは、そのクラスのArray**として**変異が適用された事前状態のメンバーに対してのみ正しい答えである。`collection_element_types`はそれ以外のすべてのメンバー —— 変数全体の`Dynamic`、外部の`Nominal`、`Constant` —— に対して`[]`と答えるため、それらは何も寄与せず、上書きによって消滅していた。直線の継ぎ目は`widen_for_mutator`が`Union`を完全に辞退してそのまま透かして読むため、このバグを決して持たなかった;ブロックとループの継ぎ目が外れ値（outlier）であり、基準（reference）ではなかったのだ。

**決定: joinは事前状態を分割（partition）する**。対象クラスのキャリアとして読めるメンバーは再導出されたキャリアに吸収され、それ以外のすべてのメンバーは調べられることなく、そのまま隣で無傷に生き延びる。ここでは`Dynamic[top] | Array[2]`となる。どちらの半分も2度調べられることはないため、何も二重に広げられることはなく、この分割は`collection_element_types` / `hash_shape_key_values`の再帰を1対1でミラーする（`ContentJoin#array_residue` / `#hash_residue`）ことで綴られるため、吸収された集合と残余（residue）が乖離することはない。

分割が解決しなければならなかった4つの点:

- **キャリアは証拠を運ぶかどうかにかかわらずキャリアである**。型引数のない素の`Nominal[Array]` —— `Array.new`、WD2.9自身の例外 —— は要素を産出しないが、それでも吸収される。「証拠がない」ことを「キャリアではない」として扱うと、#615の種にそれを閉じさせる代わりに2つ目の腕（`Array | Array[2]`）を生やしてしまう。
- **2つのArrayキャリアは依然として1つのArrayにjoinされる**。両方とも吸収される;`out << 3`の下での`flag ? [1] : [2]`は`Array[1 | 2 | 3]`のままとなる。これは「依然として成功しなければならない」半分であり、キャリアを保持する残余規則が不正確さではなく派手に壊してしまう側である。
- **ループの継ぎ目はjoinを共有しているため、この規則をただで手に入れる**。`f`の`while`版の双子も同様に発火していたが、これに伴って静かになる。
- **`nil`は生き延びない**。それは変異自体が反駁する唯一のメンバーである: `NilClass`はコンテンツ変異子を定義しないため、本体が実行されたすべてのパスにおいて束縛はnilではなかった。0反復のパスのみがその腕を保持し、そのパスは上流でモデル化されている —— `while`のベーススコープのnil注入、スライスAの`Constant[nil]`不動点の種であり、ここではない。それを保持することは純粋なコストとして測定された: `r = nil; while …; r ||= []; r << x; end; r.each`はRubyistが意図的に書く慣用形において`call.possible-nil-receiver`を獲得してしまい、一方で本当に生きているnilの腕はすでに1回、変異の箇所で報告され、そこでの`r << x`が同じ診断を引く。その推論の一般的な形 —— 変異子が未定義である任意のメンバーを落とすこと —— はこの継ぎ目が環境を持たないメソッドルックアップを必要とし、より稀な形しか救えない;`nil`はただで決定できるケースである。もし0反復のnilを再検討したくなった場合、その場所はjoinではなく注入である。

残余は、畳み込みとメソッドチェックを吸収する`Dynamic`にとって厳密に漸進的な方向である: それらのサイトは診断を失うことしかできない。外部の`Nominal`や`Constant`メンバーは**新しい**発火が現れうる唯一の場所であり（`out << 2`の下での`flag ? 5 : [2]`、その後の`out.first`）、それは正直なものである —— その腕は実在し、直線の双子は既にそのように読んでおり、その場所にArrayを捏造することこそがバグだったのだ。

ゲート: `union_seed_residue`のフィクスチャが両方のissueの形に加えてループとHashの双子、および外部の`Nominal`メンバーを運び（発火してはならない）、依然として閉じ依然として発火しなければならない素の種 / 2キャリア / 素のキャリアの兄弟（厳密な`assert_type` —— キャリアを保持する規則はそこで`Array[1 | 3] | Array[2 | 3]`と読むだろう）、そして反駁されたnilの腕とその`call.possible-nil-receiver`行セットを運ぶ。dropを復元すると、「発火してはならない」側が赤になり、他は何も変わらない。

### WD2.12 — スロットを埋めるコンストラクタは決して要素なしの種ではない（2026-09-02、issue #615）

WD2.9自身の括弧書きは`Array.new`を規則が到達しないキャリアとして挙げていたが、それを除外として読んだことが過ちだった。素の`Array`は「joinが保持しなければならない漸進的な腕を持つ種」ではない;それは**要素の腕をまったく持たない**キャリアであり、これこそが継ぎ目が要素なし（ELEMENTLESS）の種 —— そのすべての格納を把握している新鮮なアキュムレータ —— として読み取るまさにその形状であるため、ブロック自身の格納をまたいで閉じてしまう。しかし、それを生成したコンストラクタはブロックが決して触れていない`n`個のスロットを埋めている:

    acc = Array.new(n, "x")
    [1].each { acc.push(1) }
    acc.first.upcase          # 正しいRuby

これは`Array[1]`と読まれ、`undefined method 'upcase' for 1`を引いた。そして埋め込みなしの形式は、nilの配列の上で`acc.first == 1`をalways-truthyと畳み込んだ。どちらも不正確ではなく誤って精密（wrong-precise）であり、どちらも#586の規則がコンストラクタ畳み込みの動的サイズ（#531）の答えと出会ったことによる。

変わるのは継ぎ目ではない。変わるのは**コンストラクタ**である: 非リテラルのサイズを持つ`Array.new`は、本物の要素パラメータをシードするようになった —— `Array.new(n, v)` / `Array.new(n) { … }`には埋め込み値やブロック結果の型、埋め込みなしの形式には漸進的な要素。したがって継ぎ目には宣言に似た`Nominal[Array, [E]]`として届き、WD2.9はその腕をjoinを通じて変更なしに保持する。小さなリテラルサイズは位置ごとの`Tuple`畳み込みを維持する;引数ゼロの`Array.new`は本当に空の配列を構築するため、要素なしのキャリアを保持し、`[]`リテラルとまったく同様に閉じる。

3つの要素の選択は重要であり（load-bearing）、3つとも精度判断ではなく偽陽性の判断である:

- **要素は値ピン留め広げ（value-pin widened）される**。`hash_new_lift`と同じ理由である: 配列の寿命の中でスロットは書き換えられるため、`Array["x"]`とすると後続の`acc[i] == "x"`が定数畳み込みされてしまう。リテラルの**コンテナ**結果も同様に広げられる —— `Array.new(n) { [] }`はプログラムが後で追加を行う`n`個の**独立した**配列を構築し、`Array[Tuple[]]`はそれらのすべてが空のままであると主張してしまうため、隣接リストの慣用形において`adj[i].first`を`nil`と読んでしまう。これはコンテナ自身の要素やハッシュシェイプ自身の値を通じて**再帰的に**広げられる: ネストしたすべての位置も構築されたスロットごとに新鮮なオブジェクトであるため、最外層レベルで止めることは誤って精密な答えを1段階内側に移動させるにすぎない（`Array.new(n) { [[1]] }`は`Array[Array[[1]]]`のままであり、`a[0][0] << 5`の後に`a[0][0].last == 5`をalways-falseyと畳み込んだ）。この巡回はソースリテラル自身のネストによって有界である —— `Type`キャリアはボトムアップに組み立てられ自身を含むことはできない —— その背後には防御的な深さ上限もある。
- **`Union`の埋め込みはメンバーごとに広げられる**。全体として判定されると、`Array.new(n) { flag ? [1] : [2] }`は`Array[[1] | [2]]`のままで各腕は依然として固定長タプルであるため、正しいコード上で`a[0] << 5`の後の`a[0].last == 5`がalways-falseyと畳み込まれた。各コンテナメンバーは同じ再帰的な広げを受ける;非コンテナメンバーはそのまま通過するため、`Array.new(n, flag ? [] : "s")`は`Array[Array[untyped] | String]`と読まれる。
- **埋め込みなしの形式は`nil`ではなく漸進的な要素をシードする** —— サイズ引数が証明可能に`Integer`である場合や、サイズ超過リテラルのフォールバックであっても同様である。`Array.new(n)`は実際にすべてのスロットに`nil`を配置するため、`nil`はその値の正直な読み取りである;しかしそれは**キャリア**の正直な読み取りではない。下流において`Nominal`の種は**宣言された**キャリアのセマンティクスを受け取る: WD2.9のjoinは種の腕を永久に保持し、`MutationWidening#widen_for_mutator`は`Nominal`を完全に辞退するため、配列全体の書き換え —— `[]=`, `fill`, `map!`, `replace`, `concat` —— のいずれもプレースホルダーを撤回（retract）できない。したがって`nil`は「埋める前に配列の中にあるもの」であることをやめ、コンストラクタの存在理由そのものである「確保してから埋める（allocate-then-fill）」慣用形において永続的なnilの可能性になってしまう:

        dp = Array.new(xs.size); dp[0] = 1
        (1...n).each { |i| dp[i] = dp[i - 1] + xs[i] }   # `undefined method '+' for nil`

        buf = Array.new(256); 256.times { |i| buf[i] = i.to_s }
        buf.each { |c| c.upcase }                        # nilレシーバの可能性

  どちらも正しいRubyであり、どちらも`nil`の種によって沈黙からエラーへと転落した。プレフィックスサムや篩（sieve）の形状も同じ道をたどる。`nil`がもたらす真陽性 —— 何も書き込まれなかった配列に対する`Array.new(n).first.upcase` —— は、支配的な慣用形の代償を払うに値しない。漸進的であることは依然として1つの腕であり、それこそが継ぎ目が必要とするすべてである。そしてそれはRubyの配列変換可能なコピーオーバーロード（`Array.new([1, 2])`は2つのnilではなく`[1, 2]`）をただで吸収する。`nil`をシードすることが許容されるようになるのは、書き換えが`Nominal`キャリアの要素を撤回できるようになってからである —— それはコンストラクタの変更ではなく、`widen_for_mutator`の変更である。

同じ推論が**明示的な**プレースホルダーにも適用される: `Array.new(n, nil)`は`nil`を明示的に綴った「確保してから埋める」慣用形である（concurrent-rubyは`@Resolutions = ::Array.new(count, nil)`と書き、インデックスによって埋めている）。したがってnil**のみ**の要素も同様に漸進的な腕をシードする —— そうでなければまったく同じ理由で永続的になってしまい、埋められたスロットのすべての読み取りが正しいコード上で`undefined method '…' for nil`を引いてしまう。部分的にのみnilである埋め込み（`flag ? nil : "s"`）は両方の腕を保持する: ガードはnilを含む要素ではなく、nilのみの要素を読み取る。

宣言されたキャリアのセマンティクスの1つの帰結は、修正されるのではなく記録される: 埋め込み形式のクラスは、後から行われた異なる型の格納を生き延びるため、`acc = Array.new(n, true); acc[0] = false`は`Array[TrueClass]`のままになる。これは沈黙している —— 読み取りは`acc[0]`を定数へ畳み込まないため、always-truthyの判定は生じない —— そしてそれを修復することは上記の項目が名指しているのと同じ`widen_for_mutator`の変更である。

ゲート: `array_new_dynamic_seed`のフィクスチャがすべてのコンストラクタ形式が何をシードするかをピン留めし、両方の継ぎ目を通じて運び（発火してはならない）、DPの漸化式と`256.times { buf[i] = … }`バッファを「確保してから埋める」慣用形として運び、ユニオン埋め込みおよびネストしたコンテナの形状を保持する —— 一方で依然として閉じ、依然として厳密な`call.undefined-method`行セットを発火させなければならない新鮮な種の兄弟（`[]`リテラルと引数ゼロの`Array.new`）に対しても検証される。素の`Array`の答えを復元すると継ぎ目の例が赤になり、`nil`の種を復元すると慣用形の例が赤になり、ユニオン埋め込みを全体として判定したりコンテナの巡回を最外層レベルで止めたりするとコンテナの例が赤になる。リテラルサイズのタプル畳み込みは4つすべてから手を触れられない。

### WD2.13 — 自身のコレクションを読み取る格納は1回型付けされるのではなく反復される（2026-09-23）

WD2.5はブロックjoinをスライスAおよびBと同じ「`BodyFixpoint`の上限／拡大／フロア規律の下で」と規定していましたが、その継ぎ目は単一パスとして出荷されました: すべての格納の証拠をブロック進入スコープで1度だけ型付けしたのです。そこでは内容が変更された各コレクションは依然として呼び出し前の内容を保持しているため、そのコレクションから計算された格納は最初の反復の値を記録し、joinはそれを包摂して閉じてしまいました:

    h = { a: 0 }
    [:a, :a, :a].each { |k| h[k] = h[k] + 1 }
    puts "three" if h[:a] == 3   # always-falsey: hはHash[:a | Symbol, 0 | 1]と読まれた

`a << a.last + x`、`a.push(a.size)`、`a[0] += 1`、`h.store(k, h.fetch(k) + 1)`、およびエイリアス経由で読み戻された`each_with_object`メモ（`m[k] = m[k] + 1`）はすべて同一の欠陥です。それぞれが誤って精密であり、ブロックパスにおいて最もコストがかかります。なぜなら、そのjoinは意図的に漸進的な腕を追加しないからです: WD2.5の「joinパスがどれだけ見たか」は本体スキャンの証拠が完全であることに依存しており、格納の集合においては完全であったものの、それらの値においては古かったのです。

2つの修復策が考えられました。証拠が変更されたコレクションを読み取るすべての格納に1格納の漸進的フロアを与えることは健全かつ安価ですが、その`Dynamic`腕はコレクションの後続のあらゆる読み取りを沈黙させてしまい（`h[:a].upcase`が沈黙する）、エンジンが実際には境界付けできる格納の値に対して過剰です。**決定: 証拠を反復する。** ブロックの継ぎ目と`each_with_object`は1つのjoin（`StatementEvaluator#join_content_to_fixpoint`）を共有し、それがjoinする各名前を、いずれかの反復の進入時にそのコレクションが保持するものへと束縛します。joinされる名前はブロックのキャプチャされた内容変更ローカルであり、`each_with_object`の場合はメモも含まれます; その継ぎ目はメモのキャリアのみを保持するため、同じブロックが追加するキャプチャされたコレクションを読み取るメモ格納（`buf << w; m << buf.length`）は、呼び出し前の値ではなく`String`を読み取ります。格納のいずれも変更されたArrayやHashを読み取らない名前は**固定**（FIXED）です: その証拠はあらゆる反復で同一であるため、1度だけ型付けされ、名前は自身のjoinに加えてそのjoinが反駁するシードメンバー（その`nil`）へと束縛されます。Stringは常に`String`に固定されます。そのjoinは格納されたものを無視するためです。残りの名前は**変動**（MOVE）し、`BodyFixpoint`はそれらの証拠スロット（Arrayの要素ユニオン、Hashのキーユニオンと値ユニオン）をそれぞれ`bot`でシードして反復します。各パスは、変動するコレクションを固定コレクションと同様にこれまでの証拠に対するjoin＋そのjoinが反駁するシードメンバーに束縛した上で、変動する格納を再型付けします。別の変動コレクションがすでに成長した反復においても、`nil`シードは依然として`nil`であり得るためです。最終パスの値ピン留めは変動する証拠を拡大し、依然として成長するスロットはシード自身の腕の傍らに1つの未知格納フロアを取ります。`h`は`Hash[Symbol, 0 | Integer]`と読まれ、`nested << [nested.last]`は`Array[Dynamic[top] | []]`へとフロアされます。シードは0回反復の内容であるため、決して拡大されません。固定された名前の証拠も同様であり、自己読み取り格納の傍らの`acc << 1`は`Array[1]`とそれがサポートする真の畳み込みを維持します。これは第2の機構を追加するのではなくWD3に準拠します: 変動する証拠スロットは単に不動点の名前です。

固定／変動の分割とメモ継ぎ目のキャプチャされた名前は、すべての名前を反復しメモ継ぎ目にメモのみを与えていた最初の実装に対するレビューの修正です。Stringには証拠スロットがないため、変動したものとしてカウントされず、すべてのパスでシードのまま留まりました: `buf << w; lens << buf.length`は`Array[0]`と読み、`lens.last == 4`をalways-falseyと畳み込みました。また`BodyFixpoint`は最終パスですべての名前を拡大するため、何も読み取らない格納は、拡大を必要とする格納とブロックを共有するたびにその定数を失いました。証拠スコープでの名前の束縛は、継続のみのjoinが決して正しく扱う必要のなかった2つの経路を露呈させました。第1に、キャプチャされた変異のウォークは深さ >= 1で読み取られた任意のレシーバーをカウントするため、ネストしたブロック内で変異されたブロックパラメータがそれがシャドウする外側のローカルとして通り、それを束縛するとパラメータが上書きされました。第2に、joinはシードの`nil`をドロップするため、自身のjoinのみに束縛された固定名は`out << a.nil?; a ||= []; a << v`を`Array[false]`と読みました。どちらもmasterに対する新たな偽陽性であり、どちらも固定名がそのシードを保持する理由、およびキャプチャされた名前を見つけるウォークが深さ >= 1をテストするのではなく（これは本体内で直接の場合にのみ正しい）、読み取りの`depth`をそれがネストされているブロックやラムダと比較する理由です。同じ比較により、masterにも存在していたもう1つの経路が露呈しました: 自身のパラメータを束縛する内部ブロックにネストされた格納は、その名前がシャドウする外側のローカルである継ぎ目の進入スコープで証拠が型付けされていたため、`|inner| picks << inner.first`が外側の`inner = [0]`を読み取りました。そのような格納の証拠は現在、内部ブロックの名前を`Dynamic[top]`に束縛して型付けされます。また、変動する名前は最初のパスでのみシードを保持していたため、別のコレクションの成長後も生き残る`nil`を見逃していました; 現在はすべてのパスで保持します。反駁されたメンバーのみが戻り、シード全体ではありません: シードのリテラル形状を再追加するとディスパッチが十分に拡大し、`a = []; [1].each { a[0, 1] ||= [2] }`が収束を停止して`Array[2]`を失いました。

変動する名前を持たないブロックは単一パスを取るため、`acc = []; xs.each { |x| acc.push(x) }`は依然として`Array[Integer]`と読まれ（WD2.9）、一般的なブロックは変異メソッドの引数に対する1回のウォークを支払います。ループの継ぎ目は何も必要としませんでした: 証拠を`post_loop`に対して型付けし、そこでは本体内の直線joinがすでに束縛に漸進的な腕を与えているためです。

ここでは修正されるのではなく3つの残余が記録されています。すべてはこのjoinが所有していない束縛を通じて到達する同一の初回反復ピン留めです。証拠は、本体が再束縛（REBIND）するキャプチャされたローカルを呼び出し前の束縛で読み取っていました（`total = 0; out = []; [1, 2].each { |x| total += x; out << total }`は`Array[0]`と読みました; 後述のように解消済み）。そしてスライスAの再束縛不動点は、内容変更されたキャプチャを呼び出し前の内容で読み取ります（`last = nil; [1, 2].each { |x| last = a.last; a << x }`は`a = [0]`に対して`last`を`0?`に残します）。また、ブロックが削除メソッドを通じてのみ変更するコレクション（`a.shift; b << a.first`）やエイリアスを通じてのみ変更するコレクションは、まったくjoinされる名前ではないため、それを読み取る格納は呼び出し前の内容を見ます; どちらの経路もこの不動点より前から存在します。最終パスの拡大もさらなるパスなしに信頼され、これは`BodyFixpoint`自身の形状でありスライスAも同様です。拡大された境界の後にのみクラスが変わる値を持つ格納（11回の反復にわたる`h[k] = h[k] == 10 ? :done : h[k] + 1`）は、依然として`:done`なしで`0 | Integer`と読みます。拡大された仮定の再チェックはすべてのスライスで一度に`BodyFixpoint`に属し、#1220です。これとは別に、ガードされた変異の後にjoinは依然としてシードの`nil`をドロップし（`maybe << v if maybe`は`maybe`がnilのままであり得るにもかかわらず`Array[…]`を残す）、WD2.11のルールはその推論がカバーしていなかったケースに直面しています; これは#1219であり、フィクスチャのゴールデンは反転コメントを運びます。

ゲート: `block_content_self_read`フィクスチャは、6つの自己読み取り形状、String読み取りと2つの`each_with_object`キャプチャ読み取り、変異された外側ローカルをシャドウするパラメータ、1レベル深く読み取られるネストしたブロック自身のパラメータ、遅延初期化されたキャプチャ、および別の変動格納によって読み取られる`nil`シード（発火してはならず、それぞれ`assert_type`によってピン留めされる）、構造的フロア、および#586アキュムレータを運びます。また、always-falseyが依然として発火しなければならない2つの対照群（レシーバー独立の値を格納する同一のカウンタ、および自己読み取り格納とブロックを共有する`acc << 1`）も持ちます。specは正確な`flow.*`の行セットをアサートするため、あらゆる場所で漸進的になった継ぎ目は古いピン留めとまったく同じように騒々しく失敗します。
`block_content_rebound_capture`フィクスチャは第1の残余の解消をゲートします。その発火してはならない（must-not-fire）ケースは、それぞれ本体が書き込むローカルを格納します:

*（第1の残余は解消されました、2026-09-23。）* この解消は保守的なものです。本体が書き込むローカルを読み取る格納は、現在そのローカルを`Dynamic[top]`として型付けし（`StatementEvaluator#shadow_rebound_reads`）、これにより`out`は`Array[Dynamic[top]]`と読まれ、`out.last == 3`はもはや畳み込まれません。対象となるローカルは、本体が再束縛する外側のローカル、および本体が再代入するブロックパラメータまたは`;`ローカルです。パラメータのデフォルト値における書き込みもカウントされます。内部ブロックが導入する名前に対するその内部ブロック内での書き込みは、別の変数であるためカウントされず、ブロックが定義するメソッド本体内での書き込みもカウントされません。本体が再束縛も行う結合されたコレクションもカウントされます。結合の種がスライスAの継続を運ぶためです。本体が導入するローカルはすでに`Dynamic[top]`と読まれていました。

- 再束縛されたローカル自体は、スライスAがそれに与えるものを維持します。

*（第2の残余は解消されました、2026-09-23。）* スライスAのパスは現在、各変異箇所における未知の値の格納に対して広げられた呼び出し箇所の束縛 —— `Inference::UnknownStoreWidening`（要素ごとのフォールドがすでにあらゆる位置の下に敷いている束縛）において、本体がその場で変異させるキャプチャされたすべてのローカルを読み取ります。本体が再束縛と変異の双方を行う名前は、フォールドがそれを広げるのと同様に（#587 (b)）、パスの実行中の仮定に対して同じ広げを取ります: 仮定は本体の直線的な継ぎ目の出口を運び、漸進的な腕なしでコレクションを閉じることができます。`a = [0]`に対する`last = a.last; a << x`は`0 | Dynamic[top] | nil`と読まれ、`last == 1`はもはや畳み込まれません。

2つの修復策が考えられ、コーパスがそれらの間で決定を下しました。スライスAをこのjoinと共同で反復させ、それぞれが相手の実行中の束縛を読み取るようにすれば、再束縛を正確に型付けし（`0 | 1 | 2 | nil`）、第1の残余にも到達することができます。その代償は、毎回のパスで証拠を再型付けし、`eval_call`が別個に実行している2つの継ぎ目をマージすることです。**決定: 未知格納の束縛。** これは本体を評価せず広げのみを行い、キャプチャされたものを何も変異させないブロックには触れません: `sum = 0; xs.each { |x| sum += x }`はその3つのパスを維持します。そのコストは、ArrayまたはHashから読み取られた再束縛における漸進的な腕です; Stringのキャプチャは`String`へと広げられ、それを必要としません。共同反復がもたらす精度を利用するコーパスコードは存在しません。32の調査ターゲット（8,725件の診断）にわたる計測用の初期実装は、再束縛の束縛を変更することなく40のブロック箇所で作動し、最終的な変更はいかなる診断も動かしません。`lib`セルフチェックにおけるアロケーション数は3,370万個中+3,775個のコストです。

敵対的レビュー（adversarial review）により、初期実装が依然として固定していた4つの経路が発見され、すべてここで解消されました。単独の削除子、または追加子の手前に書かれた削除子（`p = s.pop; s.push(x)`）は、漸進的な腕なしでリテラルを名前的型へと閉じました。その後、追加子がその名前的型を辞退し、`h.delete(:a)`配下の`{ a: 0 }`は、Rubyが`nil`と応答する箇所で`h[:b]`を`0`と読み取りました。`UnknownStoreWidening`は現在、それがどのような種類の箇所であれ、`Tuple`や`HashShape`を閉じる箇所に漸進的な腕を与えるため、`Tuple`や`HashShape`の種に対して、回答は箇所が書かれた順序に依存しなくなりました。再束縛され変異された名前が第2の経路であり、上記でカバーされています。第3は、外側の名前を共有するネストしたブロック自身のパラメータ（`[[9]].each { |a| a << x }`）であり、`CapturedLocals.content_mutations`がそれを外側ローカルの変異としてカウントしていました。現在は、すべてのネストしたブロックを越えて解決された場合にのみ読み取りをカウントします。第4は呼び出し前に閉じられた種でした: `s = [0, 9]; s.pop`は値が固定された`Array[0 | 9]`を残し、広げがそれを宣言された名前的型と同様に辞退するため、すべてのパスがその固定値を読み取っていました。結果が依然として値固定のコレクションである広げは、現在代わりに漸進的な腕を取るようになり、リファインメントの基底も含まれます（`if s.any?`配下では、`pop`は`non-empty-array[0 | 9]`を同じ固定された名前的型へと落とします）。

オープンなまま留まるのは、スライスAが所有していない束縛を通じた同じ固定です。その場変異の前に読み取られるインスタンス変数（`last = @a.last; @a << x`）は収集されません（#1208）。ブロックローカルなエイリアス（`b = a; b << x`）はスキャンから変異を隠します。何も再束縛せず読み取りを返すブロック（名前的レシーバーに対する`xs.map { v = a.last; a << x; v }`）はブロック戻り値パスを通り、これはWD2.10の総称的な`Array[U]`の残余です。

ゲート: `block_rebind_reads_mutated_capture`フィクスチャは、10個の発火してはならない（must-not-fire）形状を運びます: 末尾、Hashスロット、空性、Stringサイズ、追加子の手前の削除子、スロットの書き換え子、単独の削除子、再束縛かつ変異、およびガードなしとガード配下の呼び出し前に閉じられた種。最初の5つは`assert_type`によって固定されています。2つの対照群（本体が変異させないコレクション、および外側の名前を共有する内部ブロックパラメータ）は依然として発火しなければなりません。specは正確な`flow.*`の行セット、本体が格納した値に対していかなるエラーも発火しないこと、およびアキュムレータのパスカウントをアサートします。

### WD3 — 一つの機構、共有

スライスAとBは**一つ**の不動点ヘルパー（入力として本体評価器＋書き込みローカルの集合＋上限＋広げ方針）を実装するのであって、2つのコピーではない──ADR-55の手書きコピーコンストラクタの教訓（2つの沈黙したテーブルドロップのバグ）が適用される。予算上限はハードかつ設定不可である（ADR-41 WD4）。新しい`BudgetTrace`カウンタが非収束の崩れを記録する。

### WD4 — ゲート: ゼロ差分ではなく裁定

スライスごとに`make verify`＋コーパス実行（Mastodonの`app/models`、haml、jbuilder、kramdown）、加えて手でプローブした弁別形（ADR-55の教訓: バイト同一のコーパスが`bot`の健全性バグを見逃した──型ダンププローブはゲートの一部であって省略可能ではない）。修正が*誤った定数を訂正する*ため、新しいdiagnosticはありうるし、**本物**でありうる（本当にnil／より広い型を見うるコード）──新しい発火はどれも裁定される: 本物 → 残し、その発火をスライスノートに記録する。エンジンの人工物（新たに覆いが外れた盲点）→ 着地前に修正または狭める。diagnosticの*除去*は期待される勝利である（それらは潜在的な誤定数のFPだった）。perfはニュートラルに保たれなければならない: ブロック本体が上限回まで再評価されるのは、キャプチャされたローカルに書き込む場合のみだ──圧倒的多数のブロックは何も書き込まず、現在どおり1回の評価で済む。

## 却下／先送りした代替案

- **無差別な「どんなブロックもキャプチャされたローカルをDynamicへ無効化する」**。却下──仕様は「yieldがすべてを無効化する」よりcall-timingモデル化を明示的に好み、それはあらゆるコーパスのあらゆるeach/mapにわたってナローイングの精度を破壊するだろう。
- **単一パスjoin（不動点なし）、常に名前的へ広げる**。主機構としては却下──累積する形（`a = [a]`式の構造的成長）は単一パスを逃れる。Dynamicフロア付きの有界不動点は厳密に安全であり、ADR-55のパターンを再利用する。（最初の実装は同じヘルパーの反復1の本体として単一パス＋広げを着地させてMAYだが、上限／フロアは最初から存在しなければならない。）
- **`:non_escaping`ブロックを1回限り（出口スコープを直接採用）として扱う**。却下──0反復パス（`[].each`）とN反復累積に対して不健全。
- **メソッドごとの反復回数サマリー（each＝N、tap＝1、…）**。先送り──仕様のcall-timingカテゴリーはこれを誘うが、事前状態とのjoin不動点はそれらなしで健全である。サマリーは後の精度リファインメントである（例: `tap`が正確に1回として出口スコープを採用する）。

## 帰結

- `fact3`式のアキュムレータループが誤った定数を生むのをやめる──エンジンで既知の最大クラスの不健全な畳み込みであり、下流の常に真／到達可能性のdiagnosticがそれらを消費するのをやめる。
- 現在畳み込まれている一部の定数が広がる。誤った畳み込みに沈黙して依存していたdiagnosticはどれも表面化し、裁定される（WD4）。
- 実装がついに §「Fact stability and mutation」のキャプチャされたローカルのMUSTを満たす。仕様の変更は不要である。
