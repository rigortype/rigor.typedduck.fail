ステータス: **提案（Proposed）、2026-09-21**。Rigor自身の開発フロー（および後のSteins）を対象とした、pi.devベースのロール拘束型マルチモデルハーネスの恒常的な形状を記録する。`agents/pi-harness/`の下の薄いスタブがこの修正とともに着地する;決定は並列受け入れパス（WD6）が一度機能するまでProposedのまま留まる。

根拠: [`docs/notes/20260921-takt-trial-setup.md`](../../notes/20260921-takt-trial-setup/)（#1090 / PR #1144におけるTAKTトライアルセットアップ＋結果）。

## コンテキスト

多くのコーディングエージェントを手動で実行すること（Claude Codeセッション、アドホックなモデル切り替え、ハーネス間のコピー＆ペースト）は、[ハーネスタックス（Harness Tax）](https://harnesstax.github.io/)を支払うことになる: トークンと注意力は作業ではなくシャトル（往復）に向かう。piは最小限で拡張可能なエージェントハーネスである;有用な動きは、単一の「最善の」モデルを追い求めることではなく、**ロールをモデルに束縛し、契約をパッケージ化すること**である。

Rigorにはすでに機能しているエージェント開発パターン（トリアージ → GitHub Issues → ワークツリー並列実装 → 敵対的レビュー → ゲートとしてのリモートCI → マージ）が存在し、Claudeプロジェクトメモリ内および`docs/agents/`（特に[`contribution-flow.md`](../../agents/contribution-flow/)、[`measurement.md`](../../agents/measurement/)）に苦心して得られた運用上の制約がある。ハーネスはそのパターンをエンコードしなければならず、[ADR-98](../98-development-flow-document-roles/)のバックログ規則を置き換えてはならない。

観察された苦痛: 安価で高速なモデル（例: DeepSeek Flash）を**方向性決定**に割り当てると、迅速なdiffと引き換えに高価なポリシーの混乱（thrash）が生じる。安価なキャパシティはアーキテクチャ設計ではなく、**並列の自由度**に属する。

Rigorが所有する3つのフローが視野にある（v1はAを優先し、BとCがそれに続く）:

- **A. 自社実装（Own-implementation）** ── 方向性決定 → ベースライン実装 → 同一形状の並列レーン。
- **B. 調査 → issue起票（Survey → issues）** ── 並列コーパス／`rigor-survey`プローブ → 統合 → issue起票。
- **C. ドキュメント（Docs）** ── JAサイト公開およびENドキュメント完成（ドキュメント専用）。

### pi対takt

**pi**は、ロール×モデルの束縛および並列レーン契約のためのパッケージサーフェスである（本ADR）。**takt**は、長時間の品質安定ループ（計画 → 実装 → ドラフトPR → CI → 敵対的レビュー → 修正）のためのオプションのオーケストレーターである。両者は相補的である: piがロール契約を所有し、takt（または将来のインツリーオーケストレーター）がそれらを消費する長いループを駆動できる。v1はtaktを要求しない; piスキル上の薄いarchitect→laneパスでWD6を証明するのに十分である。

### トライアルの知見（2026-09-21）

#1090上での`rigor-ready-for-agent`のアテンド付きTAKT実行は、人間の介入の後にドラフトPR #1144を生成した。2つの再発するボトルネック:

1. **非インタラクティブなgit push / PR作成**は、エージェントセッション内でしばしば人間の承認を必要とする ── 出荷ステップが無人であると仮定することはできない。
2. **エージェントセッション内でのCI待機**は、sleep/monitorツールが拒否されるとストールする。オーケストレーターがポーリングごとのツール承認なしに待機できるようになるまでは、**外部ポーリング＋再開**が機能する。

これらはWD4（レーンは長時間のCIウォッチャーを所有しない）を強化し、CIの所有権をレーンではなくオーケストレーター／外部ポーラーへと向ける。

## 決定

**Rigor内部でインキュベート**し、まずは**自社ソフトウェア**のワークフローを対象として、**pi上のロール拘束型マルチモデルハーネス**を採用する。

**基準:**ロールは、（1）入力契約と受け入れゲートが上位ティアのロールによってすでに固定されており、かつ（2）失敗モードがポリシー設定ではなくローカルなもの（不良なレーンは破棄または書き直される）である場合にのみ、より安価／高速なモデルを使用できる。タスクが方向性決定、契約、またはマージ判断を設定する場合、それはOpus/Grokクラス（または敵対的エンジンレビューのためのFable）に留まる。ドキュメント専用の品質作業にはGemini Flashを使用できる。

### WD1 ── 自社ソフトウェア優先

v1はRigor（および後の同型なSteins）をターゲットとする。外部OSSへの貢献は異なる苦痛（上流の規範、遅延するレビュー）を伴うため、先送りされる。

### WD2 ── パッケージ内でモデル束縛された5つのロール

| ロール | モデル帯域 | 所有対象 |
| --- | --- | --- |
| `architect` | Opus / Grok | 方向性決定、契約、計画 |
| `lane` | DeepSeek Flash | ワークツリー並列の模倣; head SHAをpushして終了 |
| `reviewer` | Fable（またはOpus/Grokクラス） | エンジン変更の敵対的レビュー |
| `docs` | Gemini Flash | JA公開＋ENドキュメント完成; **ドキュメント専用** |
| `orchestrator` | Opus / Grokクラス | issue選択、CI監視、マージ判断 |

束縛はpiのプロンプトテンプレート／スキル内に存在するため、自由な`/model`切り替えによってarchitectタスクが静かに降格されることはない。これら5つの外側の周辺ドラフトにはOpenCodeを引き続き利用できる。

### WD3 ── インツリーでインキュベートし、その後に抽出

まずRigorの下に薄いパッケージを着地させる（プロンプト／スキル＋I/O契約;例: `agents/pi-harness/`）。Steinsと共有可能なコア（`orchestrator` + `lane` + `reviewer` + `docs`）が安定したら、[`rigortype`](https://github.com/rigortype)の下の新しいリポジトリへと抽出する。Rigor専用のスキルはインストール可能なアドオンとして残る。

### WD4 ── 既存のレーン／ゲート規律を維持

ハーネスは現在のルールを弱めてはならない: ホスト上での並列フルスイートゲートは禁止;リモートCIを推奨;レーンは長時間生存するCIウォッチャーを所有しない;調査ターゲットには互いに素なチェックアウトが必要; Issuesが引き続きバックログである（ADR-98）。詳細は`docs/agents/`およびプロジェクトメモリに留まる ── 本ADRはそのカタログを重複して記載しない。

### WD5 ── miseはこのハーネスではない

miseはランタイムとパッケージマネージャーのみにとどまる。マシンのブートストラップ／dotfileの所有権はここではスコープ外である。

### WD6 ── 並列の準備状況（v1受け入れ基準）

このパスが**一度**機能したときにv1は成功する:

1. `architect`がスコープを定めた変更に対する契約を固定する。
2. **N個**の互いに素なワークツリーレーン（DeepSeek Flashクラス）がそれらの契約の下で実装する。
3. 各レーンが**そのhead SHAをpushして停止する**（CIウォッチャーなし）。
4. `orchestrator`（または外部ポーリング＋再開）がCIを所有する。
5. 敵対的レビュアーが結果を判定する: **デフォルトはGrok:max**;実装が複雑と判断された場合は**Opus:high**を追加;複雑な設計には**Fable:mediumを確保**。最終的な`Approved`には、diffに合わせた**PR本文改訂ドラフト**および**提案PRコメント**を含めなければならない（主張は現実に一致しなければならない）。任意の`Needs fix` → 修正ループ。

調査（B）およびドキュメント（C）はそのパスが一度着地するまで待つ。`agents/pi-harness/`内のスタブは受け入れ証明ではない;エンドツーエンドの実行こそが証明である。

## 却下／先送りした代替案

| 代替案 | なぜ採用しないか（v1向け） |
| --- | --- |
| まったく新しい空の`rigortype/*`リポジトリとして開始する | Rigorの規約とのフィードバックループが遅すぎる;まずインキュベートする（WD3）。 |
| すべてのフェーズで単一モデル／単一エージェントを使用する | ハーネスタックスを支払うことになる;安価なモデルを方向性決定に使用するとポリシーが混乱する。 |
| Flash（または同等品）を`architect`とする | 方向性の手戻りを引き起こす;決定基準に違反する。 |
| エンジンの敵対的レビューにGeminiを使用する | 失敗モードが誤っている; Geminiはドキュメントティアである（WD2）。 |
| ハーネスをmiseブートストラップ／自己保存dotfilesに配置する | mise-as-runtimesのスコープと衝突する（WD5）。 |
| 同じv1パッケージに外部OSS貢献を含める | 異なる苦痛を伴う;先送りする（WD1）。 |
| 唯一のv1オーケストレーターとしてtaktを必須とする | taktはオプションである; pi契約は自立していなければならない（pi対takt）。 |
| レーン所有の長時間のCIスリープループ | トライアルの知見: エージェントセッションの待機はツールの承認でストールする;オーケストレーター／外部ポーリングがCIを所有する（WD4、WD6）。 |

## 帰結

**肯定的**。ロール契約を配置する明確な場所ができる;サブスクリプションキャパシティ（Claude / Grok / OpenCode / Gemini）が職務にマッピングされる; Steinsが後に抽出されたコアを再利用できる。TAKTトライアルのボトルネック（pushの承認、CI待機）は、伝承ではなく明示的な受け入れ制約となった。

**否定的**。抽出までは、Rigorは別のインツリーエージェントアーティファクトを抱えることになる;モデルの変更に伴いロール束縛の定期的な再調整が必要となる。セッションが非インタラクティブに出荷できるようになるまでは、push/PRのための人間参加型（human-in-the-loop）が残る。

**キャリーオーバー**。1つのarchitect→laneパスをエンドツーエンドで配線する（WD6）;その後で初めて調査（B）とドキュメント（C）を行う。抽出トリガーを再評価する: Steinsが同じ4つの共有ロールを求めるか、第2の消費者が現れたとき。オーケストレーターがティックごとの承認なしにポーリングできるようになったら、セッション内CI待機を再検討する。
