## コンテキスト

#1120によってRigorはRubyのリファインメント（refinement）がどこで有効かを学習したが、それは`call.undefined-method`を**沈黙させる**ためだけであった。2つのギャップが残されている。第1に、リファインメントを通じた呼び出しは依然としてリファインされていないメソッドとして型付け・チェックされる: `M`が`Symbol#[]`を再定義している場合の`using M; :a[:b]`は引数の不一致を報告し、`String?`として型付けされる。第2に、Ruby 4.1の`Proc#refined`によってブロックスコープのリファインメントが復活し、その動機となったライブラリ（activerecord-refined）はそれらを**被呼び出し側（callee）**でアクティブ化する（`block.refined(M)`）が、ブロック自身のサイトではそれを表すものが何もない。

意図は、字句的であれ`Proc#refined`経由であれ、リファインメントを使用する正しいプログラムが、リファインメントなしでは生成されない診断を一切生成せず、かつリファインされた呼び出しに対してRigorが報告する型が、そのリファインメントが置き換えたメソッドの型を決して取らないことである。

## 決定

**基準: 有効なリファインメントはメソッドを置き換えるため、その回答はクラスの回答を完全に置き換える。Rigorが置き換えを読み取れない場合、回答はunknown（`Dynamic[top]`）となる。置き換えられたメソッドのシグネチャになることは決してない**。置き換えられたメソッドのRBSは、その呼び出しサイトでは実行されないコードを記述しているため、そこにフォールバックすることは自信を持った誤答（confident wrong answer）となり、これはADR-5が最悪と位置づける失敗である。

### WD1 ── 1つの順序付きリスト: 有効なリファインメント

あらゆるプログラムポイントにおいて、Rigorはリファインするモジュールの1つの**順序付きリスト**を回答する（`CONTEXT.md` § 有効なリファインメント）。後のアクティベーションが前のものに勝つ。リスト内にすでに存在するモジュールのアクティベートは何も変更しないため、リストはモジュールを最初の位置に保持する（`rb_using_refinement`が早期リターンする、CRuby `eval.c`; `using A; using B; using A`は依然としてBのメソッドと答える）。Ruby自身の順序に従い、4つのソースがこれを供給する:

- 字句的な`using`（テキスト順、外側の本体が内側の本体より前）;
- `refine`ブロック自身のモジュール（そのブロック内部）;
- `Proc#refined`のレシーバーであるProcリテラル（`->{}`、`proc {}`、`lambda {}`）: リテラルの字句リスト、次いで呼び出し順での各`.refined`引数（CRubyはブロックのcrefを複製してから追加する）。最初にローカル変数にバインドされ後からリファインされたProc（`l = ->{}; l.refined(M)`）はカバーされないため、その本体はリファインされた呼び出しを報告し続ける: 既知の偽陽性であり、調査コーパスがその形状を示すまで受け入れられる;
- プラグインがリファインされていると宣言したブロック（WD5）: ブロックの字句リスト、次いで宣言されたモジュール。

モジュールが`include`したモジュールはその手前に展開されるため、includerが勝つ（#1671）。非定数の`using`は*unknown*マーカーを貢献する。チェックルールと型付け器（typer）は同じリストを読み取る（#1673）。2つのリストが存在すると、呼び出しがリファインされたものとして沈黙し、リファインされていないものとして型付けされてしまう。

### WD2 ── 型付けアームは他のあらゆる回答の前に位置する

リファインされたアームは、`ExpressionTyper#call_result_type_for`において`indexed_narrowing_for`の直後に実行され、`try_literal_send`、`try_local_def_dispatch`、`try_receiver_block_folds`、`try_overriding_def_dispatch`、および`MethodDispatcher.dispatch`の前に位置する。それらはいずれもリファインメントが置き換えるメソッドから回答するためである: リファインされた`String#upcase`は畳み込まれてはならず（fold）、Tuple上のリファインされた`map`は要素ごとに畳み込まれてはならず、トップレベルの`def`は`Object`のリファインメントの手前でバインドしてはならず、プラグインはクラス自身のメソッドをモデル化する。

優先順位は`refinements.rdoc` § Method Lookupに従う。最も派生したクラスからレシーバーのクラスをウォークし、シングルトンクラスが最初となる。各クラスにおいて、そのクラスに対してその名前をリファインする最新の有効なモジュールが勝つ;それ以外の場合は、そのprependされたモジュール、自身のメソッド、およびそのincludeされたモジュールがその順序で回答する;それ以外の場合は次へ進む。したがって、`C`のリファインメントは`C`にprependされたモジュールに勝ち（Ruby 4.0.5上で実証）、モジュールのリファインメントはそのモジュールが位置する場所で決定される。より派生したクラス上のメソッドは、より派生していないクラスのリファインメントに勝つ。「メソッドを定義している」はRBSおよびプロジェクトの`def`から読み取られる。コアRBSは継承されたメソッドをサブクラス上で再宣言することがあり、ウォークはその時点で停止してリファインメントを辞退する: 既知の不精密さであり、`Object`、`Kernel`、`Comparable`、または`Numeric`のリファインメントに対して辞退する方向となる。ユニオンレシーバーはメンバーごとに決定され、`Dynamic`レシーバーは`Dynamic`のままとなる。

### WD3 ── アームが返すもの

呼び出しのレシーバーを`self`として、勝利したrefine本体の`def`の推論された戻り値型を返す。その本体が解析可能でない場合、`Dynamic[top]`を返す。これは本体が推論されないgemのリファインメント（#1672）、およびいずれかのリファインメントが名前を定義している中でリストがunknownマーカーを運んでいる場合をカバーする。refine本体内の`super`は、現在のリファインメントを除き、**`super`サイトで**有効な次のリファインメントへと継続し、その後にのみリファインされたクラスへと継続する（`refinements.rdoc` § super）。Rigorは、refine本体自身の有効なリスト内の他のモジュールがその名前をリファインしていない場合はリファインされたクラス自身のメソッドに対して型付けし、リファインしている場合は`Dynamic[top]`として型付けする。そのチェーンを精密に追跡することは先送りされる。リファインされた呼び出しは引数型とアリティのチェックをスキップする。refine本体のパラメータは未宣言メソッドと同様にバインドされ、チェック対象となるものを持たないためである。リファインされたProc内では、ネストされた`def`はProcのリファインメントを保持し、`using`は実行時に例外を発生させるため、リストに何も追加しない。

### WD4 ── 直接呼び出しは型付けされ、リファインされた間接呼び出しはunknown

このアームは`recv.m`、演算子、および暗黙的self呼び出しを型付けする。`send`、`public_send`、および`&:m`もリファインメントを尊重する（CRuby `test/ruby/test_refinement.rb`: `test_send_should_use_refinements`、`test_public_send_should_use_refinements`、`test_symbol_proc`）。それらが到達する名前がレシーバーに対して有効にリファインされている場合、`Dynamic[top]`と答え、引数チェックをスキップする;アームを通じてそれらを型付けすることは先送りされる。`respond_to?`および`method`もリファインメントを尊重するため（`test_respond_to_should_use_refinements`; Ruby 4.0.5上で実証）、リファインされた名前に対しては`Dynamic[top]`と答え、`false`に畳み込まれることは決してない。`methods`のみがリファインメントを無視し、現状の回答を維持する。

### WD5 ── プラグインは被呼び出し側でアクティベートされたリファインメントを宣言する

`Plugin::Macro::BlockAsMethod`は`refinements:`（モジュール名）を獲得する。また`self_type: :lexical`も受け付け、これは`self`を非バインドのまま残すため、`instance_exec(&block.refined(M))`だけでなく`block.refined(M).call`も表現可能となる。1つのエントリーがactiverecord-refinedの契約の両半分を担う。

### WD6 ── デフォルトでオン

このアームはbleeding-edgeフラグなしで出荷される。調査コーパスにおいてリファインメントは稀である。この変更はRigorが誤りと認識していた型を除去するが、以前はリファインされた呼び出しがフェイルソフトであった箇所に型を追加する（`:a.shout`が`String`になる）ため、下流の呼び出しが初めてチェックされ、新たな指摘が生じる可能性がある。リリースゲートのOSSスイープがそのチェックとなる。`:behaviour`フラグは解析キャッシュの同一性（`lib/rigor/bleeding_edge.rb`）にも入らなければならず、リスク以上のコストがかかる。

## 却下および先送りされた代替案

| 代替案 | 採用しなかった理由 |
| --- | --- |
| 本体の読み取りが不可能な場合にリファインされたクラスのRBSにフォールバックする | リファインメントが置き換えたシグネチャ（動機となったプローブの`String?`）で回答してしまう。 |
| 有効なすべてのリファインメントの戻り値をユニオンする | Rubyはアクティベーション順により1つの勝者を選ぶ;ユニオンはいかなる実行よりも広く、境界において依然として誤っている。 |
| リファインメントを沈黙専用のまま維持する | すべてのリファインされたチェーン（`:t[:c].in?(…)`）が、最初のリンクから下流に向かって誤ったクラスに対して型付けされてしまう。 |
| `BlockAsMethod`フィールドの代わりに別個の`RefinedBlock`マクロを設ける | activerecord-refinedは同じ呼び出し上で`self`バインディングとリファインメントの両方を必要とする; 2つのエントリーを同期させ続ける必要がある。 |
| プロジェクトメソッド自身の`&blk.refined(Const)`本体から被呼び出し側のアクティベーションを推論する | 手続き間解析となりウォームキャッシュに敏感であり、gemには到達できない。調査コーパスがプロジェクトローカルな`Proc#refined` DSLを示すまで先送り。 |
| `Proc#refined`のシグネチャを`target_ruby >= 4.1`でゲートする | デフォルトの`target_ruby`のもとで、すべての正しい4.1呼び出しが報告されてしまう（#1665）。 |

## 結果

- プラス面: リファインされた呼び出しが引数や未定義メソッドの指摘を生成しなくなり、その型が置き換えられたメソッドの戻り値を伝播しなくなる。
- マイナス面: `discovered_refinements`はすでにシードバンドル内を伝達しているが、refine本体のdefハンドルはそうではない; `(module, class, method) → def`テーブルは、ウォームキャッシュが運ぶ新たな状態となる。gemのリファインメントは、プラグインまたはRBSがより多くの情報を提供できるようになるまで、`Dynamic[top]`として型付けされる。
- 繰り越し事項: プラグインが宣言するリファインされた呼び出しの戻り値型（activerecord-refinedのカラムノード向け）、型付けされた間接呼び出し、精密な`super`チェーン、およびバインド後にリファインされたProcは未決である。#1669が最初の事項を決定する。

## 他のADRとの関係

ADR-5（頑健性: 誤った回答よりも`Dynamic`）がこの基準の根拠である。ADR-16ティアAが`BlockAsMethod`を所有し、WD5がこれを拡張する。ADR-110のオーバーライドdefディスパッチがWD2のスロットの先例である。ADR-50 WD2が、WD6が辞退するbleeding-edgeオーバーレイを定義している。
