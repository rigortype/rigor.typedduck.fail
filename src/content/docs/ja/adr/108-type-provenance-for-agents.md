Status: **Accepted, 2026-09-08 — [#826](https://github.com/rigortype/rigor/pull/826)により実装**。
`skills/rigor-type-oracle/`（本文＋3つの`references/`＋4ケースの評価スイート）、`rigor-project-init`が導入先プロジェクトの`AGENTS.md` / `CLAUDE.md`にインストールする契約段落（Phase 8a、`references/06-agent-contract.md`）、およびカタログ配線（[`lib/rigor/cli/skill_describe.rb`](https://github.com/rigortype/rigor/blob/master/lib/rigor/cli/skill_describe.rb)の`CATALOG_ORDER`、`skills/README.md`、およびマニュアルの「ここから始める」で覚えておくべきスキルが2つから3つに増加）を出荷します。ADR-107はそのリポジトリ側の双子です: 同じルールをRigor自身のツリーへと内向きに適用し、そこではさらに型のようなコメントを禁止します。エンジン内の変更はありません。

根拠: 下記の§「証拠」に記録されている2026-09-08の5モデル調査（現在は`skills/rigor-type-oracle/evals/fixtures/budget_ledger.rb`として同梱されているフィクスチャ上で実行）；そのフィクスチャに対するオラクル自身の回答（インストールされたCLIに対して検証され、`references/01-oracle-commands.md`に記録）。

## 背景

Rigorには昔からオラクルが存在していました。`rigor type-of FILE:LINE:COL`は指定位置の推論された型を出力し、`rigor annotate FILE`はファイル内の各行を1回の呼び出しで型付けし、`rigor sig-gen --print`はメソッドのシグネチャを出力し、`rigor trace`は型がどのように構築されたかを再生し、`rigor explain`は発火したルールをドキュメント化します — そしてMCPサーバー（[ADR-33](../33-mcp-server/)）により、これら同じ5つがツール呼び出し（`rigor_type_of`、`rigor_annotate`、`rigor_sig_gen`、`rigor_check`、`rigor_explain`）として利用可能です。

欠けていたのはコマンドではありません。ある特定の瞬間におけるルーティングでした: **エージェントが型を書こうとしたり、型を主張しようとしたりする瞬間です**。その瞬間がタスクの主題であることはほとんどありません。「このクラスを文書化する」、「このバグを修正する」、「このファイルにRBSを追加する」、「このPRをレビューする」という作業の第3ステップであるため、質問の形をとっていません。これが、[ADR-74](../74-offline-doc-access-and-llms-txt/)の`rigor-ask`がそこに届かない理由です。`rigor-ask`はユーザーが何かを尋ねたときに発火します。`@param currency [String]`を書こうとしているエージェントは何も尋ねていません。自信を持っているのです。

[ADR-0](../0-concept/)のコンテキスト段落は、すでにそのステークスを名指ししていました — 過剰なインラインアノテーションは「人間の開発者とAIコーディングアシスタント（LLM）の双方にノイズをもたらす」とし、インラインDSLを持たないというコミットメント全体がそこから導かれています。その前提は、エージェントが何を*読まなければならないか*に関するものでした。下記の調査はその反対側、すなわち何も誘導がないときにエージェントが何を*書くか*を測定しています。チェック対象の位置にある推測された型は、型がないことよりも有害です。パスしてしまう可能性があるからです — そして[ADR-93](../93-default-rbs-inline-ingestion/)の下ではrbs-inlineの取り込みがデフォルトで有効になっているため、推測された`#:`行はもはや単なるコメントではありません。エンジンが信じる生きた契約になってしまいます。

メンテナーによる位置づけであり、これがスキルのコミットではなくADRである理由: *AIエージェントを誘導し、コードベースを読んで推論する代わりにRigorから決定論的な型を取得させることは、Rigorが提供できる最も本質的な機能かもしれない。*すべてのチェッカーは、エージェントが書いた後にそれが間違っていると告げることができます。決定論的なオラクルを持つツールは、書く前に何が正しいかを告げることができます。

## 証拠 — 2026-09-08の5モデル調査

5つのモデル、各1サンプル: サブエージェントとしてのClaude Haiku / Sonnet / Opus；OpenCode経由のDeepSeek V4 ProおよびQwen3.7 Max。フィクスチャは現在`evals/fixtures/budget_ledger.rb`に出荷されているクラスです — 意図的に文書化されておらず、意図的に一部推論不可能な箇所を含んでいます。

**ラウンド1 — 模範（exemplar）あり**。型なしYARDですでに文書化されているファイル、5つのタスク:

| タスク | 結果（n=5） |
| --- | --- |
| 型なしYARD形式を模倣する | 5/5、角括弧付きタグはゼロ |
| 明示されたルールに従う | 5/5 |
| 「`@param format …`は何の型を明記しているか？」 | 5/5が「明記されていない」と回答し、散文の制約を正しく抽出した |
| パラメータの改名を`@param`に伝播させる | 5/5 |
| RDocスタイルの兄弟ファイルを模倣する | 5/5、`call-seq`なし、型用語なし |

模倣は失敗モードではありません。コピーすべき形式や従うべきルールが与えられれば、すべてのモデルがそれに従いました。

**ラウンド2 — 模範なし**。文書化されていないクラス、2つのアーム:

| アーム | 結果（n=5） |
| --- | --- |
| `AGENTS.md`に契約段落が存在する | **角括弧付きの`@param` / `@return`を書いたのは0/5**。逸脱は2件、いずれも`@raise`に関するもの: Opusは例外クラスを省略し、Qwenは`@raise [ArgumentError]`を書いた — これはソースが証明しているため（`raise ArgumentError`）、推測というよりは形式の逸脱 |
| ルールが一切ない | **4/5が推測された型を書いた**。Haiku、DeepSeek、Qwen: 型付きYARD（`currency [String]`、`currency [Object]`、`pattern [Regexp, String, nil]`、`at [Time]`）。Sonnet: rbs-inlineの`#:`シグネチャ（`(Regexp?) -> Array[[Numeric, String?, Time]]`）。Opus: 散文のみ |

Sonnetの結果は極めて鋭利です。ADR-93の下では、これらの`#:`行は生きた契約として取り込まれ、`String`パターンも受け入れるAPIを暗黙のうちに狭めてしまいます — 次の読者が信頼するファイルの中で、推測が偽陽性ジェネレータになってしまうのです。

**同じフィクスチャに対してRigorが実際に返す回答**（これらが推測によって置き換えられてしまうもの）:

| 箇所 | Rigorの回答 | 置き換えられる推測 |
| --- | --- | --- |
| `record`の戻り値 | `Demo::BudgetLedger` | —（推測が偶然一致した） |
| `entries_matching`の戻り値 | `Array[untyped] \| []` | `Array[[Numeric, String?, Time]]` |
| `balance`、`overdrawn?` | スキップ、`sig.skipped.untyped-return` — `@opening_balance`が`Dynamic[top]`であるため、算術演算は何も証明しない | `Numeric` |
| `currency`、`amount`、`at`、`pattern` | 設計上`untyped`（[ADR-5](../5-robustness-principle/)） | `String`、`Integer`、`Time`、`Regexp` |
| `entries_matching`の引数、`--params=observed --observe spec` | `(Regexp)` — 呼び出しサイトから導出、採用可能 | — |
| `initialize`、同上 | `("JPY", ?opening_balance: 100)` — リテラル型；採用前に拡大する | — |

**言及しておく価値のある2つの限界**。第1に、どちらのアームでも5つのモデルのいずれもRigorを呼び出しませんでした — Rigorが存在することを知らされていなかったためです。したがって、この調査は*抑制*側（推測を書かない）を測定しており、*調達*側（オラクルに尋ねる）は測定していません。それこそがスキルと契約段落が変える条件であり、評価スイートがRigor設定済みのプロジェクト内で実行されなければならない理由です（WD7）。第2に、ルールの後にも残滓が生き残ります: ファイルあたり1つか2つの散文の型単語 — 「a numeric value」、「an array of entries」。これらは機械的にゲートできず、アノテーションではなく記述として受け入れられます。

## 決定

2つの再利用可能なルールがこれを担います。

> **来歴基準（Provenance criterion）**。型の来歴は型の一部である。書き記された型は、何かがそれをチェックしたことを主張する — したがって、*Rigorから取得しなかった型は推測であり、推測された型はいかなる場所にも決して書かれない。*その系: Rigorが回答を持たない場合、**そのギャップこそが発見事項であり、埋めるべき空白ではない**。

> **ルーティング基準（Routing criterion）**。習慣は、その習慣が行使される場所で身につく。推測は他のことに関するタスクの中で行われるため、ルールがタスクに一致するスキルに依存することはできない — タスクが知られる前にコンテキスト内になければならない。

2つ目の基準こそが**スキル単独では不十分である**理由であり、決定は3層構造をとります:

1. **スキル`rigor-type-oracle`** — アクション志向（action-shaped）であり、型を書く、または主張するという行為によってトリガーされる。3つの許可された情報源、ギャッププロトコル、すべての回答への来歴付与、およびユーザーがどうしても主張する場合の制限されたパス。
2. **契約段落** — `references/02-agents-md-fragment.md`、`rigor-project-init`によって導入先プロジェクトの`AGENTS.md` / `CLAUDE.md`にインストールされる。**これが不可欠な（load-bearing）層である**（WD2）。
3. **ゲート** — 矛盾時に`rigor check`がレッドになることが、両者の下での安全網である。Rigor自身のツリーでは、ADR-107が4つ目を追加します: そこでは型のようなコメントが完全に禁止されます。

Rigor自身のリポジトリが最初の採用者です。そうでなければ「紺屋の白袴」になってしまいます — 自身の`AGENTS.md`が手書きの型を容認しながらこのルールを出荷するプロジェクトは、自己矛盾に陥ることになります。その半分がADR-107です。

### WD1 — 質問志向ではなくアクション志向: なぜ`rigor-ask`ではなく新しいスキルなのか

スキルの唯一のルーティング機構は、手元のタスクに一致する`description:`です。`rigor-ask`のトリガーは*Rigorに関する質問*（「なぜこれが発火したのか？」、「絞り込みはどのように機能するのか？」）です。本スキルのトリガーは*行為*（「RBS / `#:` / Sorbetの`sig` / YARDタグ / レビューコメント内の型を書こうとしている」）です。これらは十分に異なっており、1つの説明が既存のトリガーを鈍らせることなく両方を担うことはできません — 169語の`rigor-ask`は、すでに[ADR-81](../81-skill-set-optimization/) WD4が引き締めの候補としてフラグを立てた唯一のエントリーであり、それをさらに広げることは、依然として見落とすケース（推測の瞬間に誰も質問をしない）のカバレッジのためにトリガーの再現率を犠牲にすることになります。

したがって、互いにリンクし合う2つのスキルとします。`rigor-ask`の引き継ぎリストには「型を*書こう*としている」行が追加されます。`rigor-type-oracle`の「使用すべきでない場合」は、セットアップを`rigor-next-steps`へ、診断を`rigor-baseline-reduce`へ、カバレッジループを`rigor-protection-uplift`へとルーティングします。

### WD2 — 3つの層と、なぜ契約段落が不可欠なのか

調査がこれを浮き彫りにしました。**ラウンド2のどちらのアームでもスキルは読み込まれていませんでした**。4/5の推測と0/5の推測の唯一の違いは、`AGENTS.md`内の1段落でした。

これは構造的なポイントであり、測定上のアーティファクトではありません: 契約ファイルは*タスクが知られる前に*、無条件にコンテキスト内に存在します — これは[ADR-97](../97-adr-index-budgets/) WD1が、`AGENTS.md`にインデックスではなく前提セットを担持させることを正当化するために使用したのと同じ特性です。スキルは構造上、条件付きです。あるタスクの内部の瞬間に発火することが任務であるルールにとって、機能するのは無条件のサーフェスであり、スキルは手順が必要だと分かった後にセッションが手を伸ばすものです。

インストールは`rigor-project-init`のPhase 8aです: `AGENTS.md`にセクションを追加する；それのみが存在する場合は`CLAUDE.md`を使用する；どちらも存在しない場合は`AGENTS.md`を作成する；競合するセクションを追加するのではなく既存の型セクションにマージする；そしてプロジェクトがすでに型の著述について矛盾するルールを明記している場合は、**停止してユーザーに競合を示す** — ユーザーが別の指示を出すまではプロジェクト自身のルールが勝ちます。このセクションはPhase 9のファイルインベントリで報告され、コミットが推奨されます。その価値は、すべての貢献者のエージェントが同じルールを読むことにあるからです。

### WD3 — パラメータの例外: 観察は証拠であり、コードリーディングは証拠ではない

推論はメソッドの*本体*を読みますが、本体は呼び出し元が何を渡すことを許可されているかを明記していません。ADR-5は設計上パラメータを寛容に保つため、Rigorはそれらを`untyped`と表記します — これはギャップではなく決定です。これは、オラクルの沈黙が恒久的であり、手動の決定が正当である唯一の場所です。

そこにおいてさえ、正当な入力は直感ではなく証拠です: `rigor sig-gen --observe PATH --params=observed`は呼び出しサイトからパラメータを導出します（認識エンジンはすでにRSpecの形状を理解しているため、通常のテストスイートが観察コーパスとなります）。出力は*狭い*証拠です — 今日の呼び出し元がたまたま渡しているもののユニオンである`("JPY")`などのリテラル型を契約として固定して出力します — したがって、採用前に**レビューして拡大**され、`rigor check`が新しい診断を追加しない間だけ保持されます。

再利用可能な形式: 手書きの型が正当であるのは、オラクルの沈黙がギャップによるものではなく設計によるものである場所に厳密に限られ、そこにおいてさえ入力は観察であり、ソースの独自解釈では決してありません。

### WD4 — ギャップは発見事項であり、ルーティングされ、決して埋められない

`Dynamic[top]`、`untyped`、および`sig.skipped.*`の分類は**回答**です: 「Rigorはここで型を証明できない」。それをあなた自身の解釈で埋めることは、既知の未知を自信に満ちた虚偽へと変えてしまいます。プロトコルは、報告（正確なコマンド、正確な出力） → 特定（`#=>`列を遡る`rigor annotate`、`rigor trace --format=json --line=N`） → ルーティングです: RBSのない依存関係は`rigor-rbs-setup`へ、未設定のフレームワークは`rigor-plugin-tune`へ、プロジェクト自身のモンキーパッチは`rigor-monkeypatch-resolve`へ、プロジェクトDSLは`rigor-plugin-author`へ、疑わしいセットアップは`rigor-doctor`へ — そして残ったものは5部構成のレポートを添えてRigorのissueへ。

これは[ADR-14](../14-rbs-sig-generation/)の「ギャップこそがより価値のあるシグナルである」を一般化したものです: このリポジトリ内の`.rbs`ファイルから、あらゆるプロジェクトで型が書かれ得るすべてのサーフェスへと。決して抑制しないという半分は、[ADR-57](../57-self-call-return-adoption/)の裁定姿勢です — 発火を分類し、根本で修正し、迂回しない。

**持ち越し**。`rigor explain`は診断*ルール*のみを文書化します；`rigor explain sig.skipped.untyped-return`は`Unknown rule`と答えます。そのため、スキップ理由のテーブルは`references/03-gap-protocol.md`に存在しており、CLIが所有すべき識別子の2つ目の居場所となっています。小さなフォローアップ: `rigor explain`を`sig.skipped.*`識別子へと拡張するか、マニュアルに文書化すること。**クローズ（[#936](https://github.com/rigortype/rigor/issues/936)）:** `rigor explain`はスキップ理由のための第2のカタログを保持し、分類器が生成し得るすべてのidに応答できるようにゲートされている。

### WD5 — 来歴は回答とともに移動する

人間に提示されるすべての型には、それを生成したコマンドが付随します — 1行: *`entries_matching` returns `Array[untyped] | []` (`rigor sig-gen --print lib/demo/budget_ledger.rb`)*。形式的な儀式ではありません: 読者が信じるしかない主張と、読者が3秒で再実行できる主張の違いであり、**誤った**回答を恒久化させず発見可能にするものです。また、リポジトリから出力が離れた後にも生き残るルールの唯一の部分です — レビューコメントやチャットの回答の背後には`rigor check`が存在せず、読者が得られるのは引用のみです。

同じ特性により、評価のS3シグナルが機械的になります: 差分または回答内のすべての型文字列は、記録されたコマンドの出力に逐語的に現れなければなりません。

### WD6 — カタログエントリー、および覚えておくべき3つのスキルの1つ

[ADR-73](../73-skill-driven-user-experience/)の基準において、安価な存在判定シグナルを公開できないスキルは、**カタログエントリーであり、決して見出しの推奨事項にはなりません**。これは`rigor-doctor`と同じ意味でイベントトリガー型です: イベントとはエージェントが型を書こうとしていることであり、`rigor skill describe`はそれを取得（stat）できません。そのため`CATALOG_ORDER`は、これを末尾の`rigor-ask`の直前に配置します — エージェントが任意の時点で提供する、ジャーニーに依存しない2つのコンパニオンです。

`describe`によってルーティングできないことと、覚えておく価値があることは無関係であり、本スキルは両者を分かつケースです。マニュアルの「ここから始める」および`skills/README.md`で覚えておくべきスキルは、2つから**3つ**になります: `rigor-next-steps`（*次は何か？*）、`rigor-ask`（*Rigorについてこれに答えよ*）、および`rigor-type-oracle`（*型を書く前にRigorに尋ねよ*） — 3つ目は計画中ではなく**執筆中**に覚えておくべきスキルです。

ADR-73 WD1 / ADR-81 WD1に従い、本文は安定した足場であり、バージョン結合された詳細（正確なフラグ、出力の綴り、スキップ理由id）は`references/`に配置され、`rigor skill --full rigor-type-oracle`によって動的に提供されます。本文は再取得指令で始まります。

### WD7 — 評価の姿勢: 4つの機械採点ケースと、却下されたままの`waza`バジェット

`evals/evals.json`はフィクスチャに対して4つのケースを持ちます — 文書化されていないクラスの文書化、戻り値型の質問への回答、ファイルへのRBSの追加、およびユーザーが型を主張する否定ケース。3つの機械的シグナルがそれらを採点します:

- **S1** — 型を書き込む最初のツール呼び出しの*前*に、オラクル呼び出し（`type-of` / `annotate` / `sig-gen`、またはMCP同等物）が発生していること。
- **S2** — 最終差分内に、Rigorコマンドが生成しなかった`@param [` / `@return [` / `#:` / `# @rbs`が存在しないこと。
- **S3** — 差分または回答内のすべての型文字列が、記録されたコマンドの出力に逐語的に現れること。

否定ケースは意図的なものです: ユーザーが「`pattern`は`Regexp`である」と主張することは許容されており、*頭ごなしに拒絶することも失敗です*。合格する動作は、Rigorが報告している内容を一度述べること（理想的には主張を導出に変える`--params=observed`を提案する）、求められた内容を書くこと、`rigor check`を実行すること、そして**チェックがどの行をカバーしているかを伝えること**です — `untyped`な周囲に対してグリーンであることは、そのアノテーションがRigorに見えているものと矛盾しないことを証明するだけであり、契約が成立していることを証明するわけではありません。

ADR-81 WD3に従い、`waza`の予算アドバイザリーは却下されたクラスのままです: 本スキルは`rigor-ask`の3,103トークンに対して2,857トークンであり、どちらも公開デフォルトの500トークンを大幅に超えており、いずれも意図的に包括的です。

## 却下・延期された代替案

| 候補 | ステータス | 理由 |
| --- | --- | --- |
| スキルを追加する代わりに`rigor-ask`を拡張する | 却下 | トリガーの不一致（WD1）: `rigor-ask`は質問に対して発火するが、推測の瞬間には質問は生じない。その行為をカバーするために説明を広げると、既存のトリガーが鈍る（ADR-81 WD4）一方で、依然としてケースを見落とす。代わりに相互リンクとする。 |
| 型のような編集をブロックするフック（Claude Code `PreToolUse`） | メカニズムとして却下 | ツール固有でありエージェント間で脆弱: 差分から`@param [`、`#:`、`sig do`をパターンマッチする必要があり、スキルが推奨しようとしている*導出された*型に対してもまったく同じように発火してしまう。契約段落と`rigor check`ゲートはエージェントに依存しない。マニュアル内でCI / エディタのレシピと並んでテンプレートを提供する価値はある；ここでの決定ではない。 |
| マニュアル（`rigor docs`）でのみルールを出荷する | 却下 | コンテキスト内ではなく、要求に応じて読まれる。失敗モードはまさに、調べるべきだと疑いもしないエージェントである — そして調査の推測アームに欠けていたのは情報ではなく、プロンプトであった。 |
| オラクルにエージェントの代わりにYARD / RBSをファイルに出力させる | 却下 | そのコマンドはすでに存在し（`rigor sig-gen --write`）、スキルがルーティングする先である。欠けていたピースは書く直前のエージェントの習慣であり、別のライターではない。 |
| `rigor skill describe`の見出し推奨にする | 却下 | 「エージェントが型を書こうとしている」ことに対する安価な存在判定シグナルは存在しない（WD6）；ADR-73のガードレールは`describe`を副作用のない状態に保つ。代わりにカタログエントリー＋マニュアルでのプロモーションとする。 |

## 結果

利点:

- Rigorがすでに出荷していたオラクルが、重要な瞬間に到達可能になります。ADR-0のAIネイティブという主張は、「エージェントが読むためにコードにアノテーションは不要である」から「エージェントのアノテーションはチェッカーからもたらされる」へと拡張されます。
- スキルの読み込みが失敗してもルールは生き残り（段落は無条件）、誤った型が書かれても生き残ります（`rigor check`が安全網）。3つの層があり、それぞれが前の層の失敗モードをカバーします。
- 暗黙の虚偽のクラスがルーティングされた発見事項になります: すべてのギャップは、担当スキルを持つプロジェクト設定の修正か、再現手順を持つエンジンのissueのいずれかになります — これはADR-14が本リポジトリ内部で行っている変換と同じであり、すべての導入プロジェクトで利用可能になります。

欠点・持ち越し:

- 調査はモデル・条件あたりn=1、5モデル、1フィクスチャです。示された効果は大きいものの（4/5 → 0/5）、抑制側のみをカバーしています。調達側は未測定であり、その評価にはRigor設定済みのプロジェクトが必要です。
- 散文の型単語はルールをくぐり抜けて生き残り、ゲートできません（§ 証拠）。記述として受け入れられます。
- `rigor explain`は`sig.skipped.*`をカバーしていないため、それらの識別子はCLIではなくスキルの`references/`に文書化されています（WD4フォローアップ）。
- オンボーディングがRigorが所有していないファイルに書き込むようになります。追記のみであり、上書きはせず、矛盾するプロジェクトルールがあれば停止します — しかし`rigor-project-init`がプロジェクトのエージェント契約に触れるのは初めてであり、拒否したユーザーはスキル層のみを維持します。
- スキル識別子`rigor-type-oracle`は、カタログの残りの部分とともに、[ADR-50](../50-release-engineering-and-stability-strategy/) WD1に基づきv1.0で凍結される公開ボキャブラリに加わります。

## 他のADRとの関係

- **[ADR-0](../0-concept/)** — そのコンテキスト段落は「人間の開発者とAIコーディングアシスタント（LLM）の双方にとって」のアノテーションノイズを名指ししています。それはテーゼの読み取り側です；本ADRは書き込み側を記録しており、調査が示すように、書かれた推測は信じられてしまうため、より大きな危険となります。
- **[ADR-5](../5-robustness-principle/)** — 戻り値には厳格、引数には寛容。WD3の例外は、著述側から見たその非対称性です: オラクルが恒久的に沈黙する唯一の場所です。
- **[ADR-14](../14-rbs-sig-generation/)** — §「著述ポリシーとその理由」。本ADRはそれを2重に一般化します: 本リポジトリからすべての導入プロジェクトへ、そして`.rbs`ファイルから型が書かれ得るすべてのサーフェスへ。
- **[ADR-33](../33-mcp-server/)** — MCPツールは同じオラクルです；スキルはサーバーが接続されているときにそれらを優先し、結果をまったく同一に読み取ります。
- **[ADR-57](../57-self-call-return-adoption/)** — WD4が再利用する裁定姿勢: 各発火を分類し、根本で修正し、決して抑制しない。
- **[ADR-73](../73-skill-driven-user-experience/) / [ADR-81](../81-skill-set-optimization/)** — メカニズム。カタログvs見出しの基準（WD6）、薄いシェルと動的コアの分割および`rigor skill --full`指令、そして`waza`評価の姿勢（WD7）。
- **[ADR-74](../74-offline-doc-access-and-llms-txt/)** — `rigor docs`および質問志向の兄弟である`rigor-ask`。WD1は2つのスキルの間のトリガー境界です。
- **[ADR-93](../93-default-rbs-inline-ingestion/)** — 推測された`#:`がなぜこの欠陥の最も危険な形態であるか: 取り込みがデフォルトで有効であるため、調査のSonnetの出力はコメントとしてではなく、生きた契約としてエンジンに入ってしまいます。
- **[ADR-107](../107-checked-types-and-typeless-comments/)** — リポジトリ側の双子、[#822](https://github.com/rigortype/rigor/pull/822)で着地: 同じルールがRigor自身のツリーへと内向きに適用され、そこではさらに型のようなコメントを禁止します。本ADRはRigorが外側に出荷するものであり、ADR-107はRigorが自身に課すものです。
- **[ADR-105](../105-pr-landing-flow/)** — 着地のメカニズム；本変更のエントリーはフラグメント`changelog.d/added/type-oracle-skill.md`です。
