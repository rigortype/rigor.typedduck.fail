ステータス: **Accepted — WD1（インクリメンタルなプラグインprepareキャッシュのスレッディング）は[PR #81](https://github.com/rigortype/rigor/pull/81)で着地。WD2/WD3（シードバンドル＋遅延ハンドル）は[PR #82](https://github.com/rigortype/rigor/pull/82)で実装。WD5（ハンドル上に運ばれる記録されたdef nesting）は[#707](https://github.com/rigortype/rigor/issues/707)で着地**。 [PR #77](https://github.com/rigortype/rigor/pull/77)が開いたウォーム/インクリメンタルの一連の流れを完結させる。キャッシュHITはすでに発見事前パスをスキップしているが、本ADRはそれをMISSパスからも取り除く──`--incremental`な再チェックは、キャッシュされたファイルごとのバンドルからクロスファイルの発見を再導出し、実際にdefボディが要求されたファイルだけをパースする。

基礎資料: [`20260714-p6-seed-cache-recon.md`](../../notes/20260714-p6-seed-cache-recon/)（測定の基礎: コスト分割、ADR-54テスト、需要統計、マージセマンティクスの監査）＋[`20260713-corpus-perf-campaign.md`](../../notes/20260713-corpus-perf-campaign/)（この流れの起点）。

## コンテキスト

#77以降、`ProjectPrePasses#discover`はキャッシュミス時にのみ実行される──しかしすべての`--incremental`な再チェックはミスパスの実行そのものだ: 1ファイルのサブセットを再解析する前に、すべてのプロジェクトファイルをパース＋ウォークしてクロスファイルの発見インデックスを再構築する。この偵察調査（#74–#80適用のmaster）が測定したのは以下:

- プラグインの少ないプロジェクトにおけるウォームな単一編集/ゼロ変更のインクリメンタルは**80–92%が事前パス**（rigor lib 0.54Mアロケーション、mail 0.53M）──このスライスの対象読者だ。
- ファイルごとのバンドルの`Marshal.load`＋フォールドは、パース＋ウォークを**36倍のwall / 10倍のアロケーション**（rigor）から**570倍 / 44倍**（mail）で上回る──ADR-54の「再計算を上回る」基準は決定的にクリアされている（引退した定義blobは同じテストを366ms対137msで落とした。このtierは勝つ）。
- def-nodeの需要はインクリメンタルパスでは極小だ: 1–20ファイルの再チェックは**0–6個の別々のファイル**のボディを解決する（完全なコールド実行では39–66%）──したがってdefノードをキャッシュからeagerに実体化してはならない。
- **Railsアプリは別の場所でゲートされている**: gitlabのウォームインクリメンタルは、**再チェックごとにプラグイン`#prepare`を再実行することに86%（14.2Mアロケーション）**を費やす──再チェックパスは、プロデューサキャッシュの配線なしに新しいランナーを構築する（`IncrementalSession#build_runner`が`cache_store: nil`をハードコードしている）ため、#74でキャッシュされたスキャンでさえ再計算する。それを修正すること（WD1）が、このスライスをRailsで意味あるものにする前提だ。
- マージセマンティクス: ファイルごとの寄与は分離可能でファイル順マージ可能だが、デルタ置換可能ではない（`includes`/`class_sources`はSet和集合、`def_nodes`/`superclasses`/`methods`は後勝ち、`finalize_def_index`はプロジェクト全体の後処理パス）──健全な再構築とはファイル順にバンドルから再構築し、その後一度finalizeすることだ。クロスファイルの重複`(class, method)`ペアは3つのコーパスすべてでゼロと測定されたので、後勝ちの順序依存性は理論上のものだがそれでも保持される。
- Prismの`node_id`は同一バイトの繰り返しパースと新規パースをまたいで安定しており（不一致0件）、すべてのDefNodeで非nilだ。

## 決定

各ファイルの事前パス寄与を、**ファイルのダイジェストをキーとするプレーンデータのバンドル**としてキャッシュし、ADR-46の`IncrementalSnapshot`にホストする。有効なスナップショットを伴うミス時実行では、プロジェクトをパース＋ウォークする代わりに、バンドルをファイル順にフォールド（変更されたファイルのみ再ウォーク）して発見インデックスを再構築する。def-nodeテーブルは**ハンドル**を格納し、実行ごとのパースメモを通じてアクセサのチョークポイントで遅延解決する。このメモは**実行ごとに`(path, node_id)`ごとに1つの安定したノードオブジェクト**を生む──ADR-84の戻り値メモはdef-nodeのアイデンティティをキーにするので、アイデンティティの安定性は健全性の制約であり、あればうれしい程度のものではない。

基準（ADR-54ルールを再適用し、拘束力を維持する）: **このtierは、ロード＆フォールドが実コーパスで再計算を測定可能に上回り、かつdef-nodeの実体化が需要に従う間だけ存在する**──ASTをMarshalダンプする（各ファイルのソーステキストを引きずる）eagerな変種は、このtierの価値の大部分であるパースアロケーションの利得を放棄するので、同じ基準で棄却される。

## ワーキングデシジョン

- **WD1 — インクリメンタルな再チェックがプラグインプロデューサキャッシュを再利用する（シーケンシング上クリティカルで、最初に着地）**。根本原因を確認: `IncrementalSession#build_runner`はすべての内部アナライザーを`cache_store: nil`で構築していたため、プラグインの`cache_for`（`Plugin::Base`）はストアを見つけられずディスクキャッシュをバイパスし、クロスプロセス再チェックごとに各プロデューサーを再計算していた。修正: `Cache::Store`をセッションを通してスレッドする（`--no-cache`を尊重）。実行全体のADR-45結果キャッシュはこれらの実行と**非互換**だ──キャッシュ提供された`record_dependencies`実行は依存グラフを一切キャプチャせず、`analyze_only`サブセット実行の部分的な診断は完全実行の結果キーを共有する──ので、`Runner#run_result_cacheable?`は今や`record_dependencies` / `analyze_only`を除外する。gitlab `app/models`のウォームインクリメンタルを**16.7M → 2.8Mアロケーション（約6倍）**、プラグイン`#prepare`単独で**14.3M → 0.34M**と測定。診断はバイト同一。ストアは`--verify-incremental`にもスレッドされるので、ゲートはキャッシュ提供パスがキャッシュなしの完全実行と一致することをアサートする。
- **WD2 — `IncrementalSnapshot`上のバンドル**。 `Payload`を`seed_bundles`で拡張する（SCHEMA 5→6。#57のABIマーカー＋フィンガープリントゲートが無効化を無償でカバーする──6より前のblobはnilとしてロードされ、クリーンなコールド再構築になる）。バンドルは1ファイルのfinalize前寄与をプレーンデータとして格納する──`subtract_def_methods`前の`methods`テーブルと`classes`テーブル（Singleton値、Marshalクリーン）を含む──def-nodeテーブルはハンドルとして再表現される。`finalize_def_index`はフォールド後に一度実行される。1回のfs読み取りが再構築全体に対応する（ファイルごとの`Cache::Store`プロデューサファミリーなら、11kファイルのプロジェクトで約N回のfs操作になる──ADR-54が引退させたアンチパターンだ）。`ScopeIndexer.discovered_project_index_incremental`は各ファイルのバンドルをフォールド（ダイジェスト検証済み）するか変更ファイルを再ウォークし、正規順で行う。**再ウォークされたファイル（および`seed_bundles`が空であるコールドベースライン全体）はインデックス内にLIVEな`Prism::DefNode`を保持する**──ちょうどウォークされたファイルにはオンデマンドの再パースはない──ので、*変更されていない*ファイルだけがハンドルを運ぶ（混在テーブル）。したがってコールドベースラインのインデックスは、今日の`discovered_project_index_for_paths`とバイト同一だ。
- **WD3 — 遅延def-nodeハンドル**。ハンドルは`DefHandle(path, node_id, name, fingerprint, nesting)`（`nesting`はWD5により追加）だ。3つのサイトがノード値をderefする（`Scope#user_def_for`、`#singleton_def_for`、`#top_level_def_for`）。それらは`DefNodeResolver`（実行ごとのパースメモ）を介してハンドルを解決し、呼び出し側に本物の`DefNode`を渡す（アクセサ契約は不変。依存記録はテーブルのPRESENCEをキーにするので、解決が成功してもしなくても健全なままだ）。解決は`(path, node_id)`ごとにメモ化される──**実行ごとに1アイデンティティ**（これはADR-84のクロスファイルアイデンティティ境界も1に減らす）。`node_id`が主で`name`は解決のクロスチェック。ミス（ダイジェスト検証がずれを不可能にするはず）は新規ウォークにおける最初の同名DefNodeにフォールバックし、次にnilになる──保守的で、決して黙らない。**偵察調査のQ6監査が見逃した4番目の値deref消費者**──`Runner#symbol_fingerprints`（ADR-46スライス4）がすべてのdef-nodeをスライスする──こそが、ハンドルが`fingerprint`（defのスライスのSHA、バンドル構築時にキャプチャ）を運ぶ理由だ: symbol_fingerprintsは再パースせずにハンドルからそれを読む。他のすべての消費者はテーブル構造（キー / オブジェクトアイデンティティ）を読み、影響を受けない──バイト同一ゲートと、ハンドルを持つテーブルが不変で提供することを示すspecによって固定されている。
- **WD4 — フォールドは置換であり、決してパッチしない**。マージされたテーブル内で変更ファイルの寄与をデルタ置換することはしない（Set和集合/後勝ち監査により不健全）。変更ファイルは再ウォークされ、インデックスはバンドルからファイル順に再構築される。バンドルからの再構築それ自体が高速パスだ──フォールドは436–485kの再計算に対して5–8ms / 25–61kアロケーションと測定された。
- **WD5 — ノードアイデンティティによってキー付けされたファクトはハンドル上で運ばれなければならない（MUST）（[#707](https://github.com/rigortype/rigor/issues/707)）**。 [#681](https://github.com/rigortype/rigor/issues/681)は各`def`の`Module.nesting`を`Prism::DefNode`の**アイデンティティ**によってキー付けされた発見テーブルに記録し、WD3のresolverは独自のパースからノードを返すため、発見ウォークがキー付けしたテーブルがそれを含むことはできず、変更されていないファイルのcalleeは#681以前のレシーバー修飾名のピールを暗黙に保持していた。これは精度ギャップではなく本物のコールド/ウォーム乖離である: コンパクトな`class Admin::Maker`とネストされた記法は同じ`class_name`をレンダリングするため、ソースが`::Post`を名指すところでピールは`Admin::Post`に到達し、両者を比較すること自体が責務である`--verify-incremental`は、ユーザーが変更していないプロジェクトでOKからFAILEDに反転した。修正: チェーンはバンドル行に乗せられ（`[node_id, name, fingerprint, nesting]`、SCHEMA 13→14）、`DefNodeResolver`は自身が生成したノードにそれを再アタッチし、単一のリーダー`ExpressionTyper#recorded_def_nesting`を通じて読み戻される。**再ハイドレーションメモはそのファクトの対立ソースではない**──`Reflection.lexical_nesting_chain`を単一オーナーにするために[#685](https://github.com/rigortype/rigor/issues/685)が用いた議論は、オブジェクトの由来（OBJECT PROVENANCE）において依然として成立する: resolverは独自の`Prism.parse`を実行し、両方のテーブルは`compare_by_identity`であるため、resolverが生成したノードはアナライザー自身のウォークが生成したオブジェクトでは決してなく、両方のキーになるノードは存在しない; 2つが異なるオブジェクトを通じて同じdefに答える場合、ファイルの内容SHA-256が一致したときにのみバンドルが再利用され、チェーンはそのファイルのASTの純粋関数であるため、両者は一致する。**その議論のファイルレベル版は誤りであり、測定される前にここで主張されていた:** DEPENDENTとして再解析される未変更ファイルは、クロスファイルフォールドにおいてバンドルから提供され、自身のファイル単位インデックスのために`ScopeIndexer#merge_def_node_tables`によってライブでウォークされ、1回の`Runner#run`で両方のテーブルに寄与する。したがって将来の変更は、ファイルレベルの分離ではなく、独立したパースを保持しなければならない。再ハイドレーションは`DefNodeResolver.with_run`の内部でのみ投入される;ハンドルを消費するすべてのエントリーポイントはその内部で実行され、検査に委ねるのではなくスペックがそれを固定している。SCHEMAの引き上げは衛生的というより不可欠である: 3要素の行は`nesting`をnilとしてアンパックし、これは正規に何も記録しないトップレベル`def`と区別がつかないため、14より前のblobは読み込まれずに**拒否**（REJECTED）されなければならなかった。（[#716](https://github.com/rigortype/rigor/issues/716)以降、トップレベル`def`はnoneの代わりに空のチェーンを記録し、形状を変えずに既存の行が意味するものを変更し、同じ理由でスキーマを再度引き上げた──以下のルールがそれを1行の変更にしたものである。）**この事例が教える一般的なルール: バンドルはテーブルの値をシリアライズするため、ライブインデックスがノードアイデンティティによってキー付けするいかなるファクトも、行の上に移動させない限り失われる──1つ追加することは呼び出し側の変更ではなく、WD3の変更である**。

## 偵察調査からの乖離（実装中に発見）

- 偵察調査のQ3は、`classes`テーブルを**キーリストとして**格納できると述べていた（値は`Singleton[name]`として再構築可能）。これは`Const = Class.new(Super)`定数（その値は`Singleton[Super]`）については偽だ。バンドルは完全な`{name => Singleton}`テーブルを格納する（Marshalクリーン）。残る1点: クロス*ファイル*の`Class.new`スーパークラス解決（まれ）は、蓄積された集合全体に対してではなくバンドル内でファイルローカルにキャプチャされる。`--verify-incremental`＋コールドバイト同一ゲートがそれを後方支援する（mail / kramdown / mastodon / redmine / rigor libですべてグリーン）。
- 偵察調査のQ6は3つのアクセサを**唯一の**ノード値消費者と名指ししたが、`Runner#symbol_fingerprints`が4番目だ。WD3のハンドルはそれに対応するため`fingerprint`を運ぶ（上記）。
- `IncrementalSession`は`plugin_requirer:`フック（`Runner`をミラーする）を獲得したので、WD1のキャッシュ再利用specはプロデューサーを持つテストプラグインを登録できる──セッションはrequirerを注入できない唯一のランナービルダーだった。

## 棄却された代替案

- **eager def-node Marshal**（ASTをキャッシュ）: 各ダンプはファイルのソース全体を引きずり、ロード側のアロケーションはこのtierの支配的な利得を放棄し、完全コールドの需要（ファイルの39–66%）だけがそれが助ける唯一のケースだ──インクリメンタルパス（0–6ファイル）が対象読者だ。基準が却下する。
- **デルタ置換マージ**: 不健全（Set和集合＋後勝ち＋プロジェクト全体finalize）。
- **ファイルごとの`Cache::Store`プロデューサー**: 再構築ごとにN回のfs操作。アクセスパターンはすべてのバンドルを一度に必要とする──1回のスナップショット読み取りが正しい形だ。
- **WD1をスキップしてバンドルだけを出荷**: Railsコーパスでは、86%がキャッシュされないprepareに居座る中でこのスライスは測定で約5%になる──WD1を最初にシーケンシングすることがこの流れを誠実にする。

## 帰結

- ポジティブ: プラグインの少ないウォームインクリメンタルは80–92%の事前パスの下限を失う（rigor libのゼロ変更540k → 149kアロケーション、mail 529k → 54k。事前パス436k → 25k / 485k → 5k）。Railsインクリメンタルは86%のprepare再実行（WD1）を失い、さらにその上の事前パスも失う（gitlab 16.7M → 2.06Mの合算、約8倍）。`--verify-incremental`はバイト同一を常設ゲートとして維持する。ADR-84メモのアイデンティティ境界が締まる。
- ネガティブ: バージョン管理すべき新しいスナップショットセクション（SCHEMA規律）。ハンドルの間接参照は3つのアクセサでメモ化ルックアップを1つ追加する。コールドの`--incremental`ベースラインはわずかな追加コスト（バンドル＋フィンガープリントの構築）を払う。これはゲートされないパス上の一度きりのコストだ。バンドルの陳腐化は、ダイジェストゲートが健全なままである間だけ構築上不可能だ。
- 引き継ぎ: プレーン（`--incremental`でない）コールド実行は今日のパース＋ウォークを不変に保つ（それらは決して`collect_seed_bundles:`を設定しない）。バンドルは一般的なキャッシュMISSにも対応できるかもしれないが、そのパスの利得は小さい（Q8）──拡張する前に測定せよ。

## 他のADRとの関係

[ADR-46](../46-incremental-dependency-graph/)は本ADRが完結させるインクリメンタル機構を所有する（そのスナップショットがバンドルをホストする）。[ADR-54](../54-cache-slimming/)の再計算を上回る基準は本ADRの拘束ルールで、tierをADDする方向に適用される。[ADR-53](../53-scope-discovery-index-separation/)の不変な発見の分離こそがファイルごとのバンドルを明確に定義する。[ADR-84](../84-cross-file-return-memo-scoping/)のアイデンティティキーのメモがWD3のハンドルごと1ノードの制約を課す。[PR #77](https://github.com/rigortype/rigor/pull/77)の遅延事前パスは、本ADRのMISSパスが補完するHITパスをカバーする。[ADR-9](../9-cross-plugin-api/)/[ADR-60](../60-pre-freeze-plugin-contract-consolidation/)は、WD1が再スレッドするプロデューサー機構を所有する。
