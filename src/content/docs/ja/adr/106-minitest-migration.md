ステータス: **Accepted（却下——スイートはRSpecのまま）、2026-09-02**。

「新しいテストはminitestで書き、徐々に移行し、その間は両方のフレームワークを許容すべきか？」という問いに対するプロジェクトの答えを記録し、この問いが蒸し返されるのではなく、書かれた前提に対して決着するようにする。答えは**ノー**であり、その理由はふつう挙げられるものではない: ここでは移行の算術は成り立つし、スイートのコストはフレームワークではない。この提案が実際に求めているのは、スイートの共有ハーネスの2つ目のコピーであり、そしてRigorのユーザーが書くコードの形からの離脱である。**このADRは何もスケジュールしない**;下記の再評価トリガーが戻ってくるための道である。

## コンテキスト

この問いはCIのコストから来た——`Tests`のジョブが約11分で、ワークフローを支配していた。その前提はもう尽きている。2つの変更（[#563](https://github.com/rigortype/rigor/pull/563)が同一のRBS環境の構築を重複排除し、[#566](https://github.com/rigortype/rigor/pull/566)がジョブを3分割した）が、テストフレームワークに触れずにワークフロー全体を約10分30秒から約3分10秒にした。それ自体が最初の証拠である: コストは決してRSpecにはなかった。

提案された形はストラングラーフィグ型だった——新しいテストはminitestで、一括移植はせず、必要なだけ長く2つのフレームワークを受け入れる。この形は、いつもの「移行は決して終わらない」で片付けるのではなく、それ自身の土俵で判断されるに値する——このリポジトリでは、これはもっともらしく終わりうるからだ。

## 決定

移行しない。新しいテストは他と同じくRSpecで書く。

決定を担った判定基準は2つあり、どちらもこの問いを超えて再利用されることを意図している:

1. **提案のコストが、置き換えられる部品ではなく共有ハーネスに座っているときは、まずハーネスを抽出して計測し直すこと**——抽出はたいてい、置き換える理由そのものを取り除く。ここでは置き換え可能な部分（RSpecのランナーとDSL）は約12分のスイートのうち約1.7秒であり、置き換え不可能な部分（`spec/spec_helper.rb`＋`spec/support/runner_helpers.rb`、変異のハーネス、分割されたCIのマトリクス）にコスト全体が着地する。そして2つ目のフレームワークはそのすべてを複製する。
2. **Rigorは、そのユーザーが書く形から移行して離れない**。 Rigor自身のソースがRigorにとってのコーパスである以上、より解析しやすいフレームワークを採用することは、プロダクトのギャップを私的な便宜へ変換し、すべてのユーザーのためにそれを直したはずの圧力を取り除いてしまう。

## 却下および検討した代替案

| 選択肢 | なぜ採らないか |
| --- | --- |
| **1サイクルでのminitestへの全面移植** | それを購うだけの利益がないコストとして却下: 110,764行、約1,131箇所の`let`、約400箇所のモック、そしてbinpackerの統合の書き直しを、計測された1.7秒のために。 |
| **新しいテストをminitestで、段階的に移行（この提案）** | 却下——下記のコストの分析を参照。特筆すべきは、収束性を理由に却下したのでは*ない*ことだ: 観測された流入量なら、minitestのレーンは1年以内に424個のRSpecファイルを数で上回る。 |
| **新しい*ユニット*テストだけを移し、統合テストはRSpecのまま** | 両者のいいとこ取りの逆として却下: レーンの境界が新しいファイルごとの判断事項になり、しかもどちらのレーンが大きいかにかかわらずハーネスの複製は全額支払われる。 |
| **RSpecを維持（採用）** | フレームワークはコストセンターではなく、ハーネスは単一の住所のままになる。 |

### なぜ算術のほうは反対理由にならないのか

テストフレームワークの段階的な移行に対するいつもの反論は、古いレーンが決して空にならない、というものだ。ここではその議論は成り立たない。このリポジトリは生後4か月であり、424ファイルのスイート全体がその期間内に書かれた;直近の流入は月に38〜89個の新しいスペックファイルである。minitestのレーンは、誰も1行も移植しないまま、1年よりずっと手前で数の上でパリティに達するだろう。

これはその但し書きとともに読むべきだ——その速度は若いプロジェクトの初期の作り込みであり、減速していく——が、正直に要約すれば、収束性はこの提案の最も弱い点ではなく最も強い点であり、この決定はそれを否定することの上に立ってはいない。

### コストが実際に何であるか

このスイートのフレームワークは薄い;その**ハーネス**はそうではなく、しかも2つ目のレーンがそれぞれ複製したうえで同期を保たなければならない3か所に、単一の住所を持っている。

- **`spec/spec_helper.rb`はプロセス全体にかかる12個の不変条件を運ぶ**。それぞれが1つの欠陥に結び付いている: エンジンの同一性のメモのリセット（#289）、一時ディレクトリのリークのガード（#330）、遅延YJITのピン留め（#567）、プールのスペックの除外（ADR-15）、CI検出のピン留め（ADR-51）、rbs-inlineの自動配線のピン留め（ADR-93）、そして#563とともに追加されたRBS環境のメモ。これらは欠けていても大声で失敗しない。#567が予期すべき形だ: リークしたJITのスリーパーが*別の*ファイルでflakeとして表面化し、ローカルの12ワーカーでは通り、CIの4ワーカーで落ちた。2つのレーンは、これらのそれぞれを間違える機会が2つあるということであり、そしてこのリポジトリには乖離の前例がある——ADR-72のActiveSupportのオーバーレイは、そのプラグインの双子から12個のセレクタぶん乖離した（#449）。
- **`spec/support/runner_helpers.rb`はこのスイートの性能が住んでいる場所である**——共有のキャッシュストア、内容でキーされた`sig:`の実体化、共有のワークスペース、RBS環境のメモ。これらの1つを取りこぼしたminitestのコピーは、誤るのではなくテストごとに黙って約2倍遅くなるだけであり、それは失敗よりも気づきにくい。
- **変異のハーネスは、保護を黙って過小に報告することになる**。 `tool/mutation/self_mutate.rb:245`は、変異させた各ファイルをカバーするスペックに対して`bundle exec rspec`を走らせる。minitestによってのみ殺される変異体は生き残り、テストで保護されていないサイトとして報告される。それは、このハーネスが生み出すために存在するその計測における偽陽性であり、ファネルを使えるものにした1,969→22のノイズ除去を台無しにするだろう。

さらに2つのコストは実在するが平凡だ: `binpacker.yml`はプロファイルごとに1つの`test_runner`を束縛するので、3分割のマトリクスとその`shard-coverage`のゲートには2つ目のコピーが要り——各ジョブが自身のセットアップを払うので、移行期間中はむしろ実時間を*上げ*かねない——そしてリポジトリは2つのlintの体系を抱えることになる。

### ドッグフーディングの議論と、それが反転する理由

minitestに*賛成*する最も強い論拠は速度ではなくドッグフーディングだ: RSpecのブロックDSLは推論にとって最悪ケースに近く、`make check`は`lib`しかカバーせず、110,764行のスペックはRigor自身の解析の外側に座っている。移行すればそのコーパスが開かれる。

計測すると、その前提は聞こえるほど強くない——RigorはRSpecの形のスペックファイルで51.15%の精度に達し、`lib`では61.33%である。RSpecの形のコードのおよそ半分はすでに精密に型付けされている;差は約10ポイントであって、壁ではない。

そして残りの10ポイントは反対のことを論じる。Rigorのユーザーは**RSpecを書く**。もしRSpecの形こそが推論の最も弱いところなら、Rigor自身のスイートをRSpecから外すことは、それを直すのに最も適した人々からその圧力を取り除き、顧客に面したギャップを私的な便宜の背後に隠すことになる。51.15%という数字は、移行の理由としてではなく`docs/type-specification/`への入力として読むほうがよい。

## 帰結

- **正の面**。ハーネスは単一の住所のままなので、#567のような不変条件は一度直せば済む。変異のハーネスは、それが主張するものを計測し続ける。CIのマトリクスは1つのマトリクスのままである。
- **正の面**。 RSpecの形の推論は、内部の煩わしさではなく生きたプロダクトの関心事であり続ける。
- **負の面**。 `spec/`は`rigor check`の外側に残るので、このリポジトリで最大のRubyの塊がドッグフーディングされない。これは実在する損失であり、このADRはそれを緩和しない。
- **負の面**。プロジェクトは、自身が制御していない開発依存に留まる。露出は小さい——RSpecは開発依存であり`rigortype`には同梱されない——が、ゼロではない。
- **持ち越し**。何もスケジュールされない。スペックファイルは1つも変わらない。

## 再評価トリガー

以下のいずれかが真になったら、これを再開すること:

1. **ハーネスが抽出されたとき**。 `spec_helper`の不変条件と`RunnerHelpers`が、ランナーが単に呼ぶだけのフレームワーク非依存の素のオブジェクトになれば、判定基準1はもはや適用されず、コストはフレームワークそのものへ縮む。その抽出はそれ自体の利点で行う価値がある;先にそれを行うことは礼儀ではなく前提条件である。
2. **変異のハーネスが、フレームワークをまたいでカバーするテストを見つけられるようになったとき**。分割されたスイートが、保護されていないサイトの誤った報告を生めなくなる。
3. **RSpecの形の精度がプロダクトの関心事でなくなったとき**——それが閉じられたから、あるいは調査によってRigorのユーザーがRSpecを使っていないと示されたから。どちらも判定基準2の反転を取り除く。
4. **フレームワークに帰属できる計測されたコストが現れたとき**——テストが駆動する解析にではなく。上記の根拠には、今日そのようなものを示唆するものは何もない。

それらがない限り、これは決着済みとして扱うこと。
