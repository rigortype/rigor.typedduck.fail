ステータス: **Proposed、2026-10-01**。メンテナ向けに#120に回答する。これを受け入れても何も反転（flip）しない: デフォルトは、WD8のプレビューの後、WD7のゲートをクリアしたPRにおいてのみ変更される。

根拠: #1507のウォームジャーニーの測定結果、`e0c6b3bcb`での`engine-warm.yml`の2回の実行、#120に関する2026-07-18のメンテナの裁定、および#1545、#1552、#1577のレビュー中に起票された古い回答に関するissue。

## コンテキスト

**ギャップ**。約1,400ファイルのRailsアプリケーションへの1回の編集は、デフォルトの`rigor check`にほぼコールド実行と同等のコストを課す。ADR-45の実行結果キャッシュがオール・オア・ナッシングであるためである。`--incremental`はほとんどの編集に対してその10分の1の時間で回答する。

以下の表は、CI Linux上での実時間の中央値を示す: Mastodon v4.5.10、`app lib config`、ステップごとに3回の実行、各々クリーンなプロセスであり、すべてのウォームな回答は`--no-cache`実行と等しい。リーフファイルは`about_controller.rb`、ハブファイルは`account.rb`である。各セル内の最初の数値は[実行36746631018](https://github.com/rigortype/rigor/actions/runs/36746631018)（空のメソッドを追加）、2番目の数値は[実行36746637783](https://github.com/rigortype/rigor/actions/runs/36746637783)（コメント行を追加）からのものである。

| ルート | null | リーフ編集 | ハブ編集 | コールドプライム（1回実行） |
| --- | ---: | ---: | ---: | ---: |
| デフォルト | 0.29 / 0.24 s | 24.3 / 20.3 s | 24.2 / 19.9 s | 27.6 / 25.9 s |
| `--incremental` | 0.30 / 0.24 s | 2.6 / 2.1 s | 18.7 / 2.6 s | 35.0 / 28.4 s |

日常的な開発ループはリーフ列とハブ列であり、現在それを得られるのはオプトインフラグを見つけたユーザーだけである。ハブにメソッドを追加すると、依然としてすべての祖先依存先が再チェックされる（#1538）。

**2026-07-18の裁定が挙げた3つのブロッカー。それぞれの現状:**

1. **2つの高速パスが競合していた**。 #1552（ADR-45 WD2）によって解決: nullの`--incremental`実行は現在エンジンフリーで提供される。
2. **パスを測定するゲートがなかった**。`engine-warm.yml`がいまやそれを測定するが、`bench/baseline.json`は依然としてコールドのフルパスのみを測定している。
3. **インクリメンタルの末尾の出力が少ない**。依然として当てはまる。JSONの`config_warnings`ブロック、CIネイティブのアノテーション、`--baseline-strict`の判定、キャッシュの退避、および`--coverage`を欠いており、`--explain`を無視する（#1533）。実行統計とトレース付録は別の問題である（WD4）。

**それ以来、キャンペーンにより、インクリメンタルパスにおけるほとんどの古い回答のバグが1つの原因を共有していることが判明した**。インクリメンタルスナップショットは、厳選されたリストから自身が依然として有効かどうかを決定している:

- `IncrementalSnapshot.fingerprint`はエンジン、設定、ルート、`./Gemfile.lock`、`rbs_collection.lock.yaml`、および*設定された*`signature_paths:`をカバーする。
- その隣には解析対象セットのファイルごとのダイジェスト、および3つのゲートが存在する: ADR-88のファクトダイジェスト、エフェクトのアイデンティティ、および#1536のソースRBSゲート。

対照的に、ADR-45 WD2のインクリメンタル実行スロットはレコードアンドバリデートである。再チェックが再導出するのではなく前方へ引き継ぐチェーンの部分（`Runner#baseline_dependency_rows`）は、自動検出された`sig/`を含め、シグネチャツリーとそのルートを保持する。また、ディスカバリールートごとのリスト行を伴う発見されたが解析されていないファイル、および解析対象セット外の`pre_eval:`ファイルも保持する。そのキーは`RunCacheKey`が読み取るとおりにロックファイルを保持する。スナップショットにはこれら各々が欠けている:

| Issue | スナップショットが見ていない入力 |
| --- | --- |
| #1532 | 設定された、または自動検出されたロックファイル |
| #1554 | 自動検出された`sig/`ディレクトリ |
| #1560 | 発見されたが解析されていないファイル |
| #1585 | 解析対象パス外の`pre_eval:`ファイル |
| #1553 | キャッシュされたファイルを解析している間にプラグインがその`IoBoundary`を通じて読み取ったファイル |

各入力をフィンガープリントへパッチ当てしていくやり方こそが、リストがそれらを見逃すようになった経緯そのものである。コードの隣に置かれたリストは次の入力を見逃すのであり、これは#1531のレビューが堂々巡りし続けた失敗モードである。

その他の古い回答は他の原因を持ち、個別にゲートされる（WD7 G1）:

- #1459: 欠落した依存関係エッジ。
- #1541: プールモードでのnull再チェック。
- #1561: stat-then-digestの競合。
- #1583: 再チェックが#684のフル実行のようにディスカバリーを拡張しない。
- #980: ウォーム実行をまたいで永続化された脱落した行。
- #1525: `--no-cache`が依然としてスナップショットをリプレイする。

## 決定

**スナップショットが隣のリストではなくレコードアンドバリデートチェーンによって検証され、両方のルートが同じものを出力するようになれば、ローカルのプロジェクト全体実行において`rigor check`はデフォルトでインクリメンタルルートを採用する**。ルートは変わるかもしれない。回答が変わってはならない: 同じツリーの`--no-cache`実行と等しくなければならない。

デフォルトルートとなる任意のキャッシュに対して再利用可能な規準:

1. その妥当性はリストからではなく、記録された入力から読み取られること。
2. 同じ出力末尾で終わること。
3. 後の実行が再利用しない実行は、そのコストを支払わないこと。

### 作業決定事項（Working decisions）

- **WD1 — スナップショットは引き継がれたチェーンによって検証される**。スナップショットはチェーンの引き継がれた部分を所有する: `baseline_dependency_rows`（`BaselineRows#owned`および`#pinned`）およびファイルごとの読み取り（`by_file`）。スロットはそれらをスナップショットからコピーするため、`cache.max_bytes`の下で退避されたスロットがウォームなプロジェクトをコールドにしてしまうことはない。
  - `observed`行および`derived`行（プラグインの`#prepare`およびプロデューサーの読み取り、`watch:` glob、テンプレートファイルとglob、存在行）は、現在と同様に実行ごとに再導出される。テンプレートの編集は現在のコストを維持する。
  - **引き継がれた行のいずれかが陳腐化した場合、ファイルごとの読み取りを含め、完全なベースラインがトリガーされる**。ADR-45が記録しているように、ivar内、`producer_value`経由、またはADR-84戻り値メモによってメモ化された値は、後続のファイルに独自の読み取りなしで到達する。したがって、読み取りが帰属したファイルのみを再解析することは不健全である（#1553）。より狭い対応は将来の改訂であり、各々が独自の証明を持つ。ファイルごとの読み取りについて、その証明はプラグインがファイルをまたぐメモを保持しないというプラグイン宣言契約を必要とする。
  - **完全なチェーンなしで書き込まれたスナップショットは再利用不可であり**、次回の実行は完全なベースラインとなる。現在、ワーカープール下では記録なしで、またどのファイルにも帰属しない読み取りに対してチェーンが欠落する。
  - **ゲート:**ビルダー自身から取得された、引き継がれた部分が発行する行の種類をspecが列挙する。各種類について、プライムし、新しいプロセスでその入力を編集し、ウォームな回答が`--no-cache`実行と等しいことを主張する例が必要である。例のない新しい行の種類はspecで失敗する。
- **WD2 — スナップショットキー**。`IncrementalSnapshot.fingerprint`はエンジンアイデンティティ、スキーマ、設定、およびルートを保持する。`./Gemfile.lock`の代わりに`RunCacheKey.lockfile_entries`を通じてロックファイルを読み取る（#1532）。WD1の行が置き換える`signature_paths:`ダイジェストを削除する（#1554）。ADR-88のファクトダイジェスト、エフェクトアイデンティティ、および#1536のゲートは現在のままとする。
- **WD3 — ダイジェストはファイルごとにチェックされる**。各ファイルごとのダイジェストはファイルの2回のstatの間で取得され、statが移動したファイルは再読み取りされる（#1561、オプション1）。スロットの`WriteGuard`はスロット自身のものとして残る。微細なタイムスタンプを持たないファイルシステム上ではマークを取得せず、スナップショットをそれにゲートすると、それらのユーザーにはスナップショットがまったく残らなくなるためである。
- **WD4 — 単一の末尾**。デフォルトのミスパス、素のスロットヒット、インクリメンタルパス、およびインクリメンタルスロットヒットは1つの末尾で終わる。その末尾が`config_warnings`ブロック、CIネイティブのアノテーション、`--baseline-strict`の判定、および`--explain`の出力（#1533）を書き出す。退避はミスパス、すなわちデフォルトのミスと完全なインクリメンタルパスで実行される。スロットヒットは、現在と同様にそれを先送りするため、null実行がストアの走査のコストを支払うことはない。
  - 環境を構築した実行のみが実行統計ブロックとトレース付録を出力する: デフォルトのミスまたはコールドなインクリメンタルベースラインである。スロットから提供された実行、またはウォームな再チェックは、素のヒットがすでに行っているのと同様に、どちらも出力しない。それらのRBSカウントは、そのような実行が決して構築しなかった環境を記述してしまうためである。
  - `--incremental warm / cold`バナーおよびADR-88のファクトサーフェスノートは、`--incremental`または`incremental: true`がそのルートを要求した場合にのみ出力される。デフォルト実行の標準エラー出力は今日のままである。
  - **ゲート:** #1552のCLI specを拡張する。出力に影響を与えるすべてのフラグとフォーマットが各ルートを通過し、バイト単位で同一の標準出力、同じ終了コード、およびタイミングと統計ブロックを正規化した後に等しい標準エラー出力を生成しなければならない。
- **WD5 — `incremental: auto | true | false`**。CLIスイッチ`--[no-]incremental`が環境変数`RIGOR_INCREMENTAL`（同一の値）に勝ち、それが設定キーに勝つ。環境変数はルート専用のオーバーライドである: `RIGOR_CI_DETECT`をピン留めするのと同様に、specヘルパーがそれをピン留めするため、specはあらゆる場所で同じルートを採用する。反転時にデフォルトは`auto`となる。`auto`は以下のいずれかが成り立つ場合を除き、インクリメンタルルートを採用する:
  - **実行がインクリメンタルスロットプローブから除外されている場合**（`incremental_run_hit_eligible?`）:
    - エディタバッファ;
    - `--no-cache`（どの設定下でもスナップショットが読み書きされないことを意味する、#1525）;
    - `--explain`（#1533が着地するまで）;
    - `--coverage`（レポート実行はそこから何も得られないため）;
    - `--cache-stats`または`RIGOR_*_TRACE`プローブ;
    - ワーカープール（ワーカーがその読み取りを送り返すようになるまで、WD1）。
  - **実行が設定された`paths:`以外のファイルまたはディレクトリ引数を指定している場合**。両者を`IncrementalRunSlot.normalize_roots`が行うように正規化した後に比較する（`./lib`は`lib`）。そうでなければ、pre-commitフックやエディタの「このファイルをチェック」が記録のコストを支払い、プロジェクトスナップショットを何も再利用しないスナップショットで置き換えてしまうことになる。プロジェクトスナップショットからサブセット実行を提供することは、測定がそれを要求するまで先送りされる。
  - **環境がCIである場合**。判定は`CiDetector`のプロバイダーテーブルであり、`RIGOR_CI_DETECT`は無視される。そのスイッチはアノテーションを無効化するものであり、ジョブのルートを動かしてはならないためである。汎用の真となる`CI`もカウントされるため、それを設定する開発コンテナは、`RIGOR_INCREMENTAL`が別途指定しない限りフルルートを採用する。CIジョブは通常コールドで開始し、マージ決定が下される場所である。現在のルート上では記録のコストを支払わず、公式の記録ゲートで何も変更しない。`.rigor/cache`を永続化するジョブは`incremental: true`でオプトインする。
  - **エフェクトが有効化されている場合**（ADR-103）。その場合セッションはスロットを書き込まないため、null実行はそのエンジンフリーパスを失うことになる。
  - **前回の実行で不透明なプラグインが見つかった場合**（ADR-88、#924）、**またはどのファイルにも帰属しない読み取りが見つかった場合**（WD1）。不透明性は`#prepare`の後にのみ判明するため、ストア内のマーカーがそれを記録し、`auto`は次回の実行でそれを読み取る。マーカーはフィンガープリントと同様に、設定およびプラグインのアイデンティティによってキー付けされる。プラグインを準備するすべての実行がそれを書き直すため、フルルートも含まれ（`PluginFactFingerprint.from_registry`）、マーカーが名指すプラグインより長生きすることはない。初回実行はコストを支払う。不透明なプロジェクトは、毎回のインクリメンタル実行で、そして現在では再チェックの後にもすべてを再解析するため、フルルートのほうが厳密に安価である。
- **WD6 — スナップショットの他のリーダー**。言語サーバーがそれからプライムし（`ProjectContext`）、`rigor coverage --protection --mutation`がルートセットをまたいでそれをロードする（`Protection::MutationCache`）。両者はWD1およびWD2を通じてそれを検証し、どちらもそれらの決定が陳腐化していると呼ぶスナップショットを信頼し続けてはならない。
- **WD7 — 反転PRのためのゲート**。デフォルトは1つのPRで変更され、以下のすべてが成り立つ場合にのみ変更される:
  - **G1（健全性）:** WD1〜WD3がそのspecとともに着地していること。反転の時点で`--incremental`に対してオープンになっているすべての古い回答または出力同一性のissueがクローズされていること。現時点では#980、#1459、#1525、#1532、#1541、#1553、#1554、#1560、#1561、#1583、および#1585を意味する。#1565は両方のルートで古く、ブロックしない。
  - **G2（同一性）:** WD4が着地し、`--verify-incremental`がセットだけでなく順序も比較すること（#1542）。
  - **G3（コスト）:** `engine-warm.yml`上で、すべてのウォームジャーニー（null、リーフ、ハブ）が、`incremental: true`で`false`と比べて遅くなっていないこと。両方とも明示的に設定される。ジョブはCI上で実行され、`auto`ではフルルートを採用するためである。`RIGOR_INCREMENTAL=auto`でCI判定をバイパスした場合、ファイル引数の実行はフルルートを採用し、現在と比べて遅くならない。`engine-wall.yml`上で、空のキャッシュディレクトリへのコールドインクリメンタル実行のコストが、MastodonおよびRigor自身の`lib`上で、コールドの素の実行に対して最大10%増に収まること。比較には5回の実行の最低値と総アロケーションを使用する。±7%のCIのばらつき（ADR-50）は1つのサンプルには広すぎるためである。本日の単一サンプルでは+27%および+10%である（上記の表）。
  - **G4（性能ゲート）:** `bench/baseline.json`がADR-50 WD4の下で、空のキャッシュディレクトリへのコールドインクリメンタル実行の目標値を獲得し、記録のコストが再び忍び寄らないようにすること。
- **WD8 — プレビュー、次いでマイナーバージョンでの反転**。種別`:behaviour`の`incremental-by-default`の最先端機能（ADR-50）が、ADR-103 WD15で`effects-on-by-default`が行ったのと同様に、早期に`auto`をデフォルトにする。プロジェクト自身の証拠はドッグフーディングではなくG3のCI実行である: `make check`は`--no-cache`を実行し、`bleeding_edge: true`はエフェクトもオンにするが、WD5はこれを除外する。反転はG1〜G4の後の次のマイナーバージョンで着地し、リリースノートには`--no-incremental`および`incremental: false`が記載される。
- **維持されるもの**。`--verify-incremental`および`make check-incremental`は、WD1のspecとともに維持される。エディタモードのオプションBは依然として明示的な`--incremental`を通じてのみ到達される。`rigor unused`は引き続き`--incremental`を拒絶する。

## 却下および先送りされた代替案

| 代替案 | 理由 |
| --- | --- |
| #120が最初に求めたように、今すぐ反転する | すべてのユーザーがコンテキスト内の古い回答に遭遇し、デフォルトの末尾の出力が消失してしまう。 |
| `--incremental`を無期限にオプトインのままにする | 日常のループにおいてリーフ編集の10倍のギャップを残してしまう。 |
| 欠落した各入力をフィンガープリントへパッチ当てする | そのリストこそがバグの発生原因である。コードの隣のリストは収束せず、記録されたチェーンは収束する（WD1）。 |
| CIも含め、あらゆる場所でオンにする | コールドなCIジョブが、後の実行が再利用しない記録のコストを支払い、新しいルートが公式の記録ゲートとなってしまう。 |
| 陳腐化したプラグイン読み取りが帰属したファイルのみを再解析する | プラグインのメモ化の下では不健全である（WD1）。プラグイン契約を待つ。 |
| ルートセットごとに1つのスナップショット | ファイル引数の実行がルートセットを繰り返すことは稀であり、各々が何も再利用しないスナップショットへの記録コストを支払うことになる。また、スナップショットに欠けている退避も必要となる。WD5は代わりにそれらの実行をフルパスへとルーティングする。 |
| 依存関係グラフなしでのデフォルトパス上のファイル単位の結果再利用 | ファイルの診断は他のファイルに依存する。グラフなしでの再利用は不健全であり、そのグラフこそが`--incremental`そのものである。 |
| 新しいキャッシュフォーマット、デーモン、またはネイティブコード | #1507のプロファイルはそれらのいずれにもターゲットを与えていない。 |

## 影響

- **ポジティブ**
  - Rails規模のプロジェクトにおけるローカルな編集が、フラグなしで、コールド実行ではなく数秒のコストになる。
  - 新しい入力は読み取られることによって両方のキャッシュに加わり、WD1のspecがそれを強制する。
  - 5つのオープンなissueが1つのクラスとしてクローズされる。
- **ネガティブ（受容）**
  - ローカルのコールド実行が記録のコストを支払い、G3はその上限を10%に設定する。
  - ローカル実行とCI実行が異なるルートを採用する。`--verify-incremental`はスナップショットを決して読み取らないため、両者の回答を等しくするのはWD1のクロスプロセスspecである。それをすり抜ける古い回答はローカルで最初に現れ、そこでは`--no-cache`で回復できる。
  - 引き継がれた行のいずれかが陳腐化すると完全なベースラインが強制されるため、種類ごとの改良が着地するまで、`sig/`の編集はコールド実行のコストがかかる。
  - 不透明なプラグインを持つプロジェクトの初回実行は、1回だけ記録のコストを支払う。
  - ウォームなローカル実行は実行統計ブロックを出力しなくなる；環境を構築した実行のみが出力する。
- **同じ変更内で:** `docs/internal-spec/cache.md` §「2段階のゲーティング」、CachingおよびCLIのマニュアルページ、およびADR-46のステータス行。

## 他のADRとの関係

- [ADR-45](../45-unchanged-project-fast-path/): WD2の引き継がれたチェーンがスナップショットの妥当性検証（WD1）となり、スロットではなくスナップショットがそれを所有する。§「なぜチェーンが維持されるのか」が修正される: スナップショット同一性チェックは廃止される。反転後は、フルルート上の実行のみが素のスロットを書き込む。
- [ADR-46](../46-incremental-dependency-graph/): WD1〜WD3がスナップショットの妥当性検証とキーを改訂する。依存関係グラフは変更されない。
- [ADR-50](../50-release-engineering-and-stability-strategy/): プレビュー機構（WD8）およびベースライン目標（G4）。
- [ADR-51](../51-ci-diagnostic-output-formats/) WD7: そのプロバイダーテーブルが、`RIGOR_CI_DETECT`を無視する述語を通じて`auto`下のルートを選択する（WD5）。
- [ADR-88](../88-incremental-plugin-fact-soundness/): ファクトダイジェストはキー内に残る。不透明なプラグインはフルルートを採用する（WD5）。
- [ADR-103](../103-effect-labels/): エフェクトが有効化されたプロジェクトは、セッションがエフェクト有効でスロットを書き込むようになるまで、`auto`下でフルルートを採用する。`effects-on-by-default`がその前に昇格した場合、`auto`はあらゆる場所でフルルートを採用し、反転はそれを待つ。
