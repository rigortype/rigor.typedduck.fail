ステータス：**Accepted、2026-09-19。まだ何も実装されていません**。 `rigor lens`コマンドを追加します。これはZARDの`CONTEXT.md`およびADR-0003がすでに名指ししている「Rigor lens」です。本ADRは`rigor type-of`に関する#512の裁定を覆します：同コマンドは「unseeded」の出力を停止し、WD2の計算を採用します。実装は#1080〜#1085で追跡されます。

根拠（Grounding）：2026-09-19の敵対的レビュー（adversarial review）により、初稿の5つの前提が現在のコード上で成り立たないことが判明しました。WD2、WD3、WD4、WD5、およびWD6が修正された形状です。アンカー形式については：兄弟リポジトリ`rigortype/lisplens`内のlisplens ADR-0008（xxh3-64、4桁16進）、ADR-0013（単一モデル、簡潔なテキストが先）、およびADR-0017（ファイルレベルのドリフトゲーティング）。

## コンテキスト

今日、Rubyコードベースを学習するエージェントには2つの選択肢があります。ファイルをgrepして丸ごと読み込むことができますが、これにはトークンコストがかかり、grepで見えないもの（プラグイン合成メンバー、メソッドが実際に持つ型、どの再オープンがライブラリメソッドを再定義したか）をすべて見落とします。あるいは、一度に1つの位置（`type-of FILE:LINE:COL`）または一度に1つのスライス（`annotate`、`sig-gen --print`）をRigorに問い合わせることができます。シンボルを受け取るコマンドはありません。宣言のファイルごとのマップを提供するコマンドはありません。位置ごとのコマンドはファイル間の検出（cross-file discovery）なしで回答するため（`type_of_command.rb:91`、#512）、兄弟ファイルのクラスは`Dynamic[top]`と読み取られます。型がどこから来たのかを報告するものは何もありません。

ZARDも構造化された形式で同じものを必要としています：Rigorのファクトの上にAPI散文をオーバーレイするドキュメントツールです（ZARD ADR-0003）。

## 決定事項

> **lensとは、診断としてではなくマップとしてレンダリングされる、1つのターゲットに対する`rigor check`である**。それが出力するすべての型は、`check`がそのファイルに対して使用する型であり、`sig-gen`が書き込むとおりに綴られ、その型の来歴（provenance）とアンカーを伴う。ソーステキストは省略される。`check`が知っている情報未満で回答することは決してない。`check`と食い違うlensの回答はバグであり、トレードオフではない。

## 実務決定事項（Working decisions）

### WD1 ── 1つのモデル、2つのレンダリング；コマンドサーフェス

- **1つのモデル、2つのレンダリング**。モデルはエージェント向けのコンパクトなテキスト、およびツール向けの構造化JSONとしてレンダリングされます（lisplens ADR-0013の形状）。JSONはZARDが読み取るまで、未凍結の**`lens/v0`**として出荷されます。その後、ADR-50 WD1の凍結リスト上で`lens/v1`になります。契約が型の文字列やどの診断が発火するかをカバーすることは決してありません（ADR-50 § 決定事項3）。テキストレイアウトは凍結されませんが、その中のアンカートークン構文は凍結されます（WD6）。
- **コマンドサーフェス**。 `rigor lens`は新しいコマンドです。`type-of`、`annotate`、および`sig-gen --print`は維持されます。MCPはJSONを返す`rigor_lens`を獲得します。
- **スキルルーティング**。ユーザー向けスキルのうち、「このファイルには何があるか」という質問は`rigor-ask`へとルーティングされます（ADR-108 WD1の質問形状の境界）。エージェントが型を書く前にシンボルの契約を確認する場合、`rigor-type-oracle`がlensを指し示します。

### WD2 ── 計算：1ファイルの`check`、そして`type-of`もこれに従う

- **lensはそのターゲットファイルに対してインクリメンタルなcheckパスを実行する**。環境はプロジェクト全体の`source_files:`から構築されるため（runner.rbの#795ルール）、別のファイル内の`#:`は`check`のもとと同様に束縛されます。ADR-46のスナップショットは永続化されるため、次回のlensまたは`check`はウォームになります。
- **なぜ検出専用の事前パスではないのか**。それは調査対象のファイルに対してのみインラインRBSを合成し、Tier C / pre-eval / inflectionパス（`runner/project_pre_passes.rb`）をスキップするため、`check`を再現できません。
- **`type-of`は同じ計算を採用する**。 #512の「unseeded」注記は撤回されます：同じファイルに対して食い違う2つのオラクルは、両方を損なうことになります。
- **コールドコスト**。 redmineでの初回実行コストが測定され、受け入れ数値として記録されます。

### WD3 ── クエリとそれらが返すもの

- **クエリ形式**。ファイル、またはシンボル（`Foo`、`Foo#bar`、`Foo.baz`）。
- **名前解決**。完全修飾での完全一致が勝ちます。それ以外の場合、コマンドは候補をリストして終了コード2で終了します；`Order`と`Shop::Order`の間で推測することは決してありません。
- **シンボルの回答**。 `Foo`はファイルをまたぐすべての再オープンをマージし、各メンバーにそのファイルをタグ付けして、自身のメンバーのみをリストします。`--inherited`は祖先ごとにグループ化された祖先を追加します。`Foo#bar`はすべてのオーバーロードを返します。
- **複数サイトの検出**。マージには**すべての**定義サイトを保持する検出テーブルが必要です。現在、`fold_def_tables`は`def_nodes`を後勝ち（later-wins）、`def_sources`を先勝ち（first-wins）で畳み込むため（`scope_indexer.rb` ~:4193）、`Foo#bar`の2つの再オープンは1つの行に縮約されてしまいます。`def_sites`テーブルが追加されます；これはインクリメンタルスナップショットのスキーマをバンプするため、1回のコールド実行を消費します。
- **ライブラリで定義されたクラス**（`String`）。lensはプロジェクトの再オープンのみをリストします。ライブラリメンバーはソースごとのカウントとして要約され、`--library`はそれらを1行に1つずつリストします。
  - そのようなクラスへのプロジェクトの`include` / `prepend`は、継承ツリーの行にマークされます。このマークは検出ファクトにすぎません：ディスパッチには結合されません（#900）。
- **再オープンは拡張または再定義であり、1つの種別にマージされることは決してない**。既存のメンバーを置き換えるメンバーは`redefines <origin>`とマークされます。その型カラムは[ADR-110](../110-inherited-declaration-precedence/)のもとでの有効な型を示します。
- **`refine`メンバー**は定義元のモジュールの下で独自のグループを形成し、クラスへとマージされることは決してありません。Rigorは現在`refine`本体を解析しないため、それらの型は起源を伴う`Dynamic`として読み取られます。

### WD4 ── 行が担うもの

- **型の表記**。型は`sig-gen`が`.rbs`を書き込むのとまったく同一に書かれます：型位置におけるイレイジャ、およびリファインメントが適用される場所での`%a{rigor:v1:…}`（`%a{rigor:v1:return: non-empty-string} def number: () -> String`）。行は常に有効なRBSであるため、それをコピーするエージェントがリファインメントを型位置に書き込んでしまうことはありません（ADR-108のハザード、ADR-112 WD2）。
- **型の来歴（provenance）**は以下のいずれかです：
  - `sig`（`.rbs`のパス付き）
  - `inline`
  - `extrbs`
  - `inferred`
  - `plugin:<name>`
  - `library`

  これは宣言バッファから取得されます：インラインの貢献は仮想バッファ名を担います。`Dynamic`スロットは代わりにその動的起源を表示します。WD2がターゲットの本体を型付けするため、これは利用可能です。手書きと生成された`.rbs`は区別されません；環境はそれらを区別できません。
- **スロットごとに1つの有効な型**。ソースごとの型は、ソースが異なるときにのみ展開されます。これには[ADR-112](../112-extrbs-comment-channel/) WD5（#1075）が必要です：それまではADR-32 WD13が環境が存在する前に衝突するインラインメンバーを削除するため、lensは有効な型単独を表示します。
- **行に現れるその他の情報：**可視性、アリティ、行範囲、および行を伴う診断id。
- **プラグイン合成メンバー**。プラグインメンバー（ActiveRecordのカラムリーダーなど）は、新しい`Plugin::Base#declared_members(class_name)`フックを通じて名前と種別（kind）によってリストされます。このフックはADR-32 WD8と同様に、v1.0前では追加的なものです。今日プラグインは呼び出しごとに`dynamic_return`を回答しており、クラスごとにメンバーを列挙するものは何もありません。
  - プラグインが型を回答する場所にのみ型が出力されます：ActiveRecordのカラムリーダーは意図的に`Dynamic[top]`を回答します（#963、そうしなければ57件の偽陽性となるため）。
  - 同じ種別のメンバーは、1行の名前にまとめられます。
- **切り詰め（Truncation）**。何かがサイレントに切り詰められることは決してありません。
- **フラグの背後：**エフェクトラベル。
- **担われないもの：** APIドキュメント（ZARDがオーバーレイする）および呼び出し元（参照インデックスなし、#143）。

### WD5 ── フェーズ1ではソース本体なし；`--annotate`はフェーズ2

フェーズ1は宣言マップです。フェーズ2の`--annotate`は、行ごとの推論された型（`annotate`のデータを再利用）、行ごとのアンカー、およびトークンバジェット設計を備えた本体を追加します。Rigorがファイルを編集するかどうかは保留されています。WD6はどちらの回答もオープンにしておきます。

### WD6 ── アンカー

- **ハッシュ化されるもの**。各行は`line:hash`を担います：**先行するアノテーションコメントブロック（`#:` / `@rbs` / `@extrbs`）に宣言を加えた**逐語的なスパンに対する、4桁の16進数に切り詰められたxxh3-64です。ヘッダーは完全なファイルレベルのxxh3-64を担います。
- **なぜこれがlisplensから逸脱するのか**。 lisplensは周囲のコメントなしでデータをハッシュ化します（ADR-0008）。Rubyではアノテーションブロックは型の一部であるため、それを除外すると型の変更がアンカーによって気付かれないままになってしまいます。Rubyの編集ツールはこのスパン規則を採用します。
- **衝突**。スパンを共有する行（`attr_accessor :a, :b`）は序数を取ります。ゲーティングはlisplens ADR-0017と同様にファイルレベルです。
- **実装**。 xxh3-64は新しい依存関係なしでピュアRubyで実装されます（[ADR-31](../31-contribution-and-supply-chain-policy/)）。長さ0、1〜16、17〜128、129〜240、および241以上の入力に対する上流のベクターで検証され、lisplens（`xxhash-rust`）とクロスチェックされます。

## 却下された代替案

| 候補 | 理由 |
| --- | --- |
| 検出専用の事前パス、および唯一のルールとして「決してunseededにしない」 | `check`を再現できない：他のファイルからのインラインRBSやプラグインの事前パスが欠落する（WD2）。 |
| シードされたlensと並行して、`type-of`に対する#512の「unseeded」注記を維持する | 同じファイルが2つのオラクルから2つの異なる回答を得ることになる。 |
| 新しいコマンドの代わりに`type-of`を拡張する | ポイントクエリと宣言マップは異なる形状である；1つのコマンドでは両方をうまくレンダリングできない。 |
| 型位置にRigor自身の表記（`non-empty-string`）を出力する | ADR-112 WD3が着地するまではRBSではなく、それをコピーするエージェントが`sig/`を壊してしまう。`type-of`の2カラム形式も検討された；sig-genの形式はlens、sig-gen、および`.rbs`にわたって1つの表記を維持する。 |
| デフォルトでソース本体を含める | ファイルを読み込むより安価ではなくなる；行範囲によりエージェントは必要なものを読み込むことができる。 |
| lisplensのスパン規則（コメント除外） | 型アノテーションが変更されたときにアンカーが変化しなくなる。 |
| ネイティブの`xxhash` gem | 1回の呼び出しにつき数百バイトのためにサプライチェーンを追加することになる。 |
| 今すぐ`lens/v1`を凍結する | まだそれを読み取るコンシューマーが存在せず、凍結されたスキーマは最初の使用で明らかになったものを修正できない。 |

## 影響（Consequences）

好ましい影響：

- 1つのコマンドが、grepで見えないプラグイン合成メンバー、再オープン、および再定義を含め、「ここに何があり、その契約は何であるか」に答える。その型は`check`と一致する。
- `type-of`は、兄弟ファイルで宣言されたクラスに対して`Dynamic[top]`と回答することを停止する。
- アンカーはlisplensおよびhashlineと互換性があるため、将来の編集ツール（Rigor内部または外部）がそれらをゲートとすることができる。

好ましくない影響および持ち越し事項：

- コールドなプロジェクトでの最初のlensは、1ファイルの`check`と環境構築のコストを支払い、`type-of`もそれを支払う。
- `def_sites`スキーマのバンプは、1回のコールド実行を消費する。プラグイン契約はフックを獲得する。
- ソースごとの展開は#1075を待つ。アンカーはlisplensのコメント規則から分岐するため、Rubyの編集ツールはRigorの規則を採用しなければならない。
