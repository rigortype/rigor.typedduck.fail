ステータス: **Accepted — WD1（メモプロファイルカウンタ＋記録健全性のピン留め）は[PR #79](https://github.com/rigortype/rigor/pull/79)でランディング済み。WD2（runスコープのバケット＋依存関係のキャッシュ＆リプレイ）とWD3（イベントテイントのストアゲート）は実装済み（本PR、以下のゲート）。それぞれ、バイト単位で同一のコーパス診断＋WD1カウンタが対象の拒否量がヒットに転換していることを示すことをゲートとする**。本ADRサイクルで生まれた2つの設計は、自身の計測によって却下され、再追跡されないようWD4に記録する。WD6（相互再帰コンポーネントの走査を制限するtop戻り値の免除）は[#872](https://github.com/rigortype/rigor/issues/872)でランディングした。

根拠: [`20260713-corpus-perf-campaign.md`](../../notes/20260713-corpus-perf-campaign/)（PR #62のコールサイトごとのcallee評価に起因するmail +2.05M / +10.8%）＋[PR #79](https://github.com/rigortype/rigor/pull/79)のカウンタ表（§コンテキスト — 意思決定の証拠に再掲）。

## コンテキスト

callee本体の反復評価は、3度目に顕在化した構造的なコールドコストである（ADR-57の約+12%コールド、ADR-24 WD5の遅延サマリインデックス、PR #62の二分探索ステップ）。ADR-57のフォローアップメモ（`RETURN_MEMO_KEY`、`expression_typer.rb:1595-1770`）はrunスコープで健全だと考えられていたが、PR #79のカウンタ＋コードトレースが3点について認識を修正した:

1. **メモは実質的にファイル単位である**。そのバケットは`scope.discovered_def_nodes`のアイデンティティでキー付けされ、`ScopeIndexer#merge_project_method_indexes`（`scope_indexer.rb:~155`）が解析対象ファイルごとにそのテーブルを再構築する（`.merge` → 新しいアイデンティティ）ため、ヒットがファイル境界を越えることはない。mailの`Mail::Part#has_content_type?`は**564×**評価される（2つの相異なるキー）。これは、すべての消費側ファイルがそれを再評価するためである。このファイル単位のスコープ設定は、依存関係の記録が今日健全である理由でもある。ファイル内ヒットは、同じ消費側についてすでに記録済みのエッジをスキップし（同一キー ⇒ 同一の決定論的評価 ⇒ 同一のread-set）、クロスファイルのヒットは存在しない。
2. **支配的な拒否は、unroll実行中の候補一括除外である**。mailでは、3,355件の本体評価のうち2,706件（82%）が、定数引数unrollフレームがスタック上のどこかにある間に発生し、これはネストした結果が実際に一時的機構の影響を受けたかどうかにかかわらず、あらゆるネストした呼び出しのメモ候補性を無効化する。rigor `lib`: 9,977評価中、unroll拒否2,920件＋on-stack 2,074件。
3. **仮説として立てた2つのドライバは計測上死んでいた**: `consult-tainted = 0`が3つのターゲット全てで成立し（fixpointサマリーを参照したために拒否される祖先チェーンは存在しない）、相異なるキーの数はどこでも≤ 9である（引数粒度のスラッシングはない）。

カウンタのベースライン（RIGOR_BUDGET_TRACE=1、`--workers 0`、コールド）:

| ターゲット | inferエントリー | ヒット / ミス | 本体評価 | on-stack / unroll / tainted |
|---|---:|---:|---:|---|
| rigor lib | 18,597 | 8,620 / 4,983 | 9,977 | 2,074 / 2,920 / 0 |
| mail lib | 5,836 | 2,481 / 617 | 3,355 | 32 / 2,706 / 0 |
| activestorage analyzers | 453 | 422 / 31 | 31 | 0 / 0 / 0 |

もう一つの計測が設計を縛る。素朴な「`DependencyRecorder.active?`の間はメモをバイパスする」を実装したところ、analyzer型のサブツリーで**>200×**遅くなった（0.43s → >90s）。ファイル内DAGの重複排除はまさにメモが提供するものであり、記録run（ADR-46ベースライン、`--verify-incremental`）はそれを失う余裕がない。バイパスは元に戻され、[PR #79](https://github.com/rigortype/rigor/pull/79)は代わりにプロパティspecで現在の不変条件をピン留めする。

## 決定

メモへのあらゆる変更を統べる2部構成の基準:

1. **確定性（Finality）**。エントリーが保持できるのは、`(def_node, receiver, arg_types)`＋凍結されたrunグローバルインデックスの決定論的な純関数である値のみであり、一時的な推論状態の影響を受けた値は決して保持できない。一時性は、**計算をブラケットするイベントカウンタによって事後的に**検出する（fixpoint参照カウンタが確立したパターン）のであって、単に干渉した*かもしれない*機構に対する一括の事前ゲートによってではない。

2. **load-bearingな消費側に対する観測的等価性**。メモヒットは、診断や増分健全性に供給するあらゆる消費側にとって、新規評価と区別不可能でなければならない。すなわち、返される型AND ADR-46が記録した依存エッジである。したがってクロスファイルのヒットは、エントリーに紐づくread-setのリプレイをREQUIRE（WD2）する。記録バイパスは許容される形式ではない（>200×計測）。助言的な効果（由来の書き込み、トレースカウンタ）は明示的にnon-load-bearingである。

再帰ガードのキーは素の`(receiver, method)`のまま（ADR-24 WD5）。ADR-55の一時サマリー機構には手を触れない。

## ワーキング決定

- **WD1 — カウンタ＋不変条件のピン留め（ランディング済み、[PR #79](https://github.com/rigortype/rigor/pull/79)）**。`BudgetTrace`の`MEMO_*`カウンタ（エントリー / ヒット / ミス / 拒否内訳 / 本体評価）＋シグネチャごとの評価と相異なるキーの分布。「メモがアクティブな記録下で、記録されたエッジが完全である」ことをクロスファイルとファイル内の両ケースでピン留めするプロパティspec。ファイル単位バケットの依存性と>200×バイパス計測を名指しするメモへの不変条件コメント。素朴なバイパスは記録された却下形式である。
- **WD2 — runスコープのバケット＋依存関係のキャッシュ＆リプレイ**。ヒットがファイルを越えるよう、バケットをrun安定なアイデンティティに再キー付けする。ランディングした形式: `Runner#run_analysis`で鋳造され`scope.discovery`を通って渡される明示的なrun世代トークン（`DiscoveryIndex#run_generation`）。もう一方の候補、ランナーの凍結されたプロジェクトdef-indexオブジェクトは`merge_project_method_indexes`を生き延びない（ファイルごとに置換される）ため、スコープから到達可能なrun安定オブジェクトは存在しなかった。エントリーはdef-nodeオブジェクトのアイデンティティに強く（STRONGLY）キー付けし（`object_id`タプルではなくアイデンティティHash — run生存期間のバケットとGCされるファイルごとのパースが揃うと、そうでなければid再利用の衝突を許してしまう）、それを — 基準2に従い必須で — read-setのリプレイと対にする。記録がアクティブなとき、あるキーの最初の評価がその本体走査中に帰属したレコーダエッジを捕捉し（`compute_user_method_return`を囲むレコーダのサブキャプチャ）、それをエントリーに格納し、ヒットがそれを現在の消費側のアキュムレータにリプレイする。記録オフのrunはキャプチャとリプレイを完全にスキップする（記録はrunごとに決定される）。def-nodeアイデンティティに関する注記: calleeはrunごとに2つのノードアイデンティティを持ちうる（プロジェクトインデックスのパース対、定義側ファイル自身の解析パース） — defごとに高々2エントリー、許容範囲、経験的に検証する。ゲート: バイト単位で同一のコーパス（mail / kramdown / mastodon app-models / redmine app-models / rigor lib）。クロスファイルシグネチャが相異なるキーの数へ収束することを示すカウンタ（mail `has_content_type?` 564 → 約2〜4）。記録runの等価性spec（複数ファイルのフィクスチャでメモ無効化runとエッジが同一）。analyzerサブツリーが記録下で高速なままであること。
- **WD3 — 一括unroll除外を置き換えるイベントテイントのストアゲート**。候補性は「シグネチャがガードスタック上にないこと」に縮約される。ストアゲートは次のようになる。ブラケットされた計算の間に、（a）未確定のfixpointサマリーが参照されておらず（継承されたカウンタ、WD7で退役 ── 書き込み元を持たずイベントログがこれを包摂する）AND（b）一時機構イベント — 再帰ガードのヒット、unroll燃料枯渇フォールバック、ADR-55 WD1クランプ、fixpoint-cap崩壊 — が発火しなかった場合に限り格納する。機構（ランディング形式 — 素朴な形式はゲートなしより悪いと計測され、以下に記録）: `note_transient_fallback`のチョークポイントにおけるスレッドローカルな一時イベント深さログ（load-bearingかつトレース非依存。監査済みの5つのフォールバックサイトがそこを経由する — サイクル内ガードヒット、もつれた劣化、WD1クランプ、fixpoint-cap崩壊、燃料枯渇）。各イベントは、参照した一時状態を持つフレームのガードスタック深さを記録する。ブラケットされた計算は、あるイベントがブラケットの入口深さより**浅い**状態を参照した場合に限りテイントされる — すなわちその結果が、囲んでいる計算に属する一時的コンテキストを消費した場合である。入口深さ以下のイベントはフレーム自身のfixpoint/unrollに内在し、そのフレーム自身の決定論的な最終値を計算する一部なので、それをテイントしない（再帰クラスタの最外フレームは、構成上その収束結果を格納する）。このゲートの素朴なブラケットカウンタ形式 — 計算中にANYイベントがあれば拒否 — は最初に実装され計測された。rigor-libの本体評価は44,795件に膨れ上がった（ベースライン9,927件に対して）。再帰的な所有者が自身のfixpointの内部ガードヒットによって恒久的にテイントされ、決して格納できなくなるためである。中間的なtop-of-stackは常に格納する精緻化は15,122件でランディングした。深さ規則は両者を1つの統一基準として包摂し7,339件でランディングする。健全性の論拠: 結果に対する一時状態のあらゆる影響は監査済みのイベント経路の1つを通じて顕在化し、深さ比較は「自分のサブツリーが自身の一時機構を完了まで走らせた」（確定）を「囲んでいる計算の実行中状態を消費した」（コンテキスト依存、非確定 — 基準1）から区別する。実装者は、再帰機構（`compute_user_method_return` → `evaluate_guarded_user_method_body` → `fixpoint_user_method_return`とunrollヘルパー）内のすべての早期リターン / フォールバックを監査し、それぞれをチョークポイント経由でルーティングしなければならない（MUST） — 監査表は`TRANSIENT_EVENT_DEPTHS_KEY`の傍らに置かれ、specが正確な5サイトのカテゴリー多重集合をピン留めするため、将来のフォールバックが黙ってuntaintedに加わることはない。期待される回復: mailの2,706クラスとrigor-libの2,920クラスの多くがストア/ヒットに転換する（パーサ型のコーパスが受益者）。ゲート: バイト単位で同一のコーパス＋カウンタ（unroll実行中の拒否 → 約0、mailの本体評価3,355 → 1,500を大きく下回る）＋mail＋rigor libでのコールドA/Bのウォール/アロケーション。
- **WD4 — 計測上死んでいる設計（新たなカウンタ証拠なしに再追跡しない）**。（a）確定を意識した*サマリー*テイントゲート（「後に確定したサマリーを参照した」を「未収束のイテレートを埋め込んだ」から区別する）: `consult-tainted = 0`が3つのベースラインターゲット全てで成立 — 回復すべきものがない。WD3のイベントカウンタが健全な部分を包摂する。（WD7: その読み取りは空虚であり、カウンタに書き込み元がなかったため、何らかの証拠ではありません。結論は包摂の論拠単独で成立し、WD7はまさにそれを述べています: 唯一の参照サイトがまずイベントをログに記録します。）（b）パラメータread-maskのキー正規化（未読パラメータのディスクリプタを省く）: 相異なるキーの数がコーパス全体で≤ 9 — 潰すべきスラッシングがない。
- **WD6 — WD3ストアゲートに対するtop戻り値の免除（[#872](https://github.com/rigortype/rigor/issues/872)）**。WD3の深さ規則は健全ですが、相互再帰メソッドの強連結成分（SCC）の内部では、事実上すべての格納を拒否します: ネストされた各計算はすでにガードスタック上にあるシグネチャに再突入し、サイクル内ガードサイトはその祖先のより浅い位置でイベントをログに記録するため、ブラケットはテイントされたものとして読み取られます。[#870](https://github.com/rigortype/rigor/issues/870)のフィクスチャでは、18,436件中18,412件のメモミスが結果を計算して破棄し、メソッドが2つ追加されるごとに本体評価が約3.7倍に増加し、rufo 0.18.2の`formatter.rb`が25分経っても終了しませんでした ── これはPR #547が作り出したのではなく表面化させた形状です（#547以前の`user_method_param_shape_simple?`早期脱出により、コンポーネントの手続き間エッジがそもそも存在していませんでした）。免除: **結果が`Dynamic[top]`のときは、コンテキストによりテイントされた結果であっても格納する**。そのようなエントリーは提供すべきコンテキスト依存の情報を運んでいません ── `untyped`は束（lattice）のトップであり[ADR-5](5-robustness-principle.md)の縮退の下限であるため、テイントされていない再計算が異なりうる唯一の方法はより精密であることだけであり、格納されたtopを提供することは祖先のコンテキストが捏造した型を表面化させることも、新鮮な評価が引き起こさない診断を引き起こすことも決してありません（`untyped`からは何も報告されません）。その代償は、再計算が精密であったはずの箇所で診断を見逃す可能性があることです;経験的な答えはそれが起きないということです ── `--format json --no-cache`は`lib`、`plugins/*/lib`、`examples/*/lib`、liquid、mail、redmine、mastodonにわたってバイト単位で同一です。これは意図的にWD4（a）ではありません: あの廃止された設計は、確定を証明することによって*精密な*テイントされた結果を回復しようとしたものであり、WD4は有効なままです。これと並行して、`context_tainted?`は候補の計算ごとに`log[event_mark..]`サフィックスを確保する代わりに、インデックスによって追記専用イベントログを走査します ── これは#870がサンプリングした`rb_ary_push` / GCスイーププロファイルの背後にある、イベント数に対して2次のアロケーション項です。`Dynamic`へ縮退する`(signature, outermost entry)`ごとの本体評価上限が代替案として検討されました: これはコーパス上で発火しないことを示さなければならない本物の精度バジェットであり、走査を*上限 × シグネチャ × 最外エントリー*にしか抑え込めず、rufo上では依然として2次です ── 免除はより小さく厳密により良いため、上限は実装されていません。ゲート: `spec/rigor/inference/mutual_recursion_walk_growth_spec.rb`がフィクスチャの本体評価を制限し（サイズ6で798 → 24）、コンポーネントについて`MEMO_REFUSE_TRANSIENT`を0に固定します。
- **WD7 — WD3ストアゲートの参照カウンタ半分を退役（[#875](https://github.com/rigortype/rigor/issues/875)）**。WD3はそのゲートを2つの連言（conjunct）として表現し、そのうちの2番目が新しいものでした; 1番目はADR-84以前のメモから継承されたものであり、書き込み元を持ったことが一度もなかったことが判明しました ── `SUMMARY_CONSULT_COUNTER_KEY`は2026-06-12（`4b476918`）にすでに未書き込みの状態で導入されていたため、`summary_consult_count`はすべての実行で0を読み、`MEMO_REFUSE_CONSULT_TAINTED`はどこでも一度も発火しませんでした（上記のWD0測定および[#870](https://github.com/rigortype/rigor/issues/870)のプロファイルに記録された`consult-tainted = 0`の読み取りはこれであり、参照テイントの測定された不在ではありませんでした）。それを配線するのではなく退役させることが、機構が支持するものです: `consult_summary`には呼び出しサイトが正確に1つしかなく（`compute_user_method_return`内のサイクル内ガードヒット）、そのサイトは参照する*前に*参照されたオーナーのスタック位置で`note_transient_fallback`を呼び出すため、囲むブラケットをテイントしうるすべての参照は（b）の下ですでに入口未満のイベントとなります。したがって、カウンタを配線することは（b）がすでに拒否しているブラケットを再拒否することにしかならず、WD6のtop結果の免除を差し引くことになります ── すなわちWD6の一部をサイレントに取り消してしまうことになります。定数、`summary_consult_count`、拒否分岐、および`MEMO_REFUSE_CONSULT_TAINTED`カテゴリーとその`--budget-trace`列は削除されました;ゲートは（b）単独となります。`--format json --no-cache`は`lib`、`plugins/*/lib`、`examples/*/lib`にわたってバイト単位で同一であり、一度も実行されなかった分岐としては当然の結果です。
- **WD5 — forkスコープ設定は維持される**。forkプール下でのワーカーごとのメモ（Thread.current、fork後に投入）は維持される。fork越えの共有は、境界限定の重複排除のために`Type`キャリアをシリアライズすることになる（ADR-67 ForkMap残余の裁定）。並列runでワーカー重複評価が支配的であることを示すプロファイルが出た場合にのみ再検討する。

## 却下された代替案

- **記録バイパス**（`DependencyRecorder.active?`下でメモを無効化）: 実装し、analyzer型ファイルで>200×と計測、元に戻した — WD1に記録。基準2がその形式を禁じる。
- ホットシグネチャに対する**キーの粗粒度化 / eval-cap-then-widen**: 返される型を変える（foldが消える） → バイト単位で同一でない。速度のための精度トレードは、黙ったメモポリシーではなくADR-41の予算サーフェスに属する。
- **コールノードごとの結果キャッシュ**: 却下を再確認（ADR-52 WD5 — スコープ依存）。このメモは入力をキーとし、決してノードをキーとしない。

## 帰結

- 正: メモはADR-57がキューに入れたもの — 実際にrunスコープ — になり、増分健全性のストーリーはトレードされるのではなく強化される（リプレイは今日の偶発的なファイル単位の安全性より強い）。mailの82%の拒否量が基準に統べられたアンロックを得る。カウンタが将来のあらゆるメモの主張を計測可能にする。2つの死んだ設計が再議論に対してピン留めされる。

## 他のADRとの関係

[ADR-57](../57-self-call-return-adoption/)は健全な結果メモをキューに入れた。本ADRはそのクロスファイル形式を提供する。[ADR-24](../24-self-method-call-resolution/) WD5のガードキー制約は逐語的に保持される。[ADR-52](../52-compiled-plugin-contribution-dispatch/) WD5の却下は再確認され、基準1の「入力であり、決してノードではない」へと一般化される。[ADR-55](../55-recursive-return-precision/)の機構は不変であり、WD3はその既存のフォールバックイベントを数える。[ADR-46](../46-incremental-dependency-graph/)の深いエッジは基準2のload-bearingな消費側であり、WD2のリプレイはそれに対して設計される。[ADR-41](../41-inference-budget-design/)は、本ADRが密輸することを拒む、将来の速度のための精度トレードを所有する。
