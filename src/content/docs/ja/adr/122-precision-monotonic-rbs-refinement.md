ステータス: **Proposed、2026-10-12**。#1487、#1488、および#1489に対処。Rigorのシグネチャ生成および既存RBSのリファインメント（`rigor sig-refine`）に対する、精度単調性（precision-monotonicity）とレイアウト安定（layout-stable）の契約を確立する。

根拠: [`docs/notes/20261012-alba-onboarding-rbs-inline-pilot.md`](../../notes/20261012-alba-onboarding-rbs-inline-pilot/)におけるAlbaドッグフーディングパイロット;未解決の不具合である#1487（tighter-return候補が既存の精密なパラメータを`untyped`に拡大してしまう）、#1488（再オープンされたモジュールでの`DuplicatedMethodDefinitionError`）、および#1489（リテラル呼び出し引数から推論された特異メソッドパラメータ型）;ならびにSteepのミュータブルなインスタンス変数ナローイング境界。

## コンテキスト

Rigorのシグネチャ生成（[ADR-14](../14-rbs-sig-generation/)で導入された`rigor sig-gen`）は、もともと型付けされていないRubyリポジトリ向けのブートストラップツールとして構想されていた: アノテーションのないコードベースを読み取り、型推論を実行し、初期の`.rbs`ファイルを`sig/`に書き出す。

しかし、成熟したRubyプロジェクトの実世界での導入ジャーニー（Albaオンボーディングパイロットで実証）は、根本的に異なるライフサイクルをたどる:
1. **既存のアノテーション:**プロジェクトがゼロシグネチャから始まることは稀である。すでに手書きの`sig/**/*.rbs`ファイルや埋め込みの`rbs-inline`アノテーションを維持している。
2. **「untyped削減」のニーズ:**主なユーザー要件は、ゼロから定型句全体を生成することではなく、人間が指定した精度を低下させたり下流の型チェッカー（Steepなど）を破壊したりすることなく、既存の宣言内の残存する`untyped`箇所を外科手術的に引き締めることである。
3. **既存プロジェクトにおける現在の`sig-gen`の失敗:**
   - **パラメータの拡大（#1487）:** `sig-gen`が`tighter_return`候補を特定したとき、その候補エミッターはRuby ASTから新しい`RBS::AST::Declarations`オブジェクトを構築し、そこではアノテーションのないパラメータがデフォルトで`untyped`になる。その結果、戻り値の型を引き締めると、既存の精密なパラメータ型が破壊的にダウングレードされてしまう（例: `(Symbol | Proc) -> untyped`が`(untyped) -> bool`になる）。
   - **モジュール再オープンの重複（#1488）:** `LayoutIndex`はクラス/モジュール名をクラス宣言レベルでRBSファイルパスにマッピングする（`Alba -> sig/alba.rbs`）。2次ファイルがトップレベルモジュールを再オープンするとき（例: `lib/alba/association.rb`が`module Alba`を再オープン）、`CandidateClassifier`は`sig/alba/association.rbs`をターゲットとする定義を生成する。これにより`sig/alba.rbs`ですでに宣言されているメソッドに対して重複したメソッド定義が出力され、`RBS::DuplicatedMethodDefinitionError`によって`rbs build`および`steep check`がクラッシュする。
   - **リテラルの過剰特化（#1489）:**パラメータ観測モード（`--params=observed`）はランタイムの呼び出し引数や単一サイトのリテラルを捕捉する。プリミティブリテラルを`String`、`Integer`、または`Symbol`に一般化する代わりに、リテラルシングルトン型（例: `"foo"`、`1`）を推論するため、有効な呼び出しを拒否する脆弱なシグネチャが生成されてしまう。
   - **セッターの戻り値およびASTアーティファクトの汚染:** Ruby ASTにおいて、セッター（`name=`）は代入された値やヘルパー呼び出し（例: `reset_transform_keys`）へと評価される。`sig-gen`はこれら任意の途中の戻り値型を推論してしまい、RBSセッターの不変条件（`(T) -> void`または`(T) -> T`）に違反して`Ruby::SetterBodyTypeMismatch`診断を生成する。同様に、末尾の代入（`@ivar = val`）やループ反復（`.each`）は、メソッドの意味論的意図が`void`や`self`である場合に、戻り値推論を汚染する。
   - **Steepのミュータブルインスタンス変数バリア:** Steepにおいて、ミュータブルなインスタンス変数（`@ivar`）はローカル変数への再バインド（`v = @ivar`）なしには制御フロー分岐をまたいで絞り込まれない。ジェネレーターツールが内部ivarに対して厳格なユニオン型（`@check: Proc | false`）を推論・出力すると、Steepはあらゆる分岐で`NoMethod`の偽陽性を報告する。外部メソッドインターフェースは厳格に型付けされなければならないが、分岐によってチェックされる内部のミュータブルivarは、ローカルで再バインドされない限り、広い境界／`untyped`境界を維持しなければならない。

## 決定

**精度単調かつレイアウト安定なシグネチャリファインメントモデル**を確立し、既存のRBS宣言をアップグレードするための専用ワークフローとして`rigor sig-refine`（および`rigor sig-gen`内の`--mode=refine`）を導入する。

この設計は3つの主要な基準に支配される:
1. **精度単調性（Precision Monotonicity）:**リファインメントは既存の型を引き締めるか維持するのみでなければならない;既知の静的型を`untyped`に置き換えては決してならない。
2. **レイアウト不変性（Layout Invariance）:**プロジェクトのRBSファイルですでに宣言されているメソッドには不変の正準な配置場所（canonical home）がある;リファインメントがファイルをまたいで重複宣言を作成することは決してない。
3. **下流チェッカーの生存可能性（Downstream Checker Viability）:** Rigorが生成したシグネチャは、合成的な型絞り込みバリアを導入することなく、RigorとSteepの両方でクリーンにチェックされなければならない。

### 作業決定事項（Working Decisions）

#### WD1 ── 精度単調性の不変条件（束サブタイプ不変条件）
既存のシグネチャ $S_{old} = (P_1, \dots, P_n) \to R_{old}$ を候補 $S_{new} = (P'_1, \dots, P'_n) \to R_{new}$ へとリファインするとき:
1. **パラメータの保持:** `tighter_return`および既存メソッド候補について、パラメータ推論パスによって明示的にターゲットにされない限り、パラメータ型は $S_{old}$ から逐語的に保持されなければならない。具体的には、`Writer#emit_signature`はアノテーションのないASTノードからパラメータを再合成してはならない。
2. **untypedへの劣化の禁止:** $P_i \neq \text{untyped}$ の場合、$P'_i$ が`untyped`であってはならない。$R_{old} \neq \text{untyped}$ の場合、$R_{new}$ が`untyped`であってはならない。
3. **戻り値のサブタイプ関係:** Rigorの型束において $R_{new} <: R_{old}$ であること。
4. **プリミティブリテラルの一般化（#1489）:**観測されたリテラル（`String`、`Integer`、`Float`、`Symbol`）は、その位置がenumユニオン（`:json | :yaml`）やリテラルフラグとして明示的に型付けされていない限り、リテラル型ではなくプリミティブクラス型（`String`、`Integer`、`Float`、`Symbol`）へと一般化されなければならない。

#### WD2 ── メソッドレベルのレイアウトおよび出自インデックス（#1488）
1. `LayoutIndex`はクラスレベル（`class_name -> file_path`）からメンバーレベルへとアップグレードされる: `(class_name, method_name, kind) -> canonical_rbs_path`（ここで`kind`は`:singleton`または`:instance`）。
2. **正準な配置場所のルール（Canonical Home Rule）:**メソッドがプロジェクトの既存の任意のRBSファイル（`sig/**/*.rbs`）内ですでに定義されている場合、そのファイルがその排他的な正準ターゲットとなる。そのメンバーをターゲットとする候補はすべて、そのファイルへのインプレース編集として書き込まれなければならず、Rubyソースファイル名から派生した新しいファイルへ出力されてはならない。
3. **再オープンされたモジュールのデフォルト:** Rubyファイルが既存の名前空間を再オープンして`sig/`に存在しない新しいメソッドを追加するとき、別段の設定がない限り、正準ターゲットは兄弟ファイルを合成するのではなくプライマリ名前空間ファイル（例: `Alba`に対しては`sig/alba.rbs`）へとデフォルト設定される。

#### WD3 ── 意味論的戻り値フィルタリングおよびセッター不変条件
1. **セッター契約:** `/=\z/`にマッチするメソッド（例: `attribute=`）はセッター意味論のもとに分類される: その戻り値型は`void`（またはパラメータ型`T`）へと正規化され、末尾のクリーンアップやヘルパー呼び出し（`reset_transform_keys`）の中間的な戻り値は無視される。
2. **副作用末尾アーティファクト:**メソッドがそれ以外ではコマンドである場合に、ivar代入（`@ivar = val`）や副作用のある反復（`.each { ... }`）のみで構成される末尾の式は、構造的契約が`void`や`self`を示している場合、末尾のRHS型を盲目的に推論してはならない。

#### WD4 ── インスタンス変数vsメソッドの境界分割（Steep ivarバリア）
1. **境界の分離:**メソッドパラメータとメソッド戻り値は外部契約を構成し、最大の静的精度で型付けされなければならない。
2. **内部ivarの実用主義:**内部のランタイムポリモーフィズムに関与するミュータブルなインスタンス変数（`case @resource; when Class ... when Proc ...`）は、プロジェクトがSteepをターゲットとしている場合、狭いユニオンへと過剰に型付けされてはならない。Steepには分岐をまたぐivarの絞り込みが存在しないためである。
3. デフォルトポリシー: `--strict-ivars`が明示的に有効化されているか、ivarが1回のみ初期化され動的に再代入されないことが証明されない限り、内部で分岐されるivar上では`untyped`または広い境界を保持する。

#### WD5 ── スコープ認識型の型エイリアス畳み込みおよびインターフェース抽出
1. クラス/モジュールの名前空間全体でシグネチャを生成またはリファインするとき、繰り返される複数メンバーのユニオン型（`Symbol | Proc | String | ...`など）は認識され、プロジェクトレベルの型エイリアス（例: `type serializable_hash_type = ...`）へと畳み込まれなければならない。
2. インライン化された生のユニオン型を繰り返すよりも、プロジェクトの`sig/`環境で発見された既存の型エイリアスを保持し、優先する。

#### WD6 ── `rigor sig-refine` CLIサーフェスおよびワークフロー
1. 専用のワークフローコマンドを導入する:
   ```sh
   rigor sig-refine [paths...] [options]
   ```
   （および`rigor sig-gen`下の`--mode=refine`フラグ）。
2. モード:
   - `--check`: 既存のRBSシグネチャをRigorの型推論と照合して解析する。WD1–WD5に違反することなく`untyped`箇所を引き締め可能な候補が存在する場合、非ゼロで終了する。
   - `--diff`: 提案される精度リファインメントを示すカラー化されたunified diffを表示する。
   - `--write`: 既存のRBSファイルに対してリファインメントをその場で直接、外科手術的に適用する。
3. メトリクス: 引き締められた`untyped`箇所の正確な数、保持されたシグネチャ、および拒絶されたリグレッションを報告する。

## 却下および先送りされた代替案

| 代替案 | 採用しなかった理由 |
| --- | --- |
| `sig-gen --overwrite`のみに依存する | 手書きのコメント、型エイリアス、および精密なパラメータ型を、アノテーションのないASTのデフォルトで上書きしてしまう（#1487）。 |
| ヒューリスティックなASTのみのパラメータ推論 | ランタイムの呼び出し元の制約を知ることができない;過剰特化されたリテラル型（#1489）または偽陽性のパラメータ拒否のいずれかにつながる。 |
| すべてのivarに対する狭いユニオンの自動型生成 | ミュータブルivarの絞り込みバリアにより下流のSteepを直接破壊する;有効なRubyコード上で何十もの偽陽性を生み出す。 |
| 再オープンされたモジュールに対するファイル名1:1マッピング | 複数の`.rbs`ファイルにまたがって重複したメソッド定義を出力し、`DuplicatedMethodDefinitionError`で`rbs build`をクラッシュさせる（#1488）。 |
| Rubyコード内でのインライン型アノテーション（`@type`、`@rbs`）の要求 | Rigorのコア設計境界に違反する: RubyアプリケーションコードはRigor固有のアノテーションやDSLを必要としない。 |

## 結果

- **プラス面**
  - 確立されたRBSまたは`rbs-inline`シグネチャを持つ既存プロジェクトが、`untyped`の負債を単調に解消するためにRigorを安全に導入できる。
  - 戻り値の型を引き締める際に、既存のパラメータ型を低下させるリスクがゼロになる（#1487解決）。
  - 再オープンされたモジュールを持つコードベースにおける`DuplicatedMethodDefinitionError`を排除する（#1488解決）。
  - 生成およびリファインされたシグネチャが、RigorとSteepの両方でクリーンにチェックされる。
- **マイナス面（受け入れ済み）**
  - ファイルレベルのインデックスに加えて、2次元のメンバーレイアウトインデックス`[class, method, kind]`を維持する必要がある。
  - `sig-refine`の候補生成は、既存のRBS ASTをパースしてdiffを取る必要があるため、単純なAST出力よりも計算上の負荷がわずかに高くなる。
