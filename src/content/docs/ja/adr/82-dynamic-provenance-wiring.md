ステータス: **WD1+WD2+WD3+WD6+WD7+WD8を2026-07-06に実装;WD9（外部gem定数の所有権）を2026-07-11に実装**。[ADR-75](../75-dynamic-provenance/)は`Dynamic[T]`の由来（provenance）サイドチャネルを追加し、それを`coverage --protection`のtractabilityラベルを通じて表面化させたが、Mastodonでのフィールド計測は、そのラベルが**実際のRailsアプリでは情報量に乏しい**ことを示す: 未保護のディスパッチサイトの84%がキャッチオールの`unsupported_syntax`（→ `engine_gap`）原因を持ち、さらに14%は原因をまったく持たない一方、ラベルが表面化させるために存在する2つの*ユーザーがアクション可能な*原因——`framework_dsl_boundary`（→ プラグインを有効化）と`external_gem_without_rbs`（→ RBSを追加）——は**ゼロ**サイトでしか発火しない。このADRは、キャッチオールをユーザー（またはエージェント）がアクションを取れるアクション可能なバケットへ打破するように、由来の記録とルックアップを配線する。全体を通じて精度加算的だ——ADR-75のサイドチャネル契約に従い、型・診断・重大度の変更はない。

**WD5の計測結果（2026-07-06）:** WD2+WD3が安価な記録スライスを着地させた——発見メソッド層とユーザークラスフォールバック層で記録される新しい`inferred_return_untyped`原因だ。Mastodon app+libでは、未保護21,119件のうち**211サイト**を再バケット化する（unsupported_syntax 17,727→17,565、null 2,921→2,872）——約1%、保護比率は不変（精度加算的を確認）。スポット裁定: 移動したサイトは`<user-method>.foo`チェーンで、そのレシーバーは解決されたメモ化/属性メソッドであり、その戻り値をエンジンが推論できない（`def parsed_uri`を伴う`parsed_uri.path`、`media_attachment_file.path`）——正しく帰属されている。この小ささが**G1の診断を裏づける**: 支配的な84%はローカル/ivar読み取りのレシーバーを持ち、その起点に呼び出しノードの記録が届かないので、**WD1（ルックアップ伝播）は必須であって需要ゲート付きではない**——計測がWD5の未解決の問いをWD1構築の側に解決する。

**WD1の結果（2026-07-06）——実装済み、パフォーマンス中立、そして正直に控えめ**。WD1は、ローカル / ivarバインディングの起点を、後続の素の`x` / `@x`レシーバー読み取りへ伝播する（`Scope#local_origins` / `#ivar_origins`のサイドテーブル、代入時に設定され、レシーバー自身のノードが起点を持たないとき`ProtectionScanner`が参照する）。パフォーマンス中立だ——Mastodon `lib`のアロケーションは+0.1%動く（27.54M対masterの27.51M;`make bench-perf`ゲートが失敗するのは、そのコミット済みベースライン19.77M / 16.6秒ウォールが陳腐化しているからにすぎず——master自身も同じ27.5M / 7.2秒でそれに失敗する）。だがカバレッジの見返りは**「主要レバー」という枠付けが予測したより小さい**: Mastodon app+libでnull（原因なし）バケットから約**322サイト**を動かし（null 2,872→2,550）、比率は不変。その理由は、残余を裁定して見つかった: 支配的なキャッチオールのレシーバーは素のローカル/ivar読み取り（それらはWD1が対処する小さなnullバケットだ）**ではなく**、**中間式 / チェーンレシーバー**だ——`signed_request_account.uri[…]`（`[]`のレシーバーは呼び出しチェーンだ）、`account_id_param.present?`（レシーバーはメソッド呼び出しだ）、`Status.tagged_with(tag.id)`。`Dynamic`レシーバーにディスパッチされたチェーンリンクの`.foo`は、その結果に*何も*記録せず、上流の原因を失った。そこで根拠に裏づけられた次のレバー、**WD6——チェーン起点継承**（`Dynamic`レシーバーへのディスパッチが、レシーバーの起点をその結果へ継承し、由来がメソッドチェーンを生き延びる）が、**続いて着地した**——パフォーマンス中立で、残余のnullバケットを半分以上削る（2,550→1,356）。だがそれが買うのは由来の*完全性*であって、tractabilityの*アクション可能性*ではない: 伝播された原因のほとんどは、チェーンの根がそれを記録するため`unsupported_syntax`だ。したがってWD6の後の次のレバーは、それらの根を拡充することだ（WD6のワーキングデシジョンを参照）。WD1は保持される: 正しく、精度加算的で、パフォーマンス中立で、WD6が共有するルックアップのバインディング伝播の半分だ。

根拠: [2026-07-06 Mastodonカバレッジ/由来ノート](../../notes/20260706-mastodon-coverage-provenance-and-siggen-rbs-validity/) §2（計測 + 2つのエンジンギャップG1/G2）と、[2026-07-04 Railsオンボーディングノート](../../notes/20260704-rails-coverage-onboarding-carrier-trap/) §O5。後者はキャッチオールの誤ラベルを最初にレバーとして名指したが、そのセッションの作業がカバレッジスコープの修正（プラグイン対応 + 発見シード）に向かったため未実装のまま残していた。

## コンテキスト

`coverage --protection`（[ADR-63](../63-type-protection-coverage/)）は「ここに型を追加」ホールをランク付けし、[ADR-75](../75-dynamic-provenance/)以降は、各ホールに*tractability*: `add_rbs`、`enable_plugin`、または`engine_gap`をタグ付けする。意図は注意を誘導することだ: 手書きのRBSが閉じるホールは、ユーザーがエンジンを待つべきホールではない。Mastodon `app`+`lib`（Rigor v0.2.7、30,822ディスパッチサイト、未保護21,119）での分布は:

| tractability（原因） | サイト | 割合 |
| --- | --- | --- |
| `engine_gap`（`unsupported_syntax`） | 17,727 | 84.0% |
| （原因が記録されていない / null） | 2,921 | 13.8% |
| `add_rbs`（`explicit_untyped`） | 471 | 2.2% |
| `enable_plugin`（`framework_dsl_boundary`） | 0 | 0% |
| `add_rbs`（`external_gem_without_rbs`） | 0 | 0% |

ホールを駆動しているレシーバーはありふれたRailsのイディオムだ——`Tag.find_normalized(...).id`（`untyped`を返すカスタムActiveRecordファインダー）、`current_user&.account&.unavailable?`（Deviseのヘルパー）、`params[:limit].present?`（ActionController）。これらは「プラグインを有効化」または「RBSを追加」へ誘導される*べき*だが、代わりにすべてキャッチオールに落ちる。エンジンを読むと、この誤ラベルには2つの独立した原因がある:

- **G1——ルックアップがレシーバーノードローカルである**。`ProtectionScanner#scan`はディスパッチの**直近のレシーバーノード**（`protection_scanner.rb:49`、`scope.dynamic_origins[node.receiver]`）で由来を読むが、`MethodDispatcher`は特定の原因を**Dynamic値を生み出した呼び出しノード**（`method_dispatcher.rb:113/141/166/178`）で記録する。`tag.id`では、レシーバーノードはローカル読み取り`tag`であって、それを動的にした`Tag.find_normalized(...)`呼び出しではない。ゆえにローカル読み取りとivar読み取りのレシーバーは記録を見つけられない（→ null）か、`ExpressionTyper#fallback_for`の汎用的な`UNSUPPORTED_SYNTAX`（`expression_typer.rb:911`）へ落ちる。記録された原因がスキャナーに届くのは、レシーバーが*それ自身*生み出す呼び出しであるとき——`.c`のレシーバーが呼び出し`a.b`であるチェーンされた`a.b.c`——だけだ。

- **G2——特定の原因は、ホールでめったに成立しない条件下で記録される**。`FRAMEWORK_DSL_BOUNDARY`が記録されるのは、プラグインの`dynamic_return`が`Dynamic`を返すとき（`method_dispatcher.rb:112`）だけだが——プラグインは圧倒的に*具体的な*型を返し、具体的なレシーバーはホールではなく*保護済み*だ。`EXTERNAL_GEM_WITHOUT_RBS`はADR-10の依存関係ソース推論 / `pre_eval:`に依存し、どちらもオプトインで、素のRails設定ではオフだ。そして*ユーザー*メソッドを、その戻り値をエンジンが推論できないために`Dynamic`へ解決する2つの層——`try_discovered_method`（`method_dispatcher.rb:246`）と`try_user_class_fallback`（`:210`）——は原因を**まったく**記録しない。

どちらのギャップもラベリングの些事ではない: それらがなければ、ADR-75のtractabilityシグナル——ラベルが存在する理由そのもの——は実アプリとの接触を生き延びない。

## 決定

ディスパッチサイトのDynamicレシーバーが、**それが保持する値の最も特定的な原因**へ解決するように由来を配線し、`Dynamic`を製造するあらゆる層で原因を記録する。由来はサイドチャネルのままだ: サブタイピング・一貫性・正規化・消去に決して関与せず、診断を発火させず、重大度に決して供給しない（ADR-75 WD3、不変）。ここでのあらゆる変更の基準は**帰属の誠実さ**だ——原因は、それが値がなぜ動的なのかの健全な記述である場合にのみ記録/伝播され、疑わしいときは、値は推測された特定の原因ではなく汎用的な原因を保つ（誤った「プラグインを有効化」ヒントはユーザーの時間を浪費する——ADR-75が避けるために存在する失敗モードだ）。

由来は加算的なメタデータなので、正しさは診断コーパスでは測れない（構成上バイト同一だ）。ゲートは代わりに、Mastodon/Redmineでの**再バケット化の計測**だ: 各スライスは意味のある割合をキャッチオールの外へ動かさ*ねばならず*、*かつ*動いた各バケットは、正しく帰属されていると手で裁定されねばならない（レシーバーをスポットチェックする）。帰属の正確さを改善せずに再ラベルするだけのスライスは着地しない。

### ワーキングデシジョン

- **WD1——バインディングの起点を素のレシーバー読み取りへ伝播する。（2026-07-06実装。）**レシーバーの原因を、自身のノードだけを読むのではなく推移的に解決する: ローカル変数読み取りのレシーバーは、そこに最後に束縛された値の起点まで辿り、インスタンス変数読み取りのレシーバーは、そのフィールドの代入起点まで辿る;呼び出しノードのレシーバーは今日の直接ルックアップを保つ。メカニズム: フローでスレッド化された`Scope#local_origins` / `#ivar_origins`の名前→原因サイドテーブルで、代入時に設定され（`Scope#with_local_origin`、rhsが記録された起点を持つ`Dynamic`のとき`StatementEvaluator#eval_local_write` / `#eval_ivar_write`から呼ばれる）、レシーバー自身のノードが原因を持たないとき`ProtectionScanner`（`#propagated_origin`）が参照する。テーブルはADR-53のリトマス試験を逆に従う——それらはフローで*変わる*（リバインドが名前を落とし、`with_local`がコピーオンライトでそれをクリアする）ので`Scope`に置かれるが、`==` / `hash`からは除外され（助言的で、フロー判断を決して変えない）、メソッド本体ごとにリセットされる（新しいエントリースコープがそれらを落とすので、名前キーが本体をまたいで衝突することは決してない）。よくあるケースではゼロアロケーション（空のテーブルは凍結された`EMPTY_ORIGINS`を共有し、`drop_origin`はリバインドされた名前が実際に起点を持つときのみアロケートする）なので、ADR-44のディスパッチごとの予算は保たれる——パフォーマンス中立と計測された（上記のWD1の結果を参照）。見返りは控えめだ（素の読み取りのレシーバーは小さなnullバケットだ）;より大きなレバーはWD6だ。

- **WD6——チェーン起点継承。（2026-07-06実装。）** WD1の計測は、支配的なキャッチオールのレシーバーが、素の変数読み取りではなく中間の呼び出し/チェーン式であることを示した: `a.b.c`と`x.foo[…]`は由来を失う。というのも、`Dynamic`レシーバーにディスパッチされた`.b` / `.foo`が`dynamic_top`を返し、その呼び出しノードに*何も*記録しなかったからだ（`call_type_for`の既存の「結果は動的起点を継承する」というコメントは志向的だった——決して配線されていなかった）。WD6はそれを配線する: `Dynamic`レシーバーへのディスパッチが、レシーバーの実効起点（`Inference::OriginLookup.origin_for`——`ProtectionScanner`が使うのと同じ`dynamic_origins` + WD1バインディングルックアップ、今や共有）を、それが生み出す呼び出しへ記録し、特定の原因がチェーンを生き延びる。サイドチャネルのみ（結果の型は手つかず）;パフォーマンス中立と計測（masterに対し`lib`アロケーション+0.03%）。**結果:** *原因なし*（null）バケットを大幅に削減する——Mastodon app+libのnull 2,550→**1,356**（−1,194、WD1の動きのおよそ4倍;WD1と合わせるとベースラインの2,921 nullは半分以上削られる）。だが伝播された原因のほとんどは`unsupported_syntax`だ。というのも、チェーンの*根*がそれを記録するからだ: 暗黙のselfのメモ化リーダー、`params[:x]`インデックス、メタプログラミングされたアクセサ。したがってWD6が買うのは、**アクション可能性**（`unsupported_syntax`とnullはどちらも`engine_gap`へ誘導される）よりも**由来の完全性**（「見当もつかない」ホールがはるかに少ない）だ。それが次に露呈するアクション可能性のレバーは、**根を拡充すること**だ——暗黙のselfの解決パスに、WD2の明示的レシーバー層のように`inferred_return_untyped`を記録させ、フレームワークのインデックス読み取り（`params[:x]`、`session[:x]`）にフレームワーク原因を与える——それをWD6がチェーンを通してタダで伝播する。WD7がその根の拡充の、最初で最も価値の高いスライスを着地させる。

- **WD7——型なしパラメータのための根の原因拡充、加えて正確なサイトごとの原因メトリクス。（2026-07-06実装。）** 2つの結合した変更で、WD1/WD6の計測が*ロッシー*な集約から読まれていたと発見したことがきっかけだ。

  - **正確なメトリクス（と1つの訂正）**。`coverage --protection`はホールをメソッドごとにグループ化し、各グループの*支配的*な原因を報告し、`tractability_summary`はその支配的な原因をグループの総数で重み付けしていた。これは混在グループの少数派の原因を大幅に過小カウントする——原因なし（null）サイトを含めてだ。それらは、何らかの起点付きサイトを持つグループから完全に消える。新しいサイトごとの`cause_site_counts`（正確な集計、`"none"`を含む;`tractability_summary`は今やそれから導出される）が真の状態を明かし、それが**このADRのWD1/WD6の数字を訂正する**: それらのスライスの「null 2,921→1,356」は支配的原因のアーティファクトだった——WD1+WD2+WD3+WD6後のMastodon app+libの*正確な*原因なしカウントは**21,119件中10,390件（49%）**であり、10,126件が`unsupported_syntax`、アクション可能なバケットにはわずか約600件だ。WD1/WD6は依然として本物の仕事をした（ラベル付けされて*いた*チェーンとバインディングは今やラベル付けされたままだ）が、その規模はロッシーなメトリクスによって誇張されていた;それらの後の由来の完全性は、旧メトリクスが示唆した約94%ではなく約51%だ。

  - **拡充**。その49%の原因なしバケットの最大のアクション可能なスライスは、宣言されていないメソッドパラメータだ: `def f(x); x.foo`は`x`を`untyped`に束縛し、素のパラメータレシーバーは原因を持たなかった。`build_method_entry_scope`は今や、型なしパラメータの`local_origins`を`inferred_return_untyped`にシードする（型なしパラメータは典型的な[ADR-67](../67-parameter-type-inference/)のギャップだ——呼び出しサイトの型が流れ込まない）ので、WD1のルックアップが`x.foo`をラベル付けし、WD6がそれを`x.foo.bar`を通して運ぶ。シード時のみ（ホットな読み取りパスではない）、精度加算的、パフォーマンス中立（`lib`アロケーション+0.15%）。**結果:** Mastodonの原因なし10,390→**7,305**（−3,085）、`inferred_return_untyped` 351→**3,460**（+3,109）、比率は不変——WD6の完全性の上に乗る本物の*アクション可能性*の獲得（3,100件のホールが今やADR-67へ誘導される）。残る7,305件の原因なしは、束縛されていないインスタンス変数読み取り（[ADR-58](../58-ivar-field-typing/)のivarフィールドギャップ）と、`dynamic_top`を返すノード種（yield / super / block）が支配的だ;ivarスライスがWD8だ。

- **WD8——束縛されていないインスタンス変数読み取りのための根の原因拡充。（2026-07-06実装。）** 2つ目の根の拡充スライスで、WD7のパラメータの後に残る最大のものだ。エンジンがそのフィールドを追跡していない`@x`読み取り（`scope.ivar(name)`がnil——ivarが別のメソッドで代入されている、または一度も見られていない）は原因なしで`dynamic_top`を返したので、その上の`@x.foo`は原因なしだった。`ExpressionTyper#type_of_instance_variable_read`は今や、束縛されていない読み取りに`inferred_return_untyped`を記録し（型なしフィールドは典型的な[ADR-58](../58-ivar-field-typing/)のギャップだ）、WD6がそれを`@x.foo.bar`を通して運ぶ。WD7のパラメータと違い、これはメソッド入口ではシードできない（「束縛されていない」ことが分かるのは読み取りサイトだ）ので、読み取り時に記録する——だがすでに`dynamic_top`である分岐でのみ、精度加算的、そしてパフォーマンス中立と計測（`lib`アロケーション+0.03%、WD6と同じ形）。**結果:** Mastodonの原因なし7,305→**5,405**（−1,900）、`inferred_return_untyped` 3,460→**5,399**（+1,939）、比率は不変。WD7+WD8を通じた累積で、原因なしバケットは真の10,390（49%）から5,405（26%）へ落ち、アクション可能な`inferred_return_untyped`バケットは351→5,399（15倍）に増えた。残余の原因なしは今や`dynamic_top`を返すノード種（yield / super / block / 埋め込み変数）とクラス/グローバル変数読み取りだ——ほとんどは本当に未モデル化なので、この弧のアクション可能性のレバーはほぼ使い尽くした;残る`unsupported_syntax`（10,063件、なお48%）は未解決の呼び出しに根ざしたチェーンで、正直なエンジンギャップのフロアだ。

- **WD2——ラベルのない2つのユーザーメソッド層で原因を記録する。（2026-07-06実装。）** `try_discovered_method`と`try_user_class_fallback`は今や、`Dynamic`を返すとき、その呼び出しノードに`INFERRED_RETURN_UNTYPED`を記録する（`method_dispatcher.rb`）。これらは「エンジンが呼び出しを既知のユーザー/祖先メソッドへ解決したが、その戻り値を推論できない」——未モデル化の構文フォールバックとは異なる。層ごとに1行の`record_dynamic_origin`、サイドチャネルのみで、WD1が着地する前でもチェーンレシーバーのホールに正直な原因を与える。

- **WD3——`engine_gap` tractabilityを持つ新しい原因`inferred_return_untyped`で、パラメータ/ivar推論へルーティングする。（2026-07-06実装。）** WD2の層は`unsupported_syntax`（呼び出しは解決した）でも`explicit_untyped`（`untyped`と書いた著作RBSはない）でもない;それらは*推論*ギャップであり、その本当のレバーは[ADR-67](../67-parameter-type-inference/)（呼び出しサイトのパラメータ推論が本体の戻り値を鋭くする） / [ADR-58](../58-ivar-field-typing/)だ。この別個の原因により、`coverage --protection`は「unsupported syntax」ではなく「エンジンがまだこの戻り値を推論できない」と言える——より正直で、正しいロードマップ項目を指す。`DynamicOrigin::CAUSES` / `TRACTABILITY`に追加した;CLIはtractabilityを中央で読むので、レンダラーの変更は不要だった。ADR-75の原因集合を拡張する（まだ凍結されていない;ADR-50のv1.0語彙フリーズは将来だ）——その拡張が要点だ。（それを`ExpressionTyper`のユーザーメソッド推論フォールスルーにも適用するのはフォローアップだ;計測された211サイトが来たのは2つのディスパッチャー層だ。）

- **WD9——RBSのないロック済みgemが所有する未解決の定数をラベリングする。（2026-07-11実装。）** G2の`external_gem_without_rbs = 0`の半分を閉じる（WD4は`framework_dsl_boundary`の半分をプラグインごとのフォローアップへ見送る）。コンテキストの枠付け——「ディスパッチのレシーバークラスがRBSのないgemに所有されているとき」に原因を記録する——は機械的に不可能だ: RBSのないgemのレシーバーはクラス名を決して運ばない。定数の読み取りそのもの（`Faraday`）が解決に失敗し、汎用的な`unsupported_syntax`原因で`Dynamic[top]`へ拡幅されるからだ;ディスパッチ時点で名前は消えている（この原因を記録する2つのディスパッチャー層はADR-10 / `pre_eval:`のオプトインを要する——まさにバケットがゼロを計測した理由だ）。正直な記録サイトは**定数解決のミス**（`ExpressionTyper#unresolved_constant_fallback`）であり、WD6のチェーン継承がその原因を`Faraday.new.get(...)`を通してタダで運ぶ。所有権は*推測ではなく読み取り*で確立される: `:missing`に分類された各ロック済みgemの慣習的なエントリーファイル（`lib/<name>.rb`、ダッシュ→ディレクトリの変種）をPrismでパースし、そのトップレベル宣言をルート定数名の下にインデックス化する（`Environment::MissingGemConstantIndex`、最初の未解決定数で遅延構築;gemコードは走らない——ADR-72の姿勢）。gem名をキャメライズするヒューリスティックは意図的に却下される（`activesupport` → `ActiveSupport`で壊れる;誠実さの基準が禁じる推測だ）。すべてが**フェイルオープン**する——未インストールのgem、欠落／パースできないエントリーファイル、より深いファイルの宣言、プロジェクトのタイポはすべて汎用的な原因を保つ;失敗モードはラベルの欠落であって、決して誤ったラベルではない。**gemディレクトリの解決が要となる**: rigorは自身のバンドルの下で走る（`BUNDLE_GEMFILE=<rigor>/Gemfile`）ので、`Gem::Specification`はターゲットのではなくrigorのgemを見る——主リゾルバはターゲットのバンドルインストールツリー（`<bundle>/ruby/*/gems/<name>-<version>/`、`BundleSigDiscovery`のレイアウト）であり、`Gem::Specification`はバンドルのないプロジェクト向けのフォールバックにすぎない（gemのトップレベル名前空間定数はバージョン安定なので健全）。カバレッジはターゲットのインストールレイアウトを追う: `vendor/bundle`プロジェクト（自動検出）は完全な外部gemの母集団を得る;デフォルトgemホームのプロジェクト（rbenv/mise、`--path`なし）は`bundler.bundle_path:`を要する——これは既存のADR-27のオプトインであって新しいエンジン作業ではない: ターゲットのgemホームを自動検出することは、そのツールチェーンを走らせる（ADR-27が禁じる）か、あらゆるバージョンマネージャーのレイアウトを推測することになるからだ。確認済み（[2026-07-11のインストール境界ノート](../../notes/20260711-external-gem-install-boundary/)）: Redmineの完全なバンドルを`vendor/bundle`へインストールし、変更のないエンジンコードで再実行すると**279**件の外部gemサイト（`Rails`→railties、loofah、i18n）が得られ、すべて正しいと裁定された——サーベイアプリのフロアは、gemが一度もインストールされていなかったことであって、エンジンのギャップではなかった。計測（分母同一）: Mastodon `app/models` 47件とGitLab `lib` 124件のサイトが`unsupported_syntax` → `external_gem_without_rbs`（共有gemのフロア——`i18n`/`rack`/`activesupport`;サンプリングされたサイトは`I18n`に根ざし、そのRBSは`gem_rbs_collection`に存在するので`add_rbs`は本当にアクション可能）、他のバケットはバイト安定、診断はバイト同一（Redmine）、`make bench-perf`はグリーン。

- **WD4——具体型付けがスコープ外でも、フレームワークの*リーダー*オブジェクトに`framework_dsl_boundary`を記録する;ギャップは別の場所にある**。プラグインが具体的な型を返すというG2の観察は*正しい振る舞い*だ——それらのサイトは保護済みだ。残るフレームワークDSLのホールは、DSL境界を越えて動的なままである値だ（`method_missing`アクセサ、マクロ生成の属性）。そこに`framework_dsl_boundary`を記録するのはプラグイン側の関心事であり（プラグインは自分が動的境界を発したと知っている）、ここで汎用的に配線するのではなくプラグインごとのフォローアップへ見送る——未解決のレシーバーに対して「フレームワーク境界」と推測することは、誠実さの基準に反するだろう。

- **WD5——計測ゲート。（2026-07-06解決。）** WD2+WD3が最初に着地し（安価、スコープ変更なし）、Mastodon app+libで計測された: それらは**211サイト（約1%）**を`inferred_return_untyped`へ再バケット化し、すべて正しく帰属されたチェーンレシーバーのホールで、84%のキャッチオールを実質的に手つかずのまま残す。残余は§2のサンプルが予測したとおりローカル/ivar読み取りのレシーバーが支配的なので、ゲートはWD1を可決した。**次にWD1が着地し、それ自身が計測された**（ゲートはあらゆるスライスに適用される）: パフォーマンス中立だが、約322サイト（nullバケット）しか動かさない。というのも、§2のサンプルが素の変数レシーバーを過大に重み付けしていたからだ——残余を裁定すると、支配的なキャッチオールは中間の呼び出し/チェーン式だと分かり、次のレバーをWD6へ方向転換した。各スライスが*次の*スライスを計測することが意図されたループだ;WD1の計測こそが「主要レバー」を「WD6の基盤」に変えたものだ。

## 却下された選択肢

- **`Type::Dynamic`キャリアに由来を付け、値とともに自動的に運ばせる**。ADR-75 WD1により却下され、ここでも不変: `Dynamic`は`value_fields :static_facet`の値の等価性を使うので、2つの`Dynamic[String]`はユニオンとキャッシュで重複除去される;起点フィールドは束を起点で分岐させてしまう。WD1のサイド関連付けが是認された伝播パスだ。
- **由来をレポート時にレシーバー式のシェイプから再導出する**。却下——層が誤り（ADR-75 WD3）: エンジンは導入時にすでに原因を知っている;レポート時にASTからそれを再構築することはディスパッチを再実装し、ドリフトする。
- **`unsupported_syntax`とnullを1つの「unknown」バケットに集約し、装うのをやめる**。却下——それはtractabilityシグナルを修正する代わりに放棄する;レシーバーには*知りうる*原因がある（WD1/WD2/WD3）、エンジンがそれを記録/伝播していないだけだ。
- **由来に診断を発火させる（「このレシーバーは型なしだ」）**。却下——偽陽性の規律とADR-75の重大度なし契約に反する;由来はカバレッジサーフェスで注意を誘導するのであって、ゲートしない。

## 帰結

- `coverage --protection`の由来は正確に計測され（WD7のサイトごとの`cause_site_counts`）、実際のRailsアプリで実質的により完全で*かつ*アクション可能だ: WD2+WD3が`inferred_return_untyped`をキャッチオールから切り出し、WD1 + WD6が素の変数レシーバーとチェーンレシーバーに原因を伝播し、WD7/WD8が型なしパラメータ（ADR-67）と束縛されていないivarフィールド（ADR-58）を推論へ誘導する。Mastodon app+libで、原因なしバケットは真の10,390（49%）から5,405（26%）へ落ち、アクション可能な`inferred_return_untyped`バケットは351→5,399（15倍）に増え、比率は全体を通じて不変だ。残余の原因なしは`dynamic_top`を返すノード種（yield / super / block）とクラス/グローバル変数読み取りだ——ほとんどは本当に未モデル化なので、アクション可能性のレバーはほぼ使い尽くした;残る`unsupported_syntax`（48%）は未解決の呼び出しに根ざしたチェーンで、正直なエンジンギャップのフロアだ。
- 由来は**サイトごと**に計測され、決してメソッドグループごとの支配ではない。`add_a_type_here`リストは、ランク付けされた「ここに型を追加」ビューのために依然としてグループごとの支配的原因を示すが、`cause_site_counts`と`tractability_summary`は正確なサイト集計だ——以前のグループ支配的な`tractability_summary`は混在グループの本物の過小カウントだった（WD7）。
- 型・診断・重大度・診断コーパスへの変更なし（加算的なサイドチャネル）。ゲートはゼロデルタのコーパス実行ではなく、再バケット化の計測 + 帰属の裁定だ。
- WD3はADR-75の原因集合を1シンボル拡張する;`DynamicOrigin::CAUSES`と`TRACTABILITY`がそれに応じて増える。新しい原因ID、そしてWD7の`cause_site_counts` JSONフィールドは、公開の`--format json`語彙であり、[ADR-50](../50-release-engineering-and-stability-strategy/) WD1のもとv1.0で凍結される。
- WD1はフロー変動する2つの`Scope`サイドテーブルを、WD6はDynamicレシーバーのディスパッチごとに1つの`record_dynamic_origin`を、WD7はメソッド入口の型なしパラメータごとに1つの`with_local_origin`を、WD8は束縛されていないivar読み取りごとに1つの`record_dynamic_origin`を加える;すべてパフォーマンス中立と計測された（WD1 +0.1%、WD6 +0.03%、WD7 +0.15%、WD8 +0.03%の`lib`アロケーション、masterに対し）。コミット済みの`bench/baseline.json`は陳腐化していることに注意（19.77Mアロケーション / 16.6秒ウォール 対 今日の約27.5M / 約7〜9秒——masterもゲートに失敗する）ので、`make bench-perf`が再び意味を持つには再ベースライン化されたコミットが必要だ;その再較正はここではスコープ外だが、フォローアップとして指摘しておく。
