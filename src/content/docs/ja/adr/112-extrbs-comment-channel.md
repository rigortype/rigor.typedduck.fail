ステータス：**Accepted、2026-09-19。まだ何も実装されていません**。[#996](https://github.com/rigortype/rigor/issues/996)について、[ADR-111](../111-inline-refinement-carrier/)の推奨とは逆の裁定を下します。ADR-111は全体として置き換えられ、そのプローブが本ADRの根拠（grounding）となります。本ADRは[ADR-32](../32-rbs-inline-comment-ingestion/) WD13を部分的に置き換え、「メンバーごとに`sig/`が勝つ」をWD5の整合性ルールで置き換えます。[ADR-0](../0-concept/)の`RBS::Extended`の箇条書きを修正します。実装は#1073〜#1076で追跡されます。

根拠（Grounding）：
[`docs/notes/20260912-inline-refinement-carrier-probe.md`](../../notes/20260912-inline-refinement-carrier-probe/)。
`rbs-inline` gem、rbsの`RBS::InlineParser`、およびインラインモードのSteep 2.0.0を通じて14の記法を検証しました。行Xは`@extrbs`を測定しました：3つのリーダーすべてがそれを無視し、その横の`@rbs` / `#:`行は引き続き束縛されました。行Bは`@rbs-ext`を測定しました：rbs-inlineはそれを`@rbs`アノテーションとして読み取り、Steepはそれをエラーとして報告しました。

## コンテキスト

Rigorの前提は変わりません：Rubyコード中に型を散乱させることを誰にも要求しません（[ADR-0](../0-concept/)）。それでも一部の契約は実装の横に書くのが最適です。実装こそがそれらの理由であるためです。`:asc | :desc`のみを受け入れるパラメータや、決して空にならない戻り値などがその例です。この2種類の契約は異なります：

- **RBSで表現できるもの**（`:asc | :desc`）には、すでに置き場所があります：`@rbs` / `#:`です。Steepはそれらをインラインで読み取り、Sorbetも`#:`を読み取ります。
- **RBSで表現できないもの**（`non-empty-string`、`Integer[1..10]`）には、インラインの`%a{rigor:v1:…}`レーンしかありませんでした。そのレーンは、型の2回目の並行した言明というコストがかかります。また行単独の形式は、Steepのインラインモードのもとでエラーとなります（ADR-111の発見事項5）。

Rigorと並行して設計され、歩調を合わせてリリースされるドキュメント記法であるZARDは、これを具体化します。ZARDはAPIドキュメント（`@param` / `@return`の散文、デフォルトでは型なし）を型付けされた契約から分離して保ちます。なぜならプロジェクトが構造化コメントを書くと、YARDはすべてのスロットに型を要求し、それらの型を検証するものは何もないからです。`@rbs` / `#:`はどちらも型を前提としているため、その散文を担うことができません。ZARDはRigorのボキャブラリーを担うことができる型付けされたチャンネルを必要としています。

ADR-111はRigor所有のタグを検討し、3つのコストからそれを却下しました。各コストは否定されるのではなく、ここで回答されます：

1. **rbs-inlineのライターはテキストを保持するが意味を捨てる**。Rigorがライターです。`rigor sig-gen`が生成されたシグネチャに`%a{}`を出力するため（WD4）、いかなるリーダーもrbs-inlineライターに依存しません。
2. **v1.0で凍結すべき第2の文法**。新しい文法はありません。タグの形状は`@rbs`自身のものです。型文法は`%a{rigor:v1:…}`がすでに担っているものであり、両方のキャリアがそれを共有できるように一度だけ拡張されます（WD2、WD3）。
3. **ADR-0の「新しいRubyコメントDSLはない」**。その箇条書きの背後にある原則は型を散乱させないことであり、それは維持されます。この修正により、`@extrbs`はRBSが表現できない契約のためのオプトインチャンネルとなり、すべての型を書く第2の方法ではありません。

## 決定事項

> **パブリックな契約は他のツールが読み取るものです：`.rbs`、`@rbs`、`#:`。RBSで表現できる型はそこに書かれます。`@extrbs`はRBSで表現できないもののみを担い、Rigorは生成されたシグネチャを書き込むことで、それを他のすべてのリーダーへと運びます。作成者が同じ型を2度述べることを求められることは決してなく、Rigor専用のファクトがサイレントに消えることも決してありません**。

Rigorが`.rb`ファイルに書き込むことは決してありません。以下のすべてのキャリアは作成者の意図です；sig-genオラクル（[ADR-108](../108-type-provenance-for-agents/)）は`.rbs`のみを書き込みます。

## 実務決定事項（Working decisions）

### WD1 ── チャンネルとそのガイダンス

- `# @extrbs …`はどこに出現しても読み取られます。`# rbs_inline:`マジックコメントは必要ありません：そのコメントは`@rbs`形状の散文が誤読されるのを防ぐためのものであり、`@extrbs`はRigorだけが使用する名前です。`references/`（rbs、steep、sorbet、yardが多用されるツリー）を検索しても、その使用は見つかりません。
- **ゲートではなくガイダンス：** RBSで表現できる型は`@rbs` / `#:`に置かれます。たまたま素のRBSを保持している`@extrbs`（`@extrbs order: :asc | :desc`）は有効であり、診断を誘発しません。それを放出する記法ツールは間違っていないためです。
- `@rbs-ext`は綴りではありません。rbs-inlineは`@rbs\b`にマッチし、`\b`はハイフンの前でマッチします（プローブ行B）。

### WD2 ── タグ形式、パース、および配置

- `@extrbs`行は`@rbs`が持つ形式を持ちます：`name: T`、`return: T`、メソッド型`(T) -> U`、および`%a{…}`アノテーション。違いは、型位置で`rigor:v1:`型文法（WD3）を使用できることです。`#:`のような短いシギルは追加されません。
- **パース**。rbs-inlineの`AnnotationParser`がタグの境界を見つけて項目を分割します；ADR-32 WD3（上流リーダー）は引き続き有効です。Rigorのペイロードパーサは型位置のみを読み取ります。これはRigor自身がインライン文法をパースする唯一の場所であり、Rigorが所有する型言語にスコープされています。ADR-32はこの例外を記録します。
- **配置は規範的です**。`@extrbs`ブロックはアノテーションブロックの**先頭**に来て、1つのスペースを伴う`# @extrbs`と綴られます。rbs-inlineは、行がタグよりも深くインデントされている場合に段落を継続するため（`annotation_parser.rb`）、`# @rbs return: T`の後の`#  @extrbs`行は吸収され、サイレントにドロップされます。rbsの内蔵リーダーも同じ形状を拒否します。そのように吸収された行は、飲み込まれるのではなく報告されます（ADR-32 WD12）。
- **スタンドアロンの`@extrbs`は許可されます**。どの`@rbs` / `#:`もメンバーを記述していない場合、Rigorは消去を導出し、他のツールは生成されたシグネチャを通じてメンバーを見ます。存在する場合、`@extrbs`型はそれと整合していなければなりません（WD5）。

### WD3 ── `@extrbs`と`%a{rigor:v1:…}`のための単一の型文法

- `rigor:v1:`ペイロード文法は、**RBS型文法**とリファインメントボキャブラリーの**スーパーセット**となります。`Array[non-empty-string]`、`non-empty-string?`、ユニオン、およびレコードが両方のキャリアで記述可能になります。この変更は加法的なものです：現在有効なすべてのペイロードは同じ意味で有効なままとなります。v1.0凍結（[ADR-50](../50-release-engineering-and-stability-strategy/) WD1）の前に着地するため、`rigor:v1`の下に留まります。
- **名前解決は固定されています：**最初にリファインメント名、次にプラグインリゾルバ、そしてRBS名です。これは`Builtins::ImportedRefinements::Resolver`がすでに使用している順序であり、今回契約として表明されたため、リファインメントのように名付けられたプロジェクトエイリアスがペイロードの意味を変更することはできません。
- **すべての型が`.rbs`に書き込み可能です**。rbsは`%a{`、`%a(`、`%a[`、`%a|`、および`%a<`を字句解析し、それぞれネストやエスケープなしで、最初に一致するクローザーまで読み取ります（`references/rbs/src/lexer.re:55-59`）。ライターはペイロードに含まれないデリミタを選択します。ペイロードに5つすべてのクローザーが含まれている場合、ペイロード文法の`\u{…}`エスケープにより、生の文字が出現することなくクローザーを表現できます。生成されたファイルのみがこれを持ち、人間がそれらを手動で編集することはありません。ファクトを`.rbs`のコメントとして書き込むことはフォールバックではありません（却下された代替案6）。

### WD4 ── 生成されたシグネチャは`sig/`であり、入力でもある

- `rigor sig-gen --write`は`sig/<path>.rbs`への書き込みを継続します（[ADR-14](../14-rbs-sig-generation/)）。生成されたシグネチャは任意の`sig/`ファイルと同様に入力であり、gemが出荷し下流のRigorが読み取る契約です（`bundle_sig_discovery.rb`）。新しい`sig-gen --check`は`--diff`が空のときに成功します。これがCIの鮮度ゲートです。
- `@extrbs`で宣言されたメンバーについて、ライターは型位置に消去を出力し、その横に`%a{rigor:v1:…}`を出力します。Rigorが単に**推論した**リファインメントは消去され、決して出力されません：一度書き込まれるとアノテーションは強制されるため、契約は誰かが意図して述べたものだけです。エフェクトアノテーションは既存のオプトインフラグを維持します。
- **デフォルトですべてのメンバーが書き込まれます**。これにはインラインの`@rbs`によっても宣言されているメンバーが含まれ、`sig/`が完全で出荷可能な契約となります。Steepを`inline: true`かつ`signature "sig"`で実行しているプロジェクトは、そのようなメンバーごとに2回見ることになります（`DuplicatedMethodDefinition`）。設定により、それらのプロジェクトに対してインライン宣言されたメンバーをスキップします。その設定のもとでは、そのようなメンバー上の`@extrbs`リファインメントはソースが解析されたときにのみ有効になり、マニュアルにもそのように記載されます。
- Rigor専用のアノテーションをドロップするという`rbs-extended.md`のルールは、消去が書き込まれるプレーンRBSのエクスポートに適用され、sig-genの出力には適用されません。

### WD5 ── ソース間の一貫性が「`sig/`が勝つ」を置き換える（ADR-32 WD13）

1つのルールがインラインに対する`sig/`、および`@extrbs`に対する`@rbs` / `#:`をカバーします：

- **整合（Consistent）：**各オーバーロードについて、一方が他方の部分型である（どちらの方向でもよい）。`untyped`はあらゆるものと整合しており、移行中のプロジェクトの`sig/ -> untyped`をインラインの`-> void`の横で静かに保ちます（ADR-93のherbのケース）。
- **整合した重複は、より正確な側へとマージされる**。WD13のもとでは`sig/`が勝ち、インラインで書かれたリファインメントは何の警告もなく消えていました。今後は`sig/`の`String`と`@extrbs`の`non-empty-string`は`non-empty-string`として読み取られます。
- **矛盾（Contradiction）**（どちらの側も他方の部分型ではない）は**エラー**です。陳腐化した生成シグネチャがここに現れます。これこそが本ADRが求める厳格な警告です：再生成するか、ソースを修正してください。
- 偽陽性への規律は重要度（severity）ではなく定義を保持します。出荷前に、このルールはherb、mastodon、redmine、およびRigor自身に対して実行されます。偽陽性はルールを修正するものであり、重要度を下げるものではありません。
- 変更なし：1つのメンバーを宣言する2つの`.rbs`ファイルは依然としてクラスの定義構築を失敗させ、同梱のRBSに対するプロジェクトの`.rbs`はファイルレベルの隔離のままとなります。

## 却下された代替案

| 候補 | 理由 |
| --- | --- |
| 1. 推奨どおりのADR-111：Rigor読み取りタグなし、同一行の`%a{}`のみ | #996の人間工学的なコストが残る。契約を2回述べる必要があり（プレーンな型、次にアノテーション内のペイロード）、記法ツールは型付けされたチャンネルを必要とする。ADR-111の最大のコストであったライター境界は、Rigorがライターとなることで解消される（WD4）。 |
| 2. `# @rbs-ext …` | `@rbs`文法の内部として測定された（プローブ行B）。 |
| 3. プレーンな型を含め、`@extrbs`を唯一の型付けされたチャンネルとする | 他のツールが読み取れる契約を隠してしまう。プレーンなRBSはSteepやSorbetが見える場所に属する（WD1）。 |
| 4. Rigorが読み戻さない独立した生成ディレクトリ（`sig/generated/`） | 戻り値が生成されパラメータが1行で書かれているような、混在した来歴（provenance）を持つメンバーを壊してしまう（[ADR-107](../107-checked-types-and-typeless-comments/)）。RBSは1つのメンバーを2つのファイルに分割できない。また、出荷される成果物がgem自身の`check`によって検査されないままになり、rbs-inlineのデフォルト出力ディレクトリを奪ってしまう。 |
| 5. `@extrbs`を現在のペイロード文法に制限する | `Array[non-empty-string]`や`non-empty-string?`が記述できなくなるか、書き込み時にドロップされてしまう。 |
| 6. 表現できないペイロードを`.rbs`のコメントとして運ぶ | 他のツールはコメントをドキュメントとして表示し、RBSリライターはそれらを移動またはドロップする。これはADR-0と`rbs-extended.md`が排除している`.rbs`内のコメントキャリアを再導入することになる。WD3のエスケープにより、これがカバーすべき例外は残されていない。 |
| 7. すべての`@extrbs`の横に`@rbs`行を要求する（ADR-111 WD2） | 作成者は各型を2回述べることになる。消去は機械的であるため、Rigorが導出する。 |
| 8. 最初にWD5を警告として出荷する | 重要度こそが正しいプログラムを保護するものではない。矛盾の狭い定義とコーパス全体のスイープが保護するものである。 |

## 影響（Consequences）

好ましい影響：

- 両方のキャリアで単一の型文法となり、新しいキーワードセットはなく、v1.0で単一の凍結サーフェスとなる。
- リファインメントはあらゆる境界を生き延びる。作成者はそれを一度書き、Rigorはその横に`.rbs`を書き、下流のRigorはそれを読み戻す。
- WD13によるインラインリファインメントのサイレントなドロップは終了する。陳腐化した生成シグネチャは報告される矛盾となる。

好ましくない影響および持ち越し事項：

- Rigorはv1.0でタグ名（`@extrbs`）を所有する。タグセットはrbs-inlineのままとなる。
- インライン宣言されたメンバーをスキップするSteep-inlineプロジェクト（WD4）では、`@extrbs`専用のファクトはRigor内でのみ可視となる。
- 矛盾は従来`:info`で報告されていたが、今後はエラーとなる。整合性チェックの実装は新しい作業である：現在のところ`lib/`内にはリファインメントとそのプレーンな契約を比較するものは何もない。
- ADR-32 WD13は部分的な置き換えマーカーを持つ。ADR-0の箇条書きは修正される。

実装イシュー：[#1073](https://github.com/rigortype/rigor/issues/1073)（`@extrbs`の読み取り、WD1〜WD2）、[#1074](https://github.com/rigortype/rigor/issues/1074)（ペイロード文法とエスケープ、WD3）、[#1076](https://github.com/rigortype/rigor/issues/1076)（sig-genの出力、`--check`、およびスキップ設定、WD4）、および[#1075](https://github.com/rigortype/rigor/issues/1075)（整合性ルール、WD5）。それぞれが着地した際に拘束力のある仕様を更新します。
