ステータス: **Accepted、2026-10-22**。メンテナーは#575でv0.4.6向けにこの設計（オプションA）を選択した。2つのマニフェストフィールド、`Registry`の集約、絞り込まれた`def.ivar-write-mismatch`、およびrigor-actionpackの宣言が#575でまとめて導入される。rigor-actionmailerの宣言は#2308で続いた。

アーキタイプ: 熟議的。リスク: 中。この変更はプラグインコントラクトへの追加的変更であり、検出結果を差し控えることしかしないが、プラグインがエンジンルールに伝えられる内容を広げる。

## コンテキスト

`def.ivar-write-mismatch`は、各書き込みがどのメソッドにあろうと、クラス内のインスタンス変数のすべての書き込みを最初の具象型と比較する。その前提は「クラスのすべてのインスタンスメソッドが1つのインスタンス上で実行され得る」というものである。Railsコントローラーはこの前提を破る。各リクエストは新しいコントローラーをインスタンス化し、1つのアクションだけを実行するため、`index`の`@roles = Role.sorted.to_a`と`permissions`の`@roles = Role.sorted`が同時に生存することはない。この乖離は実行時の影響を持たず、警告は正しいコードに対する偽陽性である。

#569の着地ゲートでは、redmine（`roles_controller.rb`、`workflows_controller.rb`）でこのような発火が4件表面化した。2026-09-26の#575トリアージでは、redmine、gitlab、mastodon全体で9件の発火が計測され、そのうち4件は2つの異なるパブリックアクションにおける乖離した書き込みだった。これらの発火はRelation型が具象になったことで現れたものであり、それ以前は両方の分岐が`Dynamic`だったためルールがスキップしていた。Railsアプリに導入されるすべての精度向上レバーが、この種の発火をさらに増やすことになる。

エンジンは単独ではこれを認識できない。インスタンスが1つのエントリーポイントにのみ奉仕するかどうか、そしてどのメソッドがエントリーポイントであるかはフレームワークの事実であり、フレームワークをモデル化するプラグインこそがRigorにおいてフレームワークの事実を保持する場所である（[ADR-2](../2-extension-api/)）。

## 決定

プラグインは**呼び出し単位クラス（per-invocation classes）**を宣言できる。これは、すべてのインスタンスがただ1つのエントリーポイント、すなわち*アクション*に奉仕するクラスである。そのようなクラス（またはその子孫）の2つの異なるアクションにおけるインスタンス変数への書き込みが同時に生存することはない。

アクションとは、#575におけるメンテナーのA1決定が定義するものである。すなわち、コールバックマクロ（`before_action`、`after_action`、`around_action`およびそれらの`prepend_`、`append_`、`skip_`形式）および`helper_method`のいずれによっても名指しされないパブリックインスタンスメソッドである。

- **マニフェストフィールド**。
  - `per_invocation_classes: [String]`はクラス名を列挙する。バリデーションでは空でないStringのArrayが要求され、先頭の`::`は取り除かれる（`Plugin::Manifest`）。
  - `per_invocation_non_action_macros: [Symbol]`は、リテラルなSymbolまたはStringの引数がアクションではないメソッドを名指しするクラス本体マクロを列挙する。これらは同じマニフェストのクラスに適用されるため、クラスのないリストは拒否される。
- **集約**。 `Registry#per_invocation_classes`と`#per_invocation_class?`は`open_receivers` / `open_receiver?`（[ADR-26](../26-activerecord-relation-typing/)）を模倣しており、構築時にコンパイルされる重複排除されたフラットなリストと、完全一致によるメンバーシップ判定を提供する。`Registry#per_invocation_non_action_macros(name)`は、`name`を宣言するマニフェストのマクロを返す。
- **継承の追跡**。 `CheckRules::IvarWriteCollector`はクラスのインスタンス`Scope::ResolutionChain`を読み取るため、プロジェクトのスーパークラスチェーン（`RolesController < ApplicationController < ActionController::Base`）が対象となる。
  - 環境が認識している外部スーパークラスは、名前またはRBSの`:subclass`順序によって一致する。
  - 解決できない外部スーパークラスは記述された名前で一致する。これは、rigor-actionpackが意図的に`ActionController::Base`を未宣言のままにしているためである。このフォールバックは、いずれかの候補表記がプロジェクトの宣言するクラス（`MyApp::ActionController::Base`）を名指しする場合にはスキップされる。
  - 途中で切れたチェーンは一致しない。
- **アクション**。コレクターは各書き込みを囲むメソッド、その可視性、および同じファイルのクラス本体内で宣言済みマクロが綴る名前（SymbolとStringの引数、およびインラインの`def`（`helper_method def current_user`））を記録する。メソッドがパブリックであり、かつそのようなマクロによって名指しされていない場合、その書き込みはアクション内にある。
- **ルールセマンティクス**。乖離した書き込みWは、Wがアクション内にあり、かつ競合するすべての書き込み（非nilで異なる具象クラス）が同じクラスの*異なる*アクション内にある場合に差し控えられる。
- **最初の宣言**。 rigor-actionpackは`ActionController::Base`と`ActionController::API`、および12個のコールバックマクロと`helper_method`を宣言する。

**基準:**エンジンが2つの書き込みの比較を停止するのは、フレームワークの不変条件がそれらを同じオブジェクトの生存期間から分離し、プラグインがその不変条件を保証する場合のみである。以下のそれぞれは任意のアクション内で実行され得るため、これらの中にある競合する書き込みは検出結果を維持する:

- privateまたはprotectedメソッド
- コールバックマクロまたは`helper_method`が名指しするパブリックメソッド
- `initialize`
- W自身のメソッド

ルールはどのヘルパーにアクションが到達するかを証明しようとはしないため、この例外規定が宣言の述べる範囲を超えて広がることはない。

### 作業決定

- **WD1 — プラグインがクラスと非アクションマクロを名指しし、エンジンがメソッドを名指しする**。 Railsはパブリックメソッドにのみディスパッチし、エンジンはすでに可視性（`Scope#discovered_method_visibility`）を記録している。可視性だけでは表現できないのは、あるパブリックメソッドがコールバックやビューヘルパーであるという事実だ。どのマクロがそれらを宣言するかはプラグインが知っているため、プラグインはそれらをデータとして列挙し、エンジンはそのリテラル引数を読み取る。クラスごとのアクションリストは、静的なマニフェストには保持できないプロジェクト固有の知識を必要とするだろう。
- **WD2 — 未確定の可視性はパブリックではない**。探索テーブルに欠けているか競合しているスロット（#2013）、および`initialize` / `respond_to_missing?`その他の暗黙的にprivateなフックは、すべての呼び出しで共有されるものとして扱われる。証明されていない前提は検出結果を維持する。
- **WD3 — 値オブジェクトではなく対になるフィールド**。比較対象となった先例は[ADR-38](../38-additional-initializers/)の`additional_initializers:`であり、これは`{ receiver_constraint:, methods: }`という値オブジェクトのリストである。それがエントリーごとに答える問いは「このクラスのどのメソッドか」である。今回の場合、マクロはプラグインがモデル化するフレームワークの性質であり、宣言するすべてのクラスで共通であるため、マニフェストごとに1つのリストで一度だけ記述できる。このフィールドはそのマニフェストのクラスに紐づけられているため、あるプラグインのマクロが別のプラグインのクラスに適用されることはない。将来プラグインがクラスごとに異なるマクロを必要とする場合でも、値オブジェクトの選択肢は残されている。
- **WD3a — 名前は`methods`ではなく`macros`とする**。 ADR-38の`methods:`はイニシャライザであるメソッドを列挙する。今回のエントリーは非アクションメソッドそのものではなく、引数によってそれらを名指しするクラス本体の呼び出しである。`per_invocation_non_action_macros`はその間接参照を明確に表す。
- **WD4 — 汎用的な抑制フックではなく、1つのルールの絞り込み**。これらのフィールドは`def.ivar-write-mismatch`のみに供給される。「プラグインがエンジンルールXを辞退する」ような汎用フックはスコープ外である（#575）。

## 却下された代替案

| 選択肢 | 却下された理由 |
| --- | --- |
| **B — アクションごとの値オブジェクト**（プラグインがADR-9の事実としてアクションごとの書き込みスコープを公開する） | 同じ答えに対してコントラクト表面が増える。2つの仕組み（ファクトストアとルール）がアクションの定義について一致する必要があり、かつ事実はルールが順序付けを必要とするプロジェクト単位のデータになる。 |
| **C — 現状維持**（各プロジェクトのacknowledgeモードのベースラインに発火を残す） | すべてのRailsプロジェクトで正しいコードに対する偽陽性を残し続け、精度向上レバーが増えるたびにその件数が増加する。これは偽陽性規律（[ADR-0](../0-concept/)、[ADR-5](../5-robustness-principle/)）に反する。 |
| すべてのパブリックメソッドをアクションとみなす | アクション内で実際に実行されるパブリックな`before_action`ターゲットや`helper_method`とアクションとの間の乖離まで黙らせてしまう。 |
| プラグイン側でRelation型を劣化させる | 無関係なルールでの静粛さと引き換えに実際の精度を犠牲にするものであり、#575では誤ったトレードオフとされている。 |

## 結果

- redmineとgitlabにおけるパブリックアクションの発火が解消される。基準に挙げた検出結果、および1つのアクション内の2つの書き込みは引き続き発火する。
- **既知のサイレントケース**。以下のいずれも報告されない:
  - 別のアクションを呼び出すアクション（`def show; index; @roles = {…}; end`）。両方のメソッドがアクションであるため。
  - 別ファイル（再オープン、concern、または`ApplicationController`）内のマクロによって名指しされたパブリックなコールバックターゲットや`helper_method`。マクロ引数は書き込みを保持するファイルから読み取られるため。
  - コールバックがブロックやラムダ経由で到達するパブリックメソッド（`before_action -> { load_roles }`）。リテラルな名前（Symbol、String、またはインライン`def`）のみがカウントされるため。
  - `rescue_from X, with: :handler`や`layout :method_name`によって名指しされたパブリックメソッド。いずれのマクロも`per_invocation_non_action_macros:`に含まれないため。例外を発生させた、あるいはレンダリングを行ったアクションの内部で実行されるにもかかわらず、アクションとして扱われる（フォローアップ: #2320）。
- **引き続き発火する既知の制限**。これらは保守的な挙動である:
  - 実際には1つのアクションでしか実行されないprivateヘルパー（ヘルパー到達性の証明、#575のオプションA2は先送りされた）。
  - コントローラーにincludeされる`ActiveSupport::Concern`などのモジュール内で定義されたアクション。書き込みがモジュールに属するため。
  - 未宣言の`ActionController::Metal`上のコントローラー。
- rigor-actionmailer（メーラーのインスタンスも1つのアクションに奉仕する）は、エンジンを変更することなく#2308でこれらのフィールドを採用した。
- マニフェストの`to_h`に2つのキーが追加されるため、各プラグインのキャッシュIDが一度更新される。

## 他のADRとの関係

- [ADR-2](../2-extension-api/) — マニフェストはプラグインコントラクトである。本ADRはそこに2つの任意かつ追加的なフィールドを加える。
- [ADR-26](../26-activerecord-relation-typing/) — `open_receivers:`がここで踏襲された形式である。すなわち、検出結果の差し控えのみを行う、プラグイン保証のクラスリストである。
- [ADR-50](../50-release-engineering-and-stability-strategy/)および[ADR-60](../60-pre-freeze-plugin-contract-consolidation/) — コントラクトはv1.0.0で凍結される。それ以前の追加フィールドは1.0前の試行の範囲内である。これらは、ADR-60で`external_files:`が削除された原因である「エンジン側の消費者がいないフィールド」という欠陥を回避している。本フィールドには初日から消費者が存在する。
- [ADR-38](../38-additional-initializers/) — 兄弟関係にあるライフサイクルの事実。追加イニシャライザは「このメソッドは他のメソッドより前に実行される」ことを述べ、呼び出し単位クラスは「これらのメソッドは決して同じインスタンスを共有しない」ことを述べる。
- [ADR-0](../0-concept/) / [ADR-5](../5-robustness-principle/) — 正しいプログラムに対する偽陽性の回避は最悪ケースの読み取りより優先され、それがこの例外規定を正当化する。
