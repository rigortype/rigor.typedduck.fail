ステータス: **Accepted —— 2026-08-06に実装**。`Inference::OptimisticOrigin`は、そのnilフリー性が`RbsDispatch`の意図的に読み飛ばす`%a{implicitly-returns-nil}`に依拠している値をマークし、`if`/`unless`の分岐の削除は、そのような値が運ぶ確実性の判定を辞退する。11プロジェクトでの実測: 2,060件の判定のうち47件が影響を受け、診断はすべてのターゲットで両方向ともバイト単位で同一であり、正しいコードに対する再現可能な偽陽性が1件除去される。

根拠: 3番目の消費者を見つけた[形状の調査](../../notes/20260805-issue-286-if-unless-truthiness-elision-census/)と、それを計測してキャリア形状という選択肢を退けた[provenanceの調査](../../notes/20260806-issue-286-optimistic-carrier-provenance-census/)。いずれも[issue #286](https://github.com/rigortype/rigor/issues/286)のためのもの。

## コンテキスト

`docs/internal-spec/inference-engine.md`は意図的な賭けを記録している: コアRBSは`Hash#[]`のミスを`?`の戻り値ではなく`%a{implicitly-returns-nil}`アノテーションとして綴っており、`RbsDispatch`は戻り値型だけを読む。アノテーションを尊重する案は偽陽性を理由に却下された —— `Hash.new(0)`のレシーバーは決してnilを返さないのに、射影された`V?`は正しいコードに対して`possible nil receiver`を発火させる（Rigor自身の`lib`で25件の発火を実測）。仕様はその帰結を自ら述べている: そのような値は**証明ではなく楽観的**であり、`MAP[key]`が`"x" | "y"`と読めることは、キーが存在したかどうかについて何も主張しない。

その一節は続いて、そこから真値性を結論することを2つの消費者に禁じている: `flow.always-truthy-condition`と、`&&`/`||`の`constant_value_polarity`ゲートだ。**3番目が存在するが、名指しされたことはなかった**。 `Narrowing.predicate_certainty`は`if`/`unless`の分岐の削除も駆動しており、その消費者は`Constant`でゲートされていない —— falsey側の断片が`Bot`であるキャリアなら何にでも`:truthy`と答えてしまう。つまりエンジンは、`&&`/`||`の位置では自らに賭けを禁じておきながら、その1行隣では自由にその賭けをしている:

```ruby
MAP = { a: "x", b: "y" }.freeze
v = MAP[key]
n = if v then 1 else "none" end   # elseアームが落とされ、nは1と型付けされる
n.upcase                          # error: undefined method `upcase' for 1 —— プログラムは正しい
```

この非対称性は一見よりも重い。2つの消費者は*判定をどう使うか*が違うからだ。上のゲートは診断を出さないだけだ。削除のほうは**ルックアップが外れたときにプログラムが実際に通る分岐を消す**し、その消去は、絞り込まれた型がメソッド呼び出しに出会うまで見えない —— そこで初めて、動くコードに対する偽陽性として表面化する。それはこのプロジェクトの最上位の価値観の反対側なので、問いは様式的なものではない: この消費者はそもそもこの賭けをしてよいのか？

## 決定

**確実性の判断が値のnilフリー性に依拠してよいのは、そのnilフリー性がその値の性質 —— そのクラス、その居住性、そのリテラル —— であるときだけであり、それが我々自身のモデリング上の選択の性質であるときは決して依拠してはならない**。エンジンが、結果が不在でありうるというシグネチャ自身の言明を意図的に読み飛ばしている場所では、そこで生まれる値がその選択を運んでおり、それを実行時の振る舞いについての主張へ変換しようとするあらゆる消費者は辞退しなければならない。

これが基準であり、今日の単一のケースを越えて一般化する: Rigorが承知のうえで楽観的に型付けする将来のあらゆる箇所は、仕様が消費者をあらためて列挙しなくても同じ義務を継承する。またこれは逆方向の境界も述べている —— その値はディスパッチには完全に使えるままだ。「我々がそう選んだ」は*判断*についてのファクトであって、*型*の欠陥ではないからだ。

### WD1 —— 選択がなされる場所で値をマークする

`Inference::OptimisticOrigin`は`RbsDispatch.translate_return_type`（`rbs_dispatch.rb`のL346-372あたり、既存の`record_void_recovery`呼び出しの直後）で原因を記録する。ここは、`RbsTypeTranslator`がその区別を消してしまう前に、選択されたオーバーロードがミスをアノテーションとして綴っていたことをまだ知っている唯一の場所だ。

3つの性質が効いている。この判断は**選択されたオーバーロードごと**だ —— `RBS::Definition::Method::TypeDef#overload_annotations`がオーバーロードごとのアノテーションを公開し、`OverloadSelector.select`が`method_definition.method_types`のいずれかを逐語で返すので、同一性でちょうど解決できる: `Array#first`はマークされ、`Array#first(3)`はされず、すでにミスを`?`で綴っているシグネチャ（`String#[]`・`Enumerable#find`）は決してマークされない。これは[ADR-75](../75-dynamic-provenance/) / [ADR-82](../82-dynamic-provenance-wiring/)の意味での**サイドチャネル**だ: 呼び出しノードに記録され、代入時にローカルとインスタンス変数の束縛へ伝播し、素の読み取りから解決し直され、`Scope#==` / `#hash`からは除外され、サブタイピング・一貫性・正規化・消去には決して参加しない。そして**シェイプティアが解決した読み取りには適用されない**。`ShapeDispatch`は、その読み取りがミスしえないことを証明するレシーバーから答えているからだ —— 宣言済みシェイプ上の静的キー、非空の`Tuple`に対する`first`。

### WD2 —— falsey側の断片を広げるのではなく、消費側で辞退する

辞退は`StatementEvaluator#live_branch_for_if` / `#live_branch_for_unless`と`ExpressionTyper#constant_predicate_polarity`に置かれる。これらのキャリアがfalseyでありうると`Narrowing.falsey_nominal?` / `.narrow_falsey`に教えることで実装してはならない（MUST NOT）: `&&=` / `||=`とand/orの生き残る左辺のエッジ（`statement_evaluator.rb`のL382/L384あたり、`expression_typer.rb`のL661あたり）が同じ関数を読んでおり、そこでfalsey側の断片を広げると束縛されたローカルに`nil`を再び入れてしまい、`possible nil receiver`の発火を買うことになる。偽陽性で支払う健全性の修正は、まさにこのプロジェクトがしないトレードであり、この配置は実装上の細部ではなく制約である。

### WD3 —— キャリアの形状はこの判断の代理ではない

明白で安価なゲート —— 非`Constant`のキャリアでは辞退する —— は実装し、計測し、却下した。これは両方向に同時に間違っている。**過剰に辞退する**: コーパス中の134件の非`Constant`判定のうち、実際に楽観的なのは35件だけで、残りはクラスが本当に`nil`を除外している名前的型と、居住性から健全な`Tuple`/`HashShape`のキャリアだ。そして**辞退が足りない**: 値が1つの型を共有する`Hash`は単独の`Constant`を生むが、それはユニオンの場合とまったく同じくらい楽観的なので、12件の楽観的な判定がこのゲートを生き延びる —— うち8件はredmineの1つのクラスタで、そこでは判定が`:falsey`であり、削除が実際に走るほうのアームを落としている。

## 却下／先送りされた代替案

| 代替案 | 判定 | 理由 |
| --- | --- | --- |
| 仕様の除外にこの消費者を名指しで加え、挙動は維持する | 却下 | 正しいコードに対する再現可能な偽陽性を追認することになるし、計測は代わりに修正を取るコストがゼロであることを示している。 |
| すべての非`Constant`キャリアで辞退する | 却下 | 過剰辞退と辞退不足を同時に起こす（WD3）;キャリアがたまたま持つ形状は、この判断が依拠する性質ではない。 |
| `falsey_nominal?`を絞り、`Object` / `BasicObject` / `Kernel`を判定不能として読ませる（当初提出時の#286） | 却下 | 41,836件の述語で発火0件と実測 —— Rigorの未知のキャリアは`Nominal[Object]`ではなく`Dynamic`だ。空集合を守る未テストのガードであり、その受け入れ基準は空虚に満たされてしまう。 |
| `%a{implicitly-returns-nil}`をソースで尊重し、読み取りを`V?`と型付けする | 却下 | 当初の25件の偽陽性の計測は有効なままだ;このADRは意図的に楽観的な*型*を保ち、確実性の判断がそこから何を結論してよいかだけを制約する。 |

## 帰結

- **良い点**。不誠実なアノテーションを一切伴わない普通のRubyに届いていた、正しいコードに対する偽陽性のクラスを除去する。1つの判断が2つのルールの下で3通りに読まれていた非対称性を閉じる。この基準は、将来のあらゆる意図的な楽観に再利用できる。
- **悪い点**。 11プロジェクトにわたる47件の判定が削除をやめるので、それらの式は両アームのユニオンとして型付けされる。実測コスト: 11ターゲットすべてで両方向とも診断はバイト単位で同一;Rigor自身の`lib`は`constant`ノードを3つ*獲得*し`bot (unreachable)`を3つ失う（これまでスキップされていたアームが型付けされるようになるため）;redmineの精度比率は50.93% → 50.92%へ動く。
- **将来の作業に対するガードレール**。このゲートはprovenanceなので、マークの記録をやめるものは何であれ、静かに古い賭けを復活させる。`spec/rigor/inference/optimistic_origin_spec.rb`は、辞退の例それぞれに、依然として削除されなければならない証明側のコントロールを対にしている;「常に辞退」「決して辞退しない」の両ミュータントがそれぞれ6例を殺すので、どちらの方向のリグレッションも大きな音を立てて失敗する。
- **受け入れ**。 `make verify`が緑であること、そしてノートの手法どおり`--no-cache --no-baseline`でコーパスのA/Bが再現できること。

## 他のADRとの関係

- [ADR-78](../78-reflexive-overfold-always-truthy/) —— 本ADRが拡張するWD1の基準を述べたもの: 証明可能な真値性は本物の定数にのみ依拠する。そのprovenanceタグの却下は本件を**カバーしない**: ADR-78はエンジンが生成すべきでなかった定数を洗浄することを拒んだのに対し、楽観的なユニオンは意図的に生成され、ディスパッチには正しく、25件の偽陽性の計測に裏づけられている。ここでの問いは、エンジンがその値を生成してよいかではなく、判断がそれを証明として読んでよいかだ。
- [ADR-75](../75-dynamic-provenance/) / [ADR-82](../82-dynamic-provenance-wiring/) —— 本ADRが再利用するサイドチャネルの形。違いは何に付くかだ: `DynamicOrigin`は`Dynamic`を説明するのに対し、このマークは普通の`Union` / `Constant` / `Nominal`のキャリアに乗る。
- [ADR-5](../5-robustness-principle/) —— 方向を決めた価値観: 動いているプログラムの不変条件は前提とされるので、保守的な一手は賭けから推論することではなく両アームを保つことだ。
- issue #152 —— まさに同じ理由で見送られた`&&`/`||`の拡張;本ADRが拡張する除外こそが、それを禁じているものだ。
