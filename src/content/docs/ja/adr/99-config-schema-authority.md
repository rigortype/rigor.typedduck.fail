ステータス: **Accepted、2026-07-17——実装済み**。`schemas/rigor-config.schema.json`は`docs/compatibility.md`の凍結面テーブルにおける`.rigor.yml`の名指しされた信頼できる情報源になり、[`docs/internal-spec/config.md`](../../internal-spec/config/)は3つの検証ティア、予約名前空間ルール、予約パイプラインの規範的な言明になる。監査の3つの欠陥も同時に修正される。すなわち`cache`のネストしたドリフトとそのゲートの盲点、404の`$id`、そして欠けている`rigor_rs:`予約である。

根拠: § コンテキストに記録された2026-07-17の設定一貫性監査——以下のすべての主張は、文書から読み取ったのではなくツリーに対して再現された。

## コンテキスト

4つのアーティファクトが`.rigor.yml`を記述しており、それらがどう関係するかを述べるものは何もなかった。

| アーティファクト | 仕事 |
| --- | --- |
| `schemas/rigor-config.schema.json` | JSON Schema。`.rigor.dist.yml`が運び`rigor init`が書き込む`# yaml-language-server: $schema=`コメントを介してエディタに届く |
| `lib/rigor/configuration.rb` | `DEFAULTS`＋ コアーサー |
| `lib/rigor/config_audit.rb` | 何にも解決しない警告 |
| `docs/manual/03-configuration.md` | ユーザー向けのキーリファレンス |

[`docs/compatibility.md`](../../compatibility/)は[ADR-50](../50-release-engineering-and-stability-strategy/) WD1の凍結面テーブルを運び、その`.rigor.yml`行は信頼できる情報源を`Configuration::DEFAULTS`＋コアーサーと名指しし、ユーザー文書としてマニュアルを挙げている。**スキーマはその行から——そしてマニュアルからも——不在である**。ゆえにそれは、設定の決定が実際になされる両方の場所で不可視であり、監査はそれが何を犠牲にするかを見出した。

1. **`cache.max_bytes`と`cache.validation`はスキーマに拒否される**。両方とも`DEFAULTS`にあり、両方ともマニュアルに文書化されている。スキーマの`cache`オブジェクトは`path`だけを宣言し`additionalProperties: false`である。`spec/rigor/config_schema_spec.rb`は**トップレベルのキーについてのみ**DEFAULTS → schemaを固定するので、ネストした面はゲートの下でドリフトした。ネストしたキーを追加する貢献者は、スキーマが存在することを決して知らされない。
2. **`rigor init`が書き込むスキーマURLは404する**。その`$id`、そして生成されるすべての`.rigor.yml`に書き込まれるURLは`zenwerk/rigor`を名指すが、このプロジェクトは`rigortype/rigor`である。だから**`rigor init`で初期化されたすべてのプロジェクトはスキーマ検証を一切受けてこなかった**——そしてロードに失敗するスキーマは、苦情のないスキーマと区別がつかない。それが、これが（1）と並んでこれほど長く隠れていた仕組みである。このリポジトリ自身の`.rigor.dist.yml`は相対パスと`cache.path`だけを使うので、（1）を表面化させたであろう唯一のファイルは、たまたまそれをすり抜ける。
3. **rigor-rsはこのスキーマを自身の権威ある設定スキーマとしてベンダリングしている**。ポートはこのリポジトリを`reference/rigor`のサブモジュールとして運び、そのコピーはバイト単位で同一である。ここのどの文書もそれにその役割を与えていない。そしてトップレベルが`additionalProperties: false`であるため、ベンダリングされたスキーマは`rigor_rs:`——ポート自身の名前空間を、ポート自身のチェックアウトの中で——拒否する。

（3）が鋭いものである。すなわち、**2つ目の実装が、このリポジトリが信頼できる情報源として挙げていないファイルに依存している**。ポートの[ADR-0036](https://github.com/rigortype/rigor-rs/blob/master/docs/adr/0036-ruby-sidecar-default-reversal.md)は、「リファレンスは未知のキーを無視するので`rigor_rs:`はそれに対して透過的である」という言明された根拠で`rigor_rs:`を導入した。それは**ランタイム**の主張であり、真である——`rigor_rs:`を運ぶ設定はロードされ、クリーンにチェックされ、警告なしに0で終了する。なぜなら`Configuration`はそのキーを1つずつ読み、未知のものを決して列挙しないからである。ADR-0036は単にスキーマレイヤーを考慮しなかった。我々もしなかった。

## 決定

**スキーマは`.rigor.yml`の信頼できる情報源であり、`Configuration::DEFAULTS`とそのコアーサーと同格であり、両方の実装に対して権威を持つ**。

弁別する基準: **rigor-rsはポートであるので、リファレンスが設定面を所有する——ポートが、リファレンスが持たない概念のために必要とする名前空間を含めて**。ポート固有のキーはポートのプライベートな用件ではない。それはリファレンスが与える予約である。それはADR-0036がエンコードした直観（各実装は自身の名前空間を所有する）を反転させ、それがリファレンスが`rigor_rs:`の形を単に許容するのではなく宣言しなければならない理由である。

### WD1 — 3つのティア、3つの失敗モード

`.rigor.yml`は3つの独立したティアで検証される。あるキーがどのティアに答えるかは、すべての設定の決定が答えねばならない設計上の問いである。

| ティア | チェッカー | いつ | 失敗時 |
| --- | --- | --- | --- |
| スキーマ | エディタ / CI | 編集時 | 波線;**ランタイムへの影響なし** |
| `Configuration`ロード | この実装 | ロード時 | `ArgumentError` |
| 設定監査 | この実装 | チェック時 | STDERR警告;**終了コード変わらず** |

予約名前空間は**スキーマティアにのみ**答える。すなわち、書かれた場所で型チェックされるが、決して読まれず、決して検証されず、決して型強制されず、その値がどれほど無効であってもランタイムエラーには決してならない。これが「検証されるが評価されない」の具体的な意味であり、`rigor_rs:`が占める位置である。

### WD2 — 予約パイプライン、そしてなぜ順序が荷重を支えるのか

> ポートで提案する → **このリポジトリのスキーマで予約する** → ポートで実装する → ここでリリースする → ポートをリリースする

実装前に予約することが、新しく更新されたポートが要求し始めたばかりのキーをユーザーのエディタがフラグするのを止めるものである。パイプラインはすでに一度逆に走った——ポートはリファレンスが予約する前に`rigor_rs.ruby`を実装した。それがまさに、スキーマが今日それを拒否する理由である。

予約は**ミラーではなく権威的**であるので、予約名前空間の内容を制約するのは正しい。すなわち`rigor_rs:`下の宣言されていないキーは、ポートが予約が決して与えなかったものを出荷したことを意味する。ここが、リファレンスが読まない名前空間で`additionalProperties: false`がその価値を稼ぐ唯一の場所である。

### WD3 — 文書はスキーマを見つけられるようにし、ゲートは忘れることを失敗させる

両方の半分が必要であり、監査はなぜどちらも単独では不十分かを示す。文書（`internal-spec/config.md`、compatibility行、マニュアル）はそれらを読む誰かに届く——そして読まないことこそが、3つの欠陥すべてが起きた仕組みである。ゲートが残りを捕まえる。

- **DEFAULTS → schema、ネスト**（`config_schema_spec`）: `cache:` / `plugins_io:` / `bundler:` / … 下の新しいキーは、スキーマがそれを知らない限りビルドを失敗させる。これが、その不在が（1）を腐らせた軸である。
- **予約名前空間 → schema**: *別の*軸である。なぜなら予約名前空間は**定義上`DEFAULTS`キーではない**（`DEFAULTS.key?("rigor_rs") == false`）からである。DEFAULTSに鍵付けされたゲートをいくら広げてもそれには決して届かない——盲点はスコープの見落としではなく構造的である。
- **`$id` ↔ init書き込みURL**: 1つの定数、両方が読むので、それらは食い違いようがない。

### WD4 — `AGENTS.md`は変更なし

[ADR-98](../98-development-flow-document-roles/)の前提テスト——*それを調べに行こうとも思わなかったセッションは間違ったことをするか？*——により、設定セマンティクスは**ルックアップ**である。すなわち、それはすでに設定に触れているセッションに重要である。そして実証された唯一の失敗はいまやゲートされているので、リマインダーはゲートを重複させる指示になる（[ADR-97](../97-adr-index-budgets/)の基準2）。`AGENTS.md`はすでに解析器の契約を`docs/internal-spec/`へルーティングするので、`config.md`はそのポインタを無償で継承する——ゼロバイトで。

## 却下／先送りした代替案

| 候補 | ステータス | 理由 |
| --- | --- | --- |
| `rigor_rs:`を不透明な`{"type": "object"}`として宣言する | 却下 | 最初の本能であり、権威を反転させる。すなわちそれはポートを自身の名前空間の文法の所有者として扱い、リファレンスを単にそれを許容するものとして扱う。WD1のもとではリファレンスが名前空間を*与える*ので、それが形を宣言する。不透明なオブジェクトはまた、予約が捕まえるために存在するタイポ（`rigor_rs: { rubi: auto }`）を黙って受け入れてしまう。 |
| ポートの文法をミラーしてその進化を追跡する | 却下（枠組みの誤り） | これは形を宣言することへの異論だった——リファレンスがポートを追いかけることになる、と。それは矢印が逆である。すなわちポートがリファレンスを追跡する。追いかけるものは何もない。 |
| 予約名前空間をポートが公開するスキーマへ`$ref`する | 却下 | すべてのエディタとCIで解決されるリモート参照を必要とするが、ポートはスキーマを公開しない——それは我々のものをベンダリングする。欠陥（2）は、腐ったスキーマURLが何を犠牲にするかの生きた実証であり、それを1つ追加するには貧弱な基盤である。 |
| `rigor_rs.ruby`を`enum`で制約する | 却下 | ポートの文法は`require` / `auto` / `off` **または任意のパス**（`ruby_mode.rs`の`parse_value`: 予約キーワード、さもなくば`Path`）である。enumはすべてのパス形式を拒否してしまう——形について嘘をつく予約は、予約がないより悪い。 |
| `AGENTS.md`に設定セマンティクスを指す一行を置く | 却下 | WD4。 |
| セマンティクスを`docs/manual/03-configuration.md`に置く | 却下 | マニュアルはユーザー向けであり、ここでの根拠（スキーマの権威、ポートのパイプライン）は貢献者向けの材料である。マニュアルはスキーマが存在するという*事実*とその使い方を得る。`internal-spec/config.md`がセマンティクスを得る——`baseline.md`と`cache.md`がそのユーザー向けアーティファクトのためにすでに使っているのと同じ分割である。 |
| 同じ変更の中で未知のトップレベルキーに警告する | 先送り | #166として追跡され、これにブロックされている——新しい警告はBCを帯び、その`config_warnings`の種類はv1.0で凍結された語彙である。まず予約することが、それをそもそも安全に追加できるようにするものである。 |

## 影響

プラス:

- スキーマは設定の決定がなされる場所で名指しされ、それを忘れる両方のやり方がいまやビルドを失敗させる。
- 「検証されるが評価されない」は、`Configuration`がそのキーを1つずつ読むことの創発的な性質ではなく、文書を持つ言明された立場である。
- ポートは実装対象にできる予約と、2つのリリースを順序づけて保つパイプラインを得る。
- `rigor init`は解決するURLを書き込むので、スキーマ検証が初めて、そもそもユーザーに届く。

マイナス:

- リファレンスはいまや自身が読まない形を宣言するので、ポートの変更はその前にリファレンスのリリースを必要とする。それはパイプラインが順序を買うコストであり、それは本物である。すなわちポートのキーは我々のリリースのペースより速く出荷できない。
- 3つのティアは「設定は検証される」より説明する面が多い。ティアはすでに存在していた。これはそれらを名指すだけである。

## 他のADRとの関係

- **[ADR-50](../50-release-engineering-and-stability-strategy/)** —— WD1が凍結された公開面を所有し、すでに`.rigor.yml`キーを挙げている。本ADRはその行の信頼できる情報源にスキーマを追加する。予約パイプラインはそのペースのもとでのリリース順序の制約である。
- **[ADR-97](../97-adr-index-budgets/) / [ADR-98](../98-development-flow-document-roles/)** —— 基準2（強制されないルールは一時的な状態である）が、WD3がすべての文書をゲートと組にする理由であり、ADR-98の前提テストが、WD4が`AGENTS.md`をそのままにする理由である。
- **[ADR-10](../10-dependency-source-inference/)** —— `dependencies.source_inference:`は、セマンティクスがマニュアルの外で規定される設定キー（`docs/internal-spec/dependency-source-inference.md`）の先例である。`config.md`は一般ケースである。
- **rigor-rs ADR-0036** —— `rigor_rs:`をランタイムのみの根拠で導入し、スキーマを決して考慮しなかった。これはそれが欠いていたリファレンス側の半分である。その名前空間の決定は立つが、その権威の枠組みは立たない。
