ステータス: **Accepted、2026-09-01**。両方の半分がこのADRとともに着地する: 逐次着地の規範は`AGENTS.md`の§「Commit and PR Etiquette」にあり、`changelog.d/`のフラグメントの機構はここで出荷される（ディレクトリ、ゲート`spec/docs/changelog_fragments_spec.rb`、そして`rigor-release-prep`スキルの統合ステップ）。[PR #500](https://github.com/rigortype/rigor/pull/500)の`merge=union`属性は、リリース準備時の保険として保持される;それが符号化していた期待は以下で訂正される。

## コンテキスト

[PR #500](https://github.com/rigortype/rigor/pull/500)は、`## [Unreleased]`のエントリーを追記する並行ブランチが衝突しなくなるように`CHANGELOG.md merge=union`をマークし、まさにそれを検証した——**ローカルのgit**に対して。実効的な層はgithub.comだった: GitHubのPRのマージ可能性とマージの計算は、`.gitattributes`のマージドライバを、unionも含めて無視する。2026-09-01の不透明性のスイープのキャンペーンを着地させたことで、そのコストが具体になった: 19本のPRのキュー、それぞれが同じ`### Fixed`のアンカーに1つのエントリーを運んでおり、キューのマージが1つも起きていない段階で、すでにマージ済みの1エントリーに対して3本のPRがCONFLICTINGと読まれ、そしてマージのたびに残りのすべてのPRが再び汚れた。このキューは、それぞれ約8〜12分の「ローカルのマージ → プッシュ → フルCI → マージ」というサイクルを約17回逐次に回して捌かれた。2つの独立した原因が重なっていた:

- **共有されたホットな領域**。すべてのPRが1つのファイルの1つのアンカーに追記するので、どの2本のPRもテキスト上で重なる——そしてGitHubは、ローカルのマージドライバに関係なくそれらを直列化する。
- **先送りされたキュー**。 PRはグリーンになった順に着地するのではなくセッション中ずっと溜まっており、これは常設のmerge-as-you-goの承認（2026-08-01）からの逸脱だった。スタック（#543・#557・#558は、そのベースが着地していなかったというだけの理由でスタックしていた）と兄弟どうしの衝突を製造したのは、この先送りである: マージ後の`master`から分岐したブランチは、その先行者たちと衝突しえない。

## 決定

原因ごとに1つずつ、2つの規則。

**1. 逐次着地（直列のケース）**。逐次に監査される変更を生むセッションは、各PRをそのゲートが通った時点で（`make verify`、該当する場合はコーパスのゲート、CIがグリーン）ただちに着地させる——マージを試み、拒否されたらキューに積むのではなくただちに表面化させる。次のブランチはマージ後の`master`から分岐する;そのマージのCIは次の項目の開発と重なる。*判定基準: バッチ化とスタックは、ユーザーが1つの集合として裁定しなければならない変更のために取っておく;先送りはスタックと兄弟どうしの衝突を製造する。*

**2. changelogのフラグメント（並行のケース）**。 `[Unreleased]`のエントリーは、新しいファイル`changelog.d/<section>/<slug>.md`として着地する——既存のエントリーの文法（サブシステムのラベル、完全なPRのリンク）による1行の箇条書きであり、セクションはサブディレクトリによって符号化される（Keep a Changelogの6つの型を小文字化したもの）。リリース準備がフラグメントを`[Unreleased]`へ統合し、カットの時点でそれらを削除する;`CHANGELOG.md`そのものはリリース準備によってのみ書かれる。*判定基準: すべてのPRが追記しなければならないファイルは、ローカルのマージドライバに関係なくGitHub上の直列化点である——PRごとの追記を、衝突しえないPRごとのファイル追加へ変換する。*

## 作業上の決定

- **WD1 — セクションはサブディレクトリ**。 `changelog.d/fixed/…`・`changelog.d/added/…`、…: セクションはパスからlintでき、内容のパースは不要。
- **WD2 — slugはブランチ名から**。 PRが存在する前から一意である（PR番号はそうではない）。PRのリンクは従来どおり`gh pr create`の直後にエントリーのテキストへ入る——そしてフラグメントのゲートがそのリンクを機械的に検査するようになった。直接編集のフローでは信頼するしかなかったものだ。
- **WD3 — `merge=union`は残す**。無害であり、残った唯一の書き手（リリース準備が、master直接コミットの落ち穂と競合するケース）については依然として正しい。
- **WD4 — ゲートは`spec/docs/`に置く**（`make docs-check`とスイートの両方が走らせる）。バリデーターはインラインの例で固定するので、ディレクトリが空の間も文法が保たれる。
- **WD5 — 正直なトレード**。フラグメントは兄弟のPRをMERGEABLEに保つので、それらは古い`master`に対して走ったCIとともにマージされる。このリポジトリはもともとブランチが最新であることを要求していないので、これは新しい窓を開けるのではなく、受容済みの窓を広げるものである;バッチ後の常設の統合`master`のverifyがその網である。

## 却下した代替案

| 代替案 | なぜ採らないか |
| --- | --- |
| `merge=union`単独（PR #500） | 実効的な層で反証された: GitHubはPRのマージ可能性についてマージドライバを無視する。 |
| 自動排出ボット（DIRTYな各PRをリベース＋プッシュ） | 直列化されたCIのΘ（N）のコストが残り、そしてkeep-bothのコードの衝突には人間の判断が要る——このキャンペーンの最中に、機械的なリゾルバが`expression_typer.rb`を壊した。 |
| カットの時点でエントリーを再構成する | #500を蒸し返すことになる: 文言とPRのリンクは着地時が最も安い;v0.3.6の再構成はその準備工程を支配した。 |
| GitHubのマージキュー | CONFLICTINGなPRはキューに入れない;根本原因に手が付いていない。 |
| コミットトレーラーによるchangelog（GitLab方式） | リンクの導出をカット時の列挙へ戻すことになる——まさに#500が取り除いたコストだ。 |

## 帰結

- 並行するPRは排出の間もMERGEABLEのままであり、すべてのPRの組を襲っていた衝突のクラスについて、直列化された更新＋CIのサイクルが消える。本物のコードの重なりは依然として衝突し、依然として手作業の解決に値する。
- PRのリンクは、信頼されるのではなく着地時に機械的にゲートされる。
- `[Unreleased]`はサイクルの途中では空に読める;保留中のものを見るには`ls changelog.d/*/`。
- PRごとにファイルが1つ増える;リリース準備に機械的な統合のステップが1つ加わる。
- 将来のワークフローの変更を縛るメタな教訓: **その振る舞いを強制する層で検証すること**——github.com上での使い捨てPR 2本のプローブなら、#500の前提を数分で反証できたはずであり、ローカルのマージによる検証ではそれができなかった。
