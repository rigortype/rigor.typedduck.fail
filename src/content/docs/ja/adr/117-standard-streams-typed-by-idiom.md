ステータス: **Accepted（2026-09-26）**。一部は#1405以降維持されています: `$stdin.gets`、`STDIN.gets`、`ARGF.gets`、`Kernel.gets`は`$_`をナローイングし（WD4）、解析対象のコードに現れない置き換えはモデル化されないため、#1411は仕様どおり（by design）としてクローズされました。残りは未解決（open）です:

根拠: #1405の3回のレビューラウンド（issue #1359）、#1411および#1415の背景にあるプローブ、そして本ADRのレビュー（PR #1418）。

## 背景（Context）

動的言語において、値は2種類の型を持ち得ます。1つはランタイムが保証するもの。もう1つは言語のイディオムが人々に期待させるものです。標準ストリームはその両方を示しており、両者は乖離しています。Ruby 4.0.5において:

- **`$stdin`** — セッターは何のチェックも行いません。`$stdin = 1`も受け入れられるため、最悪の場合`$stdin`は未知（unknown）です。
- **`$stdout`、`$stderr`、`$>`** — セッターは値が`write`に応答しない限り`TypeError`を発生させます。ランタイムが保証するのは`_Writer`だけであり、それ以上のものではありません。
- **イディオム** — 3つすべてが`IO`を保持します。テストでは一時的にIO互換のオブジェクト（通常は`IO`のサブクラスではない`StringIO`）を代入し、後から元のオブジェクトに戻します。

実行時にストリームのクラスをチェックするコードは稀です。そのようなチェックが行われる場所では、チェックによってRigorを静かなまま（エラーを出さないよう）にしなければなりません（WD1）。

`$_`はより厳格な形でストリームに依存しています。C言語で実装されたリーダーは呼び出し側の`$_`を設定しますが、Rubyで定義されたリーダー（`Tempfile#gets`、`Reline`の`readline`、テストダブルなど）は設定しません。`Kernel#gets`と`ARGF.gets`は`$stdin`が何を保持していようとも`$_`を設定し、`Kernel#readline`は`$stdin`に従います。

#1405のレビューでは、3つの理由からRuby製である可能性がある`gets`が繰り返し見つかりました: `main`上のミックスイン、別ファイル内のパッチ、および`load(file, M)`のような実行モードです。PRは最悪のケースを採用し、それにより`while gets; $_`を諦めることになりました。gemは実行時にストリームに注入できるため、その集合を閉じる静的ルールは存在しません。型仕様書にはすでに支配的な原則が記されています（[`overview.md`](../../type-specification/overview/)）: *動作するプログラムこそが最も重要な事実である*。

## 決定事項（Decision）

**Rigorはランタイムが強制するものだけを診断し、読み取りはイディオムに従って型付けします**。

1. **強制された契約（Enforced contract）**。ランタイムが値に契約を強制する場合、Rigorはその契約に明白に違反する書き込みのみを報告します。その書き込みは例外を発生させるためです。
2. **イディオム的期待（Idiomatic expectation）**。ランタイムがそれ以上のことを強制しない場合、Rigorはイディオム的な期待に従って読み取りを型付けし、値がそこから逸脱する可能性があるという警告を決して発しません。そのような警告は、ほぼすべての正しいプログラムで発火して作成者には何も教えず、オオカミ少年になってしまいます。
3. **オプトインではなくデフォルト**。この期待はいかなる設定もなしに成立するものであり、これをオプトインにすることはRigorが拒否する姿勢です。それを変更する証拠は、解析対象のコードとその設定が文字どおりに述べている内容から得られます。エンジンがファイル名やフレームワークの慣例からそれを推測することは決してありません。コード内のクラスガード（`is_a?`、`respond_to?`、`case … when`）はそのような証拠です: いかなる報告や確信度の判定（アームのドロップ、到達不能な節）も、それに反するイディオム的な型に依拠してはなりません。
4. **根拠ある報告（Earned reports）**。この期待によって追加される報告は、イディオム的な占有物の下で成立しなければなりません。`while $stdin.gets`ループの後の`puts "tail" if $_`のような正確なデッドコンディションの報告は意図されたものです。

### 運用上の決定（Working decisions）

- **WD1 — 読み取り**。バインドされていない`$stdin`、`$stdout`、`$stderr`は`IO`として読み取られます（#1366）。`$>`は`$stdout`と同じ変数であり、同様に読み取られ、ジョインされます。
  - これは期待であり、ランタイムのクラスについての主張ではありません。アプリケーションコードは`$stdout`の背後に`StringIO`が存在する状態で実行されている可能性があり、それを知る筋合いはありません。
  - ファイルが行う書き込みはその値をジョインします（#1362）。
  - `LastLine.reader_global?`はメンバーがすべてコアリーダーであるジョインされた`$stdin`を受け入れなければなりません（MUST）。これによりジョインによって`$_`のナローイングが停止しないようにします。
  - クラスガードされた読み取りは静かなままでなければなりません（MUST）: `$stdout.is_a?(StringIO) ? $stdout.string : nil`、`$stdout.respond_to?(:string)`、`case $stdout when StringIO`。そのようなガードは現在グローバルや定数のレシーバーをナローイングしないため（`STDOUT`はすでにこれらのシェイプを報告します）、#1429は#1366のストリーム部分の前に着地します。
- **WD2 — 書き込み**。
  - `$stdout`、`$stderr`、`$>`への書き込みは`_Writer`に対してのみチェックされます（#1367）。`$stdout = 1`は報告されます; `$stdout = StringIO.new`や`write`を持つ任意のオブジェクトは報告されません。
  - `$stdin`への書き込みは決してチェックされません。
- **WD3 — テストスコープのビュー**。ストリームを差し替えるテストヘルパー（`config.before { $stdout = StringIO.new }`）は、[ADR-17](../17-monkey-patch-pre-evaluation/)の意味でのモンキーパッチです。したがってエンジンはそれを設定から取得します: それが提供するパスにスコープされた`pre_eval:`エントリであり、そのグローバル書き込みはそのスコープに対して、宣言された`IO`を含めず、スコープの事前評価されたファイルが書き込む値のユニオンとしてグローバルを再型付けします（#1426）。
  - オンボーディングスキルの`rigor-project-init`はそのエントリを書き込みます。ファイル名単体からではなく、プロジェクト自身の配線（`.rspec`の`--require`、テストファイルの`require`）を読み取ります（#1427）。
  - プロジェクトにそのエントリが存在するまで、テストファイル内の`$stdout.string`は、リストされていないモンキーパッチと同様に`call.undefined-method`を報告します。報告は`pre_eval:`を指し示すべきです。
- **WD4 — `$_`はコアリーダーを信頼する**。`$stdin`、`STDIN`、`ARGF`、`Kernel`、および`IO`またはその同類（`StringIO`を含む: そのリーダーはC言語製）として型付けされたレシーバーは、呼び出し元の`$_`を設定すると仮定されます。リーダーの後に`$_`を読み取るコードは、それが設定された場合にのみ機能します。可視の反証は依然として辞退します（特記のない限りすべて`lib/rigor/inference/last_line.rb`内）:
  - プログラム内の任意の場所のトップレベル、またはクラス、モジュール、シングルトン本体内の`def gets` / `def readline`（`BlockCallTiming.project_defines_anywhere?`、`block_call_timing.rb`約L168）;
  - ファイル内の`define_method`ファミリーのパッチ、またはどちらかの名前の`alias`（計算された名前を含む）（`ScopeIndexer#build_program_global_index`経由の`LastLine.patched_readers`）;
  - ファイル内で非リーダーにバインドされた`$stdin`（`LastLine.reader_global?`）;
  - `Tempfile`レシーバー（`LastLine::DELEGATING_CLASSES`）;
  - RBSが認識しないレシーバークラス（`LastLine.reader_class?`）。

  読み取られているファイルの外部での置き換え（プログラム全体でチェックされる`def`を除く）は、存在しないものと仮定されます: 別ファイル内のパッチや`$stdin`バインディング、テストダブル、gem、`load(file, M)`、DSLの`instance_eval`などです。依然としてギャップがあります:
  - `class << $stdin; def gets`、`STDIN.singleton_class.class_eval { def gets }`、または`$stdin.instance_eval { def gets }`として到達されるストリームのシングルトン上の`def`（#1423）;
  - ファイル内の文字列`class_eval`によって定義されたリーダー（`IO.class_eval("def gets(*) = 'x'")`）。
- **WD5 — 暗黙的selfのリーダー**（`while gets`）はWD4の仮定のもとでナローイングし、ファイルが`self`について示す証拠に基づいて辞退します。#1415が正規のリストと受け入れ基準を保持しています。
- **WD6 — 辞退または忘却された`$_`は`Dynamic[top]`として読み取られ、決してそのRBS型としては読み取られない**。
  `Scope#forget_last_line`は、リーダーが実行された可能性のある任意の場所で`$_`をアンバインドします。そこでのRBSフォールバック（`$_: String?`）は、`if $stdin.gets; items.each(&h); $_.chomp; end`のような正しいコードを報告してしまいます。#1366は`$_`を除外するか、`untyped_last_line`が行うようにそれをバインドしなければならず（MUST）、その`$_`部分は#1415の後に置かれます。

## 却下・延期された代替案（Rejected and deferred alternatives）

| 代替案 | 理由 |
| --- | --- |
| デフォルトで最悪のケース（unknown）によって`$stdin`を型付けする | ランタイムの事実ではありますが、コードの読者には役に立ちません。すべてのRubyプログラムは`$stdin`を`IO`として扱います。 |
| デフォルトで強制された契約である`_Writer`として`$stdout`の読み取りを型付けする | `$stdout.sync = true`、`$stdout.tty?`、`$stdout.flush`がすべて報告されてしまいます。契約は書き込みをチェックするためのものであり（WD2）、読み取りを型付けするためのものではありません。 |
| **延期:**オプトインのstrictストリームモード（`$stdout: _Writer`、`$stdin: Dynamic`） | より正確で健全ですが、一般的なパターンから外れます。より*厳格な*読み取りをオプトインすることは決定ポイント3と両立します: イディオム的なデフォルトが決してオプトインであってはならないだけです。実際のプロジェクトから要求されたときに構築し、それ以前には構築しません。 |
| ハードコードされた`IO \| StringIO` | Rubyを公称型システム（nominal type system）として読み取ってしまいます。テストビューは固定のユニオンからではなく、証拠から得られます（WD3）。 |
| デフォルトで`spec/spec_helper.rb` / `test/test_helper.rb`を事前評価する | フレームワーク知識がエンジンにバイアスを与え、テストヘルパーではない同名ファイルを持つプロジェクトが暗黙的に評価されてしまいます。スキルは代わりに配線を読み取ります（WD3）。 |
| 設定されるまで`test_paths`配下でストリームを`Dynamic`に維持する | `test_paths`はディレクトリ名によって自動検出されるため、同じ名前ベースのバイアスになります。欠落しているパッチは他のパッチと同様に報告されます（WD3）。 |
| エフェクトサマリーその他から、非IOによって置き換えられたストリームについて警告する | オオカミ少年です: `$stdout = StringIO.new`はイディオム的です。強制された違反のみが報告されます（WD2）。 |
| 置き換えが不可能な場合にのみ`$_`をナローイングする（#1405の最終的な解釈）、または置き換えをプログラム全体で調査（census）する（#1411） | gemが注入可能になるとどのレシーバーも対象外になり、調査を行っても約2打数のタッチポイントでgem、実行モード、ダブルを見逃してしまいます。 |

## 影響（Consequences）

- **肯定的な影響（Positive）**
  - ストリームの読み取りが有用な型を得られる。
  - `while gets; $_`を型付けできる（#1415）。
  - ストリームに関する診断が、例外を発生させる書き込みに限定される。
- **受け入れられた否定的な影響（Negative, accepted）**
  - Ruby製リーダーをストリームに差し替え、それでも`$_`を読み取るプログラムは、報告を失うか、差し替えられたリーダーによってのみ誤りとなる報告を受け取る可能性があります。たとえば、`if $stdin.gets; x = $_ ? 1 : "none"; x.upcase; end`は`"none"`アームを削除（elide）します。
  - #1427が設定する前にテストを解析するプロジェクトでは、エントリが追加されるまで`$stdout.string`が報告されます。
- **検証（Verification）**
  - コーパスでは`$_`やガードされたストリームがほとんど読み取られないため、各実装PRにはフィクスチャが含まれます。#1366のフィクスチャには、静かなコントロールとして上記のクラスガードされたシェイプが含まれます。
  - #1415は、現在静かなままである防御的シェイプ（`next if $_.nil?`、`$_ || "default"`、`case $_ when nil`、`unless $_`）のコントロールを追加します。

## 他のADRとの関係

- [`overview.md`](../../type-specification/overview/)の「動作するプログラム」原則を適用しています。[ADR-58](../58-ivar-field-typing/)が宣言に由来する`nil`に対して行っているのと同様です。
- [ADR-17](../17-monkey-patch-pre-evaluation/)を拡張します: グローバル書き込みはパッチとなり、エントリはスコープを獲得します（#1426。これはADR-17を修正します）。フレームワーク知識はAGENTS.mdの「CLIファースト；メタプログラミングのサポートはプラグインAPIに留める」に従ってエンジンから除外され、オンボーディングスキル内に存在します。
- **[ADR-101](../101-optimistic-carrier-branch-elision/)に対するスコープ付きの例外**。
  - ADR-101は、意図的に楽観的な型付けに依拠する確信度の判定を禁じています。WD4のtruthyエッジの`String`はすでに`if` / `unless`の削除を駆動しています。
  - この例外が成立するのは、削除されたアームがプログラムが差し替えられたリーダーで設定されている場合にのみ実行されるためです。一方ADR-101のHashミスは、正しいプログラムの通常の実行で発生します。
  - **再評価トリガー:**コアリーダーのもとで動作するプログラムにおいて、そのような判定に関するフィクスチャまたはユーザー報告があった場合。対応策は、`Inference::OptimisticOrigin`（現在はローカル変数およびivarの読み取り）をグローバル読み取りに拡張し、ナローイングに印を付けることです。
