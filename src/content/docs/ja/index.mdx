Rigorはソースに型注釈を一切書かずに`rigor check`でRubyコードを解析し、型付きレシーバーへの未定義メソッド呼び出し、引数個数の誤り、証明可能なnilデリファレンスなどの実際のバグを報告します。型はすべてコードが実際に生成する値から推論されます。チームに型注釈を書いてもらう必要はありません。

現実的なタイポを、レシーバーの*計算された値*をメッセージに含めて捕まえます:

```ruby
# demo.rb
def slug(title)
  title.downcase.gsub(/\s+/, "-")
end

s = slug("Hello World")
s.lenght
```

```shell-session
$ rigor check demo.rb
demo.rb:7:3: error: undefined method `lenght' for "hello-world"
```

レシーバーに注目してください——`for String`ではなく**`for "hello-world"`**です。Rigorはメソッド呼び出しと`downcase.gsub`の連鎖を通じて値そのものを追跡しました。注釈はどこにもありません。

**2つのコマンドで始められます:**

```sh
mise use ruby@4.0
mise use gem:rigortype
```

## Rigorが見ているものを見る

以下はすべて素のRubyです——型注釈なし、設定なし、明記した場合を除きプラグインもなし。`#=>`コメントは[`rigor annotate`](/ja/manual/05-inspecting-types/)が余白に印字する推論結果で、Rigorでは型はしばしば値そのものです。どの例も[Playground](/playground/)にそのまま貼り付けて試せます。

  kicker="Constant folding"
  title="推論は計算する"
  link="/ja/handbook/02-everyday-types/"
  linkText="日常的に出会う型（ハンドブック）→"
>
  <Fragment slot="prose">
`factorial`にシグネチャはありませんが、メソッドは`Integer`と型付けされます。さらに引数が既知の呼び出し位置では、定数畳み込み（constant folding）が計算全体を値`120`まで畳み込みます。値の確定した再帰は燃料予算の範囲で実際に展開され、予算に収まらない結果は失敗する代わりに静かに`Integer`へ戻ります。
  </Fragment>

```ruby
def factorial(n)        #=> Integer
  (1..n).reduce(1, :*)
end

answer = factorial(5)   #=> 120
```

```ruby
class Stars
  def render(n) = n <= 0 ? "" : "*" + render(n - 1)
end

Stars.new.render(3)     #=> "***"
```
</ShowcasePanel>

<ShowcasePanel
  kicker="Flow-sensitive narrowing"
  title="ナローイングはインスタンス変数まで"
  link="/ja/handbook/03-narrowing/"
  linkText="ナローイング（ハンドブック）→"
>
  <Fragment slot="prose">
ガードはローカル変数だけでなくインスタンス変数もナローイング（narrowing）します——このパターンはRigorが対応するまで、Redmineで6件の偽陽性でした。`raise`で終わる`else`は幻の`nil`を取り除き、`v`は正確に`"a" | "b"`になります。比較・正規表現マッチ・`case/in`パターンも同じように絞り込まれます。
  </Fragment>

```ruby
class Journal
  def save = true
end

class Issue
  def close
    @current_journal = Journal.new if rand < 0.5   #=> Journal?
    if @current_journal
      @current_journal.save    # narrowed to Journal — no possible-nil warning
    end
  end
end
```

```ruby
def classify(kind)
  case kind
  when 1 then v = "a"
  when 2 then v = "b"
  else raise ArgumentError
  end
  v   #=> "a" | "b"
end
```
</ShowcasePanel>

<ShowcasePanel

サイズが既知の配列はタプル（tuple）として扱われ、要素操作は正確なまま保たれます——他のチェッカーがせいぜい`Array[Integer]`を保持する場面です。ハッシュリテラルはシェイプ（shape）になるので、そこへの述語は証明されます。`Data`の値は`with`を通しても完全な値のセマンティクスを保ちます。
  </Fragment>

```ruby
xs = [10, 20, 30]
xs.rotate(2)          #=> [30, 10, 20]
xs.minmax             #=> [10, 30]

config = { host: "example.com", port: 8080 }
config.key?(:host)    #=> true
config.empty?         #=> false
```

```ruby
Point = Data.define(:x, :y)
p = Point.new(1, "two")   #=> Point(x: 1, y: "two")
p.x                       #=> 1
p.with(x: 99).x           #=> 99
```

<ShowcasePanel
  kicker="Blocks"
  title="ブロックは要素ごとに型付けされる"
  link="/ja/handbook/05-methods-and-blocks/"
  linkText="メソッドとブロック（ハンドブック）→"
>
  <Fragment slot="prose">
ブロック本体はタプルの位置ごとに型付けし直されます。キャプチャされたローカル変数への書き込みも健全に追跡されるので、ハッシュを組み立てる定番のイディオムからは——RBS単独なら`untyped`になるところで——ユニオン型（union type）をキーに持つ正確なシェイプが推論されます。
  </Fragment>

```ruby
[1, "two", :three].map { |x| x.to_s }   #=> ["1", "two", "three"]
```

```ruby
table = {}
[1, 2, 3].each { |x| table[x] = x.to_s }
table   #=> Hash[1 | 2 | 3, "1" | "2" | "3"]
```

<ShowcasePanel
  kicker="Sound under mutation"
  title="自ら撤回する精度"
  link="/ja/type-specification/"
  linkText="Rigorが保証すること →"
>
  <Fragment slot="prose">
Rigorが精密なのは、それを証明できる間だけです。ミューテーションは、自分が無効化するフロー上の絞り込みを撤回します——最後の判定が`false`へ畳み込まれ*ない*のは、`clear`の後ではその事実がもう成り立たないからです。偽陽性を出さないことは最悪ケースの静的な読みに優先します。精度は嘘になってはいけません。
  </Fragment>

```ruby
arr = gets.to_s.chars
return if arr.empty?     # arr : non-empty here
arr.clear                # the mutation retracts that fact
puts "emptied" if arr.size == 0   # correctly NOT folded to false
```
</ShowcasePanel>

distance = 100.kilometers

# rigor-activerecord — checked against db/schema.rb
User.find_by(emial: "a@example.com")

## Rigorを導入する

プロジェクトにRigorを組み込み、日々のワークフローに乗せるための導線です。

- [インストール](/ja/manual/01-installation/): mise / asdf / `gem install` / devコンテナ。上の2コマンドが最短経路です。
- [はじめての解析](/ja/handbook/01-getting-started/): 最初の`rigor check`まで。
- [設定](/ja/manual/03-configuration/): 重大度プロファイル、対象範囲、プラグイン。
- [ベースライン](/ja/manual/06-baseline/): 既存コードベースへ段階的に導入する。
- [CI](/ja/manual/11-ci/)・[エディタ統合](/ja/manual/09-editor-integration/): 日常のワークフローへ組み込む。
- [Railsクイックスタート](/ja/manual/14-rails-quickstart/): Railsアプリに最短で乗せる。

## Rigorを評価・調査する

導入を決める前に、Rigorの仕組みと他ツールとの違いを確かめるための導線です。Sorbetがインラインの`sig`を、Steepが手書きのRBSを求めるのに対し、Rigorはどちらも要求しません——型はすべてコードが実際に生成する値から推論されます。

- 他の型チェッカーから来たなら: [Sorbet](/ja/handbook/10-sorbet/)・[Steep](/ja/handbook/appendix-steep/)・[TypeProf](/ja/handbook/appendix-typeprof/)・[TypeScript](/ja/handbook/appendix-typescript/)（mypy・Go・Rustほかの付録もハンドブックにあります）。
- [型仕様の概要](/ja/type-specification/): 何を型とみなし、何を保証するか。注釈なしで推論する設計の核心です。
- [ナローイング](/ja/handbook/03-narrowing/): フローセンシティブな解析が何を実現するか。
- [型理論との接続](/ja/handbook/appendix-type-theory/): 設計を支える理論的背景。
- [互換性](/ja/compatibility/)・[ロードマップ](/ja/roadmap/): 対応Rubyバージョンと今後の方針。
