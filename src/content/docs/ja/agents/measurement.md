タスクが何らかの測定を行うとき（外部プロジェクトに対するエンジンの実行、変更前後の診断の比較、ベンチマーク、またはエンジンが推論した内容の調査）にこれを読んでください。これは`AGENTS.md`が指し示す条件付きの詳細情報です。

これらすべてにおいて繰り返し発生する失敗は、エラーではなく**自信に満ちた誤った答え**です。そのため、以下の各セクションはそれを生み出すメカニズムを中心に記述されています。

## サーベイプロジェクトに対する実行

検証ターゲットは`~/repo/ruby/rigor-survey/`の下に独立したリポジトリとして配置され、**データとして**解析されます ── エンジンがそれらの`Gemfile`に追加されることは決してありません。ターゲットのオンボーディングは[`rigor-project-init`](https://github.com/rigortype/rigor/blob/master/skills/rigor-project-init/SKILL.md)ワークフローに従います。

呼び出しを直感的でないものにしている要因が2つあります。エンジンとそのネイティブの`rbs`/`prism` gemはこのリポジトリのFlakeシェルとバンドルの内部でのみ解決されるため、呼び出しは常に`bundle exec`を経由する必要があります。また、ベースラインのパスと設定の検出はいずれもcwdベースであるため、cwdは**ターゲット**でなければなりません。代わりにRigorリポジトリから実行すると`.rigor-baseline.yml`に`../rigor-survey/...`が書き込まれ、それらのパスは診断ストリームと一致しないため、ベースラインは何も抑制しなくなります。

```sh
nix --extra-experimental-features 'nix-command flakes' develop --command bash -c '
  cd ~/repo/ruby/rigor-survey/<project> &&
  BUNDLE_GEMFILE=<rigor>/Gemfile bundle exec <rigor>/exe/rigor <subcommand>'
```

worktreeから実行する場合は、その`vendor/bundle`が存在するようになった後、3箇所すべてをworktreeに置き換えます。

## コーパスの前後差分（before/after diff）

エンジンの変更に対して「コーパス全体で新規の発火がない」と主張するには、**同一の**エンジンが各ターゲットを2回解析しなければなりません。ベースラインのアームとして`git worktree`チェックアウトを使用してはいけません：そのbundlerはそのworktreeの`Gemfile`パスに対するgemを実体化できないため、すべてのベースライン実行がエラーとなって空のJSONを出力し、誤った`base=0`を報告してしまいます。代わりに作業ツリー内の変更されたファイルをトグルします ── HEADのバージョンと変更されたバージョンを保存し、それぞれですべてのターゲットを実行し、ターゲットごとに診断セットのdiffを取り、全体を`trap restore EXIT`でラップします。

差分のそれぞれをブランチ全体ではなくサブ変更に帰属させます：`git stash -- <files-of-one-sub-change>`を実行し、影響を受けるターゲットのみを再実行します。精度向上変更の下での新規のalways-falseyまたはalways-truthyクラスタは、通常変更自体の欠陥ではなく**上流の古いフォールドファミリー**を意味します ── レバーを疑う前にそのファミリーを見つけるか起票してください。

**スイープが何を検証しないかを把握する**。 `signature_paths`はデフォルトで`nil`であり、これは自動検出を意味します：ターゲットの`sig/`は設定がそれを名指しているかどうかに関わらずロードされるため、`signature_paths: [sig]`を追加しても何も変わりません。そもそも`sig/`を出荷しているサーベイターゲットはほんの一握りであるため、**プロジェクトが宣言した**祖先にゲートされた変更に対して「コーパス全体で新規診断ゼロ」は無意味に等しいと言えます。そのような変更には、その条件を強制する的を絞ったフィクスチャが必要です。

コーパスのフォールドを再現できないスペックはピン留めであり、リグレッションキャッチャーではありません ── 一部のフォールドはターゲットの完全なクラスコンテキストを必要とします。その旨を明記し、失敗し得ないフィクスチャで識別性を偽装するのではなく、正確なコマンドと件数を伴うコーパスの実行をエビデンスとしてください。

## 嘘をつくプローブ

- **実行結果キャッシュ（ADR-45）が未解析の結果を提供する**。プローブは0.2秒で「No diagnostics」と読み取り、バグが修正されたように見えます。判定を行う際は`--no-cache`を使用してください。疑わしいほど高速な実時間はその兆候です。`coverage --protection`にはキャッシュフラグはありませんが、依然としてターゲットの`.rigor/cache`を読み取るため、A/Bプロテクション実行の間でそれをクリアしてください。
- **`rigor type-of`は`rigor check`ではない**。これはプラグインレジストリなしで環境を構築するため（したがってrbs-inlineのソースRBS合成はありません）、単一ファイルスコープインデックスで単一ファイルをパースし（したがってすべてのクロスファイル宣言は`Dynamic[top]`として読み取られます ── `class Foo`が`Dynamic[top]`として返ってくるのがその兆候です）、ディスカバリーがシードしたjoinを見ることができません（したがって両アームが`Dynamic`であるA/Bは何の証明にもなりません）。checkパスの挙動は、`check --no-cache --workers=0`に同一ファイルのポジティブコントロールを加えて帰属させてください。
- **`check`はプロジェクトが決してrequireしていない標準ライブラリのRBSをロードしない**ため、`check`の下で`Time.now`は`Dynamic`である一方、`type-of`はそれを`Time`に解決します。`Time`に基づいて構築されたコントロールは、意図したパスではなく辞退パスを実行してしまいます。
- **リテラルで構築されたコレクションは形状キャリアへとフォールドされる**。 `["a", "b"].map { … }`はタプルであるため、`.first`は形状ディスパッチを通じて解決され、テスト対象のRBSオーバーロードには決して到達しません ── テスト対象のティアがRBSディスパッチである場合は、真正なノミナルソースを使用してください。
- **`BUNDLE_PATH`は相対パスの`vendor/bundle`である**ため、リポジトリの外部にcwdを置いたFlakeコマンドはホストのgemにフォールバックし、ネイティブ拡張の不一致で死亡します。`BUNDLE_GEMFILE`ではこれは修正されません。
- **`rigor check`はロード元のツリーに対するオラクルに過ぎない**。 `exe/rigor`はその隣の`lib/`をロードパスの先頭に置くため、入力したパスがエンジンを選択するのであり、現在のブランチが選択されるのではありません：worktreeから実行された`<main clone>/exe/rigor`は`master`を解析し、`bundle exec`外の裸の`rigor`はホストにインストールされている任意のリリースを実行します。どちらもエラーにならず、そのすべてが同じ`--version`を出力します。worktree内のスペック形式の`Analysis::Runner`ハーネスと、このように解決されたCLIは、ブランチが変更する挙動そのものに関して食い違いを見せ、「ハーネスが発火する場所でCLIは`--no-cache`を指定しても沈黙している」という事象がエンジンやワーカープールの不備として読めてしまいます。それは不備ではありません：同一ツリーの`Runner`、`check --no-cache --workers=0`、および`--workers=2`は同じ診断を報告します（#1029のフィクスチャ、コールドおよびウォーム）。両者のdiffを取る前に、同じ`BUNDLE_GEMFILE`の下で`bundle exec ruby -e 'require "rigor/cli"; puts $LOADED_FEATURES.grep(%r{rigor/cli\.rb$})'`を実行して同一ツリーを共有していることを証明するか、そのブランチのみが応答するコントロール呼び出しを追加してください。

これらすべてをカバーするルール：**プローブが「no」と言ったときは、まずハーネスが「yes」と言えることを証明する**。すべての沈黙プローブに、必ず発火しなければならないコントロールを組み合わせてください。未定義のクラス名の上に構築されたフィクスチャは、「正しく辞退された」と「決して解析されなかった」を区別できません ── どちらも沈黙として読まれます。

## コントロール、ベンチマーク、測定器具

- **測定結果を公開する前に既存の測定値を検索する**。 `docs/notes/`と[`rigor-prior-art`](https://github.com/rigortype/rigor/blob/master/.claude/skills/rigor-prior-art/SKILL.md)スキルは、「これまでにこれを測定したことがあるか？」に回答します。既存の数値との照合こそが、所見とアーティファクト（測定誤差）を区別するものです。差分を説明し得るコミットを名指ししてください。
- **重複しない範囲はコントロールではない**。 `max(off) < min(on)`は、どのような条件が支配的であったにせよ試行が分離したことを示すに過ぎません。真の効果と、バッチ全体で安定していたホストのアーティファクトを区別することはできません。
- **フェーズ分けされたA/Bテストはフェーズと処置を交絡させる**。「一方のアームですべてのプロジェクトを実行し、次に切り替えてすべてを再実行する」という手法は、存在しない45%の性能悪化を報告したことがあります。各試行でアームを交互に切り替え、それぞれに独自のキャッシュディレクトリを持たせて同じコードを再実行したところ、34%の改善が示されました。フェーズ境界と処置はフェーズ分けされた形式において完全に交絡しており、正しい形式のコストはほんのわずかな追加のファイルコピーに過ぎません。
- **コスト測定ハーネスには、精度以上にゼロワークガードが必要である**。設定の相対パス`paths:`は設定ファイル自身のディレクトリに対して解決されるため、tmpdirに書き出されたバリアント設定は何も解析せず、0.18秒で完了して改善を報告してしまいました。両アームが正の、かつ同一のファイル数を解析しなければならず、そうでなければ実行をアボートさせます。
- **実時間はノイズであり、アロケーションこそがシグナルである**。重いプロジェクトを連続して実行すると、後のプロジェクトがスロットリングされます。パフォーマンスの仮説は、決定論的なアロケーション差分と保持された診断数によって判定されます。
- **測定器具を保持する**。 `docs/notes/`のノートには数値が記録されますが、それを生成したハーネス ── ポジティブコントロール、トラップクリアフラグ、クラシファイア ── は記録されません。測定器具を組み込んだビルドを独自のブランチとしてプッシュし、ノートの制限事項セクションにそのブランチ名を記載してください。同じサブシステムに対するフォローアップの問いは例外ではなく通常のことです。
