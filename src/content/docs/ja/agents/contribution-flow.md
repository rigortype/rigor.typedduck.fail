タスクがコミット、プッシュ、PRのオープンやマージ、リリースメタデータの変更、またはチェンジログエントリーの記述を行う場合にのみこれを読んでください。これは`AGENTS.md`が指し示す条件付きの詳細情報です。

## コミットとGitHub Markdown

- Conventional Commitsのプレフィックスを付けず、命令形の文頭大文字（sentence-case）のコミット題名を使用します。コミット本文は約72文字で折り返し、diffではなく理由を説明します。
- GitHubでレンダリングされるMarkdownでは、段落やリスト項目を改行しないでください：GitHubは単一の改行を`<br>`に変換してしまいます。テーブル、見出し、およびコードフェンスはそれぞれ独立した行を保ちます。
- バージョンバンプのコミットには`Bump up version to x.y.z`を使用します。

## ブランチとプルリクエスト

- **小さく、議論の余地のないドキュメント** ── タイポ、1行の修正、`docs/CURRENT_WORK.md`の更新 ── は`master`に直接コミットします。`.md`のみのプッシュはCIがスキップするため、ここでPRを作っても余分なCI実行が発生するだけです。**それより大きな変更** ── 複数項目の改定、新規ドキュメント、構成の再編 ── は他の変更と同様にレビューに値する変更です：ブランチ ＋PRを作成します。非`.md`ファイルに1つでも触れる場合は、規模に関わらずコードとみなされます：ブランチ ＋PRを作成します。どちら側に該当するか確信が持てない場合は、デフォルトでブランチを選択してください ── 直接プッシュするパスは元に戻すコストが高いパスです。
- ブランチ名には、それを作成したツールではなく行われた変更内容に応じた名前を付けます：`claude/`、`codex/`などのツール識別プレフィックスは付けません。すでにPRが開かれているブランチのリネームは安全ではありません（PRが完全に閉じられてしまう可能性があります）。後から直すのではなく、作成時に正しい名前を付けてください。
- 明示的なrefspecを使ってプッシュします：`git push origin HEAD:refs/heads/<branch>`。
- PRはDraftとして開始し、後述の§「プルリクエストのマージ（Landing a pull request）」を通じてマージ（land）します。ユーザーからの停止指示は`gh pr ready --undo`およびマージ禁止を意味します。作成者自身のPRにおいて、作成者自身の承認を待ってはいけません。
- 現在のセッションで開かれた各PRは、マージ可能になったら直ちにマージします。マージが拒否された場合は、直ちに報告してください。バッチ処理やスタックは、ユーザーが一連の変更を裁定しなければならない場合にのみ行います。
- 別のセッションの開かれたPRや未コミットのツリーが進行中の場合：そのオーナーが作業レーンを引き渡すまで、コミット、リベース、プッシュ、マージ、またはその上でのビルドを行ってはいけません。グリーンなゲートはハンドオフではありません。
- バグ報告の修正では、フラグメントを含むすべての修正コミットに`Co-Authored-By: Name <email>`を付与し、チェンジログに`thank you @handle!`を記載して報告者をクレジットします。メールアドレスが不明な場合は質問してください。決して推測してはいけません。
- 各`Fixes #N`はそれぞれ独立した行に配置します。GitHubはカンマ区切りの`Fixes #a, #b, #c`において最初の参照のみをパースし、残りを暗黙のうちに開いたままにしてしまうため、後のセッションがそれらをバックログとして読み取ってしまいます。
- 誤っていると信じる振る舞いを固定するスペックには、その場で`flip this when #N is fixed`というコメントを付けます。これがないと、次の読者はアサーションとエンジンのどちらがバグなのかを再導出しなければならなくなります ── そして、互いに素なファイルに触れる複数のPRのバッチは、あるPRが別のPRがピン留めした内容を修正したときに依然として`master`を赤くしてしまう可能性があり、これは単一のPRのCIでは検知できません。

## プルリクエストのマージ（Landing a pull request）

変更が実装され、`make verify-changed`が通過したら:

1. **プッシュしてDraft PRを開く**。 CIはプッシュ時に開始され、完全なゲートとなります。ブランチではなくheadコミットに対する結果を読み取ります。チェンジログのフラグメントにはPRリンクが必要なため、2回目のプッシュとなります。
2. **CIの後ではなく、同時に敵対的レビュー（adversarial review）を開始する**。両者は独立しており、後のプッシュによってどのみちCIは再実行されます。レビューアーは変更を書いていない新鮮なエージェントであり、ハーネスが提供する最も強力なモデル ── Claude Codeの下ではClaude Opus 5.5、それ以外では高エフォートのClaude Opus 4.6などの同クラスのモデル ── を使用します。いずれも提供しないハーネスでは最高エフォートで最も強力なモデルを使用し、独立したエージェントを開始できないハーネスはPR内でその旨を述べ、Draftのまま残します ── レビューが決して黙ってスキップされてはなりません。レビューアーにはベースコミット、PRとそのissue、および本リポジトリのルール（Flake、読み取り専用の`references/`、ローカルでの完全ゲート禁止、リリースゲート ── サブエージェントはこれらを継承しません）を与えます。深刻度順にランク付けされた所見を求め、それぞれに具体的な失敗シナリオを含め、スコープの拡張は個別にラベル付けさせます。
3. **トリアージ**。正確性の欠陥とテストの不足を修正します。別のラウンドを要求することなく、テキストや細かい指摘（nit）を修正します。PRを肥大化させるのではなく、スコープの拡張はissueとして起票します。却下する所見にはPRコメントでその理由を回答します。*深刻な（severe）*所見の却下はユーザーの判断事項であるため、PRはDraftのまま維持します。深刻度は実装者ではなくレビューアーのランキングです。深刻とはAGENTS.mdの偽陽性ルールが考慮するもの ── 正しいコードに対する診断、誤った推論型、クラッシュ、チェックなしで通過するゲート、または不可逆な誤ったアクションやゲートをスキップするアクション（マージ、プッシュ、公開、スキップされたゲート）へとエージェントを誘導してしまうガイダンス ── を意味します。不正確または不明瞭な文言は深刻ではありません。
4. **今ラウンドの修正が深刻な欠陥に対処した場合にのみ、別のラウンドを実施する**。修正コミットの差分レビューとします: 各以前の所見を再チェックし、修正が導入したリグレッションを探します。2026年9月のレビューログ（167件のPR）では、ラウンド2以降で発見された深刻な欠陥の63%が前回のラウンドの修正によって導入されたものであり、深刻な所見の後のラウンドでは半分の確率で別の欠陥が見つかりました（深刻な所見がないラウンドの後は16%）。
5. **3ラウンドで停止する**。ラウンド3でも依然として深刻な欠陥が見つかる場合、設計は収束していません: 停止し、保守的な解釈を取るか、PRを分割するか、残りを起票するかをユーザーに尋ねます。
6. headコミットでCIがグリーンになり、レビューが停止したら**マージする**（`gh pr ready`、その後に`gh pr merge --merge`）── 着地点が作業開始前に定まっていた場合: `ready-for-agent`のissue、または期待される結果を述べたユーザーのリクエスト。PRが誰も下していない決定を体現している場合は、Draftのまま残し、決定をユーザーに委ねます: `ready-for-human`のissue、設計間のトレードオフ、ADR、issueが未決定のまま残したものを選択する仕様の編集（issueがすでに述べた振る舞いを書き留めることは決定済みです）、または却下した深刻な所見。前者のいずれかによって解決されていないものはすべてDraftのまま維持します。issueを名指しすることは、それが`ready-for-agent`である場合にのみその結果を採用します。独自の着地ルールを持つスキル（`rigor-release-prep`、`rigor-dependency-update`）はそのルールを維持します。ステップ2〜5のレビューは引き続き実行されます。

## リリースの頻度（Release Cadence）

- 唯一のリリースパスは、ユーザーによる明示的な`/rigor-release-prep`の呼び出しです。日付やリリース目標はコンテキストに過ぎません。それ以外の場合は、バージョンメタデータと`[Unreleased]`に触れないでください。
- 明示的な許可なしに`bundle exec rake release`を実行してはいけません：タグ付け、プッシュ、公開が行われます。
- リリース準備のみが、`Rigor::VERSION`、リリース済み`CHANGELOG.md`セクション、`Gemfile.lock`、およびREADMEのステータス行を変更します。バージョンの各コンポーネントは1桁であり、再帰的に繰り上がります（`0.0.9` → `0.1.0`）。
- マージ時に、`changelog.d/<section>/<branch-slug>.md`（`<section>`は`added changed deprecated removed fixed security`のいずれか）にユーザー向けの1文とその完全なPRリンクを配置します。リリース準備がフラグメントを`[Unreleased]`へと統合します。通常の作業でそのセクションを直接編集することはありません。フラグメントのゲートは`spec/docs/changelog_fragments_spec.rb`です。
