タスクがコミット、プッシュ、PRのオープンやマージ、リリースメタデータの変更、またはチェンジログエントリーの記述を行う場合にのみこれを読んでください。これは`AGENTS.md`が指し示す条件付きの詳細情報です。

## コミットとGitHub Markdown

- Conventional Commitsのプレフィックスを付けず、命令形の文頭大文字（sentence-case）のコミット題名を使用します。コミット本文は約72文字で折り返し、diffではなく理由を説明します。
- GitHubでレンダリングされるMarkdownでは、段落やリスト項目を改行しないでください：GitHubは単一の改行を`<br>`に変換してしまいます。テーブル、見出し、およびコードフェンスはそれぞれ独立した行を保ちます。
- バージョンバンプのコミットには`Bump up version to x.y.z`を使用します。
- エージェントが書くissue、PR本文、またはコメントは、AIエージェントが書いたものであることを示す1行の注記で始めます。
- PRまたはissueの本文には、コミットメッセージと同様に、その変更が何をするのか、なぜ行うのかを記述します。PRがどのように組み立てられたか（1つのPRかスタックか、どのツールを使ったか、なぜリベースしたか）を語ってはいけません。

## ブランチとプルリクエスト

- **小さく、議論の余地のないドキュメント** ── タイポ、1行の修正、`docs/CURRENT_WORK.md`の更新 ── は`master`に直接コミットします（スキルがこのパスを取るのはタイポ級の修正のみです; [`skill-authoring.md`](../skill-authoring/) §「`waza`レビュー」を参照）。`.md`またはRubyスイートが一切読み込まないその他のパス（一覧は`ci.yml`の`changes`ジョブにあります）のみを含むプッシュはCIがスキップするため、ここでPRを作っても余分なCI実行が発生するだけです。
  **それより大きな変更** ── 複数項目の改定、新規ドキュメント、構成の再編 ── は他の変更と同様にレビューに値する変更です：ブランチ ＋PRを作成します。スイートが読み込むファイル（`.md`およびその一覧以外のファイル）に1つでも触れる場合は、規模に関わらずコードとみなされます：ブランチ ＋PRを作成します。どちら側に該当するか確信が持てない場合は、デフォルトでブランチを選択してください ── 直接プッシュするパスは元に戻すコストが高いパスです。
- ブランチ名には、それを作成したツールではなく行われた変更内容に応じた名前を付けます：`claude/`、`codex/`などのツール識別プレフィックスは付けません。すでにPRが開かれているブランチのリネームは安全ではありません（PRが完全に閉じられてしまう可能性があります）。後から直すのではなく、作成時に正しい名前を付けてください（復旧方法：§「GitHubとgitの罠」）。
- PRブランチのプッシュには`bin/lane-push`を使用します：最新の`origin/master`を取得してリベースし、その結果に対して`verify-changed`を再実行し、明示的なrefspecとleaseを使ってプッシュします。手動でプッシュする場合は、`-u`は決して使わず、明示的なrefspec `git push origin HEAD:refs/heads/<branch>`を使用します。理由と復旧方法は[`rigor-worktree`](https://github.com/rigortype/rigor/blob/master/.claude/skills/rigor-worktree/SKILL.md)スキルに記載されています。
- PRはDraftとして開始し、後述の§「プルリクエストのマージ（Landing a pull request）」を通じてマージ（land）します。ユーザーからの停止指示は`gh pr ready --undo`およびマージ禁止を意味します。作成者自身のPRにおいて、作成者自身の承認を待ってはいけません。
- 現在のセッションで開かれた各PRは、マージ可能になったら直ちにマージします。マージが拒否された場合は、直ちに報告してください。バッチ処理やスタックは、ユーザーが一連の変更を裁定しなければならない場合にのみ行います。
- 別のセッションの開かれたPRや未コミットのツリーが進行中の場合：そのオーナーが作業レーンを引き渡すまで、コミット、リベース、プッシュ、マージ、またはその上でのビルドを行ってはいけません。グリーンなゲートはハンドオフではありません。
- バグ報告の修正では、フラグメントを含むすべての修正コミットに`Co-Authored-By: Name <email>`を付与し、チェンジログに`thank you @handle!`を記載して報告者をクレジットします。メールアドレスが不明な場合は質問してください。決して推測してはいけません。コミット時にクレジットを付与してください。計画、ブリーフ、またはハンドオフには、修正が報告に由来することやトレーラーを引き継ぐことは記載してもよいですが、クレジットをタスク、チェックリスト項目、または「必須（must）」として列挙してはいけません：それは報告者に対して礼を失する表現になります。AIが起票したissueは、その元となった人間の報告まで遡って追跡してください。
- リポジトリに設定されたidentityでコミットしてください。`--author=`を渡したり、`GIT_AUTHOR_*` / `GIT_COMMITTER_*`を設定したりしてはいけません：2026年9月にサブエージェントのコミットにメンテナーのプライベートアドレスが載ってしまい、書き換えが必要になりました（#628）。レーンブリーフでもこれを繰り返し注意しています。
- 各`Fixes #N`はそれぞれ独立した行に配置します。GitHubはカンマ区切りの`Fixes #a, #b, #c`において最初の参照のみをパースし、残りを暗黙のうちに開いたままにしてしまうため、後のセッションがそれらをバックログとして読み取ってしまいます。
- 誤っていると信じる振る舞いを固定するスペックには、その場で`flip this when #N is fixed`というコメントを付けます。これがないと、次の読者はアサーションとエンジンのどちらがバグなのかを再導出しなければならなくなります ── そして、互いに素なファイルに触れる複数のPRのバッチは、あるPRが別のPRがピン留めした内容を修正したときに依然として`master`を赤くしてしまう可能性があり、これは単一のPRのCIでは検知できません。

## GitHubとgitの罠

これらはすべて静かに失敗します：コマンドは成功し、もっともらしいが誤った結果を報告します。一般的なシェルの罠については[`measurement.md`](../measurement/) §「Shell commands that answer wrong silently」を参照してください。

- **空のPR本文**。空の`$var`で`gh pr edit N --body "$var"`を実行すると、本文が空になります。`--body-file`を渡すか、`[ -n "$var" ]`でガードしてください。
- **CIの判定**。`gh pr checks --watch`は、プッシュによって以前の実行がキャンセルされると「no checks reported」で終了コード1を返し、開始時に存在していたチェックセットのみを監視します。実行の`conclusion`も判定にはなりません：Draft PRの軽量実行は`CI required`がSKIPPEDのままsuccessで完了し、`gh pr ready`の後は2つの実行が同じhead SHAを共有します。head上の最新の`CI required`チェック実行は`bin/ci-required <full-head-sha>`で読み取ります（SUCCESS、FAILURE、SKIPPED、保留中はNULL）。これは`bin/land-pr`が適用するルールです。GitHubのロールアップとマージボックスはSKIPPEDの必須チェックをパス扱いするため、そこではDraftのheadがグリーンに見えてしまいます。実行のジョブを読み取るには、`gh run list --branch <branch>`から`headSha`を一致させてIDを見つけます（`gh run list --commit`には完全なSHAが必要であり、短縮形は`[]`を返します）。`gh run watch <id> --exit-status`はジョブがまだ実行中であっても返ることがあるため、`gh run view <id> --json status`が`completed`になるまでポーリングしてください。マージ後のmaster実行は常にフル実行であるため、その実行の`conclusion`と`headSha`が判定になります。`gh pr view --json merged`というフィールドは存在しません。`state`、`mergedAt`、または`mergeCommit`を読み取ってください。
- **スタックされたPR**。親ブランチを削除するのは、親が`MERGED`になり、そのマージコミットが`origin/master`の祖先になってからにしてください：キューに入った親はまだマージされておらず、キュー内のPRのブランチを削除するとそのPRがクローズされてしまいます。これは以下の両方のスタック形式に当てはまります。スタックには2種類あります。GitHubネイティブのスタック（`gh stack`）はリターゲット不要です：一番下のPRがマージされるとGitHubが次のPRを`master`にリターゲットします（#2194の後の#2200で確認済み）。下のPRがマージされ、GitHubが次のPRを`master`にリターゲットした後にのみ、そのPRで`bin/land-pr`を実行してください。ベースが`master`でないPRは拒否されます。`gh stack merge`は決して使わないでください：レビュー済みSHAと`CI required`のチェックなしにキューに入れてしまいます。スタックされた各PRは`bin/land-pr`でキューに入れてください。
  手動で作ったベースチェーンの場合：ベースが親ブランチのまま子PRをマージすると`MERGED`と報告されますが、そのコミットは親ブランチに入り、`master`には到達せず、`Fixes`も発火しません。親ブランチを削除すると、スタックされた子PRはリターゲットされずにクローズされてしまいます。したがって、親をマージし（`bin/land-pr`はブランチを削除しません）、各子PRを自分でリターゲットし（`gh pr edit <child> --base master`）、上記のルールに従って親ブランチを削除してから、子PRをマージしてください。各マージはPRの状態ではなく`origin/master`に対して証明してください（後述の「マージ後の後片付け」を参照）。
- **消失したhead ref**。開いているPRのheadブランチがリネームまたは削除されると、PRはクローズされ、refが再び存在するまで`gh pr reopen`は失敗します：古いSHAを古い名前でプッシュし直し、再オープンして、スタックされた子PRを`gh pr edit --base master`でリターゲットしてください。
- **スカッシュ**。`git reset --soft origin/master`は決して使わないでください：他のセッションのfetchがそのrefを動かすため、そのコミットはCIがグリーンのまま間にマージされたすべてのPRをリバートしてしまいます。`git merge-base HEAD origin/master`にリセットし、プッシュ前に`git diff --stat origin/master...HEAD`が自分のファイルのみを列挙していることを確認してください。
- **リバートされた変更の再適用**。そのコミットをすでに祖先として含むブランチ上では、リベースは何もリプレイせずリバートの上にfast-forwardします。代わりにチェリーピックしてください。
- **マージ後の後片付け**。ワークツリーやローカルブランチを削除するのは、PRの内容が`origin/master`に入ってからにしてください：`gh pr view N --json state,baseRefName,mergeCommit`がベース`master`で`MERGED`を示し、かつ`git merge-base --is-ancestor <mergeCommit.oid> origin/master`が終了コード0を返す必要があります。これはマージコミット、`--rebase`、`--squash`のどのマージ方式でも同じです。リベースやスカッシュの後はhead SHA自体は祖先にならず、親ブランチにマージされた子PRは`baseRefName`で失敗します。
  削除コマンドを`bin/land-pr`の後ろに繋ぐときは必ず`&&`を使い、`;`は使わないでください（拒否されたマージでも後続が実行されてしまいます）。また、PRがまだキューにある状態で終了コード0を返す`--no-wait`の後ろにも繋がないでください。
- **マージキュー**。PRをキューに入れるには`gh pr merge`ではなく`bin/land-pr N <reviewed-head-sha>`を使用してください：`gh`はこのリポジトリが無効にしているauto-merge API経由でキューに入れようとし、「Auto merge is not allowed」で失敗します。`bin/land-pr`はレビューされたheadのみをキューに入れ（それ以降にプッシュされたコミットは拒否されます。PRから読み戻したSHAではなく、レビューアーが報告したSHAを渡してください）、そのheadの最新の`CI required`チェック実行がパスしていることを確認し（`gh pr ready`の後はDraft実行のSKIPPEDもそのheadに付いているため、フル実行が成功するまで拒否します）、`master`にマージキューがない場合は拒否します（その場合マージ結果をテストするものがなくなるため、停止してユーザーに伝えてください）。その後、PRがマージされる（終了コード0、マージコミットを表示）かキューから外れる（終了コード1）まで1分ごとにポーリングし、そのPRに対する唯一の監視役となります。ネイティブスタック内のPRでは非同期マージREST APIにフォールバックし、`--no-wait`はそのリクエストがまだ保留中のまま返ることがあります。待機はフォアグラウンドコマンドの制限時間を超えることがあるため（キューのバッチ処理に最大5分、CIに約12分かかります）、バックグラウンドで実行してください。すでにキューに入っているPRに対して再実行すると、待機のみを行います。マージされたツリーが、`master`への`pull_request`実行で`CI required`をパスしたツリーと一致する場合（このリポジトリのブランチからの署名付き`Tested tree`アテステーションによるもの。通常はheadがすでに`master`を含んでいるため）、キュー実行はその結果を再利用して約1分で完了します（[ADR-123](../../adr/123-merge-queue-and-post-hoc-approval/)、2026-10-19改定）。そうでない場合はフルCIが実行されます。キューから落とされたPRはキュー内のPRとまったく同じ`OPEN`状態のままになります：`gh run list --event merge_group`で失敗した実行を確認するか、それを外した新しいプッシュや手動削除を確認し、ブランチ上で修正してください。`gh pr merge --admin`は決して使わないでください：キューとそのチェックをスキップしてしまいます。
- **プッシュに対するマージ可能性の遅延**。`git merge-base --is-ancestor origin/master origin/<branch>`によってブランチがmasterを含んでいることが確認できている場合、「Head branch is out of date」という拒否は自然に解消します。`master`を再度マージするのではなく、バックオフしてリトライしてください。
- **メインクローンは共有されている**。メインクローン内の未コミット編集はすべてのブランチ切り替えに追随し、次の`git add -A`で巻き込まれます。並列ワーカーはそれぞれ専用のワークツリーを使用してください。

## プルリクエストのマージ（Landing a pull request）

変更が実装され、`make verify-changed`が通過したら：

1. **プッシュしてDraft PRを開く**。Draft PR上のCIは軽量ゲートです：コードPRでは変更検出と`lint`、非コードPRでは`docs-check`が実行されます。重いジョブはすべてスキップされ、`CI required`はSKIPPEDで完了するため、Draftのheadが`bin/land-pr`にとってグリーンになることはありません（GitHubのマージボックスはSKIPPEDチェックをパス扱いしますが、それを通じてマージされることはありません：キューは常にフルで実行されます）。フルCIは`gh pr ready`時（ステップ6）、その後のready状態のPRへのプッシュごと、およびマージキュー内で実行されます。ブランチではなくheadコミットに対する結果を読み取ります（方法：§「GitHubとgitの罠」）。チェンジログのフラグメントにはPRリンクが必要なため、2回目のプッシュとなります。
2. **CIの後ではなく、同時に敵対的レビュー（adversarial review）を開始する**。両者は独立しています。レビューは軽量実行とローカルの`make verify-changed`を読み取り、`gh pr ready`時のフル実行とマージキューでのマージ結果に対する実行が着地する内容を検査します。レビューアーは変更を書いていない新鮮なエージェントであり、ハーネスが提供する最も強力なモデル ── Claude Codeの下ではClaude Opus 5.5、それ以外では高エフォートの同クラスのモデル（Piハーネスのco-primaryペアは[ADR-115](../../adr/115-pi-multi-model-harness/)を参照）── を使用します。いずれも提供しないハーネスでは最高エフォートで最も強力なモデルを使用し、独立したエージェントを開始できないハーネスはPR内でその旨を述べ、Draftのまま残します ── レビューが決して黙ってスキップされてはなりません。レビューアーにはベースコミット、PRとそのissue、および本リポジトリのルール（Flake、読み取り専用の`references/`、ローカルでの完全ゲート禁止、リリースゲート ── サブエージェントはこれらを継承しません）を与えます。深刻度順にランク付けされた所見を求め、それぞれに具体的な失敗シナリオを含め、スコープの拡張は個別にラベル付けさせます。1つのPRであってもバッチであっても、すべてのレビューアーブリーフでは、その契約を保持している[`rigor-reviewer`](https://github.com/rigortype/rigor/blob/master/.claude/skills/rigor-reviewer/SKILL.md)スキルをロードするようエージェントに指示します。
   その§ Reportが、どのハーネスでレビューする場合でも唯一のレポート形式です：Piハーネス（[`contracts/README.md`](https://github.com/rigortype/rigor/blob/master/agents/pi-harness/contracts/README.md) § Reviewer）およびtaktのadversary（[`adversarial-review.md`](https://github.com/rigortype/rigor/blob/master/.takt/facets/instructions/adversarial-review.md)）もそれを返した上で独自のフィールドを後ろに追加するため、どこで実行されたレビューでもこのステップを満たし、マージする側が同じフィールドを読み取れます。その形式になっていないレビュー ── 深刻度なし、所見ごとの再現手順なし ── はまだ誰によってもトリアージされておらず、ステップ3を適用できません：PRを再レビューするのではなく、その形式でのレポートを要求してください。
   スキルを変更するPRは、同時に[`skill-authoring.md`](../skill-authoring/)にある`waza`レビューも実行します。その所見はこのトリアージに合流します。
3. **トリアージ**。エンジンを変更するPRでは、`gh pr ready`が開始するフル実行（Draftの軽量実行ではどちらもスキップされます）における「Engine allocations（advisory）」ジョブのサマリーと、「Acceptance gates」ジョブのtype_ofシャドウセクション（ADR-129ステージ3）も確認してください：どちらも警告を発してもグリーンのままであるため、`gh pr checks`には表示されません。シャドウのFAILは失敗するスペックと同様の所見です。警告は所見の一種であり、他と同様に修正するかPRコメントで理由を回答してください。`pr_allocations_pct`（`bench/thresholds.yml`）を上回る増加は、それが削減されるかマージするセッションが承認キューエントリーで受け入れるまでPRを保留にします。リリースゲートの許容範囲を超える増加を受け入れることは重大な決定です（§「決定と承認キュー」）。正確性の欠陥とテストの不足を修正します。別のラウンドを要求することなく、テキストや細かい指摘（nit）を修正します。PRを肥大化させるのではなく、スコープの拡張はissueとして起票します。却下する所見にはPRコメントでその理由を回答します。*深刻な（severe）*所見の却下は重大な決定（§「決定と承認キュー」）であるため、PRはDraftのまま維持します。深刻度は実装者ではなくレビューアーのランキングです。深刻とはAGENTS.mdの偽陽性ルールが考慮するもの ── 正しいコードに対する診断、誤った推論型、クラッシュ、チェックなしで通過するゲート、または不可逆な誤ったアクションやゲートをスキップするアクション（マージ、プッシュ、公開、スキップされたゲート）へとエージェントを誘導してしまうガイダンス ── を意味します。不正確または不明瞭な文言は深刻ではありません。

   **誰も調整役をしていない場合**。無人ループ ── takt、Piハーネス、スクリプト化されたハートビート ── が独力でPRをマージしてよいのは、ステップ6のすべての条件が満たされ（スキルPR上の`waza`コメントを含む）、かつこのステップで判断を求められない場合のみです：ステップ2が要求するすべてのレビューがマージ対象のhead上で`Severe remaining: no`を報告し、未解決の判定を残していないこと（PiハーネスではADR-115 WD6が指定するco-primaryペアのそれぞれ、末尾が`Approved` / `Needs fix`のレポートを返すハーネスでは`Approved`を返していること）、そのラウンドの修正が振る舞いではなく文言またはスペックのみを変更したものであること、およびadvisoryジョブが警告を発していないこと。レポートに深刻な所見が含まれていなくても`Needs fix`を返すことがあり、ハーネス契約はそれをレビューアーの判断に委ねています。未解決の`Needs fix`はレビューが停止していないことを意味するため、ループはそれを無視してマージするのではなく待機（park）します。
   それ以外のすべては、レビューレポートをPRコメントとして投稿した状態でDraftのまま停止し、これが引き継ぎとなります：深刻な所見、ループが却下しようとする所見、アロケーション保留、または§「決定と承認キュー」が対象とするあらゆる決定 ── 重大なもの、およびまだエントリーが書かれていない重大でないもの。待機することのコストは待ち時間だけですが、代替案のコストは誤ったマージ、または誰も対処できないレビューです。ループが決して行わないことが3つあります：どのレビューも読んでいないPRをreadyにすること（CIランナーがスループットを律速しているため、失敗するready PRはフル実行1回分のコストになります ── [`.takt/README.md`](https://github.com/rigortype/rigor/blob/master/.takt/README.md)）、ある所見が深刻ではないと独断で決めること、そしてより綺麗な答えを得るために未変更のheadを再レビューすること。深刻な所見は修正とそれを確認する差分レビューによって解消されるのであり、同じheadへの別レビューによって解消されることは決してありません：レビューアーの結果は実行ごとにばらつくためステップ2でペアを求めることがあり、クリーンなレポートが返るまで再抽選するループはゲートを通過したのではなくスキップしたことになります。
4. **今ラウンドの修正が深刻な欠陥に対処したか、振る舞いを変更した場合にのみ、別のラウンドを実施する**。修正コミットの差分レビューとします：各以前の所見を再チェックし、修正が導入したリグレッションを探します。2026年9月のレビューログ（167件のPR）では、ラウンド2以降で発見された深刻な欠陥の63%が前回のラウンドの修正によって導入されたものであり、深刻な所見の後のラウンドでは半分の確率で別の欠陥が見つかりました（深刻な所見がないラウンドの後は16%）。文言やスペックではなく振る舞いを変更する非深刻な所見の修正にも同じ差分レビューを行います。これは3ラウンドの上限にカウントされます。v0.4.3バッチでは、これら（#1884、#1890、#1894）のそれぞれでマージ前に修正すべきさらなるギャップが見つかりました。
5. **3ラウンドで停止する**。ラウンド3でも依然として深刻な欠陥が見つかる場合、まず設計が収束しているかを問います。いずれかの深刻な所見が以前のラウンドで修正したギャップの言い換えに過ぎない場合、または保守的な修正が存在しない場合は、PRをDraftのまま保持します：保守的な解釈を取るか、PRを分割するか、残りを起票するかをユーザーが選択します。そうでなく、すべての深刻な所見が限定的であり、保守的な修正 ── 述べることを減らすかチェックを増やす方向にのみ動き（エンジンでは診断を落とすか推論型を`Dynamic`側へ広げ、ゲートではチェックを増やし、ガイダンスではより多く保留・確認する）、それ自体とそのスペックおよびスペックテキスト以外の何ものも変更しない修正 ── が存在する場合、それらの修正を適用し、修正コミットに限定した差分レビューを1回実行して、各修正が保守的であることの確認をレビューアーに求めます。深刻な所見が何も見つからず、すべての修正が保守的であると確認された場合はステップ6に従ってマージします。そうでなければユーザーのためにPRをDraftのまま残します。そのチェックからの非深刻な所見は文言またはスペックのみで修正し、振る舞いを変えるものはissueとして起票します。ラウンド3の後に行われるその他の修正は、追加のラウンドなしでマージします。
6. **キューを通じてマージする**（`gh pr ready`を実行し、フル実行の`CI required`がパスしたら`bin/land-pr N <reviewed-head-sha>`を実行する。§「GitHubとgitの罠」を参照）。これはheadコミットで軽量実行がグリーンになり、レビューが停止し、かつ着地点が定まった後に行います：着地点が定まっているとは、`ready-for-agent`のissue、期待される結果を述べたユーザーのリクエスト、またはPRが体現するすべての決定が後述の§「決定と承認キュー」の下で下されていることを指します。キューに入れるためにPRが最新の`master`を含んでいる必要はありません。キューはマージ結果をテストします。`gh pr ready`は最後にレビューされた修正プッシュの後にのみ実行してください：これによりフルCIが開始され、その実行がCIでスペックを最初に実行する場となるため、その後にフルCIが失敗すると修正プッシュと別のフル実行が必要になります。一度readyにしたPRはreadyのままとなり、`gh pr ready --undo`はすでに進行中のフル実行をキャンセルしません。
   `agents/pi-harness/scripts/land-when-green.sh`はPRをreadyにし、その実行を待ち、ステップ3のadvisoryジョブが警告なしで完了した場合にのみ`bin/land-pr`を実行します。いずれかが警告を出したか判定がない場合は、実行のリンクを出力して終了コード6で停止します：サマリーを読み、警告への回答または受け入れが済んでから手動でマージしてください。再プッシュ（`bin/lane-push`）は、CIが開始されずキューに入れない`CONFLICTING`状態のとき、またはキューから落とされたときにのみ行います。ステップ3のアロケーションルールによって保留されたPR（フル実行、すなわち`gh pr ready`後に読み取られます）は、その保留が解消されるまでキューに入れません。スキルを変更するPRには`waza`レビューコメントも必要です。それが投稿されるまでDraftのまま維持します。重大な決定を含むPRは、ユーザーがそれを下すまでDraftのまま維持します。独自の着地ルールを持つスキル（`rigor-release-prep`、`rigor-dependency-update`）はそのルールを維持します：作成直後にPRをreadyにするため待機するCIはフル実行となり、ユーザーの明示的なゴーサインがキュー投入をゲートします（`bin/land-pr`は`RIGOR_RELEASE_APPROVED=1`なしでは`release/**` PRを拒否します）。ステップ2〜5のレビューは引き続き実行されます。

## 決定と承認キュー

作業では、まだ誰も下していない決定 ── ゲート行、issueが未決定のまま残した解釈、issueの一部を先送りすること ── が日常的に必要になります。境界線より下の決定は先例に従って自分で行い、マージし、それぞれをユーザーが追認できるように記録します（リリース時、または長いリリース期間でキューが溜まった場合はバッチで先に追認します。[`approval-queue.d/`](https://github.com/rigortype/rigor/blob/master/approval-queue.d/README.md)を参照）。マージ前に停止して確認するのは重大な決定のみです。この根拠は[ADR-123](../../adr/123-merge-queue-and-post-hoc-approval/)にあります。

**重大（Serious） ── 先にユーザーに尋ねること。回答があるまでPRはDraftのまま維持します：**

- リリース、バージョンバンプ、公開、または`rake release`が行うあらゆること;
- ユーザーが挙動の変化を目の当たりにするデフォルト値：デフォルトでのルールのオン/オフ、デフォルトの深刻度、デフォルトのフラグや設定値（#120）;
- パブリックコントラクトに対する破壊的変更：CLIオプション、終了コードや出力形式、設定キー、プラグインAPI;
- 新しいキャッシュ形式、ネイティブコード、または新しいランタイム依存関係（ADR-31）;
- 新しいADRの決定、またはAcceptedなADRを覆す改定;
- リリースゲートの計測（`bench/baseline.json`に対する`make bench-perf`）がその許容範囲を超えることになる場合に、`pr_allocations_pct`（`bench/thresholds.yml`）を上回るPR単位のアロケーション増加を受け入れること;
- チェックを減らすゲート：チェックの削除や緩和、レビューのスキップ、既存のissueなしでの`--no-verify`、または同じ種類の先例が存在しない箇所での許可リスト行や残余ピン（residue pin）の引き上げ（同じゲートファイル、同じ種類の理由について）;
- このセクション自体、承認キューのゲート（`spec/docs/approval_queue_spec.rb`およびそのCIステップ）、または`rigor-release-prep`における追認ステップ;
- リポジトリ、organization、またはCIの設定：必須チェック、ルールセット、シークレット、パーミッション;
- 深刻なレビュー所見の却下、またはラウンド3の後もなお収束していない設計（§「プルリクエストのマージ（Landing a pull request）」ステップ3および5）;
- `ready-for-human`のissue、またはユーザーが自分に持ち帰るよう指示したあらゆること。

**それ以外のすべて ── 決定し、マージし、記録する**。最も近い先例に従います：追認された決定（`Ratify approval queue entries` PRまたはリリースコミットによってエントリーが削除された後の、そのエントリーの由来となったマージ済みPR）、ユーザーがその決定を承認したマージ済みPR、またはADR。まだキュー内で待機しているエントリーは先例になりません。当てはまるものがなく、その決定が重大でない場合は、自分自身の推奨案を採用し、それが先例を作ることを明記します。`gate-row`は決して先例を作りません。なぜなら先例のないゲート行は重大だからです。そして同じPR内の[`approval-queue.d/`](https://github.com/rigortype/rigor/blob/master/approval-queue.d/README.md)の下にエントリーを追加します：なぜ決定が必要だったか、選択肢とそのトレードオフ、先例、および元に戻す方法を書きます。その場にいなかった読者のために書いてください。報告の中でもその決定についてユーザーに伝えてください。セッションが終わった後に残るのはそのエントリーです。健全性や精度を譲歩し、後で解除することを意図した決定には、`known-limitation` issueも起票します（[`triage-labels.md`](../triage-labels/) §「Known limitations」）：エントリーは追認時に削除され、再検討を担うのはそのissueだからです。レーンの場合は、コーディネーターがレーンの`Known limits`（[`parallel-lanes.md`](../parallel-lanes/)）から、制限ごとに1つ起票またはラベル付けします。

より厳しくするだけの決定（残余ピンの引き下げ、より多くチェックするようになったチェック）や、`ready-for-agent` issueがすでに述べていた結果を書き留めるだけの決定には、エントリーは不要です。

**待つべきだったのにマージされてしまった決定**は、リバートではなく記録上で修復されますが、それは次の2つのケースに限られ、それ以外にはありません：エントリーのない重大でない決定、またはまだ追認されていない先例を挙げたエントリーを持つ決定。変更自体は残り、そのエントリーにはプロセスが見落とした点と検証された内容を記載し、メンテナーが追認時に判断します。すでに公開済みのものやこのリポジトリの履歴の外にあるものはこの方法では保持されず、意図的にマージすることは一切認められません：重大な決定は上記の通り待機し、ステップ3の無人ループはそれを待機（park）させます。このルール、その境界、および事前に待つ基準が変わらない理由は、[ADR-123](../../adr/123-merge-queue-and-post-hoc-approval/)の2026-11-14改定に記述されています。

## リリースの頻度（Release Cadence）

- 唯一のリリースパスは、ユーザーによる明示的な`/rigor-release-prep`の呼び出しです。日付やリリース目標はコンテキストに過ぎません。それ以外の場合は、バージョンメタデータと`[Unreleased]`に触れず、最後にカットまで`/rigor-release-prep`を1回実行するだけであることを伝えて終えてください。このゲートはリズムのために存在します：マージされたバッチごとにバージョンバンプを行っていた頃（v0.0.5からv0.0.8）は、リリース間隔が狭すぎて各リリースがユーザーに見える価値を持てませんでした。依頼されていないのにリリースをカットすること（「11時までにリリース」と読み取って行った0.3.8）は、プロセスのミスではなく信頼の失墜です。
- 明示的な許可なしに`bundle exec rake release`を実行してはいけません：タグ付け、プッシュ、公開が行われます。
- リリースは追認された決定のみを出荷します：`/rigor-release-prep`は最初に[`approval-queue.d/`](https://github.com/rigortype/rigor/blob/master/approval-queue.d/README.md)を報告し、README以外のものが何も残らなくなるまでリリースは待機します。
- リリース準備のみが、`Rigor::VERSION`、リリース済み`CHANGELOG.md`セクション、`Gemfile.lock`、およびREADMEのステータス行を変更します。バージョンの各コンポーネントは1桁であり、再帰的に繰り上がります（`0.0.9` → `0.1.0`）。
- マージ時に、`changelog.d/<section>/<branch-slug>.md`（`<section>`は`added changed deprecated removed fixed security`のいずれか）にユーザー向けの1文とその完全なPRリンクを配置します。リリース準備がフラグメントを`[Unreleased]`へと統合します。通常の作業でそのセクションを直接編集することはありません。フラグメントのゲートは`spec/docs/changelog_fragments_spec.rb`です。
