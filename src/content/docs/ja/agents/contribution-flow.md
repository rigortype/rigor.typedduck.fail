タスクがコミット、プッシュ、PRのオープンやマージ、リリースメタデータの変更、またはチェンジログエントリーの記述を行う場合にのみこれを読んでください。これは`AGENTS.md`が指し示す条件付きの詳細情報です。

## コミットとGitHub Markdown

- Conventional Commitsのプレフィックスを付けず、命令形の文頭大文字（sentence-case）のコミット題名を使用します。コミット本文は約72文字で折り返し、diffではなく理由を説明します。
- GitHubでレンダリングされるMarkdownでは、段落やリスト項目を改行しないでください：GitHubは単一の改行を`<br>`に変換してしまいます。テーブル、見出し、およびコードフェンスはそれぞれ独立した行を保ちます。
- バージョンバンプのコミットには`Bump up version to x.y.z`を使用します。

## ブランチとプルリクエスト

- **小さく、議論の余地のないドキュメント** ── タイポ、1行の修正、`docs/CURRENT_WORK.md`の更新 ── は`master`に直接コミットします。`.md`のみのプッシュはCIがスキップするため、ここでPRを作っても余分なCI実行が発生するだけです。**それより大きな変更** ── 複数項目の改定、新規ドキュメント、構成の再編 ── は他の変更と同様にレビューに値する変更です：ブランチ ＋PRを作成します。非`.md`ファイルに1つでも触れる場合は、規模に関わらずコードとみなされます：ブランチ ＋PRを作成します。どちら側に該当するか確信が持てない場合は、デフォルトでブランチを選択してください ── 直接プッシュするパスは元に戻すコストが高いパスです。
- ブランチ名には、それを作成したツールではなく行われた変更内容に応じた名前を付けます：`claude/`、`codex/`などのツール識別プレフィックスは付けません。すでにPRが開かれているブランチのリネームは安全ではありません（PRが完全に閉じられてしまう可能性があります）。後から直すのではなく、作成時に正しい名前を付けてください。
- 明示的なrefspecを使ってプッシュします：`git push origin HEAD:refs/heads/<branch>`。
- PRはDraftとして開始し、ユーザーがマージしてよいと明示的に指示し、CIがグリーンであり、かつ保留中の停止指示がない状態になるまでDraftのまま維持します。停止指示は`gh pr ready --undo`を意味します。作成者自身のPRにおいて、作成者自身の承認を待ってはいけません。
- 現在の自律セッションで開かれ、監査済みかつグリーンのPRは、マージ可能になったら直ちにマージ（land）します。マージが拒否された場合は、直ちに報告してください。バッチ処理やスタックは、ユーザーが一連の変更を裁定しなければならない場合にのみ行います。
- 別のセッションの開かれたPRや未コミットのツリーが進行中の場合：そのオーナーが作業レーンを引き渡すまで、コミット、リベース、プッシュ、マージ、またはその上でのビルドを行ってはいけません。グリーンなゲートはハンドオフではありません。
- バグ報告の修正では、フラグメントを含むすべての修正コミットに`Co-Authored-By: Name <email>`を付与し、チェンジログに`thank you @handle!`を記載して報告者をクレジットします。メールアドレスが不明な場合は質問してください。決して推測してはいけません。
- 各`Fixes #N`はそれぞれ独立した行に配置します。GitHubはカンマ区切りの`Fixes #a, #b, #c`において最初の参照のみをパースし、残りを暗黙のうちに開いたままにしてしまうため、後のセッションがそれらをバックログとして読み取ってしまいます。
- 誤っていると信じる振る舞いを固定するスペックには、その場で`flip this when #N is fixed`というコメントを付けます。これがないと、次の読者はアサーションとエンジンのどちらがバグなのかを再導出しなければならなくなります ── そして、互いに素なファイルに触れる複数のPRのバッチは、あるPRが別のPRがピン留めした内容を修正したときに依然として`master`を赤くしてしまう可能性があり、これは単一のPRのCIでは検知できません。

## リリースの頻度（Release Cadence）

- 唯一のリリースパスは、ユーザーによる明示的な`/rigor-release-prep`の呼び出しです。日付やリリース目標はコンテキストに過ぎません。それ以外の場合は、バージョンメタデータと`[Unreleased]`に触れないでください。
- 明示的な許可なしに`bundle exec rake release`を実行してはいけません：タグ付け、プッシュ、公開が行われます。
- リリース準備のみが、`Rigor::VERSION`、リリース済み`CHANGELOG.md`セクション、`Gemfile.lock`、およびREADMEのステータス行を変更します。バージョンの各コンポーネントは1桁であり、再帰的に繰り上がります（`0.0.9` → `0.1.0`）。
- マージ時に、`changelog.d/<section>/<branch-slug>.md`（`<section>`は`added changed deprecated removed fixed security`のいずれか）にユーザー向けの1文とその完全なPRリンクを配置します。リリース準備がフラグメントを`[Unreleased]`へと統合します。通常の作業でそのセクションを直接編集することはありません。フラグメントのゲートは`spec/docs/changelog_fragments_spec.rb`です。
