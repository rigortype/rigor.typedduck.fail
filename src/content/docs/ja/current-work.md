## 数字より価値のある2つの発見

**より多くの式に型を付ける畳み込みは、既存の間違った型を診断ルールから到達可能にする**。 #503のプロトタイピングは4件の診断を生んだ;どれもそれが原因ではなかった。4件すべてが実在のミューテーションのシェイプの偽陽性（#501、#506）であり、ゲートもコーパスもそれを見つけていなかった。診断の件数を精度の比と同じ表に置くこと、そして精度のレバーが自分の起こしていないバグによってゲートされることを予期すること。

**このリポジトリ自身の`lib`で計測されたレバーは、Rigorが対象とするプログラムではなく型検査器に対して較正されている**。コーパスはこのセッション自身の順位付けを2度ひっくり返した: #508はここでは+2.27ptの価値があるが、2つのアプリケーションでは+0.81 / +0.85ptであり、一方の#505——計測の訂正として起票された——はそちらで+3.89 / +5.97ptを運ぶ。そして原因の構成比はまったく別の形をしている: `inferred_return_untyped`は`lib`の保護されていないサイトの56.6%を占めるが、アプリケーションでは27〜30%であり、そこでは`unsupported_syntax`が29.7% / 44.0%に対してここでは7.2%である。**何かを順位付けする前にコーパスで検証すること**。

## いまも縛る落とし穴

- **ゲートの終了ステータスはそれ自身の呼び出しで読むこと**。 `make docs-check | tail`はtailの0を返す。マージ解決を含む**最後の**編集の後にゲートを走らせること——`###`のセクションをそれぞれ開く2つのブランチは黙って重複した見出しへマージされ、changelogの適合性のスペックだけがその網である。
- **CLIに出力形式を追加するときは、速度だけでなく契約を検証すること**。 #515はレビューを1周増やして出荷された。列挙がPrismの0始まりの列を印字していた（コマンドの契約は1始まりであり、しかもスペックが間違った値を固定していた）、`group_by(&:file)`が結果を引数の順序から並べ替えていた、厳密な位置のクエリと行のクエリを混ぜると1つのブロックとして描画されていた、そして40行の上限が黙って切り詰めていた、からだ。速さを計測する前に、自分の新しい形式をユーザーがそうするように走らせること。
- **フェーズに分けたA/Bはタイミングの対照ではない**;`tool/perfbench/ab_probe_interleaved.sh`がそのテンプレートだ。決定的なカウント（診断の集合、調査）は対象外——どちらを持っているのかを述べること。
- **設定の相対的な`paths:`は設定**ファイル**のディレクトリに対して解決される**。そして`effects.envelopes[].match:`のglobは相対でなければならない——どちらも計測を空虚にグリーンにする。
- **サーベイのプロジェクトに対して走らせる**には、cwdを対象にすること**かつ**`BUNDLE_GEMFILE`をこのリポジトリのGemfileにすることが要る;後者がないと対象自身のbundleをロードしてネイティブ拡張のクラッシュに遭う。
- **エンジンを動かすマージのあとは、`check`の実行で診断スロットを再プライムすること**——`unused`はそれを決して書かないので、次の「ウォームなcheck」の計測が黙ってコールドのものになる。
