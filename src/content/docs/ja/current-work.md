## このアークで学んだ、コミットには残っていないこと

- **コンシューマーを作る前に、それが最適化する対象を取り除くことでヘッドルームを計測すること**。
  B2.2のリセットを完全に無効化するのは#389がゲートにしうるあらゆる基準の上界であり、コストは
  対象ごとに2ランだった。809のリセットサイトにわたって取り除いた診断はゼロで、偽陽性を1つ追加した。
  歩留まりのパーセンテージではこれは見つからなかっただろう: joinはサイトの3〜5%がスキップ可能だと
  言っており、それは何もないというよりは小さな勝利のように読める。
- **受け入れ基準は再現不能でありうる。フィクスチャを書くことがそれを知る方法だ**。 #389は
  `return unless @user; audit!; @user.name`から`call.possible-nil-receiver`を取り除くと約束した。
  その形は1つも報告したことがない: ルールはローカル変数のレシーバーでのみ発火する
  （`check_rules.rb:1271`）。フィクスチャは10分かかった;スライスなら数日かかっていただろう。
- **どちらの極端にもコントロールが要る**。診断の変化ゼロは壊れたトグルの形なので、そのゼロが何かを
  意味する前に、センサスはまさにそのサイトでリセットが発火していることを示し、トグルは推論された型を
  動かさなければならなかった（`String?` → `String`）。Ractorの縮退も同じだ: 修正は、ワーカーを
  ポイズンして、10分を超えてハングしていたランが数秒で終わるのを見ることで証明された。
- **CIが決して選ばないバックエンドは腐るバックエンドだ**。`runner_pool_spec.rb`は`make verify`で
  走るが、*fork*バックエンド上でだ —— `cache_store`なしの例だけがRactorをピン留めし、それは何かを
  spawnする前にreturnする。Ractorパスはすべてのゲートが緑のまましばらく死んでいた。specファイルの
  名前と行使するバックエンドが食い違うとき、決めるのは名前ではない。
- **ハングはクラッシュより悪く、死んだコードの中でも修正すべきだ**。Ractorコーディネーターの
  `while done_count < pool.size`にはワーカーの死を観測する手段がなかった。`Ractor#monitor`は同じ
  メールボックスに`:exited` / `:aborted`を投函するので、`:done`ではなく終了でループを境界付けるのは
  4行の変更で、際限のないハングを縮退に変える。
- **`gh issue close`と連結された`gh`コマンドはこのハーネスでは自動承認されない**;コメントと
  `gh pr create` / `merge`はされる。証拠を投稿し、クローズはオーナーに委ねること。
