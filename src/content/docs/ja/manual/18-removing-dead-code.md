この章は、古いコードベースを渡されて「何を捨てられるか」を問われた人のためのものです。`rigor unused`は「この1,500個のクラスのうちどれが死んでいるのか？」を、具体的な問いの有限のリストへと変えます。その問いに答えることはしません。

コマンドリファレンス——すべてのフラグ、すべての出力セクション——は[CLIリファレンス](../02-cli-reference/#rigor-unused)にあります。この章はその周りのワークフローです。

**始める前に**、動作する`rigor check`のセットアップが必要です: `paths:`を持つ設定ファイルと、あなたのフレームワーク向けのプラグインが有効化されていること。[設定](../03-configuration/)と[プラグインの利用](../07-plugins/)を参照してください。`rigor unused`は同じ設定を読み、同じ`plugins:`をロードします。そしてプラグインの半分はオプションではありません——[ルート](#ルートがレバーである)の節が、`rigor-rails-routes`なしのRailsアプリがほとんどノイズのレポートを生む理由を説明します。

## 何が分かり、何が分からないか

`rigor unused`はちょうど1つの問いに答えます: **到達可能なコードが1つも名指ししていないプロジェクトのクラスとモジュールはどれか？** これは「何が死んでいるか」と同じ問いではなく、両者の隔たりこそがこの章の主題のすべてです。

ある中規模のRailsアプリケーションで、生き残ったすべての候補をリポジトリ全体に対して手で確認したところ、**57件中4件が本当に死んでいました**。残りの53件は、この解析には見えない手段で到達される生きたコードでした。

この比率は定数ではなく桁の目安として扱ってください。これは1つのコードベースの1回の裁定であり、あなたの比率は、あなたのフレームワークのどれだけがプラグインでカバーされているかに依存します。一般化できるのはその形です: ほとんどの行は生きたコードになるので、この出力は作業リストではなくレビューキューです。それが、これを`rigor check`の診断ではなく独立したコマンドとして出荷する理由でもあります——[ADR-102][adr-102]を参照。

作業を計画する前に知っておく価値のある限界が3つあります:

- **名指しは呼び出しではない**。定数が1回名指しされ、すべてのメソッドが死んでいるクラスは、完全に到達可能として数えられます。これは定数レベルのレポートです;未使用の*メソッド*はまったく報告されません。
- **未知の量だけ過少報告する**。過剰に主張するルートのソースは、行を黙って取り除きます——[ドリフトの監視](#キャンペーンとして走らせる)を参照。再現率の数字はなく、レポートが一度も見せなかったクラスを裁定する以外に、それを計測する方法もありません。
- **値定数**（`TIMEOUT = 30`）は完全に省略されます;ファイルをまたいで解決されないので、そのすべてが偽の行になるからです。**再オープンされたgemまたは標準ライブラリのクラス**は決して候補になりません——イニシャライザで`String`を再オープンすることはそれをあなたのプロジェクトで宣言しますが、それをunusedと呼ぶのはあなたの権利ではありません。

## 最初の実行

```sh
rigor unused
```

これは毎回プロジェクト全体を解析します;インクリメンタルモードはありません。部分集合に対して計算された到達可能性は健全でないからです。フルの`rigor check`とおおよそ同じコストを見込んでください: 1,300ファイルで約14秒、11,000ファイルで約4分です。

サマリーは、レポートの残りを読む価値があるかどうかを教えてくれます:

```
Reachability
  declared (project-owned): 1497
  roots:                    428 (312 from plugins, 3 matched no declaration)
  reachable:                1417
  candidates:               45
  reachable only from tests: 164
  cannot decide:            25
  namespace-only (excluded): 10
```

`reachable`・`candidates`・`cannot decide`・`namespace-only`は`declared`を分割します——合計で1497になります。**`reachable only from tests`は`reachable`の部分集合**であって5番目のバケットではないので、足し込まないでください。

まず`roots`を読んでください。ルートとは、あなたのコードの外側にある何かが到達する宣言です——エントリーポイント、ルート（route）、フレームワークの規約。到達可能性はルート*から*計算されるので、薄いルートの集合はその下のすべてを膨らませます。病的なケースは`0 from plugins`のRailsアプリケーションです: Rubyのソースの中でコントローラーを名指しするものは何もないので、あなたが所有するすべてのコントローラーが死んでいるように見えます。比較すべき公表された健全な比率はありません;あなたが確認しているのは、その数がフレームワークにとってもっともらしいかどうかであり、フレームワークアプリでの`0 from plugins`は決してもっともらしくありません。

## 数を減らす

数を変えるものは2つあります。役に立つのはそのうち1つだけです。

### ルートがレバーである

ルートのソースを配線することで、あるアプリケーションの候補リストは129から57へ、別のアプリケーションでは278から45へ下がりました——**56%と84%**です。

**あなたのプラグイン**が、まず第一に、そして大部分です。`rigor-rails-routes`は`config/routes.rb`を静的に読み、それがディスパッチするすべてのコントローラーを名指しします。条件分岐の下に書かれたルート（route）も含みます;`draw(:admin)`を`config/routes/*.rb`へと追います。`rigor-pundit`は、あなたの`authorize`呼び出しが実際に名指しするポリシーを公開します。マウントされたエンジンや、Devise/Doorkeeperのコントローラーの再マッピングはカバーされません——それらのコントローラーは依然として候補として現れます。あなたのフレームワークにRigorプラグインがまったくない場合、そのエントリーポイントは何も供給せず、それはあなたのコードについての発見ではなくカバレッジの隙間です。

**あなたが宣言するエントリーポイント**は、どのプラグインも到達しないものすべてに対して:

```sh
rigor unused --entry-point='lib/cli.rb' --entry-point='lib/workers/**/*.rb'
```

繰り返し指定できます。各globはすべての宣言のパスに対してマッチされ、マッチしたファイル内のすべての宣言をルートにします。

**ファイルレベルの参照**は無償です。ロード時に走るコード——クラスを名指しするイニシャライザ、`.rake`タスク——は、それが名指しするものをルートにします。これはそれらのディレクトリが`paths:`にあるかどうかにかかわらず起きます。参照はプロジェクト全体から収穫される一方、宣言は`paths:`からのみ来るからです。

### `paths:`を広げることはレバーではない

明白な最初の一手は、プロジェクトのより多くを解析することです。3つのアプリケーションで計測したところ、`paths:`に`config/`を加えても候補数の変化は**+0.7%、−0.8%、+3.4%**でした——何もない、2方向に。

理由は上の非対称性から導かれます: 参照はすでにプロジェクト全体から来ているので、`paths:`を広げることは説明すべき*宣言*を増やすだけで、それを説明する参照を増やしません。型チェックしたければ`config/`を解析してください。それはこのリストを短くしません。

## リストを処理する

4つのセクションがあり、4つの異なる判断を要します:

| セクション | 意味 | すべきこと |
| --- | --- | --- |
| **Reachable only from test code** | 生きたテストがあり、本番の呼び出し元がない | 最初に処理する |
| **Candidates** | 到達可能なものが何もそれを名指ししない | 裁定する——ほとんどはまだ生きている |
| **Cannot decide** | 実行時に何かがそれを名指しできる | 理由を読む;ここから削除しない |
| **Namespace-only** | 生きたコードを包むモジュール | 候補から除外;数だけ |

この順序で処理してください——これはサマリーを*読む*順序ではありません。そちらでは`roots`が最初に来ます。残りを信頼してよいかを教えてくれるからです。

### テストのみの行から

セクションが小さいからではなく——上のサンプルでは候補45行に対して164行です——各行が自前の証拠を運んでいるからです。通るspecがあって本番の呼び出し元がないクラスは、死んでいるか、書き留める価値のある機構によって到達されているかのどちらかであり、いずれにせよspecファイルから決着させられます。あるアプリケーションでは、このセクションは唯一の残る呼び出し元が`spec/policies/`である22個のポリシークラスを含んでいました。この22件は裁定されなかったので、このセクションを高収量ではなく高シグナルとして扱ってください;収量は未計測です。

### 候補: そのクラスがどれだけ規約的かでソートする

候補の行は、その名前と宣言位置です:

```
Candidates — nothing reachable references these (45)
    1  Api::V1::Timelines::TopicController   app/controllers/api/v1/timelines/topic_controller.rb:3
```

裁定した実行の53件の偽陽性は、いくつかの繰り返し現れる形に分かれ、そのうち28件が最初の形でした。これらを認識できれば、リストの大半をすばやくスキップできます:

- **フレームワークの命名規約**——名前でコントローラーと対になるヘルパーモジュール、Railsのジェネレータ、`ActiveSupport::Concern`によって自動的にextendされる`ClassMethods`モジュール、gemが名前でモデルに適用するデコレータ、`has_many :speakers_talks`を通じて到達される結合モデル、あるいはオプションキーから導出されるカスタムバリデータ（`validates :start_date, date: true`は`DateValidator`という名前を解決します）。名前を書くものは何もありません;フレームワークがそれを導出します。このうち2つはクラスタ全体を一度に片づけるので、行を1つずつ処理する前に確認してください: **`include_all_helpers`はデフォルトでtrue**なので、アプリがそれを無効にしていない限り、すべての`app/helpers/*Helper`は生きています;そしてデコレータgemの規約は`app/decorators`を丸ごとカバーします。
- **設定内で文字列として名指しされている**——定期ジョブのスケジュール（`config/recurring.yml`・`config/schedule.yml`・`sidekiq.yml`のスケジューラブロック）、キュー定義、設定ファイル内のクラス名。スケジューラは名前でそれを解決するので、Rubyコードがそうする必要はなく、スケジュールされたジョブはリポジトリのどこにも`perform_later`呼び出しを持たないのが普通です。そのファイルが実際にロードされているか確認してください——`--recurring_schedule_file`を渡す`Procfile`やデプロイ設定が確証となる証拠です。
- **ビューから呼ばれている**——`app/views/**/*.erb`はRubyではなく解析されないので、テンプレートからのみ使われるヘルパーには、レポートが見られる呼び出し元がありません。ヘルパーの行を信じる前にビューツリーをgrepしてください。
- **自己登録するクラス**——その本体が登録DSL（`add "link"`・`register :thing`）を呼ぶクラス。使用の証拠はクラスの外ではなく中にあります。
- **公開された拡張ポイント**——あなたのリポジトリの外側からのみサブクラス化される基底クラス。内側からは死んでいて、外側からは荷重を支えています。
- **一度も使わなかった機能のスキャフォールド**——`rails new`は、チャネルを追加するかどうかにかかわらず`ApplicationCable::Connection`と`ApplicationCable::Channel`を生成します。`app/channels`に他に何もなければ、正直な発見はそのクラスではなく機能が未使用だということです。機能について判断してください。

### Cannot decide: 理由を読み、削除しない

これらは、実行時に何かがそのクラスを名指しできるために`candidates`から降格されたものです。各行はそれが何であるかを述べます:

```
  1  Handlers::Alpha                     lib/handlers.rb:2
       constantize on an interpolated string (lib/dispatch.rb:14)
```

`"Foo".constantize`は`Foo`をちょうど名指しするので、通常の参照として数えられ、決してこのセクションには到達しません。`"Foo::#{key}".constantize`は名前空間を限定することしかできないので、`Foo`配下のすべてが降格されます。`.yml`・`.json`・テンプレートファイル内に文字列として現れるクラス名も同じように降格されます——定数参照より弱い証拠であり、使用の証明でも、死んでいると呼ぶ根拠でもありません。

ここのセクションが大きいことは、このコードベースでは動的ディスパッチが荷重を支えていると告げており、それが削除キャンペーンがそこで止まる正直な理由です。

## 削除する前に

候補の行は案件の始まりです。以下のそれぞれを確認してください:

1. **レポートがマッチできない綴りを検索する**。完全修飾名を再びgrepしないでください——FQNがレポートの読む場所のどこかに現れていたら、その行は`candidates`にないはずです。代わりに、レポートがマッチできない形をgrepしてください: snake_caseされたautoloadパス（`admin/reports_controller`）、demodulizeされた末尾、補間で組み立てられる名前、そしてビューツリー。
2. **規約で到達されていないか確認する**——上記の形。
3. **リポジトリの外側の何もそれを参照していないか確認する**。gem、ライブラリ、サードパーティの拡張を持つアプリでは、「unused」は「私に見える呼び出し元からは未使用」を意味し、あなたの公開APIはまさにあなたに見えないものです。
4. **gitの履歴を読む**——ただしまず本物か確認すること。最近追加されて一度も配線されなかったクラスは、デッドコードではなく未完成の作業です。浅いクローンや、履歴が依存関係のバンプばかりのクローンでは、「最終変更」の日付は作為であり何も証明しません;ボットのコミットをファイルの年齢として引用する代わりに、そう述べてください。
5. **そのテストも一緒に削除する**。テスト対象のクラスより長生きしなければならないspecは、何もテストしていません。

**空であることは死んでいることと同じではありません**。フレームワークがあらゆる場所でincludeするがメソッドを1つも宣言しないモジュールは、このレポートが使うあらゆる尺度で生きており、それでも削除する価値があります——デッドコードとしてではなく、ジェネレータの残骸として。2つのうちどちらを見つけたかを述べてください;レビュアーに求められる注意の量が違います。

### 他の人に主張を通す

役に立つ成果物は、宣言位置付きの候補の行、ステップ1の結果、そしてそのファイルの最後の実質的な変更の日付です。

尋ねられるのを待たず、精度の数字を自分から述べてください。レポートがほとんど偽陽性であること、そしてあなたがこの行を手で確認したことを知っているレビュアーは、その具体的な主張を信頼する理由をより多く持ちます——少なくではなく。このツールが過少報告することについても同じくらい率直であってください: すべてを見せてくれたわけではありません。

## キャンペーンとして走らせる

**削除した後ではなく、設定した後に再実行する**。リストは、クラスを1つ取り除いたときよりルートのソースを1つ加えたときのほうがはるかに動きます。

**`matched no declaration`を監視する**。これはプラグインが供給したルートのうち、あなたのプロジェクトが宣言していないものを名指ししている数です:

```
  roots:  428 (312 from plugins, 3 matched no declaration)
```

数件は普通です——`Rails::HealthController`のようなフレームワークのクラスは正しく名指しされ、正しくあなたのものではありません。引用すべき閾値はありません;重要なのは傾向です。なぜなら**過剰に主張するルートのソースは、デッドコードを黙って隠す**からです。供給不足はリスト上に行を残すので目に見えます;過剰供給は見えないところで行を取り除きます。

**ドリフトは一方向を予期する**。新しいコードは候補を増やし、新しいルート（route）やエントリーポイントは候補を減らします。誰もデッドコードを追加していないのに数か月かけて数が上がるなら、コードベースを疑う前にプラグインがロードされなくなったことを疑ってください。

これらのいずれかを追跡するには、自分で数を保持しなければなりません——`--format json`の出力をコミットするか、サマリー行を記録してください。このコマンドにはベースラインファイルはありません。

### プロジェクトが生成されたRBSを出荷している場合

シグネチャファイルは宣言も参照もし、参照だけが数えられます。`sig/`内の`class Talk < ApplicationRecord`は`ApplicationRecord`を参照します;それが宣言する`Talk`は`Talk`への参照ではありません。もしそうなら、生成されたシグネチャを持つすべてのクラスが自分自身をルートにし、レポートはあなたが望むまさにその行を欠くことになります。

これは、最近まで間違っていて症状が静かだったので知っておく価値があります: あるアプリケーションでは101のルートのうち48が`sig/`から来ており、11行が決して現れませんでした。これが修正される前のリリース（[issue #363][issue-363]）を使っているなら、`signature_paths:`を空にした実行と比較してください——両者の大きな差がその証です。

## 自動化する

**これでビルドをゲートしないでください**。このコマンドは実行されれば常に0で終了します。まさにチェックになりえないようにするためで、唯一の非ゼロ終了は`--incremental`を渡すなどの使用法エラーです。候補数への閾値は、あなたのコードと同じくらい頻繁にあなた自身のツーリングに対して発火するでしょう——数が上がるのはたいていプラグインがロードされなくなったことを意味します。

**レポーティング**ジョブとして走らせるのは構いませんし、上で述べたドリフトに気づくための意図された方法です: スケジュールで走らせ、JSONを公開し、人に傾向を読ませてください。
