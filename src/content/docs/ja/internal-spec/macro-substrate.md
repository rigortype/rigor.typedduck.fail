**マクロサーフェス**（macro substrate、マクロ基盤）は、メタプログラミング
ライブラリが利用者に公開する呼び出し形状をRigorに教えるために、プラグイン
作者が宣言するプラグインマニフェストの値オブジェクト群である。エンジンが
ソースを読むだけでは見えない`define_method` / `class_eval` / `const_missing`
パターンを指す。これは[ADR-16](../../adr/16-macro-expansion/)（4ティア）で
導入され、[ADR-18](../../adr/18-substrate-per-call-site-return-type/)（呼び出し
箇所ごとの戻り値型）と
[ADR-36](../../adr/36-mangrove-enum-nested-class-emission/)（ネストクラスの
発行）で拡張された。

本ドキュメントは**プラグイン作者向けの値オブジェクト形状**を規定する。
すなわち、フィールド、その型、検証、そして各エントリーが満たす同一性／
不変性の契約（contract）である。これらの形状は、プラグインgemが基づいて
記述される永続的な契約である。エンジン側での消費 ── ディスパッチャーの
合成メソッドティアと`Environment#synthetic_method_index` ──
は[`inference-engine.md`](../inference-engine/)が規範的に定める
（ディスパッチャーのティア順序＋`Environment`のクエリサーフェス）。
floor/ceiling配信ポリシーとティアごとの根拠はADRにある。

4つのクラスはすべて`Rigor::Plugin::Macro`名前空間
（`lib/rigor/plugin/macro/`）の下にあり、[`plugin.md`](../plugin/#rigorpluginmanifest)
で文書化された対応する`Manifest`スロットを通じて宣言される。
`block_as_methods:`、`heredoc_templates:`、`trait_registries:`、
`nested_class_templates:`。ティアDは**テンプレート単位**（[#392](https://github.com/rigortype/rigor/issues/392)）として需要に応じて復帰した;その値オブジェクトは`Rigor::Plugin::TemplateUnit`（`lib/rigor/plugin/template_unit.rb`）であり、その宣言が呼び出し形状ではなくコンパイルされたソースである唯一のティアであるため、上記の4つと並べるのではなく後述の「テンプレート単位」で規定される。

## 共通の値オブジェクト契約

すべてのマクロ値オブジェクトは、同じ同一性および不変性の規則をMUST満たす
（残りのプラグイン契約キャリア（carrier）と一貫している）。

- **構築時にフリーズ**。すべてのフィールドは`#initialize`内でdup-freeze
  され、インスタンス自体もフリーズされる。構築後`Ractor.shareable?`は
  trueをMUST返す（ADR-15 Phase 1）。これにより、実体化されたプラグインは
  fork/Ractor境界を越えてサーフェス宣言を運ぶ。
- **構築時に検証**。各フィールドは`#initialize`内でチェックされる。
  不正な宣言は、スキャン時に黙って失敗するのではなく、マニフェスト
  ビルド時（ロード時）に`ArgumentError`をMUST送出する。`Manifest`
  スロットは、すべてのエントリーが期待されるクラスのインスタンスであることを
  再検証する。
- **値による同一性**。`#==` / `#eql?` / `#hash`はフィールド値によって
  比較する（ほとんどは正準的な`#to_h`を介する）ため、構造的に等しい2つの
  宣言は交換可能である。
- **`#to_h`はキャッシュキーへとラウンドトリップする**。すべてのクラスは
  文字列キーの`#to_h`を公開する。マニフェストはそれを`Manifest#to_h`に
  畳み込み、これはキャッシュキーとして安定している。プラグイン作者は、
  エンジン統合が先送りされている場合（後述の_実装状況_を参照）でも、
  今日どのティアでもMAY宣言できる。宣言はラウンドトリップし、対応する
  `Manifest`リーダーで公開され、エンジンスライス（slice）が着地したときに
  前方互換となる。
- **`receiver_constraint`のマッチング**。すべてのティアが
  `receiver_constraint`を運ぶ。呼び出しの字句的レシーバー
  クラスがその完全修飾名と**等しいか、それを継承している**ときにエントリーが
  発火し、`Environment#class_ordering`を通じてマッチされる。`Singleton[X]`
  レシーバー（クラスレベルDSL呼び出し）については、マッチは
  `extend`エッジも参照する: `X`のシングルトン上の呼び出しに応答する
  モジュール ── シングルトン祖先探索順（`scope.discovered_extends`は
  最近接を先頭に格納）で`extend`エッジを辿り、次いで発見されたスーパークラス
  チェーンを上り、`Environment#singleton_extended_modules`によって表面化
  されるRBS宣言の`extend`を含む ── が制約に解決され、かつ実際に`method_name`を
  定義しているときにエントリーが発火する。クラス自身のシングルトンdefは
  あらゆる`extend`エッジに先行する ── ただし、それらが実行された（RUN）後に
  限られる: 呼び出し時点では`def`が実行されていないため、
  `sig { ... }; def self.sig`は依然として`T::Sig`を束縛する。
  `Scope#singleton_def_shadows_call?`は、ファイルごとのdef / block / lambda
  本体範囲テーブルである`discovered_deferred_ranges`からこれを判定する: 
  そのような範囲に含まれる呼び出しは呼び出し時まで遅延され、同じオーナーの
  同名defが既知である場合（すでに発見されているか、サイトテーブルが
  見逃した行によって記録されているかのいずれか）にのみシャドウされる。
  一方、先行評価されるクラス本体の呼び出しは、開始オフセットがそれに先行する
  同名・同オーナーのdefによってのみシャドウされる（バイトオフセットであるため、
  同一行のdefも正しく順序付けられる;最先の一致defが決定するため、後の再定義が
  ブリッジを復活させることはできない;行は修飾されたオーナーを運ぶため、別の
  クラスの`def self.sig`が`F`の呼び出しを順序付けることはできない）。遅延範囲の
  内側にネストされたdef ── メソッド本体やブロック内部の`def` ── は呼び出し時に
  インストールされ、順序付けから除外される一方、`module_function`行は
  呼び出し箇所でのモードトグルおよび`module_function :x`の遡及的インストールを
  モデル化する。先行評価される本体は範囲ではない: `Const = Class.new do … end`や
  `class_eval`ファミリーのブロックは囲む本体の実行中に実行される ── evalブロックの
  defはレシーバーのサーフェスに属するため、命名可能なレシーバーがそれらの
  オーナーを提供する（defサイト、メソッド、可視性、およびextendsテーブルは
  evalブロック本体を同じレシーバーに帰属させる）。ただし、この分割は2つの
  コンテキストである ── evalブロック内で`Module.nesting`は変化しないため、
  その内部の`class` / `module` / 定数書き込みは依然として字句的名前空間の下に
  登録される一方、`def`はレシーバーに束縛される。eval本体内部では`self`も
  レシーバーであるため、ネストされた`self.class_eval`、素の`class_eval`、または
  `self::X.class_eval`は囲むレシーバーに対して解決される ── 字句的な`module M`の
  下で`M::X#h`となることは決してなく、`Y.class_eval { self::X.class_eval { def h; end } }`は
  `Y::X#h`をインストールする ── 一方でCONSTANTレシーバーは読み取りがまさにそうするように
  `Module.nesting`を通じて解決される ── トップレベルの`M::Y.class_eval`内部の
  `Y.class_eval`は再び`M::Y`を開くのではなく、トップレベルの`Y`を開く ── したがって
  ファイルの自身の宣言が含む最初の`<rung>::X`が最内を優先して勝つ（`class S`内部の
  `X.class_eval`は、呼び出しが`class <<`の下にあるかどうかにかかわらず、ファイルが
  `S::X`を宣言しているときに`S::X`を命名する）。そして、どのラングも宣言していない
  シャドウ ── 通常は別のファイルで定義されているもの ── のみが書かれたとおりに登録される。
  `class <<`本体の内部では`self`はシングルトンである ── `self::X`読み取りおよび
  `self::X` / 素の定数書き込みはその定数テーブルに着地するが、テーブルはそれを
  命名できないため、両方とも辞退される。同じ命名不能なcrefが宣言を支配する: 
  `class <<`内部の`class D`は`#<singleton>::D`を開くため、すべての発見ウォーク ── 
  メソッド、シングルトンdef、可視性、includes/extends、スーパークラス、defネスト、
  ivar、メンバーレイアウト ── は、捏造された`C::D`ではなくクラスなしの下にそのファクトを
  登録し、宣言／発見プロデューサー（`discovered_classes`、`class_sources`、
  `declared_types`、`local_constant_names`）も`C::D`/`C::K`を登録しない ── さもなければ
  `known_namespace?`があらゆる`D`ファミリーの解決を相互汚染してしまう。そこでは
  素のヘッダーまたは書き込み（および`self::`基底）のみが命名不能である: 明示的な
  基底を持つすべてのパス ── `::T`、`C::D`、`Foo::Bar`、`::K =`、`C::K =` ── はその
  基底を字句的に解決し、非シングルトンウォークが用いるのと同じコンパクトヘッダー
  近似の下で再アンカーされる。`class <<` EXPRESSIONはこの境界を証明する例外である: 
  シングルトンが開く前に囲むコンテキストで評価されるため、
  `class << (class D; self; end)`は依然として`C::D`を宣言し、シングルトン本体の
  内側の`class << self`はシングルトン自身のシングルトン（`#<Class:#<Class:C>>`）を開くが、
  何ものもこれを命名しない。evalおよびメタブロックは`self`を再束縛しながらそのcrefを
  保持するため（`class <<`の下の`Foo.class_eval { X = 1 }`は依然としてシングルトンの
  テーブルに書き込む）、`self::`にアンカーされたevalレシーバーはすべてのコンシューマー
  ウォーク ── メソッド、シングルトンdef、可視性、遅延範囲、includes、およびextendsの
  すべて ── で辞退し、`class << <non-self>`の下の素または`self`レシーバーは何ものも
  命名しない。`instance_eval`/`instance_exec`はさらに分割される: これらのテーブルが
  読み取る`self`アンカーのファクトについて`class_eval`とまったく同様に`self`を
  レシーバーに再束縛するが（`X.instance_eval { extend M }`は`X`をextendし、
  `X.instance_eval { include M }`はレシーバーをモジュールとする呼び出しが実際に送信する
  includeエッジを記録する）、内部のデフォルトの被定義者はレシーバーのシングルトンである ── 
  `X.instance_eval { def m }`は`X.m`をインストールし、キーワード`alias`/`undef`は同様に
  シングルトン側で束縛される ── 一方で`define_method`、`attr_*`、`alias_method`、および
  可視性呼び出しはインスタンスサーフェス上でレシーバーをモジュールとする呼び出しのまま
  留まる。defを所有するウォークはそれを個別の`defs_singleton`フラグとして運ぶため、
  キーワード形式のみが移動する; `define_method`本体または名前のない
  `Class.new { … }`ファミリーのブロックはオーナーなしで歩く。すでにシングルトンである
  本体の内部では分割が反転する: 素または`self`の`instance_eval`は同じシングルトンselfを
  再評価するため、呼び出しはそこでの`class_eval`のものとまったく同様にシングルトンの
  インスタンスサーフェスに着地する（`class << S; instance_eval { define_method(:m) }`は
  `S.m`をインストールし、`include`/`extend`は同じシングルトン祖先エッジを生成する）。
  一方で`def`/`alias`はシングルトン自身のシングルトン ── `#<Class:#<Class:S>>` ── 上で
  束縛されるが、何ものもこれを命名しない;ウォークはその被定義者を`:unnameable`とマークし、
  それらを`S`の下に登録するのではなくリーフを辞退する。メタnewブロックはその逆を行う: 
  `K = Class.new { extend M }`は`K`をextendするため、mixinテーブルはブロックを命名可能な
  `K`に帰属させ、`K`自体が命名不能であるときにのみ辞退し、ファクトリー呼び出しの
  レシーバーと引数は依然として囲むコンテキストで評価される（`K = Class.new(X.class_eval { extend M })`は
  `X`をextendする）。ただしメタnewブロックは依然として`self`の再束縛にすぎない ── その内部で
  `Module.nesting`は字句的なままである ── したがって`def`、`alias`、mixin、および`self::`
  アンカーのファクトは書き込みが命名するクラスに帰属する一方、ネストされた`class` / `module`
  宣言は囲むcrefを保持する（`C`の`K = Class.new { … }`内部の`class Inner`は`C::Inner`を開き、
  決して`K::Inner`とはならない; `class <<`の下ではシングルトンのテーブルに着地し、
  そこにある他の任意の宣言と同様に辞退する）。ファイル間defおよびインデックスが見たことのない
  ファイルは両方ともシャドウされたものとしてカウントされる ── プロジェクトメソッドが
  呼び出しを所有している場所で`DeclBuilder`を束縛すると診断を捏造してしまうため、保守的な
  方向である。これが、`class F; extend T::Sig; sig { ... }; end`と
  `class Doc < T::ImmutableStruct; sig { ... }; end`の両方が`sig`エントリーに到達する
  方法である（#1097）── 一方で、同じ名前を定義するモジュールのより近い`extend`（`extend T::Sig; extend CustomSig`）、
  またはクラス自身のすでに実行された`def self.sig`が呼び出しを所有し、束縛は辞退される。
  そのカスタムメソッドが実行時にブロックのselfを選択するからである。

## ティアA ── `BlockAsMethod`（`block_as_methods:`）

「`method_names`のいずれかのクラスレベルDSL呼び出しに渡されたブロックは、
`receiver_constraint`のサブクラスツリー上のインスタンスメソッドとして
実行され、`self`はそれに応じて型付けされる。」正準的なターゲット：
Sinatraの`get '/path' { ... }`（ブロックは文字どおりルートメソッド本体に
なる）。

| フィールド | 型 | 注記 |
| --- | --- | --- |
| `receiver_constraint` | 空でない`String` | 呼び出しの字句的レシーバーがそれであるか、それを継承していなければならないFQクラス名。 |
| `method_names` | 空でない`Array<Symbol>` | ブロックがインスタンスメソッドとして実行されるDSLメソッド名（`Symbol`／空でない`String`から強制変換）。 |
| `self_type` | `Symbol`または`String` | ブロック内の`self`バインディング。`:receiver_instance`（デフォルト）は`Nominal[レシーバークラス]`を束縛する ── Sinatraの規約。StringはDSLがブロックを`instance_eval`する対象のクラス名を指定する：`"Foo::Bar"`は`Nominal[Foo::Bar]`を束縛し（`Grape::Validations::ParamsScope`上のGrape `params`本体、`Grape::Endpoint`上のHTTP動詞本体）、さらに`Nominal[Y ≤ receiver_constraint]`レシーバーにもマッチする。これにより、`params`本体内のネストした`requires do … end`が同じコンテキストに再突入できる。`"singleton(Foo::Bar)"`は`Singleton[Foo::Bar]`を束縛し（`Grape::API::Instance`クラスオブジェクト上のGrape `namespace`本体）、`Singleton`レシーバーにのみマッチする。`:receiver_singleton` / `:dsl_recorder`は引き続き予約名であり、まだ受理されない。 |

## ティアC ── `HeredocTemplate`（`heredoc_templates:`）

「クラスレベル呼び出し`<receiver_constraint>.<method_name>(name_arg, …)`は、
呼び出し元クラスに合成メソッドを発行し、その名前は`symbol_arg_position`の
ソースで可視なリテラル引数を補間する。」正準的なターゲット：dry-structの
`attribute :name, T`とActiveStorageの`has_one_attached :avatar`。

| フィールド | 型 | 注記 |
| --- | --- | --- |
| `receiver_constraint` | 空でない`String` | FQクラス名（等しいか継承）。 |
| `method_name` | `Symbol` | DSLメソッド（`Symbol`／空でない`String`から）。 |
| `symbol_arg_position` | `Integer >= 0` | デフォルト`0`。各emit行に補間される`name`となる、リテラルSymbol値を持つ引数のインデックス。 |
| `emit` | `Array<Emit>` | 呼び出し元クラスに合成するインスタンスメソッド（`Hash`から強制変換）。 |
| `class_level_emit` | `Array<Emit>` | 同じ形状。合成されるメソッドはシングルトン（クラスレベル）。 |

`NAME_PLACEHOLDER`は、emit行の`name:`テンプレートが補間のために運ぶ
リテラル`"#{name}"`トークンである。

### `HeredocTemplate::Emit`

emitテーブルの1行。

| フィールド | 型 | 注記 |
| --- | --- | --- |
| `name` | 空でない`String` | 合成メソッドの名前テンプレート。`"#{name}"`プレースホルダーは`symbol_arg_position`の呼び出し箇所リテラルシンボルで補間される。 |
| `returns` | 空でない`String`または`nil` | 宣言された戻り値型名。`Environment#nominal_for_name`を介して解決される。`returns`と`returns_from_arg`の両方が`nil`のとき、合成メソッドの戻り値はADR-16 WD13のfloorに従って`Dynamic[top]`にフォールバックする。 |
| `returns_from_arg` | `ReturnsFromArg`または`nil` | 呼び出し箇所ごとの戻り値型（ADR-18）。`Hash`から強制変換される。 |

### `HeredocTemplate::ReturnsFromArg`（ADR-18）

`HeredocTemplate`の下の`Emit`の兄弟クラス（`Emit`の中にネストされて
いない）で、`Emit#returns_from_arg`から参照される。合成メソッドの戻り値型が
**呼び出し箇所の引数のソース表現**から来ることを宣言し、それはプラグイン
横断のファクト（fact）チャネル（[ADR-9](../../adr/9-cross-plugin-api/)の
`FactStore`）で探索される。記述形状：

```ruby
returns_from_arg: { position: 1, lookup_via: { plugin_id: "dry-types", fact: :dry_type_aliases } }
```

| フィールド | 型 | 注記 |
| --- | --- | --- |
| `position` | `Integer >= 0` | ソース表現が探索キーとなる呼び出し箇所の引数インデックス。 |
| `plugin_id` | 空でない`String` | 生成側のプラグイン（`lookup_via:`から）。 |
| `fact` | `Symbol` | そのプラグインの`FactStore`バケットから読むファクト名（`lookup_via:`から）。 |

`.coerce(value)`は`Hash`（`lookup_via:`のHashを要求する）、`ReturnsFromArg`、
または`nil`を受理し、それ以外の形状ではすべて送出する。

## ティアB ── `TraitRegistry`（`trait_registries:`）

「クラスレベル呼び出し`<receiver_constraint>.<method_name>(:trait_a,
:trait_b, …)`は、`modules_by_symbol[:trait_a]` + `[:trait_b]`で名指された
モジュール（および任意の`always_included`モジュール）を、呼び出し元
クラスに実質的にincludeする。」正準的なターゲット：Deviseの`devise
:database_authenticatable, :recoverable`。

| フィールド | 型 | 注記 |
| --- | --- | --- |
| `receiver_constraint` | 空でない`String` | FQクラス名（等しいか継承）。 |
| `method_name` | `Symbol` | DSLメソッド（例：`:devise`）。 |
| `symbol_arg_position` | `:rest`または`Integer >= 0` | `:rest`（デフォルトであり、スキャナが尊重する唯一の形式）はすべての位置Symbol引数をトレイトとして扱う。Integerインデックスは将来の単一トレイト形状のために予約されている。 |
| `modules_by_symbol` | `Hash<Symbol, String>` | 認識された各トレイトシンボルをFQモジュール名にマッピングする。テーブルに存在しないシンボルは素通りする（スキャナは`macro.tier_b.unknown-trait`の`:info`マーカーを発行する）。 |
| `always_included` | `Array<String>` | シンボルが1つもマッチしない場合でも、マッチするすべての呼び出し箇所で追加されるFQモジュール名。 |

`#module_for(symbol)`はトレイトシンボルに対するFQモジュール名を返し、
不明な場合は`nil`を返す。ティアBはティアCの`Dynamic[T]`のfloorの対象では
**ない**。合成されるメソッドは、includeされたモジュールが記述したRBS戻り値型を
再生する（ADR-5のロバストネス ── サーフェスは与えられていない精度を捏造
しない）。

## ネストクラスティア ── `NestedClassTemplate`（`nested_class_templates:`、ADR-36）

ティアCが*メソッド*を合成するのに対し、このティアはenum形状のブロックDSLで
宣言された*ネストされたサブクラス*を合成する。動機となる形状：Mangroveの
`variants do variant Circle, Float end`。ここで各`variant <Const>, <Type>`
行は、`#inner : <Type>`を運ぶネストされたサブクラス`Shape::Circle < Shape`を
鋳造する。

| フィールド | 型 | 注記 |
| --- | --- | --- |
| `receiver_constraint` | 空でない`String` | ブロックが認識されるために、囲んでいるクラスが`extend`しなければならないFQモジュール名（例：`"Mangrove::Enum"`）。 |
| `block_method` | `Symbol` | 囲んでいるDSLブロック。デフォルト`:variants`。 |
| `variant_method` | `Symbol` | ブロック内の各宣言呼び出し。デフォルト`:variant`。 |
| `symbol_arg_position` | `Integer >= 0` | デフォルト`0`。ネストされたサブクラスを名指すリテラル定数を持つ引数のインデックス。 |
| `inner_arg_position` | `Integer >= 0` | デフォルト`1`。型式が`#inner`リーダーの戻り値型となる引数のインデックス。定数型引数は解決される。定数でないinner形状は`Dynamic[top]`に降格する。 |
| `inner_reader` | `Symbol` | 各バリアントサブクラスに合成されるペイロードリーダー。デフォルト`:inner`。 |

`sealed`-親ファクト＋`is_a?`バリアント横断の網羅的ナローイング
（ADR-36 WD3）は、先送りされたceilingである。

## テンプレート単位 ── `TemplateUnit`（`template_globs:` + `#template_units_for_file`、#392）

復活した[ADR-16](../../adr/16-macro-expansion/)のティアD。ティアDは`external_files:`（「宣言された呼び出し箇所にその本文が貼り付けられたかのように評価され、`self`は宣言されたクラスとして型付けされるファイル」）と`bound_ivars:`を宣言していたが、[ADR-60 WD1](../../adr/60-pre-freeze-plugin-contract-consolidation/)がエンジン側のコンシューマー不在を理由に削除した。その需要がエフェクトに伴って到来し（`docs/design/20260816-effect-labels.md` § 11.3：「このリクエストは何を行うか」というレビューの問いが、`render`においてテイントで終わる）、復活した継ぎ目はティアDに欠けていた唯一のもの、すなわちパース前の**行マップを伴うソース変換**を追加する。

上記の4つのティアとは異なり、テンプレートはパターンマッチされるのではなくコンパイルされるため、これは1つのマニフェスト行ではなく**クレーム（claim）＋フック**である：

| サーフェス | 形状 | 役割 |
| --- | --- | --- |
| `Manifest#template_globs` | `Array<String>` | プラグインがクレームするプロジェクト相対のglob。絶対globと`..`セグメントはマニフェスト構築時に拒否される。何も宣言しないプラグインは呼び出されず、プラグインが何も宣言しない実行ではglob展開は行われない。 |
| `Base#template_units_for_file(path:, source:)` | `-> Array<TemplateUnit>` | 変換フック。マッチしたファイルごとに親プロセス上で解析前に1回だけ呼び出される。`[]`はそのファイルを辞退（decline）する。 |

返されるユニットは、提供されたファイルを指名しなければならない（`unit.path == path`）。それ以外のものを指名するユニットは拒否される。このチェックがないと、別のプロジェクトファイルを指名する`path:`はそのファイルのソースを暗黙のうちに**置き換えてしまい**（エンジンはユニット自身のpathに対してそのバイト列を提供する）、プロジェクトルート外のものを指名する`path:`は依存記述子の行なしで解析されてしまう（いずれも1つの誤った文字列に起因する）。

3つの失敗モードは脱落させずに報告され、それぞれテンプレートファイルに位置付けられた1つの`:plugin_loader` `runtime-error`診断として報告される：**例外を送出した**変換、**読み込めなかった**テンプレート、および**誤ったpathを指名した**ユニット。これは他のすべてのプラグインフックが報告に使用する隔離エンベロープと同じである（[ADR-2](../../adr/2-extension-api/) § 「プラグインの信頼とI/Oポリシー」）。ファイルはユニットに寄与せず、実行は継続し、プラグイン作者には読める情報が残る。

2つのユニットが異なるpathをまたいで`logical_name`を共有してもよい。これは拒否されない：両者は個別に解析され、それらのサマリーは単一の`view:`キーの下で結合される。これは2つのファイルで再オープンされたメソッドが受ける解釈と同じである。同じ**path**に対する2つのユニットは発生し得ない ── 最初のクレームが勝ち、すでに別のプラグインがコンパイルしたファイルをクレームする2番目のプラグインは登録順序に従って脱落する。

### `TemplateUnit`

`Rigor::Plugin::TemplateUnit.new(logical_name:, path:, ruby_source:, line_map: {}, self_type: nil, locals: {}, ivar_seeds: {}, transform_id: nil)`。

| フィールド | 型 | 注記 |
| --- | --- | --- |
| `logical_name` | 空でない`String` | ハンドラ非依存の名前（`users/show.html.erb`ではなく`users/show.html`）。これによりERB → Hamlの書き換えがリネームにならない。`view:<logical_name>`エフェクトユニットキーの綴りとなる。 |
| `path` | 空でない`String` | ユーザーが書いたとおりのテンプレートファイル（プロジェクト相対）。すべての診断やすべての`Runner#effect_sources`行がこのpathを指名する。 |
| `ruby_source` | `String` | コンパイルされたRuby。合成された`class … def`でラップされることなく、ファイルとしてパースおよび型付けされる。後述の位置ルールを参照。 |
| `line_map` | `Hash<Integer, Integer>` | `{ ruby_sourceの行 => テンプレート行 }`。両側とも1始まり。いずれかの側で正でない行を指定すると例外が発生する。空のマップは恒等変換。 |
| `self_type` | `String?` | 本文の`self`が型付けされる完全修飾クラス。ユニット内の暗黙のself呼び出しが解決されるオーナーでもある。 |
| `locals` | `Hash<String, String>` | `{ 名前 => 型名 }` ── レンダー箇所のパラメータ。 |
| `ivar_seeds` | `Hash<String, String>` | `{ "@name" => 型名 }` ── レンダリングするアクションが設定したassign。 |
| `transform_id` | `String?` | コンパイラの識別情報（`"erubi-1.13"`）。デフォルトは宣言側プラグインの`id@version`。 |
| `suppressed_rules` | `Array<String>` | #393 ── このユニットの診断に対してエンジンが破棄するルールIDプレフィックス。後述の「ルール姿勢」を参照。 |

これは4つのティアと同じ共通規約を満たす：構築時のfreeze、構築時のバリデーション（不正な形式の宣言はスキャン時ではなく変換時に`ArgumentError`を送出する）、値の等値性、およびラウンドトリップ可能な`#to_h`。さらに**`Marshal`クリーン**でもあり、フォークプールがこれに依存している。

環境が解決できない`self_type`、`locals`、または`ivar_seeds`の型名は、推測されることも**未束縛のまま残されることもなく**、`Dynamic[top]`に束縛される。この違いは`self_type:`で最も重要となる：これを未束縛のままにすることは「クレームなし」ではなく、本文がトップレベルで実行されるというクレームであり、テンプレート内のすべてのヘルパー呼び出しが`call.unresolved-toplevel`を報告することになる（これを試した最初の実際のRailsアプリにおいて、プラグインがプロジェクトにRBSのないクラス`ActionView::Base`を指名したことで、1行ごとに所見が発生した）。`Dynamic`は「レシーバーは宣言されているがアナライザーには見えない」という誠実な解釈であり（[ADR-5](../../adr/5-robustness-principle/)）、沈黙する。

### 位置（Positions）

`ruby_source`はそのままパースされ、エンジンが`self_type` / `locals` / `ivar_seeds`でシードしたファイルごとの`Scope`の下に置かれる ── メソッド境界で`StatementEvaluator#build_method_entry_scope`が実行するシード処理をファイル境界に適用したもの。本文を合成された`class … def`でラップするとすべての行がシフトし、エンジン独自のマッピングをプラグインのマップと合成せざるを得なくなる。現状では、動作するマッピングはプラグインのものだけである。

さらに、`locals:`の名前はパース時の囲む`scopes:`としてPrismに渡される。これがないとシードは機能しない：代入が見当たらない裸の識別子をPrismは**メソッド呼び出し**としてパースするため、テンプレート内の`size`は`CallNode`となり、`Scope#local(:size)`が参照されることはなかった。これらを宣言することは、パーシャルのlocalsをコンパイル済みメソッドのパラメータへとコンパイルする際にRails自身が行うことでもある。

ユニット内で生成された診断は、実行から出る前に`line_map`を介して再指示される（`Analysis::TemplateUnits#remap`）：**pathはすでにテンプレートのもの**（パース時にそれが付与される）であるため、行のみが移動し、列は1に落ちる ── コンパイラは行を保持しつつ各行のテキストを書き換えるため、コンパイルされたRubyの列はテンプレート内の何にも対応しない。マップされていない行はその前の最も近いマップされた行にアンカーされ、存在しない場合は1行目にアンカーされるため、所見は常にファイル内に着地する。

列ルールは、ユニットが空でない`line_map`を運ぶ場合は常に適用され、実際に行が移動したときだけに限定されない：たまたま行を元の位置のまま残すコンパイラであってもその行のテキストを書き換えているのであり、ERBはまさにそのケースである ── そのマップはほぼ恒等変換であり、その列はいずれにしても無意味である。空のマップを持つユニットはマッピングをまったくクレームせず、その診断はそのまま通過する。

### ルール姿勢（Rule posture、#393）

`suppressed_rules:`は、「このコンパイラの出力においてどの所見ファミリーが有意義か」に対する**ユニットごと**の回答である。プレフィックスはドット区切りのファミリー（`call.`）または完全なルールIDであり、マッチングは`String#start_with?`で行われ、`Analysis::TemplateUnits#remap`は実行のストリームが親プロセスを離れる前にマッチした診断を破棄する。空のリスト（デフォルト）はすべてを報告する。

これは意図的に`disable:`エントリーではない：`disable:`はプロジェクトの`.rb`ファイルでもルールを抑制してしまい、テンプレートユニットプラグインが望むことの正反対である。また、意図的にエンジンポリシーでもない：自身の変換が何を出力するかを知っているのはプラグインだけであり、あるコンパイラにとっての誠実なデフォルトが別のコンパイラにとっての誠実なデフォルトとは限らない。これはユニットダイジェストに乗るため、ファミリーを再び有効にすると再解析が行われる。

rigor-actionpackは、`view_type_checks:`がオフ（デフォルト）の間、`["call.", "flow."]`を宣言する。そして`docs/notes/20260917-erb-template-units.md`には、この2つのプレフィックスがそれぞれ拠って立つコーパス測定が記録されている ── レンダー箇所の`locals:`が追跡されていないときにパーシャルが書き出すオプショナルlocalプリアンブルに起因する、redmineでの3件の`flow.always-truthy-condition`偽陽性である。

### エフェクト、キャッシュ、プール

- **エフェクトユニット**。テンプレートユニットは`view:<logical_name>`をキーとする単一のエフェクトユニットである ── ビューにはオーナークラスもセレクタもないため、`MethodKey`ではない。スキャナは`def`ごとに1つ生成するのではなく、ファイル本文全体をそのユニットとして受け取り（`Effects::Scanner#scan_template_unit`）、`Runner#effect_sources`はそのキーを`path`へと辿る。
- **キャッシュ同一性**。各ユニットのダイジェストは、**`ruby_source`のバイト列 ＋ 変換ID＋ 合成バージョン**（`TemplateUnit::SYNTHESIS_VERSION`。エンジンが合成内容を変更するたびにインクリメントされる）である。3つの行がこれを運ぶ：
  - ADR-45の実行結果**キー**は、クレームされたglobをハッシュ化した`template-units`の`configs:`スロットを獲得し（これにより、プラグインが自身の`template_globs:`を編集するとキーが移動する）、すべてのユニットダイジェストおよびすべての失敗をハッシュ化する。失敗が含まれているのは、失敗のみを生成した実行であっても回答を生成したことには変わりないためである。これらがないと、そのような実行のキーはテンプレートなしのキーと等しくなってしまい、ADR-87のboot-slimプローブが正確に再構築して（プラグインをロードしない）、テンプレートが修正または削除された後もそれらの行を提供してしまう。このスロットはいずれかのプラグインがglobをクレームしたときは常に存在する ── プローブのキーが意図的に再構築不可能であり、プローブがヒットではなくミスする条件である。
  - 成功・失敗を問わず、実行が読み取ったすべてのテンプレートは、`:stat`ファイル行として記録される依存記述子に加わる。
  - クレームされたすべての`template_globs:`パターンは、マッチしたかどうかに関わらず、`:names` glob行として加わる（#979のメカニズム）。glob行だけがテンプレートの**出現**を検知でき、これがないとプロジェクトの最初のテンプレートは何らかの`.rb`ファイルが変更されるまでウォーム実行から見えないままになっていた。

  プラグインがglobをクレームしないプロジェクトはこれら3つのいずれも追加しないため、既存のキーや記述子は一切動かない。
- **フォークプール**。インデックスは親プロセスで構築され、単一のpre-fork `WorkerSession`に継承されるため、ワーカーは親プロセスがコンパイルしたのとまったく同じバイト列からユニットを解析する。プールされた出力は、診断ストリームとエフェクトテーブルの両方においてシーケンシャルな出力と等しくなる。
- **`--incremental`**。ユニットは依存クロージャに**参加しない**：ADR-46の依存グラフにおいて合成ファイルを指名するものは何もないため、ユニットをクロージャに入れるエッジは存在しない。保守的な解釈が取られ、**実行は常にすべてのテンプレートユニットを再解析する** ── これはウォームインクリメンタルパス上でテンプレートごとに1回のパースを要するが、古い回答を提供することは決してない。ユニットをファーストクラスの依存関係にすることは将来のスライスである。2つの仕組みがこれを支えている：`Runner#target_files`はまず`.rb`展開を絞り込み、次にユニットを追加する（先に追加すると`analyze_only`の選択に飲み込まれてしまう）。そして`IncrementalSession`はユニットpathを`@analyzed`から**除外**するため、ユニットがファイル別キャッシュから提供されることはなく、消失したプロジェクトファイルとして読み取られることもない。
- **エディタモード**。単一バッファの公開（クロージャのない`buffer:`）はエディタが表示しているバッファについて回答するため、他のユニットはその解析セットに加わらない ── すべてのビューを追加すると、エディタが要求していないファイルの診断が公開されてしまう。バッファがテンプレートで**ある**場合、`.rb`バッファと同様にその単一ユニットが解析セットとなり、保存されたファイルではなく**バッファの**バイト列に対して変換が実行される（`TemplateUnits.collect`は`BufferBinding`を受け取る）。これにより、テンプレートを指名する`--tmp-file` / `--instead-of`はエディタが表示しているものを報告する。クロージャを持つ`--incremental --tmp-file`の再チェックは、すべてのユニットを解析する。
- **インデックスの引き継ぎ（#1038）**。`Analysis::ProjectScan`はコンパイルされたインデックスを保持するため、長時間稼働する`LanguageServer::ProjectContext`はキーストロークごとにプラグイン変換を再実行しない ── ERBの場合、これは公開ごとにプロジェクト内のすべてのビューに対するErubiコンパイルであった。`prebuilt:`ランナーはスナップショットのインデックスを`TemplateUnits.collect(previous:)`に渡し、高コストなものを保持しつつ低コストなものを再実行する：クレームされたglobは実行ごとに再展開され（globのみがテンプレートの出現や消失を検知する）、生き残ったすべてのテンプレートはADR-87のstat-then-digestパック（`Cache::FileDigest.stat_fresh?`。その権威はコンテンツダイジェストであるため、touchされただけで編集されていないテンプレートは引き続き再利用され、編集されたテンプレートが再利用されることは決してない）を通じて再検証される。このパックは`Cache::FileDigest.with_run`スコープ（`ProjectPrePasses#build_template_units`）の内部に記録され、これによりADR-87の競合ガードが背後に配置される：スコープがない場合、記録の瞬間はパック自体の`File.stat`の後に取得され、競合することは決してないため、コレクタの読み取りとそのstatの間に書き換えられたテンプレートは新しいstatタプルとともに古いダイジェストとして記録され、それ以降タプルの高速パスから永遠に提供されてしまう。プラグインが**辞退した**（または変換が例外を送出した）テンプレートはユニットを生成しないため、引き継ぐべきものは何もなく、公開ごとに再提供される ── コストは辞退したテンプレートごとに1回の変換であり、ネガティブキャッシュはそれとともに`plugin_loader`の行を運ばなければならない。
  3つの事象がインデックスを全面的に再構築する。いずれもバイト列が動いていない場合でも変換が生成する内容を変更し得るためである：異なるルート、異なるクレーム対象globの集合、異なるglobクレームプラグインの集合。さらに1つの事象が単一プラグインのクレームを全面的に再構築する（[#1047](https://github.com/rigortype/rigor/issues/1047)）：ディスク上でそのプラグインのテンプレートのいずれかが編集、追加、または削除された場合（ユニットを生成しなかった削除されたテンプレートは、この検知が見逃す唯一の変更である。それは兄弟が読めるものには何も寄与しなかった）。変換はそのプラグインの**他の**クレームされたテンプレートを読み取る可能性がある（rigor-actionpackはパーシャルをレンダリングするすべてのビューからそのlocalsをシードする）。そのため、テンプレート自体の鮮度はそのユニットを保証できず、継ぎ目はどのユニットが独立しているかを宣言するようプラグインに求めない。エディタのバッファは除外されるため、これがキーストロークのコストになることは決してなく、オーナーが無効化していないディスク上の編集でのみ影響する（保存すると`didChangeWatchedFiles`が発火し、いずれにせよコールドで再構築される）。プラグインが辞退したテンプレートは単純なstatパックとして保持されるため、変更されていないバイト列が編集として解釈されることはない。変換がそのようなファイル間状態をメモ化するプラグインは、`Plugin::Base#template_units_pass_started`を通じてパスが開始されたことを知る。これはすべてのユニットが引き継がれる場合でも、任意の`#template_units_for_file`の前にパスごとに1回呼び出される。これとは別に、インデックスの残りの部分が何を行うかに関わらず、エディタのバッファがバインドされているpathは公開ごとにバッファのバイト列から再コンパイルされ、そのユニットが共有インデックスに入ることは決してない。スナップショットはfreezeされているため、**スキャンが構築されて以降に**ディスク上で編集されたテンプレートは、オーナーが無効化するまで公開ごとに再コンパイルされる ── 変更されたテンプレートのクレーム内のテンプレートごとに1回のコンパイルであり、保存すると`workspace/didChangeWatchedFiles`が発火して無効化される。CLI実行は`previous:`を渡さず、以前とまったく同様にスクラッチからインデックスを構築する：そのプロセスは実行とともに終了するため、引き継ぐべきものは何もなく、健全性を証明すべき第2のキャッシュもない。
- **パスの綴り（Path spellings）**。ユニットはクレームされたglobが綴るとおりにキー設定され（`Dir.glob(base:)`が返すプロジェクト相対パス）、ルックアップやクレームテストの前に他のすべての綴りはその形式へと縮約される（`Analysis::TemplateUnitPaths`）。見かけよりも多くのバリエーションが存在する：言語サーバーは絶対パスでバッファを指名し、シェルは`./app/views/x.rbx`や`lib/../app/views/x.rbx`を渡し、シンボリックリンク経由で到達した同じディレクトリは同じディレクトリである（`Dir.pwd`は常に解決される。macOSではエディタの`/var/…`とpwdの`/private/var/…`は同一の場所であり、解決は最も近い**既存の**祖先まで辿るため、エディタがまだ作成していないディレクトリ内のビューであっても解決される）。その縮約後も依然として絶対パスであるパスは**プロジェクト外**であり、アンカーのないクレーム（`**/*.rbx`）はそれに到達しない：プラグインのglobはプロジェクトに対するクレームであり、`Dir.glob`がそのパスを返すことはあり得ない。
- **位置プローブ（Position probes）**。ロードされたプラグインの`template_globs:`がクレームするパスに対する`rigor type-of`は、実行のインデックスを構築し、ユニットの**コンパイル済み**ソースを`parse_scopes`でパースし、`seed`を通じてファイルスコープをシードし、逆マップ（`Analysis::TemplateUnitPositions`、[#1040](https://github.com/rigortype/rigor/issues/1040)）を通じて要求された**テンプレート**位置を解決する。どのプラグインもクレームしないパスはインデックスを構築せず、以前とまったく同じようにプローブする。変換が例外を送出したクレーム対象テンプレートはその失敗を報告して終了コード1で終了する。プラグインが辞退したテンプレートはその旨を述べた上で、コマンドが従来ファイルをプローブしていたとおりにプローブされる。逆マップは導出されるのではなく選択される。なぜなら、継ぎ目が出荷するものは何一つそのように動作しないからである：
  - **行（Lines）**。`line_map`は単射ではないため、テンプレート行はその`template_line`がその行であるコンパイル済み行の**集合**を指名する（そこからの診断が報告するのと同じ集合）。
  - **列（Columns）**。列は対応しないため、**最長一致の逐語的連続部分（longest verbatim run）**を通じて解決される：その列におけるテンプレートのバイトが、それらのコンパイル済み行上のすべての一致するバイトと照合され、バイトが一致する限り各配置が拡張され、最長の一致が勝つ。回答はマッピングされたオフセットにおける最も深いコンパイル済みノードであり、その最長の一致が**一意**であり（同点は2つの読み方 ── 曖昧として辞退される）、ノードが単一行上の連続部分の完全に内側に位置し、**他の**配置のノードが自身の連続部分の内側かつ勝利した連続部分のコンパイル済みスパンの外側に位置していない場合にのみ受け入れられる。「完全に内側」という条件はマークアップを排除する：コンパイラはテンプレートテキストを文字列リテラルにコピーし、リテラルの引用符はテンプレートのバイト列ではない。これはコンパイラがコピーではなく**書き換えた**コードも同様に排除する（rigor-actionpackの`yield` → `__rigor_yield`）。
    対抗配置（rival-placement）条件が存在するのは、より長い連続部分がそれだけでより良い解釈とは言えないためである：コンパイラ自身の句読点がテンプレートのバイト列を結合してテンプレートには存在しなかった連続部分を作り出すため、`<%=`の`=`が`<=`、`==`、`+=`や代入の`=`と一致し、`"= v "`（4バイト、**誤った**`v`で終わる）がタグ本文`" v "`を上回ってしまう。これがないと、`<%= v %><% if 1 <= v %>`はもう一方の`v`について回答し、終了コード0で`rigor check`が不同意とする型を返していた。勝利した連続部分の**内側**での繰り返しは対抗相手とはみなされない。なぜなら、1つのタグ本文は1回コピーされ、2回目の出現はもう一方の端から見たそのコピーだからである：この例外がないと、`<%= @author.nil? ? l(:a) : l(:b, f(@author)) %>`は辞退され、実際のビューの混み合った行の回答の3分の1が失われていた。依然として辞退されるのは、**タグをまたぐ**繰り返し（`<%= v %> <%= v.to_s %>`、または文字列の`v`でプローブされた`<%= v %><%= "v" %>`）であり、これはタグがどこにあるかを知らない代償である。プラグインによってエクスポートされたタグスパンがあればこれらに回答できるようになり、このルールはその先を見据えて保守的になっている。
  - **巻き上げられたテキスト（Hoisted text）**。このテンプレート行自身の上の最も近い**空行でない**コンパイル済み行が、こぼれ先（SPILL）ターゲットとして検索に加わり、そこで見つかった文字列リテラルのみがカウントされる。標準ライブラリのERBは行の先頭テキストを上の行に出力するため（`_erbout.<< "\nname ".freeze`）、そのテキスト内のプローブでは、結びつくべきリテラルはこのテンプレート行のコンパイル済み行にはまったく存在しない：こぼれ先がないと、HTMLの単語でプローブされた`name <%= name %>`はタグのコードとして型付けされていた。それが「テンプレート行L-1のコンパイル済み行」ではなく最も近い空行でない行である理由は、1つのテキストギャップは1つのリテラルであり、コンパイラが飲み込んだ行を空白で埋めるため、リテラルは何らかを出力した最後の行（L-1自身がタグを持っていた場合のみL-1）に位置するからである。そこにある**コード**ノードはカウントされてはならない。さもないと、連続するテンプレート行で繰り返されるすべての`<%= v %>`が辞退されてしまう。
    「そのノードがコードのように見える配置」によるタイブレークは、同じ系統の理由で却下された：コードを優先するとテキストの単語を型付けしてしまうことになる。
  裸の`FILE:LINE`は、そのスパンが正確な形式によってその式が始まる場所から始まるノードへと解決されるテンプレート列に逆マッピングされる、それらのコンパイル済み行上の式のみを一覧表示するため、テーブルは`FILE:LINE:COL`が辞退するような列を出力することは決してない。`--trace`のフォールバックはテンプレート行で報告され、その位置が逐語的連続部分にある場合にのみテンプレート列で報告される。このルールはERBについて何も知らない：恒等変換は1行につき1つの連続部分であり、ERBコンパイラはタグ本文につき1つである。`dump_type`ヘルパーには独自のプローブパスはない ── それは`rigor check`の診断であるため、シードされたスコープの下でコンパイル済みユニットをすでに型付けし、テンプレート行で報告する。言語サーバーのホバーはまだユニット経由でルーティングされていない。
- **その他のファイルセット**。ユニットは**解析対象**ファイルであり、決して`source_files:`のファイルではない：環境構築時の`source_rbs_synthesizer`には`.rb`展開のみが提示される。なぜなら、テンプレートのバイト列はRBSシンセサイザーが読めるRubyではないからである。`RunStats#target_files`はユニットをカウントする。それらは実行がパースしたファイルであるためである。

実装済みコンシューマー：`spec/fixtures/template_units/view_demo_plugin.rb`（#392が出荷した恒等変換）、および[#393](https://github.com/rigortype/rigor/issues/393)以降で`app/views/**/*.erb`をクレームし、解析対象プロジェクトのバンドルで解決できる場合はErubiを通じて（[ADR-90](../../adr/90-target-library-resolution-from-project-bundle/)）、そうでない場合は標準ライブラリの`ERB`を通じてそれぞれをコンパイルする**rigor-actionpack**。

#392がそのコンシューマーに必要であると予想していたものの、実際には必要としなかった2つの事項：

- これは`#template_units_for_file`**だけ**を変更するのではない。コンパイルされたテンプレートの型付けはまだ1行ごとの診断に値するものではないため、上記のユニットごとのルール姿勢を必要とした。また、`view:`ユニットキーが`effects.envelopes:`の対象（`Effects::MethodKey.envelope_owner` ── ビューにはオーナークラスがなく、`MethodKey.split`は`view:users/show.html`をクラス名`view:users/show`の下にグループ化してしまい、そのようなクラス名は実行で生成されたことがない）である必要があった。
- コンパイルされたRubyが**パースできない**テンプレートは、継ぎ目の`[]`の出口を通じて、引き渡されるのではなくプラグインによって辞退される。レイアウトがその実測ケースであった：`<%= yield %>`は正当なERBであり、メソッド外では不正なRubyであるため、その代替案はRailsがレンダリングするテンプレート上のレイアウトごとに2つのパース診断が出ることだった。[#1047](https://github.com/rigortype/rigor/issues/1047)はそれを**継ぎ目の中ではなく、変換の中で**解決した ── プラグインはどちらのコンパイラを実行する前にも、`yield`キーワードを合成されたビューコンテキスト上の呼び出しへと書き換える。これはこのセクションのPositionsルールが強制する形状である：本文を合成メソッドでラップするとすべての行がシフトし、プラグインのマップに第2のマップを合成することになるため、書かれたとおりにパースされなければならない本文は書かれたとおりに書き換えられなければならない。書き換えは幅を保持するものではなく、保持する必要もない ── 空でない`line_map`を持つユニットは、構造上列1で報告される。
- コントローラーのアクションは、レンダリングするテンプレートへとエッジで**結ばれる**（[#1048](https://github.com/rigortype/rigor/issues/1048)）。これはこの継ぎ目内の何らかを通じてではなく、アトリビューション行の`callee:`ルールを通じて行われる：テンプレートユニットがすでに保持しているユニットキーはエッジが指名するcalleeキーであるため、2つの半分は新しい解決なしにサマリーテーブルで出会う。`render`テイントは、エッジが解決されない場所（計算されたターゲット、またはどのユニットも応答しない名前）で正確に残存する。#1047以降、レイアウトはユニット**である**ため、ビュー側の`render layout:`は他のパーシャルレンダーと同様に解消される。エッジで結ばれないまま残るのは、Railsが*アクションの*テンプレートをラップするレイアウトであり、その名前はクラス本文の宣言＋慣例によるルックアップであるため、calleeルールが読めるものの範囲外である。
