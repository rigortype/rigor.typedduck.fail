ステータス: **ドラフト**。この文書はRigorがエフェクトサマリーをどう*生成する*かを仕様化します: 収集がいつ走るか、コレクターが何を観測してよく何を観測してはならないか、ファイルの寄与がどう形作られマージされるか、プロジェクト全体のクロージャがどう計算されるか、そしてそのいずれかが失敗したとき何が起きるか。それが値を生成するラベル言語——文法、包摂、レジストリ、レーン、汚染原因のenum——は[`docs/type-specification/effect-labels.md`](../../type-specification/effect-labels/)で規範的であり、ここの記述がそれと矛盾する場合は常にそちらが拘束します。根拠は[ADR-103](../../adr/103-effect-labels/);研究は[`docs/design/20260816-effect-labels.md`](../../design/20260816-effect-labels/)です。

「エフェクトラベル」「エフェクトサマリー」「エフェクトエンベロープ」は罠のある複合語です（[`CONTEXT.md`](https://github.com/rigortype/rigor/blob/master/CONTEXT.md)）。素の「エフェクト」は依然として`Rigor::FlowContribution`のフローエフェクトのバンドルを名指します。

## 弁別的な性質

収集は**観測的**です。タイパーがいずれにせよ行う決定を記録し、それ以上を行うようMUST NOT求めてはなりません。具体的には、コレクターはMUST NOT:

- そうでなければ走らないオンデマンドのメソッド走査を引き起こす;
- ディスパッチャーが辞退した呼び出しを解決する;
- `Scope`を変更する、または後の`type_of`が読み返せるものを書く。

これが、スイッチの2つの設定を`rigor check`にとって交換可能にするものです: 収集オンで計算されたファイルごとの診断結果は、オフでも有効であり、その逆も同様です。ゲートは、機能が存在し収集がオフの状態と、収集がオンの状態とで**バイト同一の診断ストリーム**です。

## 有効化

収集は、ロードされた設定が`effects:`ブロックを運ぶとき、そしてそのときに限り走ります——**真偽値ではなく存在**です;`effects: {}`も素の`effects:`キーもどちらもそれを有効にします。`rigor effects`は、プロジェクトの設定をロードし、それがブロックを持たないときは暗黙の空ブロックを適用することで（`Configuration#with_effects_enabled`）、自身の実行のためにそれを有効にします。

他の何も収集をオンにしません。特に、プロジェクトのRBS内の`%a{rigor:v1:effect …}`または`%a{pure}`アノテーションはMUST NOTオンにしてはなりません: アノテーションはプロジェクト全体のコストの崖を作ってはなりません。（そのようなアノテーションを未読として表面化させる`:info`の残余は[#384](https://github.com/rigortype/rigor/issues/384)です。）

`Runner`・`WorkerSession`・`PoolCoordinator`はそれぞれ、すでに保持している設定から有効化を導出するので、ワーカーとその親の間でフラグがずれることはありえません。

### オフのときのコスト

レコーダーは`Analysis::DependencyRecorder`の形に従います: モジュールレベルの有効化カウントなので、`Effects::Collector.active?`は`Thread.current`のルックアップではなく素の整数読み取りであり、記録自体を隔離するスレッドごとのアキュムレータを持ちます。

記録サイトは3つあり、ディスパッチごとのホットパス上にあるのはそのうち1つだけです:

| サイト | 記録するもの | ガード |
| --- | --- | --- |
| `ExpressionTyper#call_type_for`、レシーバー型の計算後 | レシーバーのクラス射影、それが`Dynamic`だったか、その背後の`DynamicOrigin`の原因 | `Collector.active?`——整数読み取り |
| `ExpressionTyper#unresolved_call_result` | すべてのディスパッチティアが辞退したこと | `Collector.active?` |
| `Runner#analyze_file_body` / `WorkerSession#analyze_body`、パース成功後 | ファイルのASTルート | レコーダーの内側——ファイルごとのサイトで、`Thread.current`読み取り1回はすでに無視できる |

## 同一性

エフェクト単位は既存のシンボルテーブルでキー付けされます:

| 単位 | キー |
| --- | --- |
| インスタンスメソッド | `Class#method` |
| シングルトンメソッド（`def self.x`、`class << self`本体） | `Class.method` |
| クラス本体の外の`def` | `<toplevel>#method`（`ScopeIndexer::TOP_LEVEL_DEF_KEY`） |
| `define_method(:literal) { … }` | `Class#literal`、そのブロックを本体として |
| `attr_reader` / `attr_accessor`のリーダー | `Class#name`、合成された∅ |
| `attr_writer` / `attr_accessor`のライター | `Class#name=`、合成された`mutate.self` |

再オープンは**和**を取ります: 1つのキーのすべての`def`が、どのファイルにあろうと1つのサマリーに結合されます。実行時の最後勝ちは解析時には知りえないので、和が健全な読みです。

リテラル名の`define_method`はエフェクトスキャナで行われる発見の拡張であり、`ScopeIndexer`でではありません: defノードテーブルはそれをスキップし、エフェクトの外側ではまだ何もそれを必要としません。

## 単位のスキャンが記録するもの

スキャンは1つのメソッド本体を歩きます。2つの規則がそれを形作ります:

- **封じ込め**。ブロックリテラルの起点は常に囲むメソッドのサマリーに結合されます——呼び出し先がそのブロックを今呼ぼうが、後で呼ぼうが、決して呼ぶまいが——エンベロープはメソッドの*コード*についての契約だからです。したがって走査はブロックリテラルの内部へ降り、ネストした`def`またはリテラル名の`define_method`——それぞれ独立した単位——でのみ止まります。
- **観測**。スキャンがレシーバーについて知るすべては、タイパーがその呼び出しノードで記録したものです。

### 起点

各ラベルバンドルは**起点**（origin）でキー付けされます: 何がそれに色を付けたかと、どのソースが色付けをしたかの組——証明レーンでは`:catalogue`または`:construct`、宣言レーンでは`:attribution`または`:envelope`。起点は**行を持たない**ので、サマリーは行の移動の下で安定であり、スナップショットの差分は書式ではなく振る舞いの変化を示します。呼び出しサイトはレポートのためだけに実行ごとに保持され、サマリーには決して保持されません。

言語構文、起点名ごと:

| 構文 | 起点 | ラベル |
| --- | --- | --- |
| `` `cmd` ``・`%x(cmd)` | `xstring` | `io.process` |
| `$g`読み取り（フレームローカルの特殊変数`$~ $_ $& $` $' $+ $!`を除く） \| `gvar-read` \| `global.read` |
| `$g = …`とその演算子形式 | `gvar-write` | `global.write` |
| `@@cv`読み取り | `cvar-read` | `global.read` |
| `@@cv`書き込み | `cvar-write` | `mutate.static` |
| インスタンスメソッド本体内の`@iv`書き込み | `ivar-write` | `mutate.self` |
| シングルトンメソッド本体内の`@iv`書き込み | `ivar-write` | `mutate.static` |
| 本体内の`alias` / `undef` | `alias` / `undef` | `mutate.static` |
| 本体内の`define_method` | `define-method` | `mutate.static` |
| 変更呼び出し、レシーバーの所有権による | `receiver-mutation` | `mutate.self` / `mutate.instance` / `mutate.local` / `mutate.static` |
| `attr_writer`の合成された本体 | `attr-writer` | `mutate.self` |

カタログ化された起点は、行がマッチした呼び出し先キーでキー付けされます（`catalogue:Kernel#puts`・`catalogue:Time.now`）。

### 所有権

変更呼び出しが主張されるのは、セレクタがそれを確定するときだけです: 任意のレシーバー上の`[]=`と属性ライター、そしてタイパーがレシーバーのクラスを名指したときのクラスごとのミューテータ集合（`MutationWidening::ARRAY_MUTATORS` / `HASH_MUTATORS`、およびStringのもの）。名前のないクラス上の`<<`は意図的に主張**されません**——それは`Array`のappendであるのと同じくらい容易に`Integer`のビットシフトであり`IO`の書き込みです。

ラベルはそのあとレシーバーの所有権に従い、それは構文的な問いです:

| レシーバー | ラベル |
| --- | --- |
| `self`、`@ivar`、または暗黙のレシーバー | `mutate.self`（シングルトンコンテキストでは`mutate.static`） |
| `@@cvar` | `mutate.static` |
| パラメータ | `mutate.instance` |
| すべての代入が確保であり本体から決して逃げないローカル | `mutate.local` |
| それ以外 | **なし**——`unknown-ownership`の汚染 |

`mutate.local`はそのローカルが新規に確保され（`[]`・`{}`・`""`・`+""`・`.new`・`.dup`・`.clone`・ラムダ）、決して逃げないことを要求します。エスケープ解析はフローインセンシティブで本体全体に対するものです: どこかで逃げるローカルは、変更の後であっても資格を失います。これは「変更呼び出しの前に逃げた」より厳密に保守的であり、それが偽陽性の予算が走る方向です（[ADR-5](../../adr/5-robustness-principle/)）。

証明できない所有権は、証明された素の`mutate`を生むのではなく、MUST汚染しなければなりません。

### 汚染

| 原因 | トレーサーが記録するとき |
| --- | --- |
| `dynamic-receiver` | タイパーのレシーバー型が`Dynamic`であり、その静的ファセットが名指したクラスをどのエンベロープも束縛しない（§呼び出しサイトでの宣言レーン）;詳細は記録されていれば`DynamicOrigin`の原因名 |
| `dynamic-send` | 非リテラルのセレクタを伴う`send` / `public_send` / `__send__`（リテラルのものは通常のエッジ） |
| `opaque-callable` | ラムダリテラルでもその単位自身のブロックパラメータでもなく、クラスが未知または`Proc` / `Method`であるレシーバー上の`.call`;またはシンボルでもその単位のブロックパラメータでもない`&expr`ブロック引数 |
| `unresolved-self-call` | **すべての**ディスパッチティアが辞退し、その単位自身のクラスがそのセレクタに対するエンベロープを運んでいない暗黙的self呼び出し;詳細はセレクタ |
| `unknown-ownership` | レシーバーの所有権が分類できない変更呼び出し |
| `collector-error` | その単位のスキャンがraiseした |

`method-missing`・`plugin-attribution`・`template-not-analysed`・`budget`はenumにありますが、このスライスではプロデューサーがありません。

汚染は決して発見を生みません。非網羅的なサマリーは「これらのエフェクト、そしておそらくそれ以上」と読めます。

### このスライスの既知の境界

- `super`はエッジでも汚染でもありません。それを解決するには囲むクラスの*上の*祖先が必要で、伝播器がそれを供給できます;トレーサーを薄く保つために除外されています。
- ディスパッチャーがユーザークラス祖先フォールバックを通じて楽観的に解決する暗黙的self呼び出しは、プロジェクトがそのようなメソッドを定義していなくても汚染**しません**。その形はまさに`call.self-undefined-method`がカバーするものであり、偽陽性を理由に既定でオフです（[ADR-24](../../adr/24-self-method-call-resolution/)スライス4）。
- カタログが列挙しないクラスのレシーバー上のカタログにない呼び出しは何も寄与せず、汚染しません。カタログが列挙*する*クラスはその姿勢で答えます——下記§カタログを参照。
- クラス本体はエフェクト単位ではありません。その文はロード時に走り、それはまだどのスライスもモデル化していない独立した単位です。

## カタログ

`Rigor::Effects::Catalog`は`data/effects/core.yml`——コアと標準ライブラリのクラスの手で監査された表——をロードし、プロセスごとにメモ化し、forkプールをまたいでそのまま継承します。欠落した、または読めないファイルは空のカタログへ劣化します（フェイルオープン、`Registry.load_file`に一致）;存在するが不正なファイルはraiseします。それは選択ではなくパッケージングのバグだからです。

**行は上界です。** 世界に向いたクラスの引数を見ない行はMUST親ラベルでなければなりません: `IO#write`は`io.fs.write`ではなく`io`です。チャネルはファイルであるのと同じくらい容易にソケットだからです。精度が戻るのは、呼び出し自身の引数がそれを証明する場所だけです。

すべての行は1行の`why:`を運び、ローダーはそれを持たない行を拒否します。正当化は監査記録です: このファイルはデータであり、ラベルを行に置いた理由付けはコミットメッセージではなく行の隣に住みます。

行は空のラベル集合であってMAYよく、それは行を持たないこととは同じではありません: 明示的な∅は、カタログがその呼び出しを知っており、それが何も寄与しないことを知っていると述べます。それが、`Thread.new`のブロックが封じ込めによって囲むメソッドに結合される一方で`Thread.new`が未解決と読まれるのを止めるものです。

### 姿勢

Rubyのコアサーフェスはどんなカタログも完成させられないほど大きいので、クラスは**姿勢**（posture）——そのカタログにないメソッドが寄与するもの——を運び、ファイル自身の`defaults:`表から名前を付けられます。3つのティアが重要です:

| クラス | カタログにないメソッドの読み |
| --- | --- |
| 列挙済み、`posture: value` | ∅ |
| 列挙済み、任意の世界に向いた姿勢（`world` → `io`、およびより狭い`fs` / `net` / `http` / `ipc` / `process` / `signal` / `global` / `nondet` / 3つの標準ストリーム） | その姿勢のラベル |
| **まったく列挙されていない** | なし、汚染もなし——すべてのプロジェクトおよびgemクラスの読み |

姿勢集合が「valueは∅ / worldは`io`」より広いのは、`io`が`nondet.random`の上界ではないからです: 列挙されていないメソッドが非決定的であるクラスは、誤った`io`の既定ではなく`nondet`の既定を得ます。本当に混在したサーフェスを持つクラス（`Time`・`Pathname`・`Random`・`Logger`）は、世界に向いた行を綴り出した`value`です。そのパス代数とアクセサに対する一括の`io`は誤ったラベルになり、誤ったラベルは欠けたラベルより悪いからです（[ADR-5](../../adr/5-robustness-principle/)）。

2つの精緻化が、姿勢が通常の呼び出しに**誤った**ラベルを置くことを防ぎます:

- **普遍セレクタリスト**——あらゆるレシーバーに存在し何にも触れない`Object`レベルの名前（`class`・`respond_to?`・`frozen?`・`inspect`・`to_s`・`hash`・`tap`…）——はクラス自身の行の後、その姿勢の前に参照されるので、`socket.class`は`io.net`ではなく∅です。クラス自身の行は依然としてリストに勝ちます。
- クラスは2つの側が異なるときMAY`singleton_posture:`を運んでよいです。`Kernel`がそのケースです: そのインスタンス側はプロセス境界ですが、`Kernel.x`は`module_function`のコピーであり、実際にそのように呼ばれるのは純粋な変換ファミリー（`Kernel.Float`）なので、そのシングルトン側は`value`です。

姿勢は3つの場所でMUST NOT答えてはならず、それぞれがトレーサーがすでに持っていたより具体的な読みを飲み込んでしまいます:

- **暗黙的self**（または`self.`）呼び出し。プロジェクト本体内のあらゆる非修飾呼び出しは`Kernel#name`を綴るので、`world`の既定は世界全体に色を付けてしまいます。
- **`Dynamic`レシーバー**。タイパーが射影したクラスはそこでは推測であり、`dynamic-receiver`が真実の答えです。
- **`send` / `public_send` / `__send__` / `call`**。それら自身の汚染（`dynamic-send`・`opaque-callable`）が同じサイトのより具体的な読みです。明示的な**行**は依然として勝つので、`Fiddle::Function#call`は`ffi`です。

### 行、姿勢、プロジェクトエッジ

**行**はその呼び出しが何をするかについて権威的です;`mutates: receiver`は、その上に所有権の判定（§所有権）を求める方法です。したがって`ENV["k"] = v`は`global.write`であり意図的にレシーバー変更ではなく、一方`Time#localtime`は両方です。**姿勢**はセレクタについて何も述べないので、カタログにないパスの自身の変更規則がそのまま適用されます。

主張された2つの形は依然としてその**プロジェクトエッジ**を寄与し、サマリーはそのときカタログの読みとプロジェクト定義の読みの和になります:

- 暗黙的self呼び出し。非修飾名はまずselfの祖先に対して解決され、同名のプロジェクトメソッドが実行時に勝つからです。`Kernel#format`は本物の行であり、Redmineの`CustomField#format`は本物のメソッドです;和だけが両方を読みます。
- 姿勢の答え。プロジェクトが再オープンするコアクラスは、依然としてそのオーバーライドのサマリーを伝播させなければならないからです。

プロジェクト定義に到達しないエッジは伝播器によって落とされるので、1つを保つコストはゼロで、1つを落とすコストは呼び出し先1つです。

### ミューテータ集合、参照による

値クラスは`mutators: array | hash | string`を名指し、ローダーはそれを`MutationWidening::ARRAY_MUTATORS` / `HASH_MUTATORS` / `MutationClassifier::STRING_MUTATORS`へ解決します。データファイルはセレクタリストをMUST NOT再び綴ってはなりません;specが両方向の一致を固定します。

### 引数依存のナローイング

行の`narrow:`は`Rigor::Effects::Narrowing`のハンドラを名指し、それは**呼び出し自身の引数リテラルだけを読み、他は何も読みません**。データフローなし: スキャンは観測的であり、推論を参照するナローイングはカタログの答えを目の前のソースではなく解析品質の関数にしてしまいます。すべてのハンドラは全域的であり、推測するのではなく行自身の`effects:`——その絞られていない上界——へ劣化します。

| ハンドラ | 読むもの | 行 |
| --- | --- | --- |
| `kernel_open` | リテラルの先頭`\|`はサブプロセス;そうでなければモードリテラルが方向を決めるパス | `Kernel#open` |
| `file_open` | 引数1のモードリテラル、または`mode:` | `File.open` |
| `pathname_open` | 1つ左の同じ引数、レシーバーがパス | `Pathname#open` |
| `time_new` | 位置アリティ: なしは`Time.now`、任意は構築 | `Time.new` |
| `random_new` | 位置アリティ: シードは生成器を再現可能にする | `Random.new` |
| `uri_open` | スキームのリテラル: `http(s)://`・`file://`または素のパス | `URI.open`・`OpenURI.open_uri` |
| `sql_verb` | SQL文の先頭の動詞リテラル: `SELECT`は読み取り、`INSERT` / `UPDATE` / DDLは書き込み、`BEGIN` / `COMMIT`はトランザクション | `connection.execute` / `exec_query` / `select_all`のプラグイン行（#387） |

ハンドラが固定する2つの読み。**不在の**モード引数は未知のものではありません——Rubyの既定は`"r"`なので読み取りであり、計算されたモードや整数フラグはサブシステムの親で答えます。そしてターゲットテストは補間文字列の**リテラルの先頭**を読みます。`open("|#{cmd}")`は残りが計算されていてもサブシステムを決める部分を書いているからです。

### 意図的に行にしないもの

位置引数を伴う`eval` / `instance_eval` / `class_eval` / `module_eval`、および素の`binding`は`opaque-callable`を汚染します: アナライザーが読まないコードについて述べる上界はありません。ブロック形式は封じ込めであり汚染しません。

### `purity:`の禁止

生成された`data/builtins/ruby_core/*.yml`の`purity:`ファセットはエフェクトソース**ではなく**、ローダーは`data/builtins`をMUST NOTまったく開いてはなりません。そのファセットはCディスパッチの意味での畳み込み安全性に答え——`Random#rand`は`leaf`、`Array#push`は`leaf`——それをエフェクトの自由さとして読むことは両方向に誤りです（ADR-103 WD3）。既存のカタログが寄与**する**のは証拠であり、行ごとに引用されます: `c_effects: mutate` / `block`マーカー、`lib/rigor/inference/builtins/*_catalog.rb`内の手で監査された`mutating_selectors:`ブロックリスト、`MethodCatalog::NON_REPRODUCIBLE_SELECTORS`、`MutationWidening`のミューテータ集合、`ClosureEscapeAnalyzer`のエスケープテーブル。

## ファイルごとの形とマージ

ファイルは`FileCollection`を寄与します: その単位の直接サマリー、未解決エッジとして記録した呼び出し、そして伝播器が必要とする祖先関係（`superclasses`・`includes`）。すべてのフィールドはMarshalクリーンです——Stringのフローズンなハッシュ、フローズンな配列上の`LabelSet`、`Data`のエッジ——forkプールがワーカーのコレクションをファイルの診断とともにマーシャルして戻すからです。

マージはあらゆるテーブルで**結合的かつ可換**です: サマリーはキーごとに結合、エッジリストは和、祖先関係はマージ。したがって実行のファイルをプールの完了順に畳み込むと、逐次解析が生むのとまったく同じテーブルになります。

実行のコレクションはMUST**1パス**で畳み込まれなければならず（`FileCollection.merge_all`）、ペアごとの`#merge`に対する`reduce`によってではありません。各ペアごとのマージは蓄積されたテーブル全体を再構築し再フリーズするので、ファイルごとの畳み込みはO(ファイル数 × メソッド数)のコストがかかります——それが計測されるまで、収集をmastodonで+50%、gitlabで+230%の実時間にしていたものです（[`docs/notes/20260817-effect-collection-perf.md`](../../notes/20260817-effect-collection-perf/)）。これはコストの契約であって意味論のものではありません: どちらの綴りも同じテーブルを生成します。

祖先の名前は**書かれたとおりに**記録される（`module Tracer`内の`class Loud < Base`は`Base`を名指す）ので、コレクションはRuby自身のレキシカルルックアップが試みるであろう候補リストを最も修飾されたものから順に運び、伝播器がマージされたプロジェクトが定義するものを選びます。

## 伝播

伝播は`Runner#assemble_run_diagnostics`のプール後の集約スロットで、`conforms_to_diagnostics`の隣で、収集が走ったときにのみ走ります。2つのステップがあります。

**エッジ解決。** 記録された`(receiver class, kind, selector)`について:

1. 定義をレシーバー自身のクラス、次にそのinclude、次にそのスーパークラス連鎖を通じて、再帰的かつ巡回ガード付きで解決する;
2. レシーバーのクラスのプロジェクトサブクラスにある同じセレクタの**プロジェクトが知るすべてのオーバーライドを結合する**。Rubyには`final`がなく、アナライザーはすでに型に対してこの閉世界の姿勢を取っています（ADR-103 WD4）。

サブクラスインデックスは書かれたとおりの各スーパークラスを単一の親——プロジェクトが定義する最も修飾された候補——へ解決するので、異なる名前空間の同名の2つのクラスがオーバーライドを共有することはできません。

プロジェクト定義に到達しないエッジは、汚染されるのではなく**落とされます**: そのような呼び出しの大半はカタログが行を持たない通常の継承された呼び出しであり、それらを汚染するとビットが情報を運ばなくなります。

エッジ解決は`(receiver class, kind, selector)`でメモ化され、推移的サブクラスクロージャはクラス名でメモ化されます。どちらも付随的ではなく必須です: 1つのトリプルは呼び出しサイトごとに1回問われ、Railsのルートクラスのサブクラスの森はさもないと数千回再走査されます。

**不動点。** ソートされたキー順のワークリストで、真の不動点まで:

- `proven(m) = direct(m) ∪ ⋃ proven(callee)`
- `undischarged(m) = undischarged_direct(m) ∪ ⋃ undischarged(callee)`
- `declared(m) = declared_direct(m) ∪ ⋃ declared(callee)`
- `exhaustive(m) = direct_exhaustive(m) ∧ ⋀ exhaustive(callee)`
- `causes(m) = direct_causes(m) ∪ ⋃ causes(callee)`

`undischarged_direct(m)`は、`effects.tolerated:`が解消**しない**直接サマリーの起点バンドルの結合です（§ポリシーによる解消）。それを同じ不動点の第2レーンとして運ぶことが、起点ごとの解消を構造的にコストゼロにするものです: 起点はちょうど1つの単位の直接サマリーに属するので、生き残るバンドルの推移的な和はシードされたもののクロージャであり、どのメソッドも推移的起点の集合を実体化する必要がありません。`tolerated:`リストがなければ2つのレーンは同一にシードされ、2番目はエッジ訪問ごとにアロケーションなしの結合1回のコストです。

**宣言レーンはこの不動点のレーンであり、メソッドごとのファクトではありません**（[`effect-labels.md`](../../type-specification/effect-labels/) §エフェクトサマリー）: 証明レーンとまったく同じようにエッジを旅するので、帰属されたgem呼び出しの2ホップ上のコントローラーは、その呼び出しが残した汚染だけでなく主張を読みます。それは自分自身へ結合され、`proven`へは決して結合されません——その分離が主張が決して発見を生めない理由であり、それはどの消費者の注意でもなく不動点の性質です。

すべてのレーンは`LabelSet`の結合であり、ソースが何も足さないときレシーバーをそのまま返すので、収束した領域はレーンごとに比較1回のコストでアロケーションなしです。

束は有限（閉じた語彙上のラベル集合 × 1ビット × 閉じた原因enum）であり、すべてのステップは単調なので、再帰的または相互再帰的な巡回はそれ自体で収束します。**ここでは再帰の上限は使われず、望まれもしません**——戻り値型の走査のKleene反復と違い、強制すべき広げはありません。

キーのクロージャが動くと、それを**呼ぶ**メソッドのクロージャしか動きえないので、各パスは前のパスで変わったものの呼び出し元だけを再訪問します——決してテーブル全体ではなく。エッジに沿ってレーンを結合することは、何も足さないときMUST NOTアロケートしてはならず、それが収束した領域上のパスを無償にするものです。

ソートされた反復順序が、プールされた実行と逐次実行が単に同等ではなく同じテーブルを生成するようにするものです。（束は有限ですべてのステップは単調なので最小不動点は一意であり、訪問順序はそれを変えられません;ソートされたパスは*作業*も再現可能にします。）

テーブル上のレーンは**生**です。描画規則——同じ行の証明集合がすでに認める宣言ラベルは落とされる。証明レーンが厳密により多くを述べるから——は出力が生成される場所（`EffectTable::Entry#rendered_declared`・`Snapshot.entry_for`）で適用され、テーブルには決して適用されません。さらなる結合が実際に何が宣言されたかを見る必要があるからです。

結果はランナー上の`Rigor::Effects::EffectTable`（`Runner#effect_table`）であり、マージされた直接コレクションは別途利用できます（`Runner#effect_collection`）。**それは診断ではありません**: `rigor check`のストリームに決して入らず、実行の終了コードはそれが計算されたかどうかにかかわらず同一です（[ADR-102](../../adr/102-unused-code-reachability-report/)のレポート対診断の境界線）。

## エンベロープ: 読み取りとチェック

エンベロープのラベル言語と、境界が何を意味するかは[`effect-labels.md`](../../type-specification/effect-labels/) §エフェクトエンベロープで規範的です。アナライザー内部なのは、エンベロープが*どこから*来て、チェックが*いつ*走るかです。

### リーダーはパースし、構築された環境を読まない

`RbsExtended::EnvelopeScanner`はプロジェクト自身のシグネチャソースを直接パースします——設定された`signature_paths:`（または`sig/`の既定）配下のすべての`.rbs`、加えてローダーの`virtual_rbs`エントリー。後者はrbs-inlineの`# @rbs %a{…}`コメントとプラグインの`source_rbs`合成が到来する方法です。`RbsLoader`の構築された環境は歩き**ません**。それは明白なルートであり`ConformanceChecker`が取るルートですが。

2つの理由があり、どちらも拘束力があります:

- **環境キャッシュはロケーションを破壊する。** `Cache::RbsEnvironmentMarshalPatch`はすべての`RBS::Location`をゼロ範囲の`<cached>`センチネルへダンプするので、ウォームな実行は宣言がどのファイルから来たかも、ましてやどの行かも言えません。診断は境界が書かれた場所を名指さなければならず、その日の2回目の実行で黙って発火しなくなるチェックは、決して発火しないものより悪いでしょう。
- **信頼規則を構造的に強制する。** ADR-103 WD6はプロジェクトが著したエンベロープをチェック済み層にします。プロジェクト自身のソースだけを読むことは、rbs coreやgemが出荷するRBS内の`%a{pure}`が、たまたま同じキーを共有するプロジェクトメソッドを束縛できないことを意味します——間違えうるパスフィルタなしに。

コストは実行がすでにglobするツリーの1回のパースであり、`effects.check`がオンのときにのみ払われます。

リーダーはあらゆるレベルでフェイルソフトです: パースできないシグネチャはエンベロープを寄与せず（ローダーがすでにそれを隔離し`rbs.coverage.quarantined-signature`を報告する）、不正なペイロードと`pure`/`effect`の矛盾はスキャンが所有する`RbsExtended::Reporter`に記録され、認識されないラベルは`Effects::Envelope#unknown_labels`に乗ります——タグの完全なトークンリストがその隣の`#declared_labels`にあり、それが診断にリスト全体がこの語彙で書かれたかを問わせるものです。不正なペイロードと認識されないラベルは異なる扱いを持つ異なる状態であり、マージしてはなりません: 前者は文法に違反し、後者はそれに従いました。

### 未知のラベルと残余

2つの`:info`診断がエンベロープリーダーの残す継ぎ目を読みます。どちらもエンベロープチェックと同じキャッシュ規則のためにそこで計算され、それぞれが**もう一方**が起きえない実行にゲートされています。

**`effect.unknown-label`**はエンベロープパス、その`effects.check`ゲート、そのプロジェクトのシグネチャの単一走査に乗ります。強制と一緒にすることが要点です: それは宣言が強制を**やめた**ことを報告するので、強制をオンにするスイッチが、強制を正直に保つ診断にとって正しいスイッチです。

- `Effects::LabelIntent.evident?`がFPゲートです——[`effect-labels.md`](../../type-specification/effect-labels/) §未知のラベルの4つのシグナル。`(token, registry, siblings)`上の純粋な述語なので、設定側と宣言側のプロデューサーが乖離することはできません。
- `Effects::UnknownLabelReport`が描画し、`Effects::UnknownLabelCheck`が歩きます。チェックは値オブジェクトを答え、決して診断でもファイルシステムでもなく、その呼び出し元から`subject` / `consequence`の言い回しを受け取ります——それが4つの`.rigor.yml`ラベルサーフェス（`tolerated:`・`labels:`・`envelopes[].effect`・`attribution:`の値）がそれぞれ、1つのウォーカーを通じて、読み手が編集すべき場所を名指せるようにするものです。
- 発見は**書かれた場所**（`[location, spelling, token]`）で重複除去され、それが束縛するメソッドキーではありません: `def self?.x`メンバーは1つのアノテーションから2つのキーを宣言し、直すべきタイポは1つです。
- 位置は宣言です。`.rbs`のロケーションはそのまま使われます。`.rb`ファイル内のロケーションは`virtual:`バッファからしか来ておらず、rbs-inlineのライターは生成された各メンバーの上に作者のコメントブロックを再出力します——したがって合成された行はその上のすべての本体の長さだけソース行からずれ、パスはRubyファイル内でアノテーション自身の`%a{…}`テキストを見つけて再アンカーします。設定値はロケーションをまったく持たず、`.rigor.yml:1:1`に着地します。`rbs.coverage.quarantined-signature`の先例です。
- 抑制コメントは`.rb`ファイルからのみ読まれます。`# rigor:disable`を探すために`.rbs`や`.rigor.yml`をRubyとしてパースするのは、機能を装った嘘でしょう;それらの位置は`disable:`とベースラインで抑制可能です。

**`effect.annotations-unchecked`**は`Runner::EffectAnnotationResidualPass`であり、そのゲートはちょうど補集合——`effects:`ブロックがまったくない——なので、2つのパスのちょうど1つだけが何かを生みえます。それは無償のままでなければならないサーフェス上で走り、それがその予算を固定します:

- エンベロープチェックが使うのと同じ層規則である`Effects::SignatureSources`を再利用するので、残余は何がプロジェクト自身のシグネチャと数えられるかについてチェックと決して食い違えません。
- 検出は行ごとの`SignatureSources::ANNOTATION_HINT`——`.rbs`テキスト上のルーティング正規表現で、RBSパースも解析もありません。シグネチャツリーのないプロジェクトは何にもマッチしない`Dir.glob`のコストです。
- 実行が**すでに**解決したローダーを受け取り、決して構築しません。エフェクトオフのパスでの環境構築はプロジェクトが求めていないコストなので、rbs-inlineコメントとしてのみ書かれたアノテーションは、ローダーがたまたま手元にあるときに検出され、そうでなければ検出されません。アドバイザリの`:info`の過少報告はフェイルクワイエットの方向であり、他の何もこのパスに依存しません。
- `.rigor.yml`ではなく最初のアノテーションに位置づけられます: 修正は設定の編集ですが、不活性なものは作者が書いたものです。

### `.rigor.yml`に書かれたエンベロープ

`effects.envelopes:`は第2のエンベロープ層です——同じ`Effects::Envelope`値に、アノテーションなしで到達する（[`effect-labels.md`](../../type-specification/effect-labels/) §規約によるエンベロープ）。`Effects::ConfigEnvelopes`がそれを所有し、意図的に分けられた2つのステップで:

- **`.build`**は各エントリーの`effect:`リストを実行のレジストリに対して一度解決し、エントリーの境界——いずれかのメンバーが認識されないときは`LabelSet::TOP`。アノテーションが取るのと同じフェイルオープンの劣化——と、`effect.unknown-label`プロデューサーが読む`unknown_labels`を生成します。
- **`.for_classes`**は、エフェクトテーブルが実際に運ぶクラス名上で、各エントリーがどのクラスを選択するかを決めます。`namespace:` globは完全修飾名をセグメントごとにマッチします;`match:` globは、`Runner#effect_sources`から、プロジェクトルートに対して相対化され`File.fnmatch?` + `FNM_PATHNAME`で比較された、そのクラスのメソッドのいずれかを定義する任意のファイルにマッチします——`unused --entry-point`と`effects.snapshot.reach:`の意味論を一度綴ったものです。クラスを選択する**最初の**エントリーが勝ちます。

結果はクラスキーのエンベロープマップであり、`Effects::EnvelopeCheck.distribute`が3層を1箇所で適用します: メソッドごとのアノテーションはクラスレベルのアノテーションに勝ち、それは設定されたエントリーに勝ちます。設定されたエンベロープは、`#rebind`が自身の`source`を保つ唯一のものです。分配こそが*それ*だからです——メッセージで名指す価値のあるファクトは、それが分配されたクラスではなくスタンザ（`.rigor.yml effects.envelopes[2]`）です。

設定された層はRBSの走査に依存**しません**。シグネチャツリーのないプロジェクトはその規約を判定してもらえます: アノテーションのスキャンはローダーがないか何も見つからないときスキップされ、パスは設定エントリーだけで進みます。それがこのサーフェスの要点のすべてです——1つのスタンザが、RBSが存在する前の初日から、アーキテクチャの層をチェックします。

### ポリシーによる解消

`effects.tolerated:`は`Effects::Discharge`によって、判定時に、他のどこでもなく適用されます。規則は起点ごとです: **バンドルは、そのラベルのいずれかが許容されたときに解消される**。起点は1つの呼び出し先または1つの構文であり、それが*何のため*だったかを許容することはそれに付随して来たトランスポートを解放するからです。2つの消費者、1つのポリシーオブジェクト:

- **エンベロープチェック**、上の伝播器の`undischarged`レーンを通じて。`EnvelopeCheck.run(apply_tolerated: false)`は代わりに`proven`を読み、それが`--no-tolerated-effects`です。
- **スナップショット差分**、`Snapshot.undischarged_index`を通じて——現在側の`{table => {symbol => [label]}}`で、スナップショットの隣に構築され、その中には決して保存されません。*追加された*ラベルはそのとき、それを導入するあらゆる起点が解消されるときちょうど許容されます;*削除*は参照すべき現在側の起点が残っておらず、ラベルで判定されたままです。インデックスなし（テーブルのない呼び出し元）では両方ともラベルの読みへフォールバックします。

ディスク上の記録は両方向で未解消のままであり、コレクターは未解消のラベルを帰属させます: ポリシーはファクト上のレンズであって、それらへのフィルタでは決してありません。

### 呼び出しサイトでの宣言レーン: `EnvelopeIndex`

`Effects::EnvelopeIndex`はエンベロープについてのもう1つの問いに答えます。`EnvelopeScanner`と`EnvelopeCheck`は「**この**メソッドの本体を何が束縛するか？」を問い、プロジェクト自身のソースだけからそれに答えます。それが契約をチェックできる層だからです。インデックスは「私が呼んでいるものは何を約束するか？」を問い（[`effect-labels.md`](../../type-specification/effect-labels/) §呼び出しサイトでの宣言レーン）、したがって1つ多い層を読みます。

**インポートが起きる場所。** `Effects::UnitScan#import_envelope`で、`#attribute`の隣で、カタログがルックアップされるのと同じ`(owner, selector)`上で——1つの違いを伴い、それがこのメソッドが存在する理由のすべてです: レシーバーなしの呼び出しはカタログには`Kernel#name`と綴られ、それに対するエンベロープキャリアは囲む単位自身のクラスなので、スキャンは`owner_class:`を渡されます。それが生成するのは、呼び出し先キーにちなんで名付けられたソース`:envelope`の`Origin`の下の`Summary#declared_bundles`内のバンドルです。それはカタログの代わりではなく隣で走り、決して呼び出しを主張しません。

**エンベロープによって網羅的。** 返されたエンベロープはまた、カタログにないパスにサイトが未知ではなく束縛されていると告げるものであり、それが[ADR-103](../../adr/103-effect-labels/) WD6の解消です:

- 静的ファセットが依然としてクラスを名指す`Dynamic`レシーバーは、そのクラスのメソッドがエンベロープを運ぶとき`dynamic-receiver`の汚染を寄与**せず**、そのプロジェクトエッジは寄与します——したがって閉世界の証明レーンは依然としてプロジェクトが定義するオーバーライドを通じて旅し、知りえない残余だけが境界で答えられます;
- すべてのディスパッチティアが辞退した暗黙的self呼び出しは、単位自身のクラスがそのセレクタに対するエンベロープを運ぶとき`unresolved-self-call`の汚染を寄与しません。プロジェクトがメソッドとその境界の両方を宣言したからです。

⊤のエンベロープはエンベロープではありません: `EnvelopeIndex#[]`はそれに対してnilを返すので、未知のラベルで劣化したタグはインポートも解消もできません。

**第2のエンベロープソース、そしてそれが読み取り専用である理由。** 受け入れられた層は`Environment::RbsLoader#each_annotated_method_member`——アノテーションを運ぶすべてのメソッドメンバーを生成する、**構築された**`RBS::Environment`の走査——から、`RbsExtended::EnvelopeScanner.from_loader`を通じて来ます。3つの性質が、プロジェクトが書いていないRBSを読むことを安全にします:

- 契約チェックに到達できません。`EnvelopeCheck`と`LiskovCheck`は`EnvelopeScanner.scan`のプロジェクトソースのテーブルを渡され、決してこれを渡されないので、除外は間違えうるフィルタではなく構造的です。
- `location`を運びません。ADR-54の環境キャッシュがすべての`RBS::Location`を`<cached>`センチネルへダンプするからです。診断はそのような境界が書かれた場所を、たとえ望んでも名指せません——それはプロジェクト側のリーダーに環境を歩くのではなくパースさせたのと同じファクトを、反対側から読んだものです。
- チェックすべき本体がありません。gemメソッドは定義上未解析です;WD6はADR-1がすでにその型を信頼するのと同じ理由でその宣言を信頼します。

プロジェクト自身のシグネチャも構築された環境にあるので、受け入れられたテーブルにも現れます。それは無害です: プロジェクトの層が先に参照され、両方が解消します。クラスレベルのアノテーションは意図的に環境から読まれません——分配は「発見が知るそのクラスのすべてのメソッド」を必要とし、それはプロジェクトのファクトです。

インデックスは**プロセスごとに**一度、解析が解決する最初の環境から構築され（`Runner#effect_envelope_index`・`WorkerSession#effect_envelope_index`）、帰属テーブルとまったく同じように収集ウィンドウに運ばれます（`Collector.collect_for(path, attribution:, envelopes:)`）。ワーカーは親と同じ設定と同じシグネチャ内容からそれを導出するので、2つは同期を保つチャネルなしに一致します。それは`effects:`ダイジェストを通じて、そしてRBS層については診断同一性がすでにカバーするシグネチャファイルを通じて、エフェクトのキャッシュ同一性に参加します。

### Liskov包含: `LiskovCheck`

`Effects::LiskovCheck`は`effect.liskov-widened`を決め、`EffectEnvelopePass`の層の単一解決と発見テーブルの単一強制に乗ります——2つの契約はメソッドを*どの*境界に対して拘束するかで異なり、境界がどこから来るかや発見がどこに位置づけられるかでは異なりません。

- それが解決するエンベロープは、生のメソッドごとのアノテーションのベース上の`EnvelopeCheck.distribute`のものです。ベースが重要なのは1つの形です: メソッドが`.rbs`にのみ存在する基底クラス——Rubyの本体を持たない抽象的な`def find: (Integer) -> User`——はエフェクトテーブルにキーを持たず、したがって分配されたエントリーもなく、その境界はまさにオーバーライドが継承するものです。
- 祖先関係は`FileCollection#superclasses`、コレクター自身の書かれたとおりの候補リストであり、ここでは`Propagator::Index#build_descendants`が解決するのと同じように解決されます: プロジェクトが定義する最も修飾された候補が勝つので、`A::Base`と`B::Base`が素の綴り`Base`を共有することはできません。閉世界のオーバーライド結合と同じテーブルを読むことが、Liskov関係と証明レーンが誰が誰から継承するかについて食い違うのを止めるものです。
- 位置は`EnvelopeCheck::Positions#for`から来ます。そこが「Rubyの`def`、クラスのファイルへフォールバック」が両ルールに対して一度綴られている場所です。

### プラグイン層: フレームワークの帰属とフレームワークのエッジ

**ステータス: #387以降規範的。** フレームワークをモデル化するプラグインは、プロジェクト自身のソースが供給できない3つのものを、すべてフローズンなマニフェストフィールドを通じて寄与します（`docs/internal-spec/plugin.md` §エフェクトの寄与）: **ラベル**（`effect_labels:`）は`Registry.for_configuration(configuration, plugin_facts:)`を通じて実行の語彙に加わり;**帰属**（`effect_attributions:`）はフレームワークへの呼び出しに色を付け;**エッジ**（`effect_edges:`）は呼び出しサイトの構文が含まないフレームワークが行う呼び出しです。

コンパイルされた形は`Effects::PluginFacts`であり、`configuration.effects_enabled?`の背後でプロセスごとに一度構築され、帰属テーブルとエンベロープインデックスとまったく同じように、同じ理由で収集ウィンドウに運ばれます（`Collector.collect_for(path, plugin_facts:)`）: forkプールのワーカーはMUST親と同じテーブルの下でスキャンしなければなりません。`Plugin::Registry#effect_contributions`は遅延です。プラグインはプロジェクトのファクトからその行を導出してMAYよく——rigor-activejobはその`IoBoundary`を通じて`config.active_job.queue_adapter`を読む——収集オフの実行はその読み取りを払ってはならないからです。

#### 帰属

`UnitScan#attribute_plugin`で、カタログの隣、`effects.attribution:`の隣で、同じ呼び出しに対して参照されます。3つのレシーバー形が構文の近い順に試され、適用される最初のものではなく**すべての**形が試されます: プロジェクト自身のスーパークラス連鎖を通じてマッチしたクラス名（`User < ApplicationRecord < ActiveRecord::Base`上の`user.save`に到達する`ActiveRecord::Base#save`）、書かれたとおりにマッチしたレシーバーパス（`Rails.cache` + `read`）、`within:`でスコープされたselfパス（コントローラー内の`self.session` + `[]=`）、そしてレシーバーを生成したクラスでマッチした`on_result:`行（`UserMailer.welcome(u).deliver_now`）。歩かれる祖先関係はクロスファイル事前パスの`discovered_superclasses`で、上限付き・巡回ガード付きです;RBSの祖先連鎖は意図的に参照されません。

ラベルはソース`:plugin`の`Origin`の下の`Summary#declared_bundles`に着地します。サイトが**汚染されるか**が2つの権威を分けます:

| 寄与者 | 汚染 | 読み |
| --- | --- | --- |
| ファーストパーティのバンドル済みプラグイン、`discharge: true` | なし | 「これがそれのすること」——ADR-103 WD6の受け入れられたシグネチャの地位 |
| それ以外の誰でも | `plugin-attribution` | 「これを宣言した、そしておそらくそれ以上」——`effects.attribution:`と同一 |

解消する行は加えて、インポートされたエンベロープとまったく同じように**サイトを束縛します**: `dynamic-receiver`の汚染を抑制し（RailsのRBSを持たないRailsアプリは`Rails`を`Dynamic`と型付けし、どんなアノテーションも決してクリアできない汚染はノイズです）、`unresolved-self-call`の汚染を抑制し（暗黙的selfの`render`は正当に解決されません——定義はAction Packにあります）、レシーバー変更に対する所有権の判定を抑制します（`session[:user_id] = id`は何も型付けしないオブジェクトを書き、行の`mutate`は`unknown-ownership`より精密で、しかもすでに信頼されています）。行は依然として`template-not-analysed`または`opaque-callable`の明示的な`taint:`をMAY運んでよく、それはフレームワークモデルが本当に見られない1つのことを述べます。

#### エッジ

`effect_edges:`は**閉じたエンジン側の戦略enum**を名指します;プラグインは基底クラスだけを供給します。戦略は**フレームワーククラス自身の上の合成エフェクト単位**（`Effects::FrameworkUnits`）として実体化され、同じ走査の間にスキャナーがクラス本体から収穫します:

| 戦略 | 祖先関係が基底に到達するプロジェクトクラス上に合成されるもの |
| --- | --- |
| `:activerecord_callbacks` | `Klass#save` / `#save!` / `#update` / `#touch` / `.create` / `.create!`をクラス本体の`before_save :sym`・`validate :sym`・`after_commit :sym`…へエッジ;`Klass#destroy`をdestroyコールバックへ;`Klass#valid?`をバリデーションのものへ。`validates … uniqueness: true`は同じ単位に`io.db.read`バンドルを追加する。コールバックも一意性バリデータもないトリガーは合成されない。 |
| `:perform_now` | `Klass.perform_now`を`Klass#perform`へエッジ。 |
| `:mailer_body` | `Klass.<action>`を`Klass#<action>`へエッジ、クラスが定義するインスタンスメソッドごとに1つ。 |

呼び出しサイトではなくクラス上に合成することが、これをそもそも動作させるものです: 呼び出しサイトは別のファイルにあり、ファイルごとの収集ウィンドウは1つのファイルを見ます。伝播器はそのあと、通常の`(User, :instance, "save")`エッジを、他のあらゆるエッジが取るのと同じ祖先関係と閉世界のオーバーライド結合を通じて合成単位へ解決するので、サブクラスは自身のコールバックを無償で拾い、`User#save`自体を定義するプロジェクトは合成単位と結合します。

このenumには**`perform_later` → `perform`がありません**。それがADR-103 WD4の「帰属は時計ではなくコードに従う」の機械的な強制です。それに似た唯一のエッジ——`target: :perform_now, method: :perform_later`——は、プロジェクト自身の`queue_adapter = :inline`を読んだプラグインによってのみ出力され、そこではRailsは本当に呼び出し元のスタックでジョブを走らせます。

#### エントリーポイントのプリセット

`effect_entry_points:`は`effects.snapshot.reach:`のプリセットを名指し、`PluginFacts`がコンパイルされるとき`Effects::EntryPoints`に登録されます。プリセットはプラグインが名前を付け、プラグインは検証されている設定*から*ロードされるので、`Configuration`は`reach:`エントリーの**形**だけを検証します;`Snapshot.expand_reach`が存在チェックを行い、そこでraiseします。

### 帰属: 宣言レーンの第2のプロデューサー

`effects.attribution:`は`Effects::UnitScan`で、カタログがルックアップされるのと同じ`(owner, selector)`上で参照されます——定数パスのレシーバーでは構文が名指す所有者、それ以外ではタイパーがレシーバーを射影したクラス。それはカタログの代わりではなく**隣で**走り、決して呼び出しを主張しません: カタログ化された行はRuby自身のサーフェスが証明することを述べ、帰属はRigorが決して読まなかった本体についてプロジェクトが主張することを述べ、両方である呼び出しは正直に両方と読めます。

それが生成するのは、ソース`:attribution`の`Origin`の下の`Summary#declared_bundles`内のバンドルと、サイトでの`plugin-attribution`の汚染です。決して証明されたラベルではなく、決して解消された汚染ではありません（ADR-103 WD6）。2つの帰結が導かれ、どちらも荷重を支えます: 帰属のせいでエンベロープが発火することはありえず、唯一の色が帰属されたメソッドは「クリーン」ではなく「∅、そしておそらくそれ以上」と読めます。主張はそのあと伝播します。`declared`は上の不動点のレーンだからです: 帰属された呼び出しに到達するあらゆる呼び出し元がそれを運びます。

テーブルは実行ごとに一度設定から構築され、収集ウィンドウに運ばれる（`Collector.collect_for(path, attribution:)`）ので、forkプールのワーカーは親とまったく同じ主張の下でスキャンします。それは`effects:`ダイジェストを通じてエフェクトのキャッシュ同一性に参加するので、テーブルを編集すると古いものの下で色付けされたサマリーを再利用するのではなく再収集します。

### チェックが走る場所

`Runner::EffectEnvelopePass`は`#run_analysis`内で、`#compute_run_diagnostics`の**外側**にあります——意図的にであり、他のプロジェクトレベルのストリームが座る`conforms_to_diagnostics`の隣ではありません。

理由はキャッシュです。`assemble_run_diagnostics`の結果はADR-45の実行全体の診断スロットが保存するものであり、`effects:`ブロックはそのスロットの同一性から意図的に不在です（§キャッシュ）——それがプロジェクトがそのチェックを無効化せずに収集をオンにできるようにするものです。そのエントリーに書かれたエンベロープの発見は、したがってそれを生んだ設定より長生きします: `effects.check: false`に反転してもキーは動かず、ウォームなエントリーは発見を提供し続けます。実行が最終的に得たテーブル——ウォームでもコールドでも——の上でパスを走らせることがADR-103 WD12の「毎回再計算、決して保存しない」であり、それはまた、決して集約しないウォームパスも依然として出力することを意味します。

パスは、プロジェクトが使うものに対して払うよう順序づけられています: まずエンベロープを読み、何もなければそこで止まり、エンベロープを宣言したプロジェクトだけが、メソッドキーをそのRubyの`def`へ写像するクロスファイル発見テーブル（`ensure_project_discovery`）を強制するか、`effect.liskov-widened`が読むスーパークラステーブルのために実行のコレクションをマージします。位置は`discovered_def_sources` / `discovered_singleton_def_sources`から来て、自身の`def`を持たない合成されたアクセサでは`discovered_class_sources`へフォールバックします。両方の契約——メソッドと自身の境界、オーバーライドと継承する境界——はその単一の解決に乗ります。

発見はパスを離れる前に、そのファイルのコメントとプロジェクトの`disable:`リストとともに、ファイルごとに`CheckRules.filter_suppressed`を通るので、`def`行上の`# rigor:disable effect.envelope-exceeded`はファイルごとのルールに対するのとまったく同じに振る舞います。下流のすべて——重大度の解決、ベースライン、`--format json`——が適用されます。診断が`apply_severity_profile`の前に通常のストリームに加わるからです。

## スナップショット文書

コミットされたエフェクトスナップショットが主たる検証モードです（[ADR-103](../../adr/103-effect-labels/) WD7）。そのラベル言語は[`effect-labels.md`](../../type-specification/effect-labels/)で規範的です;そのファイル契約はここにあります。

### レイアウト

ファイルは**JSON互換のYAML部分集合**で書かれます——文字列キー、JSONスカラー、フローシーケンス、アンカーなし、タグなし、タイムスタンプなし——ので、その`YAML.safe_load`は`JSON`を通じて変わらずラウンドトリップし、兄弟の実装はYAMLリゾルバーなしにそれを読みます。`YAML.dump`ではなく手書きのライターで描画されるのはまさに、その保証、先頭のコメント、キーの順序がすべて契約の一部だからです。

```yaml
# .rigor-effects.yml — generated by `rigor effects update`. Commit it; review its diff.
schema: 1
rigor: "0.3.3"
vocabulary: 1
config_digest: "9ec82bfc…"
methods:
  "PaymentGateway#charge":
    effects: ["io.net.http", "telemetry"]
  "Reports::Nightly#perform":
    effects: ["io.db.read"]
    exhaustive: false
    unresolved: ["dynamic-send"]
reach:
  "OrdersController#create":
    effects: ["io.db.read", "io.net.http", "job.enqueue"]
```

行ごとに: `effects:`は証明レーン、`declared:`は`≤`レーン、`exhaustive:`はビット、`unresolved:`はそれが偽である理由。両方のラベルレーンは**そのテーブルの**読みで読まれます——`methods:`は直接の宣言集合を、`reach:`は推移的なものを記録します——そして描画規則は行自身の`effects:`がすでに認める宣言ラベルを落とします。読み手が既定にできるフィールドは省略されます——空のとき`declared:`、真のとき`exhaustive:`、何も言うことがないとき`unresolved:`。

`unresolved:`は**汚染原因**を運び、呼び出し名ではなく`cause`または`cause(detail)`として描画されます: コレクターは原因を保持し、詳細を持つ原因については詳細がすでに呼び出し名です（`unresolved-self-call(save!)`）。

### 直接とリーチ

| テーブル | サマリー | メンバーシップ |
| --- | --- | --- |
| `methods:` | **直接**——単位自身の本体、ブロックリテラル、カタログ化された / 帰属された呼び出し先;決してプロジェクトの呼び出し先ではなく、それはエッジ | 実行が収集したすべての単位 |
| `reach:` | **推移的**——伝播器が計算したクロージャ、両方のラベルレーンで | `effects.snapshot.reach:`にマッチするファイルで定義されたすべての単位 |

直接は差分を帰属可能に保つものです: エントリーが動くのは、自身の行、カタログ、または帰属が動いたときだけです。リーチは葉の変更がファンアウト*するべき*場所であり、ファンアウトが情報です。

`reach:`エントリーはファイルglob——パスまたはglob文字を運ぶもの、`File::FNM_PATHNAME`付きの`File.fnmatch?`を通じてプロジェクト相対でマッチ、`unused --entry-point`の意味論——か、`Rigor::Effects::EntryPoints`に登録されたプリセットの素の名前です。プリセットはフレームワークをモデル化するプラグインが寄与します;**このスライスでは1つも出荷されず**、未知の名前は黙って何にもマッチしないglobではなくtier-2の設定エラーです。エントリーポイントのglobは*ファイル*を選択するので、そこに書かれたすべての単位がエントリーポイントです。

### 省略

`--full`はすべてを記録します。それ以外では行は次のとき省略されます

- そのサマリーが網羅的で、証明済み ⊆ `{mutate.local}`——`%a{pure}`の読みで、あらゆるエンベロープが許容する——であり、その宣言レーンが描画規則の後に空で生き残るとき（`methods:`では`Summary#trivial?`、`reach:`では`EffectTable::Entry#trivial?`）。生き残る`≤`境界は行を非自明にします: `≤ io.db`はレビュアーが差分を読む理由であり、行を省略することはそうでないと主張するメソッドについて「クリーン」と言うことになります;または
- **汚染のみ**であるとき: どちらのレーンにもラベルを運ばないので、行は`exhaustive: false`とその`unresolved:`原因以外何も言いません。それは`rigor effects`と`rigor effects explain`が生きたグラフに対して答える問いであり、レビュアーがコミットされた記録に対してラチェットするファクトではなく、Railsアプリケーションではテーブルの過半数です（決定時点でredmineの3,581の`methods:`行のうち2,021——660KBから296KBへ）。網羅性の遷移は、ラベルまたは宣言された境界を運ぶすべての行について可視のままです;ラベルがすべて消えたものは`exhaustive-lost`イベントではなく削除されたシンボルとして読まれ、依然としてゲートします。後でラベルを証明するメソッドは追加されたシンボルとして到来します;または
- その直接サマリーが**合成された既定**であるとき: すべての起点が合成されたアクセサ構文（今日は`construct:attr-writer`;`Struct` / `Data`のアクセサは発見がそれらを合成するとき加わる）。そのような行は`attr_accessor`の行を言い直します。手書きの`def name=`は行を保ちます。その起点は合成された構文ではないからです。

ファイルは興味深いものを列挙するので、不純に*なる*メソッドは追加されたキーとして到来します。

### ヘッダーと決定性

ヘッダーは`schema`（この文書の形）、`rigor`（`Rigor::VERSION`）、`vocabulary`（`Registry#vocabulary_version`）、`config_digest`——正規化された`effects:`ブロックのSHA-256、あらゆる深さでキーをソートしJSONとして描画したもので、ダイジェストはブロックが書かれた順序に依存しない——を運びます。4つのいずれかの不一致は**再生成イベント**です: 記録は異なる規則の下で書かれ、2つの側は比較可能ではありません。

出力は構成上決定的です: キーとラベルはソートされ、タイムスタンプはなく、すべての描画はソートされた`EffectTable`から導出されます。1つのツリー上の2回の`update`と、逐次実行に対するプールされた実行は、バイト同一です。

### 判定

記録は**未解消**です。`effects.tolerated:`とゲートは`Effects::SnapshotDiff`で適用され、書き込み中には決して適用されないので、`update --no-tolerated-effects`と`update`は同じバイト列を書き、ポリシーの変更は記録ではなく設定の差分になります。

イベントカテゴリー、シンボルとテーブルごと: `label-added` / `label-removed`・`declared-added` / `declared-removed`・`materialised`（宣言ラベルが証明済みになった——1つのイベントで、決して削除と追加ではない）・`exhaustive-lost` / `exhaustive-gained`・`symbol-added` / `symbol-removed`、加えて`regeneration`と`missing-snapshot`。現在側が非網羅的である削除は**ヘッジされます**: 「おそらくそれ以上」は不在を証明できません。何も運ばないシンボルはイベントを生みません（`--full`の下でのみ存在します）が、依然としてフッターで数えられるので、リネームは1つの追加と1つの削除として釣り合います。

ゲートはそれらのカテゴリーを読みます。`symmetric`（既定）はあらゆるイベントで失敗します;`additions`は`symbol-added`・`label-added`・`declared-added`・`exhaustive-lost`・`regeneration`・`missing-snapshot`でのみ失敗します——最後の2つは両方のゲートの下で、比較不能な記録はラチェットする対象ではないからです。イベントは、ポリシーがそれが運ぶあらゆるラベルを解消するとき**許容されます**（シンボルイベントはそのシンボルの全集合を運びます）;許容されたイベントは自身の見出しの下で報告され、`--strict-tolerated`でない限りゲートしません。`--no-tolerated-effects`はリストが空であるかのように判定します。ラベルを運ばないイベント——網羅性の遷移、再生成——は決して許容されえません。追加は呼び出し元が現在側の未解消インデックスを供給するとき起点ごとに判定されます（§ポリシーによる解消）;それ以外はすべてラベルで判定されます。

`rigor effects explain`は同じグラフからリーチの半分に答えます: `EffectTable::Entry#edges`上の幅優先走査で、その*直接*サマリーがラベルを証明する最初のメソッドまで行き、そのメソッドの起点で終わります（`Rigor::Effects::PathFinder`）。最短なので、レビュアーは利用可能な最も締まった説明を得ます。`methods:`の変化には経路がありません——ラベルは単位自身の本体から来た——ので、それを説明するのは起点自体です。

スナップショットコマンドはレポートが走らせるのと同じ解析を走らせ、どちらも診断を出さず`rigor check`のストリームに入りません。

## 失敗の隔離

コレクターと伝播器は3つのレベルでフェイルソフトであり、そのどれもチェックを変えたり失敗させたりしてはなりません:

| レベル | 例外時 |
| --- | --- |
| 1つの単位のスキャン | そのメソッドは`collector-error`とともに非網羅的として記録される;その兄弟は影響を受けない |
| 1つのファイルのスキャン | ファイルは`failed?`とマークされた空のコレクションを寄与する;他のファイルは影響を受けない |
| 伝播 | テーブルは空 |

## キャッシュ

1つのキャッシュ、2つの同一性、1つの追加スロット（ADR-103 WD13）。第2のストアはありません: 両方の既存ストアはすでに解決済み設定全体をダイジェストしているので、`effects:`を追加するプロジェクトは何も無効化しません——ブロックは`Configuration#to_h`から意図的に**不在**であり、その不在こそが2つの同一性を、片づけるべき冗長性ではなく独立したものにするのです。

**診断の同一性**は通常のものです。収集は観測的なので、収集オンで計算された診断エントリーはオフの実行に有効であり、その逆も同様で、この節の何もそのエントリーを無効化・書き換え・再形成してはなりません。

**エフェクトの同一性**は診断の同一性に、解析されたバイトを1つも動かさずにサマリーが*意味する*ものを変える4つの入力を加えたものです: 語彙バージョン（`Registry#vocabulary_version`）、カタログの同一性（`Catalog#identity`——そのスキーマと`data/effects/core.yml`の内容ダイジェスト）、`effects:`ブロックのダイジェスト、そして**プラグインファクトのダイジェスト**（`PluginFacts#digest`——コンパイルされたすべてのラベル・帰属・エッジ・プリセットとそれを寄与したプラグイン、#387;`perform_later`を再色付けするプラグインのアップグレードは、ソースが決して動かなかったサマリーを再色付けする）。`Rigor::Effects::Identity`がそれを計算する唯一の場所で、同じ3入力の2つの綴りで: `.digest`（16進文字列、自身のディスクリプタを持たないストア向け）と`.descriptor`（実行のキーディスクリプタに、そのダイジェストを運ぶ1つの`configs:`エントリーを合成したもの）。`Snapshot.config_digest`——スナップショットヘッダーの`config_digest`——は同じメソッドなので、コミットされた記録とキャッシュキーはどの`effects:`ブロックがそれを生んだかについて決して食い違えません。

永続化の単位は**ファイルごとの`FileCollection`**であり、伝播されたテーブルでは決してありません。葉のサマリーはあらゆる呼び出し元に到達するので、保存されたテーブルはプロジェクトのすべてのファイルによって無効化されなければならないでしょう;代わりに不動点はマージされた全体の上で毎回の実行で再走され、それが安価な半分であり、ファイルごとの再利用を健全にする半分です。

2つのスロットがそれを運びます:

| ストア | スロット | キー |
| --- | --- | --- |
| ADR-45の実行全体キャッシュ | プロデューサー`analysis.run-effects`、実行ごとに1エントリー | `Effects::Identity.descriptor`——`analysis.run-diagnostics`のキーディスクリプタにエフェクトのエントリーを加えたもの |
| ADR-46のインクリメンタルスナップショット | `Payload#effect_collections` + `Payload#effects_identity`（`SCHEMA` 12） | スナップショット自身のグローバルフィンガープリント、そして復元時に比較される同一性 |

収集**オン**の実行はもはや実行全体の結果キャッシュから除外されません。まずエフェクトスロットを参照します。それが作業を強制しうるスロットだからです: ヒットはコレクションを採用して不動点を走らせ、ミスは再解析し（収集は観測的なので、収集する唯一の方法は解析すること）スロットに書きます。いずれにせよ診断スロットは自分で決めます——診断エントリーがウォームなエフェクトのミスはウォームな診断を提供し、エフェクトエントリーの検証は同じ実行後の依存関係ディスクリプタを使うので、診断を無効化するまさにそのファイル集合がサマリーを無効化します。

エフェクトスロットが欠落している、異なる同一性である、または破損しているエントリーは、**エフェクト消費者に対してのみ**ミスです。収集**オフ**の実行はスロットを決して読みも書きもしません: `rigor check`はバイト同一で、そのキャッシュキーは不変で、ADR-87のブートスリムプローブは依然としてエンジンをロードせずに`analysis.run-diagnostics`からそれを提供します。

したがって`rigor effects`とスナップショットの動詞は`rigor check`が通るのと同じキャッシュを通ります: 設定された`effects:`ブロックの下での`rigor check`の後、同じジョブ内の`rigor effects check`はウォームヒットと不動点であり、決して再収集しません。

`--incremental`スナップショットの同一性は意図的に**プラグインを見ません**（`IncrementalSession#current_effects_identity`は`plugin_facts:`を省略します）。その2つの側は実行の反対側にあるからです: 復元はプラグインがロードされる前に問い、保存はロード後に問うので、見えるダイジェストは決して見えないものとマッチせず、再利用は死んでしまいます。境界は、プラグインのアップグレードが`--incremental`スナップショットのエフェクトコレクションを無効化しないことです;主たるパスである実行全体スロットにはそのような穴はなく、`--incremental`はオプトインです。

ADR-46の再チェックは変更されたクロージャだけを再収集し、他のあらゆるファイルのコレクションをスナップショットから提供します;不動点はマージされた全体の上で走るので、葉の編集は再チェックが決して開かなかったファイル内の呼び出し元のリーチを動かします。`effects_identity`がこの実行のものと異なる復元されたスナップショット——語彙のバンプ、再監査されたカタログ行、`effects:`の編集、または収集オフで書かれたスナップショット——は再利用を辞退してフルベースラインを取ります: 再チェックはクロージャだけを再収集するので、部分的な再収集はプロジェクト全体の不動点へ閉じられませんでした。それが「エフェクトのミスはエフェクトを再計算する」のインクリメンタルの綴りであり、収集オフの実行によって払われることは決してありません。

型付け消費者（WD9）は、解析キャッシュキー内のそのidを持つ`BleedingEdge`風のフィーチャーとして同一性をフォークします。収集がオンであることはそれを決してフォークしてはなりません。

## 並列性

収集する実行は、`fork`が利用可能なときforkバックエンドに固定されます。`record_dependencies`の実行と同じ理由です: forkパスだけがワーカーごとのサイドテーブルをマーシャルして戻し、Ractorのメッセージはサイドテーブルのチャネルを運びません。`fork`なしでは逐次に劣化し、ランナー自身の`analyze_file`を通じて正しく収集します。
