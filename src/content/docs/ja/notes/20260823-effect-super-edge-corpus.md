ステータス: 計測ノート、設計上のコミットメントはなし。ブランチ`claude/effects/super-edge`のRigor 0.3.4に対して、redmineとmastodonの調査チェックアウトのプライベートコピーの上で実施。

[#446](https://github.com/rigortype/rigor/issues/446)は宣言レーンの健全性（soundness）の穴だ: `super`がサマリーに何も寄与せず、**かつ**行を網羅的なまま残したので、本体全体が上位へ委譲するメソッドが証明可能にエフェクトフリーであると読め、あらゆるエンベロープを通過していた。修正は`super`にエッジを与え——囲むクラスより上で解決される——プロジェクト自身の祖先が何も答えないときは`unresolved-super`で汚染する。呼び出しエッジの追加はサマリーをコーパス全体で動かす。それがこのノートが計測するものだ。

## ハーネス

両プロジェクトはまずスクラッチディレクトリへ`rsync`された;調査チェックアウトの中には何も書かれていない。チェックアウト: redmine `a12198ea0`、mastodon `163f96cee`。各プロジェクトのコミットされた`.rigor.dist.yml`から`baseline:`を除き`effects: {}`を追加したもの——[`20260817-effect-collection-perf.md`](../20260817-effect-collection-perf/)が使うのと同じ形——を`.rigor.446.yml`として保存した。

```sh
cd <scratch>/survey/<project>
rm -rf .rigor/cache                                     # every run is COLD
BUNDLE_GEMFILE=<rigor>/Gemfile bundle exec <rigor>/exe/rigor \
  check   --config .rigor.446.yml --format json         # diagnostics + the stats block
BUNDLE_GEMFILE=<rigor>/Gemfile bundle exec <rigor>/exe/rigor \
  effects --config .rigor.446.yml --full --format json  # the whole table, per arm
```

キャッシュを毎回の実行前に消去するのは、ADR-45の実行結果キャッシュがプロジェクトと設定をフィンガープリントし、そのどちらもアーム間で変わらないからだ: ウォームな実行は一方のアームの収集を他方へ再生してしまっただろう。

2つのアームは`git apply` / `git checkout --`で`lib/`を切り替えた同じワーキングツリーであり、**インターリーブ**されている——7回の反復で`off, on, off, on, …`——ので、負荷がドリフトするホストは両アームを一緒に動かす。動きは2つの`effects --full --format json`テーブルをキーごとに差分して読む: 単位ごとに得られた・失われたラベル、網羅性ビットの遷移、そして`unresolved-super`の背後にどのセレクタが座っているか。

## 動き

決定的であり、ここがこのノートで信頼に値する部分である理由だ: これは2つのJSONテーブルの差分であって、タイミングではない。

| | redmine | mastodon |
| --- | --- | --- |
| テーブル内のエフェクト単位 | 4,683 | 8,355 |
| `app/` + `lib/`内の`super`の出現 | 166 | 114 |
| 証明済みラベルを**得た**単位 | 28（0.6%） | 121（1.4%） |
| 証明済みラベルを**失った**単位 | 0 | 0 |
| 網羅的 → ヘッジへ遷移した単位 | 37（0.8%） | 28（0.3%） |
| ヘッジ → 網羅的へ遷移した単位 | 0 | 0 |
| `unresolved-super`原因を運ぶ単位 | 463（9.9%） | 792（9.5%） |
| …うち、別の理由ですでにヘッジされていたもの | 440 | 768 |

3つの読み。

**ヘッジは広いがほとんど無償だ**。全単位のおよそ1割がこの原因を運ぶことになる。原因は他のあらゆるものと同様に呼び出しエッジを旅するからだ;しかしその95%は自身の理由（`dynamic-receiver`、`unresolved-self-call`）ですでに非網羅的だったので、得るのは原因であって遷移ではない。*新しい*情報——かつて完全性を主張していて、もはや主張しない行——は37と28単位だ。

**何もラベルを失わなかった**。これはこの変更が持つべき単調性だ: エッジは追加しかできない。

**得られたラベルはRailsの祖先が行うことだ**。mastodonでは上位3つが`mutate.local`（107）、`nondet.random`（97）、`nondet.time`（81）で、ほぼすべてが`super`を通じてActiveRecord形のプロジェクト祖先へ入るものだ。redmineでは広がりはより広くより小さい: `mutate.self` 13、`mutate.instance` 10、`mutate.local` 9、`io.fs.read` 5、そして`io`・`io.process`・`io.net`が1桁。

未解決の`super`の背後のセレクタは、まさにフレームワークの境界だ——redmineの`mail`（下流に209単位）、`identifier=`（65）、`admin?`（33）、`initialize`（33）;mastodonの`current_user`（350）、`authorize`（340）、`role`（33）、`initialize`（24）。これらはどれも実装をgemに持つので、「プロジェクトの祖先はそれを定義しない」がそれらについての真実であり、汚染が正直な答えだ。

**`rigor check`の診断ストリームは両プロジェクトともアーム間でバイト同一だ**——redmineで792診断、mastodonで2,349診断、すべての反復で追加ゼロ・削除ゼロ、異なるのは`stats`ブロック（実時間、RSS）だけ。どちらのプロジェクトもエンベロープを宣言しておらず、汚染は決して発見を生まないので、動きのすべてはレポートと、ここでは誰もオプトインしていない判定とに着地する。それが*偽陰性*を修正する変更に期待される形だ: それは作者が境界を書いた場所でしか決して発火しえない。

## コスト

ADR-103 WD13は収集パスに予算を組んでいるので、このエッジには値付けが要る。アームごとに7回のコールドなインターリーブ反復——redmineの`off`アームは6回で、その最初の1回は下で脇へ置かれる;数字は`rigor check`自身の`wall_seconds`で、プロセス起動を除く。両アームはすべての反復で同じ陽性ファイル数——redmineで347、mastodonで1,312——を解析した。

| プロジェクト | アーム | 実時間（秒）、範囲 | 中央値 | ピークRSS（MB） |
| --- | --- | --- | --- | --- |
| redmine | off | 9.33〜9.69（n=6） | 9.52 | 414〜436 |
| redmine | on | 9.41〜9.61 | 9.54 | 416〜424 |
| mastodon | off | 13.89〜14.53 | 14.17 | 697〜712 |
| mastodon | on | 13.65〜14.37 | 14.16 | 677〜716 |

範囲は両プロジェクト・両指標で完全に重なり、中央値の差はどちらのアーム内の広がりよりも小さい。**このサンプルサイズで検出できるコストはない**。それが期待される形だ: コレクターは`super`ノードごとに1つのエッジを追加し——この2プロジェクトで166と114、数万の通常の呼び出しエッジに対して——伝播器の解決は他のあらゆるエッジと同じタプルでメモ化されている。

この計測がそうでないもの2つ:

- ホストは実行の間じゅう、同じリポジトリで作業する**他の3つのエージェントセッションと共有されていた**。それがアームをインターリーブする理由であり、単一の中央値ではなく範囲を掲げる理由だ: 立てている主張は「2つのアームは同一条件下で区別できない」であり——インターリーブはこれを支える——「収集は9.54秒かかる」ではない——このホストにはこれは言えない。
- セッションの最初の実行（redmine、offアーム、反復1）は、自身のアームの9.33〜9.69秒の範囲に対して15.78秒だった。上ではセッションのウォームアップとして除外されている——最初のコールドな実行は、セッションの残りが払わないバンドル済みRBSのビルドを払う——そして黙って捨てるのではなくここに記録される。含めていたら*未修正の*アームが6秒遅く見えたはずで、それはまさに読み手が疑ってかかるべき方向だ。

## これが答えないもの

`unresolved-super`の率はプロジェクトの祖先のどれだけがgemであるかの関数であり、ここでの両プロジェクトはRailsだ。プロジェクト内のクラス階層を持つライブラリなら`super`呼び出しのほぼすべてを解決し、ヘッジなしでラベルの動きを見るだろう;ここでは何もその形を計測していない。
