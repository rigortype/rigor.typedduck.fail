Status: 計測ノート、設計上のコミットメントなし。Rigor **v0.3.8**、GitHub Actions `ubuntu-latest`、binpacker 0.5.0に対する観測、2026-09-09。[#863](https://github.com/rigortype/rigor/pull/863)、[#867](https://github.com/rigortype/rigor/pull/867)、[#889](https://github.com/rigortype/rigor/pull/889)として着地。

## きっかけ

[run 34269150881](https://github.com/rigortype/rigor/actions/runs/34269150881)において、Testsの3つのシャードの終了時刻に顕著な差がありました（339秒 / 172秒 / 117秒）。この分割を均等化できないかという疑問が生じました。

## 均等化できなかった — すでに均等だったからである

binpackerの`--shard K/N`は、ワーカーに使用するのと同じ重み平衡パーティショナーでスライスを分割するため、最初に読むべきはジョブの実行時間ではなく各シャードの実行レポートです。レポートは分割が最適であることを示していました:

| | shard 1 | shard 2 | shard 3 |
| --- | --- | --- | --- |
| スライスの重み | 534.6s | 534.6s | 534.6s |
| `predicted_makespan` | 167.341 | **133.661** | **133.661** |
| `actual_deviation_pct` | 24.6% | 5.8% | 4.3% |

438ファイル、予測作業量約1604秒、12ワーカー（3シャード × 4） — 各々の理論上の下限は約133.7秒であり、シャード2と3は予測偏差0.0%で*正確に*これに一致していました。いかなる分割もシャード数も、これを改善することはできません。

## 原因1 — 1つのマトリクスアームに固定された145秒の無関係な作業

`Run pool-runner spec`（18秒）と`Run plugin integration tests`（127秒）が、`if: matrix.shard == 1`でガードされたステップとして実行されていました。どちらもどのシャードにも属していません: `binpacker.yml`の`test_exclude`は、グローバルな状態を変更し自身のrspecプロセスを専有する必要があるため、両方をシャード化スイートから除外しています。唯一の要件はそれらが正確に1回実行されることであり、シャード1はスイート内で最も重いファイルを保持していたにもかかわらず、その要件を満たす任意の場所として選ばれていました。

これが222秒のばらつきのうち145秒を占めていました。それらを同等のピアジョブに移すことでクリティカルパスから127秒が回収され、すべてのスケジューラのレバーを合わせたものよりも大きな効果をもたらしました。

**これはbinpacker自身のデータには現れません**。レポートがバランスよく見えるのは、実際にバランスが取れている*から*です；余分な作業はレポート内にまったく含まれていません。これを診断するには、シャード間で`predicted_makespan`を比較してそれらが一致していることを確認し、その上でbinpackerの外部に完全に目を向ける必要があります。

### これは2026-07-18のノートを洗練させるものであり、矛盾するものではない

[20260718-ci-test-time-growth-attribution.md](../20260718-ci-test-time-growth-attribution/)には*「カテゴリー別ジョブ分割の検討（否定的）」*というセクションがあり、より多くのジョブに分割することは逆効果であると結論づけています: N個の最大値が遅延の裾野を悪化させ、binpackerのグローバルなバランシングを破棄し、固定オーバーヘッドがN倍になり、より大きなランナーがあらゆる軸でそれに勝るためです。最後は「現rigorは単一gemのunit specなので該当なし」と締めくくられています。

**その議論は、その実際の主題 — *バランスの取れたspecプール*をカテゴリジョブに切り分けること — について依然として正しいものです**。ここで分割されたのは、ノートが考慮していなかった別のカテゴリーでした: **すでにプールの外にあった**作業です。#863は`test_exclude`がbinpackerのスケジューリングから除外していた2つのスイートを移動しました；#889はテストですらない4つのゲートを移動しました。グローバルなバランスは決して危険にさらされておらず、どちらの分割もN個の最大値の抽選にシャードを追加していません — *テスト*ジョブの数は変わっていないからです。

2026-07-18の結論は次のように読んでください: *binpackerがバランスを取っているものを細片化してはならない。* binpackerが最初からバランスを取っていなかった作業については何も述べておらず、まさにそこにウォールタイムが潜んでいたのです。

## 原因2 — ワーカーごとの予算を超過した1つのファイル

`spec/rigor/analysis/runner_spec.rb`は約134秒の下限に対して約167秒の重みを持っていたため、LPTは正しくそれにワーカーを丸ごと1つ割り当て、シャードのメイクスパンはその1つのファイルそのものになりました。specファイルはスケジューリング単位であり分割できないため、これこそがスケジューラが真に修正できない唯一の事柄です。

継ぎ目（seam）を見つけるのは容易であることがわかりました。タイミングファイルは**example**ごとに記録するため、重いファイルを測定器なしでブロックに帰属させることができます — 各exampleのサンプルの中央値を、トップレベルの`describe`ごとにグループ化して合計します:

```
  93.3s  65.2%  n=225  L1405  CheckRules diagnostics (Slice 7 phase 8)
  13.4s   9.4%  n=32   L176   configuration wiring at runtime (audit guard)
  12.5s   8.8%  n=17   L5297  `rigor:v1:conforms-to` conformance directive
   8.9s   6.2%  n=6           (root-level examples)
   …23 more blocks, 14.4s combined
```

1つのブロックが65.2%を占め、次は9.4%でした — 判断の余地のない単一の継ぎ目です。このブロックは共有状態を持っていなかったため（`analyze`ハーネスは`spec/support/runner_helpers.rb`に存在）、そのまま逐語的に移動され、自身の`describe`ラッパーを保持したため何も再インデントされず、すべてのexampleの完全な説明はバイト単位で同一のままでした。両側での`rspec --dry-run --format json`により、同一の説明セットを持つ355個のexampleが確認されました。5,955行 → 2,605行 + 3,361行。

## 原因3 — Self-check（コールド）で同じ形状が3回目に現れた

そのジョブをステップごとに帰属させると、**自身の17%しかセルフチェックに使っていなかった**ことがわかりました:

| ステップ | 中央値 | 割合 |
| --- | --- | --- |
| Run rigor self-check | 27–31s | 17% |
| `make coverage` | 23–26s | 15% |
| `make check-plugins` | 12s | 7% |
| `make check-incremental` | 70–78s | **43%** |
| `make check-mutation-cache` | 22–24s | 14% |

4つのゲートは`if: matrix.cache == 'cold'`を介してwarm/coldマトリクスにぶら下がっており、その横には根拠が書かれていました — *「結果は決定論的であり、warm/coldのクロスチェックは不要」* — これこそがそれらがマトリクスの一部ではない理由です。`acceptance-gates`に移動: コールド164–196秒 → **40秒**。

## 分割が成果を出す前にかかったコスト

3つの問題に噛まれましたが、当時はupstreamで文書化されていませんでした。すべてコードにコメントされ、binpackerにフィードバックされました（下記）。

1. **binpackerは、存在しなくなったテストに対してもファイルに請求を行う**。`Timing#load_with_fallback`はファイルパスをキーとし、`compact!`はテストごとのサンプルを削減しますが、消滅したテストを削除することはありません。分割後、古いパスは実際には88.7秒で実行されているにもかかわらず163.9秒と予測され続け、履歴のない新しいファイルはファイルサイズにフォールバックして実際の66.5秒に対して0.3秒となりました。シャード1の偏差は43.6%になり、そのジョブは213秒になりました — **正しい分割がバランスを悪化させたのです**（[run 34274577832](https://github.com/rigortype/rigor/actions/runs/34274577832)）。キャッシュキー内の世代トークン（`binpacker-timings-v2-…`）で修正されました；specの分割、改名、または削除の際にはこれをインクリメントしてください。example名を保持しても役には立ちません — ルックアップはパス単位だからです。
2. **`--report`の書き込みが暗黙のうちにキャッシュヒットに依存していた**。`Report#write`はmkpathを伴わない単なる`File.write`であり（タイミングライターはmkpathを行う）、`tmp/`はgitignoreされているため、`actions/cache`が最初に`tmp/binpacker.timings`をそのディレクトリに復元したからこそ動作していました。最初の真のキャッシュミスで、**シャードの3,357個のexampleすべてがパスしているにもかかわらず**マトリクス全体が失敗しました（[run 34275199747](https://github.com/rigortype/rigor/actions/runs/34275199747)）。`write_report`は`finalize`にも先行するため、その実行ではタイミングも記録されませんでした。
3. **キャッシュキーのインクリメントは1回ではなく2回のコールド実行のコストがかかる**。フィーチャーブランチに保存されたキャッシュは`master`からは見えないため、マージ後の最初の実行もコールドになり、実際に名前空間をシードするのはその実行です。復元ステップで`Cache not found for input keys`がログに出力された実行からは、パーティションのバランスを決して読み取らないでください。

## 結果、および現在の下限の場所

| | 変更前 | 変更後 |
| --- | --- | --- |
| ワークフローのウォールタイム | 371s | **220s** |
| Tests shard 1 / 2 / 3 | 339 / 172 / 117s | 180 / 176 / 164s |
| シャードの実際のメイクスパン | — | 互いに4.4秒以内 |
| Self-check（コールド） | 164–196s | 40s |

151秒のほぼすべてが#863からもたらされました。下限は現在176〜182秒のTestsマトリクス（12ワーカー、実際のメイクスパン約160秒＋セットアップ）であり、ジョブやシャードの形状でこれをさらに動かすものはなく、specのボリュームを減らすことだけが動かせます。#889自身が予測した約20秒は実現**しませんでした**: Self-check（コールド）が184〜196秒を記録した実行を基準に見積もられていましたが、ワークフローが実際に判定された実行では164秒であり、すでにTestsを下回っていたためです。*ジョブ分割のサイズ見積もりは、サンプル内の最悪の実行ではなく、引用している同じ実行のクリティカルパスに対して行ってください。*

## 永続的な知識の行き先

- **binpacker**（[binpacker#20](https://github.com/rigortype/binpacker/pull/20)、マージ済み） — 不均衡なマトリクスを診断するためのREADMEセクション（最初に予測メイクスパンを比較する；下限の計算；example単位の帰属レシピ）およびファイル移動後のタイミングデータに関するセクション；同梱のスキルを両方とも更新；罠1と2は`.scratch/rigor-shard-rebalance/`配下にgemのissueとして起票。
- **本リポジトリ** — 罠が牙を剥く場所、すなわち[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)および[`Makefile`](../../Makefile)の`test-binpacker`ターゲットにコメントを記載。

言及しておく価値のあるギャップが1つあります: `docs/CURRENT_WORK.md`のヘッダーは運用の落とし穴を*「そのワークフローのスキル」*にルーティングしていますが、それらを受け取るCIや検証のスキルは`.claude/skills/`の下に存在しません。一度きりの作業では作成を正当化できませんでした；2回目のCIキャンペーンであれば正当化されるでしょう。
