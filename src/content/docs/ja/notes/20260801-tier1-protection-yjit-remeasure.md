ステータス: 計測ノート、設計上のコミットメントはなし。観測は`master` @ `a7a7cc1d`（#258後）、macOS arm64、Ruby 4.0.5、2026-08-01。

## 理由

[#257](https://github.com/rigortype/rigor/pull/257)は、`Inference::ForkMap`が`fork`後に遅延YJITを再アームしていなかったことを発見した —— ティア1の`coverage --protection`スキャンとADR-67のパラメータ推論事前パスを含む、`ForkMap`に支えられたあらゆるパスが、ワーカープロセスを完全にインタプリタ実行していた。[#258](https://github.com/rigortype/rigor/pull/258)はその修正をさらに締めた: 子は新しい5秒の窓ではなく、親の*残り*のデッドラインで再アームする。#257自身のPR本文がその帰結を直接名指ししている:

> ティア1のP3-10の数値（`61秒 → 43秒`）は、潜在的なForkMapの欠損がある状態で計測された;Mastodon規模で再計測すれば、おそらく改善するだろう。

本ノートがその再計測である。

## 旧数値の出所

「61秒 → 43秒」の数字は[PR #67](https://github.com/rigortype/rigor/pull/67)（"Fork-parallelize the coverage protection scan"、2026-07-10マージ）に遡る。これは保護スキャンとADR-67のパラメータ推論事前パスの両方にP3-10のfork-mapを導入したものだ。PR本文より:

> 4ワーカーでwall **61秒 → 43秒**、**ピークRSSはおよそ半減**（814MB → 351MB）;パラメータ推論パス単独では8ワーカーで**2.3倍**。

そして、スキャンだけでなく*両方*のパスをfork-mapする動機になったフェーズ内訳（Mastodon `app lib`、ウォームキャッシュ）:

| フェーズ | 時間 |
| --- | ---: |
| env構築（ウォームキャッシュ） | 1.2秒 |
| ADR-67のパラメータ推論事前パス | 48.6秒 |
| 保護スキャン | 11.0秒 |

圧縮された形がchangelogの`docs/CHANGELOG-0.2.x.md:38`に着地している:

> パラメータ推論の事前パスとファイルごとの保護スキャンは、それぞれ1つの親側環境から作られたワーカープロセスにfork-mapされます（RBS環境、プラグインレジストリ、クロスファイルのシードを一度だけ構築し、コピーオンライトで継承）。ワーカー数は`check`とまったく同じに解決され（`--workers=N`＞`RIGOR_RACTOR_WORKERS`＞`.rigor.yml`の`parallel.workers:`＞`0`）、出力は逐次実行とバイト単位で同一です。Mastodon `app lib`での実測: 4ワーカーで61秒 → 43秒、ピークメモリはおよそ半減。

**アームの不一致に注意**: 歴史的な比較は逐次（`--workers 0`）対**4**ワーカーであって、8ではない。本ノートは0・4・8を計測するので、新しい数値は旧数値と比較可能であり、かつタスクが求めた8ワーカーのアームもカバーする。

欠損そのものとその修正は#257/#258に記録されている（執筆時点でまだ`docs/notes/`にアーカイブされていない —— 両PRとも本日2026-08-01、`a7a7cc1d`でマージされた）。#257自身の計測（`lib/rigor/analysis`に対するもの。別のコーパスであり、ティア1ではなくティア2のミューテーションスキャン）は、欠損が実在したことの直接の証拠だ:

| ワーカー | YJIT修正前 | 修正後 |
| --- | ---: | ---: |
| 0 | 37.2秒 | 35.1秒 |
| 2 | 48.0秒 | 27.8秒 |
| 4 | 43.6秒 | 26.7秒 |
| 8 | 67.4秒 | 23.2秒 |

つまりプールは修正前は8ワーカーで*悪化要因*であり（67.4秒、逐次より悪い）、修正後は明確な勝ちになった（23.2秒）。#258は、新しいデッドラインではなく残りのデッドラインを持ち越すことで、8ワーカーのケースをさらに約8%削った（23.2秒 → 約21.3〜21.6秒）。

## 手法

ターゲット: `~/repo/ruby/rigor-survey/mastodon`。`.rigor.dist.yml`（paths: `app`・`lib` —— 歴史的な「Mastodon `app lib`」のスコープに一致）を持つが`.rigor.yml`はないので、ツリーにコピーするのではなく`--config .rigor.dist.yml`を明示的に渡す。

```
cd ~/repo/ruby/rigor-survey/mastodon
BUNDLE_GEMFILE=/Users/megurine/repo/ruby/rigor/Gemfile \
  nix --extra-experimental-features 'nix-command flakes' develop /Users/megurine/repo/ruby/rigor --command \
  bash -c 'time bundle exec /Users/megurine/repo/ruby/rigor/exe/rigor coverage --protection \
    --config .rigor.dist.yml --workers <N> app lib'
```

アーム: タスクに従って`--workers 0`と`--workers 8`、加えて上の歴史的な数字と比較可能にするための`--workers 4`。各アームを2回実行。`coverage --protection`はRigorの永続的な`.rigor/cache`に触れない（そのストアは`coverage`ではなく`check`を支える —— grepで確認済みで、`lib/rigor/cli/coverage_command.rb`に`cache`/`CacheStore`の参照はない）ので、あるアームの2回の実行の間にキャッシュのウォームアップ効果を挙げる必要はない;どちらも同じ意味でコールド／ウォームである（gem/rbsファイルに対するOSのページキャッシュは、計測開始前の`bundle check`のドライランですでに温まっている）。

## サニティチェック: ワーカー数は答えを変えてはならない

**強く合格**。上のすべての実行が、ワーカー数によらず同一の`protected dispatch sites: 10264 / 30822 (33.3%)`を報告する。サマリー行を越えて、`--workers 0`と`--workers 8`の間で完全な`--format json`出力をバイト単位で差分した（上の計測実行の使い回しではなく新規実行）: 両者ともSHA-256が同一（`60bd0fc9118c3cc...`）。この実行では、ワーカー数は速度だけを変え、答えを変えることは決してない。

## 本ノートが示すこと、示さないこと

**wall clockの大きさは、#257/#258の修正が説明しうるどちらの方向でも、歴史的なエントリーと一致しない**。歴史的には逐次61秒 → 4ワーカーで43秒。ここでは（静かな再実行）逐次18.2秒 → 4ワーカーで15.3秒。逐次（`--workers 0`）のアームは決してforkしないので、`ForkMap`/#257/#258はそれにまったく触れられない —— にもかかわらず、それ自体が**2.7倍**下がった。この差は、この修正ではなく2つの計測の間の3週間の一般的なエンジン作業に帰属させるほかない: PR #67（「61秒 → 43秒」の出所）は`0.2.9`サイクルに対して2026-07-10にマージされた;本セッションは`0.3.1`上の`a7a7cc1d`を計測しており、これはv0.3.0のパフォーマンスキャンペーン（YJITのデッドライン調整、`rigor_each_child`、prepareキャッシュ、遅延事前パス —— [`20260713-corpus-perf-campaign.md`](../20260713-corpus-perf-campaign/)、PR #74〜#77）と#207のスタブ検出のアロケーション削減の向こう側にある。Mastodonのチェックアウト自体は変わっていない（`163f96ce`、2026-07-03、両回とも`app`+`lib`配下の同じ1,312ファイル）ので、コーパスのドリフトは説明として除外される。

wall clockのドリフトの影響を受けずに、本ノートが裏づけることが2つある:

- **ピークRSSは歴史的な数字とほぼ正確に一致する**（逐次で現在813 MB対当時814 MB;8ワーカーでの現在354 MB対4ワーカーでの当時351 MB）。wall時間が2.7倍下がったにもかかわらずだ。メモリは一度きりの親側のRBS環境構築（COWで子と共有される）に支配されており、その間のパフォーマンス作業はそこを狙っていない —— ピークメモリはwall clockに影響する変更ではなくその共有構築が決めるという歴史的な主張と整合する。
- **並列化のスピードアップ比は歴史的な値より*低い***（静かなときで4wで1.19倍 —— 負荷下では1.37倍 —— 対して旧値は4wで1.42倍）。これは純粋なYJIT再アームの勝ちが予測するのとは*逆*の方向だ。もっともらしい説明はPR #67自身が文書化した残余だ ——「サブリニアなスケーリングは、ディスパッチごとの解決メモのforkによる再ウォームに内在する[…] 大きなツリーほどよく償却される」—— これはワーカーあたりの**固定**コストである。無関係なパフォーマンス作業によって総作業量が約2.7倍縮んだので、その固定オーバーヘッドが小さくなった総量のより大きな割合を占めるようになり、#257/#258が別の場所の実在する欠損を直したにもかかわらず、達成可能なスピードアップを押し下げた。
- **#257自身の計測が、欠損が実在したことのきれいな証拠である**。効果を切り分けられる別の（より小さく、ティア2のミューテーションの）コーパスでの話だ: `lib/rigor/analysis`（45ファイル / 916ミュータント）は、修正前は8ワーカーでプールが**悪化要因**だった状態（67.4秒、逐次の37.2秒より悪い）から、修正後の明確な勝ち（23.2秒）へ移り、#258がさらに約8%削った（約21.3〜21.6秒）。その前後比較は修正自体を除いてツリーを固定していた —— 本ノートのMastodonの数値はそうではない。2つのMastodonのデータ点は3週間とパフォーマンスキャンペーン1本で隔てられているからだ。

**したがって本ノートは、現在のmasterに対する新しいMastodon規模の参照値（上の0w/4w/8wのwall時間とRSS）を確立するが、Mastodon上で#257/#258の差分を切り分けて再導出しようとはしていない** —— それをきれいに行うには同一ツリーでの前後比較（隔離したworktreeで#257の直前のコミットをチェックアウトし、このコマンドをそのまま再実行する）が必要であり、メインのチェックアウトに対する読み取り専用／ブランチ切り替え禁止という制約の下では今回のスコープ外だった。Mastodon規模で切り分けた差分がほしければ、自然なフォローアップとして推奨する。

## 正直さ／環境

マシン: 12コア（`sysctl -n hw.ncpu`は12を報告;上の`uptime`）、macOS arm64。**本セッションを通じて持続的なバックグラウンド負荷**があった。別のClaude Codeセッション（`~/repo/rust/steins`）の無関係な`cargo test --workspace`の起動と、通常のデスクトップアプリの負荷（Chrome、Slack）である。ロードアベレージ（1分）は本ノートのすべての実行にわたって**7.16〜9.26**の範囲にあり、このリポジトリ自身のパフォーマンスの教訓が求める約4の閾値を一度も下回らなかった。最初の実行の前に5分の待機（`Monitor`で5秒ごとにポーリング）を試したが下がらず、1分の数字はRSSの実行の直前に一度4.49まで落ちただけで、すぐにまた上がった。プロジェクト自身の過去のパフォーマンスの教訓（「負荷下で取ったパフォーマンス数値は破棄した」）に従い、**上の絶対的なwall clockの数字は、きれいなものではなく参考として読むべきである** —— 負荷は一般的なデスクトップ＋別セッションのCPUバウンドなRustのコンパイル／テストであって、この計測が自分自身と争っていたわけではないので、相対的な比較（0w対4w対8w;歴史的な値と現在の差の方向）はおそらくなお有益だ。**その静かな再実行は実施された**（§静かなマシンでの再実行。逐次と4ワーカーのアームで1分ロード約4.1〜4.4）ので、引用すべきはその数字である;上の負荷下の表は、負荷への感度 —— そのほとんどが逐次のアームに落ちること —— を示すために残してある。
