## 欠陥の再確認

名前空間の内部から呼び出されたトップレベルの`def`は、その定数を**呼び出し元の**名前空間の下で解決する。トップレベルの`def`本体におけるRubyの`Module.nesting`は`[]`であるため、`def helper = Post.new`はどこから呼び出されようとも`::Post`を名指すが、Rigorは呼び出しが`module Admin`の内側から行われたときに`Admin::Post`と答えてしまう。

[#709](https://github.com/rigortype/rigor/pull/709)は宣言時に各`def`のネスティングを記録し、トップレベルの`def`に対しては正しく**何も**記録しない ── `Inference::ScopeIndexer#walk_def_nestings`はそのとおり明記している。その後`Reflection.lexical_nesting_chain`は「未記録」と読み取り、スコープの囲みクラスパスを剥ぎ取るフォールバックを行うが、その時点でのクラスパスは呼び出し元のものである。フォールバックは書かれたとおりのことを正確に行っている;バグは、トップレベルの`def`におけるnilチェーンが「答えが記録されていない」ことではなくRubyの答えであり、Rubyの答えは`[]`であるという点にある。

master上で、RBSが関与しないコールドな状態で再現された:

```
f716.rb:13:11: info: dump_type: Admin::Post [dump.type]
```

同じファイルに対してMRIは`Post`と答える。

## なぜ最初に規模を測定しなければならなかったのか

剥ぎ取りの撤回は、移動する読み取りに対して偽陽性を優先する方向であるが、剥ぎ取りはトップレベルヘルパーの定数読み取りをそもそも解決させているものでもある。トレードオフが本物となるのは、剥ぎ取りが現在耐荷重性を持っている場合に限られるため、どちらかを仮定するのではなく互いに素な2つの母集団を測定する。

- **movable（移動可能）** ── トップレベルの`def`が、素の名前がプロジェクトのトップレベルと一部のプロジェクト名前空間の両方に存在する定数を読み取っている。呼び出し元名前空間の剥ぎ取りがトップレベル以外の何かを答えうるのはここだけである。
- **nested-only（入れ子限定）** ── その名前が名前空間の下にのみ存在する同じ読み取り。Rubyはこれらで`NameError`を発生させる;剥ぎ取りが任意の答えの唯一のソースであるため、これらは無条件の撤回がまさに犠牲にするものである。

両方とも**静的な上限**である: プローブはトップレベルの`def`が剥ぎ取られる名前空間の内部から実際に呼び出されているかをチェックしておらず、ソースツリーのみから名前がプロジェクト宣言されているとカウントするため、gemやRBSを通じて実際に解決される定数は*nested-only*を膨張させる。各列は移動可能な母集団の上限として扱い、サイト数として扱ってはならない。

## ハーネス

Prismを使用し、ループ内にRigorは関与しないため、数値は挙動が問題となっているアナライザーから独立している。ブランチではなくインラインで保持されている: このノートから再実行するのに十分短い。

```ruby
require "prism"
# ステージ1: 囲みclass/moduleキーワードを持たず、レシーバーを持たない`def`ノード。
# ステージ2: そのうち、本体が定数を読み取るもの。
# ステージ3: 各読み取りを、その素の名前がプロジェクト内のどこで宣言されているかによって分割する ──
#          トップレベルかつ入れ子 => "movable"（剥ぎ取りが異なって答えうる）
#          入れ子のみ             => "nested-only"（RubyがNameErrorを発生; 剥ぎ取りが唯一の答え）
#
# `declared`はすべてのClassNode / ModuleNodeを歩き、囲みプレフィックスに対して
# そのconstant_pathを修飾し、ルート化された`class ::Foo`をトップレベルで
# 再アンカーすることによって構築される。`toplevel_defs`はツリーを下降し、
# ClassNode / ModuleNode / SingletonClassNodeを越える再帰を拒絶することによって構築される。
```

完全なスクリプト: `movable_toplevel_def.rb`。上記の3つのステージから約70行で再構築可能;唯一の微妙な点は、`Prism::ConstantPathNode`がその最初のセグメント（`A::B`の`A`）を寄与することである。それがレキシカル解決が答えるセグメントだからである。

## 決定 ── そしてそのコスト

測定により、issueが懸念していたトレードオフのバージョンは除外された。10のターゲットのうち7つでは剥ぎ取りは何にも到達せず、何かに到達する場所（mastodon）では剥ぎ取りの答えは**間違った**もの ── アプリモデルではなくシャドウモデル ── であるため、撤回はそこでの精度の低下ではなく正しさの向上である。

しかし*nested-only*は大規模ではゼロではなく（gitlab 486、dependabot-core 33）、それらの読み取りは今日、剥ぎ取りがあるからこそ解決している。したがって撤回は無条件であるべきではない。コストのかからない順序付け:

1. ネスティングが空（明確にトップレベル）として記録されている`def`は、呼び出し元のチェーンを通じてではなく、トップレベルで定数を解決する ── Rubyの答え ──。これは呼び出し元から導出された祖先段（`Reflection.resolve_constant_type`のステップ2）も抑制しなければならない。これもトップレベルの`def`にとっては同様に間違っている: そこでのRubyのcrefは`Object`である。
2. トップレベルが答えないときは、今日とまったく同様に剥ぎ取りにフォールバックする。

段2はRubyに対して不健全である ── これらは`NameError`のサイトである ── が、今日解決しているすべての読み取りを解決させ続けるため、この変更がどこかで精度を回帰させることはなく、カバーするサイトはRigorがどちらにしても何も報告しないものである。それらを発火させることは独自のFPバジェットを伴う別の問題であり、この修正に乗せるべきではない。

修正が拠って立つ区別は**「空として記録されている」対「記録されていない」**であり、テーブルはすでにそれを表現できる: `discovered_def_nestings`はノードの同一性によってキー付けされ、実際の宣言ウォークによってのみ投入されるため、`[]`を伴って存在するノードは「ウォークされ、トップレベルである」ことを意味し、不在は依然として「ウォークなし」を意味して剥ぎ取りを維持する。`walk_def_nestings`は今日、トップレベルの`def`に対して何も記録しておらず、方針を変更しなければならない唯一の場所である。
