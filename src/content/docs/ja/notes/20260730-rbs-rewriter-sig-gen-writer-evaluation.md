日付: 2026-07-30。`rbs` 4.1.0（4.1.0タグの`references/rbs`）と、706行時点の`lib/rigor/sig_gen/writer.rb`に対して。

ステータス: **評価、決定済み —— 採用しない**。 [#228](https://github.com/rigortype/rigor/issues/228)に答える。コード変更なし。この知見の再利用できる部分はgemではなくモデルのほうだ。§5を参照。

---

## 問い

`rbs` 4.1は[`RBS::Rewriter`](https://github.com/ruby/rbs/pull/2927)を出荷した —— `RBS::Location`によって`RBS::Buffer`に対して適用される置換で、重なりは拒否される —— そして上流は`rbs annotate`をその上に作り直した。`rigor sig-gen --write`は既存の`.rbs`を更新するとき、同じに見える問題を解いている: ファイルの残りを乱さずに宣言を変える。採用すべきか？

#228が名指しした核心はバージョンフロアだ: `RBS::Rewriter`は4.1以降であり、gemspecは`rbs >= 3.0, < 5.0`をサポートしている。以下の3つの知見がフロアの問いを無意味にするので、それは最後に答える。

## 1. `RBS::Rewriter`が実際に何であるか

70行（`references/rbs/lib/rbs/rewriter.rb`）であり、そのうち機構は15行だ:

- `rewrite(location, string)` —— 置換を蓄積する;既存のものと重なればraiseする。
- `string` —— 開始位置でソートし、逆順に適用する。
- `add_comment` / `replace_comment` / `delete_comment` —— コメント専用のヘルパー3つ。

#228にある「上流がメンテナンスするので、位置のドリフトは向こうの問題になる」という論に対しては2つの性質が効くが、どちらも接触に耐えない:

- **ロケーションを解釈することが決してない**。 `start_pos` / `end_pos`（とコメントヘルパーでの`start_column`）だけだ。継承すべきパーサとの結合がないので、外部化すべきドリフトも存在しない。
- **バッファの出自を検査しない**。 *別の*バッファに対して構築された`Location`は黙って受理される（プローブ済み）。したがって重なりの保証は、1つの座標系を保つという呼び出し元自身の規律と同じ強さしかない —— そしてそれこそが、呼び出し元がこれを採用することで解放されたい当の規律である。

同一アンカーでの幅ゼロの挿入は、追加された順に出てくる（1つのアンカーに12挿入までプローブ済み）。それは`sort_by`がたまたま安定なだけで、文書化された保証ではない —— 知っておく価値はあるが、それに基づいて決める価値はない。

## 2. 上流自身の用途はコメントの付加であって宣言の編集ではない

`rdoc_annotator.rb`が`rbs`ツリーで唯一の消費者であり、それが呼ぶのは3つのコメントヘルパー**だけ**で、汎用の`rewrite`は決して呼ばない。`rbs annotate`はすでに存在する宣言にRDocコメントを付ける。宣言を挿入することも、名前空間を作ることも、移動することもない。

したがってsig-genの問題との類似は表面的だ。ワークロードは互いに素である:

| sig-genの`--write`がすること | `RBS::Rewriter`が提供するもの |
| --- | --- |
| クラスへメソッド宣言を挿入する | —— |
| 欠けている名前空間チェーンを作る | —— |
| 宣言を親の下へ、再インデントし先頭を短縮して移動する | —— |
| 既存メンバーのメソッド型を置換する | `rewrite(member.location, text)` |
| 触れていないバイト列をそのまま保つ | APIではなくモデル |

1行だけだ。`Writer#replace_eligible_conflicts`は`string`とまったく同じ理由ですでにバイト位置の降順でソートしており、それは1行である。

## 3. 障害: 我々のマージの各ステップは、先行ステップが書いたテキストにアンカーする

`Rewriter`のモデルは、あらゆるロケーションが1つの不変なバッファ由来であることを要求する。ライターのマージはそれを供給できないし、自分でそう言っている（`writer.rb`の`merge_candidates`）:

> 祖先が先。そうすれば`Foo::Bar`がネスト先の親を探す前に`Foo`が作られる（または見つかる）。

`merge_class`は`Foo`を**作る**かもしれない;次の反復はそこで`Foo`の閉じ`end`を見つけて`Foo::Bar`をその中にネストする。`merge_class_shells`が再パースされた宣言を読むのも同じ理由であり、`collapse_nested_declarations`はマージ後のテキストに対して走る。ライターがステップ間で再パースするのはそのためだ —— オフセット管理の怠慢ではなく、後のアンカーが先行する出力に本当に依存しているのである。

置換モデルは、まずマージを「元のバッファに対して計画する」パスへ再構成しなければこれを表現できない。その再構成こそが潜在的な勝ちのすべて（N回のパース → 1回）であり、しかも**バージョンコストゼロで入手できる** —— それは上流のAPIではなく我々のマージアルゴリズムだからだ。`RBS::Rewriter`を採用してもそれは手に入らない;先にそれを勝ち取らねばならず、そのあとで`Rewriter`が§1の15行を足すだけである。

## 4. 生き残らないもの

バイト操作のサーフェス（`insert_before_end`・`append_top_level`・`splice_out`・`reindent`・`line_start_index`・`blank_range?`・`apply_replacement`で約60行）は、その大半が`Rewriter`には概念すら無いレイアウト規則だ: スニペット自身のインデントが勝つように挿入を行頭にアンカーすること、切り取りが残す改行の継ぎ目を畳むこと、移動したブロックを新しい親のメンバー深度へ再インデントすること。すべて残る。

## 5. 決定

**`RBS::Rewriter`は採用しない**。決定的になった順に3つの理由がある:

1. 我々にとって使えるサーフェスはメソッド型の置換1つだけであり（§2）、しかもそれが作られた目的ではないワークロードに対してだ。
2. #228が期待した構造的な勝ちは我々自身のマージ順序に阻まれており、それは依存関係なしに、望むときにいつでも自分たちで取れる（§3）。
3. そこで初めてフロアが問題になるが、[ADR-94](../../adr/94-rbs-inline-reader-and-the-rbs-3x-floor/)がまさにこのトレードを、移行がもっと多くを買う場合について既に裁定している: *回避策がすでに買っている正しさを買う依存関係の移行は、サポートするツールチェーンの範囲を狭めることを正当化しない。* [ADR-79](../../adr/79-rbs-version-range-over-pinned-determinism/)は、Rigorはプロジェクトが実際に解決するツールチェーンに対してチェックするという原則で、この範囲を固定した。

保つ価値があるのは**モデル**のほうだ: 重ならない編集を1つの不変なバッファに対して蓄積し、一度で適用する。ライターの再パース連鎖がいつかコストとして表面化したら —— まだしていない: `--write`の実行は小さく、ファイル数で上限が付いている —— 直し方は、元のバッファに対してマージを計画することであり、それは`merge_candidates`への変更であって新しい依存関係ではない。

## 再検討するとき

- 無関係な理由で`rbs`のフロアが4.1以降へ動き、**かつ**そのときまでに`RBS::Rewriter`がコメントヘルパーではなく宣言レベルの編集（挿入、移動）を備えている場合。
- ライターの再パース連鎖が、実際の`--write`実行で計測可能になった場合。
