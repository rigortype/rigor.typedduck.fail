日付: 2026-10-17。

ステータス: **調査ノート、設計上の確約なし**。 `rigor check`（およびそれゆえ`check`が読み取るものを報告する`rigor lens`）がプロジェクトの`attr_reader` / `attr_accessor`のリーダー呼び出しに戻り値型を与えられるかを検討します。エンジンは`4f4e8d9ad`時点の`master`です。設計案は設計パートナーとともに起草され、その後敵対的に批評されました。双方が独立に同じ利得を計測しました。

2026-11-17に未改訂のまま着地: 以下の計測値は`4f4e8d9ad`時点のツリーのものであり、ここでは再導出していません。それ以降に動いた事実は1つあり、それは本ノート自身の最初の推奨事項 ── **#1931は修正されクローズされた**ため、「まず#1931を修正する」は完了しています。利得および4つの欠陥を含むその他すべては執筆時のままです。末尾の決定事項は依然としてオープンです（#1907）。

## なぜ持ち上がったか

`rigor lens`のドキュメント利用者であるZARD（#1907）は、Rigor自身の`lib/` APIをレンダリングします。そこでは、`docs/internal-spec/lens.md` § Membersが要求するとおり、すべての属性メンバーのオーバーロード戻り値が`not_computed`を伴う`unavailable`になっています: 1,456個のリーダーメンバーがあり、そのうち1,112個が`single_site`です。Lensは`check`が持たない型を報告できないため、問いは`check`に関するものになります。

## 現在のエンジンの挙動

- **リーダー呼び出しは書かれた場所にかかわらず未型付けである**（所有者の自身のファイルでも別ファイルでも）。マクロは`discovered_methods`に名前と種別のみを記録し（`ScopeIndexer#record_attr_methods`）、`MethodDispatcher#try_discovered_method`は`def`ノードを持たない発見されたメソッドに対して`untyped`を返します。呼び出しは`inferred_return_untyped`を記録します。
- **直接のivar読み取りは型付けされる**。 `StatementEvaluator#seed_instance_ivars`は、クラスごとのivarセンサス（`ScopeIndexer#build_class_ivar_index`が構築する`Scope#class_ivars_for`）から各インスタンス`def`本体にシードします。
  - プローブ: `initialize`内の`@name = "x"`に続いて`take: (bool) -> void`に対する`take(@name)`は、`got "x"`を報告します。
  - 同じクラス内で、`take(name)`は何も報告しません。
- **センサスはファイル単位である**。 `Runner#project_scope_seed_tables`はそれをシードしません。別ファイルのリーダーや、別ファイルでのクラスの再オープンは、そのクラスに対して空のテーブルを見ます。
- **`def`本体の呼び出しサイト再型付けもivarをシードしない**。 `ExpressionTyper`は`build_user_method_body_scope`を通じて呼び出し先本体を型付けし、これはパラメータのみを束縛します。自明な`def name = @name`であっても、呼び出しを通じて読まれればマクロとまったく同様に未型付けとなります。Lensは定義自身のメインウォークインデックスを読み取るため、そのdefの`body_return`を依然としてリテラルとして報告します。
- **ADR-58は1点について古くなっている**。その250行目は「アクセサの戻り値はnilを落とす（`Node`上の`x.parent`は`Node`と読まれる）」と述べていますが、これはもはやエンジンを記述していません。

## 設計前に計測された利得

Rigorの`lib/`（587ファイル）に対して`rigor lens`と`rigor sig-gen --format=json`を実行しました。その後、1,109個のインスタンス`single_site`リーダーを、sig-genが各アクセサにマップするivarシードと結合しました。sig-genはあらゆるリーダー機構が読み取るであろうものと同じマッピングを適用します。

| リーダーのivarシード | リーダー数 |
| --- | --- |
| 具象的、nilフリー（`Set`、`0 \| Integer`、タプル） | 30 |
| 具象的だがnil許容 | 1 |
| `untyped`を含む（766個が純粋な`untyped`） | 781 |
| エントリーなし（sig-genがスキップ） | 297 |

1,078個の未型付けリーダーは、ほぼすべてがコンストラクタパラメータからの`@x = x`です。センサスはローカル束縛なしで各右辺値を型付けするため、`sig/`が型付き`initialize`を宣言している場合でも、パラメータは`Dynamic[top]`になります。kramdownでは27個のリーダーが得られ、そのうち18個が`single_site`、1個が型付きです。批評側も同じデータから件数を再導出しました。

つまり**リーダーは正しい継ぎ目だが、そこを流れるものがほとんどない**のです。単独では、リーダー機構はZARDの数値を1,112個の`unavailable`から約1,082個へと動かすにとどまります。ボトルネックはコンストラクタパラメータの型付けです。

## 候補となる機構と、批評がそこに見つけた穴

**パートA**は発見済みメソッドティア内のリーダー応答です。`try_discovered_method`は`untyped`の前に、所有者の`@name`に対するセンサスエントリーをその消去型へ拡大して返します（決してリテラルではない; `FalseClass`がfalseyに畳み込まれるため`true`または`false`は`bool`と読まれる）。次のようにゲートされます:

- マクロがクラス本体の確実な直接の文であること;
- クラスが1つのファイルで宣言されていること;
- いかなるプロジェクトサブクラスもリーダーをオーバーライドしていないこと;
- いずれかの`nil`、`Dynamic`、または`Bot`構成要素がある場合は辞退し、現在の`untyped`を残すこと。

設計パートナーは2つの代替案を却下しました:

- #644の定数公開の類似物であるファイル横断の公開センサス（フォールド規則、新しいエッジ種別、およびスナップショットスキーマのバンプが必要）;
- `@name`本体を合成してdefパスを再利用すること（前のセクションが示すとおり`Dynamic`を生む）。

敵対的批評は、**起草されたままの**パートAに正しいコード上で誤った型や診断を出させる4つの欠陥を発見しました:

1. **いかなる書き込みよりも前の読み取りによるnilが不可視である**。センサスが`nil`を結合するのは、兄弟の`def`が書き込み前にそのivarを読み取り、かつ`initialize`がそれに書き込まない場合のみです。リーダーは`def`本体ではないため、その最初の読み取りとして決して数えられません。
   - `attr_reader :data; def load = @data = { a: 1 }`は`data`を`{ a: 1 }`にマップし、`initialize`内の`@v = 1 if flag`は`v`を`1`にマップします。どちらのリーダーも実行時には`nil`を返します。
   - 修正: `initialize`（またはADR-38イニシャライザ）の無条件のトップレベル文がそのivarに書き込む場合にのみリーダーを型付けする。
2. **`def`でない後続の再定義が見逃される**。オーバーライドゲートは`discovered_def_nodes`のみを読み取り、階層の下方向のみを見ています。
   - マクロの後の`define_method(:name) { "s" }`は見逃され、`name`を定義する`prepend`されたモジュールも見逃されます。
   - 修正: 可能な定義、不透明エンベロープ、複数のクラスソース、およびクラスエッジをすでに結合している`SelfCallIvarWrites#single_definition`を再利用する。`discovered_methods`（任意のスペリング）から再定義者集合を構築し、所有者が何かをprependしているときは辞退する。
3. **`instance_variable_set`がすでに偽陽性であり、リーダーがそれを広げてしまう**。センサスはそれを決して見ません。`@timeout = 5`の後に`options.each { |k, v| instance_variable_set(:"@#{k}", v) }`が続くと、`@timeout.end_with?("s")`は現在`undefined method 'end_with?' for 5`を報告します。具体的な再現コードは現在#1931にあります。
   - 修正: 所有者の本体が`instance_variable_set`、または非リテラルもしくは`=`接尾辞付きの名前の`send` / `public_send`を呼び出しているときは辞退する。モジュールをincludeまたはprependしているときは辞退し、そのコストを計測する。さらに良いのは、まず#1931を修正すること。
4. **モジュール所有者が誤りである**。 `initialize`が`@x = "s"`と書き込むクラスにincludeされる`module M; attr_reader :x; def setup_m = @x = 1; end`は、`M#x`を`1`にマップします。（`is_a?`またはRBSパラメータによって）`M`にナローイングされたレシーバーは、誤った型を読み取ることになります。修正: クラス所有者のみとする。

また、4つの中程度の論点も挙げられました:

- **インクリメンタルエッジ**。単一ファイルゲートには、`read_missing(:class)`に加えて`ResolutionChain.record_class`（すべての宣言ファイル上の読み取りサイト）が必要です。そうでなければ再オープンを削除した際に陳腐化した`untyped`が返され、`--verify-incremental`に失敗します。オーバーライドゲートの祖先エッジはメモミス時にのみ記録されるため、メモの外側で記録されなければなりません。
- **実行時のサブクラス**。所有者自身のメソッド内の暗黙的self呼び出しは、しばしばivarを異なる方法で書き込むサブクラスインスタンス上で実行されます。発見されたサブクラスが存在するときに辞退するゲートは計測が必要です。
- **Lensが過剰に主張してしまう**。センサスがファイル単位であるため、`check`は所有者自身のファイル内の呼び出しサイトでのみリーダーを型付けします。Lensの定数`value`はすでに別ファイルからの読み取りを報告しています（`docs/internal-spec/lens.md` § Sites）。したがって型付きの属性スロットは、ほとんどの呼び出し元が得るものより多くを主張することになります。辞退されたリーダーに対して`dynamic`を報告すると、約1,082個の`unavailable`スロットが新しい情報を持たない`() -> untyped`オーバーロードに変わってしまいます。
- **パートBは見た目より大きい**。パートBは宣言されたシグネチャ（RBSまたはrbs-inline）からセンサス内の`initialize`パラメータを束縛します。センサスはフローを持たないため、書き込み前にパラメータが再代入される場合（`x = Integer(x)`）にエントリーで束縛するのは誤りであり、オーバーロードされた`initialize`には辞退が必要です。
  - それはリーダーだけでなく、`seed_instance_ivars`がシードするすべての直接的な`@x`読み取りを変更します。
  - 独自のコーパスゲートが必要であり、本体が決して書き込まないパラメータのみを束縛すべきです。

## 推奨事項

- **パートAを単独で着地させない**。修正後でも、Rigorの`lib/`上で高々30個のlensメンバーとkramdown上で1個を型付けするのみであり、`check`がそれらを得るのは所有者自身のファイル内の呼び出しサイトに限られます。
- **レバレッジはパートBにある**。上記の制約の下で、`tool/engine_diag_diff.rb`を用いてADR-58コーパス上の独立したスライスとして計測します。Rigorの`lib/`内の270個の`single_site`リーダー所有者のうち`sig/`に現れるのは18個のみで、そのうち8個が50個のリーダーをカバーする型付き`initialize`を宣言しています。したがってその利得はエンジンではなく、宣言されたコンストラクタとともに増加します。
- **パートAはその上でパートBに乗せる**。 4つの修正を伴い、ファイル横断の到達範囲は別途決定し（ADR-46の改定）、lensは辞退されたリーダーに対して`unavailable`を維持します。
- **まず#1931を修正する**。その偽陽性はこれらすべてとは独立に今日存在します。
- **今すぐZARDにボトルネックを伝える**。属性型のほとんどがunavailableなのは、lensがそれらを省いているからではなく、コンストラクタパラメータが未型付けだからです。

## メンテナーへの決定事項

1. パートB（ADR-58の改定: 宣言されたコンストラクタパラメータをセンサス内で束縛する）を進めるか、またどのコーパスゲートを用いるか。
2. 到達範囲が所有者自身のファイルである間にパートAがそもそも望まれるか。これはlensの契約上の問いです: § Sitesは別ファイルからの読み取りを報告します。
3. 上記の利得を踏まえ、ファイル横断の到達範囲（公開センサス）がADR-46の改定に値するか。
