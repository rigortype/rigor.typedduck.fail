ステータス: 測定ノート（設計上のコミットメントなし）。2026-11-04にmaster `950faa291`（v0.4.7以降）に対して取得したものである。#1507が残した問いに答える: プロファイリングで「機能のコストが薄く広く分散している」と判明したあと、定数倍ではなく計算量そのものを削減するアーキテクチャレベルの変更はあるか？

## 測定手法

計測ハーネスがエンジンにカウンタをprependし、`rigor check --no-cache --workers=0`をインプロセスで実行する。フェーズごとの排他スレッドCPU時間、ノードあたりおよび同一の`(scope object, node)`ペアあたりの`ExpressionTyper#type_of`と`StatementEvaluator#evaluate`の呼び出し回数、`Scope`の構築回数、`Combinator.union`の呼び出し回数、そして実行理由別に分類されたすべての戻り値メモ計算を報告する。`MEMO=1`スイッチにより、そのレバーの規模を測るためのプロトタイプ`type_of`メモが有効になる。ハーネスはブランチ`work-census-harness`にある（§ 制約事項）。

コーパス: Rigor自身の`lib`（654ファイル、536K ASTノード、プラグインなし）、Mastodonの`app lib`（1,416ファイル、235Kノード、10個のRailsプラグイン）、Redmineの`app lib`（876ファイル、6個のプラグイン）。調査用チェックアウトはまずプライベートディレクトリにコピーした。どちらにも2026-10-27の`rigor-project-init`再初期化（Phase 5、`rigor sig-gen`）が#2437修正前に書き出した未追跡の`sig/`が含まれていた: 宣言を書き出していないスーパークラスに対するサブクラス宣言が含まれている。これによりMastodonで70件、Redmineで74件のRBS定義構築が失敗し、推論量に偏りが生じるため、コピーからはこれを削除した。チェックアウトのgem RBSコレクションはそのまま保持している。

CPU秒は負荷のかかった1台の共有ホスト上で計測した。フェーズ表はコーパスごとに1回の実行結果である。プロトタイプのA/B比較はMastodonと`lib`で交互に3ペア、Redmineで1ペア実行した。アロケーション数と呼び出し回数は決定的である。ウォール時間はCI上で計測していない。

## 乗数

`MODE=census`のカウント結果:

| | rigor `lib` | Mastodon |
| --- | ---: | ---: |
| `type_of`呼び出し回数 / ユニークな型付きノード数 | 2.82M / 477K (5.9×) | 1.45M / 192K (7.5×) |
| 同一の`(scope object, node)`ペアを繰り返す呼び出し | 1.16M (41%) | 1.08M (74%) |
| フェーズ別`type_of`呼び出し: 呼び出し先本体 / ルール / メインパス（`index:eval`） | 1.73M / 566K / 481K | 456K / 652K / 313K |
| `evaluate`呼び出し回数 / ユニークノード数（同一ペア重複） | 1.04M / 350K (30K) | 207K / 129K (9K) |
| ブロック深度0 / 1 / 2 / 3における型付きノードあたり`type_of`回数（解析対象ファイル自身のノード） | 6.5 / 11.3 / 15.8 / 29.3 | 9.4 / 9.4 / 9.5 / 14.0 |
| 呼び出し先本体評価回数 / ユニークdef数 | 50.6K / 14.7K（最大619） | 9.3K / 5.3K（最大268） |
| 戻り値メモ参照回数 / ヒット回数 | 133K / 98K | 94K / 84K |
| `Scope`オブジェクト構築回数 / `union`呼び出し回数 | 1.16M / 1.82M | 310K / 307K |

大部分は2つの構造的な要因で説明できる。

1. **`type_of`の結果が記憶されない**。メインパスは各ノードの入り口スコープを記録するがその型は記録しない（記録用ラムダ、`lib/rigor/inference/scope_indexer.rb:231-235`）。そして`Scope#type_of`はクエリごとに新しい`ExpressionTyper`を構築する（`lib/rigor/scope.rb:2363-2365`）。その後、各呼び出しノードは約10個のルールによってチェックされ（`lib/rigor/analysis/check_rules.rb:303-316`）、そのうちいくつかはレシーバチェーンを独自に再型付けする（`check_rules.rb:1956`、`:2237`、`:3145`）。Railsコードではこれが最大の重複要因である: Mastodonの`type_of`呼び出しの74%が同一ペアを繰り返しており、ルール走査が全`type_of`呼び出しの45%を占めている。フェーズごとの重複数は計測していない。
2. **呼び出し先本体は呼び出しコンテキストごとに1回評価される**。戻り値メモはレシーバー、引数型、`:self` fold grant、およびyield型をキーとしている（`lib/rigor/inference/expression_typer.rb:3454-3457`）。そのため、メインパス自身による本体評価とは別に、新しいレシーバーや引数型の組み合わせごとにdefが再評価される。

ブロック深度の行は3つ目のより小さな要因であり、一部のコードでのみ発生する。ブロック本体は値パスと文パスによって、異なる入り口スコープビルダー経由で2回型付けされる（`expression_typer.rb:4548`、`statement_evaluator.rb:8328`）。`lib`ではネストレベルが1つ深くなるごとに呼び出し率がおおよそ倍増する。Mastodonの率は横ばいだが、深度1に19K個の型付きノードがあるため、ネストの浅さでは説明できない。レビュー中のフィクスチャ調査により、この倍増は値パスが型付きレシーバーのもとでブロック本体を型付けする場合にのみ発生することが判明した: 4つの引数型で評価される呼び出し先内の`map`の中の`map`の中の`map`は、ノードあたり17.3 → 34.3 → 65.3回となった。同じチェーンを`Dynamic`パラメータに対して実行すると3.3 / 4.0 / 5.0にとどまり、ネストした`each`は4.0 / 5.0 / 4.8であった。Rails DSLのブロックはほとんどが型なしレシーバーを持つ。`lib`の勾配は呼び出し先の多重度とも絡み合っている。呼び出し先本体が`type_of`呼び出しの61%を占めており、最もホットな箇所がブロックを多用するウォーカーであるためだ。深度の行は解析対象ファイル自身のノードのみを対象としており、他ファイルのノードに対する766K回の呼び出し（27%）を除外している。深度0の率に対する超過分として試算すると、深度の影響は約284K回（`lib`の`type_of`呼び出しの10%）となる。深度3単体は662ノードである。

## 呼び出し先CPU時間の内訳

各計算は入り口で、そのdefまたはキーが以前に見られたかどうかによって分類される。ハーネスはレシーバーと引数型のみをキーとしており、これはメモのキーより粗い:

| クラス | rigor `lib` | Mastodon |
| --- | ---: | ---: |
| そのdefの初回評価 | 16.0 s (28%) | 9.3 s (21%) |
| 新しいレシーバーまたは引数型のもとでの評価済みdefの再評価 | 13.8 s (24%) | 3.7 s (8%) |
| 以前に見られたレシーバーと引数型でのメモミス（store-gate拒否、またはfold grantやyield型のみが異なるキー） | 1.07 s、709回評価 | 0.07 s、52回評価 |
| シグネチャがガードスタック上にある間のサイクル内再入 | 0.06 s、14.7K回評価 | 0.00 s、244回評価 |

2回目のセンサス実行では、同じ計算を引数形状でタグ付けした: 型付き引数 / すべての引数が`Dynamic[top]` / 引数なしは、`lib`でそれぞれ25.7 s / 6.2 s / 1.1 s、Mastodonで5.0 s / 2.6 s / 5.3 sであった。割合は各センサス実行自身の合計（57–61 sおよび44 s。フックがCPU時間を追加する）に対するものである。サイクル内再入は`lib`では回数が多い（`CalleeWriteCensus::ValueSources#sources`などの再帰的ASTウォーカーは619回評価される）が安価である: 本体を走査せずに現在のADR-55サマリーを返すためだ。

結果を変えずに呼び出し先キーをどこまで縮約できるか？

| 縮約 | rigor `lib` | Mastodon |
| --- | ---: | ---: |
| 本体を走査した計算のうち、本体が`Scope#local`経由で一度も読まなかったパラメータを除外する | 35,011回中443回評価（1.3%）、83件不一致 | 9,026回中224回（2.5%）、17件不一致 |
| 全計算のうち、引数が一致する場合にレシーバーを除外する | 50,592回中1,417回（2.8%） | 9,298回中1,592–1,894回（17–20%） |
| 複数キーを持ち、そのすべてのキーが同じ型を返したdef | 6,988個中4,991個 | 630個中561個 |

パラメータ読み取りマスクは有効なレバーではない。`Scope#local`経由で未読のパラメータを残した評価は644件（`lib`）および190件（Mastodon）しかなく、そのインターフェースで定義されるいかなるマスクもこれが上限となる。またマスクされた結果の一部は不一致となる。ここでは切り分けていない原因として、ローカル変数テーブル全体を受け取るリーダー（`AliasMutationFloor`、`lib/rigor/inference/alias_mutation_floor.rb:318`）は`Scope#local`を使わずにパラメータの型を参照でき、さらにハーネスキーはfold grantとyield型を省略しているためである。これはADR-84 WD4（b）の判定を、キー数ではなく評価計算量によって裏付けるものである。

レシーバー軸はRailsでは実質的な意味を持つ。継承されたヘルパー（`current_account`、`authorize`）がコントローラサブクラスごとに1回評価されるためだ。範囲が広いのは、カウントに最大302回の同一キー重複が含まれるためである。これを健全に縮約するには、本体が`self`について何を読んだかの記録が必要であり、ここで計測したものはそれを提供しない。「すべてのキーで同じ型」の行は事後的な観察にすぎず、何も正当化するものではない。

## プロトタイプメモ

`MEMO=1`は`ExpressionTyper#type_of`を`(scope identity, node identity)`でメモ化する。typerがオペランドテーブルを引き回している間またはキー存在ガード走査がアクティブな間はバイパスされ、ファイルごとにクリアされる。ストアゲートはない。交互に実行したbase/memoペアの総排他CPU時間:

| コーパス、設定 | CPU base → memo | アロケーション数 | 診断 |
| --- | --- | ---: | --- |
| Mastodon、survey設定（lenient、ベースライン有効）、ペア1 | 42.1 → 35.0 s (−17%) | 99.0M → 65.1M (−34%) | 6件、同一 |
| Mastodon、survey設定、ペア2 | 45.3 → 30.1 s（−34%）、ホスト負荷シフトあり | 99.0M → 65.1M | 6件、同一 |
| Mastodon、strict、ベースラインなし | 42.7 → 33.3 s (−22%) | 98.3M → 64.4M (−34%) | 2,783件、順序も含め同一 |
| Redmine、strict、ベースラインなし | 37.7 → 30.8 s (−18%) | 79.6M → 60.6M (−24%) | 1,844件、順序も含め同一 |
| rigor `lib`、ペア1および2 | 52.7 → 51.6 s（−2%）、54.3 → 49.0 s（−10%）、ホスト負荷シフトあり | 75.4M → 67.3M (−11%) | 1件、同一 |
| rigor `lib`、strict | 53.5 → 50.8 s (−5%) | 75.7M → 67.6M (−11%) | 1件、同一 |

Mastodonのペア2は、パース（0.41 → 0.31 s、−24%）やivarインデックス（−19%）などメモが到達できないフェーズも短縮しているため、−34%のうち約20ポイントはホスト負荷の影響である。`lib`のペア2も同様にシフトしている（パース −11%）。信頼できる軸はアロケーション数である: Railsコーパスで−24%から−34%、`lib`で−11%となった。Mastodonのクリーンな2ペアでは、ルール走査（`rules*`）が52–53%、呼び出し先本体が12–18%、メインパスが8–15%削減された。`lib`ではルール走査のみが動いた。重複のほとんどは安価なリーフノードであり（1.16M回のうち606K回が`LocalVariableReadNode`）、また別個の呼び出し先評価はそれぞれ独自の本体スコープを構築するため、ある評価での計算が別の評価でヒットすることはない。

診断が同一であっても、以下の理由からこのプロトタイプは健全ではない:

- **仕様の純粋性MUSTは現在成り立っていない**。`docs/internal-spec/inference-engine.md:24`は、1回の実行内で同じ`(scope, node)`ペアが構造的に等しい結果を返すことを要求している。しかし1回の呼び出し先評価の中でも、ADR-55の不動点計算は変化するスレッドローカル仮定のもとで同じ`body_scope`オブジェクトを最大3回評価する（`expression_typer.rb:3755-3758`）ため、エンジンはすでに反復をまたいで同じペアを異なる型に型付けしている。後の反復でメモヒットが起きると以前の反復結果が返ってしまう。またヒットによってreturn-sinkへのプッシュがスキップされると、`fixpoint_step`はjoinではなく計算値を返すため（`expression_typer.rb:3835-3843`）、`return`アームが失われる可能性もある。メモはそのMUSTを根拠として引用できない。実際に何が成り立つかを述べるよう仕様を改訂する必要がある。
- **本物のメモにはストアゲートが必要である**。計算がサイレントであった場合にのみ結果を保存する: シンクが増大せず、ADR-84の一時イベントが記録されず、ADR-46のレコーダが非アクティブであり、かつ計算途中でコンテキストフラグが設定されなかった場合である。
- **キーはアンビエント状態を網羅しなければならない**。仕様にはtyperが読み取るすべてのスレッドローカルを列挙し、それぞれがキーに含まれるか、あるいは理由付きの許可リストに載っていることを要求する必要がある。スレッドローカルではない入力が2つある:
  - typerのインスタンスごとの`tracer:`（`expression_typer.rb:256-258`）。このフォールバックイベント（仕様のFallback Tracerセクションで規定）がヒットによってドロップされるため、lensや`--explain`出力に影響する。
  - キー存在ガード走査の分離されたサイドテーブル。`Scope#with_isolated_side_tables`（`scope.rb:414-417`）は`optimistic_origins`を含めそれらをコピーするため、メモはこの走査を引き続きバイパスしなければならない。
- ADR-52 WD5はプラグイン貢献結果の呼び出しノード単位キャッシュを却下した。それらの結果が参照時のナローイング状態に依存するためである。スコープのアイデンティティをキーにすればその問題は解決する。`Scope`はイミュータブルであり、すべての遷移で新しいものが割り当てられるためだ。WD5はアンビエント状態に言及しておらず、それこそがゲートと仕様でカバーすべき対象である。

## 改善レバーのランキング

| # | レバー | 計測値または上限の効果 | リスク |
| --- | --- | --- | --- |
| 1 | サイレント計算ストアゲート付きの`(scope, node, context)` `type_of`メモ（#2709） | プロトタイプ: Railsコーパスでアロケーション−24から−34%、`lib`で−11%。CPUはクリーンなMastodonペアで−17から−22%、Redmineで−18%、`lib`で−2から−5% | 健全性はストアゲートとアンビエント状態の列挙に依存し、まず仕様のMUSTを改訂する必要がある。設計上、出力は同一 |
| 2 | defの引数なしまたは全`Dynamic`キーに対して、メインパスが戻り値メモにシードできるようにする（#2710） | 上限: 引数なしまたは全`Dynamic`とタグ付けされた初回評価の計算で、MastodonのセンサスCPUの約14%、`lib`の9% | 未検証: メインパスの`widen_clauses:`、yieldフレーム、レシーバー、fold grantが呼び出し先のものと一致する必要があり、ヒット時にはADR-46の読み取りセットを再生しなければならない |
| 3 | 値パスと文パスで共有される1つのメモ化されたブロック入り口スコープ（#1228の一般化） | `lib`の`type_of`呼び出しの約10%（深度0の率に対する超過分）。Railsではわずか | 現在2つのビルダーは異なっている。独自の等価性仕様が必要 |
| 4 | 継承メソッドに対するレシーバー非依存キー（#2711） | Mastodonの呼び出し先評価の17–20%、`lib`の3% | 本体が`self`について何を読んだかの記録が必要 |

レバーではないと計測されたもの:

- パラメータ読み取りマスク（上記）。
- サイクル内再入（14.7K回評価、0.06 s）。
- `call.possible-nil-receiver`ガード再走査（`lib/rigor/inference/key_presence_guard.rb:132-146`）: ハーネスはMastodonの1,416ファイルに対して1,418回の`ScopeIndexer.index`実行、654個の`lib`ファイルに対して654回を観測したため、再走査は最大2回である。
- ファイル単位プリパス走査の統合: 最大でも10–11%の行にとどまり、#1507による#1197の走査統合の計測では、4つの走査をまとめてもコールド実行の約0.2%であった。

未計測だが採用しない理由があるもの: TypeProf v2スタイルのコンテキスト非依存データフローグラフ（defあたり1つの戻り値頂点、`references/typeprof/lib/typeprof/core/graph/box.rb:698-723`）。これはすべての呼び出し元の引数型を1つの答えにunionするため、偽陽性規律が排除している最悪ケースの解釈となる。またプラグインフックとインクリメンタルゲートを作り直すことになり、それでもすべてのキャップが必要になる。

レバー1–4のあとに残るのは、主に異なる引数型のもとで再評価される呼び出し先本体である: 型付き引数を持つ`lib`の`new_key`計算は12.8 s、センサス実行CPUの21%を占める。これを削減するには、たとえばk個の異なるキーのあとに引数型をワイドニングするなど、キーを抽象化する必要がある。それは推論される型と診断を変えるため、パフォーマンス変更ではなくメンテナーの判断事項となる。

## その他の発見

`optimistic_origins`は4箇所で型付けの判断に読み戻されている: `expression_typer.rb:1941`（`widen_optimistic_predicate_constant`）、`def_return_typer.rb:129`、および`optimistic_origin.rb:111`と`:172`。推論エンジン仕様の純粋性の段落では、何も読み戻さないアイデンティティキー付きアドバイザリテーブルとして`dynamic_origins`と`void_origins`を挙げている。そこでは異なる振る舞いをする`optimistic_origins`に言及していない。メモ設計ではこれを入力として扱う必要がある。ガード走査の外にあるアイデンティティキー付きメモに対しては無害である。テーブルは派生スコープ間で参照共有されており、最初の計算がすでにエントリーを書き込んでいるためだ。

## 制約事項

- 計測器はブランチ`work-census-harness`（`tool/work_census/`、README付き）にあり、追跡質問のために残されているものでマージを意図していない。その呼び出し先キーはレシーバーと引数型のみである。そのレシーバー縮約カウントにはサイクル内計算と同一キー重複が含まれる。ガード再走査回数はフェーズ突入回数から推測している。
- CPU時間は負荷のかかった共有ホストから得たものである: フェーズ表はコーパスあたり1回実行、プロトタイプは最大3ペアでうち2つはホスト負荷シフトあり。アロケーション数とカウントの差分が信頼できる軸である。これらを高速化として引用する前には、CI-Linuxでのウォール時間A/Bテスト（`engine-wall.yml`）が依然として必要である。
- Rigor自身の`lib`はstrictプロファイルのもとでも診断を1件しか出さないため、その出力の一致には重みがない。Railsコーパスの4,627件がその主張を支えている。
- ハーネスは呼び出し先計算を入り口で分類する。あるクラスのCPU時間は本体の排他時間であり、ネストした計算はそれぞれのクラスに計上される。
- `~/repo/ruby/rigor-survey/`配下の調査用チェックアウトには依然として#2437以前の`sig/`が残っており（§ 測定手法）、そこからそのまま取得した計測値には同じRBS構築失敗が引き継がれる。その上で`rigor sig-gen`を再実行しても、sig-genが古いヘッダを保持するため解消しない（#2716）。`sig/`を削除して再生成するとMastodonの失敗は解消するが、Redmineには6件残る（#2715）。
- プロトタイプメモは実装候補ではない（§ プロトタイプメモ）。
