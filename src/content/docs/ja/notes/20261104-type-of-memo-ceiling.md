ステータス: 測定ノート、設計上のコミットメントなし。[ADR-129](../../adr/129-type-of-result-memo/)の根拠となる資料です。2026-11-04に、ブランチ`work-census-harness`の`726e61af0`にあるハーネス（master`7d0b051e8`ベース、`tool/work_census/memo3.rb`および`memo3_shadow.rb`）で取得しました。これは1つの問いに答えるものです: 別の周囲状態のもとで計算された結果を返せないようにメモをキー付けしたとき、ルールウォークの外側に削減可能な重複型付けはどれだけ残るか？

## なぜこの問いなのか

[センサス](../20261104-work-multiplier-census/)により、Mastodonの`type_of`呼び出しの74%が同一の`(scope object, node)`ペアを繰り返していることが判明しました。このペアだけをキーとするメモは誤りです。ネストされたブロックは外側のスコープオブジェクトのまま入るため（`Scope#entering_opaque_block`は`self`を返します）、1つのペアが異なるフレームのもとで型付けされ、実際の`call.undefined-method`が失われました。ADR-129の第2ドラフトでは、メモをルールウォークに限定しました。しかし3回のレビューラウンドのたびに、リストが見落としていた別の入力と、失敗し得ないランディングゲートが見つかりました。続いて、2つの独立した設計レビューが行われました:

- Fable 5.1（xhigh effort）;
- Opus 5.5（xhigh effort、Fableのレポートを読まずに実施）。

どちらのレビューもチェックインされていません。本ノートは、両者が合意した点と測定によって決まった点を記録します。

## 両レビューが独立して発見した点

インストールされたフレームのスナップショットを取るトークンは、型付けの隠れた状態をカバーしていません。さらに3つの種類が存在し、両レビューはそれぞれを同じコード箇所とともに挙げました:

- **インプレースで変更される状態:**
  - 復元なしでデクリメントされるunroll fuel（`ExpressionTyper#unroll_fuel_remaining`）;
  - ADR-55サマリー（その`:consulted`フラグに至るまで）;
  - 1つの配列に対してpushおよびpopされる再帰ガードスタック。
- **前後の差分として読み取られるカウンタ:**
  - `LoopValueRecord.loops_evaluated`;
  - fixpointのconsultマーク;
  - ADR-84の一時イベントマーク。

  メモヒットはインクリメントをスキップするため、差分を読み取る側は異なる値を見ることになります。
- **スコープの同一性をキーとする1スロットキャッシュ:**
  - `LoopValueRecord`;
  - injectアキュムレータレコード;
  - `MatchRebinding::Frame#memo`（フリーズされたスコープから到達可能なミュータブルオブジェクト）。

両者はまた、次のように結論づけました:

- 修正では、キーを列挙するのではなく、状態が宣言されている場所で種類ごとに状態を分類し、デフォルト拒否（deny-by-default）の静的仕様を持たせる必要がある;
- テーブルの読み取りはヒット時にログ記録および検証し、ネストされたヒット時には外側の計算のログにマージする必要がある;
- トークンのインターン化（interning）には価値がない。

Opusはさらにいくつかの点を追加しました:

- 型付け状態は`Thread.current[]`の外側にも存在する: `thread_variable_set`（`Plugin::IoBoundary`、`RunDisclosureCredit`）やモジュールレベルのivar内。
- `FlowTracer.active?`は`Combinator.union`のファストパスを変えるため、単なるバイパスではなく入力である。
- ゲートにはフォールトインジェクションが必要であり、メカニズムが取り除かれたときに失敗することを実証できなければならない。

Fableは次を追加しました:

- `MemoAudit::Mismatch`は`StandardError`であるため、型付けパス上の`rescue StandardError`がシャドウモード内でそれを握りつぶしてしまう（既存の監査について#2785として起票）。
- リーフノードは保存する価値がない。

同じ棚卸しにより、ADR-84のreturnメモ自身のキーもこれらの入力のうち2つを欠いていることが判明しました:

- リフレクティブなivarの繰り返し深さ（#2773）;
- ブロック本体のスレッディング抑制（#2782として起票）。

これは4回のレビューサイクルを経たメモの内部で起きた、同じ種類の障害クラスです。

## 手法

`MEMO=3`は`(scope identity, node identity, state id)`をキーとするライブメモをインストールします:

- **State id:**モジュールレベルの整数です。すべてのフレームのインストールが新しいidを取得し、フレームは終了時に古いidを復元します。すべてのインプレースのリソース書き込みも新しいidを取得し、ガードスタックの所有者はdrain時に保存していたidを復元します。
- **対象となるフレーム:**
  - yieldおよびフォワード引数のフレーム、threadedフラグと繰り返し深さ;
  - 6つのジャンプシンクとretryフレーム;
  - key-presenceウォーク、Acceptance拒否キー、writer-scopeキー、unentered-evaluatorキー;
  - トレーサのスイッチ。
- **拒否ルール:**
  - `escape`: シンクへのpushまたはリソース書き込みが、その外側にインストールされたスロットをターゲットにしている場合に計算を拒否する;
  - `any`: 何らかのリソースまたはシンクに触れた計算を拒否する。
- **リプレイ:**プロトタイプv2と同様に、ヒット時にadvisoryテーブルへの書き込みをリプレイします。
- **メモのスコープ:**ファイルごとにクリアされ、`MEMO_PHASES`によってルールウォーク、メインパス、および呼び出し先本体が選択されます。
- **シャドウモード:** `SHADOW=1`はメモを停止した状態で全ヒットを再計算します。リプレイ後の型および4つのテーブルの状態を、再計算後の状態と比較します。

コーパス: Mastodonの`app lib`（10個のRailsプラグイン）、Redmineの`app lib`、およびRigor自身の`lib`。

- プライベートコピーはセンサスで使用したものです。
- 出力は`--format json --no-cache --workers=0`で、ベースラインなし・strictプロファイルです。
- ベース実行とメモ実行を交互に行いました。
- ホストのロードアベレージは12コアで約70だったため、実測CPU時間はノイズです。判断は決定論的なアロケーションと、カウントモードのCPU予測値に基づきます。予測値は最も外側のヒット候補のCPUからカウンタ自身のブックキーピングを差し引いたものです。これはグロス値であり、ルックアップとストアのコストは差し引かれていません。

## 結果

Δはベースに対する値です。`r`はルールウォーク、`m`はメインパス、`c`は呼び出し先本体です。`_e`と`_a`は拒否ルールです。

| フレーム計装あり、メモ閉鎖 | +0.5% | +4.9% | — | +0.8% | — |
| `r_e` | −18.95% | −6.5% | −10.87% | −2.00% | — |
| `rm_e` | −23.37% | −4.6% | −14.48% | −2.63% | — |

ベース数値:

- Mastodon: CPU 43.4 s、98.3Mアロケーション、診断2,783件。
- Redmine: 37.5 s。
- `lib`: 53.8 s、75.75Mアロケーション。

**ルールウォーク以降の残余**（メインパスと呼び出し先本体の合計）:

| コーパス | アロケーション | カウントモードCPU予測値 |
| --- | ---: | ---: |
| Mastodon | 11.2% | 2.85 + 4.40 = 7.25% |
| Redmine | 7.4% | 1.87 + 2.38 = 4.25% |
| `lib` | 3.4% | 0.75 + 2.34 = 3.09% |

**正確性:**

- 診断: 3つのコーパスすべてにおいて、すべての構成およびすべての反復で−0 / +0。
- シャドウモードでは`type_of`メモのみを停止し、ADR-84のreturnメモおよび他のすべてのメモは有効のままにしました。
  - `rmc_a`（`any`ルール）のもとでチェックされたヒット数: Mastodonで101K、`lib`で158K、Redmineで119K。全構成合計では101K〜236K、158K〜652K、119K〜394K。
  - 型の不一致は**0**回でした。再計算が拒否されたことはなく、idを動かしたものもありませんでした。
  - ハーネスはテーブルの読み取りをログ記録も検証もしていないため、これらのヒット数は上限値です。特に、計算中にキーをABSENTとして読み取った後にそれを書き込むエントリーは、単純な読み取り検証のもとでは自身を無効化することになります; ADR-129のリードスルーキャッシュルールはそのケースのために存在します。
  - ハーネスはリソースの書き込みのみで拒否を行いました。ADR-129の第2ラウンドレビューが調査した2つの読み取り箇所（ユーザーメソッド推論エントリーと`record_conditional_value`）でも拒否するようにしたところ、Mastodonでのアロケーションは−30.1%ではなく−24.2%となりました。ADR-129はその2つの読み取りを免除しており、書き込みのみのカウントがそれを近似しています。
- `rmc_a`のもとで、再計算の書き込みリストが保存されたリストと異なった回数は416回、846回、1,104回（Mastodon、`lib`、Redmine）でした。各実行60件のサンプルでは、リストの違いはターゲットスコープの同一性のみでした。以下の比較では、最終的なテーブル状態を使用しています。
- リプレイ後のテーブル状態が再計算と一致しなかった回数は、`rmc_e`（`lib`）で1回、`rmc_a`で0回、同一インストールでidを保持した場合は167回、198回、43回でした。
  - 各不一致は、ネストされた推論中に呼び出し先本体の内部で書き込まれた`dynamic_origins`のcauseです。後の再計算時にADR-84のreturnメモが本体をウォークせずに応答するため、リプレイされたcauseが古くなります。
  - これは両レビューが予測したリードバック（read-back）のクラスです。
  - `check`の出力は変化せず、再現ファイル（`lib/rigor/inference/alias_mutation_floor/reach.rb`）での`coverage --protection`はバイト単位で同一です。

**拒否ルール:**

- `any`はMastodonでメインパスのヒットを301件失い（20,829に対して20,528）、72件に対して6,808件の計算を拒否します。
- アロケーションの削減幅は0.05、0.24、0.07ポイント小さくなります（Mastodon、`lib`、Redmine）。
- ルールウォークはコーパスあたり約5つの呼び出し先本体のみを開始します。
- escapeのもとで、Mastodonの145万回の呼び出しに対する拒否は、リソース書き込みが9,294件、エスケープイベントが750件、内部イベントが68件、シンクへのpushが105件でした。

**リーフ:**

- リーフを保存すると、Mastodonで135K件、`lib`で494K件のヒットが追加され、CPUの0.8%および0.66%と予測されます。
- `lib`のアロケーションは悪化し（+0.5ポイント）、RSSは+10.8%に上昇します。

**キーの粒度**（Mastodonにおける最も外側の非リーフヒット数）:

| キー | ヒット数 |
| --- | ---: |
| `(scope, node)`のみ | 115,807 |
| 正確なid | 101,316 |
| 同一インストールを跨いで保持するid | 111,966 |
| フレーム値のベクタ（インターン化の上限） | 112,512 |

- ギャップの大部分は、`eval_def`がnilのreturnシンクの上にnilのものをインストールするため、ルールウォークのルックアップがメインパスのエントリーを見逃すことによるものです。
- ノードごとの一方向スロットによるヒット損失は0.3%未満です。
- センサスにおける`(scope, node)`の重複の94%は、正確なidのもとでも生き残ります。

## 制限事項

- idはスレッドごとのスロットではなくモジュール変数に置かれています。`--workers=0`のみ対応。
- escapeのもとでは、プロトタイプv2と同様に、イベントが開いているすべての計算を拒否します。`any`は読み取りではなく書き込みをカウントします。
- フレーム値のベクタはサマリーの内容を省略しているため、インターン化の上限は健全（sound）ではない可能性があります。
- `KeyPresenceGuard`の再ウォークはメインパスとしてカウントされています。
- Redmineの1回の実行がYJITパニック（"YJIT should only see live objects"）で終了しました。再実行は正常でした。
- コーパスはサーベイのチェックアウトの最新同期ではなく、センサスのプライベートコピーです。
