Status: [#870](https://github.com/rigortype/rigor/issues/870)のための計測ノート；[#872](https://github.com/rigortype/rigor/issues/872)が修正しなければならなかった原因を特定。この特性評価はエンジン変更なしで着地しました；下記の解決策セクションには、その後#872が変更した内容が記録されています。

## 課題

`rufo-0.18.2/lib/rufo/formatter.rb`（4,221行、オプショナルおよびキーワードパラメータを持つ相互再帰的な`visit_*`メソッド群の単一クラス）に対する`rigor check --no-cache`が終了しません: v0.3.4では11ファイルのgem全体で23秒だったのに対し、v0.3.8では25分以上、master `5cab4e07`では120秒以上かかります。報告者の874ファイルからなるコーパス内の他のすべてのgemは12秒以下に留まっています。報告者はこれを[`acd35612`](https://github.com/rigortype/rigor/pull/547)（「シグネチャ単位で諦める代わりに、パラメータごとにユーザーメソッド呼び出しの引数をバインドする」）に二分探索で絞り込み、プロセスが`rb_ary_push` / `ary_ensure_room_for_push` / GCスイープに時間を費やしていると読み取りました — ハングではなく、超線形な探索による配列拡張の激しいチャーンです。

報告者の仮説は、パラメータごとのバインダーがメモや予算なしで手続き間に呼び出し先の戻り値を再推論しているというものでした。その半分は正しく、もう半分は間違ったコンポーネントを指しています: メモは*存在し*、キー付けも正しく行われており、バインダーがそれをスラッシングしているわけではありません。欠けているのは、メモが*保存を拒否（refuse a store）*することを許可される頻度の上限でした。

## フィクスチャ

`spec/integration/fixtures/issue_870_mutual_recursion/`にジェネレータとそのコミットされたサイズ6の出力が保持されています。その形状は、rufoの`formatter.rb`をその本質的な構造へと縮小したものです — 1つのクラス、単一の強連結成分（SCC）内にある`size`個の相互再帰的メソッド、各々がオプショナルな位置引数とキーワードパラメータを持ち、各々がリテラル引数値で3つの兄弟を呼び出す:

```ruby
class Visitor
  def visit_0(node, indent = 0, force: false)
    return node if force
    a0 = visit_1(node, indent + 0, force: true)
    a1 = visit_2(node, indent + 1, force: false)
    a2 = visit_3(node, indent + 2, force: true)
    a0 || a1 || a2
  end
  # ...
end
```

gemなし、`sig/`なし、未定義のミックスインなし — 実際のファイルが発生させる`Rufo::Settings`ミックスインの障害は付随的なものであり、再現には不要です。6を超えるサイズは計測用であり、コミットされていません；`ruby spec/integration/fixtures/issue_870_mutual_recursion/generate.rb 14 3`で再生成されます。

## 計測時間

master `5cab4e07`における`rigor check --format json --no-cache --workers 0`、1実行あたり1ファイル、macOS、連続実行。約2.0秒の下限はプロセスの起動とRBS環境の構築です；増加分はその上の項です。

| メソッド数 | 行数 | ウォールタイム | ピークRSS | `infer`エントリー | 本体評価数 | メモヒット率 |
|---|---|---|---|---|---|---|
| 8 | 58 | 2.5 s | 231 MB | 3,687 | 3,264 | 25.8% |
| 10 | 72 | 3.9 s | 309 MB | 14,709 | 13,316 | 22.2% |
| 12 | 86 | 7.0 s | 476 MB | 55,365 | 50,812 | 19.8% |
| 14 | 100 | 14.0 s | 725 MB | 207,609 | 192,414 | 18.0% |

ファイルが14行増えるごとに、メソッドが2つ追加されるたびにウォールタイムは倍増し、推論エントリーは約3.7倍に増殖します。コンポーネントが大きくなるにつれてメモのヒット率は*低下*します。これは強連結成分のサイズに対して指数関数的であり、これが4,221行の1ファイルが874ファイルのコーパス全体と異なる振る舞いをする理由です。

## 二分探索: #547が実際に変更した内容

同じジェネレータが、同一の呼び出しグラフが必須位置引数のみを使用する対照群を出力します（`def visit_0(node, indent, force)` / `visit_1(node, indent + 0, true)`）。`acd35612^`および`acd35612`でエクスポートされたツリーに対して両方の形状を実行した結果:

| 形状 | `acd35612^`（#547前） | `acd35612`（#547後） |
|---|---|---|
| 必須位置引数のみ | 12.5 s | 12.6 s |
| オプショナル＋キーワード（`opt`） | **1.25 s** | **14.1 s** |

この爆発的な増加は#547で新設されたものでは*ありません*。必須パラメータのメソッドに対しては`acd35612^`の時点ですでに完全に存在しており、コミットによって変化していません。#547が変更したのは、どのシグネチャがそこに到達するかでした: コミット前は、`user_method_param_shape_simple?`がオプショナル、rest、キーワード、またはブロックパラメータを持つあらゆるシグネチャを拒絶し、`build_user_method_body_scope`が`nil`を返し、`infer_user_method_return`が最初のホップで`nil`を返していました — そのため、オプショナル／キーワードスタイルで書かれた`visit_*`クラスタに対しては手続き間のエッジが存在せず、コンポーネントが形成されることもありませんでした。#547はそれらのエッジを実在化させ、それによって以前から存在していた非有界な探索を露呈させたのです。パラメータごとのバインドをリバートすることは問題を再び隠すだけであり、修正することにはならないため、#872はそれを禁じています。

## 原因

`ExpressionTyper#consult_and_store_return_memo`は、計算された戻り値を保存してよいかどうかを事後的に決定します（ADR-84 WD3）。計算中に記録された一時機構イベント（transient-machinery event）がブラケットのエントリー深度より*深い（浅い位置にある）*スタックフレームを参照していたことを`context_tainted?`が検出した場合、保存は拒否されます。強連結成分の内部では、その条件はほぼ常に真になります: すべてのネストした計算の本体は、最終的に再帰ガードスタック上にすでに存在するシグネチャ（祖先）に再突入し、`note_transient_fallback`がそれを祖先の（より浅い）位置に記録します。サイズ12におけるカウンタがそれを正確に示しています:

```
infer entries:   55365
memo consults:   22989  (hits 4553 / misses 18436; hit rate 19.8%)
body evals:      50812
non-stored:      on-stack 32376  unroll-in-flight 0  consult-tainted 0  transient-tainted 18412
top signatures by body-eval count (evals / distinct-keys / signature):
      5512       2  Visitor#visit_1
      5396       2  Visitor#visit_2
      ...
```

18,436件のメモミスのうち18,412件（99.87%）が結果を計算した後に保存を拒否されました。コンポーネント内部のものは一切メモ化されないため、すべての呼び出しエッジが呼び出し先サブツリー全体を再探索します: 分岐係数はファンアウトに等しく、深さはコンポーネントのサイズに等しくなります。

**固有キー（distinct-key）の列が対立仮説を打ち砕きます**。各シグネチャは5,000回以上評価されながら、厳密に*2つ*のキーの下でのみメモ化されています。これはパラメータごとのバインダーの値固定された引数による引数粒度のスラッシングではないため、`memo_key`を拡大または正規化すること（#547のPR本文が言及していた最適化の余地）はここでは何の役にも立ちません。`RECURSION_UNROLL_FUEL`と`RECURSION_FIXPOINT_CAP`はどちらも0を示しています: 既存の予算は間違った軸にあります。爆発している量である*最外層エントリーあたり、シグネチャあたりの本体評価数*に対する制限は一切存在していません。

### 確認

まさにそのゲートを無力化する（エクスポートされたツリーで`context_tainted?`を強制的に`false`にする — 一時的なクリーネ反復に役立っているため健全ではなく、提案される修正ではありません）と、その項は崩壊します:

| ターゲット | master | ゲート無力化 |
|---|---|---|
| フィクスチャ、12メソッド | 7.0 s / 55,365 entries | 2.4 s / **111** entries |
| フィクスチャ、14メソッド | 14.0 s / 207,609 entries | 2.0 s / **129** entries |
| `rufo-0.18.2/lib/rufo/formatter.rb` | > 900 s（強制終了） | **4.0 s** |

エントリー数は3桁減少し、実際のrufoファイルは4秒で終了します。この項は完全に保存ゲートに起因しています。

### 報告者がサンプリングした配列チャーン

`stackprof`（CPUモード、1 ms、サイズ12フィクスチャ、プロセス内ランナー）は、テイント機構自体をRigorのフレームの最上位に位置づけています:

```
Samples: 4809   GC: 1339 (27.84%)
  1166 (24.2%)  (sweeping)
   525 (10.9%)  Rigor::Inference::ExpressionTyper#note_transient_fallback
   338  (7.0%)  Rigor::Inference::ExpressionTyper#context_tainted?
   159  (3.3%)  (marking)
   134  (2.8%)  Rigor::Inference::ExpressionTyper#consult_summary
```

これが報告者の見た`rb_ary_push` / `ary_ensure_room_for_push` / スイープのシグネチャであり、それ自体に二次的な原因があります: `TRANSIENT_EVENT_DEPTHS_KEY`はガードスタックが空になったときにのみクリアされる追記専用のArrayであるため、1つの最外層エントリー内でイベント総数まで肥大化し、`note_transient_fallback`がそこにpushし続け、`context_tainted?`が候補計算ごとにサフィックススライス（`log[event_mark..]`）をアロケートします。指数関数的な再探索の上に、イベント数に対する二次関数のアロケーション項が加わります。どちらも探索が制限されれば消えますが、ログの肥大化自体も制限する価値があります。

## #872が行ったこと（2026-09-09）

レバー1の形状（a）が、コンポーネントモデルなしで健全な狭い形式で着地しました: **コンテキストが汚染された結果であっても、それが`Dynamic[top]`であれば保存される**（ADR-84 WD6）。コンポーネントの内部ではすべての結果がそれであるため、探索は崩壊します；その外部ではゲートは変更されません。`untyped`は束のトップであり、ADR-5の劣化の下限であるため、保存されたtopを提供することは、テイントのない再計算よりも精度が*低く*なることしかありません — 祖先のコンテキストが捏造した型になることは決してなく、新規の評価が発生させない診断を発生させることも決してありません。形状（b）である`(signature, outermost entry)`ごとの本体評価上限は実装されませんでした: 探索を*cap × signatures × outermost entries*にしか制限できず、rufo上では依然として二次のままであり、例外とは異なり実際の精度予算になってしまうためです。レバー2も着地しました — `context_tainted?`はサフィックススライスをアロケートする代わりに、インデックスによってログをスキャンします。

| メソッド数 | 変更前: ウォール / 評価数 | 変更後: ウォール / 評価数 |
|---|---|---|
| 8 | 1.7 s / 3,264 | 1.1 s / 28 |
| 10 | 3.2 s / 13,316 | 1.1 s / 32 |
| 12 | 6.2 s / 50,812 | 1.2 s / 36 |
| 14 | 13.9 s / 192,414 | 1.2 s / 40 |

`rufo-0.18.2/lib/rufo/formatter.rb`: > 900秒（強制終了） → **2.7秒**；gem全体の`lib` → **2.8秒**。
`--format json --no-cache`は`lib`、`plugins/*/lib`、`examples/*/lib`、liquid、mail、redmine、およびmastodon全体でバイト単位で一致しています。

## #872に向けた修正の方向性（修正前に書かれた内容）

互いに独立した2つのレバーがあり、いずれも探索を制限できます；第1が根本であり、第2は安価な保険です。

1. **自コンポーネントのイベントに対してテイントゲートを完了認識可能にするか、再探索を制限する**。ゲートは健全ですが粗すぎます: 「祖先の実行中状態が自分のサブツリーのどこかで触れられた」ことを「自分の結果はコンテキスト依存である」として扱っています。1つのSCCの内部ではそれはすべてのフレームです。互いに比較計測する価値のある2つの形状: （a）コンポーネントをキーとする*暫定的な（provisional）*エントリーを保存し、最外層エントリーが空になったときに無効化する。これにより、同じ最外層探索内での繰り返しがヒットする；（b）`RECURSION_FIXPOINT_CAP`と並んで、`(signature, outermost entry)`ごとの厳格な本体評価上限を設け、枯渇時に`Dynamic[top]`に縮退する。（b）はより小さな変更であり、ADR-5に準拠しています — 間違った型ではなく`Dynamic`に縮退する上限 — ただし、縮退によって診断が動いてしまうため、コーパス上で発火しないことを示す必要があります。（a）は健全にできるのであれば厳密により優れています。どちらを選択するにせよ、受け入れテストは`lib`、`plugins/*/lib`、および調査プロジェクト全体で`--format json`がバイト単位で一致することです。
2. **`TRANSIENT_EVENT_DEPTHS_KEY`を制限する**。 `context_tainted?`は`event_mark`以降のいずれかのイベントが`entry_depth`より浅いフレームを参照したかどうかを知る必要があるだけです — マーク以降の最小深度を保持するか、サフィックススライスなしでスキャンすることで、レバー1に関係なくアロケーション項を排除できます。なお、これは現在のゲートを正しく機能させているのと同じログであることに注意してください；エントリーより浅いイベントを見落とすような方法で切り詰めてはなりません。

ゲートスペックは、ウォールクロックではなく本体評価カウンタを持つサイズ6のフィクスチャ上に配置すべきです: `spec/rigor/inference/mutual_recursion_walk_growth_spec.rb`は現在*好ましくない*形状（メソッド数をはるかに超える評価数、最大4つの固有キー）を固定しているため、#872は最初の期待値を上限へと反転させ、レッドからグリーンになるゲートを持つことができます。

## 再現手順

```sh
# Flakeの内部、リポジトリのルートから
ruby spec/integration/fixtures/issue_870_mutual_recursion/generate.rb 14 3 > /tmp/visitor_14.rb
RIGOR_BUDGET_TRACE=1 bundle exec ruby -I lib -I plugins/rigor-rbs-inline/lib exe/rigor \
  check --format json --no-cache --workers 0 /tmp/visitor_14.rb
```

`--workers 0`が必須です: カウンタは`fork`をまたぎません。[#775のノート](../20260908-v037-allocation-regression-attribution/)で言及されているように、予算トレースカウンタは1つのホスト上で数時間の間に約1%ドリフトするため、上記のすべての比較は同じツリー上で連続して行われています。
