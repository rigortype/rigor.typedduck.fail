## 1. 背景と問い

Rigorのエフェクトシステムは、メソッドが*何をするか*（`io.db.read`・`nondet.time`）をメソッドごとのサマリーとして報告し、`rigor effects`のレポートとコミットされたスナップショットを通じて表に出す。Capture Checkingは、値が*何に到達しうるか*を型の接尾辞として報告する（`Logger^{fs}`）。この2つは表面的には交換可能に見え——どちらもプログラムの実体の隣に、エフェクトめいた名前の小さな波括弧の集合を印字する——そしてm3techの記事はCCの提示形式を魅力的に見せる: 正しいコードにはアノテーションの負担がゼロで、リソースがエスケープする場所にだけエラーが出て、依存関係が推論された型の中に見える。

このノートが答える問い: **Rigorは自身のエフェクトラベルをCCの装いで誠実に見せられるか**——たとえば`rigor type-of`の出力・sig-genの出力・診断の中の`String^{db, net}`のように——**そしてその翻訳で何が失われ、得られ、あるいは過剰に約束されるのか？**

## 2. Scala 3のCapture Checking

### 2.1意味論

Capture CheckingはScalaの型システムを変更し、**値の中のケイパビリティへの参照**を追跡する（[overview](https://nightly.scala-lang.org/docs/reference/experimental/capture-checking/overview.html)）。リファレンスドキュメントによる可動部:

- **ケイパビリティは項レベルの値である**。「*オブジェクトケイパビリティ*とは、構文的にはメソッドまたはクラスのパラメータ、ローカル変数、あるいは囲むクラスの`this`である」——その型が空でないキャプチャ集合を運ぶもの（[basics](https://nightly.scala-lang.org/docs/reference/experimental/capture-checking/basics.html)）。ケイパビリティは他のケイパビリティから作られ——`val lg: Logger^{out} = new Logger(out)`——その連鎖は**ルートケイパビリティ**で底を打つ。現在のnightlyでは`any`と綴られる（`T^`は`T^{any}`の略記;古いドキュメント・論文・両方のブログ記事では`cap`と綴られる——このリネームは最近のもので、m3techの記事が指摘する複数の揺れの1つだ）。
- **キャプチャ型**。 `T^{c₁, …, cᵢ}`は、形状の型`T`と、値が保持しうるケイパビリティの集合を対にする。`T^{}`は純粋である。関数の矢印も同じことを符号化する: `A => B`は不純（`A ->{any} B`）、`A -> B`は純粋、`A ->{c, d} B`はちょうど`c`と`d`をキャプチャする。
- **サブキャプチャ**。キャプチャ集合は、導出の順序に沿ってより広いものが期待される場所で許容される: `{l} <: {fs} <: {any}`——`fs`から導出されたケイパビリティは`fs`によって説明される。
- **ボックス化された型**。ジェネリックな型構築子の下のキャプチャ型は「ボックス化」され、ボックス化／解除の適応は推論される;これが多相性を健全にしているもの（「キャプチャトンネリング」）であり、ユーザーからはおおむね不可視である（*Capturing Types*の§boxing;[polymorphism](https://nightly.scala-lang.org/docs/reference/experimental/capture-checking/polymorphism.html)）。
- **エスケープ検査**。ローカルにスコープされたケイパビリティは、外側のスコープのキャプチャ集合に現れてはならない。文書化されたエラーは§5にとって示唆的だ:

  ```
  Found:    (f: java.io.FileOutputStream^'s1) ->'s2 () ->{f} Unit
  Required: java.io.FileOutputStream^ => () ->'s3 Unit

  Note that capability f cannot be included in outer capture set 's3.
  ```

- **Separation Checking**（より新しく、CCの上に重ねられる;`captureChecking`のオプトインの上に、自身の`import language.experimental.separationChecking`を必要とする）は、このモデルをミューテーションとエイリアシングへ拡張する（[separation-checking](https://nightly.scala-lang.org/docs/reference/experimental/capture-checking/separation-checking.html);tanishikingの記事も同じ地面を例付きで歩く）。ミュータブルなクラスは`Mutable`トレイトを継承し、そのミューテーターに`update`修飾子を付ける;すべてのケイパビリティは、その型が`SharedCapability`を継承しない限り排他的であり、各排他的ケイパビリティ`x`は読み取り専用版`x.rd`を持つ（`Ref^`は`Ref^{any}`へ、該当位置の素の`Ref`は読み取り専用の`Ref^{any.rd}`へ展開される）。検査そのものは干渉の規則である: 2つのキャプチャ集合は、一方が排他的ケイパビリティ`x`を保持し他方が`x`またはその読み取り専用版`x.rd`に言及するとき干渉する;推移的なキャプチャ集合が干渉しないとき、それらは分離されている。検査器は、呼び出しの引数どうしの分離（各引数の隠れ集合を、他の引数のキャプチャ集合・関数の前置部・結果に対して照合する）と、文の並びにおける、使われるケイパビリティと先行する定義の隠れ集合との分離を要求する——形式パラメータのキャプチャ集合が衝突するパラメータを明示的に名指しているときの逃げ道付きで。`consume`パラメータはムーブ意味論を与える: 渡されたケイパビリティは呼び出しを超えて予約され、元の参照はその後使えなくなる。リファレンスのページ自身が、この層をCapture Checking本体より成熟度が低いものとして注記している——安全性と表現力の釣り合いはまだ問われている最中だ。

### 2.2エフェクト多相性は項を渡すことから自然に落ちてくる

ケイパビリティは通常の値なので、通常のジェネリックなシグネチャがすでにエフェクト多相である: `def map[B](f: A => B)`は、どこにもエフェクト変数を置かずに「純粋な関数**および**キャプチャする関数に対して動く」——`B`を実体化して`f`を渡すことが、キャプチャの情報を運び通す（[polymorphism](https://nightly.scala-lang.org/docs/reference/experimental/capture-checking/polymorphism.html)）。明示的なキャプチャ集合パラメータ（`class Source[X^]`、シールされた`CapSet`マーカー上の有界なキャプチャ集合変数）は、暗黙の多相性では表現できない場合——遅延コレクション、リスナーのレジストリ——のために存在するが、ドキュメントは暗黙の経路を優先せよと述べる。

### 2.3ユーザーに触れる面

- **ファイル単位のオプトイン**: Scala 3のnightlyで`import language.experimental.captureChecking`。Separation Checkingはその上に自身の`separationChecking`のimportを必要とする——そのページによれば、まさにその層が成熟度の低い方だからこそ分けられている（[how-to-use](https://nightly.scala-lang.org/docs/reference/experimental/capture-checking/how-to-use.html)）。
- **ユーザーは境界にアノテーションを付け、コンパイラが中間を推論する**: パラメータの型がケイパビリティのマーカーを得る（`FileOutputStream^`）;クロージャと結果のキャプチャ集合は推論され、`-Vprint:cc`で表示できる。Scaladocはnightlyの標準ライブラリのAPIドキュメントでキャプチャ型を描画する。
- **エラーのスタイル**: キャプチャ集合に対するFound/Requiredの対と、流れられないケイパビリティを名指す注記。m3techの記事は、メッセージが具体的な修正を提案することを強調し、その哲学を「正しいコードには何も要求せず、間違ったコードだけを弾く」と要約している。
- **健全性の姿勢**: CCは自身が検査するコードに対する*健全な検査器*である——キャプチャ集合は値が保持しうるものの完全な説明であり、サブキャプチャとエスケープ検査によって強制される。その完全性の主張こそ、接尾辞の構文が*視覚的に断言している*ものであり、§4.3にとって荷重を支える。
- **安定性**: 実験的であり、活発に揺れている——m3techの記事（Scala 3.8.3に対するもの）は、`cap` → `any`のリネーム、ケイパビリティ階層の再編、そして数か月のうちにreachケイパビリティが削除されたことを注記している。関係者の誰も本番利用を推奨していない。

## 3. Rigorの実装済みエフェクトシステム

### 3.1それが何であるか

[`docs/type-specification/effect-labels.md`](../../type-specification/effect-labels/)で規範的に定められ、[`docs/internal-spec/effect-summaries.md`](../../internal-spec/effect-summaries/)に従って生成され、[ADR-103](../../adr/103-effect-labels/)で決定された。その形:

- **ラベルは閉じたレジストリ内のドットパスであり**（`io.db.read`・`nondet.time`・`mutate.self`）、セグメントを意識した前置subsumptionで検査される（ADR-103 WD1〜WD2）。それらは*呼び出しが何をするか*を分類する——プログラム変数の名前ではない。
- **単位はメソッドである**。サマリーは`Class#method` / `Class.method`でキー付けされ（`effect-summaries.md:39-52`）、開き直しは和を取る。エフェクトは、人手で監査されたカタログと、小さな構文の集合（バッククォート、gvar/cvar/ivarの書き込み、`define_method`、…）に由来する（`effect-summaries.md:69-81`）;カタログの行は**上界**である——`IO#write`は`io.fs.write`ではなく`io`だ。チャネルがソケットでありうるからである（`effect-summaries.md:141`）。
- **2つのレーンと1ビット**。サマリーは*証明済み*レーン（アナライザーがコードを読んだ）、*宣言*（`≤`）レーン（信頼するが読んでいない主張: プラグインの行、`effects.attribution:`、呼び出しサイトのエンベロープ）、そして原因の閉じた列挙（`dynamic-receiver`・`opaque-callable`・`unresolved-super`、…）によって汚染される網羅性のビットを運ぶ（`effect-summaries.md:117-129`）。「汚染は決してfindingを生成しない。網羅的でないサマリーは『これらのエフェクト、そしておそらくもっと』と読める」（`effect-summaries.md:129`）。
- **伝播**はプロジェクトの呼び出しエッジ上のレーンごとの単調な不動点であり、閉世界のオーバーライド結合を伴う（`effect-summaries.md:241-263`）。宣言レーンは不動点*の*レーンであって、証明済みへ結合されることは決してない（`effect-summaries.md:251`）。
- **エンベロープ**（`%a{pure}`・`%a{rigor:v1:effect …}`・`.rigor.yml`の規約スタンザ）は、**証明済みレーンのみ**に対して検査される宣言された上界である（`effect.envelope-exceeded`・`effect.liskov-widened`、どちらもオプトイン）。**スナップショット**（`.rigor-effects.yml`、`rigor effects update|check|diff|explain`）が主たる検証手段である: コミットされた記録であり、そのレビューされた差分とCIのゲートが強制の面となる（ADR-103 WD7）。

### 3.2今日それがどこに現れるか

レポート（`docs/manual/19-effect-labels.md`の§「行を読む」）はメソッドごとにこう印字する:

```
IssuesController#create: [global.read, io, mutate.instance, …] ≤ [email.send, job.enqueue, …] …? (21 reasons, --why)
```

——証明済みリスト、`≤`の宣言リスト、そして「おそらくもっと」を表す` …?`。このツリーで2クラスのスクラッチプロジェクトに対して再現した（`rigor effects --full`、続いて`--why`）:

```
Greeter#greet: [nondet.time]
Greeter#initialize: [mutate.self]
Mailer#deliver: [global.read, io.fs.write] …? (1 reason, --why)
    dynamic-receiver
──
3 of 3 units printed
3 carry a proven label · 0 carry a declared (≤) one · 2 are exhaustive
```

（`dynamic-receiver`は`$stdout.puts`である——そのグローバルの型が追跡されていないので、2行のメソッドでさえ誠実にヘッジする）。今日エフェクトが**現れない**場所: `rigor type-of`はノード・推論された型・RBSの消去だけを印字する;`sig-gen`は`%a{…}`を出力しない（ADR-103 WD9は`%a{pure}`とエンベロープの出力を「網羅的で未解消のサマリーからのみ」行うと計画している——消費者であり、まだ着地していない）;LSPのホバーはv0.4.xのスライスまで意図的にエフェクト抜きである（WD16 §4）。`rigor effects explain`はリーチの変化の背後にある最短のエッジのパスを印字する。

### 3.3提示形式が尊重しなければならない確定済みの裁定

- **宣言レーンは決して判定されない**（WD17、[#454](https://github.com/rigortype/rigor/issues/454)）: redmineとmastodonでは、`io.db.read`/`io.db.write`が証明済みレーンに現れる回数は**ゼロ**であり、宣言としての出現は数千ある——Railsにとって意味のあるラベルはすべて、どの診断も読んではならないレーンに住んでおり、それに対する強制の面はエンベロープではなく`rigor effects check`（`≤+`のドリフトのマーカー）である。
- **否定的な読みは決して許されない**。 `%a{pure}`の読みは*網羅的な*証明済み ⊆ `{mutate.local}`である;redmineでは4,683ユニット中262が網羅的であり、印字される行の約90%が` …?`で終わる——「Railsアプリケーションの正常で健全な状態」だ（`docs/manual/19-effect-labels.md`の§「レポート」）。
- **エンベロープには合っているが、破棄については調律を誤っている**。 `effect.discarded-pure-result`はコーパスで14回発火し、すべて偽陽性で、「このルールが名前にしている落とし穴の実例はコーパスのどこにもない」（[`20260819-discarded-pure-result-corpus-gate.md`](../20260819-discarded-pure-result-corpus-gate/)）。
- **有用性はエフェクトの機構ではなくレシーバーの型付けによって境界づけられる**: スーパークラスの`before_action`で代入されたivarは、`@group.save`が何も寄与しない状態を残す（[#455](https://github.com/rigortype/rigor/issues/455)——redmineの27個の`#update`アクションのうち0個しかDBへの書き込みを記録しない）。
- 既定オンはWD15/WD16の前提条件の背後でv0.4.0に着地する（[#409](https://github.com/rigortype/rigor/issues/409)）;10本のユーザーストーリーの裁定は[`20260823-effect-user-stories-corpus.md`](../20260823-effect-user-stories-corpus/)にある。

### 3.4 Rigorにはすでに「ケイパビリティ」があり、それは別のものである

Rigorの**ケイパビリティロールの推論**（[`docs/type-specification/rigor-extensions.md:17`](../../type-specification/rigor-extensions/)、[`structural-interfaces-and-object-shapes.md`](../../type-specification/structural-interfaces-and-object-shapes/)の§「ケイパビリティロール」）は、*メソッド本体がパラメータまたはレシーバーに要求する最小の構造的インターフェース*である——名前的な`IO`まるごとの代わりに、キュレートされたカタログからの`_Reader`風のロールとしての「読み取り可能で巻き戻し可能なストリームの振る舞い」。これは**シェイプ**の概念だ: 渡されたものにどのメソッドが存在しなければならないか。Scalaのオブジェクトケイパビリティの規律は**権限**の概念である: この値の保持者がどのエフェクトを行ってよいか。両者は接触する——どちらも本体がパラメータに何を要求するかについて推論し、Rubyの本物のケイパビリティ的な読みはまさにこの渡されたオブジェクトの解析から始めねばならないだろう——が、ケイパビリティロールは環境的な権限について何も言わないし（`File.write`はパラメータをまったく必要としない）、本体側の*要求の推論*自体がいまだ先送りされている（[`control-flow-analysis.md:221`](../../type-specification/control-flow-analysis/)）。CC風の面はまた、この確立した語彙と衝突する: 「ケイパビリティ」はこのリポジトリではすでに占有されており、CCが意味するものを意味しない。

## 4. 概念の対応とミスマッチ

| | Scala 3のCC | Rigorのエフェクトラベル |
| --- | --- | --- |
| 付く先 | **値**の型 | **メソッド**のサマリー |
| 集合の要素 | スコープ内のプログラム**変数**（ケイパビリティ） | 分類の閉じた**語彙** |
| 向き | 前向き: この値を使うと何に*到達しうる*か | 後ろ向き: このコードが何をしたと*証明された*か |
| 完全性 | 断言される（健全な検査器;エスケープ検査） | 明示的にヘッジされる（` …?`、汚染の原因） |
| 多相性 | 自由。項の受け渡し＋ボックス化による | 回避されている: ブロックリテラルには封じ込め、不透明なcallableには汚染 |
| 純粋性の主張 | `T^{}`は検査可能で一般的 | 網羅的な証明済み ⊆ `{mutate.local}`によってのみ許可される——稀である |
| 境界vsファクト | 1つのレーン（検査された型） | 2つのレーン（証明済み／宣言）＋3つ目としての著者側の境界であるエンベロープ |

議論を担うミスマッチは4つある:

**4.1ケイパビリティvs分類**。 `Logger^{fs}`の波括弧集合は*値*を名指す（`fs`は変数だ）;サブキャプチャは値から値への導出に従う。`[io.fs.write]`はレジストリ内の*カテゴリー*を名指す;subsumptionはラベルの木に従う。仮想の`String^{db, net}`は活字の上でのみキャプチャ集合だろう——それが名指すべき`db`という値はプログラムに存在しない。さらに悪いことに、2つの読みは逆方向を向く: CCでは接尾辞は*保持者がその値でまだ何をしてよいか*を述べる;Rigorがそれに与えられる唯一の意味は、*その値を生成すること*がすでに何をしたかである——つまりエフェクトの履歴であり、Rigorが行っておらずADR-103が何も収集していない値の由来の解析だ。エフェクトは構成上メソッドの粒度で付く（`effect-summaries.md:39`）;飾るべき値ごとのファクトは存在しない。

**4.2高階のコード**。 Scalaの`map`がエフェクト多相なのは、`f`がキャプチャ集合を伴って移動する項だからだ。Rigorは意図的にエフェクト変数を持たない: 「ブロックリテラルは**常に**囲むメソッドのサマリーへ結合される（封じ込め）……したがってエフェクト多相性はエフェクト変数を必要としない」（ADR-103 WD4、`docs/adr/103-effect-labels.md:106-107`）。ブロック*リテラル*については、両者は呼び出しサイトを囲むメソッドにおいて同じ観測可能な答えを与える。しかしキャプチャ集合による提示は、まさに両者が乖離するところで過剰に約束してしまう: 後で呼び出される保存された`Proc`（`opaque-callable`の汚染——`effect-summaries.md:121`）、エフェクトが本当にそのブロック引数に*依存する*メソッド（`Array#each`は`->{f}`多相としては描画できない;そのカタログの行は定数だ）、そして複数のフレームを通されるcallable。CCの構文はパラメトリックな伝播を宣伝する;Rigorの機構はヘッジで答える。そして構文は、ヘッジが差し控えるものを約束してはならない。

**4.3健全性の非対称性**。 CCの接尾辞が信頼できるのは、検査器が検査対象のコードに対して健全である*からこそ*だ: `() ->{c1} Unit`は、c2が証明可能に流れ込めないことを意味する。Rigorの標準の方針は逆のトレードだ——「偽陽性は最悪ケースの静的な読みに優先する」（AGENTS.md;ADR-5）——証明済みレーンは証明されたぶんだけ厳密であり、コーパスの評決は、Rubyでは推論された純粋性は知りえないというものだ（ADR-103の§コンテキスト）。CCから借りてきた素の`String^{db, net}`は視覚的に「せいぜいこれら」と断言するが、このアナライザーではそれは稀な網羅的な行しかできない主張である;一般的な行の誠実な描画は`^{db, net, …?}`になるだろう——その時点で、この提示形式はCCのものであることをやめ、括弧が違うだけのRigorの現行のものになっている。この非対称性は様式の問題ではない: WD17は、Railsのポリシーが気にするラベルが宣言レーンに座ることを示している。したがってRailsコードに対するCC風の接尾辞は、`io.db.*`を丸ごと省く（誤解を招くほどきれいになる）か、証明を含意する構文で主張を印字するかのどちらかになる。

**4.4環境的な権限**。 CCが機能するのは、Scalaで`FileSystem`をパラメータで通していくのがもっともらしいスタイルであり、検査器が追跡対象のリソースについてその引き回しを必須にするからだ。慣用的なRubyの権限は環境的である: `File.write`・`Time.now`・`Net::HTTP.get`、グローバル、定数、あらゆる`self`上の`Kernel#`のメソッド、ロード時にそのどれをも再配線しうるオープンクラス。名指すべきケイパビリティの値が存在しないので、キャプチャ集合が*含む*べきものが何もない——それこそが、ADR-103がケイパビリティ的な読みではなくメソッド上のラベル、つまりエフェクトシステム的な読みを選んだ理由である。ケイパビリティロールのカタログ（§3.4）は、権限のうちパラメータの形をした*一部分*（本体が渡されたものに何を要求するか）には足場を与えるが、環境的な残りには何も与えない。そしてほとんどすべてのラベルが由来するのはその環境的な残りの側だ（`effect-summaries.md:69-81`: パラメータではなく、構文とカタログの行）。

CC風の提示形式が*得る*ものは本物だが狭い: コンパクトさ（一目で分かるフットプリントの接尾辞）、目に見えて流行している機能との共通のメンタルモデル、そしてCCの採用のストーリー——それはRigorがすでに持っているものだ（オプトインの`effects:`ブロック、アプリケーションコードに何も要求しない、既定での推論はWD5の梯子;m3techの記事の「正しいコードには何も要求しない」はADR-103自身の姿勢を正確に記述している）。

## 5. 提示形式の選択肢

**（a）`type-of`／ホバーでの型へのキャプチャ集合風接尾辞——却下**。カテゴリーエラー（§4.1: 値ごとのエフェクトのファクトが存在しない）、完全性の過剰主張（§4.3）、そして語彙の衝突（§3.4）。式の*型*への接尾辞は、パイプラインのどの部分も行っていない値レベルの追跡を主張することになる。これは、概念上の違いが単に複雑にするのではなく本当に禁じる唯一の選択肢である。

**（b）sig-gen出力へのエフェクトの行——アノテーションの形をした面であり、すでに決定済み**。 ADR-103のWD9は、`sig-gen`による`%a{pure}`とエンベロープの出力を「網羅的で未解消のサマリーからのみ」に限定している——誠実さのゲートは決定の中にある。エンベロープはこのアナライザーにとって正しい極性を持つ: それは*境界*（`≤`）なので、それを書くことが推論の完全性を断言することには決してならず、それを読む検査器は証明済みレーンのみを読む。`rigor effects --pure`はすでに候補を名指している（redmineで436件）。これがCCのアノテーションに最も近い誠実な類似物である: 著者に見え、検査され、漸進的だ。

**（c）診断のみ——現状の誤った特徴づけ**。現状はレポート＋スナップショット＋3つのオプトインの診断であり、WD17は、チームが最も気にするラベルについての強制の面が診断ではなくスナップショットであることを確定させた。ここに変えるものはない。

**（d）専用のレポートコマンド——すでに存在し、その行の文法はキャプチャ集合の誠実な版になっている**。 `Key: [proven] ≤ [declared] …?`は、*正しいキャリア*（メソッドのキー）の上の3レーンの波括弧集合であり、CCが必要とせずRigorが落とせないヘッジを伴う。CCから得られる改善は記法ではなく記法の届く範囲だ: その同じ行を、CCがScaladocでキャプチャ集合を置く場所に置く——すなわちWD16 §4がすでに確保しているv0.4.xのLSPホバーのスライス（「メソッドのラベルを報告するホバーは、自身の消費者を持つv0.4.xのスライスである」）に、レポートの文法で描画し、決して型の接尾辞としては置かない。

**推奨**。 CCの構文を借りないこと;その意味論は移らないし（§4.1〜4.4）、接尾辞の視覚的な完全性の主張こそ、Rigorの裁定が禁じている当のものだ。代わりにCCの*配置と姿勢*を借りること: （i）レポート＋スナップショットを主たるものとして保つ（確定済み、WD7/WD17）;（ii）WD9のsig-genの出力をアノテーションの面として着地させる——それは「ユーザーが境界にアノテーションを付け、アナライザーがそれを検査する」というCCと類似のループを、極性を境界へ正した形で実現する;（iii）ホバーのスライスが着地したら、既存の`[proven] ≤ [declared] …?`の文法でメソッドのサマリーを見せる。CCのユーザーの「一目でフットプリントを見たい」という期待が実際に満たされるのはそこだ。3つとも、すでに下された決定の再確認であり、それ自体が1つの発見である: ADR-103は独立に、CCの提示形式の誠実な部分集合へ到達していた。最後に、m3techの記事からの小さな警告: CC自身の面は数か月のうちにルートケイパビリティをリネームし、1つの機能クラスを削除した——たとえ意味論的に移植可能だったとしても、その記法はまだ収束先として安定したものではない。

## 6. 未解決の問い

1. **呼び出しサイトの変種**。 *呼び出し*の位置での`rigor type-of FILE:LINE:COL`は、型に触れずに呼び出し先のサマリーを別のラベル付きの行として印字できるだろう（`effects: [io.fs.write] …?`）——値ではなく呼び出しにラベルを付けるので誠実である。これには`type-of`の実行の新しい消費者としてエフェクトのテーブルが必要であり（WD13に従うキャッシュの同一性）、どちらの向きにもこれを扱う裁定はない。
2. **Separation Checkingの読み／書きの分割**。公式ページのモデル（§2.1）はレシーバー側の所有権の規律であり、素のCCよりもRigorの`mutate.*`のファミリーに近く響く: `update`修飾子はメソッドを、それがレシーバーをミューテートするかどうかで分類するが、それは`mutate.self`とレシーバー所有権の分類体系の残りとの切れ目と同じである;排他vs `x.rd`は、Rigorのカタログが行ごとに符号化する読み／書きの区別を検査可能にした版である;そして`consume`の呼び出しを超えた予約は、`mutate.local`の新鮮でエスケープしていない所有権の解析（`effect-summaries.md:94-99`）の、強制寄りの従兄弟である。行動に移すものはない——Rigorの所有権は構文的で意図的に保守的であり、ページ自身がこの層を未成熟と注記している——が、Separation Checkingが安定すれば、権限ではなくエイリアシングについてのものである分、より興味深い比較対象になる。
3. **検証されたプラグインの行**。 #454が却下した選択肢3（アナライザーが読んだソースに対して*検証された*プラグインの行）は、境界寄りの提示形式が`io.db.*`を診断の読むレーンに見せられる唯一の未来である。裁定は、その寄与の種類が存在するようになった場合にのみ再考せよと述べている;提示形式の設計がそれを先取りすべきではない。
4. **命名**。もしいずれかのエフェクトの面がケイパビリティ寄りの語彙を育てるとしても、「ケイパビリティ」を再利用してはならない——この語はケイパビリティロールに占有されている（§3.4）。「フットプリント」（すでにマニュアルの語だ）が使える名詞である。
