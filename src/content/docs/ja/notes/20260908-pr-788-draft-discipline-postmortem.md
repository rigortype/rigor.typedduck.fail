## なぜPRがDraftではなかったのか、そしてなぜそれが障害のすべてだったのか

- #788は（先行する#783や#787と同様に）`--draft`ではなくReadyで作成されていた。
- 停止指示はPRの状態（`gh pr ready --undo`）に変換されることはなかった。指示は1つのセッションの会話の中に留まり、コンテキスト圧縮後は要約の中に存在した — 他のすべてのセッションにとって、そしてやがてはそのセッション自身にとっても不可視になった。
- レビューはGitHub外で行われたため、GitHubには他のセッションが読み取る唯一のシグナル（オープン、グリーン、Ready、未レビュー）しか表示されていなかった。
- 「マージしてはならないPRはDraftのままとする」というルール（ユーザー指示、2026-09-02）はエージェントの記憶の中にのみ存在し、インデックス行によって「Draft-PR remote CI post-rebase」へと圧縮されていた。リポジトリのどのドキュメントにも記載されていなかった。2026-09-02以降の40件のPRのうち、Draftを経由したのは6件（09-03のレビューサイクル）であり、2026-09-05以降はゼロであった。
- `master`にはブランチ保護もルールセットもないため、レビューゼロでのマージが機械的に許可されている。
- AGENTS.mdの「随時、監査済みかつグリーンのPRを着地させる」は、誰のPRかについて何も述べておらず、コーディネーターのリリースに向けた位置づけが、「監査済み＋グリーン」を自身が所有していないPRのマージトリガーに変えてしまった。

## 何が変更されたか

- [#814](https://github.com/rigortype/rigor/pull/814) — AGENTS.md: すべてのPRは`--draft`で作成され、マージ不可能なPRはDraftのままとする；`gh pr ready`はGitHub上のAPPROVEがあり、CIがグリーンで、停止指示がない場合にのみ行う；停止指示は即座にPRの状態にする；レビュー判定はGitHub上に残す。随時マージのルールはそのセッションが開いたPRのみを拘束し、別のセッションのオープンなPRや未コミットのツリーは進行中の作業である。バグ報告の修正は報告者をクレジットする。唯一のリリースパスはユーザーが`/rigor-release-prep`を呼び出すことである。
- `rigor-dependency-update`および`rigor-release-prep`内の`gh pr create`の例は、PRを`--draft`で作成し、Readyの手順を明記する。
- 記憶: Draftルールがインデックス行に復元され、両方のセッションがそれぞれの役割を記録した。
