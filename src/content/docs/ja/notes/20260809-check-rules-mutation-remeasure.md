ステータス: 計測ノート、設計上のコミットメントはなし。観測は`origin/master` @ `31b5f656`、macOS arm64、Ruby 4.0.5、2026-08-09。

## 理由

[#135](https://github.com/rigortype/rigor/issues/135)で`lib/rigor/analysis/check_rules.rb`について記録された融合の数字は、すべて**テスト軸のみ**だ。このファイル自身のドキュメントコメントがバッククォート付きで`` `# rigor:disable-file all` ``を引用しており、抑制パターンはコメント内のどこにでもマッチしたので、そのドキュメントがルールを定義する3,000行のファイル自身をファイル抑制していた（[#306](https://github.com/rigortype/rigor/issues/306)）。したがって`DiagnosticOracle`はそこで**914件中0件**のミュータントしかkillしなかった —— 生きた型のネットとしては構成上ありえない結果であり、偵察の最大の発見だった。PR #314がすべてのマーカーをコメントの先頭にアンカーし、このファイルはチェック可能になった。

その偵察以降、7本のPRが6つの新しいトピック別specファイルにわたって**136例**を追加し（#309/#310/#311/#314/#325/#326）、このファイルのルールに触れる2つのエンジン変更が着地した: [#327](https://github.com/rigortype/rigor/pull/327)（`OptimisticOrigin`の極性ゲート。`check_rules.rb`から`flow.always-truthy-condition`のディレクティブも1つ引き戻した）と#313の診断だ。

したがって偵察の`169 → 95 test-killed → 74 raw → 70 de-noised, 56.2 % fused`（サイト169 → テストkill 95 → 生の生存者74 → ノイズ除去後70、融合56.2%）はベースラインではない。本ノートは両軸を生かした状態でこの全数調査を再導出し、第3波が正当化されるかを決定する。

## ハーネスの起動とサイトモード

計測した設定は、`tool/mutation/self_mutate.rb`の**融合**パス（ADR-70の静的∪動的）を`--site biteable`で走らせたものであり、**完全な全数調査**だ —— `--limit`なし、つまりサンプリングなし:

```
bundle exec ruby tool/mutation/self_mutate.rb --site biteable --json \
  lib/rigor/analysis/check_rules.rb
```

`:biteable`は具体型のディスパッチサイトのみを保持する（FPセーフなデフォルト）;これはPR #287が名指ししたのと同じスコープの縮小であり、偵察の時点ではそれだけが*噛みつきうる*唯一の軸でもあった。`--site all`は依然として実行不能のままだ —— §スコープの注意を参照。

**`SpecMap`は13のトピック別specすべてを解決する**。PR #307がハーネスに`lib/rigor/a/b.rb -> spec/rigor/a/b/*_spec.rb`というディレクトリ規約を教えた;`[fused]`のログ行は`argument_type`・`collector_diagnostic_builders`・`nil_argument_mismatch`・`non_nil_argument_mismatch`・`override_and_return_type`・`raise_non_exception`・`refined_receiver_dispatch`・`remaining_rule_families`・`rule_walk_equivalence`・`safe_navigation_undefined_method`・`suppression`・`union_undefined_method`・`wrong_arity`を名指しする。（issueのコメントは「7つ」と言っているが、それは*偵察時点*での数だった;波1と波2がさらに6つ追加した。）

### 実際にどう駆動したか

このハーネスは中断・再開できないし、本セッションのコマンドあたりの上限は10分なので、この全数調査はインデックスのスライスに対するチャンク分けされたスクラッチドライバを通して走らせた —— PR #287が先例とした手法だ。`self_mutate.rb`との忠実性の契約は「同等」ではなく*同一*だ:

- **サイトの順序** —— `MutationScanner#kept_mutations`（private、`send`経由）を`site_selector: :biteable`・`limit: nil`・`seed: 1`・`base_scope: nil`・`discovery_seed: nil`で、`Driver#scanner`とまったく同じに;
- **型の判定** —— `MutationScanner#classify`（private、`send`経由）を同じ`DiagnosticOracle`のベースラインに対して;
- **テストランナー** —— `out`/`err`を`/dev/null`に向けた素の`system`、すなわち`BundledRunner`: rspecのサブプロセスはRigor自身のBundler環境を継承する。SUT（テスト対象システム）のバンドルがRigorのものだからだ;
- **specコマンド** —— `bundle exec rspec` + `SpecMap.for(path)`を逐語で再実装。

ドライバが足すのはペーシングと再開だけだ（rspecの実行を開始する*前に*チェックされる実時間の予算と、すでに記録済みのインデックスのスキップ）。どちらも判定を変えることはできない。

**ハーネス自身の融合モードは別途スモークテストされ、正確に一致した**。変更していない`self_mutate.rb`を`--site biteable --limit 30 --seed 1`で通すと`type_killed: 24, test_killed: 6, unprotected: 0`と報告される;ドライバの、同じ30サイトについての記録も同じ30件の判定を運ぶ。ハーネスを通した`--site all --limit 6 --seed 3`の融合実行も同様に`1 / 5 / 0`と報告する。

先行する部分的な実行を再利用する前に、サイトインデックスの安定性もチェックした: 今列挙される169サイトは、`(index, line, operator, method, receiver, rule)`において、以前killされた試行が列挙したものとバイト単位で同一なので、その最初のチャンクは再計測されるのではなくこの全数調査へ組み込まれた。

### 2×2、そしてどのセルが健全か

`scan_file_fused`はショートサーキットする: 高価なスイート実行の対価を払うのは型生存者に対してだけだ。したがって、型軸があるサイトをkillするとき、そのサイトのテストの判定は単に*観測されない*ままであり、完全な分割表を作るには38回ではなく169回のスイート実行（約3時間）がかかることになる。それでも2つのセルは健全だ。偵察は**すべての**169サイトでテスト軸を観測しており（その型軸は何もkillしなかった）、スイートはそれ以降*増える*一方だったからだ —— 偵察でのテストkillがテスト生存者に転じることはありえない。

| --- | ---: | ---: | ---: |
| **型kill** | **75**（両方） | 56（型が引退させた） | 131 |
| **型生存** | **38** | **0** | 38 |
| 合計 | 113 | 56 | 169 |

- **両軸によるkillが75件** —— 今や生きている型軸も噛みつく、偵察時点のテストkill。
- **型軸によるkillが56件** —— 偵察の*生の生存者*、つまり以前は何にも捕まえられなかったサイトだ。136の新しい例がこれらもkillしたかどうかは、ショートサーキットのため観測されていない;「56」は「型軸がそれらをkillする」ことを意味し、「型軸だけがそれらをkillする」ことは意味しない。

## 明示的な見送り

**なし**。偵察は74 → 70のノイズ除去を、4サイトをスコープ外と宣言することで行っていた: `run_node_collectors` / `shadow_verify_node_collectors`内のL194×2とL215×2で、`RIGOR_SHADOW_RULE_WALK=1`の下でのみ到達可能であり、そこでは乖離があれば必ず*raise*する —— 例の形をした振る舞いというよりハーネスの不変条件だ（PR #289のRactorゲーティングの先例）。`pipeline / orchestration`の5件の生存者すべて、その中の4件の見送りを含めて、今や**型kill**されている: `ENV["RIGOR_SHADOW_RULE_WALK"]`は普通の`RBS::Unnamed::ENVClass#[]`のディスパッチサイトであり、ファイルがチェックされさえすれば、それがガードする分岐が実際に走るかどうかにかかわらず型のネットが噛みつく。

## なぜ100%は計測であって作為ではないのか

エラーで終わる実行は偽の*生存者*を生み、スイートのコマンドが壊れている実行は偽の*kill*を生み、あらゆるミュータントが捕まったように見えてしまう。100%という結果はその失敗モードが取る形そのものなので、仮定するのではなく直接チェックした。

- **グリーンなベースライン**: `TestSuiteOracle#green?`はクリーンなコードで通る（405例、失敗0件）。したがって`runner.call → true`に到達可能であり、`killed? = !runner.call`は`false`を返しうる。
- **陰性コントロール**、同じオラクル・ランナー・specコマンドを通して:

  | コントロール | 判定 |
  | --- | --- |
  | 恒等ミュータント（`mutant_source == original`） | **生存** |
  | `shadow_verify_node_collectors`内部への毒（`RIGOR_SHADOW_RULE_WALK`でゲート） | **生存** |

  2つ目が決定的だ: 実在のメソッドを本物の名前エラーで壊すが、デフォルトのスイートはそれを見ることができない。偵察の見送りが予測したとおりだ。このオラクルはこのファイル上で生存者を報告する能力を十分に持っており、報告しなかったのは、このサイトモードには生存者が存在しないからだ。
- **ディスクは一度も要因にならなかった** —— §正直さを参照。この全数調査の以前の試行は`Errno::ENOSPC`で死んだ。これはまさに偽の生存者が作られる典型的な経路なので、空き容量を各チャンクの前にチェックし、常に278GiBを下回らなかった。
- 作業ツリーは、全数調査の後とコントロールの後の両方でクリーンであることを確認した（`git status --porcelain`が空）。したがってディスク上にミュータントが残ることも、汚れたファイルに対して判定が下されることもなかった。

## 決定: 第3波はなし

**基準** —— 波1と波2が使ったのと同じ枯渇の基準だ: *波が正当化されるのは、計測されたサイトモードでの全数調査がノイズ除去後の生の生存者、つまり型のネットもspecも気づかずに壊せるサイトを残しているとき、かつそのときに限る。*この全数調査が残すのは**ゼロ**だ。スコープすべき執筆単位が（互いに素かどうかにかかわらず）存在しないので、「並列化可能な最小の単位集合」は空集合だ。

`check_rules.rb`は**`--site biteable`において完了している**。チェックボックス1の次のティアのメンバーは、PR #282/#287/#289が掃かなかった、issue本文が挙げる巨大ファイル群だ。

持ち越す価値のある2つの二次的な結果:

- **生きた型軸は、この全数調査をより*良く*するだけでなく、より*安く*もした**。漸進的ショートサーキットは、対価を型生存者に対してだけ払う。したがって169サイトのうち131件は一度もrspecへ到達しなかった: 予測されていたテスト軸の約63分の実時間は、実際には約35分に収まった。真に型チェックされているファイルは、ミューテーションテストが安いファイルだ。
- **波1・波2でのspecへの投資は、型軸によって無駄にはならなかった**。38サイトはスイート単独で捕まえられており、うち18サイトは波1と波2が閉じたものであり、そのそれぞれがどんな型も到達できなかったサイトだ。

## 発見: specスイートは一時ディレクトリをリークし、ミューテーションハーネスがそれを増幅する

これは、前回のこの全数調査の試行を殺したのがこれだったことと、それを蓄積させているのがこのハーネスであることから記録しておく。

Rigorのspecは`Dir.mktmpdir`ディレクトリを作成しても削除しない。このマシンで、`$TMPDIR`が空の新規に入ったFlakeシェルで計測した:

| 実行 | 例数 | 実時間 | `$TMPDIR`に残ったエントリー | サイズ |
| --- | ---: | ---: | ---: | ---: |
| `rspec spec/rigor/analysis/check_rules/`（カバーするスイート） | 405 | 1分40秒 | 3 | 21.8 MB |
| `make test`（フルスイート） | 9,093 | 9分06秒 | 25 | 86 MB |

プレフィックスは`rigor-scanner-spec-*`（25件中18件）、`rigor-spec-{cache,workspace,sig}-*`、`rigor-plugin-spec-cache-*`、`rigor-mutant-*`、`rigor-brute-force*`、そしてRuby自身のデフォルトである`d<YYYYMMDD>-<pid>-<rand>`だ。

**ミューテーションハーネスは小さなリークを大きなリークに変える**。融合の全数調査は型生存者*ごとに*1回のスイート実行だからだ: この全数調査はカバーするスイートを約45回起動したので、それだけで**約1GB**をリークした。偵察の保護レベルではさらにひどかっただろう —— 生の生存者74件とテストkill 95件で169回のスイート実行を意味し、1回の全数調査で約3.7GBだ。

執筆時点でこのマシン上には: **`/tmp/nix-shell.*`ディレクトリが249個、約24GB**あり、うち79個は今日より前のもので7.0GBを保持している。これは1回のFlakeセッションあたり約100MBであり、上のランごとの数字と整合する。

**何も削除しなかった**。空き容量はこのセッションを通じて一度も制約にならなかった（278〜301GiB）。ブリーフ自身の安全ルール —— エントリーがすべて`rigor-`プレフィックスであるディレクトリのみを削除する —— はどのみち古いものを除外する: それらはRubyデフォルトの`d20260805-*`エントリーを`rigor-`のものと一緒に含んでいるからだ。恒久的な修正はspec側にある。定期的な掃除ではなく: ブロック形式の`Dir.mktmpdir { ... }`か、例が作ったものを削除する`after`フックだ。

## 正直さ／環境

マシン: 12コアmacOS arm64、Ruby 4.0.5、すべてNix Flake経由。`/System/Volumes/Data`の空き容量は各チャンクの前にチェックした: 開始時142GiB、それ以降278〜301GiB。あるチャンクを無効化しうる2GiBの床には一度も近づかなかった。

この全数調査は5つの逐次チャンクとして走らせ、加えて、サイトインデックスのチェックが構成可能であることを証明した、以前の試行からの再利用済みの最初のチャンクを含む。本ノートの実時間の数字はクリーンルームではなく参考の値だ: マシンは通じて普通のデスクトップ負荷を運んでいたし、この全数調査はベンチマークというよりI/Oとサブプロセスにバウンドなものだ。

**本計測は[PR #328](https://github.com/rigortype/rigor/pull/328)より前のものだ**。これは`31b5f656`の時点でまだオープンだった。それは`possible-nil-receiver`と`argument-type`の消費者の間で、1つの宣言由来のADR-58述語を共有するので、`argument_type`ファミリーでエンジンの挙動を変える —— 偵察の生存者が1つの例で閉じられた唯一のファミリーだ（`argument_type_spec.rb`の「ローカルコピーではまだ発火する」というケースで、これは意図的に現在の挙動を固定しており、#324が着地したら反転させよと述べている）。この全数調査の再実行が必要になるのは、#328が*サイト*の集合を変えた場合だけだ;それは`check_rules.rb`を変えないので、169サイトはそのまま成り立ち、型軸の判定はkillが増える方向にしか動きえない。
