Status: [#775](https://github.com/rigortype/rigor/issues/775)に関する計測＋着地したレバーの記録。ハーネスを保存するルールに従い、ハーネスは未マージのブランチ`perfbench-harness-775`（`tool/perf775/`）にあります。[`20260725-check-allocation-attribution.md`](../20260725-check-allocation-attribution/)の後継ノートですが、その見出し（実行時間の54%が一回きりのRBS環境構築）はもはや成り立ちません: 現在その構築は実行の3%であり、リグレッション全体がファイルごとの型付けに存在しています。

## 課題

Linux CI上の`make bench-perf`（`tool/bench.rb`、プロセス内での`rigor check --no-cache lib`）は、v0.3.6カット時の18,849,919アロケーションからv0.3.7で36,171,454へと増加し（+91.9%）、リリースを着地させるために[#775](https://github.com/rigortype/rigor/issues/775)でその数値が暫定承認（bless）されました。このissueは、誰かが再び再調整を行う前に、v0.3.6..v0.3.7のどの変更が17Mを支払ったのかを問うています。アロケーションはホスト非依存であるため（macOSはCIを1%未満の差で再現: 同じ2つのツリーで18,972,086および36,492,665）、以下のすべての数値は同じコマンドにおけるローカルの`GC.stat(:total_allocated_objects)`の差分です（YJITオフ: `RIGOR_DISABLE_YJIT=1`、診断はシリアライズされた`--format json`バイトとして比較）。ウォールクロックは目安としてのみ引用されています: ホストは終始高負荷（12コアでロードアベレージ9）でした。

## 手法

3つの独立した測定機器。すべてドライバ側（`lib/`の外部からの`Module#prepend` / `TracePoint`；計測のためにツリー内のコードは一切編集していません）:

1. **マージごとのスイープ**。`v0.3.6..v0.3.7`のコードに触れるすべてのファーストペアレントコミット（175中127コミット、各々独自worktreeチェックアウトと独自の`Gemfile.lock`バンドル）における`tool/bench.rb`。ゲートがそうであるのとまったく同様に、各コミットは自身の`lib`を計測します。
2. **単一ターゲットでのエンジンA/B**。v0.3.6のエンジンと現在のエンジンが両方とも*同じ* v0.3.8のツリー（cwd = ターゲット、`$LOAD_PATH` = エンジン）を解析し、以下の条件下で実行: （a）排他アロケーションフェーズプローブ、（b）解析された4ファイルごとに対するアロケーションサイト調査（このウィンドウの間GCを無効化した`ObjectSpace.trace_object_allocations`、ウィンドウ内で割り当てられたオブジェクトの85〜87%が列挙可能、残りはVMスロット）、（c）メソッドごとの呼び出し回数、（d）`RIGOR_BUDGET_TRACE`メモおよびユニオンアリティカウンタ、（e）10個以上のメンバーを持つすべての`Combinator.union`の呼び出し元トレース。
3. **レバーごとの計測**。各回復コミットをその親に対して単体で計測し、JSON出力をmasterのものとdiff。

ハーネスが教えてくれた2つのこと（次のスイープで再び苦労しないように記録）。zshの`pipefail`の下では、gitが書き込みを終える前にgrepが終了すると`git diff --name-only … | grep -q`が失敗するため、最初の「非Markdownファイルに触れる」フィルタは127件のマージのうち13件を黙って維持してしまい、大きなマージがすべて脱落しました。また、`RIGOR_BUDGET_TRACE`カウンタは1つのホスト上で数時間の間に約1%ドリフトするため（同じmasterツリーに対して42,285 → 42,728のinferエントリー、両実行とも決定論的で診断はバイト単位一致）、バックツーバックでのみ比較可能です。

## 17Mはどこへ消えたか

### ターゲットでもgemの更新でもない

v0.3.8のツリーを解析するv0.3.6のエンジンは、自身のツリーでの19.68Mに対して21.40Mをアロケートします: 9%大きなターゲットが、+17.4Mのうち**+1.7M**を説明します。`rbs`の4.1.3 → 4.2.0への引き上げ（[#651]）は、スイープにおいて+0.17M、直接のA/B（v0.3.6のlockfile下での現在のエンジン）において+0.19Mの価値があります。残りのすべてはエンジンの振る舞いによるものです。

### スイープ

累積のファーストペアレントアロケーション、`lib`のセルフチェック、計測された127ステップの上位（完全なシリーズはハーネスブランチ上の`tool/perf775/sweep-v0.3.6-to-v0.3.7.csv`にあります）:

| マージ | Δ アロケーション | +17.4Mのシェア | 何を行っているか |
| --- | ---: | ---: | --- |
| [#547] パラメータごとのバインダー | +4,102,008 | 23.6% | シグネチャ全体を拒否する代わりに、ユーザーメソッドの呼び出しサイトでオプショナル／rest／キーワードパラメータをバインドするため、はるかに多くの呼び出し先本体が評価される（issue #524） |
| [#556] エイリアス＋交差の変換 | +2,315,727 | 13.3% | RBSの`type`エイリアスが`untyped`と読まれる代わりに展開され変換される（#529） |
| [#753] autoload安全な`resolve_class` | +1,805,005 | 10.4% | Ruby階層のサブタイプチェックが、`const_defined?` / `autoload?`を走査するために呼び出しごとにクラス名を分割する |
| [#664] 宣言されたreaderの優先 | +1,727,027 | 9.9% | RBS宣言された属性readerが推論されたreaderより優先される |
| [#543] オプショナルレシーバーのディスパッチ | +906,831 | 5.2% | メソッドがnilに対して例外を発生させる場合、`T?`レシーバーが`T`上でディスパッチする |
| [#712] `Result` / `Maybe`キャリア | +720,977 | 4.1% | `Rigor::Type::t`にさらに2つのメンバー、HKTスライス4〜5 |
| [#584] ブロック戻り値スコープのスレッド化 | +676,546 | 3.9% | |
| [#734] サブセット実行プロジェクト発見 | +631,417 | 3.6% | |
| [#558] オーバーロード選択でのエイリアススレッド化 | +515,082 | 3.0% | |
| [#726], [#685], [#537], [#669], [#620], [#581], [#538] | 各+200k … +411k | 13.9% | |
| [#709] 呼び出し先再走査のネスト | −729,453 | −4.2% | 回収をもたらした唯一のマージ |
| 残り105コミット | ≈ +1.5M | 8.6% | +150kを超えるものはない |

単一の変更がリグレッションの原因ではありません；上位4つで57%、上位10個で77%を占めます。最大の4つのうち3つは、意図的により多くの推論を行う精度向上機能です（[#547]、[#556]、[#664]）；1つは実装がたまたまアロケーションを行っていた正しさの修正です（[#753]）。

### 単一ターゲットでのエンジンA/B

パイプライン領域ごとの排他アロケーション、両エンジンがv0.3.8ツリー（446ファイル）を解析:

| 領域（排他） | v0.3.6エンジン | v0.3.8エンジン | Δ |
| --- | ---: | ---: | ---: |
| `ExpressionTyper#type_of` | 9,038,084（750,980回） | 20,162,957（982,341回） | **+11.1M** |
| `StatementEvaluator#evaluate` | 6,002,622（221,130回） | 9,732,578（317,615回） | **+3.7M** |
| `analyze_file_body`（残り） | 1,660,669 | 1,971,894 | +0.3M |
| プロジェクト発見 | 650,928 | 1,304,603 | +0.7M |
| `ScopeIndexer.index` | 492,841 | 739,576 | +0.2M |
| 一度きりのRBS環境構築＋`for_project`＋スタブパス | 1,956,740 | 1,962,964 | 0 |
| オンデマンド定義（`build_*_definition`） | 920,133 | 1,047,117 | +0.1M |
| **合計（プローブ）** | **21,396,734** | **37,603,946** | **+16.2M** |

エンジン側の増加の92%は2つの型付け領域であり、呼び出し回数の増加（`type_of`が+31%、`evaluate`が+44%）と呼び出しあたりのアロケーション増加（`type_of`あたり12.0 → 20.5）の両方によるものです。メモカウンタもそのボリュームで一致しています: ユーザーメソッド戻り値推論が25,862 → 42,285（+64%）、本体評価が10,764 → 18,044（+68%）、`Combinator.union`の結果が78,252 → 179,902（2.3倍）、ユニオンアリティのp90が3から**18**へ移動し、10メンバー以上のユニオンが753件から**20,250件**へ増加。

### 呼び出しあたりの背景

ワイドユニオンのトレースは、20,250件のワイドユニオンのうち13,592件が厳密に21メンバーであり、すべて`translate_alias`配下の`RbsTypeTranslator.translate_union`によって構築されていることを突き止めました: すべてのエンジンメソッドが返す21メンバーのエイリアスである**`Rigor::Type::t`**が、[#556]以降、すべての呼び出しサイトで再変換されていたのです。展開自体はそのPRでメモ化されていましたが（`expand_type_alias`）、展開の*変換* — フラット化、`Nominal#==`によるO（n²）の`unique_members`、`describe`をキーとするソート、21個の新規メンバー — はメモ化されておらず、結果として生じた21メンバーの`Union`がすべての結合（`Scope#join_bindings`は各バインディングをそれ自身とunionする）と絞り込みに流れ込んでいました。`Nominal#==`は179,880回の呼び出しから**4,845,228回**へと急増しました。

調査の差分（同じ111個のサンプリングされたファイル、3.32M → 6.60Mのウィンドウオブジェクト）が残りを特定しました: ウィンドウあたり`String` +735k、ほぼすべてがクラス名の正規化（プレフィックスのない名前に対する`delete_prefix("::")`のコピー、`resolve_class`の`split("::")`、`TypeName#relative!.to_s`）；`Array` +1.42M（`content_mutation_target`での`[nil, nil]`拒否、オーバーロード選択での`params.zip(arg_types)`ペアと`partition` / `+`、`positional_params_for`での`required.dup`、およびrbs自身の`Substitution.build`（110k回の呼び出し、そのうち109,672件は`RbsLoader#class_type_param_names`から。`RBS::Definition#type_params`が呼び出しごとに置換を通じてその名前を再導出するため））；オーバーロード選択あたりの2つのラムダからの`Proc` +62k；`AcceptsResult` +55k；`**shared`再スプラットと空の`{}`回答からの`Hash` +280k。

## 着地したレバー（ブランチ`perf-775-allocation-levers`）

各ステップは機械的なアロケーションの削減です — 共有のfrozenな空の回答、純粋関数のメモ化、または中間オブジェクトなしで同じものを計算する書き換え。出力は、各コミット後の`lib`セルフチェックにおいて、および末尾の[redmine](https://github.com/redmine/redmine)（app + lib、7つのプラグイン、354,912バイトのJSON）において、masterとバイト単位で一致しています；`make verify`はグリーンです。累積、`rigor check --no-cache lib`:

| レバー | 適用後のアロケーション | Δ |
| --- | ---: | ---: |
| master (`ffb456b0`) | 36,492,665 | |
| `normalize_name`は`::`プレフィックスが存在する場合にのみコピーする（3箇所） | 35,545,804 | −946,861 |
| `content_mutation_target`は単一のfrozenな`[nil, nil]`で拒否する | 34,598,075 | −947,729 |
| `Nominal`は単一のfrozenな空の`type_args`を共有する | 34,187,174 | −410,901 |
| `RbsExtended`リーダーは空の回答を共有する | 33,561,727 | −625,447 |
| トランスレーターが名前ごとに`TypeName#relative!.to_s`をメモ化する | 31,436,905 | −2,124,822 |
| トランスレーターが閉じたエイリアス展開の変換をメモ化する | 30,856,415 | −580,490 |
| `union(x, x)`は`x`を返す；`unique_members`は同一性を最初に試行する | 30,278,276 | −578,139 |
| `resolve_class`が名前の分割をメモ化する | 28,484,075 | −1,794,201 |
| ラムダ、`**`スプラット、`zip`、`dup`、`compact`なしのオーバーロード選択 | 26,655,925 | −1,828,150 |
| 順序が変化する場合にのみレシーバー親和性を並べ替える | 25,304,174 | −1,351,751 |
| リテラル理由ごとに1つの`AcceptsResult` | 25,055,693 | −248,481 |
| ローカル名ごとに1つの`FactStore::Target` | 24,322,534 | −733,159 |
| `class_type_param_names`をローダー上でメモ化・frozen化 | 22,501,792 | −1,820,742 |
| 空の型変数マップと発見ルックアップペアを共有 | 22,115,323 | −386,469 |
| `nil` / `true` / `false`のConstantをインターン化 | 21,938,254 | −177,069 |
| **ブランチhead** | **21,933,996** | **−14,558,669（−39.9%）** |

CIの数値と比較すると: v0.3.7の36,171,454は約21.9M（−39%）となり、これはv0.3.6の18,849,919に対して+92%ではなく+16%となります。高負荷ホスト上でのローカルウォールタイムは19.2秒 → 17.1秒となりました。

エイリアス変換メモがそのトレースが示唆したよりも小さかったのは、ユニオンが共有されても21メンバーユニオンの下流コストが消えるわけではないためです — 無料になるのは`union(x, x)`結合だけです。両方のコミットの後、ワイドユニオンの数は（19,985件から）8,890件になり、21メンバーユニオンは（13,592件から）2,829件になりました。

## 残余、およびなぜそれが本物であるか

同じターゲットにおいて、v0.3.6のエンジンはフェーズプローブ下で21.40Mをアロケートし、ブランチエンジンは23.58Mをアロケートします。ブランチはv0.3.7系統の作業 — 64%多いユーザーメソッド戻り値推論、68%多い本体評価、[#547]のパラメータごとの本体、[#556]の変換されたエイリアス、[#664]の宣言されたリーダー — を、v0.3.6のエンジンがより小さな作業を行ったときよりも約10%多いアロケーションでこなしています。`type_of`呼び出しあたりで見ると、ブランチはv0.3.6の12.0オブジェクト、masterの20.5オブジェクトに対して10.0オブジェクトになっています。残っているのは、それらの機能がもたらす推論ボリュームに加えて、不変な`Scope`の設計（`scope.rb`は調査において最大の残存ファイルです: バインディングごとに再構築される`Scope`とマージされたローカル変数の`Hash`）、訪問ノードごとの`RuleWalk::Context`、および`Scope#type_of`ごとの1つの`ExpressionTyper`です — これらは各々が設計の継ぎ目であり、機械的な削除ではありません。

試みられず、計測されて後のサイクルに残されたもの: 遅延評価される`AcceptsResult`の理由（補間された理由は依然として判定ごとに`String`と`Array`を構築する、≈150k）、ディスパッチごとの`receiver_descriptor`の3要素配列（≈260k）、`sub_eval`ごとの`StatementEvaluator`（≈250k）、およびノードごとの`RuleWalk::Context`（≈400k）。

## ゲート

[#775](https://github.com/rigortype/rigor/issues/775)は、Linuxの`release-gate.yml`の`make bench-perf`が36.2Mの暫定承認値ではないベースラインの帯域内に収まることでクローズされます。このブランチがマージされた後の`master`での次回のrelease-gate実行は約22Mアロケーションを読み取るはずです；ここを指す`note`を添えてそのアーティファクトを`bench/baseline.json`としてコミットし、v0.3.6に対する+16%の残余が、暫定承認ではなくv0.3.7系統の推論ボリュームの記録され説明されたコストとなるようにします。
