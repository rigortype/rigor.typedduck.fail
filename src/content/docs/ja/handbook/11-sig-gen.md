`rigor check`がコードに満足しているのに`sig/`がまだほぼ空のとき、解析器は自分以外には届かない有用な推論を行っています。`rigor sig-gen`はその仲間のコマンドで、推論されたシグネチャをRBSとして発行し、ツールチェーンの残り（Steepのクロスチェック、IDEのツールチップ、あなたのgemの`sig/`を読む下流の消費者）がRigorが見ているものを見えるようにします。

この章では、コマンドのUX、分類モデル、出力モード、そして[ADR-5](../../adr/5-robustness-principle/)の非対称な「戻り値には厳格、パラメータには寛容」ルールから直接出てきた`--params`ポリシーのトレードオフを順に見ていきます。

## 使いたくなる場面

- RBSカバレッジがゼロのRubyプロジェクトを引き継ぎ、`rbs prototype rb`の構文的なスケルトンよりも誠実な出発点が欲しい。
- メソッドを追加し、`rigor check`がそれを認識した。今度はシグネチャを手で打ち直すことなく対応するsigファイルを更新したい。
- 既存のRBSは`() -> Numeric`と宣言しているが、Rigorは`() -> Integer`を証明している。レビューの後、より厳密な綴りを`sig/`に適用したい。

そうで**ない**もの: ソースコードに表れていない意図を捉える手書きのRBSの置き換え。公開メソッドが「`to_s`に応答するものなら何でも」という契約（contract）のために`_ToStr`を受け付けるべきでも、現在の呼び出し元がたまたま`String`しか渡していない場合、`sig-gen`は`_ToStr`をあなたのために発明しません。後述の[`--params`ポリシー](#--paramsポリシーとadr-5)セクションとADR-5がその理由を説明します。

## 初回の実行

`lib/calc.rb`が次のように与えられたとします:

```ruby
class Calc
  def add(a, b)
    "sum"
  end

  def greet(name)
    "hi"
  end
end
```

そして空の`sig/`の下で`rigor sig-gen`はRBSスケルトンを表示します:

```
$ rigor sig-gen
# lib/calc.rb
class Calc
  # [new]
  def add: (untyped, untyped) -> String
  # [new]
  def greet: (untyped) -> String
end
```

デフォルトではコマンドは何も書きません。レビューできるよう提案を表示するだけです。`--write`を渡すと提案を`sig/`に適用します。

## 出力モード

| モード | 動作 |
| --- | --- |
| `--print`（デフォルト） | RBSをstdoutに表示。ソースファイル+クラス宣言でグループ化される。 |
| `--diff` | 既存の宣言された綴り（あれば）と推論された綴りを比較する統一スタイルのdiffを表示。読み取り専用。 |
| `--write` | 提案を`sig/<path>.rbs`に適用。ファイルを作成し、既存のクラス宣言に新しいメソッドを挿入し、クラスがまだ宣言されていないファイルには新しいクラスブロックを追加。 |
| `--check` | 書き込みを行わずに`--write`のマージを実行し、何が変更されるかを表示して、何か変更がある場合は終了コード`1`で終了。読み取り専用。 |

4つのフラグは相互に排他的です; 2つの異なるフラグを渡すと使用法エラー（usage error）になります。

`--write`はファイルシステムに触れる唯一のモードです。`configuration.signature_paths`（デフォルト`sig/`）の**内側でのみ**動作します;そのツリーの外側にあるものは書き込まれずに`skipped_outside_sig_root`として報告されます。

### CIでsig/を最新に保つ

`--check`は鮮度ゲート（freshness gate）です。`--write`と同じオプションを受け付け、その`--write`がファイルを作成または変更するか、メソッドを拒絶する場合にまさに失敗します:

```sh
rigor sig-gen --check lib
```

```
would create sig/greeter.rbs (1 method(s))
  + def greet: (String name) -> String
```

メソッドが拒絶されている間（`sig.skipped.inline-differs`）も、`--write`が同様に拒絶するため失敗します。それ以外の場合は終了コード`0`で終了し、`sig/ is up to date`と表示します。`--format=json`の下では、ペイロードは`{"up_to_date": …, "results": […], "refused": […]}`となります: `--write`のJSON形状におけるターゲットごとに1つのエントリー（`action`は`would_create` / `would_update`）と、拒絶されたメソッドごとに1つのエントリーです。

このゲートは`--diff`ではなく`--write`に従います（[ADR-112](../../adr/112-extrbs-comment-channel/) WD4にこの方針の経緯が記録されています）。すでに存在する宣言に対する`tighter-return`は、`--write`が`--overwrite`なしには拒否する提案であるため、`--check`も失敗させません: レビュー済みの意図的により広い型が、ゲートを永遠に失敗させ続けるべきではないためです。`--check --overwrite`はそれをカウントします。`--write --overwrite`がそれを適用するためです。`--check`には`--write`が使用する`--params`や`--effect-envelopes`フラグを渡してください。そうしないと異なる出力をチェックしてしまいます。

## 分類モデル

`rigor sig-gen`が考慮するすべてのメソッドは、6つの状態のいずれかに着地します:

| 分類 | 意味 |
| --- | --- |
| `new-file` | レシーバークラスを宣言するRBSファイルが一切ない。 |
| `new-method` | RBSファイルがクラスを宣言しているが、このメソッドは宣言していない。 |
| `tighter-return` | RBSファイルがメソッドを宣言しているが、推論された戻り値が宣言された戻り値の真の部分型（subtype）。提案は、戻り値のみが置き換えられた宣言行になります; [より厳密な戻り値は宣言されたパラメータを保持する](#より厳密な戻り値は宣言されたパラメータを保持する)を参照。 |
| `inline-overwrite` | `--overwrite`下でのみ: `# @rbs` / `#:`でインライン宣言されたメソッドで、`sig/`宣言がそれと不一致のもの; `sig/`のメンバー全体がインラインのもので置き換えられる。[インライン宣言されたメソッド](#インライン宣言されたメソッド)を参照。 |
| `equivalent` | `sig-gen`が提案するものは何もない: 推論された戻り値が同一、より広い、または無関係であるか、ジェネレータが辞退するナローイング（より広い宣言の下でのリテラル、宣言された`void`の下でのすべて、オーバーロードされた宣言または`alias`）、あるいはメソッドがクラスがすでに宣言している`initialize`である。サイレントにスキップ。 |
| `skipped` | 以下のいずれかの理由で対象外。 |

`sig.skipped.*`理由は:

- `sig.skipped.complex-shape`: レンダラーが表記できないパラメータ形状のために予約。現在では`def`が宣言できるすべての形状（任意、rest、後続、キーワード、キーワードrest、`...`転送、`&block`）がレンダリングされるため、ジェネレータはこの理由を生成しません;そのようなメソッドすべてに対して以前発火していたゲートが廃止された際（#778）、予約されたまま残されました。
- `sig.skipped.untyped-return`: メソッド本体の最終式が`Dynamic[top]`として型付けされる。`untyped`を引き締めとして発行することは助けではなくノイズになる。
- `sig.skipped.user-authored`: `--overwrite`が設定されておらず、メソッドの既存のRBS宣言を置き換える必要がある。
- `sig.skipped.inline-declared`: `.rigor.yml`が`sig_gen.inline_declared: skip`を設定しており、メソッドがインラインで宣言されている。[インライン宣言されたメソッド](#インライン宣言されたメソッド)を参照。
- `sig.skipped.inline-generic-class`: メソッドのクラスがインライン宣言によってジェネリックであり、`sig/`がまだそれを宣言していないか、型パラメータの名前を異なって付けている。[インラインでジェネリックにされたクラス](#インラインでジェネリックにされたクラス)を参照。
- `sig.skipped.generic-reopening` — メソッドのクラス、またはそれがネストされているクラスが、境界またはデフォルト値を持つ型パラメータを伴ってロードされたRBSによりジェネリックとして宣言されており、`sig/`がそれを宣言していない。[ジェネリッククラスの再オープン](#ジェネリッククラスの再オープン)を参照。
- `sig.skipped.inline-differs`: メソッドがインラインと`sig/`で宣言されており、両者が不一致。拒絶（refusal）: `--write`と`--check`は`1`で終了する。[インライン宣言されたメソッド](#インライン宣言されたメソッド)を参照。
- `sig.skipped.top-level-def` — プレーンなトップレベル`def`。これはprivateな`Object`メソッドを定義します。sig-genはこれをリストしますが（`--format=json`ではファイル、メソッド名、およびこの理由）、それに対するRBSを書き出さないため、`--write`と`--check`には影響しません。そのJSON行には`class`キーがありません。`def self.x`、ブロック本体内の`def`、および`class << obj`内の`def`は報告されません。
- `sig.skipped.unrenderable-rbs`: このメソッドに対してRigorがレンダリングしたシグネチャがRBSとしてパースできない。これは**Rigor自身のバグ**であり、あなたのコードの性質ではない——生成された行はすべて出力される前にパースされ、`rbs`が拒否した行は書き出される代わりに破棄される。パースできない`.rbs`は`rigor check`によって*丸ごと*隔離されるため、1つの不正な行がファイル内の他のすべての型を道連れにしてしまうからだ。他のシグネチャには影響しない;スキップされたメソッドはstderrに報告され、私たちに報告する価値がある。

### より厳密な戻り値は宣言されたパラメータを保持する

`tighter-return`は戻り値のみを変更し、それ以外のものは変更しません。可視性、オーバーロードのアノテーション、メソッド型パラメータ、パラメータリスト、およびブロックは書かれたとおりの宣言からコピーされるため、提案を適用してもシグネチャが受け付ける呼び出しが変わることは決してありません:

```
$ rigor sig-gen --diff lib/c.rb
--- lib/c.rb: C#m
- def m: (Integer x) -> untyped
+ def m: (Integer x) -> Float

--- lib/c.rb: C#n
- def n: (?) -> untyped
+ def n: (?) -> Float
```

`-`行は提案が置き換える宣言です。祖先でのみ宣言されているメソッドは異なります: 提案はそのメソッド自身のクラスにオーバーライドを追加し、新しいメソッドと同様に、そのクラスの`def`から`untyped`パラメータを用いて記述されます。祖先のパラメータは祖先の`def`を記述しており、オーバーライドは他の引数を取る可能性があるためです。

2つの宣言は提案を受け取りません:

- 複数のオーバーロードを持つもの（`def m: (Integer) -> untyped | (String) -> untyped`）。本体はそのすべてのオーバーロードに対して一度だけ型付けされるため、推論された戻り値はどのオーバーロードが何を返すかを示しません。オーバーロードを1行にマージするとそれらが脱落してしまい、すべてのオーバーロードに同じ戻り値を与えるとより狭く書いたものが広がってしまいます。
- クラス自身が`alias al m`を通じて宣言する名前。そのパラメータは`m`のものであり、提案は`m`の行の書き換えとして読まれてしまいます。祖先のみが宣言するエイリアスは、他の任意の祖先宣言と同様にオーバーライドされます。

`sig/`がすでに宣言している`initialize`も同様に`equivalent`です。sig-genは宣言を持たないクラスに対してのみコンストラクタスタブを記述します。例外は`--params=observed`です: 観測された引数型が宣言がまだ持つ`untyped`を置き換える場合、`--overwrite`がそれを適用できるようにスタブが提案されます。

## インライン宣言されたメソッド

`# @rbs`または`#:`でアノテーションを付けたメソッドには、すでにコードの隣に書かれた契約が存在します。`sig-gen`はそれに対して契約を推論しません;あなたの契約を`sig/`にコピーするため、生成されたシグネチャはあなたのgemが出荷する契約全体となります:

```ruby
class Greeter
  # @rbs name: String
  # @rbs return: String
  def greet(name) = "Hello, #{name}"

  #: () -> Integer
  def count = 1

  # @rbs num: Float
  def pair(num) = [num, num.to_s]
end
```

```
$ rigor sig-gen
# lib/greeter.rb
class Greeter
  # [new]
  def greet: (String name) -> String
  # [new]
  def count: () -> Integer
  # [new]
  def pair: (Float num) -> [Float, String]
end
```

`count`はその本体が証明する`1`ではなく`Integer`として書かれます: その宣言こそがあなたの意図したものであり、推論がそれを上書きすることはありません。`pair`はそのパラメータを宣言し戻り値を宣言していないため、パラメータがコピーされ戻り値は本体から導かれます。[ADR-107](../../adr/107-checked-types-and-typeless-comments/)が著述されたパラメータと生成された戻り値の間に引いた境界線と同じです。`initialize`はその本体が何で終わろうとも常に`-> void`として書かれます。`# @rbs %a{deprecated}`のようなインラインで書いたメンバーアノテーションも一緒にコピーされます。独自のアノテーションを持たないメソッドは、他のファイルとまったく同様に提案されます。

`sig/`がコピーを保持すると、`rigor check`はそれをインライン宣言と並んで読み取り、同一のペアは沈黙を保ちます（[ADR-112](../../adr/112-extrbs-comment-channel/) WD5）。sig-genは実行ごとに`attr_*`宣言を含めて両者を比較します。テキストとしてではなく型として比較されます: パラメータ名、空白、ユニオンの表記方法（`String?`と`String | nil`、`Integer | String`と`String | Integer`、`bool`と`true | false`）、先頭の`::`は考慮されません。`::`が考慮されるのは名前の意味を変える場合のみです: `module NS`の内側では、`NS`がそれを宣言していれば`Foo`は`NS::Foo`であり、その場合`::Foo`ではありません。オーバーロードの順序は考慮されます。RBSは一致する最初のオーバーロードで呼び出しに応答するためです。両者が一致し、`sig/`がインラインで書いたすべてのアノテーションを保持している場合、何も行うことはありません。

両者が異なる場合、sig-genは一方を選択することはありません。インラインアノテーションはあなたの新しい編集かもしれませんし、`sig/`メンバーは誰かが意図的に変更したレビュー済みの契約かもしれません。メソッドは`sig.skipped.inline-differs`として拒絶（refusal）されます: 何も書き込まれず、`--write`は`REFUSED`行を表示して`1`で終了し（`--format=json`の下では拒絶されたメソッドは`refused`の下に一覧表示されます）、`--check`は失敗するため、矛盾がCIを気づかれずに通過することはありません。2つの方法のいずれかで解決してください:

- インライン宣言を保持する: `--overwrite`を付けて再実行します。`sig/`のメンバー全体が、rbs-inlineが読み取った通りのインライン行で置き換えられます ── アノテーションを付けなかったパラメータは`untyped`、アノテーションを付けなかった`&block`は`?{ (?) -> untyped }`となり、`attr_*`宣言は同じ綴りのインライン属性で置き換えられます。両辺がスロットごとに混ざり合うことは決してありません: それらのオーバーロードと型変数は対応する必要がないためです。これはまた、`sig/`にのみ書かれていたオーバーロードが削除され、それに依存していた呼び出し元が型チェックに失敗し得ることも意味します;まず`--diff`を読んでください。置き換えられたメンバー内のコメントや、すでにそのメンバーに付いていたアノテーションは保持されます。
- `sig/`メンバーを保持する: インラインアノテーションを編集または削除して一致させます。

`def m: ... | ...`と書かれた`sig/`メンバーはコピーではありません: インライン宣言にオーバーロードを追加するものであり、sig-genはそれをそのまま残します。

パラメータのみのアノテーション（`# @rbs name: String`、`return:`なし）はパラメータのみを述べるため、パラメータのみが比較されます。それらが一致する場合、`sig/`内の戻り値は任意の宣言された戻り値と同様に評価されます: `-> void`、本体が証明するものより広い型、または本体がたまたま返すリテラル（`"x"`に対する`-> String`）はそのまま残され、本体が厳密により狭いと証明する戻り値は`tighter-return`提案となり、`--overwrite`を付けた場合にのみ適用されます。パラメータが異なる場合、メソッドは`--overwrite`下でも拒絶されます: 本体は`sig/`メンバーが宣言するパラメータの下で型付けされるため、新しい行に対して推論された戻り値は変更されようとしているパラメータを記述することになってしまうからです。`sig/`メンバーを削除して再実行してください;するとsig-genはメソッドを新規に書き込みます。

### ジェネリッククラスの再オープン

ロードされたRBSがジェネリックとして宣言しているクラス ── `class Array`、`class Hash`、gemのクラス、あるいはあなたの`sig/`が宣言するクラス ── をコードが再オープンするとき、sig-genはその宣言の型パラメータを伴ってヘッダーを書き出します: `class Array[unchecked out E]`。rbsはパラメータが異なる再オープンを拒絶するため、素の`class Array`は該当クラス、およびシグネチャがそれを言及するすべてのクラスを`GenericParameterMismatchError`で失敗させてしまいます。メンバーは要素型について依然として`untyped`と表記し、コピーされたパラメータと名前が一致するクラスはアンカー付き（`::E`）で書き出されます。素の`E`はそのパラメータを指名してしまうためです。

パラメータがコピーされるのは、すべてのパラメータがプレーンである場合のみです: 名前、変性、および`unchecked`。境界またはデフォルト値（`class Box[T < Comparable]`）は宣言元ファイルの名前空間向けに記述された型であり、sig-genが書き出す場所では別のクラスを意味する可能性があるため、そのクラスのメソッド、およびそこにネストされたクラスのメソッドは`sig.skipped.generic-reopening`としてスキップされます。`sig/`内でパラメータを伴ってクラスを宣言すれば、sig-genはその宣言の中にメンバーを書き出します。すでにそのクラスを宣言しているファイルは自身のヘッダーを保持します。

### インラインでジェネリックにされたクラス

sig-genはインライン宣言から型パラメータをコピーしません。したがって、インラインでジェネリックと宣言されたクラス（`# @rbs generic T`）は`sig/`内でオープンされません: パラメータのないヘッダーは、rbsがそのクラスおよびそのシグネチャがそれに言及するすべてのクラスを`GenericParameterMismatchError`で拒絶することになるためです。そのメソッド、およびネストされたクラスのメソッドは、`sig.skipped.inline-generic-class`としてスキップされます。`sig/`内で同じパラメータでクラスを宣言（`class Box[T]` ... `end`）すれば、sig-genはその宣言内にメンバーを書き込みます。異なる名前を付けた`sig/`宣言（`class Box[U]`）も同様にスキップされます: コピーされた`-> T`は何にも束縛されないパラメータに名前を付けてしまうからです。

### 同じアノテーション上でSteepを実行するプロジェクト

Steepがあなたのインラインアノテーションを読み取る場合（`signature "sig"`の隣に`check "lib", inline: true`）、`sig/`内のコピーは各メソッドの2番目の宣言となり、Steepは`DuplicatedMethodDefinition`でクラスを拒絶します。`sig-gen`にそれらのメソッドを除外するよう指示してください:

```yaml
sig_gen:
  inline_declared: skip
```

インラインリーダーが宣言するすべてのメソッドが`sig.skipped.inline-declared`としてスキップされます。これには何らかのアノテーションを持つファイル内のアノテーションのない`def`も含まれます。リーダーがそれらも（`untyped`として）宣言するためであり、Steepの`inline: true`が使用するrbs自身のインラインパーサも同様です。まったくアノテーションのないファイルはRigorによってインラインで読み取られないため、そのメソッドは依然として書き込まれます; Steepがそのファイルをインラインで読み取る場合は、`sig-gen`に与えるパスからそれを除外してください。

この設定が犠牲にするもの: `sig/`はもはや完全な契約ではなくなります。出荷された`sig/`のみを読み取るコンシューマー ── あなたのgemに依存するプロジェクト内のRigorまたはSteep ── はスキップされたメソッドを見ることは決してありません。そこに書かれたRigorリファインメントを含むそれらのインラインアノテーションは、ソース自体が解析される場所（すなわちあなた自身のプロジェクト）でのみ有効となります。

## エフェクトアノテーションの出力

`.rigor.yml`に`effects:`ブロックが含まれている場合、`sig-gen`はもう1つのものを書き込みます: Rigorがフットプリント全体を読み取り、何もないと判断したメソッドの上に、rbsやSteepがすでに理解している純粋性アノテーション`%a{pure}`を出力します。

```ruby
class Label
  def render
    parts = []
    parts << "a"
    parts.join
  end
end
```

```
$ rigor sig-gen
# lib/label.rb
class Label
  # [new]
  %a{pure}
  def render: () -> String
end
```

アノテーションが書き込まれるには5つの条件を満たす必要があり、そのすべては誤ったアノテーションがページに載らないようにするために存在します。出力されたアノテーションは単なるヒントではありません ── エフェクトのオプトインはそれを**エンベロープ（envelope）**として読み戻し、そのメソッドおよびそのメソッドが到達するすべてのものに対して強制するため、`sig-gen`が捏造した`%a{pure}`は正しいコードに対して`effect.envelope-exceeded`を発生させてしまいます。

- サマリーは**網羅的（exhaustive）**でなければなりません: メソッドが到達するすべての呼び出しが解決されていること。網羅的でないサマリーは「これらのエフェクト、および場合によってはそれ以上」と読まれ、これはまさにエンベロープが主張してはならないことです。
- サマリーは**未免責（undischarged）**でなければなりません: メソッドのフットプリント内のいかなるものも、`effects.tolerated:`が無視するように指示しているという理由だけで不可視になっていてはなりません。フットプリント全体が許容された`telemetry`呼び出しであるメソッドは、*あなたの*プロジェクトにとってのみクリーンに見え、出荷された`sig/`を読むコンシューマーや、あなた自身の`--no-tolerated-effects`監査など、他の誰にとってもクリーンには見えません。
- すべての呼び出し先が**何らかのものによって記述されている**必要があります: カタログ行、プラグイン、エンベロープ、またはあなた自身のプロジェクト内の定義です。「すべての呼び出しが解決された」と「すべての呼び出し先のフットプリントが判明している」は異なる問いです。本体が誰も行やエンベロープを書いていないgemへの1つの呼び出しであるメソッドは網羅的ですが何も語らないため、純粋と呼ぶのではなく素のまま残されます。
- メソッドは**すでに独自の境界（bound）を持っていてはなりません**。メソッド上またはそのクラス上のアノテーション ── `sig/`内またはrbs-inlineの`# @rbs %a{…}` ── や、`namespace:`または`match:`によってそれを選択する`effects.envelopes:`スタンザは、あなたがこの本体について書いた契約です;sig-genがそれを同じ本体に関する推論で置き換えることはありません。ラベルのスペルが間違っている境界もカウントされます: それは何の境界にもなりませんが、上書きすると`effect.unknown-label`レポートが指し示しているアノテーションが削除されてしまいます。
- `≤`レーンは**空**でなければなりません。独自の境界を述べる呼び出し先は、何も証明することなくその主張をあなたのメソッドの宣言レーンに置くため、証明されたレーンが空である場所で`rigor effects`は`[] ≤ [io.net.http]`を表示します。Rigorは、自身が決して証明して取り除いていない主張の上に`%a{pure}`を書き込むことはありません。

`--effect-envelopes`は、フットプリントを持つメソッドに対してラベル付きの表記（`%a{rigor:v1:effect io.db, nondet.time}`）を追加します。`%a{pure}`はエコシステムのアノテーションであり、こちらはRigor独自のものであるため、別のフラグとなっています: `sig/`内のラベル付きエンベロープはRigor固有の契約であり、明示的に名前を指定して要求すべきです。

`--write`の下では、アノテーションはそれが束縛する宣言の上の行に配置されます。**すでに**アノテーションを持っている宣言はバイト単位で変更されずに残され、`sig.effect.left-unreadable`として報告されます: ライターは自身が書いたアノテーションとあなたが書いたアノテーションを区別できず、2つをマージする文法も持たないため、その領域を書き換えることはありません。それが何を述べるべきかを決定し、自分自身で書いてください。

`sig.effect.*`の理由は以下のとおりです:

- `sig.effect.emitted` ── アノテーションがレンダリングされた。
- `sig.effect.withheld-tolerated` ── フットプリントは`effects.tolerated:`の下でのみクリーンである。
- `sig.effect.withheld-non-exhaustive` ── メソッドが到達する一部の呼び出しを解決できなかった。
- `sig.effect.withheld-unclaimed-callee` ── 到達する一部の呼び出しが解決されたが、その呼び出し先が何を行うかを説明するものがどこにもない。
- `sig.effect.withheld-declared` ── メソッドがすでに手書きの境界を持っているか、`≤`レーンにラベルが残存している。
- `sig.effect.left-unreadable` ── 対象の宣言がすでにアノテーションを持っているため、そこには何も書き込まれなかった。

知っておく価値のある制限が1つあります: アノテーションは`sig-gen`が提案するシグネチャ行に乗るため、宣言がすでに完全に正しいメソッドは何のアノテーションも取得しません。したがって、最新の`sig/`はその場でアノテーションが付与されることはありません;それらのリーダーは`rigor effects --pure`であり、それらを書き込むことは依然として手動の編集です。

`.rigor.yml`に`effects:`ブロックがない場合、これらの処理は一切実行されず、出力は以前とバイト単位で同一になります。

3つの`sig.generated.*`識別子（`sig.generated.new-file` / `new-method` / `tighter-return`）は`--format=json`の下でJSONフィールドとして発行されるため、CIゲートの消費者がこれらをルーティングできます。すべての`skipped`行も同じペイロードの一部であり、`skip_reason`としてその`sig.skipped.*`識別子を運ぶため、あなたの`sig/`に欠けているメソッドは、出力された行の隣にその理由を持ちます。テキストモードでは代わりに1行のstderrサマリーが理由ごとのスキップされたメソッド数をカウントし、stdoutは貼り付けに適したクリーンさを保ちます。

## ジェネレータが埋められないギャップの記録

`sig-gen --diff`は、自身が型付けできるすべてのメソッドに対して「この宣言は実装が証明するものか？」に答えます。答えられないものこそが興味深い対象です: 適用しないと決定した`tighter-return`、スキップされたメソッド、背後に一切`def`が存在しない宣言。これらはいずれも手書きの型であり、誰も理由を書き留めなかった手書きの型は、それ以来誰も見ていない型と区別がつきません。

Rigorが自身の`sig/`で採用している規約は、メンバーのRBSコメント内の1行です:

```rbs
class Registry
  # sig-gen gap: #1234 — sig-gen types the body `untyped`
  # (the ivar has no inferred field type yet), so this
  # return is hand-written until it can prove one.
  def resolve: (String name) -> Entry
end
```

`void`の戻り値にはマーカーは不要です。`sig-gen`が`void`に対して値を提案することは決してありません: `void`は戻り値が契約の一部ではないことを意味し、いかなる推論もそれを合成しないため、`void`宣言はパラメータ型と同様に著者の意図そのものです（[ADR-14](../../adr/14-rbs-sig-generation/) §「推論vs RBS矛盾ルール」）。

本体がリテラルとして証明する宣言にも不要です。本体が文字列`"bot"`である`def describe: () -> String`に対して、`sig-gen`が`"bot"`を提案することはありません: 宣言された型はその本体に対するあなたの抽象化であり、リテラルに固定してしまうとすべての兄弟クラスが共有する契約を書き換えてしまうことになります。`sig/`内に手書きした宣言された`untyped`も、値リテラルに対して同様に扱われます: 本体が証明するInteger、String、またはSymbolはそのクラスへと広げられ（`-> 1`は`-> Integer`に、`-> ("S" | nil)`は`-> (String | nil)`になります）、`true`や`false`は`bool`（`(false | true)`と表記）へと広げられるため、他方でメソッドをオーバーライドするサブクラスが戻り値を広げていると報告されることはありません。`nil`のみを返す本体は`untyped`を維持します: これはサブクラスが肉付けするテンプレートメソッドの形状であり、`-> nil`にすると値を返すあらゆるオーバーライドが広げられたとみなされてしまうためです。タプル、レコード、または型引数の内側にあるリテラルも、形状を保ったまま同様に広げられます（`-> [1, "a"]`は`-> [Integer, String]`に、`-> { a: 1 }`は`-> { a: Integer }`になります）。ジェネリック型の中では、`Array`、`Hash`、`Set`、`Range`、`Enumerator`の引数のみが広げられます。ユニオンまたは形状の内側の`nil`、および計算された`Float`はそのまま提案されます。メソッドがパラメータのみに対するインライン`# @rbs`アノテーションも持っている場合、ネストされているかどうかにかかわらず、広げられる対象のリテラルを保持する戻り値は一切提案されず、`untyped`が維持されます。アノテーションを付けなかった`def`に対してインラインリーダーのみが合成する`untyped`はリテラルを保持し、いかなる`.rbs`も宣言していないメソッドも同様です ── リテラルは依然として本体が証明する最も厳密なものであり、それが書き出されます。

`%a{…}`アノテーションではなくコメントにするのには3つの理由があります: `rigor:v1:`ディレクティブ名前空間（[`docs/type-specification/rbs-extended.md`](../../type-specification/rbs-extended/)）の外側に留まること、どのエンジンパスもそれを読み込まないこと、そして`RBS::Parser`がそれをメンバーにバインドするため、チェック処理が行を走査する代わりにAST上でそれを見つけられることです。issue番号は耐荷重となる半分です ── ジェネレータが回答できるようになるエンジンの作業を指し示しており、手書きのRBSへと促すギャップこそがより価値の高いシグナルであるという[ADR-14](../../adr/14-rbs-sig-generation/)のルールに基づいています。

CLIのいかなる機能もこれを強制しません。これは自身のスイート内でゲート化できる規約です: `sig/**/*.rbs`をパースし、ジェネレータを実行し、生成結果と同等でもマークされてもいない宣言に対して失敗させます。Rigor自身のゲートは`spec/rigor/sig_gen/provenance_spec.rb`（[ADR-107](../../adr/107-checked-types-and-typeless-comments/) G3）です。

そのリストの中の1つのケースは、マーカーのケースではまったくありません。背後に`def`を持たない宣言は、単にRubyが生成するメソッド ── `attr_*`、`Data`メンバー、ロード時にクラスマクロが定義するもの ── を記述しているだけかもしれませんし、削除または名前変更された`def`の遺物である可能性もあります。`rigor check`とSteepの双方が実装が`sig/`と一致するかどうかを問い、その逆を決して問わないため、これは何も検知されません。Rigorのゲートは、自身のプロジェクトインデックスとロードされたツリーに問い合わせることでこの2つを分離します（[#839](https://github.com/rigortype/rigor/issues/839)）。このチェックには`sig/`配下のコードが必要であるため、リポジトリゲートのままとなっています: あなたのプロジェクトにおける`sig-gen`は変更されません。

## ジェネレータが対応するメソッド形状

スライスごとに（各スライスはCHANGELOGエントリーを通じて出荷された。このリストは現在の状態です）:

- 任意のパラメータ形状（必須、任意、rest、後続、キーワード、キーワードrest、`...`転送、`&block`）を持つ**素のインスタンス`def foo`**。パラメータリストはすべての位置に`untyped`を置いて実行時形状を反映し（`--params=observed`下では観察されたユニオン）、ブロックは`?{ (*untyped) -> untyped }`としてレンダリングされます。new-methodとtighter-returnの両パスが適用されます。
- **シングルトン側`def self.foo`**と`class << self; def foo; end`。`def self.foo: ...`としてレンダリングされ、既存のRBSに対しては`Reflection.singleton_method_definition`と照合される。
- リテラルSymbol引数を持つ**`attr_reader` / `attr_writer` / `attr_accessor`**。戻り値型は`Scope#class_ivars_for`から累積されたivar型。コンストラクタパラメータから代入されたivarは、コンストラクタが`def initialize(...)`である場合にのみそのパラメータから型付けされます。あるいは、`attr_reader`はそのファイル内のクラスリテラルに対する`.new(...)`呼び出しから代入されたivarを反映します（`Box.new(0)`により`def count: () -> 0`が得られる）。ただし、これはその代入がそのファイル内のクラス本体におけるそのivarへの唯一の書き込みである場合に限られます: attrライター、手書きのセッター、または他の任意のインスタンスメソッド内の書き込みがある場合、リーダーとライターの双方がスキップされます。別のファイル、スーパークラスやモジュール、あるいは外部からの`class_eval`を通じて宣言されたライターは認識されません。ジェネレータは長形式の`def name: () -> T`スペルを発行し、ライターのマージパスが変更なしに適用されるようにします;既存の短形式の`attr_reader name: T`宣言はユーザー著作として認識され、重複する`def`挿入を生成しません。

これらのメソッドを取り巻くクラス宣言と型名には2つのルールが適用されます:

- **コアまたはstdlibクラスのサブクラス**は、自身が出力するメソッドを持たない場合であっても宣言されるため、それを返すメソッドが解決されます: `class MyHash < Hash; end`は`class MyHash < ::Hash[untyped, untyped]`と書かれます。この宣言はそのソースファイル用に書き出されるファイルに入るため、そのソースファイルに出力すべきメソッドが少なくとも1つある場合にのみ現れます。何らかのシグネチャがすでに宣言しているクラスは、その宣言に任されます。
- **名前空間がシャドウする型名**は、先頭に`::`を付けて書かれます。`Foo::Set`を宣言する`module Foo`の内部では、コアの`Set`を返すメソッドは`-> ::Set[untyped]`と書かれます。RBSがそこでの素の`Set`を`Foo::Set`と読んでしまうためです。名前をシャドウするものが何もない場所では、以前と同様に素のまま書かれます。

ジェネレータがまだ対応**しない**メソッド形状:

- `define_method(:name) { ... }`。
- 本体が`Dynamic[top]`として型付けされるメソッド（本体推論が有用な戻り値型を証明できない）。

これらはADR-14のフォローアップとして追跡されています。

## `--params`ポリシーとADR-5

`--params=POLICY`フラグは、発行されるRBSでパラメータ位置がどう綴られるかを制御します。3つのポリシーがあります;2つは今日接続されており、1つは予約済みです。

| ポリシー | 動作 |
| --- | --- |
| `untyped`（デフォルト） | すべてのパラメータが`untyped`として綴られる。推論由来のパラメータ契約は将来の呼び出し元に課されない。ユーザーがパラメータ型付けの著作権を完全に保持する。 |
| `observed` | `--observe=PATH...`（設定された`test_paths:`、または`spec/`と`test/`のうち存在する方がデフォルト）配下のすべての呼び出し箇所から引数の型を収集し、パラメータ位置ごとにユニオンし、RBSに消去して、ユニオンを発行します。観察すべきテストルートがない場合、または宣言されたルートが存在しないかもしくは読み取られない場合、sig-genはstderrでその旨を報告し、`--format=json`はトップレベルの`observation`キー（後述）に同じ事実を保持します。 |
| `observed-strict` | 予約済み。ロールカタログが出荷されるとケイパビリティロール（`_ToStr`、`_ToS`、…）へさらに広げる。現在は使用エラーで拒否される。 |

`--params=observed`の下では、`--print` / `--diff`のJSONペイロードは`candidates`の隣にトップレベルの`observation`キーを獲得するため、stderrをまったく読み取らない消費者（MCPの`rigor_sig_gen`ツールを含む）でも、「テストルートが観察されなかった」のか「テストが型付きの引数を渡していない」のかを区別できます:

```json
{ "candidates": [ … ],
  "observation": { "paths": ["/app/spec"], "missing": ["/app/tests"] } }
```

`paths`はコレクターが読み取るルート（ディレクトリまたは`.rb`ファイル）です; `missing`はその他の宣言されたルートであり、存在しないもの、または存在するが読み取られないもの（`README.md`）です。同一の重複は1回だけリストされます。`missing: []`を伴う`paths: []`は、テストルートがまったく存在しなかったことを意味します。パスは実行がそれらを解決したとおりに表記されます: `--observe=PATH`は入力されたまま、`test_paths:`は設定ファイルのディレクトリに対して解決された絶対パス、自動検出された`spec/` / `test/`は絶対パスです。このキーは`--params=untyped`の下では存在せず、独自の形式を持つ`--write`および`--check`のJSONペイロードからも存在しません。

デフォルトが意図的に`untyped`を優先するのは、[ADR-5](../../adr/5-robustness-principle/)の節2のためです: メソッドのパラメータ契約は、現在の呼び出し元がたまたま使う**最も具体的な**形ではなく、本体のロジックが正当化する**最も寛容な**形であるべきです。`observed`をロックすると、「既存のスペックがたまたま渡すもの」が契約として静かに凍結されてしまいます。これが章の冒頭で示唆した精度 / 採用のトレードオフです。

`--params=observed`は意図的なオプトインです: あなたは「*私の呼び出し元が今日渡すものの和集合こそが、私の望むパラメータ契約だ*」と言っているのです。これは正しさを保つ拡幅です（既存のすべての呼び出し元は依然として通過する）が、`untyped`に比べて契約を狭めます。

## プロジェクトが宣言する型エイリアス

提案の型が、あなた自身の`sig/`で宣言された`type`エイリアスの展開とメンバーが正確に一致するユニオンである場合、エイリアス名が出力されます。`Rigor::Type::Combinator`上のメソッドに対して、sig-genは以下を出力します:

```
def hash_shape_keys: (untyped) -> ::Rigor::Type::t
```

`Rigor::Type::t`が展開される22個のメンバーを出力する代わりです。名前は絶対形式で記述されるため、同じ綴りのより近い定数に再束縛されることはありません。

これは戻り値だけでなく、sig-genが型をレンダリングするあらゆる場所に適用されます: `--params=observed`のパラメータ位置、`attr_*`アクセサ、そして`Data` / `Struct`メンバーもすべて同じように畳み込まれます。`--format=json`ペイロードは、その`rbs`フィールドに畳み込まれた表記を運びます;`inferred_return`はエンジンが計算したキャリアであり、展開されたままとなります。

ルールはメンバー集合の同値性であるため、エイリアスの1つのアームを欠く提案は依然として完全に出力されます ── エイリアスはそのメソッドが返すことのできない型の名前を挙げており、それを主張することは単に冗長であるだけでなく誤りとなるからです。

誤ったエイリアス名は、長いユニオンよりも害悪です: それはあなたが行っていないRBSの主張です。4つのルールが畳み込みによる推測を防ぎます。

**あなたのエイリアスのみ**。候補は設定された`signature_paths:`（設定されていない場合は`sig/`）から得られます ── bundle内のgemからでも、`rbs collection`ツリーからでも、コアや標準ライブラリのRBSからでもありません。コアは`Warning::category`を`:deprecated | :experimental | :performance`と宣言しています;そのエイリアスを書いたことがないプロジェクトの提案にそれが現れることはありません。ロードされたプラグイン自身のシグネチャディレクトリは、あなた自身が`signature_paths:`にリストした場合でも差し引かれます ── それらのエイリアスはプラグインのボキャブラリーです。

**名前空間の近接性**。エイリアスは、そのオーナーがエイリアス自身の名前空間の内側にあるメソッドに対してのみ提供され、最も近いそのようなエイリアスが勝利します ── 最も具体的なものが最初、次に（ファイル、行、名前）による宣言順です。これがないと、コードベース内のあらゆる場所の`:positive | :negative`が、たまたまそのペアに名前を付けている任意のエイリアスを拾ってしまいます。

**曖昧さのないエイリアス本体のみ**。一部のRBS形式は、レンダラーに到達した時点で別のもののように見えます: インターセクションはそのメンバーの1つとして読まれる可能性があり、proc型は素の`Proc`として、ネストされたエイリアスはそれが展開された先のものとして読まれる可能性があります。それらのいずれかを本体に含むエイリアスはスキップされます。それへの畳み込みは、メソッドが返さない型をシグネチャに配置してしまうからです。クラスインスタンス、シングルトン、リテラル、ユニオン、オプショナル、タプル、および`nil` / `bool` / `bot`ベースのみが対象となります。

**ユニオンのみ、非ジェネリックのみ**。`type name = String`エイリアスが通常の`String`戻り値を書き換えることは決してなく、ジェネリックエイリアス（`type boxed[T] = ...`）には一致させる固定されたメンバー集合がありません。

エイリアスを宣言していないプロジェクトは、以前とバイト単位で同一の出力を得ます。

## RSpecを意識した観察

観察対象のテストルートがRSpecスイートを保持している場合、ジェネレータは4つのRSpec形のバインディングパターンを認識し、それを使って`Dynamic[top]`に縮退するレシーバーを型付けします:

```ruby
RSpec.describe Calc do
  subject { Calc.new }         # :subject → Nominal[Calc]をバインド
  let(:other) { Calc.new }     # :other   → Nominal[Calc]をバインド
  before { @calc = Calc.new }  # @calc    → Nominal[Calc]をバインド

  it "..." do
    subject.greet("Alice")     # 観察: Calc#greetがStringを受け取る
    other.greet("Bob")         # 観察: 同上
    @calc.greet("Carol")       # 観察: 同上
    described_class.new.add(1, 2)  # 観察: Calc#addがInteger、Integerを受け取る
  end
end
```

認識器は`RSpec.describe Foo`、素の`describe Foo`（`RSpec.`レシーバーなし）、`subject { … }`、`subject(:name) { … }`、`let(:name) { … }`、`let!(:name)`、`before`ブロックのトップレベル式で代入されたインスタンス変数、そして`described_class.new(...)`を扱います。ネストされたスコープを越えた同名の`subject` / `let`バインディングは「後勝ち」;認識器はRSpecの完全なスコープルールを再実装しません ── 典型的な1スペックファイルの形状がターゲットです。`before`のインスタンス変数はスコープ化されます: それはその`before`を保持する`describe` / `context`ブロックの内部でのみ読み取りを型付けし、ネストされた`describe` / `context` / `it` / フックブロックを通じて有効ですが、他のいかなるブロック（`Class.new { … }`、`instance_eval { … }`、`each { … }`）を通じても有効ではなく、2つの囲む`before`が異なるクラスを代入している読み取りは観察されません。

`test/`配下のMinitestスイートも、独自の認識器なしで観察されます: レシーバーが1つのクラスに型付けされる呼び出しがカウントされます。`setup`は`initialize`ではないため、`setup`で代入されたレシーバーは`test_*`メソッドの内側では`Foo | nil`と読まれます;そのような形状のレシーバー ── 1つのクラスまたはクラスオブジェクトに加えて`nil` ── は、`nil`がそのメソッドに応答しない場合、その呼び出しが`nil`に対して行われたはずがないため、そのクラスとして観察されます。`nil`が応答するメソッド（`==`、`respond_to?`、`is_a?`）の呼び出しは、`nil`上で実行された可能性があるため観察されません;`&.`を伴う場合は、`&.`が`nil`をスキップするため観察されます。`nil`がどのメソッドに応答するかは、`NilClass`、`Object`、`Kernel`向けにロードされたRBSに由来するため、ライブラリが`nil`に追加するメソッド（ActiveSupportの`try`、`as_json`）は、そのライブラリのRBSがロードされている場合にのみカウントされます。`@foo&.bar(1)`も同様にカウントされます。2つのクラスのいずれかになり得るレシーバー（`Foo | Bar | nil`）や、`untyped | nil`は依然として観察されません。

認識器はジェネレータ自身の一部です;その恩恵を受けるために`rigor-rspec`をインストールする必要はありません。すでに`rigor-rspec`を診断のために使っている場合、両者は協調なしに並行して動作します。

## 安全性: `--write`が行うことと行わないこと

- **行う**: `lib/<path>.rb`のレイアウトをミラーする新しい`*.rbs`ファイルを作成（`configuration.paths.first`のベース名を取り除き、`configuration.signature_paths.first`の下に配置）。
- **行う**: クラス宣言の閉じる`end`キーワードのすぐ前に新しいメソッド宣言を挿入。ファイルの他のすべてのバイトをそのまま保持。
- **行う**: ターゲットファイルがまだクラスを宣言していない場合、新しい`class Foo … end`ブロックを追加。
- **行う**: シグネチャツリー配下のファイルが、同じ種類の`def`または`attr_*`（インスタンスまたはシングルトン）によってそのファイルのいずれかのクラスの開きで同じクラス上に宣言している場合、メソッドをすでに宣言されたものとして扱う。`def self?.`は両方の種類を宣言し、`def self?.`の提案はいずれかの種類が宣言されていれば宣言済みとカウントされる。メソッドはクラスの最初のファイルに追加される代わりに、それを宣言しているファイル内で更新（`--overwrite`）またはスキップされる。置換はそのクラスの最初の開きにある提案自身の種類の`def`にのみ着地する: 単独の`def self.f`または`def f`に対する`def self?.`提案、`def self?.f`に対する通常の提案、または後の開きで宣言されたメソッドはスキップされる。`def f: ... | ...`オーバーロードは決して置き換えられず、`f`を宣言しているファイルとしてカウントされることも決してない。`alias new old`（または`alias self.new self.old`）はそれ自身の種類の下で`new`を宣言し、決して置き換えられないため、その名前に対する提案はスキップされる。
- **行わない**: 設定されたシグネチャツリーの外側のファイルには触れない。
- **行う**: スキップしたすべての提案を、ターゲットの下に1つの`  skipped Class#method (reason): <proposed RBS>`行（シングルトンの場合は`Class.method`）としてリストし、`--format=json`の`skipped`の下にも同じ行を含める。理由は`user-authored`（ターゲットがそのメンバーを宣言しており、ライターがそれを置き換えない）または`outside-sig-root`（そのメンバーが、宣言されているかその中にあるクラスに対して新規であるかに関係なく、`--write`が変更しない最初のパス以外のシグネチャパス内のファイルにルーティングされる）である。スキップのみによって変更されなかったターゲットは`unchanged <file>`を出力する。終了ステータスは`0`のままである: スキップは拒否ではなく、`--check`は依然として`sig/`を最新として報告する。
- **行わない**: `--overwrite`が設定されており、かつ候補が`tighter-return`である場合を除き、既存のメソッド宣言を置き換えない。その場合でも戻り値のみが変更され、宣言の残りの部分は保持される。`--overwrite`がない場合、既存の宣言はユーザー作成のものとみなされ、新しいメソッドはスキップされる。
- **行わない**: `--overwrite`が設定されていない限り、メソッドのインライン宣言と一致しない既存のメソッド宣言を変更しない;メソッドを`REFUSED`として報告し、`1`で終了する。`--overwrite`を付けた場合、メンバー全体がインライン宣言で置き換えられ（`inline-overwrite`）、すでにそのメンバーに付いていたコメントやアノテーションは保持される。
- **行わない**: 既存のRBSにある`attr_reader` / `attr_writer` / `attr_accessor`宣言には触れない。それらは常にユーザー著作として扱われる。

推奨されるワークフローは、まず`--diff`、レビュー、それから`--write`（または引き締めが意図的だと判断した場合は`--write --overwrite`）です。

### 引き締めが*おそらく*不完全な推論であるとき

真の部分型チェックはtighter-returnを発行するための*必要*条件です。既存のRBSが間違っていることを示す*十分*なシグナルではありません。スライス1の本体型付けパスは暗黙の戻り値式しか検査しないため、次のようなメソッド:

```ruby
def find(key)
  return nil unless @table.key?(key)
  @table[key]
end
```

は`@table[key]`単独の戻り値として型付けされます。既存のRBSが`(K) -> V | nil`と宣言している場合、推論された`V`は厳密に締まって見えます。しかしそれは間違った理由で締まっています（`nil`分岐は本体型付け器の目には到達不可能ですが、ランタイムの目には到達可能です）。これを適用すると`nil`の腕をサイレントに削除してしまいます。

**ヒューリスティック**: 引き締めが既存のRBSが宣言するユニオンメンバーを落とすとき（`T | nil → T`、`false | true → true`、`Float | Integer → Float`、`Array[T] → [T]`）、それを精度の勝利ではなく矛盾シグナルとして扱い、既存のRBSはそのまま残します。ジェネレータはこれらを自動的に分類しません;`--diff`レビューステップが人間のゲートが座っている場所です。

`rigor`自身の`sig/`ツリーに対しては、これが荷重を支えるポリシーです: 既存の宣言と矛盾するすべてのtighter-returnは、別途証明されるまで不完全な推論として疑われます。

## まとめ

新しいファイルに対する典型的なイテレーション:

```sh
# 1. Rigorが何を提案するか見る。
rigor sig-gen lib/calc.rb

# 2. テストルート（`test_paths:`）をパラメーター型シグナルとして
#    使うためobserved-paramsポリシーで実行する。
rigor sig-gen --params=observed lib/calc.rb

# 3. 現在のsig/ツリーと比較する。
rigor sig-gen --params=observed --diff lib/calc.rb

# 4. 適用する。
rigor sig-gen --params=observed --write lib/calc.rb

# 5. rigor checkを再実行して回帰がないことを確認する。
rigor check
```

5つのステップは、コマンドが構築されている5つのADR-14スライスに対応します。期待しなかった結果がいずれかのステップで表示された場合、同じコードに対して解析器が発行するであろう診断が真実のソースです。`sig-gen`は推論の下流の消費者であり、別個の解析ではありません。

## 今日の制限

- ブロックパラメータは常に寛容な`?{ (*untyped) -> untyped }`としてレンダリングされます;型付けされたブロックシグネチャは、エンジンがyield形状を端から端まで追跡するのを待ちます。
- `define_method`と`Data.define`固有の発行は先送りのフォローアップ（`Data.define`由来のリーダーはメソッド本体が存在すれば通過）。
- 真の部分型チェックは今日漸進的（gradual）モードの受理を使用;`Inference::Acceptance`に予約された`:strict`モードはフォローアップで到着。
- `RBS::Writer`を介したラウンドトリップは使用されない（上流の設計でコメントを落とす）;ジェネレータのバイト範囲挿入は触れない宣言をそのまま保持しますが、触れた宣言の範囲*内に*散りばめられたコメントは保持できません。

これらはADR-14の先送り項目です;設計の根拠は[`docs/adr/14-rbs-sig-generation.md`](../../adr/14-rbs-sig-generation/)にあります。
