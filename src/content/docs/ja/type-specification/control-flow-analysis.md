RigorはPHPStan、TypeScript、Pythonの型チェッカーのスタイルでフローセンシティブ（flow-sensitive）な型解析を実行します。解析器はガード、リターン、raise、ループ脱出、パターンマッチ、等価比較、述語メソッド、プラグイン提供ファクトによって型をリファインします。

この文書は以下を定義します:

- エッジ対応スコープの構造;
- non-localな脱出（exit）が、それが離脱する構文の値にどのように寄与するか;
- サポートされているナローイング（narrowing）ソース;
- ナローイングのためのRuby等価セマンティクス;
- ファクトの安定性、無効化、ミューテーション効果;
- 出荷済みのナローイングサーフェス（surface）と、なお先送りされているもの。

`RBS::Extended`アノテーションとプラグイン貢献で使われるフロー効果バンドルスキーマは[rbs-extended.md](../rbs-extended/)にあります。

## エッジ対応スコープ

スコープは構文位置のエッジで分岐します:

- 正常完了;
- 真値条件の結果;
- 偽値条件の結果;
- 例外または非リターン終了;
- `bot`で表される到達不能な結果。

これらのスコープは**正のファクト**と**負のファクト**の両方を運びます。結合はそれらのファクトを保守的にマージします。

エッジ対応スコープは`if`条件全体に1つのスコープを割り当てるよりも細かいです。短絡式はオペランド間でスコープを更新します:

- `a && b`は`a`が生成した真値スコープで`b`を解析します。
- `a || b`は`a`が生成した偽値スコープで`b`を解析します。
- `!a`は真値スコープと偽値スコープを入れ替えます。
- どのような綴りであれ、条件として使用される条件式`(p ? q : r) ? … : …`は、その`&&` / `||`相当の事実を運びます: それは`p && q`または`!p && r`を通じてtruthyであり、`p && !q`または`!p && !r`を通じてfalseyであるため、`(s.nil? ? false : x.finite?) ? x : 0.0`は`(!s.nil? && x.finite?) ? x : 0.0`と同様に`x`をナローイングします。リテラル`false`などの値が確定しているアームは、その真偽性が楽観的ルックアップに依存していない限り、その有効なエッジのみを寄与します。事実は最大2つのネストされた条件式まで導出されます;それ以上のスタックはナローイングを寄与しません。
- `unless a`は`if a`と同じ条件ファクトを使い、ブランチの宛先を入れ替えます。
- `case`、パターンマッチ、連鎖した`elsif`式は、後のアームに前のアームからの負のファクトを渡します。
- 三項演算子`a ? b : c`、修飾子`b if a` / `b unless a`、およびブロック形式は同一の構文要素です: それぞれが同一の条件の事実からそのアームをナローイングしなければならず（MUST）、条件式の値はそれが文であるか値であるか —— 引数、レシーバー、コレクション要素、または書き込みの右辺 —— にかかわらず同一でなければなりません（MUST）。Float比較のfalseyアームはあらゆる綴りでエントリー型を保持します。`!(x > c)`は`NaN`に対しても成り立つためです。
- `a && b`と`a || b`はあらゆる位置において同一の構文要素です: `x.finite? && x`の値は、それが文であるか値であるかにかかわらず同一でなければならず（MUST）、定数の左オペランドに対する短絡評価（`false && b`は`false`、`1 || b`は`1`）も同様でなければなりません（MUST）。動的キーを持つリテラルハッシュルックアップのように左オペランドのnilフリー性が楽観的である場合、その短絡評価は右オペランドを破棄してはなりません（MUST NOT）。ルックアップがミスしうるためです。Float比較のfalseyエッジはここでもエントリー型を保持します。

```ruby
def contradictory(foo)
  # `foo`が有限リテラルドメインと通常のString等価を持つと仮定します。
  if foo == "foo" && foo == "bar"
    p foo # Rigorの型: bot; このエッジは到達不能です。
  end
end
```

`&&`の右辺は、左辺の真ファクトが`foo`を`"foo"`にナローイングした後で解析されます。その後`foo == "bar"`の真エッジが`"foo"`と`"bar"`の積集合を取り、`bot`に正規化し、本体を到達不能としてマークします。Rigorは診断ポリシーに応じて比較または到達不能な本体で矛盾を報告できるべきです（SHOULD）。

`||`では、反対方向に同じ精度が適用されます:

```ruby
def impossible_after_or(foo)
  # `foo`が有限リテラルドメインと通常のString等価を持つと仮定します。
  if foo == "foo" || foo == "bar"
    p foo # Rigorの型は"foo"と"bar"の代替のみを含みます。
  else
    p foo # Rigorの型は"foo"と"bar"の両方を除外します。
  end
end
```

## Non-localな脱出の値

`return`、`next`、または`break`は、それ自身の位置では値を生成しません。その型は`bot`であり、union下で吸収されるため、分岐結合（branch join）は完了可能なアームのみに集約されます。それが運び出す値は、それが離脱する構文に属し、その構文の推論される値は、そのフォールスルー結果と解析が到達可能なすべてのそのようなアームのunionでなければなりません（MUST）:

- `return value`は囲むメソッドを脱出し、そのメソッドの推論される戻り値の型に結合します。ネストした`def`、lambdaリテラル、任意のレシーバーに対する`define_method`または`define_singleton_method`のブロック、および`Kernel`に到達する`lambda`のブロック（裸、`self`上、または`Kernel`上で呼び出される）は ── 直接的または`send`、`public_send`、`__send__`を通じて ── 障壁となり、それらのreturnは内側の定義に属します。他の任意のブロック内に書かれた`return`は、依然として囲むメソッドを脱出しそこに結合します（決して実行されないかもしれないブロックも含み、これは単に型を広げるだけです）。このルールはメソッドの戻り値型のすべての読み手を同様に拘束します: `rigor check`が呼び出し元に示すもの、および`rigor sig-gen`と`rigor annotate`が提案するもの（Issue [#1382](https://github.com/rigortype/rigor/issues/1382)）。
- `next value`は現在のブロック呼び出しを終了し、`value`をその呼び出しの結果とするため、**ブロックの**値型に結合します。単体の`next`は`nil`を寄与します。ネストしたブロック、lambda、`def`、またはループは、その配下に書かれた`next`の対象を変更し、そのような`next`は外側ブロックの値に結合してはなりません（MUST NOT）。
- `break value`はyieldを行っている**呼び出し（call）**を終了し、ブロックの値ではなくその呼び出しの値となります。ブロックの値型に結合してはなりません（MUST NOT）。呼び出しの推論される型は、calleeが生成する結果と到達可能なすべての`break`アームのunionでなければなりません（MUST）。単体の`break`は`nil`を寄与します。ネストしたブロック、lambda、`def`、またはループは、その配下に書かれた`break`の対象を変更します —— そのような`break`はその内側の構文に属し、外側の呼び出しに到達してはなりません（MUST NOT）。unionは精度フォールド（precision fold）の内部ではなくその上に位置するため、フォールドはブロックが決してbreakしないパスについて正確に応答する自由を保ちます。任意のcalleeはブロックを実行せずに戻る可能性があるため、calleeの結果はunionに残ります。唯一の例外は、戻る前に厳密に1回yieldすることが知られているcalleeであり、その場合、ブロックの到達不能な通常完了はそれを除去します（§「ブロック呼び出しタイミング」）。実行せずにブロックを保存する呼び出し —— `Kernel`に到達する`lambda { … }`や`proc { … }`、`define_method` / `define_singleton_method`、および`Proc.new`、`Thread.new` / `start` / `fork`、`Fiber.new`、`Enumerator.new`、`Hash.new` —— は`break`アームを一切持ちません: ブロックはその呼び出し中に実行されないため、その中の`break`は、保存されたブロックが後で実行された際にlambdaや定義されたメソッドから戻るか、または`LocalJumpError`を発生させ、呼び出しの値に結合してはなりません（MUST NOT）。

解析が到達不能と証明した分岐上のアームは決して取られず、何も寄与しません。*到達可能*なアームを落とすと、あたかもフォールスルーが完全な回答であるかのように報告され、プログラムが持たない精度として読まれてしまいます: `ops.all? { |o| next false unless o; true }`は`true`として型付けされ、述語が定数に畳み込まれ、正しいコードに対して警告が発せられてしまいます（[#841](https://github.com/rigortype/rigor/issues/841)）——そして`break`で書かれた同じ形状も、アームが決して呼び出しに到達しない場合に同様に警告を発してしまいます（[#853](https://github.com/rigortype/rigor/issues/853)）。

## yieldの値

`yield`は呼び出し元（CALLER）が提供したブロックを実行するため、その値はそのブロックの値となります。上記の3つの脱出構文は値を構文の*外部*へと運び出しますが、これは値を再び*内部*へと運び戻すものです。

- 既知の呼び出し元に代わってメソッド本体が再型付けされる場合（手続き間戻り値推論）、その本体内の`yield`は、その呼び出し元のスコープで計算された、当該呼び出し箇所で書かれたブロックの値型として型付けされなければなりません（MUST）。呼び出し元が不明な場合（`def`自体の単体解析）、`yield`は`untyped`として型付けされなければなりません（MUST）。
- ブロックの値が呼び出し元の戻り値に到達するのは、callee本体の通常の評価を通じてのみであり、メソッドがyieldを行うことを認識することによるものではありません: `def wrap; yield; end`はそれを返し、`def announce; yield; "done"; end`は`"done"`を返し、`rescue`アームや条件付き`yield`は他のいかなる本体と同様にunionされます。`yield`の存在からラッパーの戻り値を推論してしまうと、ラッパーが自身の値で代用している箇所で架空の型を捏造することになります。
- ブロック、lambda、またはループの内部に書かれた`yield`も、依然としてそれを囲む**メソッド**のブロックを指すため、それらの構文はここでは境界とはなりません（`next` / `break`に対して行う対象変更とは異なります）。ネストした`def`、`class`、`module`、または`class << self`の本体は新しいメソッドブロック束縛を開始するため、その内部の`yield`は外側の呼び出しのブロックを読み取ってはなりません（MUST NOT）。

これがなければ、全体の値をyieldするヘルパーから受け取るメソッドはすべての位置で`untyped`となり、`sig-gen`はそれを拒絶し、すべての呼び出し元がその不透明性を引き継ぐことになります —— 一方で、インラインで書かれた同一のロジックには型が付きます。スコープ付きの関心事（`with_run`、保存/復元、計装）は通常ラッパーとして書かれるため、この損失はより良い構造に従うものでした（[#720](https://github.com/rigortype/rigor/issues/720)）。

## サポートされているナローイングソース

サポートされているナローイングソースには以下が含まれます:

- リテラルとシングルトン値に対する信頼された等価および不等価チェック。
- `nil?`チェックとnil比較。
- 真偽性チェック（`nil`と`false`が偽ブランチをナローイングします）。
- `is_a?`、`kind_of?`、`instance_of?`、クラスとモジュールの比較。クラスが`Nominal`レシーバーと素であるガードは、アームが到達不能であることを報告することなくそのアームを`bot`にナローイングします（[クラスガード](#クラスガード)参照）。
- メソッド名が静的に既知の場合の`respond_to?`チェック。真ブランチはそのメソッドを欠いていると把握されているメンバーを脱落させます（[クラスガード](#クラスガード)参照）;可視性ルールは[structural-interfaces-and-object-shapes.md](../structural-interfaces-and-object-shapes/)を参照してください。
- グローバル変数または定数の読み取りに対するガード。ローカル変数をナローイングするのと同様にナローイングし、そのグローバル変数や定数を再バインドするコードが実行される可能性のある場所で復元されます（[グローバル変数と定数のガード](#グローバル変数と定数のガード)参照）。
- リテラルなSymbol/Stringキーに対する`Hash#key?` / `#has_key?`で、レシーバーがそのキーをオプショナルとして持つハッシュシェイプ（shape）の場合。真の分岐はキーを必須に昇格させるため、後続のインデックス読み取りはオプショナル性の`nil`を落とす（値自身の本質的な`nil`は保持される —— キーの存在は格納された値が非nilであることを含意しない）。偽の分岐は保守的なノーオペ。これは集合論的な`is_map_key`スタイルのキー存在リファインメントのRuby版だ。
- レシーバーが`Array[T]`の場合の`Array#empty?` / `#any?` / `#none?`（むき出し、ブロックも引数もなし）。「少なくとも1要素」を含意するエッジ —— `empty?` / `none?`の偽エッジ、`any?`の真エッジ —— はレシーバーを`non-empty-array[T]`にリファインするため、長さを返すメソッド（`size` / `length` / `count`）は`positive-int`を読む。反対側のエッジはノーオペ（`any?` / `none?`が偽でも空であることは含意しない）。非空（`tuple_size`スタイル）のコレクションリファインメントのRuby版だ。リファインメントはレシーバーの*束縛*ではなく*内容*を記述するため、レシーバーを空にし得るインプレースミューテーター（`clear`、`pop`、`shift`、`delete_if`、…）はそれを無効化しなければならない（MUST）: 束縛は`Array[T]`に戻って広がり、後続の`size`は基底の`non-negative-int`エンベロープを再び読む。そのような呼び出しを越えてリファインメントを保持すると`arr.size == 0`が定数に畳み込まれ、正しいコードに対して偽の常偽条件を報告してしまう。
- パターンマッチとcase解析。
- リーダーレシーバーに対する`gets` / `readline`条件、または暗黙的`self`に対する`gets`条件（そのエッジ上で`$_`をバインドします; [最終行（`$_`）のナローイング](#最終行_のナローイング)参照）。
- `rescue`節（`$!`と`$@`をバインドします）およびサブプロセス呼び出し（`$?`をバインドします; [レスキューとサブプロセスのグローバル](#レスキューとサブプロセスのグローバル)参照）。
- Rigorプラグインによって登録された述語メソッド。
- `RBS::Extended`アノテーションに記述されたアサーションとガード（[rbs-extended.md](../rbs-extended/)参照）。

## 負のファクト

負のファクトはファーストクラスのスコープファクトです。Rigorは後の診断を改善する場合、「nilではない」、「falseではない」、「このリテラルではない」、「この名前的クラスを持たない」といったファクトを保持すべきです（SHOULD）。

負のファクトは**ドメイン相対**です: 値のすでに既知の正のドメインから値を取り除きます。比較の右辺から新しい正のドメインを導入してはなりません（MUST NOT）。負のファクトの完全なセマンティクスと表示規則は[type-operators.md](../type-operators/)にあります。

Pythonの`TypeGuard`と`TypeIs`は述語効果の有用な参照点です。真ブランチのみをリファインする述語は`TypeGuard`に似ています。真ブランチと偽ブランチの両方をリファインする述語は`TypeIs`に似ています;内部的に偽ブランチは`A & ~R`のような補完との積集合として、または同等の差分型としてモデル化すべきです（SHOULD）。

## Ruby等価セマンティクス

Ruby等価はメソッドディスパッチです。`foo == "foo"`のような構文的比較は`foo.==("foo")`を呼び出し、任意のクラスがそのメソッドをオーバーライドできます（MAY）。Rigorは以下を区別しなければなりません（MUST）:

- `x.equal?(obj)`のような**同一性ファクト**（シングルトン同一性を証明できます）;
- 安定したRuby値テストである**nilとブーリアンチェック**;
- 有限の`String`、`Symbol`、`Integer`、`true`、`false`、レシーバードメインにすでに存在する`nil`の代替のように、ディスパッチターゲットが安定している**既知の組み込みドメインの等価ファクト**;
- 信頼された述語と等価メソッドに対して**RBSまたはプラグインが貢献した比較ファクト**;
- 解析器が値型をナローイングするのに十分なメソッド情報を持たない限り、最大でも関係的ファクトを生成すべき（SHOULD）**未知の等価メソッド**;
- `NaN`、符号付きゼロ、無限大、強制変換が網羅性と等価推論を誤って表現しやすくするため、デフォルトではリテラルナローイングを生成してはならない（MUST NOT）**浮動小数点比較**。数値リテラルに対する`Float`型のローカル変数の関係比較（`<`、`<=`、`>`、`>=`、`between?`）は、その**真値**エッジを比較が含意する`Float`範囲にナローイングしてもよく（MAY、`x > c` → `Float[c..]`、`x < c` → `Float[...c]`; [ADR-109](../../adr/109-ruby-native-range-notation/) WD5）、`!(x > c)`は`NaN`に対しても真となるため、偽値エッジではエントリー型を維持しなければなりません（MUST）。`x.nan?`はその偽値エッジのみを（`non-nan-float`へ）、`x.finite?`はその真値エッジのみを（`finite-float`へ）ナローイングしてもよいです（MAY）。

等価ナローイングは比較値のみから正のドメインを導入してはなりません（MUST NOT）。`foo`が生の`untyped`であれば、`foo == "foo"`は、Rigorがディスパッチされた等価メソッドに信頼されたナローイング効果があることを知らない限り、動的由来の関係的ファクトを持つ`Dynamic[top]`として`foo`を保持します。`foo`がすでに`"foo" | "bar"`として知られている場合、同じ比較は真ブランチを`"foo"`に、偽ブランチを`"bar"`にナローイングする場合があります（MAY）。

### 等価の信頼レベル

Rigorは等価ファクトを信頼レベルで分類すべきです（SHOULD）:

- **`equal?`からの同一性ファクト**は、観測された参照自体が安定している限り値ファクトです。
- **組み込みリテラルドメイン等価**は、既知のコアディスパッチターゲットを持ち、レシーバードメインがすでに互換性がある場合にのみ、すでに互換性のあるレシーバードメイン内でナローイングできます。
- **`Module`、`Class`、`Range`、`Regexp`、`===`ベースのcaseの挙動**は、一般的な等価として扱うのではなく、種別ごとの明示的なルールまたはプラグインファクトが必要です。
- **ユーザー定義の`==`、`eql?`、`===`、強制変換に敏感な比較**は、RBSメタデータまたはプラグインが真エッジと偽エッジの効果を宣言するまで関係的ファクトのままです。

初期の信頼された等価サーフェスは意図的に狭くなっています:

- `equal?`は観測された参照にバインドされた同一性ファクトを生成します。このファクトは、再代入、エイリアスエスケープミューテーション、未知の呼び出し、またはプラグイン宣言効果によって無効化されます。
- 組み込みリテラルドメイン等価は、`String`、`Symbol`、`Integer`、ブーリアン、`nil`の有限リテラルセットに対してのみ、かつレシーバーのディスパッチターゲットが既知でレシーバードメインがすでに互換性がある場合にのみ信頼されます。
- `Float`リテラル（等価）ナローイングはデフォルトで拒否されます。関係比較は上記のように真値エッジを`Float`範囲にナローイングします;診断のために関係的ファクトを保持してもよいです（MAY）。
- `Range`、`Regexp`、`Module`、`Class`、`===`ベースのcase挙動は、それ自体では一般的な値ナローイングファクトを生成してはなりません（MUST NOT）。値ドメインをナローイングする前に特定のナローイングルールまたはRBS/プラグイン効果が必要です。
- ユーザー定義の`==`、`eql?`、`===`は、明示的なRBSメタデータ、`RBS::Extended`フロー効果、または必要な安定性または純粋性の仮定とともにプラグイン宣言の真エッジと偽エッジのファクトを通じてのみ、関係的ファクトから値ファクトに昇格されます。

### Regexpマッチ述語ナローイング

上記の信頼レベルが先送りする`Regexp`の「特定のナローイングルール」とは、`=~`マッチ述語ルールのことです。`subject =~ pattern`（または`pattern =~ subject`）述語はそのエッジでRubyの正規表現マッチのグローバル変数をバインドします。条件がすべて補間のない正規表現リテラルである対象を持つ`case`の`when`節は、以下の真値エッジと同様にその本体でそれらをバインドします;複数の正規表現条件（`when /a(b)/, /(c)/`）がある場合は、グループが互いに異なるため、`$~`、`$&`、`` $` ``、および`$'`のみをバインドします。正規表現リテラルを別の条件と混在させた節（`when "x", /(a)/`）、および対象のない`case`の節も、Rubyがその正規表現にマッチせずに本体にエントリする可能性があるにもかかわらず、それらをバインドします（[#1486](https://github.com/rigortype/rigor/issues/1486)）。これらは、RBSまたはプラグイン効果なしで値ナローイングファクトを生成する唯一のRegexp構文です。左オペランドが名前付きグループを持つ正規表現リテラルである`=~`（`/(?<num>\d+)/ =~ s`）は、その名前付きローカル変数をバインドしますが、グローバル変数はまだバインドしません（[#1482](https://github.com/rigortype/rigor/issues/1482)）。`subject !~ pattern`は結果を反転して同じマッチを実行し、そのレシーバーが設定する制限の範囲内で、入れ替えられたエッジ上でグローバル変数をバインドします（[#1379](https://github.com/rigortype/rigor/issues/1379)、以下参照）。どのマッチとも同様に、以前のナローイングも無効化します（以下参照）。

マッチグローバル変数がグローバル変数の型の出所の中でどこに位置するか、および各特殊変数が存在するスロットについては、[global-variables.md](../global-variables/#特殊変数スロット)に記載されています。

- **パターンオペランドの認識**。ちょうど1つのオペランドが正規表現パターンに解決されなければなりません（MUST）: 構文的な正規表現リテラルか、型が値固定された`Regexp`リテラルである定数参照のいずれかです（したがって`RE = /.../`と`RE = Regexp.new(...)`は定数を通じて参加し、解析器が定数読み取りに使うのと同じレキシカル定数ルックアップで解決されます）。このルールは次の場合には辞退しなければなりません（MUST、どちらのエッジでもナローイングしない）: どちらのオペランドも正規表現に解決されないとき、両方が解決されるとき（バインドすべき文字列サブジェクトがない）、定数オペランドが複数の値のユニオンとして型付けされるとき（二度代入された定数で、単一のパターンを固定できない）、または解決されたパターンが拡張（`/x`）モードでコンパイルされているとき —— コメントや自由間隔の`(`をキャプチャグループと区別できず、参加解析にとってそのグループインデックスが信頼できないため。
- **真値エッジ**（マッチ成功 —— `=~`が`Integer`位置を返した）: `$~`は`MatchData`にナローイングされる; `$&`、`` $` ``、`$'`は`String`にナローイングされる（グループ化に関係なく、どの成功マッチでも非nilである）; *無条件に参加する*番号付きグループ`$N`はそれぞれ`String`にナローイングされる; `$+`（最後にマッチしたグループ）は少なくとも1つのグループが無条件に参加する場合にのみ`String`にナローイングされる。
- **偽値エッジ**（マッチなし —— `=~`が`nil`を返した）: `$~`、すべての無条件な`$N`、および`$+`（ゲートインされている場合）は`nil`にナローイングされる。
- **`!~`**。`subject !~ pattern`は`Kernel#!~`であり、`!(subject =~ pattern)`を返し、呼び出し元のフレームでマッチを実行します。これは`=~`と同じパターンオペランドを認識し、同じケースで辞退します。その偽値エッジはマッチエッジです: 上記の真値エッジと同様にバインドし、`\A…\z`でアンカーされたパターンが指定するレシーバー全体のリファインメントを含みます（サブジェクトが`String`であるか`nil`になり得る`String`であることが既知でない限り除外されます。型なしまたは`Symbol`のサブジェクトは`Symbol`である可能性があり、その`String`リファインメントはそれを記述しないため、このエッジに到達することはありません）。したがって`return if line !~ /\A(\w+)=/`の後、`$1`のコピーは`String`を読み取ります。その真値エッジは非マッチエッジであり、上記の偽値エッジと同様にバインドします。レシーバーの`=~`がどのエッジが成立するかを決定します:
  - パターンがレシーバーである場合（`pattern !~ subject`）、`Regexp#=~`は`nil`サブジェクトを含め両方の結果で`$~`を設定するため、両方のエッジがナローイングされます。
  - レシーバーの型のすべてのメンバーが`String`または`Symbol`である場合、両方のエッジがナローイングされます: `String#=~`および`Symbol#=~`は失敗したマッチで`$~`をクリアします。
  - `NilClass#=~`は`nil`を返し、`$~`を元のまま残すため、`nil`になり得るレシーバーは以前のマッチがバインドされたまま非マッチエッジに到達します。メンバーがString、Symbol、`nil`、または`Dynamic`（型なし、またはそれらのクラスの静的ファセットを持ち、実行時に`nil`を除外しないもの）である場合、マッチエッジのみがナローイングされます。非マッチエッジは、呼び出しがそれらを再バインドした可能性があるため、グローバル変数をナローイングされないまま（`String | nil`、`$~`は`Dynamic[top]`）維持します。マッチエッジでは、`=~`ルールが型なしサブジェクトに対して仮定するのと同様に、型なしレシーバーはStringまたはSymbolであると仮定されます;その型なしスロットにRubyで定義された`=~`を持つ実行時オブジェクトはその仮定を破り（次の項目）、その場合エッジはRubyが`nil`のまま残す可能性のあるグループに対して`String`を読み取ります。
  - その他の任意のレシーバーはRubyで`=~`を定義している可能性があり、これは呼び出し元ではなく自身のフレームで`$~`をバインドするため、どちらのエッジもナローイングされません。`nil`レシーバーでマッチすることなく`nil`を返すセーフナビゲーション`recv&.!~(pattern)`も同様です。

  `=~`ルールはまだこのようにサブジェクトをチェックしません: SymbolサブジェクトをStringへとリファインし、`nil`になり得るサブジェクト上で非マッチエッジをバインドします（[#1494](https://github.com/rigortype/rigor/issues/1494)）。
- **参加**は一方向的で保守的です。番号付きグループが無条件に参加するのは、それ自体もそれを囲むどのグループもゼロを許容する量指定子（`?`、`*`、`{0,…}`）を持たず、かつ選択（alternation、`|`）の分岐の内側に位置しない場合に限ります; `(?:…)`と先読み・後読みはキャプチャしません。オプショナルであるか、選択で到達可能であるか、その他疑わしいグループは条件付きとして扱われます —— その`$N`は両エッジで`String | nil`のままです —— 全体のマッチが成功しても、実行時にそのようなグループが未マッチ（`nil`）のままになり得るからです。`$+`も同じゲートに従います: ゼログループまたは全グループがオプショナルのパターンでは`String | nil`のままになります。
- **無効化**。マッチグローバル変数はフレームローカルなファクトです。Rubyはそれらを、マッチを実行するメソッド本体（またはクラス、モジュール、ファイル本体）の特殊変数スロットに保持します。ブロック、およびその本体で作成されたクロージャ —— ラムダリテラル、`lambda {}`、`proc {}`、`Proc.new {}` —— は通常同じスロットに到達するため、それが実行するマッチは本体のグローバル変数を再バインドします;新しいスレッド、ファイバー、またはラクターのルートブロックは到達しません（以下参照）。ネストした`def`、クラス、またはモジュール本体は独自のスロットを持ち、Rubyで定義されたメソッドへのすべての呼び出しも同様です: 呼び出し先の本体でのマッチは呼び出し先のスロットを再バインドし、呼び出し元のスロットは決して再バインドしないため、述語とグローバル変数の使用の間の`log("parsed")`、`warn "debug"`、または`self.log("x")`はナローイングを維持します（[#1364](https://github.com/rigortype/rigor/issues/1364)）。呼び出し元のスロットは、呼び出し元に代わってマッチを行うCコード、そのフレームで評価されるコード、およびそれが作成したブロックまたはクロージャによってのみ到達されます。述語とグローバル変数の使用の間に介在し、それに到達する可能性のある呼び出しは、ナローイングを無効化します:
  - 呼び出されるメソッドとそのオペランドによって読み取られる、スロットに代わってマッチを行う呼び出し（レシーバー不問、[#1365](https://github.com/rigortype/rigor/issues/1365)）。この読み取りは、このルールの前に解析器がその呼び出しで忘却したかどうかに依存し、Rubyが再バインドするナローイングを新たに維持する呼び出しがなく、推測に基づいて新たに忘却する呼び出しもないようにします:
    - `=~`、`!~`、`match`、`sub`、`sub!`、`gsub`、`gsub!`、`scan`は、実行場所や引数に関係なくカウントされます: Stringパターンを指定した`sub`や`scan`もグローバル変数を設定し、`!~`は`=~`を実行します。
    - `[]`、`slice`、`slice!`、`index`、`rindex`、`partition`、`rpartition`、`split`、`===`、`grep`、または`grep_v`という名前の文または代入自体の呼び出し（および、暗黙的selfまたは`self.`呼び出しの場合、`start_with?`、`byteindex`、`byterindex`、`[]=`、`~`、`any?`、`all?`、`none?`、`one?`、eval、または`send`）は名前だけで忘却しており、構文上マッチできないことが証明されない限り依然として無効化します。ルックアップは、すべての引数が非Regexpリテラルである場合にナローイングを維持します: Symbol、補間のないString、数値、`nil`、`true`、`false`、またはそれらの範囲; `[]=`の場合は格納される値ではなくインデックス引数が読み取られます。したがって`val = row[:name]`、`csv.split(",")`、`list.index(3)`、`s.slice(0, 2)`はナローイングを維持し、Rubyはそれぞれの間で`$1`を維持します。区切り文字なし、または`nil`の`split`（`row.split`、`row.split(nil, 2)`）は`$;`で分割し、これがRegexpを保持している場合は`$~`を再バインドします; Regexpフィールドセパレータは稀であり、すべての`line.split`で忘却すると正しいコードが報告されてしまうため、ファイルがどこにも`$;`（または`$-F`）を書き込まない限りナローイングを維持します。別のファイルで設定された`$;`、`ruby -F`による設定、または演算子書き込み（`$; ||= re`）や多重代入（`$;, x = re, 1`）を通じてのみ設定された`$;`はギャップです。`match?`は決して無効化せず、ブロックなしの`grep`や`grep_v`（呼び出し元のグローバル変数を変更しない）、そのようなリテラルまたはクラスやモジュールを指定する定数に対する`===`（`String === s`）も無効化しません。その他の引数またはレシーバーは、推論された型に関係なく依然として無効化します: `String`を示すフロー型は値がRegexpである間に古くなる可能性があり（[#1380](https://github.com/rigortype/rigor/issues/1380)）、`row[key]`、`u.index(@pattern)`、`u.split(pat)`、`Regexp`サブクラスに対する`u.index(RebindRegexp.new(src))`、およびその中での`self === s`は依然として無効化します。暗黙的selfのevalと`send`は以前と同様に無効化します。
    - その他の呼び出しは、このルールの前には決して無効化しなかった位置で実行され、マッチすることが既知である場合にのみ無効化します: 明示的レシーバーの`start_with?`、`byteindex`、`byterindex`、`any?`、`all?`、`none?`、または`one?`、文自体の呼び出し以外の場所でのルックアップでRegexpであることが既知の引数を持つもの;ブロック形式で同じ条件の`grep`および`grep_v`; Regexpであることが既知のインデックスを持つ`[]=`、またはインデックス`||=`、`&&=`、`op=`（`s[re] = v`、`s[re] += v`）; Regexpであることが既知のレシーバーに対する`===`および単項`~`（Integerに対する`~n`はビット否定）;ファイルが既知のRegexpを`$;`に書き込む場合の、区切り文字なしまたは`nil`の`split`;コードのStringがマッチする可能性のある明示的レシーバーの`eval`、`instance_eval`、`class_eval`、または`module_eval`、および解析器が読み取れないコードの`binding.eval`（`binding`呼び出しで終わるレシーバー、および`send`経由）または`Kernel.eval`（これらはこのフレームでコードを実行するために存在するため、以下参照）;これらのメソッドのいずれかを指定し、名前の後に渡す引数を持つ明示的レシーバーの`send`、`__send__`、または`public_send`（`u.send(:match?, re)`ではなく`u.send(:=~, re)`）、または計算された名前に対してRegexpであることが既知の引数が渡されるもの（その名前が補間された属性ライター`"#{name}="`である場合を除く）。オペランドが*Regexpであることが既知*であるとは、正規表現リテラル、`Regexp.new` / `.union` / `.compile`、要素がそうであるsplat、または推論型が`Regexp`もしくは環境が`Regexp`の下に配置するクラス、そのようなメンバーを持つユニオン、または静的ファセットがそうである`Dynamic`である場合です。`Dynamic[top]`は該当しません: `h[k] = 1`、`x = [h[k], 1]`、`h[k] += 1`、`out << row[key]`、`obj.public_send(meth)`、`sock.send(packet, 0)`は以前と同様にナローイングを維持します。コードのStringが*マッチする可能性がある*とは、パース可能なリテラルであり、その文がブロック本体がマッチする可能性のあるもの（以下参照）を内部の`def`やクラスの外側に保持している場合、または各補間が名前を表すものとして同様に読み取られる補間文字列である場合です。したがって`klass.class_eval("def foo; end")`やメソッドを定義する`class_eval`ヒアドキュメントはナローイングを維持します; `Kernel.eval('"zz" =~ /(q)/')`は維持しません。パースできないリテラルは実行前に例外を発生させます。解析器は変数のコード、各補間が名前を表すとしてもパースできない補間String、64 KBを超えるコード、256ブラケットより深くネストしたコード、またはスキャンがスタックオーバーフローを起こすコードを読み取ることはできません。そのようなコードは上記のように`binding.eval`または`Kernel.eval`としてカウントされます。そのようなコードの`instance_eval`、`class_eval`、または`module_eval`は、テキストに何が含まれていてもカウントされません: これはメソッドを定義するための一般的なイディオム（`klass.class_eval(code)`）であり、忘却すると正しいコードが報告されてしまうため、そのようなコード内でのマッチはギャップとなります。
  - 引数がこのフレームでマッチを実行する可能性がある暗黙的selfまたは`self.`呼び出し（引数内の呼び出しは上記のルールでカウントされない場合でも）: 名前テーブルが忘却した呼び出し（上記2番目の項目に挙げたもの、レシーバー不問）で構文上マッチを含まないことが証明されないもの、マッチメソッドを指定するSymbolまたはStringリテラル（`inject(:=~)`、メソッドがこのフレームのCから実行する可能性がある）、`yield`、または次のルールの広範な読み取りの下でブロック本体がマッチする可能性のある構文（以下参照）。これは、このルールの前に暗黙的self呼び出しが忘却したすべての引数のうち、リテラルで証明されたもの以外を維持します: `log(row[:name])`はナローイングを維持し、`log(row[key])`は維持しません;
  - 解析器が追跡しないコードにスロットを渡す本体内の暗黙的selfまたは`self.`呼び出し。これは呼び出し先フレームルールの前にすべての暗黙的self呼び出しが行ったのと同様に無効化します。これは、マッチする可能性のある本体を持つブロックまたはラムダリテラルを保持する本体（広範に読み取られます。ブロックが渡されたメソッドがそれを保持し、後の呼び出しから実行する可能性があるため。`on { |l| l =~ re }` … `emit("q")`）です。広範な読み取りは、ブロック本体がマッチする可能性のあるもの（以下参照）をカウントし、さらにRegexpである可能性のある任意の引数を持つルックアップ（`[]`、`index`、`split`、`start_with?`、…）もカウントします。これは非Regexpリテラルまたは非Regexp値にバインドされた定数以外のすべてです: ブロックパラメータが該当し、別のファイルで定義されたRegexpなど解決されない定数（[#1373](https://github.com/rigortype/rigor/issues/1373)）も、そこおよび`when` / `in`値、そのsplat、または`===`レシーバーとして該当します。任意のレシーバーおよび引数の型に関係なく、引数を持つ`!~`、`~`、`start_with?`、`byteindex`、`byterindex`、`[]=`、`any?`、`all?`、`none?`、`one?`、Stringの`eval`、および名前が計算されるか上記のメソッドのいずれかを指定する`send`をカウントします。また、メソッド自体の`&block`に対する`yield`、`call`、`()`、または`yield`（このフレームで呼び出し元のC関数procを実行する可能性がある）もカウントします。同じフォールバックは、任意の綴りで`binding`を呼び出す本体（`binding`、`proc {}.binding`、`send(:binding)`、計算された名前を持つ`send`）も対象とします。その`Binding#eval`はどこで呼び出されてもこのフレームで実行されるためです。また、メソッド自体のブロックを転送する本体（`&blk`、無名の`&`、`...`。C関数procである可能性がある）も対象とします。本体がフレームをスタンプしない場合、暗黙的self呼び出しも以前と同様に無効化します。明示的レシーバーの呼び出しは、すべての本体において他のルールのみによって読み取られます;
  - 自身のブロックリテラルの本体がマッチを実行する可能性のある呼び出し（以下で定義）;
  - この本体で作成されたprocである可能性のある`&expr`ブロック引数を渡す呼び出し。これはSymbolリテラル（`=~`、`!~`、`match`、`sub`、`sub!`、`gsub`、`gsub!`、`scan`、または`===`を指定する場合を除く）、無名の`&`、または本体が再バインドもシャドウもしていないメソッド自体の`&block`パラメータ以外のすべてです;最後の2つは呼び出し元が作成したブロックを転送します;
  - マッチを実行する可能性のある本体を持つクロージャを作成する本体内の任意の呼び出し —— ラムダリテラル、または後で実行するためにブロックを保持する呼び出しのブロック（`lambda`、`proc`、`Proc.new`、`define_method`、…）で、本体内またはメソッドのパラメータデフォルトにあるもの —— クロージャは後の任意の呼び出しを通じて実行できるためです。このルールは、クロージャの後の呼び出しだけでなく、本体内のすべての呼び出しを対象とします。ループ内では、クロージャの前に記述された呼び出しがクロージャの後に実行される可能性があるためです。

  文はこのフレーム内で自身の呼び出し以上のものを実行します。Rubyはメソッドの前に呼び出しのレシーバーチェーンと引数を評価し、文の配列およびハッシュリテラル値、補間、`rescue`修飾子、定数値、インデックスまたは属性の複合書き込み、および`super`または`yield`引数を同じフレーム内で評価します。このルールの前にはそこでの呼び出しは無効化されなかったため、それぞれ第1ルールの第3項目が呼び出しを読み取るのと同様に読み取られ、それらに対するブロックリテラルまたはブロック引数はブロックルールによって読み取られます: `out.push(line.sub(re, ""))`、`u.sub(re, "").size`、`[s.index(re)]`、`x = { a: items.find { |i| i =~ re } }`、`"#{items.map { |i| i =~ re }}"`はそれぞれ無効化します。Rubyは文自身のメソッドの前にそれらを実行するため、そのメソッドのブロックは無効化されたナローイングから開始します（`s.sub(re, "").each_char { $1 }`、`[u.index(re)].map { $1 }`）。そこでの暗黙的self呼び出しも同様に読み取られます。メソッドがマッチしなくても暗黙的self呼び出しがスロットに到達するものとして扱う2つのルールは、文自身の呼び出しに留まります（以前に適用されていた場所です）;そうでなければ、フォールバックが対象とするすべての本体で`value.upcase`などの属性読み取りが無効化されてしまうためです。各呼び出しの読み取りはその呼び出し単独がスロットを再バインドする可能性があるかどうかを示し（それが何を行うかの過剰近似）、呼び出しの答えはその周囲のオペランドが書き込むかどうかに依存しません: `$stdout.puts(Integer(v = $2))`は、`$stdout.puts(Integer($2))`と同様に`$1`のナローイングを維持します。

  ブロックまたはクロージャの本体は、ネストした`def`、クラス、またはモジュール本体、あるいはルートブロック（以下参照）の内部を除き、以下のいずれかを保持している場合に*マッチを実行する可能性がある*とみなされます:
  - `=~`、`!~`、`match`、`sub`、`sub!`、`gsub`、`gsub!`、または`scan`の呼び出し（引数に関係なくグローバル変数を設定します。`!~`は`=~`を実行します）;
  - Regexpであることが既知の引数を持つ`[]`、`slice`、`slice!`、`index`、`rindex`、`partition`、`rpartition`、`split`、`start_with?`、`byteindex`、`byterindex`、`any?`、`all?`、`none?`、または`one?`の呼び出し: 正規表現リテラル、それにバインドされた定数、ブロックが記述されたスコープでそれにバインドされたローカル変数またはインスタンス変数、あるいは`Regexp.new` / `.union` / `.compile`。`grep`と`grep_v`は同じ条件でカウントされますが、ブロック形式でのみカウントされます。ブロックなしでは呼び出し元の`$~`を変更しないためです。ブロック内ではこれらの名前は圧倒的にHash、Array、およびStringのルックアップであり、スキャンはその引数を型付けしません（ブロック外では上記のようにフロースコープが型付けします）。したがって他の方法でルックアップに到達するRegexpはカウントされません。ブロックパラメータとして到着するか、ブロック内で代入されるか、メソッドの戻り値から来るRegexpは既知のギャップです;
  - Regexpである可能性のあるレシーバーに対する`===`;
  - サブジェクトを持つ`case`の`when`条件、または`in` / `=>`パターン内の値で、Regexpである可能性のあるもの: 正規表現リテラル、ピン留めされた式またはその他の非定数式、Regexpにバインドされた定数、あるいはそれを保持する定数のsplat。以下はカウントされません: Regexpではないリテラル;それ以外のもの（クラスまたはモジュール、コレクション、その他の任意の値）にバインドされた定数;および解決されない定数（クラスとして読み取られます）。別のファイルで定義されたRegexp定数は現在解決されません。ファイル間定数センサスがRegexpリテラルを公開しないためであり、カウントされません;そのギャップは[#1373](https://github.com/rigortype/rigor/issues/1373)で追跡されています。サブジェクトのない`case`は`===`を実行せず、パターンの`if` / `unless`ガードは通常のコードであり、本体の残りの部分と同様にスキャンされます;
  - 単独の正規表現条件、`$~`への書き込み、または上記のような`&expr`ブロック引数。

  要素がRegexp引数を渡すルックアップを指定するSymbolブロック引数（`&:[]`、`&:index`）もグローバル変数を再バインドします;これはカウントされず、実際には稀な既知のギャップです。

  スロットに到達する一部のコードは認識されません:
  - `yield`、およびメソッド自体の`&block`に対する`call`、`()`、または`yield`（`blk.call(x)`）。これらは呼び出し元がC関数procを渡す場合にこのフレームを再バインドします: `"zz", /(q)/`をyieldする`y(s, &:=~)`は`y`の`$1`をnilのままにします。これらは文の位置でもブロック本体でもそれ自体では無効化しません。それらをカウントするとマッチと読み取りの間でyieldを行う正しいコードが報告されてしまい、そのようなメソッドに渡されるマッチメソッドのSymbol procは稀であるためです。本体が渡すブロックまたはラムダの内部では、これらは本体の暗黙的self呼び出しを上記のフォールバックに戻します;
  - 上記の名前以外のC実装メソッド（ネイティブ拡張のものなど）、明示的レシーバーでの`inject(:=~)`または`reduce(:=~)`、およびC実装マッチメソッドの`Method#call`または`UnboundMethod#bind_call`（`"".method(:sub).call(re, "")`、`String.instance_method(:=~).bind_call(s, re)`）。これらはこのフレームでCからマッチメソッドを実行します;
  - [#1365](https://github.com/rigortype/rigor/issues/1365)の前に無効化されなかった位置 —— オペランド、インデックス書き込み、名前テーブル外の明示的レシーバー組み込み、`send`、または`eval` —— で、解析器がそれを示すことができないRegexpである引数: `Dynamic[top]`（アノテーションのない`pattern`を持つ`[u.index(pattern)]`）、環境が`Regexp`の下に配置しないソースでのみ定義されたRegexpサブクラス、転送された`...`、および解析器が読み取れない明示的レシーバーの`instance_eval`、`class_eval`、または`module_eval`のコード（`klass.class_eval(src)`、または上記の境界を超えるリテラル）、あるいは補間が注入するもの。これらは以前のすべてのそのような位置と同様にナローイングを維持します;
  - ブロックまたはクロージャ本体の内部で、Regexpインデックスを持つ`[]=`、単項`~`、マッチメソッドを指定するか計算された名前を持つ`send`、およびStringの`eval`。上記のブロックスキャンはこれらを読み取りません（[#1377](https://github.com/rigortype/rigor/issues/1377)）。明示的レシーバーのevalが実行するコードはブロックスキャンの条件で読み取られるため、同じギャップを持ちます;
  - 上記のフォールバックが対象とする本体内のオペランドにおける暗黙的self呼び出し（`on { |l| l =~ re }`の後の`$stdout.puts(emit("q"))`）。これはそれが呼び出すもの単独によって読み取られます;
  - それを再バインドするオペランドよりも同じ文の後ろにあるグローバル変数の読み取り（`log(s.sub(re, ""), $1)`）。これは文の前からのナローイングを読み取ります。オペランド自体は文が開始するスコープで型付けされるためです。また、`&&`または`||`条件の右オペランド（結合エッジは左オペランドの`=~`ナローイングを維持します、`if s =~ re && u !~ other`、[#1376](https://github.com/rigortype/rigor/issues/1376)）も同様です;
  - 明示的レシーバー上のメソッドによって保持され、それを通じて実行されるブロック（`bus.on { |l| l =~ re }` … `bus.emit("q")`）。ルートブロック（以下参照）の内部で作成されたものを含みます（[#1400](https://github.com/rigortype/rigor/issues/1400)）;
  - 与えられたブロックからこのフレームのバインディングを取得する呼び出し先。空のブロックであっても`Proc#binding`で許可されます（`cap_binding`が`blk.binding.eval(src)`を実行する`cap_binding { }`）;
  - C実装マッチメソッドへの`super`（`String`サブクラスでの`def sub(*) = super`）;
  - メソッド自体のブロック以外を通じて呼び出されるC関数proc（`m = :=~.to_proc; m.call(s, re)`）。

  マッチを実行する可能性のあるブロック本体、またはそのようなクロージャを作成する本体内の任意のブロック本体は、ブロックの外側からのナローイングを読み取りません。以前の反復がグローバル変数を再バインドした後に実行される可能性があるためです。呼び出しの名前が`tap`、`then`、または`yield_self`であるブロックのエントリは、呼び出し先フレームルールの前にすべてのブロック本体が読み取られていた狭い条件で本体を読み取り、`!~`なし、`start_with?`、`byteindex`、`byterindex`、`any?`、`all?`、`none?`、`one?`なしであるため、そのエントリは以前のままになります。名前だけではそのようなブロックが1回実行されることを示すことはできません: プロジェクト独自の`then`がブロックを保持する可能性があり、ループは呼び出しを再度実行します（[#1375](https://github.com/rigortype/rigor/issues/1375)）。本体がマッチする可能性がある場合、呼び出しはその後も依然として無効化します。以下の2種類のブロックを除き、他のブロック本体は外側のナローイングを読み取ります。モデル化されていない既知の例外が1つあります: 呼び出しが`$~`を独自のマッチに設定した後に実行される`gsub`、`gsub!`、`sub`、`sub!`、`scan`、`grep`、または`grep_v`のブロック、および記述された場所ではなく呼び出されたときに実行されるラムダまたはproc本体です（[#1371](https://github.com/rigortype/rigor/issues/1371)）。

  2種類のブロックは、ナローイングの内容やブロックがマッチする可能性があるかどうかに関係なく、記述された場所で本体のナローイングを読み取りません（[#1361](https://github.com/rigortype/rigor/issues/1361)）:
  - *ルートブロック*: コアクラス（`Thread`または`::Thread`など。その名前のプロジェクト独自のクラスに解決される定数はカウントされません）を指定する定数に対する`Thread.new`、`Thread.start`、`Thread.fork`、`Fiber.new`、または`Ractor.new`のブロック、リテラル、または`&expr`引数です。これは新しいスレッド、ファイバー、またはラクターのルートとして実行され、Rubyはその実行コンテキスト独自の特殊変数スロットをブロックおよびその内部にネストされたすべてのブロックのために保持するため、それらは`$~`および`$1`をnilとして読み取ります: `s =~ /(\d+)/; Thread.new { $1 }.value`は`nil`であり、`Fiber.new { $1 }.resume`および`Ractor.new { $1 }.value`も同様です。同じ理由で、そのコードが実行するマッチは作成元本体のグローバル変数を決して再バインドしません。ルートブロックは呼び出し自身のブロックとして、文のレシーバーチェーンや引数内のブロックとして、あるいは別のブロックの本体内部で無効化することはなく、マッチを実行する可能性のあるクロージャとしても、暗黙的selfフォールバックに対してもカウントされません。したがって`Thread.new { "zz" =~ /(q)/ }.join`はナローイングを維持し、述語の前に格納され述語の後に再開されたファイバーも同様です（`f = Fiber.new { "zz" =~ /(q)/ }; s =~ /(\d+)/; f.resume; $1`は`"1"`です）。`&expr`ルート引数の式はブロックではありません: Rubyはスレッドやファイバーが開始する前に作成元本体でそれを評価するため、その中でのマッチは任意のオペランドと同様に無効化します（`Thread.new(&handlers.fetch(name.sub(re, "")))`）。ルートブロックの内部で作成されたラムダ、保持されたブロック、または`binding`は、本体内の他の場所と同様に依然としてカウントされます: 作成元スレッドに戻されて、本体のスロットとともにそこで実行される可能性があります（`Thread.new { -> { "zz" =~ /(q)/ } }.value.call`は本体の`$~`を再バインドします）。ルートブロックはマッチグローバル変数が非バインドの状態でエントリしなければならず（MUST）、エントリされた`Thread.new { … }`ブロック内の`k = $1; k.upcase`は、実行時と同様にnilの可能性のあるレシーバーを読み取ります。静的リーダーが見ることができない2つの事象がルールを破ります（明記されたギャップ）: `Thread#initialize`または`Fiber#initialize`にラッパーをprependし、ユーザーのブロックを呼び出す独自のブロックを`super`に渡すgem（これはもはやルートではなく、作成元本体のスロットを読み取り再バインドします）;および解析器が見えない場所で再定義された`Thread`、`Fiber`、または`Ractor`定数（`Object.const_set`、解析しないファイル）。
  - レシーバー不問の`define_method`または`define_singleton_method`のブロック。これはメソッドが呼び出されるたびにメソッド本体として実行され、その時点での定義元本体のスロットを読み取り、各呼び出し独自のマッチもそのスロットに書き込むため、メソッドが定義された場所でのナローイングは本体が読み取る内容を証明も反駁もしません。ブロックが記述された場所でナローイングされたグローバル変数は、本体内で`Dynamic[top]`として読み取られなければならず（MUST）、そこでナローイングされていないものは非バインドのままになります。本体が読み取るスロットはガードのものと正確に一致することがよくあります: 動的ファインダーのイディオムは、`name.to_s =~ /\Afind_by_(\w+)\z/`の`method_missing`ガード内で`define_singleton_method(name) { |v| where($1.to_sym => v) }`によって`find_by_email`を定義し、その後のすべての呼び出しはそのガードの`$1`を読み取りますが、本体自体の失敗したマッチや定義元本体での後のマッチはそれをnilのままにします。解析器はどちらであるかを追跡しないため、本体は読み取りをナローイングも報告もしません。ルートブロックとは異なり、定義元ブロックはスロットを共有するため、依然としてマッチを実行する可能性のあるクロージャです（上記参照）。

  `Enumerator.new`のブロックはどちらでもありません。ルートがブロックではない内部ファイバーで実行されるため、他のブロックと同様に作成元本体のグローバル変数を読み取り再バインドします: `Enumerator.new { |y| "zz" =~ /(q)/; y << 1 }.to_a`の後、およびそのようなエニュメレータに対する`e.next`の後、`$1`は`nil`です。`$_`はマッチグローバル変数と同様に両方の種類のブロックに入ります（[最終行（`$_`）のナローイング](#最終行_のナローイング)を参照）。`$!`、`$@`、`$?`は[レスキューとサブプロセスのグローバル](#レスキューとサブプロセスのグローバル)に記載されているように入ります: ルートブロックには`$!`と`$@`が非バインドで入り、ファイバーでない限り`$?`も非バインドで入ります。定義元本体には、記述された場所でバインドされていたそれぞれが`Dynamic[top]`として読み取られます。

  ブロックとは別に、失敗した正規表現の`when`アームまたは`in`パターンは`case`の後に`$~`をnilのままにしますが、このナローイングはまだモデル化されていません（[#1372](https://github.com/rigortype/rigor/issues/1372)）。

  後続の成功した`Regexp.last_match`の参照は、それらを再導出するのではなく、同じ証明済みマッチのバインディングを観測します。

### 最終行（`$_`）のナローイング

最後に読み取られた行である`$_`は、マッチグローバル変数と同じ特殊変数スロットに存在し（[#1359](https://github.com/rigortype/rigor/issues/1359)）、前節のフレームルールに基づくフレームローカルなファクトです: メソッド、クラス、モジュール、またはファイルの本体は独自のスロットを持ち、その本体で作成されたブロックまたはクロージャはそれを共有し、Rubyで定義されたメソッドへの呼び出しはそのメソッドのスロットに書き込んで呼び出し元のスロットには決して書き込まず、スレッド、ファイバー、またはラクターのルートブロックは独自のものを持ちます。`$_`への書き込みは、それを実行する本体とその本体のブロックをバインドします。他の本体にシードしてはなりません（MUST NOT）: トップレベルでの`$_ = "top"`の後、メソッド本体の`$_`は非バインドのままであり（Rubyはそれを`nil`で開始するため）、非バインドの`$_`は`Dynamic[top]`として読み取られます。宣言されたグローバル変数が読み取られた後もそうし続けなければなりません（MUST、[#1366](https://github.com/rigortype/rigor/issues/1366)）: 辞退または忘却されたすべてのリーダーは`$_`を非バインドのまま残し、そこでのRBSの`String?`は正しいコードを報告してしまいます（[ADR-117](../../adr/117-standard-streams-typed-by-idiom/) WD6）。

- **リーダー**。C実装のリーダーは、呼び出し元の`$_`をそれが返す値に設定します: `Kernel#gets`および`#readline`、ならびに`IO`およびそのサブクラス（`File`、ソケット）、`StringIO`、`ARGF`、`Zlib::GzipReader`の`gets` / `readline`。入力の終端で`gets`は`nil`を返し、`$_`は`nil`になります; `readline`は`EOFError`を発生させる前に`$_`を`nil`に設定します。`IO.foreach`はyieldする各行に`$_`を設定し、入力が終了すると`nil`に設定しますが、`each_line`および`readlines`は`$_`を変更しません。
- **ナローイング**。リーダーの値を値とする条件は、その値がナローイングされるのと同様にナローイングされたリーダーのRBS戻り値に両エッジで`$_`をバインドします: 真値エッジでは`String`、`gets`の偽値エッジでは`nil`です。条件は呼び出し自体（`while $stdin.gets`、`if STDIN.gets`、`$stdin.gets or break`、`next unless $stdin.gets`、`!$stdin.gets`）またはそれによって書き込まれた変数（`while (line = STDIN.gets)`）です; `until (line = STDIN.gets).nil?`およびその他の値の読み取りは`$_`をナローイングしません。`while $stdin.gets`の本体は、`redo`がループをターゲットにしない限り（`redo`は述語をテストせずに本体を再度実行します）、すべてのパスで`$_`を`String`として読み取り、ループ後は本体が`break`できる場合を除き`$_`は`nil`です。リーダー条件のアームは`$_`を別々にバインドするため、それらが合流する場所 —— `if $stdin.gets … end`、`$stdin.gets ? a : b`、または`(1 if $stdin.gets)`の後 —— では、`$_`は`String?`ではなく非バインドでなければなりません（MUST）;そこでの`String?`は、アーム内で設定されたフラグを通じて行を証明する正しいコードを報告してしまいます（`ok = $stdin.gets ? true : false; return unless ok; line = $_; line.chomp`）。リーダーは確実でなければなりません（MUST）:
  - `Kernel`モジュール、または`$stdin`もしくは`$<`上のブロックなしの`gets`または`readline`（ファイルがそれらを何にもバインドしないか、そのようなレシーバーの型のみにバインドしている間）。ファイルが書き込む`$stdin`は、メソッド本体を宣言された`IO`に書き込まれた値を結合したものとして開始するため（[#1362](https://github.com/rigortype/rigor/issues/1362)、[ADR-117](../../adr/117-standard-streams-typed-by-idiom/) WD1）、`$stdin = StringIO.new("a\n")`の後は`IO | StringIO`を読み取り、`if $stdin.gets`は依然として`$_`をナローイングします; `Tempfile`またはその他のメンバーは辞退します;
  - または、推論された型が、RBSが`IO`、`StringIO`、`ARGF`、または`Zlib::GzipReader`にリーダーを配置するクラスであるレシーバー上。`STDIN`および`ARGF`は、その型によってこのようにカウントされるため、いずれかをシャドウするプロジェクト定数（`module App; ARGF = CSV.new($stdin)`）はそれが保持するものとして読み取られます。`Tempfile`は該当しません: RBSはそれを`File`の下に宣言していますが、その`gets`はRubyフォワーダー（`DelegateClass(File)`）であり、フォワーダーの`$_`を設定します。`Kernel`のリーダーはprivateであるため、それを継承するだけの明示的レシーバーは読み取る代わりに例外を発生させ、RBSは除外する任意のリーダー（`CSV#gets`、Rubyの`shift`のエイリアス）をそこに配置します。

  **標準ストリームリーダーの仮定**（[ADR-117](../../adr/117-standard-streams-typed-by-idiom/) WD4）。Rigorは、プログラムが依存するリーダーがコアのものであると仮定します。読み取られるファイル外での置き換え（プログラム全体でチェックされる`def`を除く、以下参照）はモデル化されません: 別のファイルで再代入された`$stdin`、テストヘルパーがインストールするパッチ、テストダブル（`allow($stdin).to receive(:gets)`）、gemの注入、実行時にRubyリーダーを持つサブクラスインスタンスである`IO`または`File`と型付けされたレシーバー、およびファイルが見ることができない実行モード（`load(file, M)`、DSLの`instance_eval(File.read(f))`）。リーダーの後に`$_`を読み取るコードはリーダーがそれを設定した場合にのみ動作するため、ナローイングが追加するすべてのレポートはコアリーダーの下でプログラムが受けるべきものです。これには、`while $stdin.gets`ループの後の`puts "tail" if $_`のような正確なデッドコンディションレポートが含まれます。Rubyリーダーで設定されたプログラムはレポートを失うか、置き換えられたリーダーによってのみ誤りとなるレポートを受け取る可能性があります。解析されたコードが示す反証は、以下のように依然として辞退します。

  暗黙的selfまたは`self.`の`gets`（`while gets`、`self.gets`）は、スクリプト本体およびメソッド本体において同じ仮定の下で`$_`をナローイングします（[ADR-117](../../adr/117-standard-streams-typed-by-idiom/) WD5、[#1415](https://github.com/rigortype/rigor/issues/1415)）: `def lines; while gets; $_; end; end`はループ内で`String`を、ループ後に`nil`を読み取ります。読み取られるファイルが、リーダーがRubyで記述されている可能性のある`self`を示す場合、辞退して`$_`を非バインドのまま残します:
  - `main`または`Object`に到達する可能性のあるmixin（ファイル内のすべての暗黙的selfリーダーを辞退します）: クラスまたはモジュール本体の外での、またはそれらを指定する可能性のある`send`経由での、あるいはメソッドオブジェクト経由（`method(:extend).call(M)`、`Module.instance_method(:include).bind_call(Object, M)`）での暗黙的selfに対する`include`、`extend`、`prepend`、または`using`;トップレベルでの`class << self; include M; end`; `singleton_class.include(M)`;任意の明示的レシーバーに対するmixin（`TOPLEVEL_BINDING.receiver.extend(M)`、`Object.include(M)`、`Kernel.prepend(M)`、`obj.extend(M)`）; `Object`、`Kernel`、または`BasicObject`本体内の任意のmixin;任意の`using`;およびこれらを何でも行う可能性のあるStringのeval。プログラムの任意のファイルが宣言する`Object`、`Kernel`、または`BasicObject`へのmixin、およびクラスまたはモジュールメソッドの場合は`Module`または`Class`へのmixinも同様です。
  - `main`で定義されているか、ファイルが書き込む名前の下に配置されているリーダー（ファイル内のその名前の暗黙的selfリーダーを辞退します）: ファイル内の任意の場所でのその名前の`def`（トップレベルでの`def self.gets`。以下のプログラム全体チェックでは見えません）、`define_singleton_method(:gets)`、およびマクロがそれを定義する可能性のある名前を指定するSymbolまたはStringリテラル（`def_delegators :@io, :gets`、`attr_reader :gets`、`undef_method :gets`。`&:gets`およびメソッドを指定するだけの呼び出しの第1引数（`respond_to?(:gets)`、`send(:gets)`）を除く）。
  - ファイルが再バインドする可能性のある`self`: `instance_eval`、`instance_exec`、`class_eval`、`module_eval`、`class_exec`、`module_exec`、`define_method`、または`define_singleton_method`のブロック;ブロックとして記述されたクラス本体（`Class.new(CSV) { … }`、`Struct.new(:io) { … }`）;任意のブロックの内部で定義されたメソッド;モジュールのインスタンスメソッド（その`self`はモジュールをincludeするもの）; `self`以外の`obj`に対して`class << obj`または`def obj.m`が定義するメソッド;およびメソッドまたはブロック内の`class << self`が定義するメソッド（その`self`はそのメソッドのレシーバー）。それらの呼び出しのいずれかに渡されたproc（`obj.instance_exec(&blk)`、`define_method(:m, blk)`、`X.send(:define_method, :m, blk)`）、またはそのために取得されたメソッドオブジェクト（`obj.method(:instance_exec).call { … }`）は、ファイルが記述したブロックを任意の場所で実行する可能性があるため、ファイル内のすべての暗黙的selfリーダーを辞退します。
  - クラスまたはモジュール本体とそのメソッドの内部で、Rubyリーダーを保持する可能性のある祖先関係: プログラムもRBSも解決しないスーパークラスまたはmixin;定数ではないスーパークラス（`DelegateClass(File)`、`Struct.new(:io)`）、および定数書き込みが作成するクラス（`W = Class.new(CSV)`）、あるいはプログラムの任意のファイルが定数として名前を書き込むクラス（完全修飾または書き込みが存在するモジュールからの相対名。ファイル内の`const_set`はそのすべての暗黙的selfリーダーを辞退します）;定数を指定するレシーバーのない文以外としてクラス本体が書き込むmixin（`self.include(M)`、メソッド、ブロック、または`class << self`内のもの、`singleton_class.include(M)`、`include(*mods)`。これは祖先関係がそれに到達する任意の場所、再オープン、サブクラス、またはそれをincludeするクラスで、その名前によってクラスをダーティにします）;プログラムが定数として書き込む祖先名（`module Wrap; File = RubyReaderClass; class Src < File`）; RBSがリーダーのいずれかを`Kernel`、`IO`、またはその近縁以外の任意の場所に配置する祖先（`CSV#readline`、`OpenSSL::Buffering`）;プログラムのクラス本体がモジュールをmix-inするRBS祖先（`class IO; prepend M; end`はすべての`File`に到達します）; `Kernel`リーダーを持たないクラス（`BasicObject`、`SimpleDelegator`）;および`Tempfile`または`CSV`（RBSはそれらを`IO`または`Kernel`に配置していますが、リーダーはRubyです）。プログラムがスーパークラスなしで宣言し、RBSが認識していないクラスは、`Object`のサブクラスとして読み取られます。

  暗黙的selfまたは`self.`の`readline`は、まだ`$_`をナローイングしません（[#1458](https://github.com/rigortype/rigor/issues/1458)）。これは決してnilを返さないため、`while readline`は`break`または`EOFError`を通じてのみ終了しますが、ループ後のスコープは依然としてその本体が開始したスコープと合流し、ナローイングされた行は正しいコードを報告してしまいます（`x = nil; while readline; x = $_; break if …; end; x.chomp`）。WD4がファイルが見ることができない置き換えを仮定するように、以下が仮定されます: 別の`self`で実行されるトップレベルメソッド（`class Importer < CSV; def import = lines; end`）、継承したメソッドを実行するサブクラス、DSLメソッドが別の`self`で実行するブロック、別のファイルが行う`main`へのmixin、`load(file, M)`、およびDSLの`instance_eval(File.read(f))`。`while gets`内部での`$_`の防御的な読み取り（`next if $_.nil?`、`$_ || "default"`、`case $_ when nil`、`unless $_`）は静かなままです。

  `gets`または`readline`という名前のメソッドを定義またはパッチ適用するプログラムは、任意のレシーバーでその名前からのナローイングを受け取りません: 再オープンされた`IO`または`Kernel`、あるいは別のファイルが`$stdin`にバインドするプロジェクトオブジェクトは、プログラムのRubyメソッドを実行します。これは、プログラム内の任意の場所のクラス、モジュール、シングルトン、またはトップレベル本体におけるその名前の`def` —— ただし、`class << $stdin`、`STDIN.singleton_class.class_eval { … }`、または`$stdin.instance_eval { … }`を通じて到達されるストリームのシングルトン上の`def`はまだ含まれません（[#1423](https://github.com/rigortype/rigor/issues/1423)） —— および、読み取られるファイル内で、任意のレシーバーに対する`define_method`、`define_singleton_method`、または`alias_method`呼び出し（あるいはそれらのいずれかを指定する`send`、`__send__`、または`public_send`）と`alias`（メソッド名、aliasの新しい名前が`gets`または`readline`であるか、計算された名前がそのいずれかになり得るためリテラルではないもの、`$stdin.define_singleton_method(:gets) { … }`、`STDIN.singleton_class.define_method(:gets)`、`IO.define_method(name)`）を対象とします。セーフナビゲーションリーダー（`io&.gets`）はその真値エッジのみをナローイングします: `io`が`nil`のときは何も読み取りません。
- **その他のリーダー**。条件ではないリーダーは、`$_`を`String?`にバインドするのではなく非バインドのまま残します: そこでは行が非nilであることを証明するものが何もなく、nil許容の`$_`は、`$_`を読み取る前に別の方法でリーダーの値をチェックする正しいコードを報告してしまうためです（`line = $stdin.gets; return unless line; copy = $_; copy.chomp`）。上記のルールが挙げていないリーダー —— 辞退される暗黙的selfのもの、または`Dynamic`やその他のレシーバー上のもの —— も同様に`$_`を非バインドのまま残します。呼び出し元の`$_`を変更しない、Rubyで定義されたメソッドである可能性があるためです。
- **無効化**。`$_`のナローイングは、読み取りの前にRubyがスロットを設定する可能性のある場所ではどこでも忘却されなければなりません（MUST）。それを設定する可能性のあるコードは、任意のレシーバーに対する`gets`、`readline`、または`foreach`の呼び出し;暗黙的selfに対する`sub`、`gsub`、`chop`、または`chomp`（`ruby -n` / `-p`が`$_`を編集するために定義するもの）;名前が計算されるか最初の3つのいずれかを指定するリテラルである`send`、`__send__`、または`public_send`; Stringの`eval`、`instance_eval`、`class_eval`、または`module_eval`; `$_`への書き込み;およびこの本体でそれらを実行する可能性のある`&expr`ブロック引数（`&:gets`、`&:readline`、またはメソッド自体の`&block`（転送するだけ）以外のproc）です。これはネストした`def`、クラス、またはモジュール本体、`defined?`オペランド、またはルートブロックの内部を除く任意の場所で読み取られ、以下で忘却されます:
  - それを設定する可能性があり、解析が文の開始スコープで各部分を型付けする文全体: 呼び出しのレシーバーチェーン、引数、およびブロック、リテラルの要素、書き込みが格納する値。後のオペランドはリーダーが設定したものを読み取るため（`bar(gets, $_)`、`[gets, $_]`、`gets.to_s + $_`、`show(gets, xs.map { $_ })`）、ナローイングは全体で忘却され、同じ文内でリーダーの前に実行される読み取りのみが影響を受けます。文リスト、条件文、ループ、`case`、`begin`、`&&`、および`||`は各部分を順に実行し、単一の文としては読み取られません;
  - 自身の呼び出しがそれを設定する可能性のある文の後、およびブロックが設定する可能性のある呼び出しの後;
  - 節の`when`条件、またはピン留めやガードを持つ`in`パターンがそれを設定する可能性のある場合の、`case`節、その本体、および後続のすべての節のエントリ;
  - それを設定する可能性のある本体を持つクロージャを作成する本体内のすべての呼び出しの後: ラムダリテラル、またはそれを保持する呼び出しのブロック（`lambda`、`proc`、`Proc.new`、`define_method`、…）;
  - 解析器が追跡しないコードにスロットを渡す本体内の暗黙的selfまたは`self.`呼び出しの後: それを設定する可能性のある本体を持つブロックまたはラムダを保持するもの（渡されたメソッドがそれを保持し後で実行する可能性があるため）、任意の綴りの`binding`、またはメソッド自体のブロックの転送。本体がフレームをスタンプしなかった場合、すべての暗黙的self呼び出しがそれを忘却します;
  - それを設定する可能性のあるブロック本体のエントリ（後の反復が前の反復で設定されたものを読み取るため）;そのようなクロージャを作成する本体内の任意のブロック本体;およびそれ自体が設定する可能性のある呼び出しのブロック（`IO.foreach`がyieldする各行に対して行うように）、あるいはメソッドがyieldする前に実行されるレシーバーチェーンまたは引数が設定する可能性のある呼び出しのブロック。解析が進入しない値位置のブロックは、同じ条件でそのエントリを読み取ります;
  - 本体がそれを設定する可能性のある場合の、`while`、`until`、または`for`本体のエントリ、および`while`または`until`述語（本体が実行された後に再度実行されるため）;ループをターゲットとする`redo`がある場合、本体は述語なしで再度実行されるため、そのエントリも述語の`$_`のナローイングを維持しません;
  - `begin`本体がそれを設定する可能性のある場合の`rescue`節のエントリ（節は本体の任意のプレフィックスの後に実行されるため）、およびその本体またはrescue節が設定する可能性のある場合の`retry`がターゲットとする`begin`のエントリ;
  - 先行するオペランドのエッジの後に実行され、そのオペランドがそれを設定する可能性のある場合の、`&&`または`||`オペランドのエッジ、あるいは条件文のアームのエッジ。

  Rubyで定義されたメソッドへの呼び出し、およびこれらのいずれにも到達しない任意の呼び出しは、ナローイングを維持します: `if $stdin.gets; log("read"); line = $_; line.chomp; end`は静かです。ルートブロックのリーダーは無効化せず、ルートブロックは`$_`が非バインドの状態でエントリします。`define_method`または`define_singleton_method`の本体は、バインドされた`$_`を`Dynamic[top]`として読み取り、マッチグローバル変数を読み取るのと同様に非バインドのものは非バインドのまま残します。`ensure`節も同様であり、本体外への`return`、`break`、または`next`の後にも、それが型付けされたスコープとは異なるスコープから実行されます（[#1415](https://github.com/rigortype/rigor/issues/1415)）;節を通過した後の`$_`は、節がその`Dynamic[top]`をそのまま残し、`$_`を設定する可能性のあるものを何も保持していない場合にのみ節がエントリしたときのものとなり、それ以外の場合は節が残した状態（上記のルールがそれを忘却する呼び出し（フレームのクロージャ、外部に渡された`binding`）の後は非バインド）のままになります。
- **ギャップ**。該当する場合はマッチグローバル変数と共有されます: `yield`またはメソッド自体の`&block`を通じて、あるいは`Method#call`（`io.method(:gets).call`）を通じてC関数procとして実行されるリーダー;明示的レシーバー上のメソッドによって保持されそれを通じて実行されるブロック;記述された場所でナローイングを読み取り、呼び出された場所では読み取らないラムダまたはproc本体（[#1371](https://github.com/rigortype/rigor/issues/1371)）;ソースでもRBSでも解析器が読み取らないコードから継承されたリーダー;読み取られるファイル内でStringの`class_eval`が定義するリーダー（`IO.class_eval("def gets(*) = 'x'")`）;別のファイルが`main`で定義するリーダー（そのトップレベル、またはトップレベルの`class << self`における`def self.gets`。プログラム全体の`def`チェックは記録しませんが、ファイル自身のものは認識されます、[#1450](https://github.com/rigortype/rigor/issues/1450)）;および`$_`として読み取られない`English`エイリアスの`$LAST_READ_LINE`（[#1366](https://github.com/rigortype/rigor/issues/1366)）。

### レスキューとサブプロセスのグローバル

レスキューされる例外である`$!`およびそのバックトレースである`$@`は、フレームローカルではありません（[#1360](https://github.com/rigortype/rigor/issues/1360)）: `$!`の読み取りは実行中の実行コンテキストのフレームを最も近いrescueフレームまで遡るため、`rescue`節が実行されている場所、それが実行するブロック内、およびそれが呼び出すすべてのメソッド内で例外を保持し、`begin`を抜けると抜ける前に保持していたものを保持します。スレッドが待機した最後の子プロセスのステータスである`$?`はスレッドローカルです: 呼び出されたメソッドが実行するサブプロセスは呼び出し元の`$?`を設定し、ファイバーはそのスレッドのものを共有し、新しいスレッドはステータスなしで開始します。この3つはいずれもプログラム全体で共有される値を保持しません: Rubyは`$!`または`$?`への書き込みを拒否し（`NameError`）、`$@`への書き込みはレスキューされた例外のバックトレースを設定し、それらのいずれへの書き込みもプログラムグローバルな事前パスを通じて他の本体にシードしてはなりません（MUST NOT）。以下のルールがそれらを非バインドのまま残す場所では、宣言されたグローバル変数が読み取られるまで`Dynamic[top]`として読み取られます（[#1366](https://github.com/rigortype/rigor/issues/1366)）。

- **rescue節**。`rescue`節の本体は、`$!`を`rescue … => e`が`e`をバインドする型 —— 指定されたクラスのインスタンスのユニオン、単独の`rescue`の場合は`StandardError` —— として読み取らなければならず（MUST）、RBSまたはプログラムが`Exception`の下に配置するクラスではない各メンバーは`Dynamic[top]`として読み取られます: rescueリストは自身の`===`が自身のインスタンスではない例外とマッチするモジュールを指定する可能性があり（`module AnyFailure; def self.===(e) = true; end`）、解析が配置できないクラスもそのようなオブジェクトである可能性があるためです。プロジェクトクラスはスーパークラスチェーンを通じてカウントされますが（`class AppError < StandardError`）、それ自体またはプロジェクト祖先がシングルトン`===`を定義している場合（`def self.===(o) = true`、`rescue`がマッチのために呼び出す）を除きます; `===`を指定する`define_method`または`define_singleton_method`はそのクラス上に配置されないため、それを保持するファイル内ではどのメンバーもカウントされません。`$!`は`e`とまったく同じように読み取られるため、単独の`rescue`がその上でサブクラスのみが定義するメソッドに対して行う呼び出し（`rescue; $!.detail`）は、`rescue => e; e.detail`がすでに行っているのと同様に報告され、サブクラスでなければならない引数も同様です。本体は`$@`を`Array[String]`として読み取らなければなりませんが（MUST）、プログラムが任意の場所で`backtrace`という名前のメソッドを定義している場合（`$@`が呼び出す）または節が`set_backtrace`を呼び出す場合（`$!.set_backtrace(nil)`は`$@`をnilにする）を除きます;その場合`$@`は非バインドになります。本体は`$?`を非バインドとして読み取らなければなりません（MUST）: サブプロセスの待機中に例外が発生した可能性があり、その場合`$?`はnilのままになるためです（以下参照）。本体の任意の場所でクラスによって`$!`をガードする節 —— `$!.is_a?`、`kind_of?`、`instance_of?`、`respond_to?`、`X === $!`、`case $!`、または`rescue … => e`節がバインドするローカル変数（同じオブジェクト）に対する同様のガード —— は、代わりに`$!`および`$@`を非バインドとして読み取らなければなりません（MUST）: クラスガードはグローバル変数のレシーバーをまだナローイングしないため（[#1429](https://github.com/rigortype/rigor/issues/1429)）、単独の`rescue`の下での`$!.key if $!.is_a?(KeyError)`はガードに対して`key`を報告してしまうためです（ADR-117、ポイント3）。このバインディングは節が実行するすべてのブロックで保持されます（`items.each { log($!) }`）。
- **rescue修飾子と未エントリの節**。rescue修飾子のフォールバック（`expr rescue fallback`）は`StandardError`をレスキューし、修飾子の値は、同じ条件でそのフォールバックが`$!`と`$@`を読み取り、`$?`が非バインドの状態で型付けされなければなりません（MUST）。解析はフォールバック自身の式や、値位置にある`begin`または`do`ブロックのrescue節にはエントリしません（`warn(begin … rescue KeyError; $!.key; end)`）;これらは`$!`、`$@`、`$?`を非バインドとして読み取らなければならず（MUST）、囲む節のものを読み取ってはなりません（`rescue ArgumentError`節の内部での`h.fetch(:a) rescue $!.key`は実行時にKeyErrorを読み取ります）。
- **`begin`の通過後**。rescueチェーンを持つ`begin`の後、およびrescue修飾子の後では、制御がどのように離脱したか（フォールスルーによるか、rescue節からの`next`または`break`によるか）に関係なく、`$!`と`$@`はそれが開始した場所で読み取っていたものを読み取らなければなりません（MUST）。`retry`は、`begin`が最初にそれらを見出した状態のそれらとともに本体にエントリします。したがって`rescue AppError`節内のネストした`begin … rescue OtherError … end`の後、`$!`は再び`AppError`になります。本体および`else`節は`begin`のエントリ時のものを読み取ります。`ensure`節は`$!`、`$@`、`$?`を非バインドとして読み取らなければなりません（MUST）: 本体または節が終了した後（それらが以前保持していたものを保持しているとき）だけでなく、例外発生の後にも実行され、その場合`$!`は伝播中の例外であり（`rescue AppError`節内の`begin; raise OtherError; ensure; $!; end`は`OtherError`を読み取る）、本体が実行したはずのサブプロセスが`$?`を設定していないためです。節を通過した後は、節自体がサブプロセスを実行した場合を除き、節がそれらに書き込むことはできないため、節の開始時に読み取っていたものを読み取ります。
- **別の場所で実行される本体**。メソッド本体は`$!`、`$@`、`$?`が非バインドの状態で開始します: 呼び出し元がレスキューしているもの（rescue節から呼び出されたメソッドは例外を観測する）および呼び出し元の`$?`を読み取りますが、解析はこれを追跡しません。[Regexpマッチ述語ナローイング](#regexpマッチ述語ナローイング)で挙げたスレッド、ファイバー、またはラクターのルートブロックは独自の実行コンテキストで実行され、`$!`と`$@`が非バインドの状態で開始しなければなりません（MUST、rescue節内の`Thread.new { $! }.value`は`nil`です）。スレッドまたはラクターのルートブロックは`$?`も非バインドで開始しなければなりません（MUST）が、ファイバーのルートブロックはそのスレッドの`$?`を共有し、そのバインディングを保持します。`define_method`または`define_singleton_method`の本体は、バインドされた`$!`、`$@`、または`$?`を`Dynamic[top]`として読み取らなければなりません（MUST）。クロージャの本体 —— ラムダリテラルのもの、あるいは`lambda`、`proc`、`Proc.new`、`Enumerator.new`、または`Hash.new`のブロック —— は呼び出されたときに常に実行され、通常はそれが記述された節が終了した後に、場合によっては別のスレッド（`Thread.new(&f)`）で実行されるため、3つすべてが非バインドの状態で開始しなければなりません（MUST）: rescue節内の`f = -> { $! }`は、`begin`を抜けて呼び出されると`nil`を読み取ります。
- **サブプロセス**。バッククォートまたは`%x`コマンド、暗黙的`self`、`self.`、または`Kernel`に対する`system`、およびコア`Process`モジュールに対する多くとも1つのプレーンな引数（子プロセスのpid）を持つ`wait`、`waitpid`、`wait2`、または`waitpid2`は、その子プロセスを待機し、`$?`を`Process::Status`のままにします; `system`はコマンドが実行できない場合（終了ステータス127）も同様にします。いずれかを確実に実行した文の後のスコープは、`$?`を`Process::Status`にバインドしなければなりません（MUST）: 文の呼び出しそのものであるもの、そのレシーバーチェーンにあるもの（`` head = `git rev-parse HEAD`.strip ``）、またはセーフナビゲーション呼び出しではない呼び出しの位置引数であるもの（`puts(%x(date))`）で、それらの任意の深さにあるものです。ブロック、分岐、または`&&`や`||`の右オペランドにあるものは実行されない可能性があるため、それをスキップするパスは`$?`が非バインドの状態で合流します;左オペランドにあるものは実行されます。単独の`spawn`、`IO.popen`、`Open3`、`Process.detach`、およびフラグ引数を指定された`Process.wait`はそれをバインドせず、`Process.last_status`は`$?`を設定するのではなく読み取ります: `$?`がバインドされている場所では常に`$?`が読み取るものを読み取らなければならず（MUST）、`$?`が非バインドの場所では、任意の宣言されたメソッドと同様に宣言された`Process::Status?`を読み取ります（[#1366](https://github.com/rigortype/rigor/issues/1366)まで非バインドの`$?`が読み取っていた`Dynamic[top]`ではありません）。プログラムが`Process.last_status`自体を定義している場合、それは`Dynamic[top]`になります。セッターの名前のメソッドを任意の場所で定義しているプログラム（`def system`、``def `(cmd)``、`wait`）は、その代わりにRubyコードを実行する可能性があるため、その名前は何もバインドしません。
- **クリア**。Rubyは4つの方法で`$?`を`nil`に戻し、それぞれが処理されます:
  - 終了した子プロセスが見つからない`WNOHANG`フラグ付きの`wait`、`waitpid`、`wait2`、または`waitpid2`、および子プロセスのない`Process.waitall`。いずれもスレッドが呼び出す任意のメソッド内またはシグナルハンドラ内で実行できるため、任意のレシーバーで複数の引数、splat、キーワード、または転送された`...`を持つ`wait`ファミリー呼び出し、あるいは`waitall`、あるいはそのいずれかを指定する`send`を保持するファイルは、どこでも`$?`をバインドしてはなりません（MUST NOT）;
  - バッククォート、`%x`、または`system`は子プロセスを実行する前に`$?`をnilに設定するため、子プロセスの実行中に発生した例外（`Timeout::Error`、`Interrupt`、`Thread#raise`）はそれをnilのままにします。rescue節およびrescue修飾子のフォールバックはそれを非バインドとして読み取るため（上記参照）、節がフォールスルーする`begin`の後、およびフォールバックがフォールスルーする可能性のあるrescue修飾子の後では非バインドになり、`retry`が再エントリする本体はすべてのパスでそれを非バインドとして読み取らなければなりません（MUST）。文のオペランド内、または文が渡すブロック内のrescueは、そのスコープを文のスコープに合流させることが決してないため、ラムダ、後で実行するために呼び出しが保持するブロック、または`def`の外側で、rescue節またはフォールバックがフォールスルーする可能性のあるrescue修飾子を保持する文の後でも、`$?`は非バインドでなければなりません（MUST、`files.each do |f| Timeout.timeout(10) { %x(convert #{f}) } rescue Timeout::Error; warn f end`）;
  - 子プロセスがすでに回収された`IO.popen`ストリームに対する`IO#close`（解析はこれをモデル化しません。以下のギャップ）。

  それ以外の場合、`$?`は一度設定されると`Process::Status`のままであるため、それを設定しなかったパスとの合流まで、その後の呼び出し、ブロック、およびループを生き残ります: `system("make"); log("built"); $?.success?`はそれを読み取ります。呼び出されたメソッドのサブプロセスも呼び出し元の`$?`を設定しますが、解析はこれを追跡しないため、`def run = system("make"); run; $?`はそれを非バインドのまま残します。
- **ギャップ**: 別のファイル、gem、または他の場所でセットアップされたシグナルハンドラから、あるいは計算された`send`を通じて、サブプロセスと`$?`の読み取りの間で実行される`WNOHANG`待機または`waitall`;自身のサブプロセスが待機している間に発生した例外をレスキューするか（`Timeout.timeout(1) { %x(make) } rescue nil`）、すでに回収された`IO.popen`ストリームをクローズし、そのため`$?`がnilの状態で戻る呼び出されたメソッド;メソッドが別のスレッドで実行するか（スレッドプールの`post { $?.success? }`）、rescue節が終了した後に保持して実行するブロック（`on_error { $! }`、記述された場所でのバインディングを読み取ります）;同じ文が実行し、rescueをフォールスルーする保持されたブロックまたはファイバー本体（`Fiber.new { %x(make) rescue nil }.resume`、`-> { %x(make) rescue nil }.call`。文がそのバインディングを保持する間に`$?`をnilのままにします）; `$!`のコピーに対するクラスガード（`err = $!; $!.key if err.is_a?(KeyError)`）またはそのクラスの比較（`$!.class == KeyError`。これらは`e`もナローイングしません）、および節が呼び出すメソッドによって呼び出される`set_backtrace`; `send`または計算された名前を通じて`===`を指定する`define_method`、または別のファイル内のもの（`Matchy3`を宣言するファイル内の`define_singleton_method(:===)`は、辞退がファイル単位であるため、他の場所での`rescue Matchy3`が`$!`を`Matchy3`にバインドしたままにします）;暗黙的`self`を通じて到達されるgemのRuby `system`（DSLブロックの再バインドされた`self`を含む）;発見が記録しない形式でプログラムが定義する`Process.last_status`（`module Process`外での`def Process.last_status`、`define_singleton_method`、`alias_method`、prependされたモジュール。依然として`$?`のバインディングを読み取ります）; `backtrace`または`self.===`を再定義するgemの例外クラス;および`$!`、`$@`、`$?`として読み取られない`English`エイリアスの`$ERROR_INFO`、`$ERROR_POSITION`、`$CHILD_STATUS`。

### クラスガード

クラスガードは、`is_a?`、`kind_of?`、`instance_of?`、クラスまたはモジュール定数`C`に対する`C === x`、`case x when C`、および単独のクラスパターン`case x in C`（または`in C => y`）です。ガードの真値エッジでは、レシーバーはそれを満たすことができるその型のメンバーにナローイングされます。満たすことができるメンバーがない場合、メンバーが`C`と互いに素（disjoint）なクラスの`Nominal`である場合を含め、エッジは`bot`になります。

そのような`Nominal`は、プログラムが厳密には保持しない慣用的な期待値である可能性があります（[ADR-117](../../adr/117-standard-streams-typed-by-idiom/)決定ポイント3、[#1429](https://github.com/rigortype/rigor/issues/1429)）。`$stdout`は`IO`と型付けされており、テストは`IO`のサブクラスではない`StringIO`で同じコードを実行するため、`$stdout.is_a?(StringIO) ? $stdout.string : nil`および`case io when StringIO then io.string end`は正しいコードです。そのようなガードに対して:
- **アーム**。アーム内ではレシーバーは`bot`として読み取られるため、その上の呼び出しはチェックされず、アームがその後のコードと合流する場所にも何も追加しません。アームの残りの部分は通常どおりチェックされます。これはすべての位置にある`if`、`unless`、三項演算子、およびエバリュエータが実行する`case`（文、文レベルの書き込みの値、あるいはそれ自体が文またはそのような書き込みの値である呼び出しのブロック）に当てはまります。配列要素や引数など、他の任意の値位置にある`case`のアームはナローイングされていないサブジェクトに対してチェックされるため、`[case io when StringIO then io.string end]`は正しいコードに対して`call.undefined-method`を報告します（[#1484](https://github.com/rigortype/rigor/issues/1484)）。
- **評定なし（No verdict）**。`bot`はコード内の証拠に対するRigorのレシーバー型の読み取りに基づいているため、デッドコードとして報告してはなりません（MUST NOT）。節に入るときにサブジェクトが`C`と互いに素な`Nominal`メンバーを保持している`when C`または単独の`in C`節は、`flow.unreachable-clause`を報告しません（`Narrowing.disjoint_nominal_guard?`）。`is_a?`、`kind_of?`、`instance_of?`、`===`の形式は、それ自体の評定を報告しません。
- **評定を維持するもの**。ファイルが文字どおり示しているものを記録するサブジェクトは、レポートを維持します: リテラル（`Constant`）、`Tuple`、`HashShape`、クラスオブジェクト（`Singleton`、[#657](https://github.com/rigortype/rigor/issues/657) / [#898](https://github.com/rigortype/rigor/issues/898)の辞退に基づく）、および`NilClass`、`TrueClass`、`FalseClass`の`Nominal`。先行する節が網羅した節（先行する節がサブジェクトの慣用的な型のみを網羅した場合であっても、[#1485](https://github.com/rigortype/rigor/issues/1485)）や、デッドな`else`も同様です。
- **値**。`if`、`unless`、または三項演算子はすべての位置でそのアームの値を維持し、`case … in`はそのアームを決してドロップしません。`case … when`は、エバリュエータがそのアームを結合する場所（書き込みがバインドする値として、またはメソッドの戻り値として）でアームを維持します。解析が`case … when`ノード自体を型付けする場所では、`class_pattern_certainty`が`:no`と応答するため、その値はアームをドロップします: 呼び出しの引数、配列要素またはハッシュ値、呼び出しレシーバー、メソッド演算子のオペランド（`(case …) + 0`）、`!`のオペランド、ブロック本体の最終式、および条件文です。`&&`および`||`のオペランドはすべての位置でアームを維持します。条件文においてそのドロップは、決定ポイント3に反して、正しいコードに対して`flow.always-truthy-condition`を報告します（`$stdout = File.open(path)`の後の`if (case $stdout when StringIO then true else false end)`）。[#1465](https://github.com/rigortype/rigor/issues/1465)はそれらの位置をリストし、ガードされたクラスをその先にリークさせることなくアームを維持することを追跡しています。

[global-variables.md](../global-variables/#エビデンス境界)は、Rigorがイディオムによって読み取る型を変更できる証拠（そのようなガードもその一形態です）を規定しています。

上記とは無関係に、`instance_of?(C)`は正確にクラス`C`を保持します: `C`がレシーバーのクラスの下位クラスである場合（`instance_of?(Integer)`における`Numeric`）、真値エッジは`C`にナローイングされます。モジュール、スーパークラス、無関係なクラス、または順序付けられていないクラスに対しては、エッジは`bot`になります。ガードを満たすメンバーを持つユニオンは、そのメンバーを保持して他のメンバーをドロップします: `Array[Integer] | Hash[Symbol, Integer]`に対する`x.is_a?(Array)`は`Array[Integer]`を読み取ります。偽値エッジは変更されません。

値位置の`case`は、文形式がそれを実行するのと同様に、サブジェクトの節ナローイングの下で各アームを型付けします: `n: Integer | Symbol`に対する`case n when Symbol then n else n.to_s end`は`Symbol | String`を読み取ります。

静的に既知の`m`に対する`respond_to?(:m)`は、同じ意味でのガードです。その真値エッジでは:
- `NilClass`が`m`を定義している場合（この場合は何もナローイングされない）を除き、レシーバーは`nil`を失います。
- Rigorが`m`を欠いていると認識しているクラスの各メンバーはドロップされます。Rigorがこれを認識するのは以下の場合に限られます:
  - クラスがRBSで宣言されている;
  - インスタンスが任意のクラスになり得るmixinモジュール、`Object`、または`BasicObject`ではない;
  - プラグインのオープンレシーバーではない;
  - そのシグネチャもプロジェクトもそのクラス上に`m`を定義していない。
- 応答できるメンバーが存在しない場合、メンバーが3つの値固定クラス以外の`Nominal`であればレシーバーは`Dynamic[top]`として読み取られるため（読み取るべきクラス名が指定されていない）、ガードされた呼び出しは報告されません。すべてのメンバーが上記に挙げたようなリテラルキャリアである場合、エッジは`bot`になります。リテラル値の場合は正確です（`1.respond_to?(:upcase)`はすべての実行でfalseです）;クラスオブジェクトはRigorがシグネチャを持たないgemからシングルトンメソッドを獲得する可能性があり（ActiveSupport下の`Time.respond_to?(:zone)`）、そのアームはレシーバーを`bot`として読み取り、未チェックのまま通過します。

偽値エッジは変更されません。

### グローバル変数と定数のガード

真偽値性、`nil?`、`!`、セーフナビゲーション（`$g&.m`、およびセーフナビゲーションチェーン）、クラスガード、`C === x`、`case … when`、および`respond_to?`は、ローカル変数の読み取りをナローイングするのと同様に、グローバル変数の読み取り（`$stdout`）および定数参照（`STDOUT`、`Foo::BAR`、`::Foo`）をナローイングします（[#1429](https://github.com/rigortype/rigor/issues/1429)）。真偽値性、`nil?`、セーフナビゲーション、`respond_to?`、およびクラスガードはインスタンス変数もナローイングします;そのクラスガードはセクション[インスタンス変数のクラスガード](#インスタンス変数のクラスガード)に述べるように復元されます。ガードのナローイングは、グローバル変数の型が持つどの出所の上にも適用されます（[global-variables.md](../global-variables/#グローバル変数の型の出所)）。
- **非バインドのグローバル変数**は、その読み取りが持つ型からナローイングされます。何も学習しないエッジは、グローバル変数または定数をそのまま残します。
- **定数**。定数のナローイングは参照の綴り方によってキー付けされるため、`::STDOUT`と`STDOUT`は別々にナローイングされます。定数への書き込みは、最後のセグメントが書き込まれた名前であるすべての綴りのナローイングを終了します。`module Foo`内の`Foo::BAR = nil`は`BAR`が読み取る定数に書き込むためです。
- **`$stdout`と`$>`**は同一の変数です: いずれかへの書き込みは、もう一方のガードのナローイングを終了します。

グローバル変数または定数のガードによるナローイングは、以下に挙げるギャップを除き、ガードとそれを再バインドする読み取りの間でコードが実行される可能性がある場所で復元（restore）されなければなりません（MUST）: Rubyコードがグローバル変数を代入するか（ヘルパー内での`$stdout = StringIO.new`）、定数に`const_set`を行う可能性があり、解析はそのコードを見ることができないためです。復元は、ガードがナローイングしたバインディングとナローイングされた型のユニオンをバインドします。コードが値をそのまま残す可能性があるため、そのユニオンは依然としてガードされたメンバーを保持し、したがって`$stdout.is_a?(File) ? (helper; $stdout.mtime) : nil`は`helper`の後に`File | IO`を読み取り、ガードされた呼び出しは静かなままです。非nilにガードされた`$sep`は、それを`nil`に設定する可能性のある呼び出しの後に再び`String?`を読み取ります。

グローバル変数または定数を再バインドする可能性のあるコードは以下のとおりです:
- プロジェクト、gem、または未解決のコードを実行する可能性のある呼び出し:
  - レシーバーのクラスまたはその祖先関係でプロジェクトが定義するメソッド;
  - シグネチャがRubyコアおよび標準ライブラリの外側で所有されているメソッド;
  - プロジェクトまたはgemレシーバーに対するコアメソッド（コアモジュールのメソッドがコールバックする可能性があるため。`Enumerable#map`はクラスの`each`を実行する）;
  - `Kernel`、`Object`、または`BasicObject`が所有し、レシーバーでプロジェクトが定義するメソッドを呼び出すメソッド（`r != 1`は`r == 1`を実行する; `===`、`!~`、`respond_to?`も同様）;
  - 未解決の呼び出し先（`Dynamic`レシーバー、またはシグネチャが宣言していない名前）;
  - `send`、`__send__`、`public_send`、`eval`、`require`、`require_relative`、`load`、`const_set`、`remove_const`、`instance_variable_set`、および`remove_instance_variable`、ならびにリテラルブロック以外を指定された`instance_eval`、`instance_exec`、`class_eval`、`class_exec`、`module_eval`、`module_exec`;
  - `Proc`、`Method`、`UnboundMethod`、`Binding`、`Enumerator`、`Fiber`、`Thread`、またはデリゲーターに対する任意の呼び出し;
  - `&expr`ブロック引数を渡す呼び出し;
- 複合書き込みまたは`for`ループが明示的に綴らずに呼び出すメソッド: `r += 1`の演算子、`r.val ||= 1`および`r[0] += 1`のリーダーとライター（およびリーダーが返すものに対する演算子）、ならびに`for x in r`の`each`;
- グローバル変数または定数に書き込むか、そのようなコードを保持する本体を持つリテラルブロック;
- `yield`および`super`。

ルールがコードを読み取る場所:
- 文自身の呼び出し、そのレシーバーチェーンおよび引数内の呼び出し（Rubyが最初に実行する）、ならびに文が1つずつ評価せずに型付けする値内の呼び出し（配列、ハッシュ、または補間リテラル、`rescue`修飾子、定数値）;
- `&&`および`||`の後続のオペランド（自身のエッジがナローイングする前）;
- 各反復の後に再度実行されるため、ループのエントリにおけるループの本体および述語;本体の一部のプレフィックスの後に実行されるrescue節のエントリ;および`retry`が再エントリする本体。

スキャンは、スキャンされたコードが書き込むローカル変数を、コードがそれに書き込む各値と、スコープがすでにそれをバインドしている場合はそのバインディングとのユニオンとして型付けします。コードが自身の書き込みの前に実行される可能性があるためです（ループ本体、ブロック、rescue節）。リテラルブロックの本体は、そのパラメータリストが宣言するすべての名前がバインドされた状態でスキャンされるため、ブロックの外側から同じ名前のローカル変数を読み取ることはありません: 単純な必須パラメータはそのリスト内の位置でメソッドのシグネチャがyieldするものに、その他（構造化解除、オプショナル、splat、post、キーワード、ブロック、または`;`ブロックローカル）は`Dynamic[top]`にバインドされ、したがってその上の呼び出しは未解決としてカウントされます。本体が書き込むローカル変数はそれらから型付けされます。ブロックまたはラムダの本体は、そのようなコードの後に実行される可能性がある場合、ナローイングが復元された状態でエントリします:
- ラムダリテラル;
- 後で実行するために呼び出しが保持するブロック（`proc`、`lambda`、`define_method`）;
- 後のイベントで実行するために呼び出しが保持するブロック: `at_exit`、`trap`および`Signal.trap`、`trace_var`、`TracePoint.new`および`TracePoint.trace`、`ObjectSpace.define_finalizer`;および`END { }`本体;
- スレッド、ファイバー、またはラクターのルートブロック;
- それ自体がそのようなコードを実行する可能性のある呼び出しのブロック（`with_retry { $sep.length }`）;
- 後の反復が前の反復で書き込まれたものを読み取るため、それ自体が再バインドする可能性のある本体。

`Kernel`、`Object`、または`BasicObject`が所有するその他のメソッド（`puts`、`format`、`obj.frozen?`）、およびコアまたは標準ライブラリのレシーバーに対するコアまたは標準ライブラリのメソッド（`$sep.strip`、`$stdout.rewind`、`File.read(path)`）は、ナローイングを維持します。したがって`if $sep; $sep.strip; $sep.length; end`は`$sep`の非nilを維持します。レシーバーの`Nominal`と互いに素なクラスガードはレシーバーを`bot`のまま残しますが、ガードを通過した値はガードされたクラスのものであるため、レシーバーに対して呼び出されたメソッドは上記のルールによってそのクラスのメソッドとして読み取られ、そのような呼び出しがそのブロックにyieldするものに対して呼び出されたメソッドも同様です（[#1446](https://github.com/rigortype/rigor/issues/1446)）: `return unless STDOUT.is_a?(StringIO); STDOUT.rewind; STDOUT.string`は正しいコードである一方、`return unless CB.is_a?(Proc)`の後の`CB.call`は`Proc`に対する任意の呼び出しがそうであるように再バインドする可能性があり、ガードされたクラスのプロジェクトサブクラスのみが定義するメソッドも同様です。コアメソッドに対するプロジェクトサブクラスのオーバーライド（`StringIO`サブクラス内の`def rewind`）はカウントされず、これは値がサブクラスインスタンスである任意の`Nominal`レシーバーが持つギャップと同じです。クラスガードが残したのではない、`bot`として読み取られたレシーバーに対して呼び出されたメソッドは未解決の呼び出し先です。呼び出しの引数およびリテラルブロックは他の任意のものと同様に読み取られます。インデックスがグローバル変数である`for`、および参照がグローバル変数である`rescue`（`rescue => $out`）はそれに書き込み、これによりガードのナローイングが終了します。

フレームローカルな`$_`と`$~`（[#1359](https://github.com/rigortype/rigor/issues/1359)）およびレスキュースコープの`$!`と`$@`は同様にナローイングされますが、このルールによって復元されることはありません。呼び出されたメソッドは前者の2つに到達できず、復帰した呼び出しは後者の2つを元の状態のまま残すためです;上記の独自のルールがこれらを忘却します。`$?`はこのルールによって復元されます。

ギャップ（ルールが読み取らないRubyコードが実行される可能性がある場所）:
- **暗黙的変換**。プログラムが明示的に綴っていないメソッドにコールバックするコアメソッドは、コアメソッド単独として読み取られます: `puts obj`は`obj.to_s`を実行し、`"#{obj}"`もそれを実行し、`hash[obj]`は`obj.hash`を実行し、`list.sort`は`<=>`を実行し、`1 + obj`は`obj.coerce`を実行し、`[*obj]`は`obj.to_a`を実行し、`case obj when 1`は`1 === obj`を実行します。グローバル変数を代入するプロジェクトの`to_s`は、ナローイングを終了させません。
- **別のスレッド**が任意の2つの読み取りの間でグローバル変数を代入する可能性があります;ルールは現在のフローのコードのみを読み取ります。
- **フローが合流しない書き込み**。グローバル変数への直接の書き込みは、ループのバックエッジやrescue節を越えて合流しません（[#1464](https://github.com/rigortype/rigor/issues/1464)）;ルールはそこでガードのナローイングを復元しますが、ループ本体が書き込むだけのグローバル変数は最初の反復の値を保持します。

### インスタンス変数のクラスガード

クラスガード、`C === @x`、`case @x when C`、および`case @x in C`は、ローカル変数の読み取りをナローイングするのと同様にインスタンス変数の読み取りをナローイングします（[#1446](https://github.com/rigortype/rigor/issues/1446)）: `IO`と型付けされた`@io`に対して、`@io.is_a?(StringIO) ? @io.string : nil`、`StringIO === @io`、および`case @io when StringIO then @io.string end`は正しいコードです。

グローバル変数を再バインドする可能性のあるコードは`self`に到達してインスタンス変数も再バインドする可能性があるため、そのようなナローイングは、上記のグローバル変数および定数のルールが復元を行う場所で、同じギャップを伴い、ガードがナローイングしたバインディングとナローイングされた型のユニオンへと復元されなければなりません（MUST）。レシーバーが`self`である可能性があるため（`holder = self; holder.instance_variable_set(:@io, STDOUT)`）、そのルールは任意のレシーバーに対する`instance_variable_set`および`remove_instance_variable`をカウントします。ナローイングは、ルールが読み取るコード内でナローイングされた変数への書き込み時にも復元されなければなりません（MUST）: リテラルブロックの本体（呼び出し後、およびブロックのエントリ時。後の実行が前の実行で書き込まれたものを読み取るため）、ループのエントリ時におけるループの本体、およびrescue節のエントリ時における`begin`本体です。変数を書き込むリテラルブロックは、まずフロアが`Dynamic[top]`であるインスタンス変数のブロック書き戻しによって広げられるため、`[1].each { @io = nil }`の後、変数はこのユニオンが取られる前に`Dynamic[top] | …`を読み取ります。

`for`ループのインデックス（`for @io in list`）および`rescue`参照（`rescue => @io`）を含む変数への書き込みはナローイングを終了させ、書き込まれた値をバインドします。暗黙的selfまたは`self.`の呼び出しは、どのガードがナローイングしたかに関わらず、すべてのナローイングされたインスタンス変数をクラスのシードとのユニオンへと広げるため、ガードと読み取りの間の`puts`は、互いに素なクラスへのクラスガードのナローイングを終了させます。真偽値性、`nil?`、セーフナビゲーション、および`respond_to?`はこの復元なしでインスタンス変数をナローイングします: 書き込みとその暗黙的selfルールのみがそれらのナローイングを終了させます。

## ファクトの安定性とミューテーション

フローファクトは解析器がそれらが記述するパスを信頼できる間だけ有効です。RubyのふるまいがObservedターゲットをミューテート、置換、またはエスケープさせる可能性がある場合、Rigorはファクトを無効化または弱体化させなければなりません（MUST）。

ファクトはターゲットと安定性の理由を持たなければなりません（MUST）。最初の実装では少なくとも以下を区別します:

- 「ローカル`x`は現在非nil値を参照している」のような**ローカルバインディングファクト**;
- ブロック、proc、ラムダが別のレキシカルスコープからローカルに書き込む可能性がある**キャプチャされたローカルファクト**;
- ハッシュキー、インスタンス変数、シングルトンメソッド、オブジェクトシェイプ（shape）メンバーのような**オブジェクトコンテンツファクト**;
- 定数、クラス変数、グローバルのような**グローバルストレージファクト**（正規表現マッチグローバル変数は代わりにフレームローカルです; §「Regexpマッチ述語ナローイング」を参照）;
- ローカル呼び出しを生き残る可能性があるが、それでもターゲット無効化が必要な**動的由来ファクトと関係的ファクト**。

### ターゲット指定無効化

ローカルバインディングファクトは、そのローカルへの代入まで通常のメソッド呼び出しを越えて安定しています。呼び出しはローカルが参照するオブジェクトをミューテートする可能性がありますが（MAY）、ローカルが書き込むクロージャによってキャプチャされない限り、ローカル変数自体を再バインドしてはなりません（MUST NOT）。したがって:

- `x.is_a?(String)`は`x`を書き込めない未知の呼び出しの後もローカルバインディングファクトのままです;
- `x[:key]`または`x.foo`のシェイプファクトは`x`をミューテートまたはエスケープさせる可能性のある呼び出しによって弱体化される場合があります（MAY）;
- インスタンス変数、クラス変数、グローバル、定数に関するファクトはヒープまたはグローバルストレージファクトであり、より積極的に無効化されます。

未知のメソッド呼び出しはヒープファクトに対して保守的なままです。呼び出しにエスケープされた可能性のあるターゲットのオブジェクトシェイプ、ハッシュエントリー、インスタンス変数、定数オブジェクト、グローバルストレージファクトを無効化する場合があります（MAY）。現在のスコープのすべてのローカルバインディングファクトを無効化してはなりません（MUST NOT）。グローバル変数または定数のガードによるナローイングは、[グローバル変数と定数のガード](#グローバル変数と定数のガード)のルールによって復元されます。

### クロージャキャプチャ

クロージャにキャプチャされたローカルには明示的な処理が必要です。ブロック、proc、またはラムダが外側のローカルに書き込む場合、Rigorはキャプチャされたローカルへの書き込み効果を記録しなければなりません（MUST）。クロージャがすぐに呼び出されてその本体が利用可能な場合、Rigorは呼び出しエッジで書き込みを適用します。クロージャがエスケープするか後で呼び出される可能性がある場合、それが書き込める可能性のあるローカルに関するファクトは、エスケープポイント以降およびそのクロージャの未知の呼び出しの前に不安定になります。

### ブロック呼び出しタイミング

ブロックと高階メソッド呼び出しは、「yieldはすべてを無効化する」という一律ルールではなく、呼び出しタイミングとミューテーション効果によってモデル化すべきです（SHOULD）。有用な最初のカテゴリーは:

- ブロック呼び出しなし;
- 即時の非エスケープ呼び出し、1回または既知の有界な回数;
- 即時の非エスケープ呼び出し、未知の回数;
- 遅延またはエスケープするブロックストレージ;
- 未知のブロック挙動。

`tap`、`then`、`yield_self`、`each_with_object`のような既知のRubyメソッドは最終的にブロックタイミング、戻り値挙動、レシーバーまたは引数ミューテーションのサマリーを受け取るべきです（SHOULD）。そのようなサマリーなしでは、Rigorはオブジェクトコンテンツファクトに対して保守的である場合がありますが（MAY）、それでも無関係なローカルバインディングファクトを保持すべきです（SHOULD）。

最初に出荷されたサマリーは、**即時、厳密に1回（exactly-once）**yieldするものに対する戻り値の型サマリーです: `Kernel#tap`、`Kernel#then`、`Kernel#yield_self`はすべてのパスにおいて、戻る前にブロックを1回呼び出します（[#1095](https://github.com/rigortype/rigor/issues/1095)）。そのような呼び出しが、通常完了に到達不能なリテラルブロックを伴う場合、callee自身の結果も同様に到達不能であり、呼び出しの型はその`break`アーム単独のunion、またはそれがない場合は`bot`でなければなりません（MUST）:

```ruby
[1, 2].tap { break "s" }         # "s"            ("s" | Array ではない)
[1, 2].tap { raise "x" }         # bot            (Array ではない)
[1, 2].tap { break "s" if cond } # "s" | Array    (ブロックは完了可能)
[1, 2].tap { next "s" }          # Array          (`next` はブロックを完了する)
[1, 2].each { break "s" }        # "s" | Array    (`each` は一度もyieldしない可能性がある)
```

到達不能な通常完了は、両方が成立する2つの証明によって確立されなければなりません（MUST）。1つ目は構文的なものです: ブロック本体を通るすべてのパスが、ブロックレベルの`break`、`return`、`redo`、または`retry`で終わるか、あるいはプロジェクトコードがその名前で定義していない（トップレベルの`def`、いずれかの側の任意のクラスまたはモジュール上のメソッド、または`pre_eval:`パッチのすべてが対象外とします）レシーバーなし、`self.`、または`Kernel.`での`raise`、`fail`、`throw`、`exit`、`exit!`、`abort`の呼び出しで終わるか、またはそれらのいずれかを最初に評価しなければならない式で終わることです。無条件に評価される位置のみがカウントされます: ネストしたブロック、lambda、`def`、またはループは入らず、`&&` / `||`は左側のオペランドのみをカウントし、`if` / 三項演算子は両方のアームを必要とし、`rescue`付きの`begin`はその本体とすべてのrescue節が脱出することを必要とし、脱出しなければならない`ensure`はそれ単独で適格となります。2つ目は、ブロック戻り値パスがブロックを厳密に`bot`として型付けすることであり、これにより到達可能な`next`（ブロックを完了します）はunionを維持します。ブロック戻り値パスからの`bot`だけでは不十分です: ブロックの最後の呼び出しが単に`bot`戻り値を宣言している場合にも発生し、これはプロジェクトのシグネチャが行う可能性があり、以下の拡張前の`Kernel#loop`が行っていたことでもあります。構文的走査が認識しない形状はunionを維持します。

このルールはメソッド名ではなく、呼び出しが解決される宣言に基づいて制限されます: 宣言しているオーナーは、CRubyとコアRBSの両方におけるオーナーである`Kernel`でなければなりません（MUST）。レシーバーのクラス、プロジェクトの祖先、またはプロジェクトシグネチャが独自の`tap` / `then` / `yield_self`を定義しているレシーバー、その名前のトップレベル`def`、`Object` / `Kernel`またはレシーバーのクラスの任意のRBS祖先に対するプロジェクトパッチ（再オープンされた`Enumerable`、およびクラスオブジェクトレシーバーに対する`Module` / `Class`）、クラスを命名しないレシーバー（`Dynamic`、`top`）、および祖先関係がシグネチャの記述しないクラスを通じてプロジェクトを離脱するプロジェクトクラスは、すべて`break | normal-return` unionを維持します。ブロック渡し（`&blk`、`&:sym`）は証明を行う本体を持たないため、同様にunionを維持します。厳密に`bot`ではなく`nil`を保持するか`Dynamic`であるブロック値は、このルールをトリガーしません。`then` / `yield_self`について、このルールは型変数バインディングがすでに生成するものを再記述するものです（それらのRBS戻り値はブロックの型であるため、`T := bot`）; `tap`はその`-> self`戻り値がブロックに決して言及しないため、このルールが変更を加えるメソッドです。

#### `Kernel#loop`は`StopIteration`で完了する

`Kernel#loop`はコアRBSで`() { () -> void } -> bot`と宣言されていますが、そのブロックがraiseする`StopIteration`をrescueしてその例外の`result`を返すため、エニュメレータを使い果たすイディオム`loop { out << e.next }`は`e`が使い果たされると通常通りに戻ります（`e`自身の`each`値とともに）（[#1107](https://github.com/rigortype/rigor/issues/1107)）。したがって、ディスパッチが`bot`と答えるレシーバーなし、`self.`、`Kernel.`、または`::Kernel.`での`loop`の呼び出しは、その通常完了に対して`untyped`（`StopIteration#result`の宣言された型）として型付けされなければならず（MUST）、`break`アームは通常通りそれにunion結合されなければなりません（MUST）。宣言された`bot`は、ブロックがパラメータを宣言しておらず、その本体がraiseしないことが証明可能な場合にのみ維持されなければなりません（MUST）。本体内のすべてのノードは、次のいずれかでなければなりません: 整数、浮動小数点数、有理数、または虚数のリテラル;展開のない文字列またはシンボルのリテラル; `nil`、`true`、`false`、または`self`;ローカル変数またはインスタンス変数の読み取り、またはプレーンな書き込み;スプラットのない配列リテラル; `if` / `unless` / `else` / `&&` / `||`;丸括弧;またはそのような引数を伴う`break` / `next` / `redo` / `return`。正規表現、範囲、ハッシュリテラル、`__FILE__`とその仲間、定数読み取り、複合代入（`x += 1`）、任意の呼び出し（演算子や`[]`を含む）、`yield`、`super`、スプラット、文字列展開、`rescue`を含むその他すべては拡大されます。`raise`も呼び出しであり、走査は`raise "x"`と`raise StopIteration`を区別しません。宣言されたブロックパラメータは、そのデフォルト（`|v = e.next|`）が各反復で実行されるため拡大されます。ブロック渡し（`loop(&blk)`）は検査する本体を持たないため、同様に拡大されます。

```ruby
loop { e.next }                 # untyped         (bot ではない)
loop { break 1 if e.next == 2 } # 1 | untyped     (使い果たしでも終了する)
loop { break 5 }                # 5               (本体は raise できない)
loop {}                         # bot
def drain(e) = loop { e.next }  # untyped を返す (bot ではない)
```

明示的なレシーバー（`obj.loop { ... }`）はprivateな`Kernel#loop`に到達できないため、その宣言された型が維持されます。ブロックのない`loop`は`Enumerator`であり、影響を受けません。上記の`tap`ルールの構文的走査も`loop`を非復帰として扱わないため、同じイディオムに対する2番目のガードのままです。

カタログはクロージャエスケープカタログと同様に組み込まれており、`RBS::Extended`呼び出しタイミング効果（[rbs-extended.md](../rbs-extended/)）がルールを変更することなくそれを置き換えられるように`(owner, method)`のペアを指定します。同じタイミングファクトのミューテーションおよびファクト保持の用途は、これによってカバーされません。

### より強いファクト保持のための証明義務

最初の実装では、より強いファクト保持のためにこれらの証明義務を使えます:

- ローカルバインディングが代入されておらず、エスケープするクロージャによって書き込み可能でない;
- 値が不変のシングルトンまたは即値（`nil`、`true`、`false`、シンボル、整数など）;
- 値が関連操作に対してfrozenであることが証明されている;
- 値が新たに割り当てられ、エスケープしておらず、それをミューテートまたは格納する可能性のある呼び出しに渡されていない;
- RBS、`RBS::Extended`、またはプラグイン効果が呼び出しがread-only、関連ターゲットに対して純粋、または特定のレシーバーまたは引数のみをミューテートすることを宣言している。

プラグインは`Scope`を直接ミューテートするのではなく、明示的なミューテーション、エスケープ、呼び出しタイミング、純粋性、または無効化効果を返すことができます（MAY）。バンドルスキーマは[rbs-extended.md](../rbs-extended/)にあります。

## スコープスナップショットとファクトバケット

最初の実装ではカテゴリー分けされたファクトストアと不変のエッジごとの`Scope`スナップショットを組み合わせます:

- 各`Scope`は制御フローエッジをキーとする不変スナップショットです。結合、ナローイング、無効化は、インプレースミューテーションではなく構造共有を通じて新しいスナップショットを生成します。
- スナップショット内では、ファクトは上記のカテゴリーを反映したバケットに分割されます: ローカルバインディング、キャプチャされたローカル、オブジェクトコンテンツ、グローバルストレージ、動的由来、関係的。無効化ルールは特定のバケットに作用するため、未知のメソッド呼び出しはオブジェクトコンテンツをスイープしながらローカルバインディングをそのままにします。
- 複数のターゲットにまたがる関係的ファクトは独自のバケットに存在し、参加しているターゲットのバケットが変更を記録すると無効化されます。
- `Scope`の公開サーフェスはバケットを直接公開してはなりません（MUST NOT）。プラグイン、ナローイングルール、診断はターゲットに関するファクトを`Scope`に尋ねます;バケットレイアウトは進化する可能性がある内部最適化です（MAY）。

## 純粋性ポリシー

プラグイン前の純粋性ポリシーは、メソッド呼び出し結果が再呼び出しを越えて記憶されるか忘れられるかを制御します:

- メソッドはデフォルトで**不純**として扱われます。レシーバーで不純なメソッドを呼び出すと、レシーバーのオブジェクトコンテンツバケットが無効化され、同じレシーバーへの以前の呼び出しで記憶された値ファクトが破棄されます。
- 純粋性は権威あるソースがそれを宣言した場合にのみ有効になります: Rigorと共に配布されるコアRubyとstdlibのRBS、受け付けられた通常のRBSファイル、または`RBS::Extended`の明示的な`%a{pure}`アノテーション。生成されたシグネチャとプラグインの貢献はそのティア内で純粋性をナローイングする場合があります（MAY）。純粋性アノテーションは`%a{pure}`——エコシステムの既存の綴りであり、`mutate.local`を許容する空のエフェクトエンベロープとして読まれる（[effect-labels.md](../effect-labels/)）。`rigor:v1:pure`はこの節が元々名指していた綴りだ;それは実装されることなく、`%a{pure}`を優先して廃止された（[ADR-103](../../adr/103-effect-labels/) WD14）。
- 設定スイッチにより、デフォルトがより「値を返すことは不純として宣言されない限り純粋」というPHPStanのポリシーに似た挙動になり、繰り返し呼び出しを越えてより強いナローイングを望むプロジェクトに対応します。スイッチはデフォルトを切り替えますが、明示的な`pure`またはミューテーション宣言をオーバーライドすることはありません。
- `pure`とレシーバーミューテーション、引数ミューテーション、またはファクト無効化効果を組み合わせることは契約（contract）の競合であり、[rbs-extended.md](../rbs-extended/)で指定されています。

## 組み込みミューテーションサマリー

最初のユーザー可視マイルストーン（v1）は、固定されたコアとstdlibクラスのセットに対して組み込みのミューテーション、純粋性、呼び出しタイミングサマリーを提供します。対象セットは`Array`、`Hash`、`String`、`Set`、`IO`、`StringIO`、`File`、`Tempfile`、`Pathname`、`Logger`です。各サマリーは以下を記録します:

- メソッドごとのレシーバーミューテーションステータス、引数ミューテーションステータス、ファクト無効化効果;
- 上記カテゴリーを使ったメソッドごとのブロック呼び出しタイミング;
- 過度の約束なしに行えるメソッドごとの純粋性宣言。

このセット外のクラスは、通常のRBS、`RBS::Extended`、またはプラグインファクトが別に述べるまで不純がデフォルトのポリシーに従います。Rigorはそれらの純粋性やミューテーション挙動を静かに仮定してはなりません（MUST NOT）。

先送りされたロードマップはカバレッジを追加コアクラス（`Numeric`とその子孫、`Symbol`、`Range`、`Regexp`、`Proc`、`Method`、`Time`、`Date`、`DateTime`）、広く使われるstdlib（`Date`、`JSON`、`URI`、`OpenStruct`、`Forwardable`、明示的なミューテーションサマリーが必要な`Comparable`を持つクラス）、および選択されたメタプログラミング隣接コアAPI（`Module`、`Class`、`BasicObject`）に拡張します。各追加は段階的に着地するため、より大きなサーフェスが着地する間も以前に出荷された挙動は乱されません。

組み込みミューテーションサマリーはクローズドリストではありません。それらを呼び出さないコードの意味を変えない限り、新しいエントリーはマイナーリリースで追加される場合があります（MAY）;公開されたロードマップは計画補助ツールであり、契約ではありません。

## プラグイン前のナローイングサーフェス

プラグイン前のナローイングサーフェスは、ユーザープラグインがロードされる前に、高度に`Dynamic[top]`なコードでRigorが生成するファクトのセットです。

この仕様は解析器が最終的にサポートする完全なプラグイン前サーフェスを記述します。最初のユーザー可視製品リリース（v1）はそのサーフェスのスコープされたスライス（slice）です;仕様を再定義するものではありません。ファクトバケット、ケイパビリティ（capability）ロールカタログ、組み込みミューテーションサマリーのような内部データ構造はv1から規範的です;ユーザーに公開される*導出ルール*はv1で絞られ、後続のリリースで広がります。

### v1ナローイングサーフェス

- `nil`、`true`、`false`、整数と文字列リテラル、信頼された組み込みドメインに対する等価チェックによって生成された有限リテラルユニオン（union、合併型とも）リファインメント（refinement、篩型とも）のリテラルナローイング。
- 構文レベルのガード: `is_a?`、`kind_of?`、`instance_of?`、`nil?`、真偽性、`respond_to?`、リテラルセットとの等価、および文をまたぐデータフローを必要としない`case`と`case/in`形式のクラスまたはパターンマッチングナローイング。
- ユーザープラグインを必要とせずにコアRubyと整理されたstdlibのサブセットにRBSまたは`RBS::Extended`を使うメソッド呼び出し解決。生成されたシグネチャ（`RBS::Extended`から）は参加する場合があります（MAY）。
- レシーバーが静的に既知の呼び出しサイトでバンドルされたコア/stdlibミューテーションサマリーを直接適用します。サマリーはバケット無効化をローカルに駆動します。
- 直線コード、ブランチ結合、ループ本体を越えたナローイングファクトの手続き内伝播（`0.1.x`ラインで出荷）。具体的な機構: 書き込み前読み取りの`nil`貢献、介在する / ミューテーション呼び出しによるファクト無効化、`retry`エッジの幅広げ、`receiver[key] ||= default`のインデックスナローイング、単一ホップのメソッドチェーンナローイング（`if x.last.is_a?(Array)`後の`x.last`）、インスタンス変数ガードナローイング（`return if @ivar.nil?`）。
- `FlowContribution`経由のプラグイン提供フロー貢献 — プラグインの`truthy_facts` / `falsey_facts` / `post_return_facts`がナローイングエンジンを流れる（ADR-9、v0.1.1以降）。

### 先送り

- メソッド本体からのケイパビリティロール*要件推論*（カタログと明示的な`conforms-to`ディレクティブはすでに利用可能;「本体が何のロールを必要とするか」の導出は先送り）;
- プラグイン提供のフロー貢献。

各v1.1サーフェスはフィーチャーフラグの後ろで提供されるため、より大きなサーフェスが着地する間もv1の挙動は安定したままです。

## バージョンガードの条件畳み込み

**バージョンガード（version guard）**は、API世代間を選択するために、実行中のRuby——またはRigorが読み取れるバージョン定数——をリテラルと比較する`if` / `unless`述語です。複数バージョンをサポートするライブラリはこの形状を日常的に持っています:

```ruby
if Gem::Version.new(Psych::VERSION) >= Gem::Version.new("3.1.0.pre1")
  ::YAML.safe_load(yaml, permitted_classes: permitted_classes)
else
  ::YAML.safe_load(yaml, permitted_classes)   # the Psych < 3.1 positional form
end
```

そのような比較の両辺が決定可能である場合、Rigorはガードを畳み込み、実行できないブランチ（arm）を**到達不能（unreachable）**として扱わなければなりません（MUST）: そのブランチは診断を生成してはならず（MUST NOT）、そのバインディングは`if`後のスコープに結合してはなりません（MUST NOT）——これは`if false`がすでに受けている扱いとまったく同じです。Rigorはガード自体に対して`flow.always-truthy-condition`（またはその他の冗長な条件に関する診断）を報告してはなりません（MUST NOT）: バージョンガードは意図的なものであり、それを報告してしまうと正しいコードに対して発火してしまいます。

基準値はアナライザーを実行しているRubyから読み取られます。これは`RUBY_VERSION`がナローイングされ、core/stdlib RBSがロードされるのと同じ前提です。畳み込み可能なセットは意図的にクローズドになっています:

- `<`, `<=`, `>`, `>=`, `==`, `!=`に対する`RUBY_VERSION <cmp> "x.y.z"`。比較は**String**のセマンティクスを使用しなければなりません（MUST）。なぜならそれが実行されるものだからです——Rubyは文字列を辞書順で比較するため、3.9上では`RUBY_VERSION >= "3.10"`は偽（false）となり、Rigorは理想化されたバージョン順序ではなくそれを再現しなければなりません（MUST）。
- `Gem::Version.new(a) <cmp> Gem::Version.new(b)`。両辺がラップされ、`Gem::Version`のセマンティクスで比較されます。*混在した*比較（片方がラップされ、もう片方が素のString）は畳み込んではなりません（MUST NOT）: `Gem::Version#<=>`は非`Gem::Version`オペランドに対してnilを返すため、実行時に比較が例外を発生させ、どちらのブランチも生存しません。
- `RUBY_ENGINE == / != "…"`。エンジン名に対する順序比較はバージョンガードではなく、畳み込んではなりません（MUST NOT）。
- `X::VERSION`。**実行中のRubyのデフォルトgem**に属する定数に対してのみ。プロジェクトが自身の`Gemfile.lock`を通じてバージョンを解決するgemは、アナライザーのランタイムから読み取ってはなりません（MUST NOT）。2つのコピーが異なる可能性があるためです。

**ルート化された（rooted）**表記は、むき出しの表記と同じ定数を指名します —— `::`はトップレベルのルックアップを明示的にするだけです —— したがって`::RUBY_VERSION`、`::RUBY_ENGINE`、`::X::VERSION`は`RUBY_VERSION`、`RUBY_ENGINE`、`X::VERSION`とまったく同様に畳み込まれなければなりません（MUST）。これは対象セットを拡大しません: 上記のセット外のルート化された名前は、むき出しの名前と同様に畳み込み不可能です。

それ以外のものはすべて両方のブランチを生存させたままにします。これは常に安全な回答です: `<=>`（評決ではなく順序を生成するため）、`RUBY_PLATFORM`（それに対するすべての比較は構築上プラットフォーム依存であり、チェックマシンが実行マシンである必要はないため）、`defined?`スタイルの機能プローブ、`!` / `&&` / `||`の合成、`case`の対象、および2つの素のStringリテラル間の比較（バージョンガードではなく定数比較）。読み取り不能なオペランドを持つガードは決定不能であり、その両方のブランチは生存したままでなければなりません（MUST）。

根拠と偽陽性の議論: [ADR-47](../../adr/47-narrowing-driven-clause-reachability/) § WD5。

## 診断

制御フロー解析から生まれる診断は主に`flow.*`ファミリーにあります。動的由来のprovenanceに依存するストリクトモードは`dynamic.*`ファミリーにあります。カットオフ診断は`static.*`にあります。完全な識別子分類体系は[diagnostic-policy.md](../diagnostic-policy/)にあります。
