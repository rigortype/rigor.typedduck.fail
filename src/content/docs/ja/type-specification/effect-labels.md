エフェクトラベル（effect label）は、型と並ぶRigorの第2の次元です: メソッドが何を返すかではなく、何を*する*か。この文書はラベル言語——文法、包摂関係、綴りを認識するレジストリ、それらを束縛するエンベロープ構文、そしてエフェクトサマリーの形——について規範的です。収集・伝播・エフェクトスナップショットのファイル契約はアナライザー内部であり、[`effect-summaries.md`](../../internal-spec/effect-summaries/)で仕様化されています;根拠は[ADR-103](../../adr/103-effect-labels/)、その背後の研究は[`docs/design/20260816-effect-labels.md`](../../design/20260816-effect-labels/)です。

この機能全体は**オプトイン**です: ここにあるものは、`.rigor.yml`に`effects:`ブロックを持たないプロジェクトには何の影響も及ぼしません。

語彙は兄弟のPHPアナライザーである[Steins](https://github.com/rigortype/steins)と共有されているので、`io.db`を名指すポリシーはPHPサービスに対してもRailsアプリケーションに対しても同じに読めます。

複合語は罠のある用語です（[`CONTEXT.md`](https://github.com/rigortype/rigor/blob/master/CONTEXT.md)）: **エフェクトラベル**（effect label）、**エフェクトサマリー**（effect summary）、**エフェクトエンベロープ**（effect envelope）。素の「エフェクト」は依然として`Rigor::FlowContribution`のフローエフェクトのバンドルを名指し、この機能にMUST NOT使われてはなりません。

## ラベル

ラベルは小文字のセグメントのドットパスです。

```
label   = segment { "." segment }
segment = [a-z] [a-z0-9]*
```

この文法は意図的に狭くしてあります。ラベルは大文字・アンダースコア・ハイフン・空のセグメント・先頭または末尾の区切り文字をMUST NOT含んではならず、セグメントは数字でMUST NOT始まってはなりません。`io`・`io.net.http`・`nondet.time`・`job.enqueue`はラベルです;`IO`・`io_net`・`io-net`・`io.`・`.io`・`io..net`はラベルではありません。

ラベルの**ルート**（root）はその最も外側のセグメントです。その**祖先**（ancestor）は真のドットパス接頭辞で、外側から順です（`io.net.http`は`io`と`io.net`を持ちます）。祖先関係は綴りの性質です;祖先が登録された行であることは要求しません。

この文法は構文的なゲートに過ぎません。レジストリが認識しない整形式のラベルは*未知*（unknown）であり、これは異なる扱いを持つ別の状態です（§未知のラベル）。

## 包摂

ラベル上の順序は**セグメントを考慮した接頭辞の包摂**（segment-aware prefix subsumption）です。ラベル`B`がラベル`L`を包摂するのは、`L`が`B`に等しいとき、または`L`が`B`に区切り文字を続けたもので始まるときです。

- `io`は`io`・`io.net`・`io.net.http`を包摂します。
- `io`は`iota`を包摂**しません**し、`mutate.self`は`mutate.selfish`を包摂しません: この関係はセグメント上のものであり、決して文字上のものではありません。実装は素の文字列接頭辞テストをMUST NOT使ってはなりません。
- 包摂は決して上向きに走りません: `io.net.http`は`io.net`を包摂しません。

包摂は反射的・反対称的・推移的なので、ラベルはそれによって順序づけられた森を成します。

### ラベル集合、∅と⊤

**ラベル集合**（label set）は、有限で、順序なしで、重複を除去したラベルの集合です。描画はソートされるので、スナップショットの差分は安定です。

- **結合**（join）は集合の和です。
- 集合`S`が境界`B`に**包摂される**のは、`S`のすべてのメンバーが`B`のいずれかのメンバーに包摂されるときです。`{io.net.http, io.db.read}`は`{io}`に包摂されます。
- **∅**、空集合は最下部です: エフェクトなし。あらゆる境界に包摂されます。
- **⊤**は無制限の読みです——「あらゆるエフェクト、または名前を付けられないエフェクト」。⊤はあらゆるラベルを包摂し、あらゆる結合を吸収し、⊤にのみ包摂されます。⊤は登録されたすべてのラベルの集合**ではなく**、列挙可能でもありません;それはタグの意味を確立できないときにタグが劣化する先です（§未知のラベル）。

## レジストリ

**レジストリ**（registry）は、認識されるラベルの綴りの閉じたリストに、引退した綴りの表とルート所有権の規則を加えたものです。データとして——`data/effects/registry.yml`——出荷されるので、プラグインとプロジェクト設定はRubyを変えずに語彙を拡張します。

ラベルが**既知**（known）であるのは、レジストリがそれを行として宣言しているとき、またはそれが宣言された行の祖先であるときです。したがって宣言された`io.net`は、`io`が自身の行を持たなくても`io.net`の祖先`io`を既知にするので、境界はデータファイルが決して綴らない内部ノードを名指してよいのです。逆は成り立ちません: 宣言された行の*子孫*は、宣言された境界が包摂によってそれを認めるとしても、その祖先が既知であるというだけでは既知になりません。

出荷されるレジストリは、共有ベースに3層を加えたものです:

| 層 | 内容 | 所有者 |
| --- | --- | --- |
| 共有ベース | Steinsのv1集合をそのまま: `exit`・`ffi`・`global.read`・`global.write`・`io`・`io.db`・`io.fs`・`io.fs.read`・`io.fs.write`・`io.input`・`io.ipc`・`io.net`・`io.net.http`・`io.output`・`io.output.buffer`・`io.output.header`・`io.output.stdout`・`io.output.stderr`・`io.process`・`io.signal`・`mutate`・`mutate.local`・`nondet`・`nondet.random`・`nondet.time` | SteinsとRigorが共同で;乖離は出荷前に上流へ提起される |
| Rubyの葉 | `mutate.self`（selfの状態）、`mutate.instance`（selfでもフレーム所有でもないレシーバー）、`mutate.static` | Rigor |
| 提案中の共有コアの葉 | `io.db.read`・`io.db.write`・`io.db.transaction` | Rigor、Steinsによる採用待ち |
| アプリケーション意味 | `telemetry`・`email.send`・`job.enqueue`・`cache.read`・`cache.write` | 共有;これらはポリシーが名指し`tolerated:`集合が掴むラベルなので、両アナライザーで同じにMUST綴られなければならない |

`io.output.buffer`と`io.output.header`は登録されていますがRubyでは生成されません: Steinsに対して書かれたポリシーがここでパースできるように存在します。

フレームワークルート（`rails.*`）はフレームワークをモデル化するプラグインが寄与し、出荷されるファイルの一部ではありません。

### ルート所有権

レジストリの拡張は**所有者**（owner）を名指します: プラグインid、ファーストパーティのプラグインがモデル化するフレームワークルート、あるいはプロジェクト自身の設定の場合は何もなし。追加される各ラベルは以下のいずれかをMUST満たさなければなりません:

- そのルートが拡張されるレジストリにすでに既知である——拡張は既存ルートの下の葉である;または
- そのルートが所有者と等しい——拡張は所有者自身のルートを開く;または
- 所有者がプロジェクトである。プロジェクトは任意のルートを開いてMAYよい。

これらのどれも満たさない追加ラベルは、診断ではなく拡張時のエラーです: 開こうとしているルートを所有できない拡張者には、正直に進む方法がありません。追加ラベルはラベル文法もMUST満たさなければなりません。

プロジェクトは`.rigor.yml`の`effects.labels:`で語彙を拡張します。そこにラベルを列挙することが保証行為です——それがプロジェクトだけが任意のルートを開いてよい理由です——そしてそれは、ラベルが判定されるあらゆる場所でその綴りを既知にします: `effect.unknown-label`、エンベロープの境界、帰属の値、`tolerated:`のいずれも。その**形**は設定のロード時に検証されます;それ以外については何も検証されません。

プラグインはマニフェストの`effect_labels:`で、その`effect_root:`が名指す所有者の下に拡張します。プラグイン層はプロジェクトの層より**前に**畳み込まれるので、プロジェクトはフレームワークの語彙を再宣言せずに、エンベロープや`tolerated:`でプラグインが開いたラベルを名指せます。拒否は拒否したプラグインのラベルだけを落とし、エフェクトレポート上で警告として表面化します——1つのプラグインの越権が別のプラグインの名前をMUST NOT奪ってはなりません。

> **執筆時点で実装済み**（[#387](https://github.com/rigortype/rigor/issues/387)）: プラグイン層。プラグインが名指すルートを開いてよいかは`Rigor::Plugin::FirstParty`——これはエンジン自身がバンドルするプラグインか——が決め、開いてはならないプラグインは警告付きで自身のidにちなんだルートを保ちます。マニフェストのフィールドは[`plugin.md`](../../internal-spec/plugin/) §エフェクトの寄与で仕様化されています。

### 語彙の進化

レジストリは`vocabulary`バージョンを運び、それを統治する規則は包摂から導かれます:

- **葉の追加は常に安全であり、バージョンをMUST NOTバンプしてはなりません**。認識された境界はそのメンバーのあらゆる子孫を認めるので、新しい`io.db.upsert`はすでに宣言された`io.db`の内側にあります。以前に受け入れられたプログラムが拒否されるようにはなりません。
- **ラベルのリネームまたは削除は破壊的であり、バージョンをMUSTバンプしなければならず**、古い綴りはその置き換えラベルとともにレジストリの`retired`表にMUST記録されなければなりません。引退した綴りに出会った読み手はそれが何になったかを知ります;認識されない綴りに出会った読み手は知りません。
- 引退した綴りは既知ではありません。未知のラベル（§未知のラベル）として読まれ、フェイルオープンで劣化します。引退表はその劣化を説明するために利用できます。
- 語彙バージョンは、永続化されたあらゆるエフェクト記録の同一性の一部なので、バージョンバンプはそれを黙って再解釈するのではなく無効化します。

## エフェクトサマリー

> **執筆時点で部分的に実装済み**。証明レーン・網羅性ビット・汚染原因は、`effects:`ブロックが存在するときは常に[#379](https://github.com/rigortype/rigor/issues/379)のコレクターによって計算され、`rigor effects`がそれを出力します;それらがどう生成されるかは[`effect-summaries.md`](../../internal-spec/effect-summaries/)です。その**カタログ化された**起点は、クラスごとの既定姿勢と引数依存のナローイングを伴う[#380](https://github.com/rigortype/rigor/issues/380)の手で監査された`data/effects/core.yml`から来ます;カタログの契約はアナライザー内部であり、[`effect-summaries.md`](../../internal-spec/effect-summaries/) §カタログで仕様化されています。**宣言レーン**には2つのプロデューサーがあります: Rigorが決して解析しなかったコードへの呼び出しに色を付けるプロジェクトの`effects.attribution:`表（[#385](https://github.com/rigortype/rigor/issues/385)、§帰属）と、[#386](https://github.com/rigortype/rigor/issues/386)の呼び出しサイトでのエンベロープのインポート（§呼び出しサイトでの宣言レーン）。[#381](https://github.com/rigortype/rigor/issues/381)のスナップショットはそれらをレビューされるファイルへコミットします;[#382](https://github.com/rigortype/rigor/issues/382)までは*実行間で*何もキャッシュされません。

**エフェクトサマリー**（effect summary）は1つのメソッドを記述します。2つのレーンと1つのビットを運びます:

- **証明**（proven）レーン——アナライザーがカタログ化された起点・言語構文・プロジェクトのメソッド本体から、推移的に確立したラベル集合;
- **宣言**（declared）レーン——具体的な呼び出し先は未知だがその宣言されたエンベロープが信頼されている呼び出しサイトで、上界（`≤`）としてインポートされたラベル集合;
- **網羅性ビット**（exhaustiveness bit）——メソッドが行ういずれかの呼び出しが解決できなかったとき偽。

**診断は証明レーンだけを読みます**。非網羅的なサマリーは「これらのエフェクト、そしておそらくそれ以上」と描画され、それ自体で発見をMUST NOT生んではなりません。これはエフェクトに適用されたロバストネス原則です（[robustness-principle.md](../robustness-principle/)）: 証明されたとおりに厳格に、決して恐れたとおりに厳格には。

**宣言ラベルは証明ラベルとまったく同じように呼び出しエッジを旅し**、同じ不動点へ単調です: メソッドの宣言レーンは、その本体自身が主張するものと、それが呼ぶすべてのものの宣言レーンを結合したものです。したがって帰属された`Net::HTTP.get`の2ホップ上のコントローラーは「そしておそらくそれ以上」だけでなく`≤ io.net.http`と読めます——呼び出しを行ったメソッドで止まる主張は、誰も問わない問いに答えることになります。2つのレーンは決して混ざりません: 宣言ラベルはいかなる距離でも証明レーンにMUST NOT入ってはならず、それが主張が発見を生むことを防ぐものです。

**描画規則**。サマリーが*出力される*場所——レポート、スナップショット、差分——では、同じサマリーの証明レーンがすでに認める宣言ラベルは落とされます: 証明レーンは厳密により多くを述べており、`[io.net] ≤ [io.net.http]`は1つのファクトがあるところに2つと読めてしまいます。この規則は出力にのみ適用されます;レーン自体は計算されたまま保たれます。さらなる結合が何が宣言されたかを見る必要があるからです。

サマリー内のすべてのラベルは**起点**（origin）——それが由来する呼び出し先または構文と、それに色を付けたソースの組——を運びます。起点は行を持たず、ポリシーの解消が操作する対象です;平坦なラベル集合はそれらの射影です。

### 汚染原因

網羅性ビットが偽のとき、サマリーはこの閉じたenumから理由を記録します:

| 原因 | 意味 |
| --- | --- |
| `dynamic-receiver` | レシーバーの型が`Dynamic`だったので、呼び出し先が未知 |
| `dynamic-send` | 非リテラルのセレクタを伴う`send` / `public_send` |
| `method-missing` | ディスパッチがアナライザーのモデル化しない`method_missing`に到達した |
| `unresolved-self-call` | プロジェクトが知る定義を持たない暗黙的self呼び出し |
| `opaque-callable` | アナライザーが本体まで追えなかったブロックまたはproc |
| `unknown-ownership` | レシーバーがフレーム所有であると証明できなかった変更呼び出し;その変更は証明された`mutate`ラベルではなく汚染として記録される |
| `plugin-attribution` | 信頼ティアが解消しないソースから寄与されたラベル |
| `template-not-analysed` | エフェクト単位でないテンプレートへのレンダーエッジ |
| `collector-error` | コレクターがこのメソッドで失敗し、そのサマリーを落とした |
| `budget` | 推論予算が走査を途中で打ち切った |

このenumは閉じています。新しい原因はこの文書への変更であり、プロデューサーの自由な選択ではありません。

> 執筆時点で`method-missing`・`template-not-analysed`・`budget`は予約済みで未生成です;他の7つにはプロデューサーがあります（`plugin-attribution`は[#385](https://github.com/rigortype/rigor/issues/385)以降、設定された帰属表から）。どの形がどの原因に到達するかは[`effect-summaries.md`](../../internal-spec/effect-summaries/) §汚染です。

## エフェクトエンベロープ

> **執筆時点で実装済み**（[#383](https://github.com/rigortype/rigor/issues/383)・[#385](https://github.com/rigortype/rigor/issues/385)・[#386](https://github.com/rigortype/rigor/issues/386)）: 両方のアノテーションの綴りはプロジェクト自身のRBS——その`signature_paths:`ツリーと、その`.rb`ファイルから導出されたrbs-inline / プラグイン合成のシグネチャ——から読まれ、`.rigor.yml`の規約の綴りは`effects.envelopes:`から読まれ、3つすべてが各メソッドの証明済みサマリーに対して`effect.envelope-exceeded`として、また各オーバーライドのものに対して`effect.liskov-widened`として、`effects.check`がオンのとき（`effects:`ブロックの下では既定でオン）は常にチェックされます。RigorがプロジェクトからロードしなかったRBS——rbs core、gemが出荷するシグネチャ——内のエンベロープは依然として決して*チェックされません*: チェック済み層はプロジェクト自身の宣言です（[ADR-103](../../adr/103-effect-labels/) WD6）。それは発見を生まない別の1つの目的のために読まれます: 呼び出しサイトでの`≤`境界のインポート（§呼び出しサイトでの宣言レーン）。

**エフェクトエンベロープ**（effect envelope）は、メソッドのエフェクトラベルに対する作者が宣言した上界であり、メソッドの*コード*——デッドコードとブロックリテラルを含む——に対して構造的にチェックされます。RBSの綴りは[rbs-extended.md](../rbs-extended/)の`RBS::Extended`の慣習に従います:

```
envelope = "%a{" "rigor:v1:effect" WS label-list "}"
label-list = label { "," label }
```

- ディレクティブのヘッドは、`assert`や`conforms-to`と同様に空白でペイロードから区切られます;ペイロードは素のラベルトークンのカンマ区切りリストです。
- リストはMUST NOT空であってはなりません——`%a{rigor:v1:effect}`は不正です。
- パーレンで囲んだコメント形式はありません。RBSには本物のコメントがあります。

```ruby
class UserRepository
  %a{rigor:v1:effect io.db}
  def find: (Integer) -> User

  %a{pure}
  def slug: (String) -> String
end
```

`%a{pure}`が**唯一の**純粋性の綴りです。空のエンベロープとして読まれ、`mutate.local`を許容します——メソッドは自身のフレームが確保し決して逃さないオブジェクトを自由に変更してよいのです。`rigor:v1:pure`は実装されておらず、言語の一部ではありません;[control-flow-analysis.md](../control-flow-analysis/) §純粋性ポリシーは`%a{pure}`を名指します。

1つの宣言上の`%a{pure}`と`%a{rigor:v1:effect …}`は矛盾します;`pure`が勝ち、その競合は既存の`RBS::Extended`の競合チャネルを通じて報告されます。

上位型のメソッド上のエンベロープはそのオーバーライドを束縛します: 実装は継承する境界より純粋であってよく、決して純粋でなくてはなりません（§Liskov包含）。

### エンベロープが束縛するもの

境界はメソッドの**証明**レーンに対して推移的にチェックされます: その本体自身、それが含むブロックリテラル、そしてそれが呼ぶすべてのプロジェクトメソッド。`%a{rigor:v1:effect io.db}`と宣言されたリポジトリの本体が`Net::HTTP`を呼ぶヘルパーを呼ぶなら、そのエンベロープを超えています。エンベロープはメソッドが何を*する*かについての契約であって、どの行がそれを綴るかについてではないからです。

3つの規則がこれが偽陽性の予算を使うことを防ぎます:

- **宣言レーンと網羅性ビットは読まれません**。すべての呼び出しを解決できなかったサマリーは「これらのエフェクト、そしておそらくそれ以上」と読めます;その*おそらく*は決して発見を生まず、証明されたものは依然として生みます。これは第2の次元に適用された「証明されたとおりに厳格に」（[robustness-principle.md](../robustness-principle/)）です。
- **`mutate.local`はあらゆるエンベロープに許容されます**。`%a{pure}`も含めて。
- **`effects.tolerated:`はラベルごとではなく起点ごとに解消します**（§ポリシーによる解消）。チェックが比較する対象は、証明レーン*からポリシーが解消するあらゆる起点バンドルを引いたもの*なので、ポリシーは起点全体を黙らせ、由来がどこであれラベルを黙らせることは決してありません。

境界が認めない証明ラベルは（メソッド,ラベル）ごとに1つの`effect.envelope-exceeded`診断であり、`.rbs`の行ではなく**Rubyの`def`に位置づけられます**——そこが修正の入る場所であり、`# rigor:disable`が読まれる場所です。メソッドがRubyの`def`を持たない場合（クラスレベルの分配で到達される合成された`attr_*`アクセサ）、位置はクラス自身のファイルへフォールバックします。メッセージはラベル、それを証明する起点への最短経路、作者自身の境界の綴り、そしてその境界が書かれた場所を名指します;識別子の分類体系とその重大度は[diagnostic-policy.md](../diagnostic-policy/)です。

このチェックは、設定が`effects:`ブロックを運び、**かつ**`effects.check`が`false`でないときにのみ走ります;`effects.check`は存在するブロックの下では既定でtrueです。`effects:`ブロックのないプロジェクトでの`%a{pure}`は不活性です——静かな既定サーフェスでそれをチェック済みの契約として読むと、既存のアノテーションが失敗し始めてしまいます（[ADR-50](../../adr/50-release-engineering-and-stability-strategy/) WD1）。

### クラスレベルの分配

クラスレベルのエンベロープは、発見が知るそのRubyクラスのすべてのメソッド——再オープン、他ファイルでの定義、合成された`attr_*` / `define_method`メンバーを含む——に分配されます。サブクラスへは分配**されません**。モジュール上では、そのモジュール自身のメソッドのみに分配されます。メソッドレベルのエンベロープは分配されたクラスレベルのものに勝ちます;最近接が勝ち、`-except`構文は必要ありません。

### 規約によるエンベロープ

エンベロープは`.rigor.yml`に書くこともでき、1つのメソッドを名指すのではなくパスまたは名前空間でクラスを選択します:

```yaml
effects:
  envelopes:
    - match: "app/presenters/**/*.rb"     # presenters do not query
      effect: []
    - namespace: "Policies::*"
      effect: [mutate.local]
```

エントリーは`match:`または`namespace:`の**ちょうど1つ**をMUST名指さなければならず、`effect:`リストをMUST運ばなければなりません——`effect: []`は空のエンベロープであり、`effect:`の欠落はロード時のエラーです。不正なセレクタやラベルも同様です。

- `match:`は、そのメソッドのいずれかを定義する**いずれかの**ファイルがglobにマッチするとき、そのクラスを選択します。`FNM_PATHNAME`付きの`File.fnmatch?`、プロジェクト相対なので、`**`がディレクトリ境界を越える唯一の方法です。
- `namespace:`は完全修飾名でクラスを選択し、セグメントごとにマッチします: `*`はちょうど1セグメントにマッチし（`Presenters::*`は`Presenters::User`を選択し、`Presenters::Admin::User`も素の`Presenters`も選択しない）、`**`は1つ以上にマッチし（`Presenters::**`は両方を選択する）、セグメント内の`*`はその内部でマッチします（`Api::V*`）。

選択されたクラスは、そのエントリーの境界を**クラスレベルのアノテーションが分配するのとまったく同じように**受け取ります——発見が知るすべてのメソッド、それ自身の資格で選択されない限りサブクラスは決して。優先順位は最近接優先で、設定はメソッドから最も遠いものです:

> メソッドごとのアノテーション**>**クラスレベルのアノテーション**>**設定エントリー

設定エントリーの中では、クラスを選択する**最初の**ものがそれを束縛します;リストは上から下へ読まれ、後のエントリーが上に書かれたものを黙って上書きすることは決してありません。したがってメソッドは高々1つのエンベロープを、ちょうど1つのソースから持ち、境界のマージはありません。診断はそのソースを`.rigor.yml effects.envelopes[N]`として名指し、Rubyの`def`に位置づけられたままです。

エントリーの`effect:`内の認識されないラベルは、エントリー全体を⊤に劣化させ、`.rigor.yml`に位置づけられた`effect.unknown-label`として表面化します。アノテーションに対するのとまったく同じです（§未知のラベル）。

### Liskov包含

エンベロープはメソッドについての契約であり、`class PgRepo < Repo`は`PgRepo`が`Repo`が使えるどこでも使えると言っています。したがって`Repo#find`に書かれた境界は`PgRepo#find`も束縛します:

> オーバーライドは、それがオーバーライドするメソッドに書かれたエンベロープからMUST NOT逃れてはなりません。実装は継承する境界より純粋であってよく、決して純粋でなくてはなりません。

オーバーライドが継承するエンベロープは、**自身のメソッドキーがエンベロープを運ぶ最近接の祖先**について、メソッド自身のエンベロープが解決されるのと同じ3層と同じ最近接優先の優先順位で解決されたものです。オーバーライドにより近く書かれた境界はそれについてのより具体的な言明であり、祖父の境界はすでにその間の親を束縛しています。

違反は（オーバーライド,超過ラベル）ごとに1つの`effect.liskov-widened`であり、**オーバーライドのRubyの`def`に位置づけられ**、ちょうど2つの方法のいずれか一方で——決して両方ではなく、したがって1つのラベルが1行で2つの診断を生むことは決してありません——生じます:

- **オーバーライドが自身のエンベロープを宣言していない**。そのとき、それが*すること*が継承した境界が認めなければならないものであり、`effect.envelope-exceeded`が読むのと同じレーンに対して判定されます: 証明されたクロージャ、ポリシーごとに解消され、`mutate.local`は許容、汚染は無視。
- **オーバーライドが自身のエンベロープを宣言している**。そのとき比較は2つの作者が書いた境界の間で行われ、**証明とは独立**です: 継承したものより広い宣言された境界は、本体が何をすることになろうと、宣言におけるLiskov違反です。本体が何をするかはすでに`effect.envelope-exceeded`の問いであり、オーバーライド自身の境界に対して問われます。

2つの制限がこれを受け入れられた構成の内側に留めます:

- **両側が作者による**。誰かがオーバーライドされるメソッドにエンベロープを書かない限り何も発火しません;オーバーライドだけでは決して発見を生めません。これは`def.override-*`ファミリーが使うのと同じ両側作者の構成です（[ADR-35](../../adr/35-override-signature-compatibility/)）。
- **名前的なサブクラス化のみ**。includeされたモジュールのメソッドは、includeする側自身の`def`によってオーバーライドされません: Rubyの祖先はincludeする側のメソッドをモジュールのものの下ではなく*前に*置き、この規則を正当化する置換可能性の論法はサブクラスのものです。prepend、`extend`、refinementも同様に対象外です。

### 呼び出しサイトでの宣言レーン

具体的な呼び出し先が未知の呼び出しでも束縛されうるのは、それが呼ばれる*対象*が何をするかを宣言しているからです。それが成り立つ場所では、呼び出し先の境界は呼び出し元の**宣言**レーンに`≤`として、証明レーンには決して、呼び出し先を名指す起点の下で結合されます（§エフェクトサマリー）。

**キャリアは名前的です**。ルックアップは、アナライザーが射影したレシーバーの*静的な*クラスによって——暗黙的self呼び出しでは、呼び出すメソッドが定義されているクラスによって——行われ、祖先を歩きません: `PgRepo`と型付けされたレシーバーは`Repo#find`の境界をインポートしません。`PgRepo#find`がその呼び出しが到達する定義だからです。構造的インターフェースはキャリアではありません: RBSのインターフェース型は`Dynamic[top]`へ消去され、境界を付ける先を持たないので、インターフェース型のレシーバーを通じた呼び出しは何もインポートしません（[structural-interfaces-and-object-shapes.md](../structural-interfaces-and-object-shapes/);この読みは構造的キャリアとともに到来します）。層はエンベロープの層に1つ加えたもので、最近接から:

> メソッドごとのアノテーション**>**クラスレベルのアノテーション**>** `effects.envelopes:`エントリー**>**受け入れられたシグネチャ

**受け入れられたシグネチャ**（accepted signature）とは、プロジェクトが書かなかったRBS——gemが出荷するシグネチャ、Rigorのバンドル済みオーバーレイ——が運ぶエンベロープで、プロジェクトのソースからではなく構築されたRBS環境から読まれます。それは決してチェックされません。チェックする本体がないからです;それが行うのは、解析されないコードへの呼び出しが何を約束するかを述べることであり、それはそのファイルの*型*にすでに拡張されているのと同じ信頼です。

`effects.envelopes:`エントリーは`namespace:`で選択するときに参加します。`match:`エントリーは参加しません: パスのglobはクラスがどこで*定義されているか*についてのファクトであり、ファイルごとの収集ウィンドウはそれに答えられません。それでも、選択したクラスのメソッドを、エンベロープチェックとLiskov包含のために束縛します。

**解消**。このように束縛された呼び出しサイトは**エンベロープによって網羅的**です: 汚染を寄与せず、閉世界が知るプロジェクト定義へのエッジを保ちます。それが[ADR-103](../../adr/103-effect-labels/) WD6の信頼の階梯です——プロジェクトが著したエンベロープは契約チェックとLiskovチェックを受け、受け入れられたシグネチャの型はすでに信頼されている——ので、アナライザーが`Dynamic`としか型付けできなかったレシーバーは、それが名指すクラスがその境界を宣言しているなら「呼び出し先未知」ではありません。2つの層は解消**せず**、ここでもインポートしません: `effects.attribution:`（§帰属）とサードパーティプラグインのマニフェスト表。どちらも何もチェックしていないコードについての主張であり、どちらも`plugin-attribution`の汚染を保ちます。

⊤と読まれるエンベロープは何もインポートせず、何も解消しません。束縛をやめたタグが黙って呼び出しサイトの網羅性を買い戻してはなりません。

## 帰属

gemのメソッドにはRigorが解析する本体がないので、誰かがそれに色を付けなければなりません。`effects.attribution:`はそのためのプロジェクト自身のチャネルです:

```yaml
effects:
  attribution:
    "Net::HTTP.get": [io.net.http]
    "Logger#info": [telemetry]
```

キーはシンボルテーブルが綴るとおりのメソッドキー——`Owner#instance_method`または`Owner.singleton_method`——であり、他の形のキーはロード時のエラーです。所有者とセレクタがマッチする呼び出しは、そのキーの起点の下で、エントリーのラベルを**呼び出し元の宣言レーン**に寄与し、そのサイトに`plugin-attribution`の汚染を残します。

3つの性質が導かれ、それらがこのチャネルの要点のすべてです:

- **帰属されたラベルは決して証明レーンに入りません**。診断は証明レーンだけを読むので、何を主張しようと、帰属のせいでエンベロープが発火することはありえません。
- **帰属は決して汚染を解消しません**。それはアナライザーが読まなかったコードについての未チェックの主張なので、サマリーは「これを宣言した、そしておそらくそれ以上」と読めます（[ADR-103](../../adr/103-effect-labels/) WD6）。ファーストパーティプラグインのフレームワーク由来の帰属は別の、より高いティアであり解消します;プロジェクトのYAML表は解消しません。
- **主張は伝播します**。宣言レーンは呼び出しエッジを旅する（§エフェクトサマリー）ので、帰属された呼び出しに到達するあらゆる呼び出し元は同じ`≤`境界を読みます——レポートでも、スナップショットの`reach:`表でも。`methods:`は各メソッド自身の主張を保つのでその差分は帰属可能なままです。
- **レジストリが知らないラベルは拒否されず報告されます**。帰属は書かれたとおりに立ちます——汚染がすでにその読みが不完全であると述べています——そして`effect.unknown-label`が語彙がそれを説明できないと述べます。

### プラグイン層

> **執筆時点で実装済み**（[#387](https://github.com/rigortype/rigor/issues/387)）: プラグインの帰属とプラグインのフレームワークエッジ。[ADR-103](../../adr/103-effect-labels/) WD10のRails語彙全体がその上に構築されています。マニフェストのサーフェスは[`plugin.md`](../../internal-spec/plugin/) §エフェクトの寄与;テーブルがどうコンパイルされ参照されるかは[`effect-summaries.md`](../../internal-spec/effect-summaries/) §プラグイン層です。

フレームワークをモデル化するプラグインは、そのマニフェストの`effect_attributions:`を通じて、または出荷するRBS内の`%a{…}`アノテーションを通じて、そこへの呼び出しを帰属させます。どちらも`effects.attribution:`とまったく同じように**宣言**レーンに着地します。異なるのは汚染であり、それはチャネルではなく[ADR-103](../../adr/103-effect-labels/) WD6の階梯に従います:

| 寄与者 | サイトでの汚染 | 読み |
| --- | --- | --- |
| **ファーストパーティのバンドル済み**プラグインの`discharge: true`行、またはその出荷RBS内のアノテーション | なし | 「これがそれのすること」——受け入れられたシグネチャのティア |
| 他のあらゆるプラグイン、およびプロジェクト自身のYAML表 | `plugin-attribution` | 「これを宣言した、そしておそらくそれ以上」 |

解消する行はまた**サイトを束縛します**: `dynamic-receiver`・`unresolved-self-call`・レシーバー変更に対する所有権の判定はすべて、その呼び出しが何をするかの信頼された言明によってすでに答えられており、その隣の汚染はどんなアノテーションも決してクリアできないものになってしまいます。それでも行は`template-not-analysed`または`opaque-callable`の明示的な汚染をMAY運んでよいです——フレームワークモデルが正直に見られない2つのものです。

プラグインは**エッジ**も寄与します: 呼び出しサイトの構文が含まない、フレームワークが行う呼び出しです。`save`はクラス本体のコールバックとバリデータを走らせ、`Job.perform_now`は`Job#perform`を走らせ、`UserMailer.welcome(u)`は`UserMailer#welcome`を走らせます。プラグインがMUST NOT寄与してはならないのは`perform_later`から`perform`へのエッジです（§エフェクトサマリー、遅延実行）: 本体は別のプロセスの別のスタックで走るので、呼び出し元のコードはそれを含みません。利用可能な戦略はそれの綴りを持たない閉じたenumです。

プラグインの**トランスポート**行は、それが読むプロジェクトのファクトによってMAY絞ってよいです: ActiveJobのエンキューは引数を見ない素の`io`、宣言されたSolid Queueアダプタの下では`io.db.write`、Sidekiqの下では`io.net`。これは引数依存のナローイングの設定レベルの双子であり、読まれていない、または環境ごとの宣言は正直な上界を保ちます。

## ポリシーによる解消

`effects.tolerated:`は、プロジェクトが対処しないと決めたラベルを列挙します。差分または境界が**判定される**ときに適用され、ファクトが記録されるときには決して適用されず、**起点ごとに**操作します:

> バンドルは、そのラベルの**いずれか**が許容されたときに解消される。

起点は1つの呼び出し先または1つの構文であり、そのラベルはその1つのものが行うことです——したがって起点が*何のため*だったかを許容することは、それに付随して来たトランスポートを解放します。`Logger#info`は1つのバンドルで`io` + `telemetry`です: `tolerated: [telemetry]`はそれを丸ごと解消します。そのバンドル内の`io`*こそが*ロギングだからです。同じ本体内の`File.read`は別のバンドルを持つ別の起点であり、その`io.fs.read`は依然として数えられます。解消された起点と解消されない起点の両方を通じて到来するラベルは生き残ります。解消されないほうがそれ単独で証明するからです。

4つの不変条件がポリシーを統治し、それぞれが別々のコミットメントです:

1. **記録は未解消である**。エフェクトスナップショットはアナライザーが証明したものを保持します;`rigor effects update`はポリシーが何と言おうと同じバイト列を書きます。
2. **ポリシーは1箇所にある**。`.rigor.yml`の`effects.tolerated:`であり、サイトごとの抑制に散在しません。
3. **監査スイッチが存在する**。`rigor check`とスナップショットの動詞上の`--no-tolerated-effects`は、空の許容集合で同じ判定を走らせるので、ポリシーが隠すものは常に見えます。それは判定だけを変え、他は何も変えません——収集も、記録も、キャッシュの同一性も。
4. **出力は未解消の集合を使う**。アノテーションとして書き出されるサマリー（`sig-gen`）は、コードが何をするかを述べなければならず、プロジェクトが無視することに合意したものを述べてはなりません。

エンベロープチェックでは解消は推移的に適用されます: 境界が比較される対象は、証明されたクロージャからあらゆる解消された起点バンドルを引いたもので、起点自身のメソッドで計算され、証明レーン自体と同様に呼び出しエッジに沿って伝播されます。スナップショットの差分では、**追加された**ラベルはそれを導入するあらゆる起点が解消されるときちょうど許容されます;**削除**はラベルで判定されます。それを生んだ起点はもはや参照できるように存在しないからです。

## 未知のラベル

> **執筆時点で実装済み**（[#384](https://github.com/rigortype/rigor/issues/384)・[#385](https://github.com/rigortype/rigor/issues/385)）: ⊤への劣化、宣言（RBSおよびrbs-inline）とあらゆる`.rigor.yml`のラベルサーフェス——`effects.tolerated:`・`effects.envelopes[].effect`・`effects.attribution:`の値・`effects.labels:`——での意図でゲートされた`effect.unknown-label`、そして`effect.annotations-unchecked`の残余。

レジストリが認識しない整形式のラベルは**タグ全体を⊤として読ませ**MUSTなりません——決してその認識された部分集合ではなく。

これはフェイルオープンであり、唯一の安全な読みです。`io.db`のつもりで`io.bd`と書いた作者のタグは、アナライザーが束縛できないメソッドを記述しています;境界をたまたま認識したラベルへ絞ると、タイポが正しいコードへの発見に変わってしまいます。⊤へ広げることは代わりに発見を抑制し、それが偽陽性の予算が組まれている方向です（[ADR-5](../../adr/5-robustness-principle/)）。

同じ規則が引退した綴りと、プラグインが登録すると期待されたが登録しなかったラベルにも適用されます。

この劣化は診断と対になっています。黙って束縛をやめた境界はまさに、フェイルオープン規則が隠すことを許してはならない種類のものだからです。`effect.unknown-label`はそれを**宣言で**報告します——`.rbs`の行、rbs-inlineアノテーションなら`.rb`の行、設定に書かれたラベルなら`.rigor.yml`——存在すれば最も近い認識された綴りを名指し、その宣言が今や何も束縛しないと述べます。それは決して境界を変えず、`effect.envelope-exceeded`と同じ`effects.check`スイッチに乗ります: エンベロープの強制にオプトインすることが、強制が止まったと述べる診断をオンにするものです。

これは**ラベルの意図が明らかな**場所でのみ、4つのシグナルのいずれか1つから発火します: 綴りが認識されたラベルから小さい編集距離内にある;同じリストの別のメンバーが認識されている;トークンが2つ以上のドット区切りセグメントを運ぶ;またはレジストリの引退表がそれを名指す（この場合は推測の代わりに置き換えが名指されます）。単独の遠く離れた語（`%a{rigor:v1:effect database}`）はどれにもマッチせず、どこでも沈黙のままです——語彙は構成上開いている（`effects.labels:`、プラグイン自身のルート）ので、何にも似ていない素の語は、綴り間違いであるのと同じくらいこのプロジェクトが登録していないラベルである可能性があり、両方を報告すると意図としては正しいコードに発見を置いてしまいます。この沈黙は診断についてだけです: タグはいずれにせよ⊤と読まれます。

この識別子は`effect.liskov-widened`とともにSteinsと共有されています;識別子の分類体系と重大度は[diagnostic-policy.md](../diagnostic-policy/)です。

**`effects:`ブロックのないアノテーション**。エフェクトアノテーションは決して収集をオンにしません——それは1つのシグネチャファイルの1行がプロジェクトのあらゆる実行をより高価にすることを許してしまいます。同様に決して黙って不活性でもありません: 自身のシグネチャが`%a{pure}` / `%a{rigor:v1:effect …}`を運びながら`.rigor.yml`が`effects:`ブロックを運ばないプロジェクトは、実行ごとに1つの`effect.annotations-unchecked` `:info`を、最初のそのようなアノテーションに位置づけて受け取ります。`effects: {}`と`effects: {check: false}`はどちらも意図的な答えであり、それを黙らせます。

## エフェクトスナップショット

> **執筆時点で実装済み**（[#381](https://github.com/rigortype/rigor/issues/381)）: `rigor effects update` / `check` / `diff` / `explain`、`effects.snapshot.{path,reach,gate}`、そして最小限の`effects.tolerated:`。ファイルのレイアウト、その省略規則、差分カテゴリー、ゲートの意味論はアナライザー内部であり、[`effect-summaries.md`](../../internal-spec/effect-summaries/) §スナップショット文書で仕様化されています。エントリーポイントの**プリセット**はフレームワークをモデル化するプラグインが`effect_entry_points:`マニフェストフィールド（[#387](https://github.com/rigortype/rigor/issues/387)）を通じて名前を付け、`effects.snapshot.reach:`で名前によって採用されます。rigor-railtiesは`rails`（コントローラーアクション、ジョブの`perform`、メーラーアクション、チャネルのコールバック）を出荷し、各Railsコンポーネントプラグインは自身のスライスを出荷します。プラグインは検証されている設定*から*ロードされるので、`reach:`の名前は設定ロード時に**形**を、スナップショットが構築されるとき——登録された集合が完全になる最初の時点——に**存在**をチェックされます。

エフェクトフットプリントが検証される主たる方法はエンベロープではなくコミットされた記録です: `.rigor-effects.yml`は各メソッドの*直接*サマリーと宣言されたエントリーポイントでの推移的リーチを保持し、その差分はレビューされ、そのドリフトをCIゲートが報告します。そのヘッダーは上で定義した語彙バージョンを運ぶので、語彙のバンプは記録を再解釈するのではなく失効させます。スナップショットは診断を出さず、`rigor check`のストリームに決して入りません。

記録は**未解消**です: アナライザーが証明した集合を保持し、`effects.tolerated:`は差分が*判定される*ときに適用され（§ポリシーによる解消）、記録が書かれるときには決して適用されません。ポリシーを適用してファイルを書くと、それはポリシーの関数になり、ポリシーの変更がコードが何をするかの変更と区別できなくなります。
