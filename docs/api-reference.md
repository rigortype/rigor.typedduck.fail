# API reference integration

The site consumes ZARD's experimental `zard-doc/v0`, revision 1 export. `api-reference.config.json` selects an explicit documentation scope and source mapping; initially this is Rigor's plugin base API. No Rigor lens invocation or inferred signature is required.

## Ownership

The `zard-doc-astro` package in the ZARD repository owns export validation, route mapping, safe prose and semantic HTML. Its separate `zard-doc-astro/starlight` adapter owns frontmatter and sidebar-topic conversion. Neither ships CSS or depends on this site's theme.

This site owns `src/styles/api-reference.css`, source selection and acquisition, Rigor-specific copy and GitHub provenance, Japanese fallback policy, output publication and deployment. `scripts/api-reference/presentation.mjs` supplies these product choices to the package. Generated declaration markup does not live in this repository.

Until npm publication, `vendor/zard-doc-astro-0.0.0.tgz` is an explicit package snapshot installed through a relative `file:` dependency. Its origin and refresh procedure are recorded in `vendor/README.md`. Builds require no sibling ZARD checkout for the presentation package. The optional Ruby JSON producer is still selected separately through `ZARD_SOURCE_DIR`.

## Generate locally

Initialize `upstream/rigor` using the existing non-recursive submodule workflow. Install the ZARD checkout's Ruby dependencies, then run:

```sh
ZARD_SOURCE_DIR=/absolute/path/to/zard RUBY=/absolute/path/to/ruby pnpm sync:api
pnpm build
pnpm preview
```

`RUBY` defaults to `ruby` and must satisfy ZARD's Ruby requirement. `RIGOR_API_SOURCE_DIR` can select another clean Rigor checkout; it defaults to the site's pinned `upstream/rigor` submodule. Only the source mappings in the checked-in configuration are exported. The generator does not recursively initialize submodules or load the documented application. Rigor is executed only with the optional lens setting below.

`ZARD_SOURCE_DIR` is an explicit opt-in while JSON export remains unreleased. It invokes that checkout's executable, records the producer gem versions, ZARD commit and a digest of its Ruby implementation files. The implementation digest distinguishes a local producer with uncommitted changes from the same nominal gem version. Rigor source files must be clean and match their recorded SHA-256 digests; pages identify the pinned Rigor commit.

The generated `src/data/api-reference.json` contains the producer export plus site build provenance. It and the English/Japanese generated content trees are git-ignored. `sync:all` regenerates API pages after the other documentation sync tasks, using the artifact when no producer checkout is configured. Changing the selected mappings, source commit or selected file contents requires regeneration from the producer; stale inputs fail the build rather than silently publishing old data.

## Build from an explicit artifact

An environment with a prepared artifact can use:

```sh
ZARD_API_JSON=/absolute/path/to/api-reference.json pnpm build
```

Use the complete site artifact generated by `sync:api`, not an unwrapped raw ZARD export: it carries the Rigor commit and source-selection digest required for validation. The matching clean Rigor checkout must also be available. The generator validates schema/revision, publication visibility, source provenance, declaration/page associations, exported link anchors and route collisions before replacing content. Publication failures attempt to restore the previous generated pages and artifact, retaining the backup if recovery fails.

If neither input is configured and no generated artifact exists, local builds omit the API topic and pages. PR and production workflows explicitly enable generation through `.github/actions/setup-api`: it checks out a full pinned ZARD commit, installs Ruby 4.0 and exactly Prism 1.9.0, and sets `ZARD_SOURCE_DIR`. Lens is disabled by default. Both workflows build real API pages and run `pnpm check:api`; missing API output or broken generated links stop publication. Update the pinned producer commit deliberately alongside any export consumer changes.

## Optional released lens

```sh
RIGOR_LENS=1 RIGOR_COMMAND=/absolute/path/to/rigor \
  ZARD_SOURCE_DIR=/absolute/path/to/zard pnpm sync:api
```

This requires the checkout's optional `zard-rigor` dependencies and a standalone
Rigor 0.4.5 executable. Older producer exports are rejected; regenerate them with 0.4.5. `RIGOR_LENS_CONFIG` defaults to `.rigor.dist.yml`, relative
to the documented Rigor root. The CI setup action offers the same opt-in with
`with: { lens: '1' }`, installing Rigor 0.4.5, RBS 4.2.0, Prism 1.9.0,
language_server-protocol 3.17.0.6, rbs-inline 0.14.0 and digest-xxhash 0.2.9.

The adapter validates experimental `lens/v0` revision 1, source snapshots and
exact declaration bindings. The package renders member signatures separately
from each definition's body return, preserving dynamic/unavailable states.
CSS remains in this consumer. A failed analysis prevents publication and leaves
the previous artifact/pages intact. Enriched artifacts require fresh analysis
on every generation; `inputs` is not a complete dependency graph and an explicit
`ZARD_API_JSON` is therefore supported only for plain exports.

Rigor 0.4.5 handles the selected source and emits readable declared block types.
The previous trailing-comma assignment and block object-display failures are
resolved in the supported executable. Type display text remains producer output.

## Browsing and coverage

API pages include native disclosure groups linking each member to its exact
definition. Repeated definitions keep separate anchors and source-line labels.
The producer's optional written `relationships` add a hierarchy link within
each documentation scope, superclass/mixin references and reverse documentation
links. Class trees and module usage are separate. Unresolved expressions,
conflicting written parents and cycles remain explicit; effective inherited
members and runtime lookup are not inferred. Older exports retain their routes.

When lens is enabled, coverage summaries distinguish omitted constructs,
failed targets, absent capabilities and unmatched declarations from dynamic
types. Producer/schema support and the CI default release are selected by the
pinned ZARD checkout's `zard-rigor/lib/zard/rigor/compatibility.json`; changing
that manifest still requires verifying the released executable. Site CI reads
the manifest rather than maintaining a second analyzer version pin. Type facts
are enabled in CI/deployment with the reviewed Rigor 0.4.5 executable and pinned v0.4.5 source. Local generation can still omit `RIGOR_LENS=1` for a plain export. Constant value slots, aliases and module functions use only producer facts; absent capabilities remain explicit.

## Source links

The optional `sourceLinks.template` in `api-reference.config.json` maps declaration IDs to immutable source URLs in the generated artifact's `source.links`. Supported substitutions are `{commit}`, `{path}`, `{start_line}` and `{end_line}`; commit, path and start_line are required. The commit is always the validated Rigor checkout commit. Paths are selected repository-relative files, encoded segment by segment; absolute/escaping paths, unknown substitutions and credential-bearing URLs are rejected. Templates perform literal substitution only, never expression evaluation. A missing line range produces readable source metadata without a fabricated link. All retained definition sites get their own line/range destination. Omit this setting to generate without source links. Changing the template requires artifact regeneration.

## Routes and presentation

- `/apiref/` lists documentation scopes and declaration counts.
- `/apiref/<scope-destination>/` groups declarations by class, module, constant, attribute, instance method and singleton method.
- Each namespace page uses the logical ZARD page path after the site's existing slug normalization, and retains ZARD declaration anchors. Collisions caused by normalization are errors.
- `/ja/apiref/` explicitly directs readers to the English API. Starlight supplies its normal fallback notice for untranslated namespace routes. Sidebar links target the English source pages.

The API topic reuses Starlight's header, themes, responsive sidebar, collapsible groups, Markdown rendering and shared Pagefind search. Breadcrumbs and declaration entries use the existing Rigor tokens recorded in `DESIGN.md`. No client framework is added.

Repeated definitions retain separate source anchors; source text is not interpreted as runtime ownership or an inferred signature. Documentation lines are joined using their source spans before Markdown rendering. Conventional two-space-indented Ruby comment example blocks are treated as literal code, retaining indentation, quotes and blank lines. Source-supplied HTML is converted to text, code spans/blocks remain code, unsafe or unresolved links become readable text, and recognized API links are mapped to actual routes. Original contracts and documentation claims remain in the artifact, separate from displayed API prose.

## Validation

```sh
pnpm test:api
pnpm check
pnpm build
pnpm check:api
```

The package tests cover incompatible schemas, private declarations, escaped paths, missing link targets, slug collisions, repeated definitions, source-HTML injection, code preservation and multiline prose. Run them with `pnpm --dir zard-doc-astro test` in the ZARD repository. Site tests exercise the installed archive's routes, product provenance, Japanese entry and rejected-artifact publication behavior. Browser QA additionally verifies the real generated API, source anchors, navigation, theme switching, mobile layout and the Japanese fallback. Native disclosures keep documentation readable without JavaScript. The enhanced member-order selector sorts the index and declaration groups by source or name while preserving anchors and open states. Custom symbol search and version selection remain separate backlog slices.
